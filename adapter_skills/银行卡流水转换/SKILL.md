# 银行卡流水（平台统一 41 列）→ 资金事实行

把一份银行卡流水整份转换成 openhive 的 `FactRowInput[]`（`result.json`）。
这个技能绑定的是**平台「调取证据」导出的统一 41 列表头**，不是「任意银行导出」的通用解析器；
换一套表头就先改 `adapter.json` 的匹配列，再重测。

三家样本（招商/民生/另一家）的表头逐字相同，字段语义也相同：平台已经把各行的
「本方 / 对方」拆成独立列，不需要像微信流水那样先按借贷分「方」。

## 0. 契约（以仓库代码为准，不以旧文档为准）

内核 `packages/opencode/src/server/openhive/case-converter-runner.ts` 现在的调用方式是：

```
cwd = 技能目录
bun run convert.ts <原件绝对路径>        # 同时经 argv[2] 与 OPENHIVE_INPUT_PATH
```

- 只写一个文件：`adapter.json` 的 `output.file`（当前 `result.json`），内容是 `{ rows, report }`。
  本实现兼容 `--input` / `--out`，但默认仍只产出一个 `result.json`。
- 退出码：`0` 转换完成；`3` 闸门拒收（`rows` 必为 `[]`，只交 `report`）；`1` 转换器异常。
- 输出文件已存在时拒绝覆盖（exit 1），由内核负责清理/换目录。
- stdout 不写 JSON；stderr 只写一行人读摘要。
- 目录名 `银行卡流水转换`；识别卡 id `bank-card-statement`（Ingest gate 要求
  `^[A-Za-z0-9_-]+$`，中文目录名过不了）。平台按 id 分配安装目录；直接拷贝部署时把目录名改成 id。

## 1. 表的物理形状（实测）

三份真实样本（已脱敏进 `test/fixtures/sample-{1,2,3}.xlsx`）：

| 夹具 | 源字节 | 单表 | 表头行 | 列数 | 数据行 |
|---|---|---|---|---|---|
| sample-1.xlsx | 100,303 | `sheet` | 第 1 行 | 41 | 310 |
| sample-2.xlsx | 359,885 | `sheet` | 第 1 行 | 41 | 757 |
| sample-3.xlsx | 61,846 | `sheet` | 第 1 行 | 41 | 135 |

夹具是全零占位（`00000000`）原样保留的——它不含个人信息，轮转掉夹具就复现不出 §3 那条规则。

表头不在第 1 行时，在前 10 行里找「命中必需列最多」的一行；并列取最早。
必需列 6 个：`查询账号`、`交易对方账卡号`、`借贷标志`、`交易金额`、`交易时间`、`交易是否成功`。
其余 35 列全是可选列，缺了不影响转换；必需的 6 列缺任意一列 ⇒ 表头闸整份拒收。

列语义（用到的）：

| 列 | 用途 | 说明 |
|---|---|---|
| `查询账号` | `ownerAccount` | 本方卡号，同一文件通常一行一个值 |
| `交易对方账卡号` | `counterparty` | 对方账号，`-` 当空 |
| `交易对方名称` | `counterpartyName` | 对方户名，`-` 当空 |
| `借贷标志` | `direction` | 借 = 付，贷 = 收 |
| `交易金额` | `amount` | 取绝对值，符号不可信（见 §5） |
| `交易余额` | `balance` | 保留符号（样本里有负数与全 0） |
| `交易时间` | `startedAt` / `startedRaw` | 按 Asia/Shanghai 解释 |
| `交易是否成功` | 值闸 + 跳过 | 只认 `adapter.json` 声明的集合 |
| `交易对方账号开户行` | `属性:对方:开户行` | 通道名/纯数字代码不写 |
| `交易对方证件号码` | `属性:对方:证件号` | 非空即写，不校验证件类型 |
| `交易类型` | `extras.交易类型` | 非空即写 |
| `备注` | `extras.备注` | 非空即写 |
| `币种` | `currency` | 空 / CNY / RMB / 人民币 / 元 ⇒ CNY |
| `商户名称` | **不写** | 是摘要/分期说明，不是户名（见 §6） |

## 2. 角色：两列直给，不按借贷分「方」

- 本方 = `查询账号`（开具调取证据通知书时指定的那张卡）。
- 对方 = `交易对方账卡号`（无论借/贷，对方都在这同一列）。
- 不存在微信流水那种「付款方支付帐号 / 收款方支付帐号」双列互换，也没有银行卡号与开户行的成对约束。

## 3. 对方账号：没有兜底，缺就跳过

- 只取 `交易对方账卡号`。空值或 `-` ⇒ 跳过，原因「缺对方账号」，金额进 `跳过汇总`。
- **全零账号是平台的占位，不是真卡**：`00000000` 之类（正则 `/^0+$/`）⇒ 跳过，原因
  「对方账号为全零占位」。实测 sample-1 有 8 行（323.06，支付宝退款）、sample-2 有 2 行
  （219.80）。照收会把互不相关的退款并到一个假账户上，下游实体会被污染。
- **不许**拿 `商户名称`、`交易摘要`、`备注`、`交易对方名称` 当账号，也不许从这些列反推。
- 实测 sample-1 有 80 行缺对方账号（金额 38,253.32），绝大多数是「分期还款 本金 第x/36期」这类
  只有摘要、没有对手方的行；8 行全零占位（323.06）；2 行金额为零。三者合计 90 行，正好是 310 − 220。
- sample-2 有 20 行对方账号存在但 `交易对方名称` 为空；这些账号在本文件内没有出现过名称，
  **不建名册、不补全**，`counterpartyName` 留空，报告记一条「户名缺失」。

## 4. 值闸：整份拒收，不做部分产出

分母 = 候选行（非空、非合计/小计、非重复表头）。任何一项跌破阈值 ⇒ `rows: []`、exit 3。

| 检查项 | 阈值 | 判据 |
|---|---|---|
| `查询账号非空` | 1.0 | 归一化后非空 |
| `借贷标志合法` | 1.0 | 只能是 `借` / `贷`；`adapter.json` 的 `nonTransactionFlags`（当前 `["O"]`）声明的非交易值**不进分母**，逐行跳过（见下） |
| `金额可解析` | 1.0 | 可解析成两位小数（允许负号） |
| `时间可解析` | 0.99 | 标准日期/中文日期/紧凑 14 位，且是真实时刻 |
| `交易状态可识别` | 1.0 | ∈ `status.success` 或 `status.failure` |

`交易状态可识别` 是 **fail-closed**：`处理中`、空值、`已撤销` 等未声明值都会让整份文件拒收，
不会静默当成功。遇到新的合法状态值时，先在 `adapter.json` 的 `status.success/failure` 里声明，
再重跑测试——不要改 `convert.ts` 里的硬编码。

`借贷标志合法` 同样 fail-closed，但有一个**显式声明**的例外：广发信用卡流水会出现
`借贷标志 = O` 的「非资金变动」行（实测 2026-11-25：464 行里 1 行 `刷卡次数免年费`，
金额 0、余额未变、对方账号 `-`、币种 `000`）。这类值声明在 `nonTransactionFlags` 里，
**不进方向闸分母**、逐行跳过（原因「非交易行」）；没声明的值（如 `X`）仍然让整份文件拒收。
遇到新的非交易标记，先在 `adapter.json` 声明再重测，不要放宽阈值。

## 5. 逐行字段

- `direction`：默认 `借` → `付`，`贷` → `收`；缺方向不按金额正负反推。
  **唯一例外是冲正**：摘要或交易类型含「冲正」、同表紧邻下一行是同本方卡、且
  「本行余额 − 下一行余额」与金额**分厘不差**时，按余额翻向并记「冲正方向按余额修正」；
  差对不上、缺相邻余额或相邻行不是本方卡 ⇒ 保留借贷标志，记「冲正余额未核对」，不猜。
  实测 sample-2 第 445/447 行各 462,000 标「借」实为「收」；修正后全表
  收 − 付 = 0.12，恰等于最新一笔余额（含被跳过的 2 行全零退款 219.80；
  产出的 755 行 收 − 付 = −219.67，差额正是跳过金额）。普通行一律以借贷标志为准。
- `amount`：`解析金额` 后取绝对值、两位小数字符串；零金额（`0.00`）逐行跳过。
  实测 sample-1 的贷方存在负金额（如 `-2900.00`），若保留符号，收方向会变成负金额，
  整份材料被内核契约拒收（`amount` 必须 > 0）。
- `balance`：可解析就写，保留符号；解析不了只记告警、不写该行 `balance`。
  余额不可作为方向或金额的依据：sample-1 全为 0.00，sample-3 有负数。
- `startedAt`：`解析时间` 按 Asia/Shanghai（UTC+8）换算成 Unix 秒；
  `precision` 按输入形态给 `到日` / `到分` / `到秒`（当前三家都是 `到秒`）。
- `rowNo`：源文件 Excel 行号（表头是 1，首条数据是 2），不是数组下标。
- `ownerAccountRaw` / `counterpartyRaw` / `startedRaw`：保留源文件原文（只 trim）。
- `sheet`：工作表名（三家都是 `sheet`）。
- `timeType`：固定 `发生`。
- 跳过原因（逐行，金额能解析就带进 `跳过汇总`）：
  `方向不明`、`非交易行`（借贷标志是声明过的非交易值）、`金额无法解析`、`金额为零`、
  `时间无法解析`、`交易未成功`、`交易状态不明`（阈值被放宽时的防线）、`缺本方账号`、
  `缺对方账号`、`对方账号为全零占位`。

## 6. 户名：走别名，不走属性；商户名称不参与

- `交易对方名称` → `counterpartyName`，下游写 `case_entity_alias kind='户名'`，参与实体归并。
- `-` / 空 ⇒ 不写 `counterpartyName`，不臆造。
- **`商户名称` 永远不是户名**：sample-1 的该列实际是「分期还款 本金 第4/36期」这类摘要；
  把它当户名会让 82 行分期记录的对手方整体错位。本转换器完全不读该列。
- **没有 `ownerName`**：41 列里没有查询账户名称/户名列；不拿 `查询账号` 反查，也不跨文件补全。
  下游只能靠本方卡号建实体，没有本方户名别名——这是源数据的缺口，不是转换器漏写。

## 7. 属性：只写对方侧的开户行与证件号

属性键用半角冒号，归属只允许 `对方`/`本方`；本适配器只声明两个键：

- `属性:对方:开户行` ← `交易对方账号开户行`
  - 纯数字（如 `99123456`、`48400012`）是联行号/网点代码，**不写**，记「开户行疑似代码」；
    实测 sample-3 的 135 行全部是这种代码。
  - 含 `支付宝` / `财付通` / `银联` / `网联` / `微信` / `alipay` / `tenpay` 的是支付通道标记，
    **不写**，记「开户行疑似通道标记」；实测 sample-1 有 219 行、sample-2 有 590 行（产出行的口径）。
  - 其余（`建设银行`、`中国民生银行股份有限公司福州连江支行`…）原样写入。
- `属性:对方:证件号` ← `交易对方证件号码`
  - 非空即写；样本里同时出现 18 位身份证号与 18 位统一社会信用代码，本转换器不区分类型。
- 不写 `属性:对方:银行卡号`：`交易对方账卡号` 已经是标准字段 `counterparty`，再写属性是重复。
- 不写本方属性：41 列没有本方开户行/证件号列。
- 前提闸：内核只在「该侧账号满足 `是账户形状`」时才挂属性与户名别名。`交易对方账卡号` 若是
  字母数字混合（实测 sample-2 有 25 行、sample-3 有 4 行，如 `1517CNY…`），仍写进
  `counterparty`，但下游只留 mention，属性与户名别名会被丢弃；报告逐行记「账号形状可疑」。

## 8. 确定性与纯函数

- 不连库、不调模型、不发网络、不读技能目录以外的文件（原件由内核传入是唯一例外）。
- 不做远端富化、不跨文件补全、不做转账配对/去重/合计；这些是下游的事。
- 不用 `Date.now()`、随机数、`localeCompare`（ICU 版本会让排序漂移）、对象键遍历顺序。
- 行、跳过、告警都按「工作表原顺序 + rowNo 升序」稳定排序；同表同号再按码元序。
- 同一输入两次运行必须字节一致；测试会跑两遍比对。
- xlsx 解析器已 vendored 到 `vendor/xlsx.mjs`（SheetJS 0.20.3，Apache-2.0），配套
  `vendor/xlsx.d.mts` 只声明用到的最小面（typecheck 用）；不依赖仓库 node_modules，也不要求联网安装。

## 10. RED 基线：不知情工程师实际做错的地方

RED 实验：一位**没读过本 skill** 的工程师按常规做法写出了转换器，产出留档在开发机的
工作区外层 `tmp/red-bank/out/`（`stats.json` + 三份 `*.facts.json`，**不入库**）。
与本节口径逐项对账：

| 维度 | RED 实得 | 本 skill |
|---|---|---|
| 行数 | 310 / 757 / 135 全量产出，`skipped: []` | 220 / 755 / 135（跳过 90 / 2 / 0） |
| 缺对方账号 82 行、零金额 2 行（样本1） | 照收，`amount` 出现 `0` | 逐行跳过，进跳过汇总 |
| 全零占位 10 行（样本1 8、样本2 2） | 当普通对方账号 | 跳过，原因「对方账号为全零占位」 |
| 开户行 | 通道名写进 227 / 592 行；纯数字代码写进样本3 全部 135 行 | 都**不写**，记告警 |
| 冲正 445/447 | 认出来了，翻向（balanceDelta 462,000） | 同样翻向；但它没发现全零占位 |
| 疑似重复 | 样本1 检出 20 组 / 20 行 / 12,624.83，保留并告警 | 不去重（下游的事），不写检测代码 |
| `00:00:00` 行 | 标了 midnightRows（样本1 4 行、样本3 7 行），仍写 `到秒` | 同样写 `到秒`（见 §11） |
| `商户名称` | 没当户名（对） | 同样不读该列 |

结论：**显式字段（借贷、金额、时区、冲正）它能做对；错的全在「哪些行不该进库」和
「哪些开户行不是银行名」**——正是 §3 / §7 那几条没有列名可依、只能靠样本形状钉住的规则。

## 11. 已知边界（不要假装支持）

- 只支持平台统一 41 列表头。其他银行自有导出（列名不同、多行表头、合并单元格）要另写适配器。
- 41 列里没有本方户名/本方开户行/本方证件号，`ownerName` 与 `属性:本方:*` 一律不产出。
- `交易对方证件号码` 可能是身份证、统一社会信用代码或空；不校验、不推断类型。
- 非数字对方账号（字母数字混合、掩码）仍写 `counterparty`，但内核不建账户实体，
  属性和户名别名不会挂载；报告记「账号形状可疑」。
- 状态值只认 `adapter.json` 声明的集合；未声明的新状态会让整份文件拒收，这是有意的 fail-closed。
- 非交易方向值同理：只认 `nonTransactionFlags` 里声明过的（当前 `O`），逐行跳过；其他未声明值
  （实测 `X`）仍整份拒收。遇到新的非交易标记先改 `adapter.json` 再重测，不要动阈值。
- 冲正修正只认「摘要/类型含冲正 + 相邻行同卡 + 余额差分厘不差」；多卡文件、跨工作表、
  余额链断档的冲正行一律保留借贷标志并告警，不翻向。
- 部分 `00:00:00` 行（样本1 的结息类、样本3 的「支付撤销」）其实是**只到日**的批量记账；
  但源文件给的是完整时间戳，本转换器不改写 `precision`（仍 `到秒`），读端看到 `00:00:00`
  的结息/撤销行时应知道它可能不是真实时刻。
- CSV 只收 UTF-8（可带 BOM，RFC 4180 引号）；GBK/UTF-16 明确 exit 1，提示另存。
- 一个工作表里有多段表头/多张表：只认第一个命中表头，后续重复表头行跳过，不拼多段。
- 不做跨文件名册、不做转账配对、不去重、不算合计；这些是下游的事。
