# 财付通/支付宝交易流水转换（财付通含微信支付）→ 资金事实行

把一份支付账户流水，整份转换成 openhive 的 `FactRowInput[]`（`result.json`）。
这个技能绑定的是**下面这套统一表头**，不是「任意导出」的通用解析器；换一套表头就先改
`adapter.json` 的匹配列，再重测。

v1.2.0 起同一张识别卡覆盖三个通道：**微信/财付通、支付宝、通用**。三类文件的表头可以完全一致，
因此仅靠表头**无法**区分——通道必须由数据信号判定（§1.1）。v1.2.1 起零金额行逐行跳过（§5）。

## 0. 契约（以仓库代码为准，不以旧文档为准）

内核 `packages/opencode/src/server/openhive/case-converter-runner.ts` 现在的调用方式是：

```
cwd = 技能目录
bun run convert.ts <原件绝对路径>        # 同时经 argv[2] 与 OPENHIVE_INPUT_PATH
```

- 只写一个文件：`adapter.json` 的 `output.file`（当前 `result.json`），内容是 `{ rows, report }`。
  旧提示词里的 `factRows.json` + `report.json` 双文件与 `--input/--out` 已过时；本实现兼容
  `--input`/`--out`，但**默认仍只产出一个 result.json**。
- 退出码：`0` 转换完成；`3` 闸门拒收（`rows` 必为 `[]`，只交 `report`）；`1` 转换器异常。
- 输出文件已存在时拒绝覆盖（exit 1），由内核负责清理/换目录。
- stdout 不写 JSON；stderr 只写一行人读摘要。

目录名与 id：发布目录是 `财付通支付宝交易流水转换`（目录名不能含 `/`；识别卡显示名是
`财付通/支付宝交易流水转换`），识别卡 id 仍是 `wechat-wallet-statement`
（Ingest gate 要求 `^[A-Za-z0-9_-]+$`，中文目录名过不了）。平台按 id 分配安装目录；
若直接拷贝部署，把目录名改成 id。发布包内只留 `test/` 冒烟集（入库闸要求）；
完整回归与 26MB 夹具/黄金在同级目录 `财付通支付宝交易流水转换-tests/`，不随安装包复制。

## 1. 表的物理形状（实测）

测试夹具 `../财付通支付宝交易流水转换-tests/fixtures/脱敏-微信流水.xls`（真实样本脱敏后重存）：OLE2 BIFF8，15,392,768 字节，
单表 `sheet`，表头在第 1 行，28 列，16,992 个数据行。表头不在第 1 行时在前 10 行内找命中最多的一行。
真实样本的体积/内部记录与脱敏件不同（重存导致字节变化），但列结构、行数与全部数值分布一致。

必需列（缺一列整份拒收）：

```
查询账号 付款方支付帐号 收款方支付帐号 借贷标志 交易金额 交易余额 交易时间
```

常用可选列：`序号`、`交易类型`、`币种`、`付款方银行卡所属行`、`付款方银行卡号`、
`收款方银行卡所属行`、`收款方银行卡号`、`收款方的商户号`、`收款方的商户名称`、`备注`；
新版财付通/支付宝导出还有 `交易流水号`、`支付机构内部订单号`、`收单机构名称`、
`收单机构金融机构编码`、`二级商户名称`、`二级商户号`、`清算机构名称`（共 33 列，只多不少）。

`-` 在源文件里是「无」的占位，标准列一律当空串；原文只在 raw 字段里保留。

### 1.1 通道判定：只看数据，不看表头

实测两份真实文件（财付通 4,586 行、支付宝 438 行）的 **33 列表头完全相同**，而内核识别卡
只按 `requiredHeaders` 匹配——不判通道就会把支付宝静默当成微信流水。判定规则（阈值与词表
只在 `adapter.json` 的 `channel`，代码不写第二份）：

| 通道 | 数据信号（实测命中） |
|---|---|
| 微信/财付通 | 查询账号/支付帐号/开户行/收单机构含 `@wx.tenpay.com`、`微信`、`财付通`、`tenpay`、`微众`（4,586/4,586 行） |
| 支付宝 | 含 `alipay`/`支付宝`/`蚂蚁`（93 行），**或**「查询账号是 11 位手机号」且「交易流水号 == 支付机构内部订单号」两项比例都 ≥ 0.9（438/438、437/438） |
| 通用 | 两类信号都没有（老 28 列样本仍按微信识别；边界/其他统一格式按通用） |
| 冲突 | 两类信号同时命中 ⇒ **整份拒收**，闸门写 `通道可判定`，exit 3 |

判定是**文件级**：分母固定 1，冲突即 0。报告新增 `通道` 字段（表头闸失败时不写）。
`通用` 不是「未知就不管」：它表示没有支付通道标记，按通道无关的规则转换，兼容旧样本。

## 2. 先分「方」，再分母

这是整份转换的地基。不要按「付款方列 = 本方、收款方列 = 对方」硬编码。

| 借贷标志 | 方向标准列 | 本方 | 对方 |
|---|---|---|---|
| 借 | 付 | 付款方 | 收款方 |
| 贷 | 收 | 收款方 | 付款方 |

- `查询账号` 是本方主体；`方向与本方一致` 闸要求「本方这一侧的支付帐号 = 查询账号」。
- **每一侧绑定三件套**：支付帐号（主体）+ 银行卡号（名下卡）+ 银行卡所属行（该卡开户行）。
  不要跨侧拼：付款方的卡不能挂到收款方名下。
- `收款方的商户名称` **永远属于收款方这一侧**。借行里它是对方户名，贷行里它是本方户名；
  这一条错了，名册会把本方户名污染成对方（实测会在同一账号下制造大量假冲突）。

## 3. 对方账号：按顺序取，取不到就跳过

1. 对方这一侧的 `…支付帐号`（普通转账、红包、消费都有）。
2. 为空且方向为付：`收款方的商户号`。
   - 直连：整格是纯数字（如 `30000001`）→ 直接当对方账号。
   - 间连：整句「间连交易，实际收款商户名称联系间连收单机构：【机构】通过<订单号>查询」
     → 取 `通过` 与 `查询` 之间的订单号当对方账号；户名取【机构】，并记「间连商户」告警。
     真实商户名不在本文件里，不许猜。
3. 为空但对方有卡，且交易类型匹配本人卡资金搬移：
   - 借 + `提现|转账至银行卡` ⇒ 对方 = 本方账号；
   - 贷 + `充值` ⇒ 对方 = 本方账号。
   仍写 `counterpartyRaw`（取本方支付帐号原文），并记「对方账号推导」。
4. 仍为空：跳过，原因写 `缺对方账号`。**不要**拿商户名称、备注或「（个人）」当账号。

实测 511 行跳过全部是这一类：305 行借方只有户名、144 行贷方付款方支付帐号为空且无卡、
62 行借方没有任何对方标识。少了第 2、3 条会把 2,773 行商户/提现/充值行一起丢掉或造出空账号。

新版真实样本同理，但金额必须让用户看见（报告 `跳过汇总`）：

- 财付通 4,586 行：跳过 118 行 / ¥41,272.32（57 行退款对手只有姓名、61 行微信转账对手无账号）；
- 支付宝 438 行：跳过 324 行 / ¥1,462.85（366 笔入账里只有 43 笔有付款方账号，其余 323 笔
  原件根本没有对方账户标识）。这不是解析缺陷，是数据里没有可用的对方主体；转换器不臆造。

## 4. 值闸：整份拒收，不做部分产出

分母是候选行（去掉空行、合计/小计行、重复表头）。阈值只在 `adapter.json`：

| 检查项 | 阈值 | 含义 |
|---|---|---|
| 查询账号非空 | 1.0 | 每一行都要有本方主体 |
| 借贷标志合法 | 1.0 | 只认 `借`/`贷` |
| 金额可解析 | 1.0 | 千分位、货币符号、两位小数 |
| 时间可解析 | 0.99 | 允许 ≤1% 认不出（仍逐行跳过） |
| 方向与本方一致 | 0.98 | 本方支付帐号必须等于查询账号 |
| 卡行成对 | 1.0 | 有卡号就必须有开户行（分母只算有卡的行） |
| 开户人可分类 | 1.0 | 户名能判个人/企业；整表没有户名列时分母为 0、按通过 |
| 通道可判定 | 1.0 | 文件级闸：微信/支付宝信号冲突即 0（分母固定 1），整份拒收 |

任何一项低于阈值 ⇒ 整份 `rows: []`、`skippedRows: []`、只交 `report`、exit 3。
不允许「坏的跳过、好的先入库」：下游会把半份流水当成完整流水。

成功报告新增 `跳过汇总`（按原因聚合 `行数` 与 `金额合计`）；`skippedRows` 里金额可解析的行
逐行带 `金额`。金额取绝对值、以整数分累加后格式化成两位小数（避免浮点漂移）。空行/合计行/
重复表头不带金额——合计行的金额不是流水，不能计进跳过金额。整份拒收时 `跳过汇总: []`。

报告的闸条目字段必须用内核契约名：`{闸:"值", 检查项, 分母, 命中, 通过率, 阈值}`。
`case-ingest.ts` 的 `第一个失败闸` 只认 `检查项` / `通过率` / `阈值`——写成 `项` / `实际率`
会把「值闸不过」误报成「失败:转换器异常」。

`卡行成对` 的反方向（有开户行、没卡号）实测 32 行，是源数据噪声：仍产「开户行」观察、
记「有行无卡」告警，也不拒收——否则这份真实样本永远过不了闸；没有卡号可配对，不强造。
其中 13 行的开户行格是纯数字（`4830`/`1002`/`314551000113`），是行号/联行号代码而不是行名：
不写 `属性:*:开户行`，改记「开户行疑似代码」告警；把代码当行名入库会让下游答出「开户行 = 4830」。

## 5. 逐行字段

- **金额**：`amount` 永远是正数两位小数字符串；方向只由借贷列决定。不要用负号表达付出。
  千分位先验分组再剥（`12,34` 必须判 null，不能无声变成 `1234`）。整数位上限 16。
  **零金额行跳过**（原因 `金额为零`，金额照带进 `跳过汇总`）：内核契约第 2 条要求
  `amount > 0`，把 `0.00` 留在 `rows` 里会让整份材料被拒收；实测样本是支付宝
  「支付账户消费 0.00 芝麻信用专享支付」，没有资金流动。
- **余额**：`balance` 保留符号（实测有 `-3.50`），同样是两位小数字符串；解析不了就不写并告警。
- **时间**：按 Asia/Shanghai 解释，输出 Unix 秒。认紧凑 14 位（`20260411091334`）、
  `YYYY-MM-DD HH:mm:ss`、`YYYY/M/D H:mm`、`YYYY年M月D日H时M分S秒` 等。
  `H时` 没有分钟 ⇒ 分钟记 0、精度 `到分`。不许用 `new Date(无时区字符串)`；
  `Date.UTC` 会进位（2 月 31 日），必须回读逐字段核对。
- **币种**：CNY/RMB/人民币/元（忽略大小写与全半角空白）⇒ `CNY`；其余原样大写（`USD` 保留）。
- **raw**：`startedRaw`、`ownerAccountRaw`、`counterpartyRaw` 保留原件原文；归一化只写标准列。
  整行 28 列**不**塞进 `result.json`：来源靠 `sourceSha256 + sheet + rowNo` 回指源文件；
  验收用的「原始行」列由导出层拼，不属于转换契约（`extras` 只有 `ownerName`/`备注`/`交易类型`/`属性:*` 被下游读取）。
- **行号**：`rowNo` 是源文件 Excel 行号（表头在第 1 行时首条数据是 2），不是数组下标。
- `timeType` 固定 `发生`；`sheet` 用工作表名（CSV 用文件名）。

## 6. 户名：两个出口，不是属性

- 本方户名 → `extras.ownerName`；对方户名 → 顶层 `counterpartyName`。
- 户名**不能**写成 `extras["属性:对方:户名"]`：属性词表只有开户行/银行卡号/证件号，
  户名走实体别名（`counterpartyName`）与 `ownerName`，否则下游建不出正确的别名。
- 本行原文优先；缺的一侧用**名册**补：同一账号/商户号在本文件其他行出现过唯一户名。
- 同一账号出现多个不同户名 ⇒ 该键不补全，记「户名多值」告警（实测 5 个键）。
  不要取第一个、也不要投票：同号多户名本身就是证据冲突。
- `（个人）`/`(个人)` 是主体类型标注，不是户名；剥掉括号，户名空就留空并记「户名缺失」。
- 户名末尾括号里的「个人」→ 类型个人，否则企业；间连整句取【机构】并按企业。
- 不要编造/翻译户名，也不要用备注里的子商户名替换。

## 7. 属性：成对、归属、半角冒号

- 键：`属性:<对方|本方>:<开户行|银行卡号>`，冒号必须是半角 `:`；全角会让下游认不出来。
- 卡号与开户行**各自独立成观察**：同一侧有开户行就产「开户行」，有卡号就产「银行卡号」；
  单有开户行（有行无卡）也保留，照样告警；单有卡号（有卡无行）会被「卡行成对」闸整份拒收。
  卡号与开户行需要配对时，靠同一次观察共享的出处（材料#表#行）配。
- 开户行必须是**名称**：纯数字（行号/联行号）不当行名入库，记「开户行疑似代码」告警。
  支付通道标记（`alipay`/`支付宝`/`财付通`/`tenpay`/`微信` 等，词表在 `adapter.json` 的
  `channel.bankNameDeny`）也不是银行名，不写入 `属性:*:开户行`，记「开户行疑似通道标记」。
  实测支付宝文件 51 行命中；`微众银行` 是真实银行，不在黑名单里。
- 归属跟着「方」走：借行里收款方的卡是对方卡，贷行里付款方的卡是对方卡。
- 空值不写；同一行内同名键只出现一次。
- **同一账号多张卡**：逐行各写各的卡，不要拼成一个字符串。内核按实体合并 `attrs.银行卡号`
  （同值去重、保留首次出处），同一次观察的卡号与开户行共享 `材料#表#行` 出处、可按出处配对。
  本样本本方账号有 8 张卡、对方账号合计 187 张卡，都是这样并存下来的。
- 提现/充值这种对方=本方的行，卡挂在对方侧（源文件只在这一侧给了卡），允许
  `属性:对方:*` 与 `属性:本方:*` 同时存在，冲突时下游按同实体合并。

## 8. 确定性与纯函数

- 不连库、不调模型、不发网络、不读技能目录以外的文件（原件由内核传入是唯一例外）。
- 不做远端富化（N4 未实现）：不查 PG、不补客户姓名、不写缓存；户名只用本文件内名册。
- 不用 `Date.now()`、随机数、`localeCompare`（ICU 版本会让排序漂移）、对象键遍历顺序。
- 同一输入两次运行必须字节一致；测试会跑两遍比对。
- xlsx 解析器已 vendored 到 `vendor/xlsx.mjs`（SheetJS 0.20.3，Apache-2.0），
  不依赖仓库 node_modules，也不要求联网安装。

## 10. RED 基线：不知情工程师实际做错的地方

写这个技能前，让一个不知道规范、只看原件和字段表的代理独立做过一遍（16,992 行全量）。
下面是它**真实犯的错**，每条都能在本技能里找到对应约束。改这个技能时别把这些错改回去。

1. **把「尽力补全」当美德，511 行缺对方账号照样产出。** 它从备注的「子商户名称」「相关方」
   里抓名字、按订单号反查退款原交易，硬凑出对手方，最后输出 16,992 行。与正确结果相减，
   正好多出借方 367 笔 / +234,714.94、贷方 144 笔 / +509,786.88，合计 +744,501.82 ——
   就是本技能跳过的 511 行（305 + 144 + 62）的金额。多出来的不是精确，是一份掺了猜测的
   流水。**约束**：§3 第 4 条，缺对方账号就跳过；不许拿备注、商户名、「（个人）」当账号。
2. **时间只输出墙上时间字符串，不做时区。** 它输出 `YYYY-MM-DD HH:mm:ss`，既不是 Unix 秒，
   也没声明 Asia/Shanghai。**约束**：§5，按上海时区解释、输出 Unix 秒；不许 `new Date(无时区)`。
3. **户名冲突用多数投票。** 同一账号先后显示「户名甲」「户名乙」，它取多数「户名乙」并只记
   「户名冲突」。同号多户名本身是证据冲突，投票等于替下游做实体合并。**约束**：§6，不补全、
   记「户名多值」。
4. **间连商户用备注替换真实商户名。** 它把备注被截断在 100 字符的「子商户名称」当商户名，
   自己也承认 124 行提取值可能是截断片段。**约束**：§3 第 2 条，间连只留收单机构 + 订单号。
5. **退款反向配对、疑似重复分析写进转换器。** 它按订单号给 210 笔退款找原交易、给 3 组疑似
   重复打标，9 笔多候选靠打分选。转换器是逐行纯函数，配对/去重是下游的事；这类跨行推断
   既改变不了「对方账号是否缺失」，又会引入不可复核的选择。**约束**：§11 最后一条。
6. **自定义 38 列 CSV + JSONL 双产物，没有 result.json、没有 raw 字段。** **约束**：§0 单文件
   `{rows, report}`，§5 raw 保留原文、行号用 Excel 行号。
7. **没有闸门，也不整份拒收。** 它把合法性检查跑成「打印统计」，坏行坏文件照样出结果。
   **约束**：§4，任何一项跌破阈值 → `rows: []`、exit 3。

同一实验在一份 215 行切片上重做（只给字段表、不给规则），逐字段对比后又暴露六种具体错法，
全部已在对应章节约束：

- 28 行消费的收款方账号是 `-`、商户号明明有值，它却让 `counterparty` 空着，把商户号塞进
  `extras.merchantNo`。→ §3 第 2 条：商户号就是对方账号。
- 57 行提现/充值时源件对方侧本来就有支付账号，它偏用本方银行卡号当 `counterparty`
  （如 620000...），把「对方=本方账号」做成了「对方=本方卡号」。→ §3 第 3 条。
- 21 行间连它从备注截断的「子商户名称」取户名（商户甲、商户乙、商户丙），而源件能给的
  只有收单机构（某支付机构…）。→ §3 第 2 条、§6 最后一条。
- 28 行贷方转账不用文件内名册，对方户名直接留空。→ §6：缺的一侧用名册补。
- 7 行缺对方账号（`counterparty` 为空）仍照样产出，其中一行的户名取自备注
  「子商户名称：某商户」。→ §3 第 4 条：跳过，不拿备注当账号/户名。
- `extras` 塞进 orderNo、deviceIp、remark 等 3,060 个自定义键；下游只读 `ownerName` /
  `备注` / `交易类型` / `属性:*`，其余键不入库。关键信息（商户号）只放在 `extras.merchantNo`
  等于丢掉。→ §5/§7：商户号要通过 `counterparty` 成为标准字段。

它做对的地方也值得记住（这些不是陷阱）：借=付、贷=收；`收款方的商户名称` 是**收款方**
显示名而不是独立商户名；提现/充值回流时对方=本方（账号用本方支付账号，不是银行卡号）；
源文件名带 `@` 时 `XLSX.readFile` 在
Bun 下会失败，要用 `readFileSync` + `XLSX.read(buffer)` ——本技能的 `读源文件` 已按此实现。

## 11. 已知边界（不要假装支持）

- 只支持这套统一表头（老样本 28 列、新版 33 列）；其他银行流水要另写适配器。
  支付宝同格式流水已支持，但受下面三条数据限制。
- 支付宝入账（贷）大量缺付款方账号：实测 366 笔里只有 43 笔有付款方支付帐号，其余 323 笔
  原件没有对方主体，只能跳过（报告 `跳过汇总` 写清行数与金额）。换一份导出若补上付款方
  账号，同一套规则会自动产出，不需要改代码。
- 支付宝基金账户邮箱（如 `fundalipay@…`）不满足内核账户形状（6–32 位数字或
  `@wx.tenpay.com`）：仍写进 `counterparty`，记「账号形状可疑」；下游只留 mention、不建实体。
  扩展内核账户形态属产品决策，本技能不擅自放宽。
- 开户行里的通道标记（`alipay` 等）被拒绝写入属性；它不是一个银行。
- CSV 只收 UTF-8（可带 BOM，RFC 4180 引号）；GBK/UTF-16 明确 exit 1，提示另存。
- 一个工作表里有多段表头/多张表：只认第一个命中表头，后续重复表头行跳过，不拼多段。
- `(1700000001)` 这类括号值按**掩码号码**处理：不剥括号、不按 10 位数字建实体
  （实测括号内的值从未以裸形出现过；剥开等于把掩码当真实账户）。仍写进 `counterparty`，
  记「账号形状可疑」；下游可能只留 mention。
- 间连商户的真实商户名不在文件里；只保留收单机构名与订单号。
- 不做跨文件名册、不做转账配对、不去重、不算合计；这些是下游的事。
