# 06 · 改造地图：把 opencode 改造成 openhive

> 学习规划的**落脚点**。前面五层所有理解，最终都要转化为「知道改哪里、怎么改不冲突」。本文件是改造的完整清单，按「冲突风险」从低到高排列。

---

## 一、改造总原则（呼应 CLAUDE.md 三原则）

1. **能靠配置改的，绝不动源码**——改源码会和上游 `dev` 冲突，改配置零冲突。
2. **每次改动单独提交，写清「这是要保留的定制」**——冲突时能快速定位该保留哪一侧。
3. **定期同步、别攒太久**——官方更新越频繁、拖越久，合并冲突越难解。

**同步方向永远是 `upstream/dev → main`**，改造在 `main` 上做，学习笔记在 `learning` 分支。

---

## 二、A 类：零冲突改造（靠配置/环境变量，优先做）

这些改动**完全不动源码**，通过 `opencode.json` / 环境变量实现，是改造的第一优先。

| 改造点 | 方式 | 说明 |
|---|---|---|
| 默认模型 | `"model": "provider/model"` | 换成你自己的默认模型 |
| 默认 agent | `"default_agent": "..."` | 换成自定义 agent |
| 产品显示名（会话用户名） | `"username": "openhive"` | 会话里显示的名字 |
| mDNS 域名 | `"server": { "mdnsDomain": "openhive.local" }` | 局域网发现名 |
| 自定义 provider | `"provider": {...}` | 接私有模型，零代码 |
| 权限策略 | `"permission": {...}` | 定制默认权限 |
| 指令/规则 | `"instructions": [...]` | 定制 AGENTS 规则 |
| MCP / LSP / 插件 | 同名字段 | 扩展能力 |
| 配置目录整体迁移 | `OPENCODE_CONFIG_DIR` | 把 `~/.config/opencode` 迁到 `openhive` |

> 结论：**「改默认模型、改 agent、改权限、改指令、改名字显示」这些最常见的品牌化需求，全部可以零冲突完成。** 先做这一批。

---

## 三、B 类：必须改源码的硬编码点（按优先级 + 冲突风险）

这批是真正要动源码的，按「杠杆高低」排序：

### ① 产品名 `opencode`（最高杠杆，改动最小）

- **位置**：`packages/core/src/global.ts:10` —— `const app = "opencode"`
- **影响**：决定所有数据/缓存/日志目录（`~/.config/opencode`、`~/.local/share/opencode` 等）
- **改法**：改成 `const app = "openhive"`
- **冲突风险**：极低（一行，官方很少改这行），但**影响面大**（目录全变，需要做数据迁移兼容）

### ② CLI 名 / 二进制名（高杠杆）

- **位置**：
  - `packages/opencode/package.json` 的 `"name": "opencode"` + `"bin": {"opencode": ...}`
  - `packages/opencode/src/index.ts:47` 的 `.scriptName("opencode")`
- **影响**：`opencode` 命令本身 → `openhive`
- **冲突风险**：中（package.json 的 name 官方可能改，需留意）

### ③ Logo / ASCII 字标

- **位置**：`packages/opencode/src/cli/ui.ts:5-10`（`wordmark` 数组）、`packages/tui/src/logo.ts`
- **改法**：替换 ASCII 艺术
- **冲突风险**：低（纯展示，官方改 logo 频率低）

### ④ `$schema` URL

- **位置**：`config.ts` 多处（`https://opencode.ai/config.json`）
- **改法**：换成自己的 schema 地址（或保留原样，影响很小）

### ⑤ 发送给 provider 的标识头

- **位置**：`provider.ts:462-494`（`X-Title: "opencode"`、`X-Source: "opencode"` 等）
- **影响**：第三方 API 看到的名字
- **改法**：换字符串

### ⑥ MCP client name

- **位置**：`mcp/index.ts:76`（`name: "opencode"`）

### ⑦ 默认 agent 的 `"build"` 字面量

- **位置**：散布多处（`agent.ts:142`、`agent.ts:322`、`acp/service.ts:778`、`tool/plan.ts:58`、`session/reminders.ts:38`）
- **影响**：`build` 作为兜底 agent 名
- **注意**：`default_agent` 字段本身可改默认值，但「`build` 字面量」散布多处，改名需全局替换

### ⑧ 安装/升级渠道包名

- **位置**：`installation/index.ts`（`brew`/`scoop`/`choco` 的 `opencode` 包名）
- **影响**：自动更新检测

## 四、改造策略建议

### 分批推进，先易后难

1. **第一批（零冲突）**：做完 A 类所有配置改造，先让产品「用起来是 openhive」。
2. **第二批（低风险硬编码）**：① `global.ts` 产品名 + ② CLI 名 + ③ Logo——这是「品牌三件套」，改完就是 openhive 了。
3. **第三批（散点清理）**：④~⑧ 的字符串替换，用**集中常量**统一管理（比如建一个 `openhive/constants.ts` 导出 `PRODUCT_NAME = "openhive"`），减少散落字面量。

### 最小化合并冲突的两个技巧

1. **集中常量**：把品牌字符串集中到少数几个常量文件，散点引用常量而非硬编码字符串。这样官方改代码时，冲突只发生在常量文件。
2. **提交信息标注**：每个定制提交都写清 `chore(openhive): 品牌化 XXX`，`git merge upstream/dev` 冲突时一眼看出该保留哪侧。

### 一个需要留意的地方

改造前先想清楚：**数据目录是否迁移？** 改 `global.ts:10` 的 `app` 后，所有数据会从 `~/.config/opencode` 变成 `~/.config/openhive`。如果要保留老用户数据，需要做目录迁移或软链。

## 五、同步上游的完整流程（改造期间持续做）

```bash
git checkout main
git fetch upstream          # 拉官方最新
git merge upstream/dev      # 合并（冲突时保留本地定制）
# 解决冲突 → 保留「这是要保留的定制」那一侧
git add . && git commit
git push origin main
```

> 如果 `git fetch upstream` 报 `non-fast-forward`，说明官方强推过，需先备份本地定制再 rebase，**不要盲目 force**。

```

  → 理解数据流（层3）→ 理解子系统（层4）→ 改造地图（层5）
```

现在你手里有：
- **概念层**：Session Runtime 的完整词汇表（`03-核心概念`）

- **子系统层**：config/permission/provider/mcp/lsp/plugin/storage（`05-子系统`）
- **改造层**：本文件，可执行的改造清单

下一步就是**真正动手**：先做 A 类零冲突改造，再按 B 类清单分批推进。每一步都可以让 Claude 陪你对具体文件做「最小冲突」的改动。
