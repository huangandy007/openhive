# 03 · 工程结构：opencode 的 monorepo 是怎么组织的

> 对应学习规划「层 1」。目标：看懂这个仓库怎么分层、怎么构建、每个包是干嘛的。

---

## 一、整体认知：一个仓库装几十个小包

opencode 是一个 **Bun monorepo**。拆开说：

- **monorepo** = mono（单一）+ repo（仓库）：把几十个相关的 npm 包放在**同一个 git 仓库**里，共享依赖、统一构建、一起发布。
- **Bun**：既是一个 JavaScript 运行时（类似 Node.js），又是一个超快的包管理器（类似 npm/yarn）。这个项目「运行时 + 包管理」都用 Bun。

一句话：**一个大仓库，里面几十个小包，每个包各司其职，但被一个统一的构建系统管着。**

> 为什么用 monorepo？因为 opencode 有终端版、桌面版、网页版、SDK……它们共享同一套核心逻辑（会话、模型、工具）。如果拆成几十个独立仓库，改一个核心 API 要同步几十处；放一个仓库里，改一处全生效。

## 二、workspace 机制：谁是「包」由谁说了算

根目录 `package.json` 里的 `workspaces` 字段，声明了哪些目录算「一个包」：

```jsonc
"workspaces": {
  "packages": [
    "packages/*",          // packages 下每个子目录都是一个包
    "packages/console/*",  // console 下还嵌套了子包
    "packages/stats/*",    // stats 下也嵌套
    "packages/sdk/js",     // 指定某个具体目录
    "packages/slack"
  ],
  "catalog": { ... }       // catalog 见下
}
```

还有 `catalog` 字段——它把关键依赖的版本**统一锁死**（比如所有包用的 `effect` 都是 `4.0.0-beta.83`）。好处：不会出现「A 包用 effect 3、B 包用 effect 4」的版本地狱。

## 四、依赖方向：一条「单行道」（读代码的宪法）

`AGENTS.md` 写死了一条规则，它是你读代码时判断「这个 import 对不对」的标尺：

```
Schema → Core / Protocol → Server
Client 只依赖 Schema + Protocol，绝不依赖 Core / Server
sdk-next 组合 Client + Core + Server
```

用「大楼楼层」类比：**楼下（底层库）不知道楼上（上层应用）的存在；楼上可以引用楼下，反过来不行。** 这样的好处是：不会循环依赖，改底层时影响范围可控。

**实战用法**：当你在 `packages/core` 里看到它 import 了 `packages/server` 的东西，那八成是「异类」或历史遗留，值得多看一眼。

## 五、构建与工具链

| 工具 | 配置 | 干什么 |
|---|---|---|
| **Bun** | `bunfig.toml` | 装依赖（`exact = true` 锁精确版本；`minimumReleaseAge` 要求包发布满 3 天才装，防「刚发布就翻车」） |
| **Turbo** | `turbo.json` | 任务编排：把 typecheck/build/test 分配到各包、并行执行、做缓存 |
| **oxlint** | `.oxlintrc.json` | 代码检查（lint），快速 |
| **husky** | `.husky/` | git 提交钩子（提交前自动跑检查） |
| **prettier** | 根 package.json | 代码格式化 |

`bunfig.toml` 里有个有意思的配置：
```toml
[test]
root = "./do-not-run-tests-from-root"   # 故意设一个不存在的目录
```
这是**故意让「在根目录跑测试」失败**——强制你必须到具体包目录里跑测试。对应 AGENTS.md 说的「Tests cannot run from repo root」。

## 六、怎么跑起来

```bash
bun install            # 装依赖
bun dev                # 跑主程序 packages/opencode/src/index.ts
bun dev:web            # 跑网页 UI
bun dev:desktop        # 跑桌面端
bun dev:console        # 跑控制台

# 类型检查：必须在具体包目录里跑（不是根目录）
cd packages/opencode && bun typecheck

# 测试：也在具体包目录里跑
cd packages/opencode && bun test
```

> 记住一个反直觉的点：**`bun typecheck` 和 `bun test` 都要进到包目录里跑，根目录会报错/被 guard 拦**。这是这个项目的规矩。

## 七、技术栈总览（一张表记住）

| 技术 | 用在 | 一句话解释 |
|---|---|---|
| **Effect** | 贯穿全项目 | 函数式编程框架，负责错误处理、依赖注入、并发——是项目的「骨架」 |
| **AI SDK**（`ai`） | 模型调用 | 统一各家模型 API 的差异，一个接口调所有模型 |
| **Hono** | 服务端 | 轻量 HTTP 框架，处理请求 |
| **Drizzle ORM + SQLite** | 持久化 | 用 TS 类型安全地读写数据库（见 `01` 第四节） |
| **SolidJS** | 网页 UI | 前端框架（React 的轻量替代） |
| **opentui** | 终端 UI | 终端界面的组件库 |
| **Zod**（经 Effect Schema） | 数据校验 | 运行时校验数据形状 |
