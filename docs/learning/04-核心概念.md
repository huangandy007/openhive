# 04 · 核心概念：opencode 的 Session Runtime 词汇表

> 对应学习规划「层 2」。目标：过「语言关」——把 `CONTEXT.md` 里那套 opencode 自创的词汇逐个讲透。
>
> ⚠️ 这一层是**最关键**的一层。opencode 的运行时是一套「会话状态机」，概念环环相扣，不先把词义吃透，后面读 `session/` 代码会像读天书。

---

## 一、为什么必须先学这套词汇

普通程序读代码，你看到 `function loadData()` 大概能猜出意思。但 opencode 的代码里充满了 `ContextEpoch`、`SessionDrain`、`ProviderTurn`、`AdmittedPrompt` 这样的词——**这些词不是通用编程术语，而是 opencode 团队为自己的运行时「发明」的专业名词**。

好在他们把这套词汇连同准确含义都写在了 `CONTEXT.md` 里，并且明确标注了每个词的「避免叫法」（_Avoid_）。比如：

- 不要说「System prompt」（系统提示词），要说 **System Context**（系统上下文）
- 不要说「Session Context」（会话上下文），要说 **Session History**（会话历史）

**先过这一关，后面每读一行代码，你都能把代码里的名词映射回这里的定义。**

---

## 二、一个贯穿全程的类比：AI 员工 + 工作台

为了好记，把 opencode 想象成你雇的一位 **AI 员工**，它坐在一个「工作台」前替你干活：

| 概念 | 类比 |
|---|---|
| Session（会话） | 你和这位员工的一个「合作项目」的**工作记录本** |
| System Context（系统上下文） | 贴在工位墙上的**工作须知**（规则 + 环境信息） |
| Context Source（上下文来源） | 工作须知里的**一条一条**（日期、项目规则、可用技能…） |
| Context Epoch（上下文纪元） | 工作须知「打印一次贴上墙」的**一个周期** |
| Mid-Conversation System Message | 须知变了，递上去的一张**补充通知纸条** |
| Provider Turn（提供方轮次） | 员工**打一次电话给「大脑」（模型）** |
| Session Drain（会话排空） | 员工**一口气把待办清完**的一个工作时段 |
| Admitted Prompt（已准入输入） | 你递给员工的**待办便签**（还没被登记） |
| Prompt Promotion（输入提升） | 便签被**正式登记进工作记录** |
| Tool Output（工具输出） | 员工查资料/改文件后写回记录的**结果摘要** |

下面逐个精确解释。

---

## 三、核心概念逐个讲

### 1. 输入侧：你的话是怎么被接住的

**Admitted Prompt（已准入输入）**
你敲进终端的那句话，先被「准入」——它被持久化到数据库（`session_input` 表），但**还没进入会话历史、还没给模型看**。像一张已放到员工桌角的待办便签。

**Prompt Promotion（输入提升）**
把上面那张便签**正式登记进工作记录**（追加进 Session History）。这是一个原子操作：一旦提升，这句话就成为模型可见的历史消息。

> 为什么要有「准入」和「提升」两步？因为输入可能要排队、要暂缓、要等合适的时机（比如模型正在忙）。分开两步，运行时就能灵活控制「什么时候让这句话真正生效」。

### 2. 上下文侧：模型每次「看到」的是什么

**System Context（系统上下文）**
送给模型的**「初始说明书」+ 后续的补充说明**。它告诉模型：你是谁、在哪个项目、有哪些规则、当前环境如何。它不是静态的，会随时间变化。

**Context Source（上下文来源）**
System Context 是由**很多条独立的值**拼起来的，每一条就是一个 Context Source。典型例子：
- 当前日期（`date`）
- 项目里的 `AGENTS.md` 规则
- 当前 agent 可用的技能列表（`skill`）
- 各种环境状态

每条 Context Source 有：一个**稳定的 key**、一个 **JSON 编解码器**（用于比较和存储）、一个**渲染器**（把值变成给模型看的文字）。

**System Context Registry（上下文注册表）**
一个按 Location（工作目录）划分的、**有序的**注册表，记录「有哪些 Context Source 生产者」。内置的和插件注册的都在这里。

**Context Epoch（上下文纪元）**
一个**时间跨度**：从某次「完整渲染系统上下文」开始，到下次「需要重建」为止。在这个跨度内，初始的系统上下文（基线）保持不变。

**Baseline System Context（基线系统上下文）**
一个 Epoch 开始时，把当时完整系统上下文**渲染一遍**得到的结果。它会被持久化，甚至跨进程重启都能原样复用（这样重启后不用重新渲染）。

**Context Snapshot（上下文快照）**
一个**用于比较**的 JSON 状态：记录「每条 Context Source 上次给模型看的值是什么」。下次就能对比出「哪条变了」。

**Mid-Conversation System Message（对话中系统消息）**
当某个 Context Source **在对话中途变了**（比如日期从周五变成了周六），运行时不会重发整个系统上下文，而是**追加一条简短的补充消息**告诉模型「新状态是什么」。这条消息会被持久化，作为审计历史保留。

**Unavailable Context（不可用上下文）**
某条 Context Source **暂时取不到**（比如某个服务暂时挂了）。这时运行时**保留旧值、不发更新**，而不是报错。它和「成功读取到『没有』」是两回事。

### 3. 执行侧：模型是怎么被「驱动」的

**Provider Turn（提供方轮次）**
**一次对模型的请求 + 返回的响应**。这是运行时最原子的执行单位——每次「打电话给大脑」就是一轮。

**Session Drain（会话排空）**
一个**进程内**的执行周期：唤醒后，提升输入、跑所需的 Provider Turn，直到「暂时没有需要继续做的事」为止。它**不是**一个持久化的实体（数据库里没有 `session_drain` 表），只是进程里的一段协调逻辑。

**Safe Provider-Turn Boundary（安全提供方轮次边界）**
**真正调用模型之前的那个瞬间**。这是所有「上下文变化」被集中处理的时机——在这个边界上，才去检查 Context Source 变了没、该提升的输入提升没、该追加的系统消息追加没。

### 4. 工具侧：模型的「手」产出什么

**Model Tool Output（模型工具输出）**
模型让工具干完活后，工具结果在会话历史里的**「有界投影」**（被截断到一定大小）。工具可以自定义怎么截断，但最终由 Tool Registry 强制执行大小上限。

**Managed Tool Output File（托管工具输出文件）**
如果工具输出**太大**放不进历史，完整内容就存到一个**临时文件**里，历史里只留一小段预览 + 这个文件的路径。文件可能过期被删，但「有界投影」是持久的、可回放的记录。

## 四、一个完整的故事：从你输入到 AI 回复

把这些概念串起来，看一次真实的交互：

> 你在终端里对 opencode 说：**「帮我看看登录页面的 bug」**

1. **准入**：这句话作为 **Admitted Prompt** 进入 `session_input` 表（待办便签放上桌角）。

2. **唤醒**：一个 **Session Drain** 被唤醒，开始处理这个输入。

3. **安全边界**（真正调模型之前，**Safe Provider-Turn Boundary**）：
   - 你的话被**提升**（Promotion）进 **Session History**，成为模型可见的历史。
   - 运行时**惰性检查**每个 **Context Source**：日期变了吗？`AGENTS.md` 变了吗？可用技能变了吗？变了就追加一条 **Mid-Conversation System Message**。
   - 如果是这个 **Context Epoch** 的第一次调用，会先渲染完整 **Baseline System Context**，并初始化 **Context Snapshot**。

4. **调用模型**：组装好的「历史 + 系统上下文」打包，发起一次 **Provider Turn**。

5. **模型要动手**：模型回复说「我要读 `login.ts`」。工具去读文件，结果太大就存 **Managed Tool Output File**，历史里放 **Model Tool Output** 的有界预览。

6. **继续**：工具结果写回历史，模型还需要继续 → 再来一轮 **Provider Turn**。

7. **结束**：直到模型不再需要继续，这个 **Drain** 结束，会话回到空闲，等你下一句话。

**关键心智**：上面 3、4、5 步是一个循环——`组装上下文 → 调模型 → 执行工具 → 结果写回 → 再调模型`。理解了这个循环，就理解了 opencode 运行时的骨架（下一层「数据流」就是把它落到具体代码行）。

## 五、概念 ↔ 数据库表 的对应（呼应持久化）

学完概念再回头看 `01-学习规划.md` 的持久化专题，能对上号：

| 概念 | 落库的表 |
|---|---|
| Admitted Prompt / Promotion | `session_input`（`admitted_seq` / `promoted_seq`） |
| Session History 的消息 | `session_message`（`seq` 保序） |
| Context Epoch / Baseline / Snapshot | `session_context_epoch` |
| Session 元数据 | `session` |

> 这就是为什么 `session_input` 表要分 `admitted_seq` 和 `promoted_seq` 两列——它们分别对应「准入」和「提升」两个时机。

## 六、外围概念（先认识，层 4/5 再深挖）

`CONTEXT.md` 后半段还大量讲了**客户端 API 契约**相关的内容（Promise 客户端、Effect 客户端、SDK、分页游标、`sessions.prompt`/`sessions.events` 等），这些属于「对外 API 怎么设计」，不是核心运行时。它们对理解会话机制帮助不大，等学到「层 4 子系统」和「层 5 改造」时再按需回看。

其中值得现在记住的只有一点：**opencode 把「网络调用」和「嵌入式调用（Embedded）」统一成同一个 OpenCode Client**——无论你是通过 HTTP 还是进程内直接调用，走的是同一套路由和处理器，只是「传输层」不同。这个设计让桌面版、Web 版、SDK 都能复用核心逻辑。
