# 04 · 数据流 · 模型调用层（llm.stream）

> 讲「两条链汇聚后的模型调用」：`llm.stream(request)` 到底怎么把请求编码、发给哪家模型、流式结果怎么回来。这是 opencode「跟模型打交道」的抽象层。

---

## 一、先澄清：代码里有两个「stream」

读代码时最容易混淆的是，项目里有**两层同名的 stream**：

| 层 | 位置 | 作用 |
|---|---|---|
| **Session 层** `LLM.stream` | `packages/opencode/src/session/llm.ts:54` | 一次 provider turn 的**高层入口**，输入是 session 组装好的 messages/tools |
| **底层** `LLMClient.stream` | `packages/llm/src/route/client.ts:396` | 真正把请求**编码成 provider 的 wire 格式**并发出的那一层 |

两者通过一个可选的「native 适配器」衔接：默认走 AI SDK 的 `streamText`，开了 `experimentalNativeLlm` 旗标才走 `@opencode-ai/llm` 的 `LLMClient.stream`。

---

## 二、Session 层：llm.stream 的输入与输出

`packages/opencode/src/session/llm.ts:35-56`：

```ts
interface StreamInput {
  user, sessionID, model, agent, permission,
  system: string[],          // 系统上下文（字符串数组）
  messages: ModelMessage[],  // 历史消息
  tools: Record<string, Tool>,  // 工具
  toolChoice, retries, ...
}
interface Interface {
  stream: (input: StreamInput) => Stream.Stream<LLMEvent, unknown>
}
```

- **输入**：session 组装好的高层输入（AI SDK 形态的 messages/tools + 一个 `system[]` 字符串数组）
- **输出**：`Stream<LLMEvent>`——一个**统一的、与 provider 无关的事件流**（文本增量、推理增量、tool-call、usage 等）

> 关键设计：不管底层是 OpenAI 还是 Anthropic 还是本地模型，上层看到的都是**同一种 `LLMEvent` 流**。这就是「协议适配器」的价值——把差异隔离在底层。

## 三、请求是如何组装的

组装分两段：

### 第一段：Session 层拼 `StreamInput`

`packages/opencode/src/session/prompt.ts:1257-1286` 并行收集五样东西：

```ts
const [skills, env, instructions, mcpInstructions, modelMsgs] = yield* Effect.all([
  sys.skills(agent),            // 可用技能清单
  sys.environment(model),       // 环境信息（工作目录、git、日期…）
  instruction.system(),         // AGENTS.md / config.instructions
  sys.mcp(agent, permission),   // MCP 指令
  MessageV2.toModelMessagesEffect(...),  // 历史消息 → ModelMessage[]
])
const system = [...env, ...instructions, ...mcpInstructions, ...skills]
```

### 第二段：`LLMRequestPrep.prepare` 组装最终请求

`packages/opencode/src/session/llm/request.ts:56-206`：

- **system 合成**（`:58-66`）：`agent.prompt`（否则用按模型选的默认 prompt）→ `input.system` → `user.system`，用换行拼接
- **options 合并**（`:80-91`）：provider 默认 → model.options → agent.options → variant，层层覆盖
- **messages 组装**（`:101-112`）：默认把 system 字符串转成 `{ role: "system", content }` 前置进 messages；**但 OpenAI OAuth / workflow 模型例外**——system 不放进 messages，而是写进 `options.instructions`
- **params**（`:114-132`）：temperature / topP / maxOutputTokens 等
- **tools 解析**（`:148` → `resolveTools`）：按权限 `Permission.disabled` 过滤；部分 provider 强制 `strict:false`；copilot 无工具时补 `_noop`

## 四、两条执行路径：AI SDK vs native

`packages/opencode/src/session/llm.ts`：

### 默认：AI SDK 路径（`:280`）
```ts
streamText({ model: wrapLanguageModel(language), messages, tools, ... })
```
用 Vercel 的 AI SDK `streamText`，得到 `fullStream`，再经 `LLMAISDK.toLLMEvents`（`llm.ts:373-378`，`ai-sdk.ts:76-286`）归一化成统一的 `LLMEvent` 流。

### 可选：native 路径（`:227`，`experimentalNativeLlm` 旗标）
```
LLMNativeRuntime.stream → LLMClient.stream（packages/llm）
  → compile → resolveRequestOptions → route.body.from(请求)
  → route.streamPrepared → transport.frames（HTTP/SSE → 字节帧）
  → decodeEvent（帧 → protocol 事件）
  → 累积成统一 LLMEvent 流
```

## 五、协议适配器：如何把统一请求翻译成各家的 wire 格式

`packages/llm/src/protocols/` 目录下，每个协议两个核心方法：

- `body.from`：`LLMRequest` → provider 原生 JSON body
- `stream.step`：provider 的帧 → 统一 `LLMEvent`

以 OpenAI Chat 为例（`openai-chat.ts:344-370`）：`fromRequest` 生成 `model/messages/tools/tool_choice/stream:true/max_tokens/temperature/...`；`openai-chat.ts:407+` 的 `step` 是解析 delta 流的状态机。

协议目录一览：`anthropic-messages`、`bedrock-converse`、`gemini`、`openai-chat`、`openai-compatible-chat`、`openai-responses`。

> 想新增一家模型供应商？核心就是写一个新的 protocol 文件，实现 `body.from` 和 `stream.step`。

## 六、系统上下文（System Context）在哪里、何时注入

这是 `03-核心概念` 里「System Context」的代码落点，共三处：

1. **最外层 baseline**（`prompt.ts:1257-1269`）：`sys.environment` / `instruction.system` / `sys.mcp` / `sys.skills` 生成 system 块
2. **合并 agent/user 级**（`request.ts:58-66`）：agent.prompt（或默认 model prompt）→ baseline → user.system
3. **真正注入请求体**（`request.ts:101-112`）：转成 `{ role: "system" }` 消息前置，或（OpenAI OAuth/workflow）写进 `options.instructions`

## 七、小结

模型调用层的核心思想是**「一个统一抽象，多种落地」**：

```
session 组装好的高层输入
  → LLMRequestPrep.prepare（统一请求结构）
  → 二选一：AI SDK streamText ｜ native LLMClient.stream
  → 协议适配器（body.from / stream.step）
  → 各家模型 API
  → 统一 LLMEvent 流返回上层
```

上层（processor）不关心你用的是哪家模型，只消费统一的 `LLMEvent` 流。
