> 目标：从全局到细节，系统地理解 opencode 的架构与实现，最终服务于「把它定制改造为 openhive」。
> 说明：本规划是**总纲**，每一层完成后的笔记会拆成独立文件（`02-xxx.md`、`03-xxx.md`…），并在文末「进度清单」勾选。

## 一、学习目标与最终形态

1. **理解层**：能说清楚 opencode 是什么、解决什么问题、整体架构如何分层。
2. **机制层**：能讲透核心运行时的数据流（输入 → 组装上下文 → 调模型 → 工具调用 → 落库）。
3. **改造层**（终极目标）：能定位「品牌化改造点」，并判断每个改动点「改哪里、怎么改才能最小化与上游的合并冲突」。

改造层是落脚点——因为本仓库是官方 opencode 的 fork，**必须能持续同步上游 `dev`**，这是贯穿全程的最重要约束。

## 二、全局地图（先建立心智模型）

opencode 是 **Bun monorepo**（30+ 包），本质是「终端里的 AI 编程助手」（对标 Claude Code / Cursor）。理解时只需记住三层：

```
产品层（怎么用）
  ├─ packages/app        网页 UI（SolidJS）
  ├─ packages/desktop    桌面端
  ├─ packages/tui        终端 UI（opentui）
  └─ packages/cli        命令行入口

运行时层（核心，90% 精力在这里）
  └─ packages/opencode   主程序，src/ 下 40+ 模块：
        session  agent  provider  tool  permission  config
        mcp  lsp  plugin  server  snapshot  sync  storage ...

支撑层（库/协议，相对稳定）
  ├─ packages/core        领域模型 + 持久化表定义（**/sql.ts）
  ├─ packages/schema      领域类型（session/workspace/location 等）
  ├─ packages/protocol    协议定义
  ├─ packages/llm         模型适配（封装 AI SDK）
  ├─ packages/server      服务端（Hono）
  └─ packages/client/sdk/sdk-next  客户端与 SDK
```

**依赖方向是单行道**（`AGENTS.md` 写死）：
`Schema → Core/Protocol → Server`；`Client` 只依赖 Schema+Protocol，不碰 Core/Server；`sdk-next` 组合三者。看到反向依赖即为异类。

**技术栈关键词**：Effect（函数式框架，`effect@4.0-beta`）、AI SDK（`ai@6.0`，模型适配）、Hono（HTTP）、Drizzle ORM + SQLite（持久化）、SolidJS（UI）、opentui（TUI）。

## 四、专题一：持久化机制（重点）

### 1. 数据存在哪

遵循 XDG 规范，根目录 = `xdgData/opencode`（`packages/core/src/global.ts`）：

- Windows 实际在：`%LOCALAPPDATA%\opencode\`
- 内含：`opencode.db`（SQLite 数据库）、`storage/`（JSON 文件）、`log/`、`repos/` 等
- 可覆盖：`OPENCODE_DB`（换库路径 / `:memory:`）、`OPENCODE_CONFIG_DIR`（换配置目录）

### 2. 两套存储并存（关键认知）

opencode **正在从「JSON 文件存储」迁移到「SQLite」**，两套并存：

| | SQLite（Drizzle ORM） | JSON 文件（Storage Service） |
|---|---|---|
| 代码位置 | `packages/core/src/**/sql.ts` | `packages/opencode/src/storage/storage.ts` |
| 库 | `drizzle-orm` + `bun:sqlite` 原生驱动 | 无库，纯 `fs` + `JSON` |
| 存储形式 | 单文件 `opencode.db`，WAL、外键开、64MB cache | `storage/<k0>/<k1>/<k2>.json` 目录树 |
| 定位 | **V2 主存储**，结构化、可索引 | **legacy**，简单 KV，带迁移机制 |
| 并发 | SQLite + `Semaphore` | `TxReentrantLock` 读写锁 + `RcMap` |

V2 Session Core 大重构把会话/事件/权限迁入 SQLite；旧数据靠 JSON Storage 的 `MIGRATIONS` 逐步搬移。

### 3. 数据表全景（18 张，均在 `packages/core/src/**/sql.ts`）

**① 会话三件套（`session/sql.ts`）**

| 表 | 记什么 | 有什么用 |
|---|---|---|
| `session` | id、project_id、workspace_id、parent_id、slug、directory、title、summary_*（改动统计）、cost/tokens_*（用量）、revert、permission、agent/model | 会话元数据；parent_id 支持分叉 |
| `session_message` | id、type、seq、data(JSON) | V2 事件化消息流，`(session_id,seq)` 唯一保序 |
| `session_input` | prompt、delivery、admitted_seq、promoted_seq | **Admitted Prompt / Prompt Promotion**——输入先准入再提升 |
| `session_context_epoch` | baseline、snapshot、baseline_seq | **Context Epoch**——缓存上下文基线 |
| `message` / `part` | V1 旧消息/片段 | legacy，正被 `session_message` 取代 |
| `todo` | content、status、priority、position | 模型维护的待办清单 |

**② 项目与工作区（`project/sql.ts` + `control-plane/workspace.sql.ts`）**

| 表 | 记什么 | 有什么用 |
|---|---|---|
| `project` | worktree(git 根)、vcs、name、icon、sandboxes、commands | 一个 git 仓库 = 一个 project，数据归属锚点 |
| `project_directory` | project_id + directory + type(main/root/git_worktree) | project 可映射多目录（含 worktree） |
| `workspace` | id、type、name、branch、directory、project_id | project 内的隔离工作区 |

**③ 事件溯源（`event/sql.ts`，V2 核心）**

| 表 | 记什么 | 有什么用 |
|---|---|---|
| `event` | id、aggregate_id、seq、type、data | Event Sourcing：领域事件按序追加、可重放 |
| `event_sequence` | aggregate_id、seq、owner_id | 聚合根事件序号分配（防并发重号） |

**④ 权限与凭证**

| 表 | 记什么 | 有什么用 |
|---|---|---|
| `permission` | project_id + action + resource | 已批准的权限规则 |
| `credential` | integration_id、value(JSON)、active | 第三方集成凭证 |
| `session_share` | session_id、secret、url | 会话分享链接 |

**⑤ 账号（`account/sql.ts`）**

| 表 | 记什么 | 有什么用 |
|---|---|---|
| `account` | email、access_token、refresh_token | OAuth token |
| `account_state` | active_account_id、active_org_id | 当前活跃账号/组织 |
| `control_account` | 旧账号表 | legacy |

## 五、专题二：工作目录（workspace）

三层概念，从底层到高层：

```
Location（位置）   ── 一个请求「发生在哪个目录」  { directory, workspaceID? }
Project（项目）    ── 该目录属于哪个 git 仓库     { worktree, vcs }
Workspace（工作区）── 仓库内哪个隔离分支/沙箱     { type, branch, directory }
```

- **Location**（`schema/src/location.ts` + `core/src/location.ts`）：核心逻辑 `project.resolve(directory)` 给定目录解析项目。AGENTS.md 要求 session 运行器/工具/权限/文件系统全部 **Location-scoped**。
- **Project**：一个 git 仓库 = 一个 project，是数据归属与权限的最小单位。
- **Workspace**：project 内更细的隔离（不同分支/沙箱）。

**为什么必须有工作目录**——AI 编程工具的本质是「AI 替你在某仓库干活」，必须回答四问：

1. **权限边界**：AI 能读写哪些文件？（权限按 project_id 存）
2. **git 归属**：改动落到哪个仓库/分支？（靠 worktree + branch）
3. **数据归属**：会话记录算谁的？（session 用 project_id/workspace_id/directory 三列锚定）
4. **上下文正确性**：「打开 src/index.ts」是哪个项目的？（Location 是相对路径解析基准）

一句话：**工作目录 = AI 的「管辖范围」和「坐标原点」。**

## 六、贯穿全程的方法论

1. **术语先行**：opencode 有一套自己的词汇（Context Source / Context Epoch / Provider Turn / Session Drain / Tool Registry…），`CONTEXT.md` 给了每个词的准确定义和「避免叫法」。**不过这一关，读 session 代码如读天书**，这一步最值得投入。
2. **跟数据流，别背目录**：AI 编程工具本质是一条循环——`用户输入 → 组装上下文 → 调模型 → 模型要工具调用 → 工具改文件/跑命令 → 结果写回会话 → 再调模型 → …`。找到这条主循环（大致在 `session` + `agent` + `tool` 交界处），顺流读，比按字母序读模块高效得多。

---

## 七、注意事项与坑

1. **V2 vs legacy 并存**：项目正在做 V2 Session Core 重构，仓库里 V2（`SessionV2`、`SessionExecution`、`event` 表）与 legacy（`SessionPrompt.loop`、`message`/`part` 表）并存。读 `session/` 先判断是哪种，否则会学进将被删掉的设计。
2. **依赖方向**：Schema → Core/Protocol → Server，Client 不依赖 Core/Server。看到反向依赖要警惕。
3. **fork 改造约束**（`CLAUDE.md`）：品牌化优先用配置/env，不硬编码进核心源码；每次改动单独提交、写清「这是要保留的定制」；定期 `git fetch upstream && git merge upstream/dev`。
4. **同步方向永远是 `upstream/dev → main`**，learning 分支只 push 到 `origin`、从不 push `upstream`。
