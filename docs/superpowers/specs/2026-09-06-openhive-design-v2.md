## 0. 一句话结论

OpenHive 分**三层**：**opencode（能力内核，不动）→ skill（方法，长在 opencode 之上）→ 有形产物（成品，落回案件）**。它从「AI 编程工具」范式纠偏为「公安全流程 AI 工作平台」，价值不在 opencode 内核里，而在「内核之上 + 内核边界」。

## 1. 背景与目标

### 1.1 产品初衷：个人提效、组织增智

产品初衷是**个人提效、组织增智**。公安工作有很多业务场景、很多工作流程，**某一个环节的提效不能带来整个组织的系统提效**——只提升一个环节，组织整体效率上不去。因此 OpenHive 必须放眼**公安工作全流程**，让每个环节都能用 AI 提效。

**要时刻警惕「研判平台」的固有思维**：早期把 OpenHive 想成「研判平台」（话单/资金分析），这是把「全流程中的一个环节」误当成了「平台的定位」。情报研判只是全流程的一环，不是平台的全部。平台的定位是「公安全流程 AI 工作平台」，研判降级为其中一环。

全流程至少包括：

| 环节 | 典型工作 | AI 能交付什么 |
|---|---|---|
| 情报研判 | 话单分析、资金分析 | 研判报告、关系图谱、资金流向图、统计报表、**分析思路/结论** |
| 内勤文字 | 通知、总结、汇报、简报、会议纪要 | 各类公文（docx） |
| 方案制作 | 行动方案、工作方案、安保方案 | 方案文档（docx / pptx） |
| 考核督导 | 考核方案、督导报告、评分 | 考核报告（docx / xlsx） |
| 专项行动 | 行动方案、战果统计、专报 | 方案、战果报表、专报 |
| 案件办理 | 卷宗整理、侦查材料、文书 | 案件文书、材料清单 |
| 审讯取证 | 讯问提纲、笔录、取证清单 | 讯问提纲、笔录整理 |
| 报捕起诉 | 提请批捕、起诉意见、案卷 | 提请批准逮捕书、起诉意见书 |

**共性**：所有环节的产出，形态都收敛到「文档（docx）+ 表格（xlsx）+ 演示（pptx）+ 图（图谱/图表）」以及「结构化分析结论」。这是「中栏多形态内容区 + 交付层」能横向覆盖全流程的根本原因。

### 1.2 两个关键纠正（相对早期「研判工作台」定位）

1. **去掉数据脱敏与加密存储**：早期话单/资金分析设计了「敏感字段脱敏」。用户明确不需要——**这些数据（含身份证号、联系电话）本来就要研判分析，屏蔽或加密了怎么分析、反而带来工作不便**。故移除脱敏开关、列级脱敏、字段加密存储，分析对象始终明文可见，合规边界由 RBAC 权限控制，而非对数据本身做处理。
2. **分析思路/分析结论是一等公民**：研判不只是「看图出报告」，**分析思路（我为什么这么分析）和分析结论（我得出什么判断）本身就要能编辑、存档、对照**——这是「组织增智」的关键落点，老民警的思路能沉淀供新人对照，也是串并案的依据。

### 1.3 三层架构心智模型

OpenHive 分三层（cloudflare-os 拆解收敛出的核心心智模型）：

```
opencode = harness（能力内核，让大模型能持续正确干活）   → 不动
skill    = 方法（教 AI 怎么做事，含"先厘清再分析"）       → 全部长在 opencode 之上
产物     = 成品（五类：文档/表格/演示/图/分析记录）        → 落回案件、可重新打开、留痕
```

- **第一层 opencode**：agent 循环、上下文管理、工具调度、会话状态、模型调用。最难、最不可见、最不该重造，复用价值和「持续 merge upstream」都押在它身上。
- **第二层 skill**：业务技能包、研判记录、类案对照全部落地为 opencode 原生 skill，靠 `description` 自主触发。
- **第三层 产物**：opencode 天生产「改文件」，OpenHive 要「交付物」，只能在 opencode 之上补（是「缺」不是「变」）。

## 2. 已确认的核心决策

| 决策项 | 结论 |
|---|---|
| 产品定位 | **公安工作全流程 AI 工作平台**（情报研判只是其中一个环节） |
| 三层架构 | opencode（内核，不动）→ skill（方法）→ 产物（成品） |
| 前端路线 | **opencode 原生（SolidJS）换皮**，不走 React 自研（见 §5） |
| 隔离方式 | **每用户独立沙箱目录**（`/workspaces/{userId}/`）+ 每用户独立 SQLite |
| 模型凭据 | **企业统一模型（本单位）**，管理员配置，用户不感知 key；多单位路由走网关后手 |
| 认证方式 | **管理员录入 + 登录**（无自助注册；用户名 = 警号，默认密码，首次强制改密） |
| 用户规模 | 100+ 用户（实际并发活跃约 20~30%） |
| 业务数据 | **独立 PostgreSQL + RLS**（与 core 的每用户 SQLite 分开） |
| 中栏形态 | **多形态内容区**（数据/图表/文档/分析记录），代码编辑器降级为可选 |
| 「项目」→「案件」 | 一级对象对齐公安语境（案件聚合话单/资金/证据/产物） |
| 交付层 | AI 一键生成研判报告/关系图谱/资金流向图/统计报表/分析记录，**五类产物** |
| 分析思路/结论 | 可编辑、可存档、可对照，作为案件资产沉淀 |
| 业务技能包 | 「怎么分析」的方法资产（护城河），与交付层是同一链路的两段 |
| AI 资产治理 | Skill/MCP/知识库统一为「资产」，一套元数据/权限/生命周期 |
| 数据脱敏/加密存储 | **移除**（分析数据始终明文，合规靠 RBAC 而非脱敏或加密） |
| 扩展方式 | **注册式扩展**（视图/工作区/资产注册表），框架零改动 |
| 授权模型 | **capability 模型**（会话启动签发 scope 限定能力，执行层只认 capability） |

## 3. 总体架构（技术底座）

六个组件：

```
浏览器 ──HTTPS──▶ [网关 Nginx/Traefik]（唯一对外，验 JWT + 注入 X-User-ID + 亲和预留）
                      │
        ┌─────────────┼──────────────────┬─────────────────┐
        ▼             ▼                  ▼                 ▼
  [Auth 服务]    [opencode server]   [沙箱文件系统]    [模型网关]
   登录+用户管理   + 用户中间件        /workspaces/{userId}/  (多单位路由后手)
   用户表/JWT      + 每用户独立 db         │
                      │                   ▼
                      ▼              [业务数据 PG + RLS]
              [数据存储 SQLite]
              /data/{userId}/opencode.db
```

**三个贯穿全局的原则**：

1. **信任边界**：`X-User-ID` 是「网关 → opencode」的信任通道，opencode 绝不直接对外暴露（否则可伪造头冒充他人）。
2. **最小侵入**：opencode 源码只动「一个用户中间件」+「db 按用户路由」+「工具执行守卫」三处边界，不碰 `sql.ts` 表定义，保证可持续 `git merge upstream/dev`。
3. **物理隔离优先**：沙箱目录靠 OS 文件权限隔离（受限用户），应用层 bug 也拦得住。

**一次请求的数据流**：登录 → 网关发 Cookie → 携 Cookie 访问 → 网关验签注入 X-User-ID → opencode 中间件锚定沙箱目录 + 路由到该用户 db → AI 在沙箱干活 → session 写入该用户 db → 事件增量流入分析库。

### 3.1 opencode 内核边界三处必改（纠正「完全不动」的说法）

「内核不动」≠「opencode 零改动」。边界横切三处必改：

| 必改点 | 位置 | 为什么 |
|---|---|---|
| ① 用户中间件 | 请求入口 | X-User-ID → 锚定沙箱 + 路由每用户 db |
| ② Database 按用户路由 | database.ts | 全局单例 → Map<userId, 连接>（唯一深改 core） |
| ③ 工具执行守卫 | 工具 dispatch 入口 | capability / RBAC 下沉执行层 |

## 4. 账号与认证

### 4.1 用户表（Auth 服务内部，全新，不复用 opencode 的 `account` 表）

```sql
user (
  id             TEXT PRIMARY KEY,
  police_no      TEXT UNIQUE NOT NULL,   -- 警号（= 登录用户名）
  name           TEXT NOT NULL,          -- 姓名
  id_card        TEXT NOT NULL,          -- 身份证号（明文，研判对象）
  phone          TEXT NOT NULL,          -- 联系电话（明文，研判对象）
  org            TEXT NOT NULL,          -- 单位
  dept           TEXT NOT NULL,          -- 部门
  section        TEXT NOT NULL,          -- 科室
  status         INTEGER NOT NULL,       -- 状态（1 启用 / 0 停用）
  password_hash  TEXT NOT NULL,          -- argon2id
  is_admin       INTEGER DEFAULT 0,      -- 管理员
  must_change_pw INTEGER DEFAULT 1,      -- 首次登录需改密
  created_at     INTEGER NOT NULL
)
```

- **取消自助注册**：系统不提供注册入口，由**管理员后台**录入用户。
- **管理员录入**：填 8 字段 → 默认用户名（= 警号）+ 默认密码 `admin@123456`，`must_change_pw = 1`，并创建沙箱目录 `/workspaces/{userId}/`。
- **首次登录强制改密**：登录时检测 `must_change_pw = 1` → 进入主界面后弹窗强制改密；改密成功置 0。可「稍后修改」，下次登录再弹。
- **密码重置**：管理员后台可将用户密码重置回默认 `admin@123456` 并置 `must_change_pw = 1`。
- **登录**：校验密码 → 签发 JWT（`{ sub: userId, police_no, name, is_admin, exp }`，短期 2h）→ 网关下发 httpOnly Cookie。
- **敏感字段**：身份证号、联系电话**明文存储、明文展示**——它们本就是研判对象，屏蔽或加密会给研判分析带来不便。合规边界由 RBAC 权限控制（谁能看、看什么），而非对数据本身做脱敏或加密。
- **opencode 边界**：关闭自身 Basic Auth（不设 `OPENCODE_SERVER_PASSWORD`），只认网关注入的 `X-User-ID`，不碰密码逻辑。

### 4.2 治理后台（从「账号 CRUD」扩为四块）

仅 `is_admin = 1` 可见，入口在顶栏用户下拉「用户管理」。独立全屏视图。**早期只做了账号 CRUD，竞品对标后扩为「账号 + 组织 + 用量 + 审计」四块**：

| 块 | 内容 |
|---|---|
| 账号管理 | 用户列表、录入 8 字段、重置密码、停用/启用 |
| 组织架构 | 组织树（org/dept/section 三级），替换早期平铺列表 |
| 用量/成本 | 谁调了多少模型、token 数、各单位成本分摊（§5.4 分析库 → 管理员看板） |
| 审计 | §12.1 埋的审计日志，管理员检索界面 |

- 用户列表支持按警号/姓名/部门搜索；顶部统计注册总数与启用数。

## 5. 数据隔离与工作目录沙箱

### 5.1 数据库选型：保持 SQLite + 每用户独立文件（不换 PG）

- 换 PG 需改所有 `core/src/**/sql.ts`（`sqliteTable`→`pgTable`、`text({mode:"json"})`→`jsonb`、customType 重写、驱动、迁移），而这些是上游**最频繁改动**处，会造成持续 merge 冲突，违背最高约束。
- 每用户独立 SQLite：物理隔离 + 消除单写者并发瓶颈 + 零表结构改动 + 零运维（备份=复制文件）。
- 何时才换 PG：数千用户、跨机横向扩展、团队已有 PG 运维、需复杂跨用户聚合——当前场景均不涉及。
- **业务数据（话单/资金）另说**：那是 openhive 自己的模块，独立 PG + RLS（§12.1），与「core 的 sql.ts 不换 PG」不冲突。

### 5.2 每用户独立 db 的实现（唯一触及 core 架构处）

- 现状：`database.ts` 的 Database 是 `makeGlobalNode`（进程级单例，固定一个 `opencode.db`）。
- 改造三步：
  1. 仿照 `Location` 的 `LayerNode.unbound` 模式，新增 per-request 的 `User` 上下文（由中间件填 X-User-ID）。
  2. Database 内部维护 `Map<userId, 连接>`，每连接指向 `/data/{userId}/opencode.db`（惰性打开 + 复用 + 各自 PRAGMA）。
  3. db 查询从 User 上下文取 userId → 路由到对应连接。
- **零表结构改动**：物理隔离后 `session` 表无需加 `user_id` 列，不碰 `sql.ts`。

### 5.3 工作目录沙箱（三层隔离）

沙箱是「每用户一个根目录、内部按案件分隔离子目录」，保留 opencode 原生的 project 概念（project = 案件的技术载体）：

```
/workspaces/{userId}/          ← 用户根（用户隔离边界）
  ├── case-A/                  ← 案件 A（独立 git 仓库）
  ├── case-B/                  ← 案件 B
```

三层隔离：

| 隔离维度 | 文件层 | 会话（session）层 |
|---|---|---|
| 用户 vs 用户 | `/workspaces/{userId}/` 目录隔离 | `/data/{userId}/opencode.db` 独立 db（物理隔离） |
| 案件 vs 案件 | `/workspaces/{userId}/{case}/` 子目录 | `session.project_id`（逻辑隔离） |
| 会话 vs 会话 | 案件目录内 git 改动 | `session_id`（天然隔离） |

> **通俗理解「沙箱目录」**：每个用户在服务器文件系统上「自己的那块硬盘空间」，路径 `/workspaces/{userId}/`，`{userId}` 是隔离边界。AI 会话干活、创建案件、读写文件全被关在这个目录里，别人的目录看不见也碰不到。靠两道锁保证「出不去」：① 应用层锚定（忽略客户端传入 `directory`，防越权）；② OS 层兜底（进程以受限用户运行，文件权限只放行自己名下目录）。

- 中间件把请求工作目录**强制锚定**到沙箱根。
- opencode 容器以受限系统用户运行（OS 层兜底）。
- 需要「案件创建/导入」入口：web UI 里在沙箱内新建子目录 + `git init`，或上传数据。

### 5.4 跨用户分析（读写分离）

- 主库（每用户 SQLite）管隔离，独立**分析库**管聚合。
- 复用 opencode 事件溯源（`event` 表 + `SyncEvent`），增量抽取 prompt + 元数据到分析库。
- 分析库独立选型：MVP 聚合 SQLite；需全文检索再上 PG/ES；主题聚类可用大模型。
- **分析库的另一落点**：管理员「用量/成本看板」（§4.2）从这里来——谁调了多少模型、token 数、成本分摊。

## 6. 执行并发与资源隔离

- opencode 已天然支持「不同 Session 并发」（`SessionRunCoordinator`：同 Session 串行、异 Session 并发，Effect fiber + 模型 I/O 密集）。
- 共享单进程 + 并发上限：中间件 + `SessionExecution` 层加「每用户活跃 Session 计数」。
- 三层配额：每用户并发 Session 数（中间件计数）、模型调用速率（网关 rate limit）、沙箱磁盘配额（Linux quota / docker volume）。
- 并发量级：单进程几十～上百并发活跃会话；100+ 用户（20~30 并发）在舒适区；**真实拐点靠压测**；瓶颈更可能在企业模型吞吐而非 opencode 进程。

### 6.1 水平扩展（后手）

- **现在预留**（成本≈零）：网关层用户亲和配置（sticky/一致性哈希）+ 每用户独立目录结构。
- **将来做**（有真实成本）：起多进程并验证 process-local 组件在多进程下的行为。

## 7. 模型配置

### 7.1 opencode 现状（源码级结论）

模型配置由 `Config.Service` 进程启动时加载一次，落成**进程级全局** `provider` 配置，所有 session 共用，**没有「按用户区分 provider/模型」的概念**。三个入口按优先级合并：配置文件 `opencode.json`、环境变量、`opencode auth login`。

### 7.2 改造后落点

- **当前（统一本单位模型）**：配置点就是现状位置，零改动——容器注入环境变量（或挂载只读 `opencode.json`），管理员配置、用户无感知。
- **未来（多单位模型路由）**：opencode 是「进程级一套配置」，自身无法按用户切模型，**必须前置模型网关**——opencode 侧永远只配一个 `openai-compatible` 入口（baseURL 指向网关），网关按 `X-User-ID` 路由到各单位真实端点并做配额 + 优先级。
- **统一抽象**：模型配置抽象成 provider 列表 + openai-compatible 兜底，新增单位 = 网关加一条路由 + 配额。

## 8. 前端：opencode 原生换皮 + 三栏重定义

### 8.1 前端路线（已定）：opencode 原生，不走 React 自研

Figma 蓝图里约 70% 的功能是在「重画 opencode 已有的东西」（右栏会话、文件树、代码编辑器、模型选择器、Effort、设置、会话管理、通知、全屏）。这些 opencode 原生做得更全更好，且是 SolidJS——与 Figma 的 React 互不相容。**结论：复用 opencode 原生前端做品牌换皮 + 补齐三个缺失功能（治理后台 / MinIO 备份 / 站内信），Figma 蓝图定位为「视觉风格参考 + 交互规范」，不是最终部署前端。**

opencode 前端结构（源码级）：
- 左侧 rail（`sidebar-rail`，项目图标竖条）＝ Figma 的图标栏。
- 中栏（session 主内容区，`<Switch>` 渲染 `MessageTimeline` 或 `NewSessionView`）。
- 右栏（`SessionSidePanel`，review/文件树，可折叠拖拽）。
- 模型选择器、Effort、通知、设置、文件树、会话管理、全屏、导出会话——全部原生已有，直接用。

### 8.2 三栏重定义：左导航 / 中看改 / 右 AI 会话

早期「资源管理器/代码编辑器/AI 会话」是 **IDE 心智**——中栏默认是代码编辑器，系统更像一个 IDE。但**用户大多是不懂代码的民警**，中栏带程序员思维是他们用不起来、觉得「这是给程序员用的」的根因。因此做这次心智改变：

| 栏 | 职责 | 一句话 |
|---|---|---|
| 左栏 | **导航**（案件列表、文件树、会话） | 「去哪个案件、看哪个文件」 |
| 中栏 | **看改**（内容工作区：看结果 + 改结果 + 交互） | 「查看结果、进行交互的地方」 |
| 右栏 | **AI 会话**（分析、生成、问答） | 「让 AI 干活的地方」 |

**一句话心智**：中栏是用户「看结果、改结果」的地方，右栏是用户「让 AI 干活」的地方——用户不写代码，也不应该面对代码。

**中栏从「代码编辑器」翻转为「多形态内容区」**（§9）——民警最高频的 Word/Excel/PPT/思维导图/图文混排/数据明细/可视化图表都是中栏一等公民，按内容类型自动切换视图；代码编辑器降级为「少数技术用户的可选工作区」，不再是默认、也不再是主角。

### 8.3 顶栏、图标栏、登录、改密、设置

- **顶栏**：左侧品牌 Logo（OpenHive）；右侧站内信（未读红点）、全屏、用户下拉（个人信息/修改密码/用户管理/退出登录）。
- **图标栏**（rail）：项目图标 + 「案件」入口，底部「⚙ 系统设置」。
- **登录页**：由 Auth 服务提供（独立，无自助注册）；浅色专业风、深色背景图 + 白色卡片；警号 + 密码；无注册入口；登录失败统一提示「账号或密码错误」。
- **首次改密弹窗**：全屏遮罩锁死；当前密码 + 新密码（强度条）+ 确认；「确认修改」/「稍后修改」。
- **系统设置面板**：常规 / AI 引擎（默认模型）/ 云端备份策略三块。**「数据脱敏规则」这一 Tab 已移除**（脱敏移除，§1.2）。
- **站内信**：扩展现有 notification（原生只有 turn-complete/error 两种 AI 事件）为三类（系统/AI/文件）+ 未读红点 + 下拉面板 + 标记已读。

## 9. 中栏多形态内容区 + 交付层

### 9.1 中栏是「内容工作区」，不是只读展示区

中栏承载数据/图表/结论/文档四类内容，每种不仅「看」还要「动」：

| 内容类型 | 格式 | 中栏视图 | 能力等级 |
|---|---|---|---|
| Word 文档 | `.docx` | 文档预览 | 在线预览 + 拖拽到本地编辑 |
| Excel 表格 | `.xlsx` | 表格预览 | 在线预览 + 拖拽到本地编辑 |
| PPT 演示 | `.pptx` | 幻灯片预览 | 在线预览 + 拖拽到本地编辑 |
| PDF | `.pdf` | 翻页预览 | 在线预览 |
| 思维导图 | `.xmind` / `.md` | 导图视图 | **在线编辑** |
| 图文混排 | `.md` / 富文本 | 富文本编辑器 | **在线编辑** |
| 图片 | `.png` / `.jpg` | 图片预览 | 在线预览 |
| 话单数据 | 数据表 | 明细表 + 关系图谱 | 查询 + 可视化 |
| 资金数据 | 数据表 | 明细表 + 桑基图 | 查询 + 可视化 |
| **分析记录** | 富文本 + 结构化 | 分析记录视图 | **在线编辑 + 对照** |
| 代码 | 源码 | 代码编辑器 | 保留（降级为可选） |

- **视图路由**：一个「内容视图注册表」`扩展名 → 视图组件`。文件树点文件 → 查注册表 → 中栏渲染对应视图。新增格式只需注册新视图，框架零改动。
- **注册式扩展**：中栏视图、工作区、AI 资产全部「注册 = 新增，框架零改动」，一条统一抽象让注册制跑得起来。

### 9.2 文档编辑方式：拖拽出 ↔ 拖拽回

复用上传/下载能力，以「拖拽」呈现：

```
文件树里的 .docx/.xlsx/.pptx
   →（拖拽出浏览器到本地桌面）= 下载
   → 本地用 WPS/Office 编辑
   →（拖拽回资源管理区）= 上传 → 覆盖原文件（git commit 留痕）
```

- 不部署 OnlyOffice，不自研重编辑器——Office 文档用「AI 生成 + 在线预览 + 拖拽到本地编辑 + 拖拽回」。
- 思维导图/图文混排/分析记录用轻量编辑器**在线编辑**。
- 版本留痕靠 git，不搞额外版本系统。

### 9.3 交付层：五类产物，通用生成链路

**完成判据（产物即完成）**：一次 AI 工作交互的「完成」= 一个交付物已落回案件空间、可重新打开、git 留痕；否则「本轮未交付」。

五类产物（**别漏第五类**）：

| 类别 | 形态 | 说明 |
|---|---|---|
| 交付物 | 文档 docx | 研判报告、公文、方案、文书 |
| 交付物 | 表格 xlsx | 统计报表 |
| 交付物 | 演示 pptx | 方案汇报 |
| 交付物 | 图（图谱/图表） | 关系图谱、资金流向图、时序图 |
| **过程资产** | **分析记录** | 分析思路 + 分析结论（一等公民，护城河落点） |

**通用生成链路（全流程共用）**：

```
民警勾选数据 / 结束一段分析 / 指定一个环节
   → 点右栏「生成」
   → AI 汇总会话上下文 + 选中数据 → 产出结构化内容
   → 套用「环节模板」（单位抬头、字体、段落、落款）
   → 生成 .docx（可另存 PDF）/ .xlsx / .pptx
   → 中栏自动打开预览
   → 一键存回案件空间（文件树可见，随案件归档）
```

- **模板 + 结构化字段填充**（而非 AI 自由排版），保证全单位格式统一，对标千问「PPT 保留母版」。
- **一个技能 → 多个交付物**：同一套结论，选「出报告」出研判报告、选「出图」出关系图谱、选「出表」出统计报表。
- **模板体系**：管理员后台配「报告模板」「图谱样式」「报表口径」及全流程各环节文书模板。

### 9.4 关系图谱 / 资金流向图 / 统计报表

- AI 从话单/资金数据**抽取实体关系**（人、号码、账户、交易往来），产出结构化关系数据，中栏用图库渲染**可交互图谱**（拖拽/缩放/筛选/钻取），可导出图片插入报告。
- 统计报表：AI 汇总关键指标，套报表模板生成 `.xlsx`（带公式样式）。

### 9.5 技术选型（实现时验证）

| 能力 | 建议方案 |
|---|---|
| Word/Excel 预览 | docx-preview / SheetJS（纯前端） |
| PPT 预览 | LibreOffice headless 转图片/PDF |
| 思维导图 | markmap（Markdown → 导图） |
| 图文混排/分析记录 | TipTap（富文本）+ frontmatter |
| 关系图谱 | AntV G6 |
| 桑基/统计图 | ECharts |
| 文书生成 | docx 模板 + docxtemplater 填充 |

> 全部内网可自建，无外部 SaaS 依赖。

## 10. 分析记录 + 业务技能包（护城河）

### 10.1 分析思路/分析结论：人主动复盘 + AI 结构化

分析工作的产出不只是「一张图、一份报告」，而是**一套分析思路和判断**。若只存在会话里、随会话翻篇，经验就流失了。结构化、存档、可对照，才能让个人经验沉淀为组织资产。

**关键前提（纠正「AI 自动归纳」的误区）**：AI 只能捕获「可观测的行为」（勾了哪些数据、问了 AI 什么、改了什么），**捕获不了「脑内的思考」**（为什么先看频次而非资金、否掉 AI 结论的真实理由）。所以「AI 边分析边归纳分析思路」在自动归纳意义上是危险的——会沉淀出「看似有理、实则是 AI 脑补」的伪经验。

**因此原则改为：思路由人主动复盘，AI 只做结构化**。

| 能力 | 人（民警） | AI（辅助） |
|---|---|---|
| 编辑 | **主动复盘讲思路**：告一段落时用几句话讲「我先看什么、为什么；发现什么关键点；得出什么判断、还差什么没查」 | 把人的复盘**结构化、补充、归档**为草稿，不从行为痕迹里猜测思路 |
| 存档 | 「定稿」后才进入正式对照与串并案 | 每个阶段自动存「草稿快照」，经验不丢 |
| 对照 | 发起对照 | 对定稿做辅助检索（相似案件/类案推荐） |

**对照三种形态**：纵向（同一案件不同阶段思路演进）、横向（不同案件并排比对，支撑串并案）、学习（新人对照成熟范式）。

**数据形态**：`结构化字段（案件、环节、时间、作者）+ 富文本正文（思路 + 结论）+ 关联引用（数据行/图谱节点/文件）`，存储复用文件树（Markdown/frontmatter），git 留痕。

> **关于「老民警」的定位**：老民警是「候选池标签」（资历深 → 大概率有货），**不是「经验可信」的质量标签**——资历深 ≠ 分析对。分析结论的正确性在研判场景里常常滞后、稀疏，不能作为沉淀门槛；能作为门槛的是「过程质量 + 同行评议 + 使用反馈」。详见 `../discussions/知识沉淀/2026-09-06-老民警经验如何沉淀为skill.md`。

### 10.2 实现机制：封装为 skill（软触发，不做硬钩子）

不新造「钩子 + 抽取工具」，复用 opencode 原生 skill 机制：

| 能力 | 落成 | 触发方式 |
|---|---|---|
| 结构化复盘（辅助归纳） | `研判记录` skill：把人主动讲出的思路/结论，从会话上下文 + 勾选数据补全为结构化 JSON | 民警告一段落/点「结束会话」时触发；AI 也可在分析告一段落时提醒「是否记录本次思路」 |
| 存档（写草稿） | 同一 skill 内动作：写 Markdown + frontmatter + git commit | 结构化完自动落盘 |
| 对照（类案检索） | `类案对照` skill：向量检索相似定稿记录 | AI 需要参考历史时自主调用 |

- **软触发为主**（description + prompt 约定「该调时调」）+ 关键节点显式提醒（点「生成图谱」「结束会话」时主动触发），**不做硬事件钩子**。
- **思路源头是人，不是 AI**：`研判记录` skill 的结构化对象，是民警主动讲出的思路（§10.1），而非 AI 从行为痕迹里自动推断的思路。
- **需求厘清内嵌进 skill 开头**：不是 skill 之外独立的前置环节，而是每个业务 skill 的第一步即厘清输入/目标。

### 10.3 业务技能包与交付层：一条链路的两段

| | 公安业务技能包 | 交付层 |
|---|---|---|
| 本质 | 分析的过程 / 方法 | 分析的成品 / 输出 |
| 回答 | 「拿到数据，怎么下手分析」 | 「分析完了，怎么变成能交的东西」 |
| 沉淀 | 老民警的分析套路（话单关系分析、资金链路追踪、涉案画像、同案串并） | 全环节格式模板 |
| 对标 | WorkBuddy「数字员工/技能市场」 | 千问「交付型 AI」 |

**衔接点 = 结构化分析结论**：技能驱动 AI 拆数据产出结论，交付层把结论灌进模板产出成品。

- 只有技能没有交付层 → 分析到位但结论停在会话里，价值链在成品处断掉。
- 只有交付层没有技能 → 模板再漂亮，AI 不懂公安分析套路，空有格式没内涵。

**一句话**：技能是护城河（公安业务经验，竞品没有），交付层是价值出口（成品一键落地）。

## 11. AI 资产治理（Skill / MCP / 知识库）

### 11.1 统一抽象：三类资产，一套治理

| 资产类型 | 本质 | 落地载体 |
|---|---|---|
| Skill | 方法/流程（怎么分析） | opencode 原生 skill |
| MCP | 工具/接口（能查什么、调什么） | opencode MCP + 自研 connector |
| RAG 知识库 | 资料/事实（某规定是什么） | RAGFlow |

三者运行时是一条链（Skill 编排 → 调 MCP 拿数据 → 查知识库拿资料），治理上必须一套元数据、一套权限、一套生命周期。

**统一资产元数据**：名称、ID、类型、描述、图标、标签；所有者、所属部门、可见范围（全局/部门/个人）；版本号、变更说明；状态（草稿/审核中/已发布/已下线/已归档）；启用数、使用次数、评分、反馈。

### 11.2 三级资产空间 + 四类权限

| 层级 | 可见范围 | 维护者 |
|---|---|---|
| 全局资产 | 全单位可用 | 系统管理员 + 业务管理员 |
| 部门资产 | 本科室可见 | 部门业务管理员 |
| 个人资产 | 仅本人可见 | 民警自己（私藏草稿） |

四类权限动作（挂到已有的 `role/role_resource`，资产即一种资源类型，不新造体系）：
- **读**（看到、使用）、**写**（编辑内容）、**审**（审核内容、批准上线）、**管**（上下架、删除、批量授权）。

### 11.3 角色分工（审核权在业务专家，与 IT 分离）

| 角色 | 谁担任 | 职责 |
|---|---|---|
| 系统管理员 | 科信/IT | 平台运维、账号、全局资产上下架、用量/审计 |
| 业务管理员 | 法制/业务骨干/老民警专家 | **审核 skill 内容质量与业务正确性**、批准上线 |
| 资产作者 | 业务骨干 + AI 辅助 | 制作 skill、维护知识库、响应反馈迭代 |
| 使用者 | 全体民警 | 启用/使用、评分、反馈 |

**关键原则**：skill 是业务经验的封装，审核权必须在业务专家手里，不能只走 IT。IT 管技术合规（能跑、不出错），业务专家管内容正确（套路对不对、结论可不可信）——两者分离。

### 11.4 Skill 制作：低门槛 + 业务专家主导 + AI 反向生成

老民警不会编程，制作门槛必须低。三种递进方式：

| 方式 | 做法 | 适合谁 | 门槛 |
|---|---|---|---|
| ① AI 反向生成 | 分析记录（定稿）一键「沉淀为 skill **草稿候选**」，AI 从「这次怎么分析的」自动生成草稿 | 所有民警 | 零 |
| ② 自然语言编写 | 大白话描述「我遇到这类案件怎么分析」，AI 转成结构化 skill | 业务骨干 | 低 |
| ③ 模板配置 | skill 模板填关键字段（适用场景/输入/步骤/输出） | 进阶作者 | 中 |

**核心闭环（纠正「一键发布」的误区）**：`分析记录（定稿）→ 生成 skill 草稿候选 → 多案例归纳 + 人工确认「可泛化」→ 发布 → 供他人复用`。

- **单案例 ≠ 方法**：一份分析记录是「个案」，skill 需要的是「可泛化的套路」（「8·17 先查主叫频次」是案例，「遇诈骗话单先锁高频主叫再追资金」才是方法）。所以「一键沉淀」产出的是**草稿候选**，必须经过「有没有同类案例支撑 + 业务专家确认可泛化」的抽象检验，才谈得上发布。
- 这是「个人提效」迈向「组织增智」的关键动作——但「老民警的一次分析」要先变成「多个同类案例的共性」，才能变成「全单位可复用的技能」。

### 11.5 Skill 生命周期 + 启用

状态机：`草稿 → 提交审核 → 审核中 → 已发布 → 迭代中 → 已下线 → 已归档`（驳回退回草稿）。

- **上线流程**：提交 → 业务审核（业务管理员审正确性 + 可泛化性）→ 技术发布（系统管理员查能跑/无安全问题）→ 上架资产中心。
- **启用 = 授权 + 加入可用清单**（不是复制代码）：资产是共享的，启用 = 授权可见可用，复用 RBAC 而非拷贝。
- **批量授权**：管理员可把某资产一键启用到整个部门。
- **反馈**：评分（1–5 星）+ 文字 + 问题标记，回流给作者 + 业务管理员驱动迭代。
- **介绍页**（业务语言写，民警看得懂）：是什么 / 适用场景 / 怎么用 / 示例 / 注意事项 / 版本记录。**其中「注意事项」必须是显式的「不确定性标注」**——明确写「AI 可能在哪些地方不准、必须人工复核什么」，不能给新人一个「一键出正确结论」的幻觉。
- **纠错通道**：skill 的「权威性」是挣来的，不是发布时就有。发布后若发现会误导，要能快速下线、标记、迭代；使用数据（出错率、被纠错次数、低分反馈）反过来决定 skill 的存废。

## 12. 数据接入框架

公安各环节工作的数据来源远不止旧系统（蜂巢/小蜜蜂）——运营商话单、银行流水、社保、轨迹、OSINT 开源情报。抽象「数据源接入层」：

- **数据源注册**：每种来源注册一个数据源（类型、连接信息、更新频率）。
- **连接器（connector）**：统一抽取/清洗接口，话单/资金模块的数据层都基于这一层。
- **字段明文**：数据源接入时所有字段（含身份字段）保持明文，不做脱敏或加密（§1.2）。
- **血缘追踪**：某条数据从哪个源来、经过哪些处理。

> 这是 P2，依赖旧系统改造节奏，别过早做，但要留接口。

## 13. 共享案件（协作）

在「数据隔离」之上开「有边界的共享口子」。早期只共享「文件」，竞品对标后补「协同工作」（有边界地增强）。

### 13.1 共享边界：共享「结果」，不共享「过程」

- **会话（session）彻底私有**：每个成员和 AI 的对话只存自己 db，任何人（含 owner）看不到别人的会话。
- **权限只设 owner / member 两级**：成员进来就是 member（协作编辑者），owner 负责建/邀/删。不设 viewer「只读旁观」角色。
- **文件并发靠 git**：各自 commit、冲突 merge，不做实时协同编辑。

### 13.2 协同工作增强（有边界）

公安办案强调保密与留痕，不宜照搬 WorkBuddy 的开放协同。在共享案件内增加：

- **共享结论 / 标注 / 工作进度时间线**：多民警合办案件时，共享的是「分析结论、证据链、工作进展」，而不只是文件。
- **仍保持**：会话私有、全程审计留痕、权限最小化。

### 13.3 数据模型

- `project` 表加字段：`type`（`private`/`shared`）+ `shared_directory`（指向 `/shared/{projectId}/`）。
- 新增 `project_member` 表：`project_id` + `user_id` + `role`（`owner`/`member`），唯一约束 `(project_id, user_id)`。

## 14. 安全

### 14.1 capability 模型（授权下沉执行层，核心升级）

早期 §12.1 是「运行时三层拦截」。cloudflare-os 拆解后升级为 **capability 模型**：

**会话启动时**按「用户 + 案件 + 勾选数据范围」签发 scope 限定的 capability；**工具执行器入口只认 capability**，不认角色表、不靠提示词。

| 层 | 拦截点 | 机制 |
|---|---|---|
| ① 工具清单过滤 | 组装 tools 传给模型前 | 按 capability 过滤，只把有权工具放进 tools——AI 看不到 A 就调不了 A |
| ② 工具执行鉴权 | tool 执行器入口 | 执行前再验 capability，无权限返回 AccessDenied + 记审计 |
| ③ MCP 端账号兜底 | MCP server/数据库账号 | 带 user 身份，受限账号执行，GRANT/RLS 最终兜底 |

**为什么必须下沉执行层**：AI 是 agent，会自己挑工具，「提示词里说别用」不可靠（可能被 prompt injection 诱导或幻觉），必须在工具执行链路上硬拦。前端「只展示有权用的」只是 UX，不是安全。

### 14.2 数据权限：业务数据 PG + RLS（五级控制）

业务数据（话单/资金）独立 PostgreSQL + RLS：

| 级 | 控制点 | 机制 |
|---|---|---|
| 连接级 | 谁能用这个 MCP | `user → mcp` 授权表 |
| 账号级 | 能查哪些表/列、只读还是可写 | 每角色独立受限数据库账号 + GRANT |
| 行级 | 能查哪些行（数据范围） | PG 原生 RLS（`CREATE POLICY`） |
| 结果量级 | 查多少条 | MCP 层强制 LIMIT + 分页 + 导出需更高权限 |

> 原「列级脱敏」一档**已移除**（分析数据始终明文，合规靠 RBAC/RLS 而非脱敏，见 §1.2）。

### 14.3 统一 RBAC（角色为主 + 用户例外）

```sql
role:           role_id, name
user_role:      user_id, role_id
role_resource:  role_id, resource_type, resource_id, perm
-- resource_type ∈ {skill, mcp, knowledge_base}
-- 资产权限动作 perm ∈ {读, 写, 审, 管}（§11.2）
```

### 14.4 安全清单（按风险排序）

1. 信任边界：opencode 零对外端口，物理上无法绕过网关。
2. 隔离越权防护：强制锚定沙箱 + 每用户独立 db + OS 文件权限。
3. 密码/Cookie：argon2id + 统一登录失败响应 + HttpOnly/Secure/SameSite。
4. 模型凭据不泄露：key 只在容器环境变量，用户无覆盖入口。
5. 全部字段（含身份证/电话）明文，合规靠 RBAC/RLS 权限约束，不做脱敏或加密。

### 14.5 错误处理与测试

- 未登录/过期 → 网关 401 → 重定向登录；db 打开失败 → 「账户数据异常，联系管理员」；并发/配额超限 → 明确提示。
- **隔离测试（最重要验收项）**：用户 A 访问用户 B 的目录/db 必须被拒。
- 并发压测、安全测试（路径穿越、SQL 注入、未授权直连、越权读他人数据）。

## 15. 关键技术风险与应对

| 风险 | 应对 |
|---|---|
| Database 从全局单例改成按用户路由（唯一深改 core） | 仿照 Location 已验证的 unbound/bound 模式 |
| 持续 merge upstream/dev 冲突 | 不碰 `sql.ts`，侵入点收敛到「中间件 + db 路由 + 工具守卫」三处边界 |
| 企业模型吞吐成为瓶颈 | 上线前压测模型，必要时先扩模型而非 opencode |
| 多进程扩展时 process-local 组件行为未知 | 列为明确扩展项 |
| 交付层「成品」opencode 天生没有 | 是「缺」不是「变」，只能在 opencode 之上用 skill + 模板补，改不出来 |
| 图谱数据抽取准确率 | 规则 + 大模型校验，内网模型能力待验证 |

## 17. 必须钉死的点（纠正记录，防滑回）

| # | 易滑回的说法 | 纠正后的正确说法 |
|---|---|---|
| 1 | opencode 完全不动 | 内核不动，边界三处必改（中间件/db 路由/执行守卫） |
| 2 | skill 自动触发 | 软触发 + 关键节点显式提醒，不做硬钩子 |
| 3 | 四类产物 | 五类产物，含「分析记录」（过程资产，护城河） |
| 4 | 用户「下载安装」skills | 「启用 = 授权 + 加入可用清单」，不是复制代码 |
| 5 | IT 封装 skills | 业务专家是内容源头，AI 反向生成加速，IT 只兜底技术 |
| 6 | 先厘清需求再调 skill | 需求厘清主要长在 skill 内部（skill 第一步即厘清输入/目标） |
| 7 | 交付层靠「改 opencode」加出来 | 「成品」概念 opencode 天生没有、改不出来；只能在 opencode 之上用 skill 补（是「缺」不是「变」） |
| 8 | 全流程 8 个环节一次铺满 | 全流程梳理眼界要对，但落地分期——先做情报研判这一环，再横向复制邻近环节 |
| 9 | 审核走 IT 一道关 | 审核权在业务专家（审套路对不对、结论可不可信），IT 只审技术合规，两者分离 |
| 10 | 话单/资金/身份证/电话做脱敏或加密 | 所有业务数据始终明文（屏蔽或加密了怎么分析、反而添不便），合规靠 RBAC/RLS 而非脱敏或加密 |
| 11 | 中栏是代码编辑器 | 中栏是多形态内容区（数据/图表/文档），代码降级为可选 |
| 12 | OpenHive 是「研判平台」 | 平台定位是「公安全流程 AI 工作平台」，研判只是全流程中的一环；初衷是个人提效、组织增智，单环节提效带不来组织系统提效 |
| 13 | 中栏是「代码编辑器」（IDE 心智） | 三栏心智是「左导航 / 中看改 / 右 AI 会话」；用户是不懂代码的民警，中栏是「看结果、改结果」的内容工作区，右栏才是「让 AI 干活」的地方 |

## 18. 待决策点

1. **「案件」命名与结构**：是否正式把「项目」重命名为「案件」？案件字段（案件编号、性质、承办人）何时补齐？
2. **真实用户与核心场景确认**：核心用户是否确为民警？话单/资金分析是否为最高频场景？「代码编辑」是否基本无用（决定范式纠偏是否成立）？
3. **交付层优先级 vs 工期**：是否接受「先做报告生成，图谱/报表次之」的分期？
4. **拖拽回的文件冲突**：拖回同名文件默认「覆盖 + commit」，是否需要「另存为新版本」选项？
5. **思维导图格式**：`.md`（markmap）还是 `.xmind`（导入导出）？
6. **图谱数据抽取**：实体关系靠「大模型直接抽取」还是「规则 + 大模型校验」？
7. **分析记录结构化程度**：自由富文本 + frontmatter，还是字段级拆分？影响「对照」实现难度。
8. **资产中心形态**：独立「技能市场」页面，还是嵌入左栏资源面板？倾向后者（复用现有面板，最小侵入）。
9. **知识库管理粒度**：RAGFlow 按「案件一个库」还是「主题一个库」（法条库/办案规范库/历史案例库）？
10. **首批公安研判技能包清单**：话单关系分析、资金链路追踪、涉案画像、同案串并…需业务专家（老民警）输入。
11. **全流程环节接入优先级**：情报研判之外，哪些先接入？建议从「文书生成复用度最高、与研判最邻近」的环节切入。
