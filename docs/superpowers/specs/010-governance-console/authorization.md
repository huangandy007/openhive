## 2. 两类管理员

### 2.1 定义

| 类型 | 岗位（spec US1） | 职责原文（FR-003） |
|---|---|---|
| 系统管理员 | 科信 IT | 管**账号 / 组织 / 运维 / 技术合规** |
| 业务专家 | 法制骨干 | 管**内容审核 / 模板口径 / 数据项目授权** |

两类都**不是**资产的天然审核人：009 的 D0-4 明确 `is_admin` 只是治理后台总开关，
**不是**资产审核权；某一份资产能不能审/发，仍由该资产的授权行决定（§5.4）。

### 2.2 不硬互斥（为什么）

- RBAC 的 `user_role` 天然允许一个用户名下挂多个角色（`packages/auth/src/rbac.ts`）。
- 硬互斥要加一列/一条约束，却只表达**组织纪律**，不表达能力；组织纪律不归本系统管。
- SC-002「互不越界」的判据是**权限集合**，不是「一个人只能有一类角色」——
  T014 测的是「只有 A 模板的人做不了 B 的动作」，一人兼两类时自然两类都能做，不构成缺陷。

**代价要写清**：一人兼两类时，两张模板的权限**取并集**；若将来要求「同一页面两类权限互斥」
（例如一人不能既审又发同一份资产），那是 009 的**资产级**判定，不是本矩阵能表达的。

### 2.3 `is_admin` 是总开关

- 009 的 D0-4 把 `is_admin` 保留为「治理后台总开关」（`../009-ai-assets/authorization.md:136`）。
- 因此：`is_admin = 0` 的用户即使被误挂了治理授权行，也**进不了后台**，更不能调管理动作。
- 这道门由服务端执行（FR-013）；前端隐藏入口只是界面收敛（宪法 §IV）。

## 3. 权限矩阵

### 3.1 维度

| 值 | 在治理后台的含义 |
|---|---|
| `read` | 能**进入**该板块（T001 的导航可见、页面可打开） |
| `write` | 能**配置/增改**该板块的对象（录入账号、改组织树、注册数据源、改模板） |
| `review` | 能做**业务审核**（通过 / 驳回） |
| `admin` | 能**技术发布 / 兜底管理**（发布、上下架、归档、撤销成员） |

两个刻意的约定：

1. **四值互不蕴含**（沿 009 `authorization.md` §2.1）：`admin` **不**蕴含 `review`。
   否则一个人既能审内容又能发布，009 的「业务审核 + 技术发布分离」当场失效。
2. **进门要 `read`**：任何动作都假定调用者对该板块有 `read`；矩阵里给动作的格子
   同时隐含 `read`，不单独重复写。

### 3.2 主表

| 板块（id） | 系统管理员 | 业务专家 | 出处 |
|---|---|---|---|
| 账号管理 `account-manage` | `read` + `write` | — | FR-003（账号）；FR-004；US2 |
| 组织架构 `org-tree` | `read` + `write` | — | FR-003（组织）；FR-005；US2 |
| AI 资产治理 `asset-governance` | `read` + `admin` | `read` + `review` | FR-003；US3；009 `lifecycle.md` §2 触发者列 |
| 模板库 `template-lib` | — | `read` + `write` | FR-003（模板口径）；US6 场景 1 |
| 数据项目权限 `data-project-perm` | — | `read` + `admin` | FR-003（数据项目授权）；FR-007；US4 |
| 用量成本 `usage-cost` | `read` | — | FR-003（运维）；US5 |
| 审计日志 `audit-log` | `read` | — | FR-003（技术合规）；FR-009；US5 |
| 数据源配置 `data-source` | `read` + `write` | — | FR-003（运维/技术）；FR-011；US6 场景 2 |

`—` = 连 `read` 都没有 ⇒ T001 的导航里**不出现**这一项（`filterGovernanceSections` 按 id 过滤）。

**id 对账**（改任一侧都要回来跑；`LEARNINGS #002-06`）：

```bash
grep -oE 'id: "[a-z-]+"' packages/app/src/governance/sections.ts
```

八个 id 必须与上表第一列逐字相同。

### 3.3 AI 资产治理页内的动作细分

页面**两类都能进**（都有 `read`），页内动作按 009 的流转表分权——
**不另造一套触发者，照抄 009**：

| 动作 | 触发者（009 `lifecycle.md` §2） | 本矩阵的格子 |
|---|---|---|
| `submit_review` / `start_iteration` | 作者 | 治理后台不代作者提交；不授予两类管理员 |
| `approve_business` / `reject_business` | 业务管理员 | 业务专家 `review` |
| `publish_tech` / `publish_iteration` / `take_offline` / `archive` | 系统管理员 | 系统管理员 `admin` |
| `bring_online` | 作者 / 系统管理员 | 系统管理员 `admin`（作者那半在工作台，不在后台） |

MCP 与知识库（009 的生命周期未展开，此处的动作归属是**职责推定**，T007 落码时复核）：

| 动作 | 系统管理员 | 业务专家 |
|---|---|---|
| MCP 配置（注册 / 连接 / 启停） | `write` | — |
| MCP 授权下发（谁能用：部门 / 角色 / 身份三层） | — | `admin` |
| 知识库内容与可见范围 | — | `write` |
| 知识库技术发布 / 删除 | `admin` | — |

⚠️ 这三行**没有 009 的流转表背书**，是 FR-003 职责划分的延伸。T007 若发现与 009 现有判定冲突，
以 009 执行层为准，并回来改本表——**别让文档与执行层各说各话**。

### 3.4 为什么用量/审计不给业务专家

FR-003 把「运维 / 技术合规」整块给了系统管理员；SC-002 要求「互不越界」。
给业务专家加只读会让「越界」的判据变成模糊地带。若将来确有查看需求，
按「新增一行授权」处理，不靠改本表语意。

## 4. 表示法（T003 落点建议，T003 定稿）

### 4.1 建议方案：复用 `role_resource`，新增资源类型

```text
auth.role          : 两张模板角色（normal 类型）——系统管理员 / 业务专家
auth.user_role     : 人 → 模板
auth.role_resource : role_id, 'governance', <八板块 id>, <read|write|review|admin>
```

- **不用 `role.name` 做判定**：009 明写「别用 `role.name` 做字符串约定（改名即静默失效）」
  （`../009-ai-assets/authorization.md` §2.4）。名字只给人看。
- **判定读行，不读名**：与 `grantsFor()` 同一条取行路径（`packages/auth/src/rbac.ts`）。
- **前端只吃 id 集合**：T001 的 `capabilities` 是 `Set<string>`，T003 把
  「该用户有任一行授权的 `resource_id`」投影成这个集合；页内动作（§3.3）由
  T005–T012 各自按 `perm` 再收敛——**页面可见 ≠ 动作可做**。

### 4.2 迁移代价（要如实记，别当成零成本）

新增 `'governance'` 会动**一个 CHECK + 两处镜像测试**：

| 落点 | 现状 | 要动什么 |
|---|---|---|
| `packages/auth/src/migrations/0004_rbac.sql` | `resource_type IN ('skill','mcp','knowledge_base')`（约束名 `role_resource_resource_type_check`） | 新迁移（`0013_*.sql`）DROP / ADD 该 CHECK，加入 `'governance'` |
| `packages/core/src/access/rbac.ts` | `RESOURCE_TYPES = ["skill","mcp","knowledge_base"]` | 加入 `'governance'`；`resolve()` 对未知类型本就跳过，治理行不会产生工具规则 |

## 5. 边界与既有机制

### 5.1 普通民警 vs 管理员（T015 / FR-013 / SC-005）

- `is_admin = 0` ⇒ 三条管理员能力（录入账号 / 重置**他人**密码 / 停用**他人**账号）
  **服务端逐条拒绝**；管理员凭证走同样三条**正常放行**。
- 本矩阵**不改变**这条：它是进门之前的门，矩阵是进门之后的分权。
- 前端隐藏不是授权（宪法 §IV）；别把 T001 的入口收敛当成本条的实现。

### 5.2 管理员之间（T014 / SC-002）

用本矩阵逐格测，**两个方向都要**：

- 系统管理员调业务专家的动作（如 `approve_business`）⇒ 拒；
- 业务专家调系统管理员的动作（如 `publish_tech` / 录入账号）⇒ 拒；
- 各自该通的格子（如系统管理员发布、业务专家审核）⇒ **通**（只测被拒会让「全拒」也全绿）。

### 5.3 授权变更的生效时点（004 R4）

capability 在**会话创建那一刻**把 ruleset 焊死；之后改角色/授权**对已存在会话无效**
（`../004-access-control/spec.md:96-99`）。因此：

- 界面**不许**写「立即生效」；
- 真要立刻踢掉，落点是让会话作废 / 重新签发——那是另一条路径，
  **不是**把回查角色表塞回执行器（那违反 004 FR-002）。

### 5.4 与 009 资产授权的关系（两道门）

| 门 | 判什么 | 在哪 |
|---|---|---|
| 页面门 | 这个**人**能不能在治理后台做这类**动作** | 本矩阵（T003 落） |
| 资产门 | 这份**资产**他能不能审 / 发 | 009 `effectivePermissions(viewer, asset, grants)` |

**两道都要过**。只做页面门会让「有 `admin` 的系统管理员能审任意资产」，直接违反 009 的
「`admin` 不蕴含 `review`」；只做资产门则系统管理员连页面入口都进不去
（他没有该板块的 `read`）。治理后台的写动作必须在服务端**先过页面门、再过资产门**。

### 5.5 与 capability / 工具规则的关系

004 的 capability 是**会话执行层**通行证（工具清单过滤 + 工具执行鉴权 + RLS）。
本矩阵是**管理动作**的门，不是 AI 工具的门：

- 治理授权行（`resource_type = 'governance'`）经 `grantsFor()` 取到后，
  `core/access/rbac.ts` 的 `resolve()` 对不认识的资源类型**天然跳过**（fail-closed），
  不会投影出任何工具 allow 规则；
- 治理后台也不是 AI 工具执行路径，不消费 `session.permission`。
