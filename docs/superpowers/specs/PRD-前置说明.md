# PRD 前置说明（openhive · prd-writer 适配）

- **用途**：跑 `prd-writer` 生成 openhive 的 PRD 之前，**先读本说明**，把 prd-writer 的通用流程适配到 openhive 的现状。
- **为什么需要**：openhive 已有 16 份高度收敛的设计文档（不是 0→1 的模糊想法），且这些文档已经混入大量「怎么做」（How）——照搬 prd-writer 的「从调研材料开始」会走偏。本说明固化适配规则，跑一次、读一次、对齐一次。

---

prd-writer 的 Step 1 是「问用户有没有调研材料」。openhive **不需要问**——直接把以下文档当**事实源**通读提炼：

**主事实源（决定 PRD 主体，优先级从高到低）**：

1. `2026-09-06-openhive-design-v2.md` —— 总体设计（平台定位、三层架构、三栏、权限、AI 资产治理、多租户），**优先级最高**。
2. `2026-09-09-资金分析模块-design.md`
3. `2026-09-11-项目管理-design.md`
4. `2026-09-12-AI资产-design.md`
5. `2026-09-12-话单分析模块-design.md`

**辅助事实源（补充背景 / 视觉 / 机制）**：`discussions/` 下「对标研究（4 份）」「视觉规范（2 份）」「资产治理（2 份）」「架构技术（1 份）」「知识沉淀（1 份）」。

## 二、What/How 反向剥离判据（最关键的适配）

openhive 的设计文档已经越过 PRD、部分进入 TRD 领域（数据表、技术选型、架构机制都写进去了）。写 PRD 时**不是「从零写 What」，而是「从文档里反向剥离出 What、把 How 留给 TRD」**。

判据一句话：**「工程师能换一种实现仍满足这条」→ 留 PRD；「这是当前选定的实现机制」→ 搬 TRD。**

| 留 PRD（What） | 搬 TRD（How） |
|---|---|
| 业务目标、用户画像、功能列表 | 数据表结构、字段定义 |
| 验收标准（Given/When/Then） | 分区策略、批量 COPY |
| 非功能底线（性能 / 安全 / 合规） | 技术选型（AntV G6 / ECharts / RabbitMQ） |
| 业务规则与异常分支 | capability 三层拦截的实现 |
| 权限规则（谁能做什么） | 沙箱 / git 落盘机制 |

**openhive 具体例子（防误伤）**：

- 「高峰日 200 万条流水必须加载快」→ **留 PRD**（业务规模约束）；「按月分区 + 批量 COPY」→ **搬 TRD**（实现机制）。
- 「AI 不能越权调用工具、拿不到无权数据」→ **留 PRD**（业务安全底线）；「capability 三层拦截 + RLS」→ **搬 TRD**。
- 「产物要落到当前 openhive 项目、随 git 走」→ **留 PRD**（业务需求）；「沙箱目录 + 具体落盘规则」→ **搬 TRD**。

---

## 三、PRD 粒度：一份总 PRD，不拆模块

openhive 是多模块平台（资金 / 话单 / 项目管理 / AI 资产），但模块**强耦合**——共享三栏、共享权限、共享产物落点。

**写一份总 PRD**，各模块作为「功能章节」展开，**不要拆成 4 份独立 PRD**——否则三栏、权限会在多份里重复、互相矛盾。

---

## 四、章节增删（相对 prd-writer 的 14 章）

- ✅ **启用**「业务规则与异常分支」（prd-writer 的补充章节）——政务 B 端必备：权限、审计、合规、越权 / 异常处理。
- ✅ **考虑启用**「培训与运营支持」——民警不熟悉代码类工具，可能需要。
- ❌ **去掉**「数据迁移方案」——新系统，无旧系统流转（资金分析明确「手动上传、无旧系统流转」）。
- ❌ **去掉**「多语言 / 国际化」——公安内网，中文。

其余 14 章照用。

## 五、输出位置与命名

- **输出**：`docs/superpowers/specs/openhive-PRD.md`（与 design-v2、各模块 design 文档同级，是这些设计文档的「产品层总纲」）。
- **命名**：`openhive-PRD.md`（PRD 是持续演进的活文档，不带日期前缀）。
- **别搞混三类目录**：
  - `docs/superpowers/specs/` = 设计文档 + PRD（PRD 放这里，和 design 文档同级）；
  - 外层 `D:\project\study\openhive\specs\` = spec-kit 的 feature specs（001 / 002 在这里，是 PRD 的下游功能落地）；
  - 内层 `openhive\specs\` = opencode 官方仓库自带的 specs（`project.md` / `tui-package.md` 等），**不要动**。

---

## 六、与已有 spec-kit 产物的关系

openhive 已有 `specs/002-openhive-frontend-ui/spec.md`（前端落地 spec）。关系是：

- **PRD = 产品层总纲**（做什么、为什么、范围、验收）；
- **spec = 功能层落地**（某个 feature 的详细 FR / SC）。

PRD 是所有后续 spec 的上游总纲。已有的 `002` 前端 spec 不冲突，PRD 完成后可作为它的「why / what」来源。

## 七、核心信息 6 问的答案来源

prd-writer Step 2 的 6 个核心信息，openhive 大部分能从文档提取，标注「从哪找」：

1. **一句话定义** → design-v2 §0 / §2（「公安全流程 AI 工作平台，给民警用」）。
2. **目标用户** → design-v2 §2（民警 1600 人；反画像：不懂代码）。
3. **MVP 范围** → 图标栏五入口（项目管理 / AI 资产 / AI 会话 / 话单分析 / 资金分析）+ 三栏，从 design-v2 §8 + 各模块 design 提取。
4. **成功指标** → ⚠️ 文档里没有明确的量化指标，**需向用户追问**或列 Open Questions。
5. **非功能需求** → design-v2 §14（权限 / 安全）+ 资金分析 §2（200 万条 / 日规模）+ 视觉规范（可访问性）。
6. **Open Questions** → ⚠️ 各 design 文档的「待决策点」大多已收敛，**需向用户确认**是否还有遗留。
