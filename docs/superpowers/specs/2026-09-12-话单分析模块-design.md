# 话单分析模块设计

- **日期**：2026-09-12
- **状态**：待审阅
- **主题**：将既有话单分析模块（传统重型工具）重构为 openhive 的「AI 优先」话单分析工作区
- **关联**：`2026-09-06-openhive-design-v2.md`（§9.6「话单分析同构」）、`2026-09-09-资金分析模块-design.md`（本设计与之**同构**，仅数据对象与部分能力不同）

---

## 0. 一句话结论

话单分析从「几十个手工按钮的传统工具」重构为 **openhive 项目内的一个三栏分析工作区**：左栏话单项目树（数据轴），中栏四个固定数据视图（明细/聚合统计/关注清单/通话关系图）+ 沙箱产物文件（图谱/分析记录/报告等，以 tab 打开），右栏 AI 驱动清洗、分析、关联、生成产物。**数据与工作空间彻底解耦，产物落到当前工作的 openhive 项目。**

> **与资金分析同构**：话单分析与资金分析的**界面三栏、处理逻辑、权限、归档、树拖拽、右键操作、指令卡机制完全一致**，唯一差异是**数据对象**——资金分析对象是「资金项目 → 账户 + 交易流水」，话单分析对象是「话单项目 → 号码 + 通话/短信记录」。本设计只写**差异点**（数据模型、话单特有分析能力），其余同构部分直接复用资金分析文档（`2026-09-09-资金分析模块-design.md`）。

> **设计定位（薄界面 + 厚 skill）**：同资金分析——界面只做「操作 + 浏览 + 确定性查询展示」；分析能力由 **skill（AI 资产）** 扩展；确定性查询/统计走 MCP，需专家经验的研判分析走 skill。

---

## 1. 核心决策（与资金分析对齐）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 交互范式 | **AI 优先重构**：几十个按钮 → 右栏 AI 驱动，中栏只留查看 + 少数人确认 |
| 2 | 数据来源 | **手动上传文件**（话单明细，含通话/短信记录） |
| 3 | 标注落点 | **图谱 + 分析记录都要**（号码→人、关系入图，判断理由进分析记录） |
| 4 | 关系图形态 | 通话关系图（中栏可交互 + 导出图片进报告） |
| 5 | 模块定位 | 图标栏进入话单分析三栏界面 |
| 6 | 项目概念 | **三层项目解耦**：openhive 项目（工作空间）≠ 话单项目（数据组织），不建关联表 |
| 7 | 产物归属 | 落到「当前工作的 openhive 项目」 |
| 8 | 数据接入 | 上传控件 + AI 清洗 + 确认入库 |
| 9 | 读写分工 | 读走「话单数据查询 MCP」，写走后端 API + RabbitMQ 批量 COPY |
| 10 | 图谱粒度 | 只存「提取出的通话关系」，正常通话留话单表不入图 |
| 11 | 节点层级 | `call_node` 多级自关联，实际不超过 10 级 |
| 12 | 号码→人 | 复用全局 `account_identity`（对方号码作为「网」虚拟身份），不用新表 |

## 2. 规模修正

同资金分析：1600 用户；话单流水同样海量（通话/短信记录高峰每日可超百万条），要求 `call_record` **按月分区 + 批量 COPY 导入**（不可逐条 insert）。图谱只存提取后的通话关系，规模小，不上图数据库。

## 3. 整体架构与数据流

### 3.1 三栏界面

```
┌─────────┬──────────────────────────────┬─────────────────┐
│ 左栏     │          中栏                 │    右栏          │
│ 话单项目 │  四个数据视图（tab）：         │   AI 分析助手    │
│ 树       │   · 明细                     │                 │
│ ├话单A   │   · 聚合统计                 │  清洗/分析/关联/  │
│ │ ├利来  │   · 关注清单                 │  生成产物         │
│ │ └长沙  │   · 通话关系图               │                 │
│ ├话单B   │   + 文件 tab（图谱/分析记录） │                 │
│ └...     │                              │                 │
└─────────┴──────────────────────────────┴─────────────────┘
```

> 图中栏为示意：**四个固定数据视图**（明细 / 聚合统计 / 关注清单 / 通话关系图）+ **沙箱产物文件**（图谱 / 分析记录 / 报告等）以 tab 打开，详见 §5。

**左栏交互（话单项目，四 tab）**：`最近 / 全部 / 已归档 / 当前`，与资金分析完全一致（点项目 = 选中 + 自动切「当前」；权限过滤是铁律；位置指示）。

### 3.2 两条独立的轴（同资金分析）

```
【数据轴】话单项目 → 节点 → 号码 + 通话/短信记录
   存储：业务数据 PG + RLS，按「话单项目 ↔ 用户」授权
【工作空间轴】openhive 项目 → 产物（报告/图谱/分析记录/文件）
   存储：沙箱目录 + git
桥梁 = 「我此刻在哪个 openhive 项目工作」的运行时上下文
```

### 3.3 数据流（读 MCP / 写 API）

```
【写入】上传话单文件 → 进沙箱 → AI 对话清洗 → 中栏展示清洗对比
        → 人点「确认入库」→ 前端直调后端 API → RabbitMQ 队列
        → worker 批量 COPY 写 PG → 完成通知回推

【读取】AI 说「查 138XXXX 近3月通话」→ 调「话单数据查询 MCP」
        → MCP 带 X-User-ID → 后端 RLS 过滤 → 返回该用户有权看的数据
```

## 4. 数据模型

### 4.1 存储分工

| 数据线 | 存哪 | 说明 |
|---|---|---|
| 话单数据（号码 + 通话/短信记录） | 业务数据 PG | 分区 + RLS + 批量导入 |
| 通话关系（图） | 业务数据 PG（entity/relation 表） | 只存提取后的关系，递归 CTE 查询 |
| 号码→人 身份映射 | 业务数据 PG（`account_identity` 表） | **复用全局**，一跳 join |
| 分析记录 + 产物文件 | 沙箱（openhive 项目目录）+ git | Markdown + frontmatter |
| 研判画布（`.graph`） | 沙箱（openhive 项目目录）+ git | JSON（节点 + 边 + 坐标 + 引用），§5.4 |

### 4.2 话单数据表（业务 PG）

```sql
call_project (        -- 话单项目（数据轴一级组织单元）
  id         BIGSERIAL PRIMARY KEY,
  name       TEXT NOT NULL,
  archived   INTEGER DEFAULT 0,       -- 归档标记
  last_accessed_at TIMESTAMP          -- 最后访问时间（归档触发依据）
)

call_project_member ( -- 数据权限（微信群模型，同 fund_project_member）
  call_project_id BIGINT REFERENCES call_project(id),
  user_id         TEXT,
  role            TEXT,               -- owner / member
  inviter         TEXT,
  invite_time     TIMESTAMP,
  status          INTEGER DEFAULT 0,  -- 0=有效，1=已撤销
  UNIQUE(call_project_id, user_id)
)

call_node (          -- 号码分组节点（多级自关联，≤10 级）
  id              BIGSERIAL PRIMARY KEY,
  call_project_id BIGINT NOT NULL REFERENCES call_project(id),
  name            TEXT NOT NULL,
  parent_id       BIGINT REFERENCES call_node(id),
  sort_order      INTEGER
)

call_number (        -- 号码（本方号码，对应原系统「话单信息」表）
  id              BIGSERIAL PRIMARY KEY,
  call_node_id    BIGINT NOT NULL REFERENCES call_node(id),
  number          TEXT,               -- 用户号码（如 13873148847）
  number_role     TEXT,               -- 号码角色（机主/使用人/备用等，非通信方式）
  operator        TEXT,               -- 运营商
  holder_name     TEXT,               -- 持有人姓名（开户登记，可能≠实际持有人）
  number_attribution TEXT,            -- 号码归属（地市）
  sort_order      INTEGER,
  status          TEXT,               -- 号码状态
  track_status    TEXT,               -- 关注/调取状态（空=未关注；待调取/已调取待导入/已导入）
  earliest_date   DATE,               -- 话单最早日期
  latest_date     DATE,               -- 话单最晚日期
  creator         TEXT,               -- 建档人
  created_at      TIMESTAMP           -- 建档时间
)

call_record (        -- 通话/短信记录（大表，按月分区）
  id                BIGSERIAL PRIMARY KEY,
  number_id         BIGINT NOT NULL REFERENCES call_number(id),
  call_date         DATE,             -- 通话日期
  call_time         TIME,             -- 通话时间
  counterparty_number TEXT,           -- 对方号码（六要素「网」虚拟身份）
  comm_type         TEXT,             -- 通信方式（主叫/被叫/短信）
  duration          INTEGER,          -- 通话时长（秒）
  attribution       TEXT,             -- 归属地名称
  weekday           TEXT,             -- 星期
  contact           TEXT,             -- 联系人
  comm_address      TEXT,             -- 通信地址
  base_station_decimal TEXT,          -- 基站十进制
  base_station_chinese TEXT           -- 中文基站
) PARTITION BY RANGE (call_date);
```

> **语义分离（同资金分析 §4.5）**：原始 `call_record` 只存**通信事实**（通话日期/时间/对方号码/时长/基站等）；关系人标注、分析备注走 `relation` / 分析记录（沙箱 Markdown），不存原始记录表。

### 4.2.1 话单项目权限（微信群模型）

**与资金分析完全一致**（同 `fund_project_member` 规则）：谁建项目谁是 owner；owner 和 member 都能邀请；只有 owner 能撤销；member 可退群、owner 不能退群；权限管理入口 = 「当前」tab 树顶部项目名右键 →「成员管理」面板。

### 4.2.2 话单项目归档（按项目，冷热分离）

**与资金分析完全一致**：`last_accessed_at` 超 1 年 → 待归档（owner 或管理员确认）；归档 = `archived=1` + 移到「已归档」tab + 数据保留不删；恢复 = `archived` 改回 0；粒度按项目。

### 4.2.3 话单项目树 + 拖拽

**与资金分析完全一致**（邻接表 `parent_id` 自关联、节点与号码允许混合、不允许跨项目拖拽、环检测、大间隔 `sort_order`、右键「新增子节点 / 新增号码 / 重命名 / 删除」、删除仅 owner、禁止删非空）。「加载明细」改为点击节点/号码 → 弹出「数据加载面板」（§5.1），不再作为右键项。

### 4.2.4 关注清单（框定号码 + 调取状态流转）

**与资金分析关注清单同构**，对象从「账户」换成「号码」：

- **主入口**：聚合统计视图——每行（对方号码）加「关注」勾选框。
- **辅入口**：明细视图「对方号码」列右键 →「加入关注」；「当前」tab 树号码右键 →「加入关注」。
- **状态机**（`call_number.track_status`，空 = 未关注）：`待调取 → 已调取待导入 → 已导入`（同资金分析，人工标记「已调取」、系统自动「已导入」）。

### 4.3 号码→人 身份映射（复用全局 `account_identity`）

```sql
-- 复用 design-v2 §12.1 全局实体库，不新造表
account_identity (    -- 对方号码（六要素「网」虚拟身份）→ 人 的映射
  id                BIGSERIAL PRIMARY KEY,
  counterparty_acct TEXT UNIQUE,   -- 对方号码（= call_record.counterparty_number）
  holder_name       TEXT,           -- 对方户名（原始话单/运营商数据自带的联系人名/开户单位名称）
  person_id         BIGINT REFERENCES entity(id)  -- 持有人（six_type='人'）
)
```

**明细回显链路**：`call_record.counterparty_number（对方号码）→ join account_identity.counterparty_number → join entity（six_type='人'）→ 回显姓名/关键标签`；「对方户名」直接读 `account_identity.holder_name`；完整属性（身份证/职业/前科）再 join `person`。原始记录表只存对方号码，不存人名。

**「人」的信息分层（同资金分析）**：关键标签（常驻）/ 身份档案（弹窗）/ 关联关系（弹窗 + 图谱）。

> **澄清（开户持有人 vs 对方户名 vs 实际持有人）**：`call_number.holder_name` 是开户/登记姓名（本方号码）；`account_identity.holder_name` 是对方户名（原始话单/运营商数据自带的联系人名/开户单位名称，原始数据就有）；`account_identity.person_id` 是研判查明的**实际持有人**。三者可能不同，回显优先展示研判查明的 `person`，`holder_name` 作为原始字段保留对照。

**身份映射的入口（同资金分析，就地标记）**：明细表「对方号码」列右键 →「标记持有人」；或右栏 AI 说「把 138XXXX 标记为张三」——两条路径写同一张 `account_identity`。实体库无人工入口，由「持有人研判」AI 闭环自动存入、自动查重。

### 4.3.1 持有人研判流水线（AI 编排 + 两闸门确认）

**同资金分析**：日常闭环 = 浏览明细 → 聚合框定 → 调取开户信息 → 识别生活线索 → 查业务系统 → 判定持有人 → 建档关联 → 全局复用。话单的生活线索略有不同（通话基站轨迹、高频联系人），但闸门结构一致：

- **闸门 1 —— 线索确认**：AI 扫通话/短信记录，提取生活线索（高频联系人、夜间通话、基站轨迹、短信内容关键词），列出「待查证线索清单」，民警勾选/划掉。
- **闸门 2 —— 持有人判定（多候选 + 置信度）**：AI 调「业务系统查询 MCP」查证（号码→实名、车辆→车主、户籍→身份），给多候选 + 置信度，民警选一个。
- **建档弹窗（AI 预填，人确认）**：AI 预填姓名/身份证/职业，判定理由自动生成，民警核对 → 写 `person` + `account_identity` + 判定理由进分析记录。

### 4.4 通话关系（业务 PG，只存提取后）

> **本节是「事实层」**（全局实体库 `entity`/`relation`，AI 提取的确定关系，全局共享、AI 维护）。中栏的「图谱」是「思路层」——项目级研判画布，落沙箱 `.graph` 文件，见 §5.4；中栏的「通话关系图」（§5.6）是确定性号码汇总视图。三者分离：事实层不由用户随便改，思路层是用户临时画布，汇总视图是数据浏览。

**复用全局 `entity` / `relation` 表**（同资金分析 §4.4）：关系类型从「资金往来」换成「通话关系」等，`rel_type` 如 `通话`/`短信`/`同户`/`同基站`/`串号`。只存提取出的涉案通话关系，正常通话留话单表不入图。

### 4.5 数据/语义分离原则

| 类型 | 落点 |
|---|---|
| 通话事实（日期/时间/对方号码/时长/基站…） | `call_record`（干净，只存事实） |
| 身份映射（号码→人） | `account_identity` + `entity`/`person`（全局复用） |
| 通话关系/涉案关系 | `relation`（图，提取后） |
| 关系人标注 / 分析备注 / 分析判断 | 分析记录（沙箱 Markdown） |

**原则**：原始记录表保持干净，语义与判断分离——身份映射、关系、分析判断都不往记录表堆字段。

## 5. 中栏：四个数据视图 + 沙箱文件 tab

中栏顶部是**多 tab 栏**（类似浏览器），两类 tab 同级并列：

| 类 | tab | 说明 |
|---|---|---|
| 数据视图（4 个固定） | 明细 / 聚合统计 / 关注清单 / 通话关系图 | 确定性数据浏览，数据来源业务 PG |
| 文件 tab | 图谱 `.graph` / 分析记录 `.md` / 报告 / 导出图 | 沙箱产物文件，通过 tab 打开 |

**四个固定数据视图**（复用 design-v2 §9.1「内容视图注册表」，按数据类型切换）：

| 视图 | 渲染 | 数据来源 |
|---|---|---|
| 明细视图 | 通话/短信明细（join 持有人 + 号码对聚合，见 §5.2/§5.3） | PG 记录表 + account_identity/person |
| 聚合统计视图 | 对方号码维度的 GROUP BY 统计（固定列：通话次数/主叫次数/被叫次数/短信数/通话总时长/通话最早时间/通话最晚时间/有效通话天数） | PG 记录表（MCP 跑聚合） |
| 关注清单视图 | 已框定重要号码 + 调取状态（待调取/已调取待导入/已导入），点已导入号码 = 选中该号码 | `call_number.track_status` |
| 通话关系图 | 号码级通话关系网络（可交互钻取，见 §5.6） | 号码间通话汇总 |

**沙箱产物文件（不是固定视图，通过 tab 打开）**：图谱（研判画布 `.graph`，§5.4）、分析记录（`.md`，§5.5）、报告/导出图等，都落沙箱（工作空间轴），中栏「文件 tab」打开，与数据视图 tab 同级。

- 主叫/被叫的底色（蓝/白）由 `comm_type` 列渲染，不存字段。
- **中栏多 tab**：中栏顶部 tab 栏（类似浏览器），数据视图 + 文件两类 tab 并排、可切换、可关闭，各自记忆数据范围 + 滚动位置。
- **选中与加载分离**：单击节点/号码 = 选中（高亮 + 更新面包屑，**不加载**）；加载 = 点击节点 → 弹出「数据加载面板」（§5.1）显式触发。节点 = 加载该节点下所有号码的合并明细（统计区显示「共 N 号码 / M 条记录」）；号码 = 加载该号码明细。加载 = 读 MCP（带 X-User-ID → RLS 过滤），有 loading / 空态 / 数量提示。
- **统计汇总触发**：当前号码统计汇总（通话总时长/主叫/被叫/对方号码数）在**加载明细时自动算**（一条 GROUP BY 的轻量聚合，跟着明细一起返回），无需点击、无需 AI 请求；统计区在上方、明细表在下方。
- **统计区/明细表可折叠**：统计区与明细表区各自可点击标题栏收缩/展开，**默认统计区收缩、明细表展开**（把空间让给明细数据）；折叠状态记忆用户上次选择。

### 5.1 数据加载面板（时间跨度 + 时间段）

点击左栏节点/号码后，中栏弹出「加载面板」（替代原「右键加载明细」，更显式）：

1. **节点信息**：节点名 + 路径 + 号码数。
2. **时间跨度信息条**（浅金底）：显示该节点话单数据的起止时间跨度（后端实时查该节点下号码 `call_record` 的 `MIN/MAX(call_date)`，走索引 + 分区裁剪），让用户加载前就知道数据有多长。
3. **加载范围单选**：默认「**全部数据**」（一键加载，最常见）；可切「**指定时间段**」，展开开始/结束日期选择器（仅加载该时间段，命中分区更少、更快）。
4. **加载完成**：中栏切换为明细视图，顶部常驻「**当前范围**」条——`节点名 · 时间段 · [全部/指定时间段] · 涉及 N 个号码 · M 条记录 · 「修改范围」按钮`，用户始终知道「现在看的是哪一段数据」，点「修改范围」随时回到加载面板重新选。

### 5.3 号码对聚合（明细附带，窗口函数）

明细表每行附带「该本方号码 ↔ 该对方号码」在当前加载范围内的聚合信息（通话次数 / 通话跨度 / 通话总时长），让用户不切视图就能看到「和这个号码总共通话了多少」。

- **聚合范围 = 当前加载范围**（所选号码 + 时间段），不是全库历史，语义必须一致。
- **实现用 SQL 窗口函数**（`COUNT/SUM/MIN/MAX OVER (PARTITION BY number_id, counterparty_number)`），一次扫描算全、分批返回；因虚拟滚动分批加载，必须**先在整个当前结果集算完聚合，再分批返回行**。
- 与「聚合统计视图」互补不冲突：明细附带是「就地方便看」，聚合统计视图是独立的「所有对方号码维度」框定比对。

### 5.4 图谱研判画布（沙箱 `.graph` 文件）

图谱是**项目级临时研判画布**，主要帮民警理清思路，**落沙箱（工作空间轴），不是固定的数据视图**，与文件同级。

- **文件格式**：后缀 `.graph`，内容 JSON（节点 + 边 + 坐标 + 引用）。
- **绘制**：AntV G6（§7），支持拖动/缩放/钻取/右键菜单。
- **节点两种**：`number`/`person`（从明细拖入的真实引用节点，带 `ref` 指向数据轴）+ `temp`（手画的临时假设节点）。
- **交互**：右键添加/删除/重命名节点、右键在两节点间加关系连线、鼠标拖动布局——全部自由操作（画布是临时的，不碰全局实体库）。
- **新建**：话单分析「图谱」入口「＋新建图谱」/ 项目管理左栏「新建文件→研判图谱」/ 右栏 AI「生成一张研判图谱」。
- **打开**：项目管理左栏点 `.graph` 文件 → 内容视图注册表路由到图谱画布组件（G6 渲染）；话单分析中栏文件 tab 打开当前项目的图谱。
- **与事实层区分**：业务 PG 的 `entity`/`relation` 是「事实层」（AI 提取的确定关系，全局共享，§4.4）；沙箱 `.graph` 是「思路层」（研判假设，项目级临时）。画布可引用事实实体作节点，但画布本身落沙箱。

### 5.5 产物落沙箱文件夹（分门别类）

分析记录、文件等 AI 产物**不作为中栏固定视图**，而是落到沙箱的**专门文件夹**，分门别类：

```
{openhive项目}/assets/
  ├─ 分析记录/   ← 研判判断（.md）
  ├─ 报告/       ← 研判报告
  ├─ 图谱/       ← 研判画布（.graph）
  └─ 导出图/     ← 导出的通话关系图/图谱图片
```

- **文件主入口 = 项目管理左栏文件树**，用户在「话单分析 ↔ 项目管理」图标间切换查看。
- **文件也能在话单分析中栏打开**：中栏文件 tab 打开沙箱产物，与数据视图 tab 同级。
- **AI 生成分析记录后自动开 tab**：右栏 AI 记一条分析思路 → 落沙箱 `分析记录/xxx.md` → 中栏自动开一个 tab 打开，保持「AI 生成 → 就地看到」的心流。

### 5.6 通话关系图（号码级汇总；深度关系分析走 skill）

- **本次做号码级汇总通话关系图**：把加载数据中「号码之间的通话」按号码聚合，画号码→号码关系网络图（可交互钻取 + 一键导出图片进报告）。确定性查询，直接做。
- **深度关系分析（共同关系人/串码/关系网络）走 skill**：找「共同通话的关系人」「通过设备串号（IMEI）关联号码」「分析通话关系网络」本质是启发式推断，交给「话单分析 skill」的『关系分析』『共同关系人』『串码分析』能力（AI 语义推断 + 人确认闸门），不做确定性按钮。

### 6.6 数据清洗（分层落地 + 能力边界）

**同资金分析 §6.2**（skill 编排 + 后端规则引擎 + LLM 语义三层，产物「清洗对比 + 问题清单」），仅清洗对象换为话单：

- **格式对齐**：列头映射（「对方号码」→ `counterparty_number`）、日期/时间格式、号码格式规整（去空格/区号/国际码）、基站编码、多 sheet 合并。
- **去重**：完全重复行自动去；疑似业务重复（同号码+时间+对方）只标记。
- **校验异常**：通话时长异常（负数/超长）、主被叫标志缺失、号码格式、基站缺失、日期越界——AI 标记、人决定。
- **字段标准化**：通信方式枚举（主叫/被叫/短信）、归属地、星期。
- **语义提取（AI 独有）**：从通话模式提取生活线索（高频联系人、夜间通话、基站轨迹），打标签，供「持有人研判」闸门 1 用。**短信内容不纳入线索提取**（MVP 只做通话记录，短信后手）。

**能力边界（红线不变）**：涉案数据只「转换 + 标记」，不「删除 + 语义判断」。

## 7. 技术选型（实现时验证）

| 能力 | 方案 |
|---|---|
| 话单数据查询（读） | 自研「话单数据查询 MCP」，带 X-User-ID + RLS |
| 话单数据入库（写） | 后端 API + RabbitMQ 异步队列（worker 消费 → 批量 COPY 写 PG → 完成通知）+ 分区表 |
| 数据清洗 | 写侧「清洗引擎」（确定性规则）+ LLM 语义（列头识别/线索提取），skill 编排，只转换+标记不删数据 |
| 图谱渲染 | AntV G6（前端；事实层 relation 图 + 思路层 `.graph` 画布 + 通话关系图均用它） |
| 图存储 | 两层：事实层 = PG 两张普通表 + 递归 CTE（不上图数据库）；思路层 = 沙箱 `.graph` JSON 文件 |
| 统计图 | ECharts |
| 业务系统查询 | 自研「业务系统查询 MCP」（read-MCP），带 X-User-ID + capability 鉴权，AI 实时查 |
| 聚合统计（对方号码 GROUP BY） | 默认实时 GROUP BY（MCP 跑聚合 SQL，分区 + 索引够快），不做入库预聚合物化表 |

**聚合统计的升级信号**（现在不触发）：实测「对方号码聚合」单次查询 > 1~2 秒、或该统计被高频反复查询时，再上 PG 物化视图（`MATERIALIZED VIEW` + `REFRESH CONCURRENTLY`）。**不做「入库时预聚合物化表」**（同资金分析 §7 的理由：物化表是快照，增量入库后必须同步刷新，否则与明细表不一致；固定维度也覆盖不了临时统计口径）。

**图数据库的升级信号**（现在不触发）：需对全量话单记录做实时图算法时，再上 Apache AGE 或独立图库。
