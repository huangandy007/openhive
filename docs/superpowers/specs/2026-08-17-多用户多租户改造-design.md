# 多用户多租户改造设计（opencode → 多人多账户）

- **日期**：2026-08-17
- **状态**：待审阅
- **主题**：把 openhive（opencode 的 fork）改造成「多人多账户、数据隔离」的内网部署架构

---

## 1. 背景与目标

当前 openhive 是官方 opencode 的单用户模型：一个实例对应一个用户（单活跃账号 + 单密码 Basic Auth），数据按 project/workspace 隔离、无「用户」维度。

目标：改造成企业内网可部署的**多用户多租户**架构——100+ 用户通过 Web 注册/登录进入各自账户空间，账户间数据相互隔离。

## 2. 已确认的需求决策（brainstorming 结论）

| 决策项 | 结论 |
|---|---|
| 隔离方式 | **每用户独立沙箱目录**（`/workspaces/{userId}/`） |
| 模型凭据 | **企业统一模型**（管理员配置，用户不感知 key） |
| 认证方式 | **自建注册/登录**（用户名 + 密码） |
| 用户规模 | **100+ 用户**（实际并发活跃约 20~30%） |
| 数据库 | **保持 SQLite + 每用户独立文件**（不换 PostgreSQL，理由见 §5） |
| 并发 | 单进程 + 配额上限；多进程「用户亲和」留作扩展后手 |
| 文件树范围 | **项目完整树 + 高亮 session 改动文件** |
| MinIO 用途 | **备份/归档**（沙箱是主工作区，MinIO 是保险箱） |
| 共享权限 | **可协作编辑**（成员可读写共享项目文件） |
| 会话共享 | **仅共享文件，会话私有** |
| 界面布局 | **三栏**（资源管理器 / 代码编辑器 / AI 会话），均可隐藏/拖拽调宽 |

## 3. 总体架构

五个组件：

```
浏览器 ──HTTPS──▶ [网关 Nginx/Traefik]（唯一对外，验 JWT + 注入 X-User-ID + 亲和预留）
                      │
        ┌─────────────┼──────────────────┐
        ▼             ▼                  ▼
  [Auth 服务]    [opencode server]   [沙箱文件系统]
   注册/登录        + 用户中间件        /workspaces/{userId}/
   用户表/JWT      + 每用户独立 db
                      │
                      ▼
              [数据存储 SQLite]
              /data/{userId}/opencode.db
```

**三个贯穿全局的原则**：

1. **信任边界**：`X-User-ID` 是「网关 → opencode」的信任通道，opencode 绝不直接对外暴露（否则可伪造头冒充他人）。
2. **最小侵入**：opencode 源码只动「一个用户中间件」+「db 按用户路由」，不碰 `sql.ts` 表定义，保证可持续 `git merge upstream/dev`。
3. **物理隔离优先**：沙箱目录靠 OS 文件权限隔离（受限用户），应用层 bug 也拦得住。

**一次请求的数据流**：登录 → 网关发 Cookie → 携 Cookie 访问 → 网关验签注入 X-User-ID → opencode 中间件锚定沙箱目录 + 路由到该用户 db → AI 在沙箱干活 → session 写入该用户 db → 事件增量流入分析库。

## 4. 账号与认证

- **用户表**（Auth 服务内部，全新，不复用 opencode 的 `account` 表）：

```sql
user (
  id            TEXT PRIMARY KEY,
  username      TEXT UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,      -- argon2id
  is_admin      INTEGER DEFAULT 0,  -- 管理员（配置统一模型）
  created_at    INTEGER NOT NULL
)
```

- **注册**：校验用户名唯一 + 密码强度 → argon2id 哈希 → 建 user 行 → 创建沙箱目录 `/workspaces/{userId}/`。
- **登录**：校验密码 → 签发 JWT（`{ sub: userId, username, is_admin, exp }`，短期 2h，MVP 无 refresh）→ 网关下发 httpOnly Cookie。
- **opencode 边界**：关闭自身 Basic Auth（不设 `OPENCODE_SERVER_PASSWORD`），只认网关注入的 `X-User-ID`，不碰密码逻辑。

## 5. 数据隔离与工作目录沙箱

### 5.1 数据库选型：保持 SQLite + 每用户独立文件（不换 PG）

- 换 PG 需改所有 `core/src/**/sql.ts`（`sqliteTable`→`pgTable`、`text({mode:"json"})`→`jsonb`、customType 重写、驱动、迁移），而这些文件是上游**最频繁改动**处，会造成持续 merge 冲突，违背 CLAUDE.md 最高约束。
- 每用户独立 SQLite 文件：物理隔离 + 消除单写者并发瓶颈 + 零表结构改动 + 零运维（备份=复制文件）。
- 何时才换 PG：数千用户、跨机横向扩展、团队已有 PG 运维、需复杂跨用户聚合——当前场景均不涉及。

### 5.2 每用户独立 db 的实现（唯一触及 core 架构处）

- 现状：`database.ts` 的 Database 是 `makeGlobalNode`（进程级单例，固定一个 `opencode.db`）。
- 改造三步：
  1. 仿照 `Location` 的 `LayerNode.unbound` 模式，新增 per-request 的 `User` 上下文（由中间件填 X-User-ID）。
  2. Database 内部维护 `Map<userId, 连接>`，每连接指向 `/data/{userId}/opencode.db`（惰性打开 + 复用 + 各自 PRAGMA）。
  3. db 查询从 User 上下文取 userId → 路由到对应连接。
- **零表结构改动**：物理隔离后 `session` 表无需加 `user_id` 列，不碰 `sql.ts`。

### 5.3 工作目录沙箱（三层隔离）

沙箱不是「每用户一个扁平目录」，而是「每用户一个根目录、内部按项目分隔离子目录」，**保留 opencode 原生的 project 概念**：

```
/workspaces/{userId}/          ← 用户根（用户隔离边界）
  ├── project-A/               ← 项目 A（独立 git 仓库）
  ├── project-B/               ← 项目 B
```

三层隔离：

| 隔离维度 | 文件层 | 会话（session）层 |
|---|---|---|
| 用户 vs 用户 | `/workspaces/{userId}/` 目录隔离 | `/data/{userId}/opencode.db` 独立 db（物理隔离） |
| 项目 vs 项目 | `/workspaces/{userId}/{project}/` 子目录 | `session.project_id`（逻辑隔离） |
| 会话 vs 会话 | 项目目录内 git 改动 | `session_id`（天然隔离） |

- 中间件把请求工作目录**强制锚定**到沙箱根，忽略客户端传入的任何 `directory`（防越权指向他人目录）。
- opencode 容器以受限系统用户运行，只能读写自己名下目录（OS 层兜底）。
- 需要「项目创建/导入」入口：web UI 里在沙箱内新建子目录 + `git init`，或上传代码。

### 5.4 跨用户分析（读写分离）

- 主库（每用户 SQLite）管隔离，独立**分析库**管聚合。
- 复用 opencode 事件溯源（`event` 表 + `SyncEvent`），增量抽取 prompt + 元数据（脱敏）到分析库。
- 分析库独立选型：MVP 聚合 SQLite；需全文检索再上 PG/ES；主题聚类可用大模型。

## 6. 执行并发与资源隔离

- opencode 已天然支持「不同 Session 并发」（`SessionRunCoordinator`：同 Session 串行、异 Session 并发，Effect fiber + 模型 I/O 密集）。
- 共享单进程 + 并发上限：中间件 + `SessionExecution` 层加「每用户活跃 Session 计数」。
- 三层配额：每用户并发 Session 数（中间件计数）、模型调用速率（网关 rate limit）、沙箱磁盘配额（Linux quota / docker volume）。
- 并发量级：单进程几十～上百并发活跃会话；100+ 用户（20~30 并发）在舒适区；**真实拐点靠压测**；瓶颈更可能在企业模型吞吐而非 opencode 进程。

### 6.1 水平扩展（后手）

- **现在预留**（成本≈零）：网关层用户亲和配置（sticky/一致性哈希）+ 每用户独立目录结构。
- **将来做**（有真实成本）：起多进程并验证 process-local 组件（`SessionExecution`、LSP/MCP/PTY 子进程、SyncEvent 事件流）在多进程下的行为。

## 7. 前端与 Docker 部署

### 7.1 前端

- 登录/注册页由 **Auth 服务**提供（独立），opencode 前端只加：① 未登录重定向；② 去掉手动连接 server 步骤。
- 登录态用 httpOnly Cookie（`HttpOnly + Secure + SameSite`），前端不接触 token。

### 7.2 Docker 编排

```
docker-compose:
  gateway  （唯一暴露 443；鉴权 + 反代 + 亲和预留）
  auth     （注册/登录/JWT + 登录页；仅内网）
  opencode （不对外暴露端口；仅内网）
  analyzer （可选，分析库）
volumes:
  data/        → /data/{userId}/opencode.db
  workspaces/  → /workspaces/{userId}/
```

- 企业统一模型通过 opencode 容器环境变量注入，用户不可见。

## 8. 前端三栏布局

session 界面采用标准的三栏布局（Cursor / Copilot 同款范式）：

```
┌──────────┬──────────────────────┬──────────┐
│ 资源管理器 │       代码编辑器        │  AI 会话  │
│   20%    │         50%          │   30%    │
└──────────┴──────────────────────┴──────────┘
```

### 8.1 三栏统一称呼

| 位置 | 称呼 | 英文 | 组件名 | 职责 |
|---|---|---|---|---|
| 左栏 | 资源管理器 | Explorer | `FileExplorer` | 项目文件树 + session 高亮 + 文件操作 |
| 中栏 | 代码编辑器 | Editor | `CodeEditor` | 查看/编辑文件（多标签页） |
| 右栏 | AI 会话 | Chat | `ChatPanel` | 与 AI 对话 |

### 8.2 默认比例与响应式

- 默认左 20% / 中 50% / 右 30%，中栏为主战场。
- 屏幕窄时自动折叠侧栏。

### 8.3 隐藏 / 呼出

- 最左侧竖一条「图标栏（Activity Bar）」，放「资源管理器」「AI 会话」图标。
- 点图标呼出/收起对应侧栏；高亮 = 当前展开。
- 代码编辑器是主区，不提供隐藏（但可被左右栏最大化挤压）。
- 快捷键：`Ctrl+B` 资源管理器、`Ctrl+J` AI 会话。

### 8.4 拖拽调宽

- 栏间分隔条（gutter）拖拽调宽。
- 最小/最大宽度限制（资源管理器 160~400px），拖到最小以下自动贴边收起。

### 8.5 三栏联动

| 联动 | 说明 |
|---|---|
| 资源管理器 → 编辑器 | 点文件，编辑器打开（多标签页） |
| AI 会话 → 编辑器 | AI 回复里提到的文件/代码，点击跳转编辑器定位行 |
| AI 改文件 → 编辑器 | 编辑器实时刷新 + 高亮改动行 |
| 编辑器 → AI 会话 | 编辑器选中代码，右键「发送到 AI 会话」 |

### 8.6 图标栏（Activity Bar）与左侧栏切换

整个界面是「1 个图标栏 + 3 个内容栏」的四区结构：

```
┌────┬───────────────┬──────────────┬──────────┐
│图标│   左栏（可切换） │   中栏        │  右栏    │
│栏  │ 资源管理器 ⇄    │  代码编辑器   │  AI 会话  │
│    │ 资源面板        │              │          │
└────┴───────────────┴──────────────┴──────────┘
```

- 图标栏图标：📁 资源管理器、🧩 资源面板、💬 AI 会话。
- **左侧栏是可切换面板**：点 📁 显示文件树，点 🧩 切换为资源面板（两者共享左侧栏位置，互斥）。
- 点 💬 控制右侧 AI 会话栏（不参与左侧栏切换）。
- 图标高亮 = 当前左侧栏显示的内容，防迷路。

### 8.7 资源面板（Skills / MCP / 知识库）

三种「AI 能力资源」统一成三个折叠组，按用户权限过滤展示：

```
资源面板
├─ ▸ Skills  (12)   ← opencode 原生 skill
├─ ▸ MCP     (5)    ← 各类 MCP server
└─ ▸ 知识库  (3)    ← RAGFlow（底层走 MCP，UI 独立成组）
```

- 折叠组括号显示数量；点折叠条展开/收起。
- hover 到具体资源弹出浮窗：名称 + 一句话用途 + 状态（启用/已连接/文档数）。
- 知识库 = 标记 `category: knowledge` 的 MCP server（RAGFlow），底层复用 MCP 协议，UI 独立成组。
- 权限：企业统一配置资源，按用户/角色授权，只展示有权使用的。

### 8.8 项目与 Session 导航（左侧栏顶部）

左侧栏顶部是「项目 → 会话」导航，下方是可折叠的内容区块：

```
左侧栏
├─ 当前项目 [📦 项目名 ▾] [＋新建项目]     ← 项目选择器 + 新建
├─ 会话历史 [▾折叠] [＋新建会话]           ← 可折叠
│    💬 会话1 / 会话2 / 会话3
├─ 文件树 [▾折叠]                        ← 可折叠（资源管理器）
└─ ☁️ MinIO 备份 [▾折叠]                  ← 可折叠
```

- 层级：项目 → 会话 → 文件。
- 两个「＋」：项目级（新建项目 → 建目录 + git init）、会话级（新建 session）。
- **会话历史、文件树、MinIO 备份三个区块均可独立折叠/展开**，折叠后各显示一行，用户按需控制左侧栏纵向空间。
- 会话历史折叠后只显示当前会话名。
- 共享项目在项目选择器下拉里带 👥 标记（分「我的项目」「共享项目」两组）。

## 9. 前端文件资源管理器与 MinIO

左侧栏（可隐藏、可拖拽调宽）承载一个 IDE 风格的文件资源管理器：

```
左侧栏
├─ 顶部：项目选择器 + session 选择器（同一项目内切 session）
├─ 主体：项目完整文件树（高亮当前 session 改动的文件）
│         ↕ 拖拽
├─ 底部：MinIO 备份面板（可折叠/展开）
```

### 8.1 文件树与 session 标记

- 展示项目完整文件树（递归列 `/workspaces/{userId}/{project}/`）。
- 「session 改动的文件」用 snapshot/git diff 标记（复用 opencode 已有 snapshot 能力），**不用时间戳**。
- 文件实时变更复用 filesystem-watcher 推送。

### 8.2 文件操作

- 新建/重命名/删除/移动/编辑，走**专门 REST API**（不走 AI 工具路径）。
- 重命名/移动用 `git mv`、删除用 `git rm`（项目是 git 仓库时，保留历史可恢复）。
- 拖拽移动 = 调用后端移动 API。

### 8.3 上传/下载（本地 ↔ 工作目录）

- 上传：`POST /files/upload`（multipart + 目标路径），拖拽上传或文件选择器。
- 下载：`GET /files/download?path=...`，文件流 + `Content-Disposition`；文件夹打包 zip。
- 路径强制校验在沙箱内（防越权）；大文件分片上传留作后手。

### 8.4 MinIO 备份/拉回（工作目录 ↔ 对象存储）

- 左侧栏底部「MinIO 备份面板」（可折叠），展示该项目在 MinIO 里的文件（镜像沙箱路径结构）。
- 拖拽：工作目录树 → MinIO 面板 = 备份；MinIO 面板 → 工作目录树 = 拉回。
- 右键菜单「备份/拉回」作为非拖拽替代入口。
- bucket 按 `{userId}/{projectId}/` 组织。

### 8.5 闲置项目自动归档

- 后台定时任务（每天凌晨 cron）扫描项目，找出 `last_accessed` 超过阈值（可配置，如 30 天）的项目。
- 自动：备份整个项目到 MinIO → 删除沙箱文件 → 项目标记「已归档」。
- 恢复：访问已归档项目时前端提示「正在从 MinIO 恢复」，自动整体拉回（懒恢复）。
- **两种备份粒度**：手动 = 文件级；自动归档 = 项目级。

### 8.6 文件生命周期

```
本地电脑 ←(上传/下载)→ 工作目录沙箱 ←(手动拖拽备份/拉回)→ MinIO
                              └─(闲置超阈值 → 凌晨自动归档)→ MinIO
                                 (访问已归档项目 → 自动懒恢复)
```

## 10. 共享项目（协作共享）

在「数据隔离」之上开一个「有边界的共享口子」：成员可协作编辑共享项目的文件，但各自的会话保持私有。

### 9.1 核心概念

```
共享项目 P：
  ├─ 文件：/shared/{projectId}/          ← 共享空间（一个 git 仓库）
  ├─ 会话：分散在各自成员的 db 里         ← 私有，互不可见
  └─ 成员：project_member 表              ← 授权谁能访问
```

### 9.2 数据模型（增量扩展，私有项目不动）

- `project` 表加字段：`type`（`private`/`shared`）+ `shared_directory`（共享项目时指向 `/shared/{projectId}/`）。
- 新增 `project_member` 表：`project_id` + `user_id` + `role`（`owner`/`editor`），唯一约束 `(project_id, user_id)`。

### 9.3 数据流

1. owner 建共享项目 → 创建 `/shared/{projectId}/` + `git init` + `project_member` 记 owner。
2. owner 邀请 B、C → `project_member` 加 editor。
3. B 访问共享项目 → 文件路由到 `/shared/{projectId}/`，会话写进 B 自己的 db（`project_id` 关联共享项目）。
4. B 改文件 → `git commit`，A、C 拉取即可见。

### 9.4 关键权衡

| 点 | 方案 |
|---|---|
| 文件并发 | 靠 git（各自 commit，冲突 merge），不做实时协同编辑（YAGNI） |
| 会话隔离 | 成员各自私有 db，复用现有每用户 db 设计，零改动 |
| 权限 | 两级：owner（建/邀/删）、editor（读写文件 + 开会话） |
| 现有隔离 | 私有项目完全不动，共享项目是新增的一条路 |

### 9.5 与现有设计的衔接（改动是「加」不是「改」）

- 加 `project_member` 表 + `project` 表加两个字段。
- 加「文件路由」：私有项目走 `/workspaces/{userId}/`，共享项目走 `/shared/{projectId}/`。
- 加「授权检查」：访问共享项目前查 `project_member`。
- 沙箱、每用户 db、文件资源管理器、MinIO 备份全部照旧。

## 11. 安全与测试

### 8.1 安全（按风险排序）

1. **信任边界**：opencode 零对外端口，物理上无法绕过网关。
2. **隔离越权防护**：强制锚定沙箱 + 每用户独立 db + OS 文件权限。
3. **密码/Cookie**：argon2id + 统一登录失败响应 + HttpOnly/Secure/SameSite。
4. **模型凭据不泄露**：key 只在容器环境变量，用户无覆盖入口。

### 8.2 错误处理

| 场景 | 处理 |
|---|---|
| 未登录/过期 | 网关 401 → 前端重定向登录 |
| db 打开失败/目录缺失 | 明确报错「账户数据异常，联系管理员」 |
| 并发/配额超限 | 明确提示「会话数已达上限」「请求过于频繁」 |
| 模型不可用 | 统一错误 + 前端友好提示 |

### 8.3 测试策略

- 单元：Auth 服务、用户中间件。
- 集成：注册→登录→建会话→AI 干活→落库 全链路。
- **隔离测试（最重要验收项）**：用户 A 访问用户 B 的目录/db 必须被拒。
- 并发压测：模拟 N 用户并发，测单进程拐点。
- 安全：路径穿越、SQL 注入、未授权直连、越权读他人数据。

## 12. 关键技术风险与应对

| 风险 | 应对 |
|---|---|
| Database 从全局单例改成按用户路由（唯一深改 core） | 仿照 Location 已验证的 unbound/bound 模式，不做新机制 |
| 持续 merge upstream/dev 冲突 | 不碰 `sql.ts`，侵入点收敛到「一个中间件 + db 路由」 |
| 企业模型吞吐成为瓶颈 | 上线前先压测模型，必要时先扩模型而非 opencode |
| 多进程扩展时 process-local 组件行为未知 | 列为明确扩展项，非含糊「以后再说」 |

## 13. 分阶段实施建议

1. **阶段 1 · Auth 服务**（独立，不碰 opencode）：用户表 + 注册/登录 + JWT + 登录页。
2. **阶段 2 · 核心改造**：用户中间件 + Database 按用户路由 + 每用户独立 db。
3. **阶段 3 · 沙箱**：工作目录锚定 + 受限用户 + 文件权限。
4. **阶段 4 · 前端 + 部署**：前端重定向 + docker-compose + 网关鉴权。
5. **阶段 5 · 分析 + 压测**：分析管道 + 并发压测 + 隔离测试验收。
