# 文件操作失败「回到发起它的那个面」设计

- **日期**：2026-10-16
- **分支**：`multi-tenant`
- **性质**：本仓定制（openhive），提交信息须标注「这是要保留的定制」
- **上游约束**：改动落在 fork 自己的文件里（`packages/app/src/project/**`、`packages/app/src/workspace/**`），**不碰** `packages/ui` 与 `packages/session-ui` 的上游源码
- **来由**：结清 `docs/superpowers/specs/2026-10-15-file-tree-multi-select-move-design.md:34` 与 `:293` 登记的那笔「下一步」

---

## 1. 背景与目标

民警报（2026-10-16 实报）：在左栏「文件」Tab 里新建文件 / 文件夹，失败时**只在工具栏下方飘一行红字**，弹窗已经关掉了。用户原话：「我希望通过弹窗的形式进行交互提醒」。

查这条时挖出的**真根因**与本次设计**无关**（登记在此，免得后来人混起来）：那次 400 `{"error":"目标目录不存在"}` 是**那个项目在盘上的目录被删了**（`file.ts` 的 `handleCreate` 落盘前先 `stat(dir)`），与有没有会话无关；已单独处置（见 §9 附记）。

但那次暴露的**交互缺口是真的**：一句话飘在工具栏下方，而**发起这次动作的弹窗已经关了** —— 用户既看不到名字还在不在、也不知道该不该重来。

一句话目标：**一次文件操作失败时，那句话出现在发起它的那个面上**（哪个弹窗 / 哪一行），而不是飘到工具栏下方。

## 2. 范围

### v1 做

- **新建文件 / 新建文件夹**失败 ⇒ `FileCreateDialog` **不关**，弹窗里就地显示服务端那句话；名字草稿留着，改一处就能再交一次
- **删除**失败 ⇒ `FileDeleteDialog` **不关**，弹窗里就地显示
- **重命名**失败 ⇒ 那句话落在**被改名的那一行**上（不是工具栏下方）
- 三处共用一个提示件、一句措辞
- 措辞 = **服务端原话 ＋ 一句通用的下一步**（不改写原因，见 §6）

### v1 不做

- **上传 / 下载**的失败仍走内联 `file-op-message`（它们的发起面是桌面拖拽 / 右键菜单，不是弹窗，也不在树上某一行）
- **移动 / 复制**一字不改（已经是报告弹窗）
- **「项目目录没了」的修复出口**：用户 2026-10-16 裁定**只告知、不给修复动作**。弹窗里不会出现「重建目录」一类的按钮
- **重命名失败后仍留在编辑态**（让用户改了直接再按 Enter）——见 §9 取舍 2，这是本次**唯一一处偏离用户点名形状**的地方，理由是一条实测出来的守卫
- 键盘多选 / 撤销 / 失败重试的自动重放等

## 3. 总架构

一条原则替代原来那条记错的：

> **失败回到发起它的那个面** —— 判据是「**发起这个动作时，用户正对着什么**」，不是「是不是弹窗」。

| 动作 | 发起面 | 失败的归处 | 本次 |
|---|---|---|---|
| 新建文件 / 新建文件夹 | `FileCreateDialog` | 该弹窗**不关**，弹窗里就地报 | **改** |
| 删除 | `FileDeleteDialog` | 该弹窗**不关**，弹窗里就地报 | **改** |
| 重命名 | 树里**那一行**（输入条只是那一行的临时态） | 输入条照旧退场，那句话落在**那一行** | **改** |
| 移动 / 复制 | 目标选择器 → 搬完的 `FileMoveReportDialog` | 已是弹窗 | 不动 |
| 上传 | 桌面拖拽 / 右键菜单 | 内联 `file-op-message` | 不动 |
| 下载 | 右键菜单 | 内联 `file-op-message` | 不动 |

**为什么重命名那一格不是「输入条不关」**：`inline-rename-input.tsx:51-63` 有一条**真栈实测**出来的守卫「一次编辑只结一次账」（`已结算` 闩）。来由是：卸载一个**仍聚焦**的元素**会**触发 `blur`（Chromium 实测，该文件前身曾断言「不会触发」，被实测证伪），而调用方 Enter 后就把输入条卸载 ⇒ 补发的 `blur` 会再结一次账（真栈上看到两条逐字同款的请求）；Escape 那一支更坏——补发的 `blur` 会把用户**刚反悔掉的草稿**交出去。

要让重命名「失败后不退出编辑态」，就必须在校验失败时放开那个闩；而放开它，等于把这条实测过的洞重新打开（用户点了别处 ⇒ `blur` ⇒ 拿同一份草稿再发一次）。**故不放开。** 重命名的「面」本来就该按**那一行**算，输入条只是那一行的临时态——这样解释，原则仍然自洽。

## 5. 契约与数据流

### 5.1 接线层：`收下` 换签名（不是换掉它）

```ts
/**
 * 办成 ⇒ 清话 ＋ 重取清单、回 `undefined`；
 * 没办成 ⇒ **回**服务端那句话（一个字都不写进内联那行 `file-op-message`）。
 */
async function 收下(结论: FileOpOutcome): Promise<string | undefined>
```

调用点现状（`workspace-entry.tsx`）与去向：

| 调用点 | 现状 | 去向 |
|---|---|---|
| `:724` `建条` | `收下(await createEntry(…))` | `return 收下(await …)` ⇒ 交回新建弹窗 |
| `:731` `改名条` | `收下(await renameEntry(…))` | `return 收下(await …)` ⇒ 交回那一行 |
| `:738` `删条` | `收下(await removeEntry(…))` | `return 收下(await …)` ⇒ 交回删除弹窗 |
| `:649` `搬一批` 全成支 | `收下({kind:"done", path: dir})` | `void 收下(…)`（结果不用） |
| `:685` `传` 全成支 | `收下({kind:"done", path: dir})` | `void 收下(…)`（结果不用） |

`搬一批` / `传` 的**失败支一个字不改**（各回各的面：前者报告弹窗、后者内联）。

⚠️ **顺带结清** `2026-10-15-…-design.md:170` 那条「⚠️ 这份重复是**有意的**，不要顺手合并」：那条警戒的理由是「把弹窗塞进 `收下` 会连带改掉另外三个动作的报告方式」。本设计**不往 `收下` 里塞弹窗**，只让它**回一句话**、由各调用方决定报在哪 —— 那条警戒的前提没了，两处可以合成一处。

### 5.2 发起弹窗：`确定()` 的新收尾

```ts
async function 确定() {
  const name = 名字()
  if (name === undefined) return
  set忙(true)
  let 话: string | undefined
  try {
    话 = await props.onConfirm(name)
  } catch (err) {
    // 抛错 = 「我们这边坏了」。保住原注释那条理由（`file-create-dialog.tsx:65-66`）：
    // 别让用户对着一个「填好了却没反应」的框。
    dialog.close()
    throw err
  } finally {
    set忙(false)
  }
  if (话 === undefined) dialog.close()
  else set失败话(话)
}
```

三件事逐条有理由，都不是顺手加的：

1. **`忙` 守卫**：「弹窗不关」**新造**出一个旧形状不存在的洞 —— 请求在飞时用户再按一次「确定」会**建两次**。改之前弹窗立刻关，这个洞不存在。在飞期间「确定」禁用。
2. **抛错仍先关**：原注释那条理由守的是**同步抛错**那一支，它不是本次要改的射程，一个字不动。
3. **改名字清掉提示**：用户动了输入框，那句「名字不合法」就过期了；留着是不再成立的话（`#005-45` 同族）。

删除弹窗是同一份形状（它没有输入框，故第 3 条不适用）。

### 5.3 文件树：行话

```ts
// FileTreeProps
onRename?: (path: string, name: string) => Promise<string | undefined>
```

行内提交处（`file-tree.tsx:730-739`）改成：

```tsx
on提交={async (name) => {
  set改名的(undefined)                    // 照旧退编辑态（§3 的理由）
  const 话 = await props.onRename?.(row.node.path, name)
  if (话 !== undefined) set行话({ 路径: row.node.path, 话 })
}}
```

- **行话怎么存、什么时候清**：按**路径**存（`{ 路径, 话 }`），渲染时只在**当前仍存在**的那一行上画 —— 行没了，话自然不画，**不需要**在卸载时去清（少一处遗漏的机会）。显式清掉只发生在两处：① 该行**开始下一次改名**；② **清单重取成功**（树换了新数据）。两处都在树里，不跨层。
- **`就地改名输入` 的 props 一个字不改**（`on提交: (新名: string) => void`）——异步与报错都发生在**调用方**这一侧。这条是刻意的：改了它就会连带动 `ai-session/session-rename.tsx:41` 那条链（⑥ 步落点，见 §8）。

## 6. 措辞

**服务端原话照登**，下面**固定**补一句通用的下一步：

```
<服务端那句话>
如果反复出现，请把这句话告诉管理员。
```

**不改写原因** —— `openhive-file-ops.ts:377-379` 明写着这条：「服务端说了为什么就用它那句……前端不自己改写措辞，它不知道是哪一条规则挡下的」。补的这一句**不猜原因**（它不区分类别），所以不破那条原则。

这一句的**默认**取「如果反复出现，请把这句话告诉管理员。」——它是一个常量，写在 `file-op-error.tsx` 里；要换说法改这一行即可。**组合逻辑只在这一处**，三处发起面拿不到第二次改的机会。

⚠️ 另记一条**不能含糊**的事：`FileOpOutcome` 里 `rejected`（`:94`）**不等于「可重试」**。`openhive-file-ops.ts:360-373` 点名 401（会话过期）与 403（已归档）都归 `rejected`，而它们「重试永远撞同一道门」；「目标目录不存在」是 400，也归 `rejected`。所以本设计**不按 `kind` 决定形状**（不写「`rejected` ⇒ 就地报让用户改」那种话）—— 形状由**发起面**决定，与失败类别无关。

## 9. 取舍（记下来，免得后来人当漏改）

1. **上传 / 下载留在内联**：按「失败回到发起它的那个面」，它的面是**拖拽 / 右键**，不在树上某一行、也不是弹窗。要给它一个面就得先有那个面（例如行上 / 拖拽落点的高亮条），不并进本次。
2. **重命名失败不留在编辑态**（与用户点名的「同理」有偏离）：理由见 §3。代价**据实记**：名字会丢 —— 重开改名预填的是**旧名**，用户得重敲。换来的是 `inline-rename-input.tsx` 那条实测过的守卫一字不动。**若日后要改，先写真栈复现把 double-submit 与 Escape 反悔那两个洞量出来，再谈。**

   ⚠️ **本节的偏离是 2026-10-16 用户当面认可的**（选项原文：「四节都行，作为 spec」；方案 A 的描述里写明「重命名同理，报在那一行」，实施取的正是「报在那一行」而不是「输入条不关」）。

3. **不按失败类别分形状**：理由见 §6 末段。

**附记（与本次设计无关，但同一现场挖出来的真根因）**：2026-10-16 用户实报的 400「目标目录不存在」= **那个项目在盘上的目录被删了**（C 盘清理删过 `%TEMP%\openhive-real-stack-state`），与有没有会话无关。已处置：三个项目目录按 `project.ts:449-459` 的三步重建（`mkdir` → `git init --quiet` → 写 `<dir>/.git/opencode`），落盘态迁到 `D:\openhive-stack-state` 并持久化 `REAL_STACK_STATE_DIR`。**这不是本次的射程**，记在此处只为免后来人把两件事混起来。
