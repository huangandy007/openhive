# Feature Specification: 解析入库入口收敛与实体页签下架

**Feature Branch**: `011-ingest-entry-entity-tab`

**Created**: 2026-11-15

**Status**: Draft

**Input**: 依据 `docs/superpowers/specs/2026-11-09-事实卡片抽象/07-解析入库入口与实体页签-设计.md` 编写；输出目录 `docs/superpowers/specs`；严格 TDD。

**边界来源**：本 spec 的功能边界以 `07` §6（越界判据 / 做什么 / 不做什么 / 与相邻文档的边界）为准；凡 `07` §6.2 列为「不做」的，本 spec 一律不写进需求。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 上传只落盘，入库只走右键（Priority: P1）

民警把原件上传到项目里。上传只把文件放到盘上，不解析、不建材料记录、不排作业。上传完成的弹窗告诉用户下一步：要入库，右键文件或文件夹选「解析入库」。这样「先预处理、再入库」才是一条真流程，而不是一句口号。

**Why this priority**：这是流程约束的地基。上传顺手入库会绕过预处理；地基不改，后面所有入库入口都建在错的语义上。

**Independent Test**：上传一份表格文件，只看文件树与解析队列即可验证——不依赖解析成功，也不依赖批量能力。

**Acceptance Scenarios**:

1. **Given** 用户上传一份从未见过的表格文件，**When** 上传完成，**Then** 文件在树上显示「未入队」；解析队列中 0 条作业；系统中不新增任何材料记录。
2. **Given** 上传完成弹窗，**When** 显示成功结果，**Then** 成功文案下有一行弱化提示，指引右键「解析入库」；下载完成的弹窗**没有**这行提示。
3. **Given** 文件已在盘上但未入队，**When** 用户右键它并选择「解析入库」，**Then** 产生 1 条材料记录与 1 条排队作业，解析照既有流程执行。

---

### User Story 2 - 右键多选批量入库（Priority: P1）

民警一次拿到一个文件夹或多份表格。右键「解析入库」支持文件夹、多选、以及两者混选；批量执行中某一份失败不中断其余，收尾一次说清成功几份、失败几份、前几条原因。

**Why this priority**：这是本期的核心新增能力，直接决定多文件场景下民警要点多少次。它不依赖 US1（右键入口原本就在），可独立验收。

**Independent Test**：在已有文件上右键多选，观察确认框数字与最终入队份数即可验证；不需要上传链路改动先落地。

**Acceptance Scenarios**:

1. **Given** 右键一个文件夹，**When** 触发「解析入库」，**Then** 确认框说「将解析这个文件夹下的 N 个文件」，逐份入队（既有行为不变）。
2. **Given** Ctrl 多选 3 份，其中 1 份已解析，**When** 打开右键菜单，**Then** 「解析入库」右侧写「已选 3 项」，确认框正文说「将解析选中的 2 个文件」（标题固定为「解析选中的文件」，见 FR-010 的 2026-11-15 修正），并说「另有 1 个选中项不在本次范围」；点确认后只入队 2 份。
3. **Given** 同时选中文件夹 A 与 A 内的文件 B，**When** 触发「解析入库」，**Then** B 只算一次，不重复入队。
4. **Given** 选中集里全部不可入队，**When** 触发「解析入库」，**Then** 确认框仍然弹出，确认键置灰并说明原因（这是正常可达路径，不是例外——0 候选不置灰入口，见 FR-009 的 2026-11-15 修正）。
5. **Given** 处于多选状态，**When** 打开右键菜单，**Then** 「重新解析 / 取消解析 / 跳过解析 / 查看解析结果」四项置灰并给统一原因；单选时四项行为不变。
6. **Given** 批量中第 2 份提交失败，**When** 整批跑完，**Then** 第 3 份及之后仍然被提交；收尾报「成功 S 份」与「F 份未能入队」，列出前 3 条原因，并说明重试只补没成功的、不会重复；S + F = N 恒成立。
7. **Given** 右键的那一行本身已解析、但选中集里有未入队文件，**When** 打开右键菜单，**Then** 「解析入库」可用——可用性由「材料状态已接入且已读到」判定，不按右键行判定；候选集只决定 N 与确认键（见 FR-009 的 2026-11-15 修正）。
8. **Given** 多选后右键了**不在**选中集里的第三行，**When** 触发「解析入库」，**Then** 只对第三行自身操作（判据是「右键行在不在选中集里」，不是选中集大小）。

---

### User Story 3 - 左栏只留三个页签（Priority: P2）

左栏的 `会话 / 文件 / 实体 / 能力` 去掉「实体」。实体浏览清单对流水类材料是空的（本期前提：表格链路不建实体），浏览价值低于它占的位置；但「查某个人时看到他的全部事实」的实体详情页保留。

**Why this priority**：这是减负与去误导，不影响入库主链；可独立验收，删的是界面与接线。

**Independent Test**：打开左栏数页签、按键盘左右环绕；再直接打开一个实体详情地址，确认三个子视图仍能渲染。

**Acceptance Scenarios**:

1. **Given** 打开项目工作区，**When** 看左栏，**Then** 只有 `会话 / 文件 / 能力` 三个页签；键盘 ← → 按 `会话 → 文件 → 能力 → 会话` 环绕。
2. **Given** 已知一个实体 ID，**When** 直接打开实体详情（伪路径），**Then** 档案页与图谱 / 时间线 / 资金三个子视图照常渲染。
3. **Given** 实现完成，**When** 全仓检索实体面板的组件名、注入 prop 与相关测试/stories，**Then** 无残留。

### Edge Cases

- 上传同名文件：仍按既有规则拒绝，不因本次改动改变。
- 同名同内容的两份文件先后被解析：后解析者命中冲突会改写老材料行的路径——既有行为，本期只记录、不修。
- 批内执行顺序为倒序（置顶算法既有）：功能无害，本期只记录、不改。
- 「已跳过」项：单项右键放行（恢复语义），批量排除（批量不该把跳过翻回来），且排除必须对用户显式说明。
- 文件状态尚未读取完成：多选时「解析入库」不猜可用性，显示「还在读 / 读取失败」两类原话。
- 批量过程中用户离开页面：入队已逐份发出，不因离开而回滚。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 上传成功 MUST NOT 创建材料记录、MUST NOT 产生排队作业；上传只把文件写到盘上。
- **FR-002**: 上传完成弹窗 MUST 显示一行弱化提示，指向右键「解析入库」；下载完成弹窗 MUST NOT 显示该提示。
- **FR-003**: 解析入库 MUST 只有右键菜单一个入口；系统 MUST NOT 提供第二个入队入口（上传时询问、独立按钮、拖拽即入队）。
- **FR-004**: 右键「解析入库」MUST 同时支持文件夹、多选、以及两者混选；选中集与文件夹展开结果 MUST 去重（同一文件只算一次）。
- **FR-005**: 候选判据 MUST 只有一份口径：文件级「未入队 / 有问题 / 无材料行」可入队；「已解析 / 已跳过 / 排队中 / 解析中 / 产物 / 不可解析扩展名」不可入队；文件夹按目录下候选展开。
- **FR-006**: 「已跳过」在单项右键时 MUST 放行（恢复该份），在批量时 MUST 排除；两者差异 MUST 固定在同一处判据里，不许各写一份。
- **FR-007**: N > 0 且批量中有选中项被排除时，确认框 MUST 显式说明「另有 M 个选中项不在本次范围」，M 的单位是选中项（一份文件 / 一个展开后 0 候选的文件夹各算一项）；N = 0 时正文 MUST 改为概括说明没有一个可入队，并至少点名已解析 / 已跳过（其余原因按同一句概括，与契约 C4 一致）。
- **FR-008**: 多选时只有「解析入库」可用；其余四项 MUST 置灰并给统一原因；单选时四项行为 MUST 保持不变。
- **FR-009**: 多选时「解析入库」的可用性 MUST 由「材料状态已接入且已读到」判定，MUST NOT 由右键行状态判定，MUST NOT 因候选为 0 而置灰；候选集只决定 N 与确认键是否禁用：候选为 0 时确认框仍须弹出、确认键置灰并说明原因。

  > **2026-11-15 修正（终审 D2，已裁定，不改代码）**：原文写作「可用性 MUST 由候选集判定」，与契约 C3、US2 场景 4 及实现相反——按候选为 0 置灰会推翻「0 候选仍弹确认框、确认键置灰」这条可达路径。可用性只看接入与 `rowsLoaded`；候选集只决定 N 与确认键。US2 场景 4 据此理解为正常可达路径，不是例外。
- **FR-010**: 界面 MUST 区分三个数并分别命名：K（选中集大小，显示在触发项右侧）、N（展开后的候选文件数，显示在确认框正文）、M（被排除的选中项数，显示在正文）。

  > **2026-11-15 修正（终审 D1，已裁定，不改代码）**：确认框**标题**固定为动作名（多选为「解析选中的文件」，文件夹为「解析这个文件夹」）；N（「将解析选中的 N 个文件」）与 M（「另有 M 个选中项不在本次范围」）都显示在**正文**。理由：标题保持动作名、数字与解释同处正文，避免标题过长。US2 场景 2 据此理解。
- **FR-011**: 批量执行 MUST 逐份提交、失败不中断后续；收尾 MUST 按真实状态重拉一次，并一并报告成功数 S 与失败数 F（S + F = N）、前 3 条失败原因，以及「重试只补没成功的、不会重复」。
- **FR-012**: 服务端 MUST NOT 新增批量入队接口；本 feature MUST NOT 新增数据库迁移或改动表结构。
- **FR-013**: 左栏 MUST 只保留「会话 / 文件 / 能力」三个页签，键盘环绕顺序相应调整；实体面板的组件、注入 prop、测试与 stories MUST 清理干净。
- **FR-014**: 实体详情页、实体伪路径、共用的取数底座、AI 查询实体能力 MUST 保持可用——下架界面不等于下架能力。
- **FR-015**: 本 feature MUST NOT 改变解析链路（识别 / 翻译 / 落库）、作业队列与置顶算法、上传的同名判重 / 幂等 / 内容指纹语义。
- **FR-016**: 「原件是否允许入库」的机制拦截 MUST NOT 在本期实现；本期只靠流程与提示（该问题另有归属，见 `07` §9.1）。

### Key Entities *(include if feature involves data)*

- **盘上文件**：尚未入库时只有路径与所在目录；其状态由「是否有材料记录」决定（没有即「未入队」）。
- **材料**：一次解析的内容去重单位，由右键入队产生；上传不再产生。
- **解析作业**：每份被入队的材料对应一条排队记录，按既有队列顺序执行。
- **选中集**：用户 Ctrl / Shift 选中的文件与文件夹集合，是批量的作用范围来源。
- **候选集**：选中集展开、去重、按候选判据过滤后的待入队文件集合；N 即其大小。

## TDD Requirements *(mandatory)*

本 feature 严格按 TDD 实现：**先写会红的用例 → 写最小实现到绿 → 重构**。没有先观测到红的行为，不算实现完成。

- **TR-001**: 每一条 FR 在写实现前 MUST 先有一条会红的自动化用例；红的原因必须是「缺该行为」，不是拼写或环境问题；红时的实际输出 MUST 记录（`#004-03`）。
- **TR-002**: 上传链路 MUST 反向钉住既有用例：原「上传一份真表格 ⇒ 材料 1 行、作业 1 条」的断言 MUST 先改成「各 0 行」并跑出红（实得 1），再删实现到绿。
- **TR-003**: 右键入队这条唯一入口 MUST 由**已有的路由级用例**守住（`test/server/openhive-case-materials.test.ts` 的「入队一份新表格：材料进「排队中」、作业落库」已覆盖本 spec 要求的断言）；本 feature MUST NOT 新建重复用例，MUST 保证该用例在改动后仍绿。

  > **2026-11-15 修正（plan 阶段实读源码）**：原文写作「今天这条接线没有任何用例」——经查不成立，该用例已存在于上述文件，且断言包含材料行、状态、`queued_by`、指纹与作业行。此条据此修正，需求本身不变。
- **TR-004**: 批量失败 MUST 新增用例：让批量中间那一份提交失败，断言「后面几份仍然被发出去」与「收尾一条失败报告含原因」；今天的用例只覆盖全成功路径，改 `break` 为「继续」时它不会变红——等于没守。
- **TR-005**: 新增的纯函数（文件级候选判据、选中集展开去重）MUST 先有用例；从既有函数中抽出判据后，既有用例 MUST 原样全绿（行为不变）。
- **TR-006**: 每条修复 MUST 做变异验证：把实现拆掉，钉住它的用例 MUST 变红，且红值 MUST 与预期一致。
- **TR-007**: 门禁 MUST 在仓库根跑受影响包的 typecheck + 测试 + lint；本机验不了的（如真栈手工手势）MUST 如实写进缺口表，MUST NOT 写成已覆盖。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 上传一份表格后，系统新增材料记录 0 条、排队作业 0 条；用户在 1 处（右键菜单）能看到下一步入口。
- **SC-002**: 一次性提交不少于 10 份文件入库（文件夹或多选）只需 2 次点击：右键 + 确认。
- **SC-003**: 批量中任一份失败时，其余文件全部被提交；收尾一次报告给出成功份数、失败份数与前 3 条原因，且成功数 + 失败数 = 候选数恒成立。
- **SC-004**: 左栏页签由 4 个减为 3 个，键盘 3 步即可环绕；实体详情仍可直接打开并渲染三个子视图。
- **SC-005**: 本 feature 产生 0 个数据库迁移、0 个新增服务端接口；解析链路与队列行为无变化。
- **SC-006**: 所有新增或反转的用例在实现前均观测到红（记录实得），实现后全绿；变异验证逐条留痕。

## Scope Boundaries (Out of Scope)

以下由相邻文档负责，本 feature 一律不做（对应 `07` §6.2 / §6.3）：

- 预处理 skill、标准副本的生成与格式、副本复核（`01` P0 / `04`）。
- 解析阶段的识别 / 翻译逻辑，以及落库的表、字段、约束（`01`）。
- 从材料或对话给实体详情页新增入口（等事实卡片那一层）。
- 关系图产物（`08`）与 AI 探索 / MCP 工具（`09`）。
- 原件入库的机制拦截（`01` Q24）。
- 批量重新解析、把多选扩展到移动 / 下载 / 打包之外。
- 服务端批量接口、数据库迁移、作业队列与置顶算法改动。

## Assumptions

- 标准副本由独立的预处理 skill 产出；本 feature 只保证原件上传不再自动入库，不定义副本格式。
- 入队是幂等的逐份操作，重复触发不会产生重复材料。
- 实体详情页与其取数底座现状可用，无需在本次一并修改。
- 前端逐份提交在当前服务端能力下可接受，不需要并发控制或批量接口。
