# 资产使用记录（skill 调用）· 设计

> 2026-10-29 · 用户裁定：①「AI 真加载了技能」才算一次 ② 每次调用记一条 ③ 明细仅系统管理员
> ④ 本期只存数 ＋ 详情页聚合，不做分析界面 ⑤ 窗口 30 天 ⑥ MCP / 知识库本期不做

## 1. 现状：这个数今天是假的

| 环节 | 事实 | 证据 |
|---|---|---|
| 数据库列 | 有 | `auth.asset.usage_count integer NOT NULL DEFAULT 0`（`migrations/0009_asset.sql:34`） |
| 递增函数 | 有，且是唯一写法 | `asset-service/src/preferences.ts:126` `recordUsage()` → `set usage_count = usage_count + 1` |
| **生产调用者** | **零** | 全仓 `recordUsage` 只出现在 `preferences.test.ts` |
| HTTP 出口 | 无 | `server/openhive/` 下没有 usage 路由 |
| 建资产时写入 | 恒 0 | `asset-service/src/service.ts:229` `usageCount: 0` |
| 展示 | 只有详情页元信息行 | `packages/app/src/ai-assets/asset-detail.tsx`「{usageCount} 次使用」 |

**结论**：线上每份资产都显示「0 次使用」。那不是「很少人用」，是没人写过这个数——它把人往
「这资产没人要」的方向误读。

当初为什么停在这儿：`asset-service/src/notify.ts:23-27` 写明「『最近』的窗口没定义（7 天？30 天？），
凭空取一个数字就是把产品决策埋进代码」。本轮用户把口径定了：**AI 真的加载了 skill 才算一次**，
展示用**最近 30 天**，同时明细留档供后续按人 / 按岗位分析。

## 2. 事实来源：读每用户库的 `part` 表，不改内核

> **2026-10-29 修订（初版写错了源，以实测为准）**：初版写的是 `session.next.tool.called` 这条
> durable 事件。真栈实测推翻了它——见下。**代码按本节写，不按初版写。**

实测（`D:\openhive-stack-state\data` 下 3 个真实用户库，内核 `packages/opencode/package.json`
= 1.19.3，数据截至 2026-10-29 07:34 UTC）：

- `event` 表里**一条 `session.next.*` 都没有**；只有 `message.part.updated.1`（8800 条）、
  `message.updated.1`、`session.updated.1`、`session.created.1` 四类。
  ⇒ `session.next.tool.called` 是 v2 线的事件，**部署中的 v1 内核根本不写**。
- 工具调用落在 **`part` 表**：`data.type = "tool"`、`data.tool`、`data.state.status`、
  `data.state.input`。实测样例（`part` 表，`json_extract` 分组）：`bash` 584、`read` 109、
  `edit` 90、`write` 39…**目前 0 条 `skill`**（真栈还没人让 AI 读技能——不是源不对）。

| 项 | 值 | 依据 |
|---|---|---|
| 源表 | 每用户库 `part` 行 | `packages/core/src/session/sql.ts:81-98`（`id / message_id / session_id / time_created / time_updated / data`） |
| skill 调用 | `json_extract(data,'$.tool') = 'skill'` | `packages/opencode/src/tool/skill.ts` 的工具名；`data` 是 `ToolPart` JSON |
| 成功才算 | `json_extract(data,'$.state.status') = 'completed'` | `packages/schema/src/v1/session.ts:277-290`：completed 才有 `output`（技能正文真的回了模型）；error / pending / running 都不算 |
| 技能名 | `json_extract(data,'$.state.input.name')` | 同上 `ToolStateCompleted.input`；工具参数 `{ name }`（`tool/skill.ts:7-9`） |
| 时间 | `part.time_created` 是 **Unix 毫秒** | `core/src/session/projector.ts:319` 写 `event.data.time`（毫秒）；`sqlite` 侧统一毫秒 |
| 会话 → 项目 | `select project_id from session where id = part.session_id` | `packages/core/src/session/sql.ts:26`（列 `project_id`，**同库**可直接 join） |
| 项目 → 资产 | `auth.project_asset_enablement(project_id, asset_id)` | `migrations/0021_project_asset_enablement.sql:29-35` |

**一行 `part` = 一次调用**（同一个 `id` 会被后续事件反复 UPDATE，不是重复行）——正好对上用户
「每次调用记一条」的口径，且天然幂等键是 `part.id`。

**为什么不在内核加钩子**：那要改 `tool/skill.ts`——上游文件，违反「最小化与官方合并冲突」这条
第一号约束。事后抽取**一行核心代码都不用碰**，还能把部署前的历史调用一并补进来。

**为什么不用 `usage_count`**：它是累计数、没有时间维度、且从没人写过。新口径全部从源库的
`part` 行算，旧列保留但不再展示——两种数不会打架。

## 3. 归因：三条判据，缺一条就不归因

```
part.session_id
  → session.project_id（同库查 / join）
  → auth.project_asset_enablement 里该项目的 asset_id 集合
  → auth.asset.name == part.state.input.name 且**唯一**的那一份
```

- **0 条同名**：不是资产（个人草稿 / 全局技能 / 已停用）⇒ 不入表，只进抽取统计。
- **≥2 条同名**：无法判断是哪一份（`#010-05`：同名 skill 的赢家本身随到达顺序漂）⇒ 不猜，
  不入表，计入「未归因」。
- `tool !== "skill"`：整类跳过（MCP / 知识库本期不做，用户已定）。

## 4. 数据模型（migration `0024`）

```sql
CREATE TABLE auth.asset_usage_event (
  user_id      text    NOT NULL,   -- 不设外键：账号注销不能抹掉历史事实
  part_id      text    NOT NULL,   -- 每用户库 part.id（幂等键）；不叫 event_id：源不是 event 表
  asset_id     text    NOT NULL,   -- 也不设外键：资产删除后历史仍可查，报表左连
  session_id   text    NOT NULL,
  call_id      text    NOT NULL,
  skill_name   text    NOT NULL,   -- 原始技能名（state.input.name），将来可重新归因
  org          text    NOT NULL,   -- 以下三列是**写时快照**：人调岗不追溯（同 010 分析库约定）
  dept         text    NOT NULL,
  section      text    NOT NULL,
  occurred_at  integer NOT NULL,   -- ⚠️ Unix **秒**，不是毫秒、不是 bigint
  extracted_at integer NOT NULL,
  PRIMARY KEY (user_id, part_id)
);
CREATE INDEX asset_usage_event_asset_time ON auth.asset_usage_event (asset_id, occurred_at);
CREATE INDEX asset_usage_event_user_time  ON auth.asset_usage_event (user_id, occurred_at);
```

四条约定，每条都有先例背书：

1. **时间用 `integer` Unix 秒**。`0015_audit_event.sql:8-10` 记着：生产驱动把 `bigint` 读成字符串、
   PGlite 读成数字，服务层按数字严判 ⇒ 换类型会在真连接上炸而测试全绿（`#002-01`）。
2. **两张表都不设外键**。`0021` 的 `enabled_by` 级联是因为它是**关系**（账号注销不能挡住删账）；
   这里是**事实**，删账号 / 删资产之后历史仍要能答「这份 skill 被用过多少次」。
3. **`(user_id, part_id)` 主键**：重放同一段不会翻倍（`part` 行被 UPDATE 不会造新键）。
4. **组织存快照、姓名不存快照**：按岗位分析要的是「当时在哪个部门」，联查现在的部门会把历史归错；
   而姓名在账号注销后按 010 的既有口径回落成「已注销用户（前 8 位）」（`governance-usage.ts` 的
   `usersByIds` 同款）。**若要 PII 级可追溯，得另加 actor 快照——那引入个人信息，须单独裁定。**

**不复用 `auth.asset_usage`**（每用户每资产 `last_used_at`）：它是「最近一次」而非「每次」，答不了
「多少次」，也没有项目 / 组织维度。旧表与本轮的 `recordUsage` / `lastUsedAtOf` / `orderForDrawer`
继续闲置，**本轮不删**（不在本次请求范围内）。

### 游标表

```sql
CREATE TABLE auth.asset_usage_cursor (
  user_id          text    PRIMARY KEY,
  last_updated_sec integer NOT NULL,  -- 源库 part.time_updated 的水位，**Unix 秒**
  updated_at       integer NOT NULL   -- 本表写入时间（Unix 秒）
);
```

**游标是时间水位、不是 id**：源换成了 `part` 表，`part.id` 不是严格单调（`prt_...` 同毫秒
批量插入时靠随机段排序），拿它当 `id >` 游标会漏行。改用 `time_updated` 水位 + **60 秒回看**
（`where time_updated > 水位秒 * 1000 - 60000`）：重复扫到的行被 `(user_id, part_id)` 主键吃掉。
回看同时兜住「第一次扫到时还是 running、完成态晚到」的窗口（见 §5）。

**水位存秒、不存毫秒**（2026-10-29 评审修正）：`integer` 是 int4，上限 2 147 483 647——秒装得下，
毫秒（约 1.79e12）装不下，首次推进游标就报 22003，而被抽取器的 `catch` 吞成一条警告 ⇒ 游标永远
停在 0、每轮全量重扫，测试还全绿。本仓 `0001_init.sql:8-11` 与 `0005_project_member.sql:40` 都记过
这条；`bigint` 也不选（生产驱动读成字符串，`0015` 的教训）。60 秒回看下的亚秒精度损失无影响。

**不与 analytics 共用游标**：两个抽取器各推各的，共用就会出现「后跑的看不到前跑已消费的行」。

## 5. 抽取

位置：`packages/opencode/src/server/openhive/asset-usage.ts`（与 `governance-usage.ts` 同级同理由：
要用 `@opencode-ai/core/database/router` 的 `dataRoot` / `userDatabasePath`，而 `asset-service`
不依赖 core）。

```
抽取(pg, root, 名册):
  for 用户 in 名册:                       # select id, org, dept, section from auth.user（同 010）
    源 = root/{userId}/opencode.db
    源不存在 ⇒ 跳过（新用户第一次登录前就是没有库）
    水位秒 = cursor[userId] ?? 0        # 秒
    行 = select id, session_id, time_created, time_updated, data from part
           where time_updated > 水位秒 * 1000 - 60000
             and json_extract(data,'$.tool') = 'skill'
           order by time_updated asc
    for 行 in 行:
      data = JSON.parse(行.data)
      data.state.status !== "completed" ⇒ 继续（还没完成 / 失败：正文没进模型，不算用过）
      名字 = data.state.input.name；不是字符串 ⇒ 计入未归因，继续
      项目 = select project_id from session where id = 行.session_id
      候选 = 该项目里 name == 名字 的已启用资产
      |候选| != 1 ⇒ 计入未归因，继续
      insert into asset_usage_event (...)
        values (userId, 行.id, assetId, 行.session_id, data.callID, 名字,
                org, dept, section,
                floor(行.time_created / 1000),   -- part 是毫秒，表里存秒
                nowSec)
        on conflict (user_id, part_id) do nothing
    游标秒 = max(floor(行.time_updated / 1000))（没有新行则不动）
```

「已启用资产」按项目缓存一次（`Map<projectId, Map<name, assetId[]>>`）：一次抽取里同一个项目
会被问上百次，逐行查库是白给。

**失败处理**：单个用户库打不开 / 解析失败 ⇒ 记一条警告、**不推进该用户的游标**、继续下一个人。
不把失败写成「0 次」（`#002-02`）。

**触发与节流**：读接口查到需要聚合时，若距上次抽取超过 **60 秒**，同步抽一遍再查；同时用一个
进程内布尔量做单飞，防两个请求同时抽。不造后台调度器（与 010 T009「读前先抽」同款）。

**多进程**：`时控` 是每个 HTTP 应用层一份，多实例部署时各进程各抽一次（幂等主键 ＋ 游标不翻倍，
但抽取次数 × 进程数）。单进程无影响。

**已知代价**：抽取是同步 SQLite I/O，会占住事件循环；MVP 规模接受（`analytics.ts` 文件头同一
条风险），规模上来要挪到后台任务——记进缺口表。

## 6. 接口

`GET /openhive/assets` 回包多一个键（位置与 `favoritedIds` 一致，`assets.ts:190`）：

```jsonc
{
  "assets": [...], "total": 0, "page": 1, "pageSize": 20,
  "categoryNames": {}, "favoritedIds": [],
  "usageStats": {
    "days": 30,                         // 窗口由服务端给，前端不硬编码
    "stats": {                          // 只含本页**有记录**的资产；没记录的资产不出现在这里
      "asset_xxx": { "users": 3, "calls": 12 }
    }
  }
}
```

查询一条：

```sql
select asset_id,
       count(distinct user_id) as users,
       count(*)                as calls
from auth.asset_usage_event
where asset_id = any($1) and occurred_at > $2
group by asset_id
```

**为什么不塞进 `AssetMetadata`**：那是与治理后台共用的行类型（治理看的是全量、不按当前读者），
使用数是「最近 30 天」的滚动聚合，不是资产的本体属性。放进行里等于把一个时变的聚合钉进实体。

**老内核兼容**：没有 `usageStats` 键 ⇒ 前端不显示这一行（**不是**显示 0）。

## 7. 前端

详情头部元信息行（`asset-detail.tsx`）三态：

| 情形 | 文案 |
|---|---|
| skill，有数 | `最近 30 天 · 3 人用过 · 共 12 次` |
| skill，无记录 | `最近 30 天还没人用过` |
| MCP / 知识库 / 老内核没给 `usageStats` | **这一项不出现** |

累计列 `usageCount` 不再展示（`AssetMetadata` 的解析保留，服务端还在发）。卡片不变——它本来
就没有这一项。

`asset-catalog-api.ts` 的解析纪律照旧：`usageStats` 缺失 = 空表；给了就必须是
`{ [id]: { users: 有限数, calls: 有限数 } }`，形状不对 ⇒ 整页 `failed`（不猜默认值）。

## 8. 权限

- **聚合数**：与资产可读性同权——能看见这份资产的人就能看见这个数。
- **明细（谁 / 哪个岗位 / 哪次）本期没有任何出口**。将来开接口**必须先过 `is_admin`**：
  民警行为数据一旦可被同级同事检索，就从分析工具变成考核工具。这条是硬约束，写进本设计。
- 组织快照只用于聚合，导出 / 报表同样受上面两条约束。

## 9. 测试计划（按 TDD 顺序）

抽取器（PGlite ＋ 临时 SQLite 夹具，`real-pg.test` / `preferences.test` 已有范式）：

1. 一次 skill 调用 ⇒ 一行，字段（asset_id / session_id / call_id / occurred_at 秒）全对。
2. 同一会话里加载两次 ⇒ **两行**（用户裁定：每次调用记一条）。
3. 重放同一段 ⇒ 不翻倍（幂等键）；`time_updated` 落在 60 秒回看窗口里也不会翻倍。

7. 用户库不存在 ⇒ 跳过，不推进游标、不报错。
8. 组织快照：账号 dept 改了之后重跑，旧行不变。

## 10. 缺口表（本轮不假装覆盖）

1. 抽取是同步 I/O，MVP 规模接受；规模上来要挪后台任务。
2. 历史事件用**当前**启用台账归因：项目后来停用或换过同名资产时，旧事件可能归错。缓解：表里存了
   `skill_name` 原件，可重算；重算脚本不在本轮。
3. 个人草稿技能、项目外的全局技能不归因（不是资产）。
4. 「AI 读了技能」≠「照着做了」：能观测的是「技能正文进了模型上下文」，观测不到随后是否照做。
   接受这个定义，但报告时不能把它说成「跟着干了」。
5. **行为数据的告知方式与保留期没有产品口径**（默认永久保留）。公安场景的敏感项，等用户裁定。
6. 账号注销后姓名不可追溯（按 010 口径回落成「已注销用户」）；要 PII 级追溯需另加 actor 快照。
7. **源绑定 v1 的 `part` 表**：同步到 v2 内核线之后工具调用会走 `session.next.tool.called`
   这类 durable 事件（本仓库 `packages/schema/src/session-event.ts:312` 有定义，但部署中的
   1.19.3 不写）。届时要么改抽取器、要么两条源都读。本轮按部署事实做一条，不预先猜 v2 的形状。
8. **源库里的毒行被静默丢弃**：`data` 不是合法 JSON 的 `part` 行由 SQL 侧 `case when json_valid(data)`
   过滤，既不报错也不计入 `unattributed` ⇒ 「源库有坏数据」没有可观测信号（只会出现在源端被污染
   的极端情形）。要信号就得加一列统计，本轮不做。
9. **归因用例只覆盖「资产存在、但该项目没启用它」**：项目里**零启用记录**、而 `auth.asset`
   里恰有同名资产这一档没有夹具（台账查询若回归成 `left join auth.asset`，现有用例不会红）。
   两者都走 `候选.length !== 1` 同一条分支，差别只在台账第一层，暂不补。
10. **「抽取持续失败」没有任何信号，前端会显示成「还没人用过」**：单用户失败只 `console.warn`（不进
    `missing`、不进任何计数），`跑一次` 出错返 `undefined` 且结果被 `handleList` 丢弃 ⇒ 全部用户都失败时
    返回值与「没事可做」完全同形，`unattributed` 在生产里无人读。要信号得加日志或计数，本轮不做——
    但报数时不能把「没数」说成「没人用」。
11. **`days` 一样本弱**：路由测试断言 `days === 30` 只能证明回包里有这个键且值为 30，证不了它来自
    `WINDOW_DAYS`（服务端写死字面量 30 也照样绿）。要钉住来源得注入常量或时钟，本轮不做。
12. **六份既有出口测试会读默认 `dataRoot`**：它们没设 `OPENHIVE_DATA_ROOT`，`dataRoot` 缺省 `/data`
    （本机解析成 `D:\data`）。抽取只读、不写源库，但若该目录恰有同名用户库，测试会读到真实数据；
    另外每条用例的首个列表请求都会触发一次全量抽取（92 pass 里含这部分开销）。本轮不动那六份文件。

## 11. 本轮明确不做

- MCP / 知识库的使用统计（用户已定：等各自的未解细节处理完再说）。
- 使用分析界面（按人 / 按岗位 / 按技能）。
- 明细查询接口。
- 旧表 `auth.asset_usage` 与 `recordUsage` / `lastUsedAtOf` / `orderForDrawer` 的清理。
- 内核侧任何改动。
