> 日期：2026-11-26

## 1. 背景

### 1.1 openhive 的项目模型

- openhive 的工作单元是 opencode 原生 `project`，界面叫“项目”。没有独立的“案件”实体；`case_*` 是事实层表前缀，项目是唯一的隔离与版本边界。
- 每个项目目录形如 `{workspaceRoot}/{userId}/{projectId}`，项目内是 git 仓库。
- 项目创建目前只做 `mkdir` + `git init` + 写 id/DB 行，**不建模板、不建 `材料/`、不做初始 commit**。
- `材料/` 是自动入队解析的路径判据：`packages/opencode/src/server/openhive/case-parseable.ts` 中 `材料目录名 = "材料"`。
- 上传要求目标目录已存在，否则 400（`packages/opencode/src/server/openhive/file.ts`）。
- 生产镜像 `packages/opencode/Dockerfile` 是 alpine + 预编译 opencode 二进制 + ripgrep，**没有 python / bun / node**。

### 1.2 技能机制

- skill 是目录 + `SKILL.md`；frontmatter 只认 `name`、`description`。
- AI 通过 `skill` 工具拿到正文和目录，再用文件/bash 工具自行读、写、跑。
- 会话 cwd 是项目目录；没有 OS 级沙箱。
- skill 不是常驻服务：只在会话中被调用，不能 7×24 自动运行，不能自动接微信/会议录音/警综。

### 1.3 用户的实际工作

办案过程包含：分析研判、调查取证、沟通对接、落地侦查、收网抓捕、询问讯问、报捕起诉。过程中产生：

- 原始调取资料、证据资料（视频侦查、技术侦查、话单资金、鉴定等）；
- 研判报告、线索、会议纪要、任务部署；
- 抓捕对象清单、抓捕方案、资料发放；
- 讯问/询问笔录、扣押提取、法律文书。

真实痛点：

1. **信息散**：日报、会议、电话、微信、现场反馈各在一处，事后难还原“谁说的、谁定的、谁跟进”。
2. **落地难**：研判出了线索，但没人盯、没期限、没反馈；工作布置了，落没落实看不清。
3. **不一致**：人员角色一改，抓捕清单、方案、汇报、文书各自为政；一处改动，处处对不上。

## 2. 目标与非目标

### 2.1 目标

1. 在 openhive 项目内一键初始化刑事案件侦查阶段工作区：目录、模板、规则、索引。
2. 建立“材料 → 证据 → 研判 → 文书”的可追溯链，以及“线索 → 落地 → 印证 → 确认”的闭环。
3. 新增“专案协同”层，把每日动态、会议、任务、线索、印证、人员组织、抓捕筹备管起来。
4. 用“台账是源、文档是视图”的机制，实现一处改动、相关文档联动更新。
5. 让 AI 做专案内勤：人零文件操作，只说、只定、只核、只签。

### 2.2 非目标

- 不做行政案件，不聚焦单一罪名。
- 不替代警综、现勘、执法办案区等现有系统。
- 不做 AI 定罪、AI 认定事实、AI 签发法律文书。
- v1 不做平台级定时任务、外部系统集成、实时多人协同、常驻可视化大屏。
- 不内置任何法律、司法解释、判例全文。

## 4. 核心模型

### 4.1 分层与控制面

| 层 | 放什么 | 回答什么问题 |
|---|---|---|
| 事实层 | 材料、证据、研判 | 我们知道什么？能证明什么？ |
| 规范层 | 法律适用 | 依据是什么？ |
| 协同层 | 每日动态、专案会议、任务、线索、印证、人员组织、抓捕筹备 | 谁在做什么？定了什么？落实没有？下一步是什么？ |
| 行动层 | 落地侦查、收网抓捕、询问讯问、沟通对接 | 实际做了什么？结果如何？ |
| 表达层 | 文书：报捕、起诉、内部审批 | 对外/对上级怎么表达？程序是否合法？ |
| 控制面 | 主数据台账 + 文档登记表 + 变更日志 | 一处改动，怎么让所有文档保持一致？ |

### 4.2 单向引用链

```text
材料 M ──转化──▶ 证据 E ──分析──▶ 研判 A ──表达──▶ 文书
                  │                 │
                  └──证明──▶ 待证事实 F
                                    │
                                    └──新线索──▶ L ──▶ A（下一轮研判）

研判线索 L ──落地──▶ 印证 V ──证实/证伪──▶ 回写 A / P / E
法律适用 ──依据──────────────────────────▶ 文书
```

硬边界：

- 文书认定事实只能引用 E；A 只能用于分析、策略和下一步，不得当作证据。
- 研判结论不写罪名认定；是否构成犯罪属于文书和法律适用。
- 材料只读；证据必须回溯到材料；研判必须回溯到证据/事实/前序研判。

### 4.3 台账是源，文档是视图

- 主数据台账是唯一源：P 人员、O 组织、L 线索、T 任务、V 印证、A 研判、E 证据、F 事实。
- 抓捕清单、方案、对象资料、协同台账、汇报材料、文书草稿都是派生视图，从台账生成。
- 派生文档用“托管块”标记自动生成区域；块外的人工叙述不被覆盖。
- 任何联动先出影响清单和 diff，人确认后再落；法律文书只出变更建议，不自动改。

## 7. 证据索引

### 7.1 定位

证据索引是**法律转化台账**：回答“这份证据能不能用、能证明什么”。它不是证据本身，不能替代原件和保管链。

### 7.2 字段

| 分组 | 字段 |
|---|---|
| 身份 | E 编号、法定种类、证据名称 |
| 来源与取证 | 来源 M、提取人、提取时间、提取地点、保管链 |
| 证明 | 证明内容、待证事实、证明力/局限、印证证据 |
| 实物与完整性 | 原件/原始介质存放地、哈希/校验 |
| 风险与状态 | 风险标记、状态、确认人/确认时间 |

“能证明什么”的四个字段：

- **证明内容**：直接显示了什么事实。必须是具体事实命题，不能写法律结论。
- **待证事实**：对应哪个构成要件/量刑情节。受控类别：主体身份 / 主观明知 / 客观行为 / 犯罪数额 / 危害后果 / 共同犯罪地位 / 量刑情节 / 程序事实。
- **证明力/局限**：能证明到什么程度、还缺什么。关键证据必填。
- **印证证据**：与哪些 E 相互补强；引用的 E 必须存在。

### 7.3 规则

1. E 的法定种类必须是八类法定证据之一；选“待定”须写原因与补正期限。
2. 每条 E 必须回溯到来源 M；M 与 E 多对多。
3. 证明内容必填，且不能写成“构成某罪”等法律结论。
4. 待证事实必填，使用受控类别。
5. 关键证据的证明力/局限必填；印证证据引用的 E 必须存在。
6. 每条 E 至少填一个待证事实类别；若启用 F 清单，则每条 E 至少对应一个 F，每个 F 至少有一条 E。
7. 物证、电子数据必须登记原件/原始介质存放地；电子数据登记哈希。

## 8. 研判索引与溯源

### 8.1 组织方式

研判按**对象/问题**组织，不按“关系图/时间线”等形式分类。

```text
研判/
├── README.md
├── 00-研判索引.md
├── 01-专题研判/
│   ├── A001-张三角色研判.md
│   └── ...
└── 02-综合研判/
```

- 一个对象、一条资金链、一个团伙 = 一个专题。
- `A001-张三角色研判.md` 只是示例；初始化不预建研判报告。
- 时间线、关系图、资金图是**视图/附件**，优先用 `case://` 视图；需要归档时放对应专题的 `图表/`，不设顶层目录。
- L 线索统一放 `专案协同/04-线索流转/`；研判区只引用 L 编号，不重复存放。

### 8.2 研判索引字段

| A 编号 | 日期 | 主题/问题 | 输入 E/F/A | 推理摘要 | 结论：事实说明什么 | 新线索 L | 置信度 | 状态 | 产出/下一步 |
|---|---|---|---|---|---|---|---|---|---|

- 状态：新发现 / 分析中 / 已证实 / 已排除 / 待补证。
- 置信度：高 / 中 / 低。
- 不单独建研判台账；索引的状态列承担台账功能。当前工作 = 按状态筛选，或由校验脚本输出“未结研判”。

### 8.3 研判报告“溯源块”

每份 `A001-主题.md` 开头固定写：

- 问题 / 假设
- 输入及用途：每条 E/F/A 说明“用来干什么”
- 推理链：分步写，标出哪一步是推断
- 替代假设与排除理由
- 结论：事实说明了什么（不写罪名认定）
- 新线索：L 编号 + 下一步
- 置信度
- 反证 / 矛盾
- 修订记录

报告正文可以继续写叙述、图表、建议；溯源块固定在开头，不随正文改写而丢失。

### 8.4 A → L → A

```text
A001 张三角色研判
  ├─ 输入：E003 / E007 / F001
  ├─ 结论：疑似操盘手
  └─ 新线索：L001 另有收款账户
        │
        ▼
A002 核查 L001
  ├─ 输入：E011 / A001
  ├─ 结论：确认该账户为抽成归集账户
  └─ 新线索：无
```

看到 A002 的结论，能顺着“输入 A001”和“来源 L001”一路追回 E003、E007。

L 也可以来自证据分析、前序研判、每日动态、专案会议、现场反馈或技术反馈；此时 L 的来源写对应记录，A 在“输入”或“新线索”中引用 L 编号即可。A→L→A 是常见链，不是唯一来源。

### 8.5 规则

1. 每条 A 必须有主题、输入、结论、状态、产出文档；输入引用的 E/F/A 必须存在。
2. A 不能作为证据；结论不写罪名认定，只写事实意义与线索。
3. 一条研判一个文件：`A001-主题.md`；修订写在文件内，不产生 v1/v2 文件。
4. 结论方向重大变化 → 新建 A，写“替代 A00x”；旧 A 保留，不覆盖。
5. 每条 L 必须有来源（A/E/日报/会议/现场/技术）、状态、下一步；L 转 A 后回填 A 编号。
6. V（印证）记录放在 `专案协同/05-印证核实/`，A 引用 V；V 不能替代 E。

## 9. 法律适用

### 9.1 定位

`法律适用/` 是用户自管的**规范性依据存放区**，不是证据区，也不是技能自带知识库。技能不内置任何法律、司法解释、判例全文。

### 9.2 默认结构

```text
法律适用/
├── README.md        # 存放规范
└── 00-索引.md        # 已放入文件清单
```

不预建 `01-法律法规` 等分类子目录；不同案由分类不同，预建空目录会逼着人“为了填而填”。

### 9.3 README 规范

1. 只放规范性依据，不放材料、证据、研判结论。
2. 推荐分类（写在 README，按需自建）：法律法规 / 司法解释与意见 / 立案追诉标准 / 量刑指导 / 判例 / 内部指引。
3. 文件名 `<类型>-<文号或条文号>-<简称>.md`。
4. frontmatter 必填：名称、文号、条文、版本、生效日期、来源、效力。
5. 只读；勘误另建说明；不得编造、不得用摘要替代原文；引用必须写条文号。
6. 涉密内部指引按保密规定，不进共享项目。
7. 放了什么，登记到 `00-索引.md`。

### 9.4 索引字段

| 序号 | 名称 | 文号/条文号 | 版本 | 生效日期 | 来源 | 效力 | 所在目录 | 用途 |
|---|---|---|---|---|---|---|---|---|

`90-本案适用分析` 不预建，做成技能 assets 模板，需要时复制。

## 10. 专案协同

### 10.1 定位

专案协同是**协同层**，不是又一个部门文件夹。它管“谁在做什么、定了什么、落实没有、下一步是什么”，不重复存放材料、证据、文书。

### 10.2 子目录

| 目录 | 作用 | 关键产物 |
|---|---|---|
| 01-每日动态 | 每天各岗位的汇报：做了什么、发现什么、卡在哪、下一步 | `YYYY-MM-DD-每日动态.md` |
| 02-专案会议 | 会议纪要、议定事项、指挥员部署 | `C001-日期-会议主题.md` |
| 03-任务盯办 | 任务编号、责任人、期限、状态、反馈、督办 | `00-任务台账.md` + `T001-任务.md` |
| 04-线索流转 | 线索发现、来源、核查、确认/排除、转研判 | `00-线索台账.md` + `L001-线索.md` |
| 05-印证核实 | 研判线索落地结果：证实/证伪/部分证实 | `00-印证台账.md` + `V001-核实.md` |
| 06-人员与组织 | P/O 主数据：身份、角色、层级、关系、抓捕状态 | `00-人员台账.md` + `01-组织架构.md` |
| 07-抓捕筹备 | 对象清单、方案、编组、资料发放、对象资料包 | `00-抓捕对象清单.md` 等 |

台账文件初始化时创建；T/L/V 单文件按需生成。L 线索文件统一放 `04-线索流转/`，研判区只引用编号。

### 10.3 闭环

```text
发现 ──▶ 汇聚 ──▶ 研判 ──▶ 部署 ──▶ 落地 ──▶ 印证 ──▶ 确认
 │         │         │         │         │         │         │
日报/会议   线索台账    A 研判   会议决定   落地记录    V 印证    主数据更新
现场/技术   T 任务     L 线索    T 任务     E/M 回填   证实/证伪   P/O/E/F
 │                                                           │
 └────────────────────── 复盘 ◀── 案后 ◀── 收网 ◀── 生成 ◀──┘
```

关键规则：

- 每个“新线索”必须有 L 编号；每个“部署”必须有 T 编号；每个“落地核实”必须有 V 记录；每次“确认”必须回写主数据。日常性工作只进日报/任务，不强行编号。
- 没有回写的，不算闭环。
- 低风险、可回溯的自动入账；高风险、不可逆的找人确认。

### 10.4 抓捕对象清单

字段：

| 序号 | P编号 | 抓捕对象 | 角色/层级 | 涉嫌罪名 | 主要证据 | 抓捕单位 | 抓捕人 | 情报支撑 | 技术支撑 | 法制支撑 | 风险 |
|---|---|---|---|---|---|---|---|---|---|---|---|

“主要证据”填 E 编号；“涉嫌罪名”“角色/层级”由办案人/法制确认，AI 只引用已确认内容，不自行认定。

从主表派生：

- 按抓捕单位分组 → 各单位任务单
- 一人一页 → `04-对象资料/P001-姓名.md`
- 按支撑角色分组 → 情报/技术/法制保障清单
- 抓捕方案 → 时间、地点、编组、通信、应急
- 资料发放清单 → 谁领了什么、签字
- 收网会议纪要 → 公布时间、纪律、口令

发放版是只读快照：`日期-名称-发放版.md`；会后变更写 `变更日志.md`，不直接改发放版。

### 10.5 收网后处理

一人一张案后处理清单，放 `侦查/收网抓捕/04-案后处理/P001-案后处理清单.md`：

| 事项 | 责任人 | 期限 | 状态 | 产出 / 位置 |
|---|---|---|---|---|
| 到案经过 | 抓捕人 | 当日 | 待办 | 侦查/收网抓捕/01-到案经过 |
| 人身检查 / 体检 | 办案区 | 入区时 | 待办 | 材料/02-调取与扣押 |
| 第一次讯问 | 侦查员 | 法定时限 | 待办 | 材料/07-讯问询问/P001 |
| 讯问笔录 / 录音录像 | 侦查员 | 每次讯问 | 待办 | 材料/07；证据索引 E |
| 扣押 / 提取 | 侦查员 | 当场 | 待办 | 材料/02；证据索引 E |
| 物证 / 电子数据固定 | 技术员 | 当日 | 待办 | 证据索引 E；哈希 |
| 拘留证 / 通知书 | 法制员 | 法定时限 | 待办 | 文书/；D 登记 |
| 家属通知 | 侦查员 | 法定时限 | 待办 | 文书/；D 登记 |
| 送押 / 涉案财物 | 内勤 | 当日 | 待办 | 材料/02；财物清单 |
| 后续补证 / 在逃 | 专案组 | 持续 | 待办 | 任务台账 T；线索台账 L |

位置分工：

- 过程：`侦查/收网抓捕/`、`侦查/询问讯问/P001-张三/`
- 原件：`材料/07-讯问询问/P001-张三/`
- 证据：`证据/证据索引.md`
- 法律文书：`文书/` + `00-文书登记表.md`

## 11. 命名规则

### 11.1 目录

- 固定顶层：`材料/ 证据/ 研判/ 专案协同/ 侦查/ 文书/ 法律适用/`

- 目录名不用日期、不用“最终/最新/修改”等词

### 11.2 文件

| 类型 | 规则 | 示例 |
|---|---|---|

| 印证 | `V001-对象-核实.md` | `V001-L001-账户核实.md` |

- 只用半角 `-` 分隔；不用空格、括号、`#`、`?`、`*`。

- 版本写在文件内“修订记录”，不进文件名。
- 发放版是只读快照；会后变更写 `变更日志.md`。
- 台账优先，文件按需：能用一行台账说清的，不单独建文件。

## 12. AI 内勤与文档一致性

### 12.1 “零文件操作”的定义

不需要人做：

- 建目录、起文件名
- 填任务台账、线索台账
- 复制粘贴、汇总日报
- 逐份改抓捕清单/方案/文书
- 手动跑脚本、对齐版本
- 手动汇总各岗位进度

必须由人做：

- 说：汇报今天做了什么、发现什么
- 定：指挥员决定抓谁、何时收网
- 核：侦查员核实线索真假
- 审：法制员审核法律文书
- 签：在法定文书上签字负责

这些不是“操作电脑”，是办案本身。AI 不能替代。

v1 中，AI 只能在会话里生成督办清单和提醒；把提醒发到群里、打电话催办仍由人做。v2 若接入消息系统，才可能自动外发。

### 12.2 工作流

```text
民警说话 / 开会 / 贴一段文字 / 上传转写稿
                │
                ▼
        AI 专案内勤
  解析 → 提取 → 去重 → 编号 → 入账
                │
    ┌───────────┼───────────┬────────────┐
    ▼           ▼           ▼            ▼
 任务台账    线索台账    印证台账     人员台账
    │           │           │            │
    └───────────┴─────┬─────┴────────────┘
                      ▼
              生成视图 / 草稿 / 清单
                      │
                      ▼
              sync_docs 影响清单 + diff
                      │
              ┌───────┴────────┐
              ▼                ▼
        非法律文档          法律文书
        批准后更新          只出变更建议
              │                │
              └───────┬────────┘
                      ▼
              validate 校验 + 盯办提醒
                      │
                      ▼
              指挥员看板 / 待拍板事项
```

人只出现在两个位置：输入自然语言；对 AI 的“待确认/待批准”回一句“同意/不同意/改成……”。

### 12.3 一句话录入示例

> 民警：今天下午调了张三建行流水，11 月 5 日 50 万转给李四，疑似抽成；已让银行继续调对手信息。

AI 回：

> 已入账——
> - L012 张三向李四转账 50 万，疑似抽成（来源 E018）
> - T034 调取李四账户对手信息（责任人：王警官，期限：11-28）
> - E018 张三建行流水（材料/06-话单与资金）
> - 建议新增 A006 研判：抽成资金流向（待确认）
>
> 影响文档：抓捕对象清单、资金研判报告。已生成 diff，是否应用？

### 12.4 文档登记表与托管块

文档登记表 `D`：

| D编号 | 文档 | 路径 | 来源记录 | 模板 | 状态 | 源版本 | 复核人 |
|---|---|---|---|---|---|---|---|

模板里的托管块：

```markdown
<!-- AUTO:BEGIN 抓捕对象 -->
| 序号 | P编号 | 姓名 | 角色 | 抓捕单位 |
<!-- AUTO:END 抓捕对象 -->
```

托管块之外的人工叙述，同步时不覆盖。

### 12.5 联动脚本

`sync_docs.py`：

1. `--dry-run`：扫文档登记表，比对源台账版本，列出受影响文档和逐项 diff。
2. 非法律文档：人工确认后更新托管块。
3. 法律文书：只生成“变更建议”，不自动改，标注“待法制审核”。
4. 已签发/已发放文档：不改原文；在 `变更日志.md` 中追加说明。

示例：张三从“成员”改为“操盘手”：

| 文档 | 改什么 | 处理 |
|---|---|---|
| 人员台账 P001 | 角色 | 主数据更新 |
| 抓捕对象清单 | 角色、编组、风险 | 角色/编组托管块更新；风险等级由指挥员确认 |
| 抓捕方案 | 角色相关字段 | 托管块更新；审讯重点/看管等级由指挥员确认 |
| A001 研判报告 | 角色事实、结论依据 | 托管块更新；结论由研判人复核，保留修订记录 |
| 起诉意见书草稿 | 地位作用 | 只出变更建议，待法制审核 |
| 会议纪要 C003 | 历史部署 | 不改原文；在变更日志/后续纪要中说明 |

### 12.6 AI 的边界

AI 可以做：

- 解析日报/会议，提取任务与线索
- 维护台账、编号、引用、状态
- 生成清单、方案、摘要、文书草稿
- 检测矛盾、缺口、逾期、未回写
- 生成变更影响清单和 diff
- 提醒指挥员“该拍板了什么”

AI 不可以做：

- 代替指挥员做决定
- 代替侦查员认定事实
- 代替法制员签发法律文书
- 把推断写成事实、把线索写成结论
- 静默修改已签发/已发放文档
- 编造姓名、金额、时间、法条

### 12.7 一个 skill 的能力边界

一个 skill（`SKILL.md` + `assets/` + `references/` + `scripts/`）可以做到：

- 初始化目录、模板、规则
- AI 解析日报/会议文本，提取任务/线索（会话内）
- 维护台账、编号、引用
- 生成抓捕清单/方案/对象资料/文书草稿
- 一处改动，联动更新其他文档
- 校验矛盾/缺口/逾期
- 生成指挥员看板/日报（调用时）
- 零文件操作

一个 skill 不能单独做到：

- 7×24 自动运行、定时提醒（需要平台调度）
- 自动接微信/会议录音/警综（需要外部集成）
- 多人实时协同、权限控制（平台能力）
- 实时可视化大屏（可生成 HTML/Markdown，但不是常驻应用）
- 法律文书签发、事实认定（必须人做）

结论：v1 用一个 skill 覆盖“方法 + 会话内自动化”；平台级常驻服务留到 v2。

- 自然语言解析由 AI 做，不指望 Python 脚本解析自由文本。

## 14. 脚本契约

### 14.1 `init_case.py`

- 参数：`--root`、`--case-name`、`--case-no`、`--dry-run`、`--json`；已存在工作区时可省略案名/案号，读现有 `案件信息.md`。
- 预检：目录名、模板、路径安全、目标是否已是案件工作区。允许空目录或仅含项目基础项（`.git/`、`.gitignore`、`.opencode/`、`opencode.json`）；已有案件工作区（以 `案件信息.md` + `AGENTS.md` 为标志）则幂等补建、不覆盖；含其他文件且不是案件工作区则失败，不写入。
- 幂等、非覆盖：已存在文件进 `kept_files`，不覆盖。
- 创建目录、模板、`.gitkeep`。
- 输出 JSON：`created_directories`、`created_files`、`kept_files`、`warnings`；失败时输出 `errors` 并非零退出。
- Python 3 标准库；无网络。

### 14.2 `sync_docs.py`

- 参数：`--dry-run`、`--apply`、`--doc D001`、`--source P001`。
- 读文档登记表，计算源台账指纹。
- 受影响文档 + 逐项 diff。
- 非法律文档：更新托管块。
- 法律文书：生成变更建议，不自动改。
- 已发放版：不修改原文件；在 `变更日志.md` 中追加说明。
- 退出码：0 无变化/成功，1 有待确认，2 错误。

### 14.3 `validate_case.py`

- 参数：`--json`、`--strict`。
- 检查：
  - E 的法定种类属于八类，或为“待定”且填写原因与补正期限；E→M；证明内容/待证事实非空；若启用 F 清单，检查 E↔F 双向覆盖。
  - A→E/F/A；无环；A 不作证据；结论不写罪名。
  - L→来源（A/E/日报/会议/现场/技术）；L 转 A 后回填 A 编号；V→L/E；P→O；抓捕清单→P。
  - D→来源；派生文档的托管块存在；发放版只读。
  - 命名正则；编号唯一；状态合法；日期合法。
  - 任务逾期；产出缺失；跨文档一致性（P 姓名/角色、人数、金额）。
- 输出错误/警告；`--strict` 时警告也算失败。

### 14.4 `digest.py`

- 参数：`--date`、`--open`、`--json`。
- 生成/更新 `专案协同/00-协同台账.md`：新增线索、待办/逾期任务、待决策、风险、收网准备度。
- 只读台账，不写主数据。

### 14.5 测试

- 初始化：幂等、非覆盖、dry-run、路径占用、非法目录名、symlink 越界。
- 同步：源变更→diff；法律文书不改；发放版原文件不变；托管块外内容保留。
- 校验：坏引用、缺字段、编号重复、非法命名、逾期、跨文档矛盾。
- 无网络；只用标准库。

## 16. 与 openhive 的联动

- 工作单元是 `project`，界面叫“项目”；没有独立“案件”实体。
- 项目目录 `{workspaceRoot}/{userId}/{projectId}` + git。
- `材料/` 是自动入队解析的路径判据；上传要求目标目录已存在，所以初始化必须创建 `材料/` 及其子目录。
- 产物保存走 `/openhive/file/write`。
- 正文 `[[fact:类型:id]]` 回链 `case_material` / `case_citation`。
- `case://<projectId>/<view>/<arg>` 视图闭集：entity / material / timeline / money / graph / alerts / templates。
- 研判的时间线、关系图、资金图优先用 `case://` 视图；导出归档才落专题的 `图表/`。
- 技能作为普通 skill 打包，源放内层仓库 `skills/<name>/`；资产发布走 draft → submit → 业务审核 → 技术发布 → 项目启用；服务端建 junction `.opencode/skill/<assetId>`。普通 skill 不需要 `adapter.json`；`adapter_skills` 只适合转换器。

## 20. 验收标准（DoD）

### 20.1 初始化

- 在新建项目内运行 `init_case.py`，创建完整目录树、模板、`.gitkeep`。
- 重复运行不覆盖已有文件；`--dry-run` 不写盘；输出 JSON 可解析。
- 非法目录名、路径越界、模板缺失、目录已有无关文件且不是案件工作区时，预检失败，不半途写入。
- 不联网，只用 Python 3 标准库。

### 20.2 证据与研判

- 示例案件能录入 E/A/L/V，索引通过 `validate_case.py`。
- 每条 E 能回溯 M；证明内容/待证事实非空；关键证据有证明力/局限。
- 每条 A 能回溯 E/F/A；结论不写罪名；A→L→A 链可追。
- 坏引用、缺字段、编号重复、非法命名能被校验器拦住。

### 20.3 协同与一致性

- 给一段示例日报，AI 能提取 L/T/E/A 建议并写入台账（经确认）。
- 给一份示例会议纪要，AI 能提取决定和任务，生成 T 记录。
- 改一个人员角色，`sync_docs.py --dry-run` 能列出受影响文档和 diff；非法律文档批准后更新；法律文书只出变更建议。
- 发放版不被自动修改；变更追加到 `变更日志.md`。
- 抓捕对象清单能从 P/O/E 生成，A 用于角色/风险参考；按单位/角色分组；对象资料包一人一页。
- 案后处理清单能按 P 生成并进入任务台账。

### 20.4 零文件操作

- 演示中，民警只说一段话/贴一段转写，不打开文件夹、不编辑 `.md`、不跑脚本。
- 指挥员只看一页看板，回复“同意/改”。
- 所有台账和文档由 AI 维护；人只做决定/核实/审核/签发。

### 20.5 运行时

- 生产镜像含 `python3`；`SKILL.md` 能探测 `python3`/`python`。
- 无解释器时，按“无脚本步骤”仍能初始化（手工路径有文档、有自检）。
- 镜像变更单独提交，标注“保留的定制”。
