# Research: AI 探索与 MCP 工具

**Feature**: `015-ai-explore-mcp-tools` · **Date**: 2026-11-17

本文件中每个决策都遵循同一条判据：**先查源码有没有现成实现（给出 `file:line`），没有再考虑新建**。查不到就写「无现成符号」，并说明为什么不做。

---

## D1 · MVP 构建边界

**Decision**：MVP = 「验收已落地主体」+「补三处薄界面行为（收尾行 / 错误话术 / 两个入口起手）」。后置：按地点取事件、第三个起手「查一段时间」、`资金研判` skill A/B、20 题真模型回放。

**Rationale**：
1. 主体（信封、硬校验、4 原语、3 档案工具、12 次预算、工具卡、23 条夹具回放）已有实现与用例；再写一遍就是重复造轮子，直接违背用户本次的硬要求。
2. 三处补丁都是纯派生数据 / 文案 / 按钮，不改服务端契约，风险面最小。
3. 后置项各有硬阻塞：地点查询属数据侧新能力（`09` §12 #5 单列）；「查一段时间」缺数据源（下方 D5）；skill A/B 与真模型回放需凭据与真栈，本机不可验——塞进 MVP 会让「完成」无法判定（`#004-03`）。

**Alternatives considered**：
- **只做验收、不补任何前端**：规格 §7/§8 明确要求入口与收尾行，不做等于没交付 P2 全部。
- **全量交付（含地点查询与 skill）**：需新开接口 + 新改查询条件 + 真模型 A/B，工期与不可验性都失控。
- **先做地点查询**：它的「能力未就绪」是**已裁定**的对外契约（`09` §4.3），实现它等于推翻既有裁定，需用户另行拍板。

> 上一轮 clarify 的提问未获答复，本节即按推荐裁法落地；若用户改判，只需改本表与 plan.md 的「MVP 边界」，其余设计不受影响。

## D2 · 收尾行放在哪、怎么算

**Decision**：
- 渲染位置：复用 `packages/session-ui/src/components/message-part.tsx` 中 `TextPartDisplay` 已有的 copy/meta 包装块（`Show when={meta()}` 在 :1765-1769，位于 `showCopy` 内）。挂 `<ClosingLine parts={...}/>` 于其后，**只增加 2–3 行**。
- 统计口径：新纯函数 `closing-stats.ts`，输入 `readonly Part[]`；用 `是信封工具键`（`envelope-parse.ts:39`）过滤信封工具 part；用 `解析工具输出`（`:90`）拿 `缺口` / `出处`。
- 输出字段：`{查询次数, 覆盖材料数, 缺口总项, 首条缺口}`。

**Rationale**：
- `message-part.tsx` 是上游文件，但已有 3 处 fork 接线；在既有定制块内加渲染，冲突面小于新建消息渲染分支（宪法 I）。
- `data.store.part?.[props.message.id]` 在同一文件 :1727 已被 `isLastTextPart` 使用，**不新增取数通道**（`#002-06`：同一前提单一出处）。
- 解析逻辑只放 `envelope-parse.ts` 一处，收尾行不自行 `JSON.parse` 工具输出，避免两套口径漂移（`#010-06`）。

**口径定义（钉进契约与用例）**：
- **查询次数** = 本消息内 `是信封工具键` 为真的 tool part 数。**不含**图工具（它们计入服务端 12 次预算，但不是「查询」），此差异写进 `contracts/ui-card-contract.md`。
- **覆盖材料数** = 各次 `出处[].代表` 中 `#` 之前段的去重集合大小；无 `出处` 的调用不计。这是近似值，报告中如实标注。
- **缺口总项** = 各次 `缺口` 数组长度之和；`首条缺口` = 按工具调用顺序的第一条。
- **0 次查询时不渲染**；**缺口为 0 时不显示缺口段**；**查询次数 ≥ 12 时附「已达 12 次上限，未覆盖项见工具卡缺口」**。
- **措辞**：写「本轮回答查询 N 次」，**不写「本次探索」**——前端数的是本条回答的 parts，不等于服务端 10 分钟窗口计数（FR-033 / `09` §13.5）。

**Alternatives considered**：
- 新组件独立渲染在消息列表层：需复制消息分组/角色判断逻辑，冲突面反而大。
- 由服务端在回复末尾注入统计：模型输出不可控，且违反「正文只给结论」的既有分工。
- 用会话 store 全量扫描而非单条消息 parts：会把历史消息的查询算进当前回复（口径错）。

## D3 · 错误话术映射放哪

**Decision**：映射函数 `错误码引导键(码: string): string | undefined` 放 `envelope-parse.ts`；文案键放 `packages/ui/src/i18n/zh.ts` / `en.ts`；渲染在 `envelope-tool.tsx` 的 `信封错误卡`（:193）内，code/message 之下加一行。

**Rationale**：
- `信封错误卡` 已显示 `错误码` 与 `消息`（`envelope-tool.tsx:193-232`），缺的只是「人话引导」，属于加一行而非新建卡片。
- 映射放解析层同文件，保证「错误码 → 展示」只有一处（`#002-06`）。
- 走既有 i18n 通道，不新增硬编码文案（CLAUDE.md 品牌化/文案约定）。

**9 个码的引导文案**（**逐字取 `09` §8.3 表，不得自拟**；zh 为主、en 从属）：

| 码 | 引导（zh，设计原文） |
|---|---|
| `bad_input` | 参数不对，我再试一次 |
| `not_found` | 没找到这个实体 |
| `not_a_member` | 无权访问该项目 |
| `forbidden` | 只有项目属主能改 |
| `too_many` | 一次给太多，请分批 |
| `ambiguous_path` | 请先列图，再点名 |
| `write_failed` | 写进去了但读不回来（**不许**说成「没写」） |
| `tool_failed` | 工具执行失败，已记入服务端日志（保持现状那句固定中文） |
| `unknown_tool` | 没有这个工具 |

**未知码**：返回 `undefined` → 只显示原码与原消息，**不伪造**引导（反对「猜一句人话」）。

**Alternatives considered**：
- 新建 `error-copy.ts` 模块：多一个文件承载 9 行映射，且与解析层分裂。
- 在错误卡里写 `switch`：组件与文案耦合，en 无法同步。

## D4 · 入口起手复用哪条接缝

**Decision**：在 `packages/app/src/center/case-views/entity-profile.tsx` 头部加两枚按钮，`onClick` 调既有 `发到会话(预填句)`（`ask-ai.ts:18`），由 `发送到会话` 的「替换」语义写进会话输入框。**不新增接缝、不自动发送。**

**Rationale**：
- 既有的「空态问 AI」按钮（`entity-profile.tsx:615-626`）已经证明该范式可用；照抄即可。
- 实体上下文（`档().canonical_value`、`档().type`）只在该页可得；换页取需新建跨栏状态，违反复用优先。
- 预填而非直发：用户可改参数再发，符合 `09` §7「入口只帮用户起手」的定位。

**显示条件**：
- `type === "人"` → 「查个人」；
- `type === "账户"` → 「查个账户」；
- 其他（地点 / 号码 / 公司等）→ 不显示（问题模板对它们无意义）。

**预填句（本计划拟定；`09` §7.1 只规定「当前选中实体 + 时间窗」与落点，未给字面模板，产品文案需评审）**：
- 查个人：`查一下「<规范值>」名下有哪些账户、与谁有资金往来，按时间窗给出结论和出处。`
- 查个账户：`查一下账户「<规范值>」的资金往来：笔数、合计、对手排行与大额明细，并给出出处。`

> 注意：实体档案页**没有时间窗控件**（D5），所以「按时间窗」只是把时间维度的要求交给模型按默认口径处理，不是用户可选参数。若评审要求用户可控时间窗，则该起手也必须后置。

**Alternatives considered**：
- 放会话面板：会话面板拿不到「当前实体」，只能靠用户手动输入，等于没做入口。
- 放中栏顶部全局：「查一段时间」才需要它；而它缺数据源（D5）。
- 直发（跳过输入框）：用户无法改时间窗/口径，且一次误点就消耗预算（12 次）。

## D5 · 第三个起手「查一段时间」为什么后置

**Decision**：不做，记入缺口。

**Evidence**：
- `grep -rn "案件时间窗" packages/ --include=*.ts --include=*.tsx` → **零命中**（2026-11-17 实测）。
- 现有案卷页（`money.tsx`、`timeline.tsx`）都没有时间窗控件；`money.tsx` 的 props 只有 `{ projectId, id, api }`，连账户名都没有。
- MCP 工具侧 `query_rows` / `query_events` 支持时间参数，但「案件级时间窗」不是一个已有实体——要么前端新开一个项目级接口，要么让用户手填，两者都超出「适配」范围。

**Rationale**：为一个按钮新增项目级接口，违反「能适配不新建」；而入口的价值在「一键起手」，手填起不到这个作用。留给有数据源之后的 feature。

**Alternatives considered**：用会话输入框直接给模板句（`查一下 2026-01-01 到 2026-03-31 的案件全貌`）——可作为临时绕过，但不算入口交付，不写进本期。

## D6 · 按地点取事件（`能力未就绪`）为什么后置

**Decision**：维持现状契约，不实现。

**Evidence**：数据侧已有 `case_event_participant`（`packages/auth/src/migrations/0039_case_translate_p2.sql:45-56`，含 `role`）与 `事件参与者条件`（`case-mcp-tools.ts:945`，委托 `case-party.事件归属条件`），`地点角色们 = ["地点","出发地","到达地"]` 也已定义。**符号齐全，但**把「按地点取事件」接进 `query_events` 需要改工具语义与返回口径，并补一整类空原因与夹具；`09` §12 #5 已把它单列为待裁定项。

**Rationale**：它是「新能力」而非「适配既有页面」；在用户明示「只做我要求的」前提下，不擅自扩大工具语义。落地时可直接复用上述三个符号（`#002-06`：一条前提一个出处）。

**Alternatives considered**：用现有 `query_relations` + 事件参与关系绕过——返回的是关系而非事件，口径不同，会造出第二套「地点事件」定义。

## D7 · 验收已落地主体时的映射与缺口处理

**Decision**：阶段 0 产出一张 **FR → 用例** 映射表；缺的用例只补断言、不补实现；发现实现与规格不符则**停**，报根因与所需证据，不在本计划内顺手改。

**Rationale**：规格头注明「已落地 ≠ 已验收」；铁律要求「找不到根因不动代码」。补断言属于测试工作，不违反「不重复造轮子」；顺手改实现则会把验收与修复混在一个提交（Anti-Pattern：混合重构与新功能）。

**Alternatives considered**：边验收边修——无法区分「本轮引入」与「历史缺陷」，且破坏变异验证的基线。
