> 讨论记录，非设计文档。承接 `01-模型统一配置.md`。

## 0.1 产物出口的架构前提（2026-11-08 用户纠正）

讨论中出现过一处理解偏差，已纠正并记为硬前提：

- **产物 = 项目工作空间里的文件**，落到左栏文件树；**中栏是共享 tab 的浏览/编辑区**（看和改产物），
  不是"报告"这类新页面；右栏是 AI 会话。依据：`openhive-PRD.md` F1「左栏 = 导航，中栏 = 浏览
  （看和改产物），右栏 = AI 会话」。
- **出口是文件级交付**：报告/账本由 AI/skill 写成文件 → 左栏出现 → 中栏打开修改 → 随项目共享、
  备份、同步 → 导出 Word/PDF 只是文件级动作。
- 引用回链**已有实现**：保存产物时正文里的引用标记登记回库（`packages/app/src/project/case-artifact-save.ts`），
  中栏「产物复核」视图可看依据是否后来被改过（`packages/app/src/center/case-views/artifact-review.tsx`）。
- 据此新增设计的定位：**收件箱、问题 Tab 是左栏导航对象，不是产物**；它们不落文件。
  认定账本做成「纯视图 / 产物文件快照 / 两者都要」尚待拍板。

## 1. 重新定义问题

用户的洞察在系统里对应一个缺失的对象：**「我们到底要查什么」**。
现在系统能回答「这个案子里有什么」，不能回答「哪些问题已闭合、哪些还缺证、下一份证据该找什么」。
注意力应按**未闭合的问题**排序，而不是按实体数量排序。

## 2. 六个结构性缺口（按价值排序）

### G1 缺「待查事项 / 研判问题」这一层（最重要）

一条待查事项：问题、状态（未查/查证中/证据支持/证据否定/证据不足/已排除）、
关联实体与事实、结论与依据、缺口、责任人、来源（人提出 / AI 提议）。
AI 回答从「结论→依据→缺口」升级为「针对这条问题：能否下结论、支持证据、反对证据、还缺什么、下一步查什么」。

### G2 确认粒度错了：应确认「主张」，不是「行/实体」

研判要确认的是主张（此号码实际由张三使用 / 两人构成同伙 / 该笔为赃款），
一条主张由多条事实支撑、也可能被一条事实推翻。需要主张对象：支持/反对证据、
来源强度、确认人、确认时间、被哪些产物引用。

### G3 矛盾不是一等公民

需要「矛盾对」对象：两条不能同时为真的事实 + 冲突类型（时间/身份/金额/供述）+
影响范围 + 处置状态，并进入注意力队列。这是研判价值最集中的地方。

### G4 没有覆盖/缺口模型，沉默会被当成证据

必须区分：查过但没有 / 没查 / 查失败（解析失败、模型失败、材料缺失）。
需要覆盖矩阵：数据源类型 × 实体 × 时间段 × 解析状态。
本次 docx 全片失败只显示「有问题」，用户看到的是「没有实体」——沉默看起来像结论。

### G5 注意力没有统一收件箱，排序不可解释

提醒、AI 提议、低可信事实、未确认的关键实体、解析失败应收进一个收件箱，
按「影响 × 时效 × 不可逆」排序，每条给三句话：是什么、为什么现在看、不看会怎样。
默认只放「需要人决策」的项；可稍后/忽略并记原因。

### G6 AI 回答缺结构化协议与引用强制

每个断言绑定 citation；UI 渲染为可点击证据块；无引用断言单独标红或阻断落产物；
区分「数据直接记录 / 人认定 / AI 推断」三种口吻；产物保存时做引用完整性校验。

## 3. 建议的边界（不做的事）

- 不做完整案件管理系统/工单系统（若专案管理承载，则复用其任务对象）
- 不新造知识图谱平台；复用现有实体/关系/引用/可信状态
- 不把所有信息做语义索引；先用「问题—证据—缺口」收敛注意力
- 不引入新中间件；内网部署仍是一份配置 + 一个网关

## 4. 优先顺序

- P0 可靠性/真实性：失败可见、覆盖与缺口、回答引用协议
- P1 注意力：待查事项 + 统一收件箱
- P2 深度：主张确认、矛盾对、身份归并置信与留痕、质量指标

## 6. 本轮结论（2026-11-08）

> 本节只记已达成的决策，**尚未进入设计、未动代码**。

### 6.1 已拍板

- **认定可推翻**：新证据出现后旧认定标「已撤销」，新认定接上，历史留痕；下游产物标脏并提示复核（`产物复核` 视图已有"依据被改过"的派生能力）。
- **认定账本形态 = C**：平时是「问题」Tab 的已闭合视图（真相只在库里一份）；交付时一键生成快照文件落 `产物/`，**不维护第二份数据**。
- **出口沿用现有架构**：产物是项目工作空间里的文件（落左栏文件树），中栏打开/编辑，导出 Word/PDF 是文件级动作。详见 §0.1。

### 6.2 对外只暴露一个概念

问题 / 主张 / 矛盾 / 覆盖四层，收成一个「**待查问题**」：

- 主张 = 问题的结论（不另立对象）
- 矛盾 = 规则自动生成的问题（不另立对象）
- 覆盖 = 问题上的缺口字段（不做独立矩阵）
- 责任人 = 标注字段（不分配、不提醒、不统计）

### 6.3 收件箱首版只收三类

待拍板的问题 / AI 提议 / 解析失败。矛盾命中直接转问题；存疑事实挂在对应问题上，不单独进箱。
每条仍是三句话：是什么 / 为什么现在要看 / 不看会怎样。每天上限 10 条。

### 6.4 不做（裁剪清单）

- **左栏「需要你看的」派生清单**（2026-11-08 用户否决；见 `03-实体显示与治理.md`）
- 独立「矛盾对」对象与处置流
- 覆盖矩阵（数据源 × 实体 × 时间段 × 解析状态）
- 主张级独立对象（G2 降级为「问题的结论」）
- 质量评分 / 质量看板
- 责任人分配、截止时间、完成率统计（与专案管理重复）
- 任何推送通知（只有左栏一个数字）

### 6.5 P1 范围 = 四件事

1. **失败可见**：0 成功切片不得记「完成」，材料与作业都要显式标失败原因。
2. **结论可追溯**：引用强制（已有登记回链 + 产物复核），报告末尾固定「未查清事项」。
3. **注意力收敛**：问题层 + 收件箱（三类、三句话、可稍后/忽略记原因）。
4. **交付**：报告与账本作为项目文件落左栏，导出为文件级动作。

### 6.6 判断尺子（以后每加一个功能都要过）

1. 它改变用户的一次点击或一句结论吗？不改变 = 不给界面。
2. 它复用了已有对象吗？要新造一套 = 先怀疑。
3. 把它删掉，产物会变差吗？不会 = 删。

### 6.7 验证指标（在 `1105反诈交流` 试点两周）

1. 「材料导入完成 → 首份可交付报告」的耗时（前后对比）。
2. 报告被上级退回、要求补依据的次数。
3. 收件箱每日推送条数 vs 实际处理条数（推得多而无人理 = 噪音，需砍）。
