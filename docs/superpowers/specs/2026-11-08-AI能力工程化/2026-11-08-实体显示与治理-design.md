# 实体显示与治理 · 设计（2026-11-08）

> 上游讨论记录见 `03-实体显示与治理.md`。本文是**设计**，不是实施计划。
> 状态：范围与四个关键决策已由用户确认（见 §2 决策汇总）。

## 1. 背景与目标

### 1.1 问题

`1106柏加信访案件梳理` 实测（2026-11-08）：59 个实体、10 条关系，**47 个实体没有任何关系（约 80%）**。
地址 / 组织 / 物品里大量是不可指认的泛称与方位碎片；同时存在真东西被埋没的反例：

- `刘子加` 关系数 = 0，但事件摘要写着「以刘子加为首」——事件参与人没有被算作连接；
- `40棵桂花树` 关系数 = 0，但是本案核心标的物。

另一个极端：`1105反诈交流` 35 份资金表、177,713 行明细 → 0 实体、0 关系、0 事件（表格通路不产实体）。

结论（讨论记录 §0）：**实体表是案卷目录，不是数据字典**；默认视图只显示「有意义的连接」的对象，
其余折叠为「提及」；档案页按「为什么值得看」重排，全量折叠但不丢。

### 1.2 目标

1. 左栏默认只显示有意义的实体，其余进「提及」（折叠、可展开、可搜索）；
2. 中栏档案重排：一句话 → 数字卡 → 关系 / 事件 / 出处，各自默认 5 条、可一键展开；
3. 减少源头垃圾：泛称 / 方位碎片不进实体表，单位名纠正为「组织」，身份证显示为「证件号」；
4. 不改抽取的模型调用，不改明细表，不新增数据表。

### 1.3 非目标（本轮明确不做）

| 项 | 原因 |
|---|---|
| 交易对手明细聚合（话单 / 资金另一头 Top 20） | 用户裁定本轮不做；它是独立后端通路，见 §9 |
| 事件结构化（刀2：事件带物 / 地 / 角色） | 建模未决（扩 `participants` 还是新增关联），且要重跑存量抽取；等议题一落地后单独立项 |
| 重复实体自动提议 | 现在没有「重复检测器」，`case_ai_proposal` 只是提议的**容器**；AI 生成提议依赖模型 |
| 「关联问题」卡片 | 依赖议题二的问题层（尚未实现） |
| 「关键事实 Top 5」 | 选取口径未定（§9.2-4），且服务端只返回前 200 条关系 |
| 存量数据修复 | 准入规则只影响新抽取；存量 59 个实体的噪声靠「提及」折叠消化，不清理 |
| 「已排除」语义扩展（新增「不涉案」动作） | 见讨论记录 §9.2-1，本轮只改文案 |

## 3. 服务端：分组、排序与聚合

唯一改动的读路径是 `packages/opencode/src/server/openhive/case-entity-list.ts`（新增聚合与过滤），
以及 `case-ui-routes.ts` 的 `/entities` 出参。

### 3.1 核心 / 提及的判据

三个可算信号的并集（讨论记录 §3.2 的五个信号里，跨源、量级异常、与问题相关本轮不具备）：

```text
核心 = 有效关系度数 ≥ 1
     或 事件参与数 ≥ 1
     或 trust_state ∈ {已确认, 已修正}

提及 = trust_state ≠ 已排除 且 不属于核心
```

- **有效关系**：与现有清单 `关联数` **同一份谓词**——关系未排除、对方实体未排除、关系两端之一是该实体；
- **事件参与**：`case_event.trust_state ≠ '已排除'` 且 `participants @> array[该实体规范值]`；
- `已排除` 的实体 / 关系 / 事件一律不参与统计（与现有三个出口同一口径）。

### 3.2 查询形状

`where` 不能引用同层 select 的别名 ⇒ 分三层：最内层算两个计数，中间层算权重与分组，
最外层做 `group` / `q` 过滤、报总数、排序与截断：

```sql
select 行.*, count(*) over() as 总数
  from (
    select t.*,
           (t.关联数 + t.事件参与数) as 权重,
           case when t.关联数 > 0 or t.事件参与数 > 0
                  or t.trust_state in ('已确认','已修正') then '核心' else '提及' end as 分组
      from (
        select e.id, e.type, e.canonical_value,
               array_to_json(e.aliases)::text as aliases,
               e.attrs, e.trust_state, e.created_at,
               (select count(*)::int from auth.case_relation r
                 where r.project_id = e.project_id
                   and r.trust_state <> '已排除'
                   and (r.from_id = e.id or r.to_id = e.id)
                   and (case when r.from_id = e.id then r.to_id else r.from_id end)
                       in (select id from auth.case_entity
                            where project_id = e.project_id and trust_state <> '已排除'))
                 as 关联数,
               (select count(*)::int from auth.case_event ev
                 where ev.project_id = e.project_id
                   and ev.trust_state <> '已排除'
                   and ev.participants @> array[e.canonical_value]::text[])
                 as 事件参与数
          from auth.case_entity e
         where e.project_id = ${projectId}
           and e.trust_state <> '已排除'
           -- 仅在给了 q 时加；在最内层过滤，`aliases` 仍是 text[]（外层已转 JSON 文本）
           and (e.canonical_value ilike ${模式} escape '\\'
                or exists (select 1 from unnest(e.aliases) as 别名
                            where 别名 ilike ${模式} escape '\\'))
      ) t
  ) 行
 where true
   -- 仅在给了 group 时加；搜索省略 = 跨两组
   and 行.分组 = ${group}
 order by …
 limit …
```

排序：

| `sort` | 顺序 |
|---|---|
| `涉案`（默认） | `权重 desc, (trust_state ∈ {已确认,已修正}) desc, canonical_value asc, id asc` |
| `名称` | `canonical_value asc, id asc` |
| `时间` | `created_at desc, id asc` |

提及组权重恒为 0，`涉案` 自然退化为名称序。

### 3.3 出参变化

`实体清单项` 新增：

```ts
readonly 事件参与数: number
readonly 权重: number
readonly 分组: "核心" | "提及"
```

`实体清单结果` 新增 `总数: number`（`count(*) over()`，过滤后全量），`缺口` 仍按 `总数 > 上限` 生成。

`实体清单入参`：新增 `分组?: "核心" | "提及"`；**删除 `type`**（左栏不再按类型导航，仓库内无第二个调用点）。

### 3.4 类型计数 → 分组计数

`类型计数()` 删除，改为：

```ts
export interface 分组计数 {
  readonly 核心: number
  readonly 提及: number
}

export async function 分组计数(db: Queryable, projectId: string): Promise<分组计数>
```

一次查询、同一个派生表、同一份核心条件（`count(*) filter (where …)`），避免第二份判据。

### 3.5 档案页的「待确认」

`实体档案` 新增：

```ts
readonly 待确认: {
  readonly 实体: number   // 0 或 1
  readonly 关系: number
  readonly 事件: number
  readonly 合计: number
}
```

- **实体**：`trust_state ∈ {自动抽取, 存疑}` ⇒ 1；
- **关系**：该实体的有效关系中 `trust_state ∈ {自动抽取, 存疑}` 的条数（**不受 200/100 上限影响**）；
- **事件**：`participants` 含该实体且事件未排除、`trust_state ∈ {自动抽取, 存疑}` 的条数；
- 已排除一律不计（「显示已排除」开关打开时也不计——排除是人的决定，不是待办）。

谓词拆分（`#002-06`：同一前提只写一份）：

| 名字 | 用途 |
|---|---|
| `关系基础条件` | project + 触达该实体 |
| `关系可见条件(含排除)` | 基础 + （不含排除时）关系未排除且对方未排除 |
| `关系待确认条件` | 基础 + 关系未排除且对方未排除 + 关系 `trust_state ∈ {自动抽取,存疑}` |
| `事件基础条件` | project + participants 含规范值 |
| `事件可见条件(含排除)` | 基础 + （不含排除时）事件未排除 |
| `事件待确认条件` | 基础 + 事件未排除 + `trust_state ∈ {自动抽取,存疑}` |

### 3.6 接口形状

`GET /openhive/case/entities`

| 参数 | 必填 | 说明 |
|---|---|---|
| `projectId` | 是 | |
| `group` | 否 | `核心` / `提及`；省略 = 跨组（搜索用） |
| `q` | 否 | 跨组搜索；`%` `_` `\` 继续转义 |
| `sort` | 否 | `涉案` / `名称` / `时间` |
| `limit` | 否 | 1..200 |

回包：

```ts
{
  groups: { 核心: number; 提及: number },
  list: { 行们: 实体清单项[]; 总数: number; 缺口: string[] }
}
```

`group` 非法 ⇒ `400 bad_request`（与 `sort` 同一种失败形态）。

## 4. 左栏（`entity-panel.tsx`）

### 4.1 结构

```text
[搜索姓名 / 号码 / 账户…]

核心对象 12                       ← 默认最多 20 条
  ★ 李旭文      人   4 条关系 · 2 起事件
    项小文      人   3 条关系 · 1 起事件
    13800000001 号码 2 条关系
    …                            ← 超出 20：「展开全部 N」

提及 47 ▸                        ← 折叠；点开才请求
  （展开后 20 条 + 缺口提示；可收起）
```

- 搜索（`q`）时两组标题消失，改为一行「搜索结果 N 条」；结果每行带 `分组`，提及行画「提及」小标；
- 搜索与两组清单都按 `limit=20` 取；「展开全部」按 `limit=200` 取（`清单上限`）；
- 星标仍只存 `localStorage`、仅视图层置顶（服务端口径不受影响）；
- 排序按钮（涉案 / 名称 / 时间）保留，作用于当前清单；分组计数不受排序影响。

### 4.2 行的解释性

- 右侧固定写 `N 条关系 · M 起事件`（来自 `关联数` / `事件参与数`）；
- 两个数都为 0 时（只能因 `已确认/已修正` 进核心组）改画信任态徽章，否则用户看不出它为什么在核心组；
- 提及行两个数都为 0，画「无连接」一次，不重复两个 0。

### 4.3 状态与错误

| 链 | 信号 | 失败文案位置 |
|---|---|---|
| 分组计数 | `计数载入` / `计数错误` | 清单区上方 |
| 核心 / 搜索清单 | `清单载入` / `清单错误` | 清单区内 |
| 提及清单 | `提及载入` / `提及错误` | 提及组内（不污染核心清单） |

三条链各自 `onCleanup` 作废迟到回包（`LEARNINGS #005-03`）；换项目时全部清空。

## 5. 中栏档案（`entity-profile.tsx`）

### 5.1 版面

```text
一句话（服务端生成，不变）

数字卡：关系 / 事件 / 对手方 / 待确认
        （删「出处」；「待确认」点一下 = 回到整条实体并聚焦底栏「✓ 正确」）

关系：共 N 条 · 数据说的 n1 · 人说的 n2
  数据说的（默认 5 条）   [展开全部 n1]
  人说的（默认 5 条）    [展开全部 n2]
事件（默认 5 条）       [展开全部 n3]
出处（默认 5 条）       [展开全部 n4]
```

- 折叠是**纯前端**：数据已在回包里（服务端仍按 200 / 100 / 500 截断）；
- 换实体重置全部折叠（含出处）；裁决 / 切「显示已排除」重取不改变阅读位置；
- 折叠状态不写库、不跨会话记忆。

### 5.2 数字卡

| 格 | 值 | 落点 |
|---|---|---|
| 关系 | `关系总数` | 关系块 |
| 事件 | `事件总数` | 事件块 |
| 对手方 | `对方数` | 关系块（对手方在关系里） |
| 待确认 | `待确认.合计` | 回到整条实体 + 聚焦底栏「✓ 正确」 |

- 可读名 / `title` 带构成：`实体 x + 关系 y + 事件 z`；
- 缺口文案仍画在数字卡下方（服务端截断说明）。

### 5.3 裁决文案

底栏改为：

```text
抽取是否正确：  [✓ 正确]  [✗ 抽错]  [？存疑]
```

- 可见文字与 `aria-label` 同步改；
- `纠正原因们`（识别错 / 抽取错 / 材料本身有问题）不变；
- 语义仍是**数据质量**裁决，不是「排除涉案」。

## 6. 阶段 B：准入与纠正

### 6.1 新模块 `case-admission.ts`

```ts
/** 返回命中原因（写进 parse_detail 提示）；不是泛称返回 undefined。 */
export function 不可指认原因(类型: string, 规范值: string): string | undefined
```

规则（代码常量，逐条有单测）：

| 类型 | 规则 | 种子 |
|---|---|---|
| 地点 | 精确词表 | 现场、上侧、下侧、内侧、外侧、山林、山路、林地、本村山上、自留山/责任山、涉案山体、山上、山下、路边、附近、周围 |
| 地点 | 后缀规则：`(上侧\|下侧\|内侧\|外侧\|附近\|周围\|边上\|旁边)$` 且长度 ≤10 | — |
| 组织 | 精确词表 | 村委会、居委会、林业部门、林业主管部门、林业局、银行、运营商、派出所、鉴定机构、政府部门、相关单位、有关单位 |
| 人 | 精确角色词 | 民警、被害人、嫌疑人、证人、报案人、报警人、当事人、家属、群众、工作人员、负责人、不明人员 |
| 物品 | 精确词表 | 树木、林木、涉案树木、树桩 |

- **只做精确匹配 / 明确形状**，不猜近义；判不出就保留（fail-closed 的落点是「不拒」）；
- `40棵桂花树`、`柏加派出所`、`桂花树` 都**不拒**——它们是可指认的对象，缺的是连接（刀2）；
- 词表维护：本轮只改代码、带测试；不新增配置面（与会话 01 的「配置面越小越好」一致）。

### 6.2 落点：`case-extract.ts` 的 `加实体`

`加实体` 是实体进入输出的**唯一入口**（实体清单 / 关系端点 / 事件参与人都经它）：

- 命中 `不可指认原因` ⇒ 记 `提示`（**不进 `问题` / `须改正`**，不重试、材料不标黄）并返回 `undefined`；
- 实体清单里被拒 ⇒ 不建实体；
- 关系任一端点被拒 ⇒ `加实体` 返回 `undefined` ⇒ 关系在 `回读` 里跳过，记提示；
- 事件参与人被拒 ⇒ **保留原文**进 `participants`，不建实体。事件仍显示该文字；档案页按规范值等值匹配，
  不会把未入准的值误挂到任何实体上。

> `participants` 的契约从「只存实体规范值」扩展为「实体规范值，或未准入的提及原文」。
> 事件 id 含 `participants.join("|")`：重跑同一材料会得到新 id，但该材料的事实是先删后写
> （`case-ingest.ts:497-500`），不会产生重复。

### 6.3 组织后缀纠正：`case-subtype.ts` 的 `纠正大类`

```ts
const 组织后缀们 = [
  "派出所", "公安局", "法院", "检察院", "村委会", "居委会", "委员会",
  "管理局", "公司", "银行", "学校", "医院", "事务所", "鉴定所", "营业厅",
  "运营商", "林业局",
]
// 人 + 后缀命中 ⇒ 组织
```

- 只在 `大类 === "人"` 时改，其余大类原样返回；
- 不使用裸 `局 / 所 / 院`：会把「X 院」这类人名误改；
- `case-ingest.ts` 的 `端点()` 必须同步：候选大类改为由 `纠正大类` 推导，而不是硬列
  `人 / 号码 / 账户`——否则「柏加派出所」被纠正成「组织」后关系端点找不到，关系被静默丢弃。

### 6.4 证件号显示

前端新增唯一映射：

```ts
export function 细类显示名(细类: string | undefined | null): string | undefined
// "身份证" → "证件号"，其余原样
```

显示点：左栏行、档案标题 / 底栏对象文本、关系行「类别」、关系图浮层文字。
`graph-icons.tsx` 的图标查表**继续用原始 `subtype`**（`身份证` → id-card），不经过映射。

## 7. 数据模型与兼容

- **不新增表、不加列**（`待确认` 是聚合值，不落库）；
- 存量数据不迁移：
  - 旧泛称实体保留，靠「提及」分组折叠；
  - 旧「人」类型的单位名保留原类型，新抽取才会纠正；
  - 同一值可能同时存在「人」与「组织」两行（唯一索引含 `type`），属于显式重复，交人工合并；
- 服务端查询口径只改两处：清单分组过滤、档案数字卡聚合——与验收口径一致。

## 10. 已知缺口（如实登记）

1. **三个信号缺位**：跨源、量级异常、与问题相关本轮不具备；核心判据是「关系 / 事件 / 人确认」的并集。
2. **重复提议缺失**：`case_ai_proposal` 只是容器，没有检测器；误分类型的同一值会以两行出现。
3. **存量不修**：1106 案的 47 个孤立实体只会折叠，不会被清理；旧「人」类型的单位名不会自动纠正。
4. **表格通路**：话单 / 资金仍不产实体与关系；「200 个对手方」场景本轮无解（用户已裁定不做）。
5. **事件参与只认「人 / 号码」**：抽取器对参与人只推断这两类；物 / 地 / 角色要等刀2。
6. **别名不参与事件匹配**：`participants` 存规范值，别名命中不算连接。
