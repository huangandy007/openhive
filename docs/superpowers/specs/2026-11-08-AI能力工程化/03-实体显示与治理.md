# 议题三：实体显示与治理（2026-11-08）

> 合并原《议题3-实体档案界面优化》与《议题4-实体噪声与准入》。
> 讨论记录，**尚未进入设计、未动代码**。
>
> 一条线：**什么算实体 → 默认显示什么 → 档案页怎么显示**。

## 0. 缘起与结论

用户查看 `1106柏加信访案件梳理`，认为地址、组织、物品中的大部分实体不是用户关心的，
抽取存在重复，噪声对项目核心目的没有意义。随后追加反例：话单里 200 个对手方全部有通话关系，
「有连接才显示」在高基数数据上失效。

结论：

- **实体表是案卷目录，不是数据字典。** 明细可以有十几万个值，实体表只装与案子有关的那几十个。
- 默认视图只显示**有意义的连接**的对象；其余折叠为「提及」。
- 中栏档案按「为什么值得看」重排，全量折叠但不丢。
- 左栏「需要你看的」派生待办清单**否决**（被否决的是"待办清单"，不是"按连接分层显示"）。
- **表格明细不做 AI 抽取**：列解析已是确定性的，缺的是按对手方聚合与「提升」；
  明细是真相源，关系是提升后的产物（见 §4.1）。
- **AI 发现先提议**：MCP 保持只读；AI 发现的候选对象进收件箱 / 行内卡片，
  人拍板后才写 `case_entity`（对象）或进待查问题（判断）（见 §3.4）。

## 2. 三类噪声（处理方式不同）

### 2.1 假实体：不可指认的泛称 / 方位碎片

- 地点碎片：`现场`、`上侧`、`山林`、`山路`、`本村山上`、`自留山/责任山`
- 职能泛称：`村委会`、`林业部门`、`林业主管部门`、`银行`、`运营商`、`鉴定机构`、`派出所`

判据：**能不能指着它说"就是这一个"**。不能，就不是实体（最多是"提及"）。

### 2.2 重复实体：同一对象被抽成多个

- 桂树系列：`桂花树` / `40棵桂花树` / `40棵树` / `树木` / `林木` / `涉案树木`
- 机构：`林业部门` / `林业主管部门`；`派出所` / `柏加派出所`
- 类型冲突：`柏加派出所` 同时登记为"组织"和"人"（精确值重复仅此 1 组，近似重复更多）

结论：重复由**系统提议合并、人确认**，不由用户手工整理（与议题二"AI 只提议"一致）。

### 2.3 孤立实体：真东西，但没连上（最关键）

见 §1.3。处理不是删掉，而是**把事件里的物、地、角色连上去**，让它们获得意义。

### 2.4 类型错分

- 18 位身份证号归入"号码"（显示时应为"证件号"）。
- 单位名归入"人"（`柏加派出所`）。

## 3. 判据：什么算实体

### 3.1 案件对象 vs 数据端点

| | 案件对象 | 数据端点 |
|---|---|---|
| 是什么 | 案卷里要写"经查……"的人 / 账户 / 号码 | 记录另一头的值：对方号码、对手账户、收餐地址、商户 |
| 数量 | 几十个 | 几百到几万个 |
| 该放哪 | 实体表（案卷目录） | 明细行 / 聚合视图（数据字典） |
| 用户怎么用 | 点开看档案、拍板 | 排序、筛选、看异常 |

### 3.2 提升为实体的五个信号（满足任一，而非每条边都算）

1. **跨源出现**：同一值同时出现在话单、资金、笔录等 ≥2 类数据中（最强信号）
2. **量级异常**：金额最大、通话最多、夜间占比异常、首次/末次时间反常
3. **与问题相关**：出现在未闭合问题或已认定结论里（依赖议题二的问题层，见 `02-注意力与事实确认.md`）
4. **有人说过**：笔录 / 事件参与人里被点名
5. **人工关注**：星标、AI 提议、被转成问题

不满足的：留在明细里，不建实体、不进左栏，但**两次点击内可搜索到**。

### 3.3 一句话判据

> **有意义的连接**：边的权重（金额/频次/时段）＋ 跨数据源 ＋ 与问题相关 ＋ 被人提到。
> 单独一条普通边，不足以让一个值变成实体。

### 3.4 AI 发现的归宿（2026-11-08 追加）

AI 通过 MCP 查到可疑值时，**第一动作不是写实体表，也不是写产物**，而是生成「提议」。

先分三类：

| 类型 | 例子 | 归宿 |
|---|---|---|
| 对象 | 「账号 X 收款 37 万」「号码 Y 夜间通话 82%」 | 实体 Tab（人确认后） |
| 判断 | 「A 与 B 是同一人」「这笔是赃款」 | 待查问题 / 认定账本 |
| 中间过程 | 「Top 20 里排第一」 | 会话，不落持久对象 |

链路：

1. **生成提议**：值 + 类型 + 可验证的理由（跨源 / 异常 / 与已认定冲突）+ citation + 建议动作。
2. **双入口展示同一份数据**：右栏 AI 回复的行内卡片（记入案卷 / 转为问题 / 不用了），
   左栏收件箱（议题二的第二类「AI 提议」）。
3. **人拍板**：提升 → 写 `case_entity`（带 `role` / `reason` / 提案人 = AI）；
   转问题 → 进待查问题；忽略 → 记原因。
4. **产物引用回流**：报告里写下的对象必须能在实体 Tab 点开；保存产物时若引用了
   未提升的值，提示是否提升。

边界：

- **MCP 只读**，AI 不能直接写 `case_entity`；要写只能写「提议」。
- 不直接写实体表的三条理由：实体 Tab 是**全组共享**的案卷目录；AI 判定「可疑」的成本极低
  （按金额 / 频次排 Top N 自然靠前）；无 `reason`、无提案人、无幂等键会随会话重复膨胀。
- **产物不是发现的容器**：把发现直接写进报告会让报告变草稿本。产物的角色是「提升的最强信号」。

## 4. 多数据类型政策

| 数据 | 端点 | 默认展示 | 提升条件 |
|---|---|---|---|
| 话单 | 对方号码 | 按通话时长 / 夜间占比 / 首末次聚合，Top 10–20 | 跨源、异常、被笔录提到、人工关注 |
| 资金 | 对手账户 / 户名 | 按进出金额聚合，Top 10–20 | 大额、快进快出、分散转入、跨源 |
| 订餐 / 外卖 | 地址、电话、商户 | **不产实体，产「轨迹点」**（时间 + 地点 + 号码） | 与嫌疑人 / 涉案地址关联时才提升 |
| 物流 | 收寄人、电话、地址 | 同上，轨迹点 | 同上 |
| 文本笔录 | 人、物、地、组织 | 按 §2–§3 准入（可指认、有连接） | 出现在事件 / 关系里 |

关键：订餐、物流的主要价值是**时间 + 地点的轨迹**，不是"又多了几百个地址实体"。

### 4.1 表格与文本是两条通路

| | 文本（笔录 / docx） | 表格（话单 / 资金 / 订餐） |
|---|---|---|
| 方法 | LLM 抽取（现有 `跑文本`） | 确定性列映射 + SQL 聚合 |
| 产物 | 实体 / 关系 / 事件 | 明细行 → 聚合视图 → 少量提升 |
| 为什么不能用 LLM | — | 17 万行：贵、慢、不可复现、会编；切内网后更不可控 |

**现状基础（已具备）**：

- `case-mapping.ts:157-167` 的词典已覆盖 `对方账号 / 对方户名 / 对手账号 / 对手户名 → counterparty`，
  以及 `amount`、`balance`、`startedAt`、`durationSec`、`caller`、`callee`。
- `case-rows.ts:158-175` 已把这些值结构化写入明细行；认不出的原值回落 `extras`。
- 因此「谁跟谁、多少钱、什么时候」已经在表里，缺的是聚合与提升，不是抽取。

**三条原则**：

1. **明细是真相源，关系是产物**。现有 `aggregate_money` 从 `case_relation` 出发，
   没有关系就聚合为空；表格聚合应直接读明细，关系只承载「人说的」与已提升的部分。
2. **先出聚合视图，后写实体表**。聚合是派生的（改口径重算即可），实体是案卷目录（写错要人工清理）。
3. **列映射质量是前置门槛**。第 0 步先验证真实资金表上 `counterparty` 的识别率与空值率；
   识别率低就先修映射，不碰实体。

**落地顺序**：

| 步 | 内容 | 写库 |
|---|---|---|
| 0 | 对真实资金表按 `counterparty` 分组查 Top 20，核对识别率 / 本方账号误判 / 空值 | 否 |
| 1 | 资金 / 话单视图的「对手方 Top 20」（笔数、进出金额、首末次、夜间占比） | 否 |
| 2 | 提升规则 + 人工提升，命中 §3.2 五信号才写 `case_entity` | 是 |
| 3 | 与问题层联动（出现在未闭合问题里的值强制提升） | 是 |

## 5. 显示层

### 5.1 左栏实体 Tab

```text
核心对象（12）        ← 人 / 号码 / 账户 / 关键物，案卷目录
交易对手（Top 20）     ← 话单 / 资金的另一头，按权重排；可搜索全部
提及（折叠）           ← 无权重、无连接、无人提到
```

- 200 个对手方 → 默认 20 条 +「查看全部 200」+ 搜索；
- 点开对手方看到的是**聚合摘要**（通话 37 次、夜间 80%、首次 10-01），不是空档案；
- 对手方详情入口在「话单 / 资金」视图，实体 Tab 只给摘要与跳转；
- 类型计数可拆成「核心 / 提及」，截断说明放顶部（「提及」是否入库取决于 §9.1-3）。

**明确不做**：左栏「需要你看的」派生待办清单（按后果过滤、同实体聚合、溢出计数、稍后/忽略）。

## 6. 处理方案（四刀，按顺序）

| 顺序 | 内容 | 说明 | 成本 |
|---|---|---|---|
| 1 | **默认视图只显示"有意义的连接"实体**，其余折叠为「提及」 | 不改库、不改抽取；但**必须动服务端查询口径**（按连接权重过滤 / 排序）——只在已返回的 200 条里前端筛，会漏掉排在后面的有连接实体；判据见 §3.2 | 中 |
| 2 | **事件结构化**：事件带参与人、涉及物、地点、角色 | 让 `40棵桂花树` 从孤立噪音变成核心物；治本 | 中 |
| 3 | **准入规则**：泛称词表 + 方位碎片规则 + 专名要求；身份证归"证件号"；重复由 AI 提议合并 | 减少源头垃圾 | 中 |
| 4 | **按案件类型配实体 schema**（信访 / 资金 / 电诈 关注的实体与关系不同） | 长期，避免把通用 NER 结果直接倒给用户 | 大，最后做 |

## 7. 数据模型原则

**明细不动，聚合按需算，提升是显式动作。**

- 17.7 万行继续留在明细表（现状已如此）；
- 聚合视图现算，不落成实体；
- 「提升」由规则（跨源、阈值）或人工触发，写入 `case_entity` 时带 `role`（核心对象 / 交易对手）
  与 `reason`（为什么提升）；
- 不提升的值不写 `case_entity`。

目标：**明细规模 ×10，实体规模不超过 ×1.5**——两个规模解耦。

## 8. 验收指标

- 默认视图 ≤ 20 条；话单 200 个对手方时，默认 ≤ 20 条且排序可解释"为什么它在前面"；
- 有用实体率 = 有意义的连接的实体 ÷ 全部实体 ≥ 60%（本项目旧口径 12/59 ≈ 20%）；
- 精确重复（同值同项目）不超过 1%；
- 「提及」可搜索、可点开，但默认不出现；任意对手方两次点击内可查；
- 订餐 / 物流数据产生的实体数 ≈ 0，产生的是轨迹点；
- 首屏不再出现超过 5 行的关系表格；出处默认不超过 5 条（现状 20，`entity-profile.tsx:43`）；
- 所有全量数据仍可一键展开，展开条数与「总数」一致；不新增数据表；
- 除数字卡聚合与第 1 刀的连接过滤外，不改服务端查询口径；
- 「一句话」仍由服务端生成，前端不拼第二份结论；
- 折叠状态不写库、不跨会话记忆（每次打开默认收起）。

## 9. 未决

### 9.1 建模与抽取

1. 事件与物 / 地 / 角色的建模方式：扩 `participants` 结构？新增事件—实体关联？还是用关系类型表达？
2. 泛称词表的范围与维护方式（谁加词、是否按案件类型分表）。
3. 「提及」是否入库：仍写 `case_entity` 但标记，还是只保留在材料文本里。
4. 合并提议的交互：并入议题二的 AI 提议通道，还是单独入口。
5. `case_entity` 是否新增 `role` / `reason`，还是单开一张「提升记录」表。
6. 「跨源」判定口径：同一规范值在不同 `case_material.kind` 出现即算，还是要求不同事实类型。
7. 轨迹点（订餐 / 物流）落在哪：扩展 `case_event`，还是明细聚合视图。
8. 聚合 Top N 的权重公式（通话时长 / 次数 / 夜间占比 / 金额）如何配比、是否可解释。
9. 真实资金表上 `counterparty` 的识别率与空值率（第 0 步前置验证；不达标先修映射，不碰实体）。

### 9.2 档案显示

1. 裁决文案：现状已查清——「排除」必填的原因类型是 `识别错 / 抽取错 / 材料本身有问题`
   （`case-fact-change.ts:42`），即**数据质量**语义，不是「不涉案 / 排除嫌疑」。
   待定的是：文案怎么改（`✗ 错` 容易被读成排除涉案），以及是否需要新增「不涉案」这个业务动作。
2. 「涉案金额」口径：只算转账类关系？含已排除吗？人说的与数据说的如何合并？
3. 「待确认」计数口径：实体本身未确认，还是其关系/事件里未确认的条数？
4. 「关键事实 Top 5」选取规则：金额 / 次数 / 与未闭合问题的相关性？
   服务端只返回前 200 条，前端取 Top 5 可能漏掉被截断的大额，是否改由后端出。
5. 折叠默认条数：5 条是否合适（关系 / 事件 / 出处统一，还是分开）。

### 9.3 排期

- 第 1 刀（默认过滤）与议题二问题层的实施先后。
