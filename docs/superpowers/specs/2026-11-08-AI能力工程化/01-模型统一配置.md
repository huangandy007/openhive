## 3. 根因

- 聊天与后台抽取是**两套模型解析机制**：聊天按会话显式传 `{providerID, modelID}`；
  后台任务走 `provider.defaultModel()` 兜底（`provider.ts:2033-2066`：配置 `model` →
  最近模型缓存 `model.json` → 配置的 provider（未配置则全部 provider）里排序后的第一个模型），
  **全程不校验供应商是否可达**
- 作业在 0 成功切片时仍记录「完成」，失败不可见

## 4. 已达成的决策

| 编号 | 主题 | 决策 |
|---|---|---|
| D1 | 内网模型接入形态 | **A：统一 OpenAI 兼容网关**（所有模型共用一个 `baseURL + key`，模型名走网关） |
| D2 | 后台任务用哪个模型 | **B：独立 `task_model` 槽位**，缺省回落到聊天默认 `model`；共用同一套 provider 配置 |
| D3 | 配置位置与运维方式 | **A：只认配置文件**（`opencode.jsonc` + 部署时由运维提供网关连接参数），改完重启生效 |
| D4 | 失败语义 | **C：启动自检 ＋ 运行期显式失败**（作业失败标「失败」并在前端显眼展示原因，聊天明确报错） |
| D5 | 总体方案 | **方案 1：统一模型槽位 ＋ 单一解析器**；聊天默认、案件抽取、复制项目全走同一解析器；删除 `OPENHIVE_CASE_EXTRACT_MODEL` |
| D6 | 严格程度 | 后台任务**强制**要求 `task_model` 或 `model`，未配置直接拒绝作业并提示；聊天保留现有兜底行为 |
