# 模型统一配置 · 设计（2026-11-08）

> 上游讨论记录见 `01-模型统一配置.md`。本文是**设计**，不是实施计划。
> 状态：已逐节确认（§1 范围 / §2 配置 / §3 行为 / §4 自检与展示 / §5 测试）。

## 1. 背景与目标

### 1.1 问题

`020602` 在 `1105反诈交流` 解析后看不到实体。查出的直接原因有两条：

1. 后台抽取走 `provider.defaultModel()` 兜底，落到不可达的 `openai/gpt-5.6-terra-pro`，
   4 个切片 × 3 次重试全部 `ECONNREFUSED`；
2. 0 个切片成功时作业仍记「完成」，失败不可见。

结构性原因是**两套模型解析机制**：聊天按会话显式传 `{providerID, modelID}`；
后台任务走 `defaultModel()` 的隐式兜底（配置 `model` → 最近模型缓存 → 第一个可用 provider），
全程不校验可达性。后期切到内网自部署模型时，这套隐式兜底会让切换不可控、不可复现。

### 1.2 目标

- 后台任务使用**显式配置**的模型，不再隐式兜底；
- 聊天、抽取、复制项目共用**一个解析入口**；
- 只认配置文件，改完重启生效；
- 失败可见：缺配置、模型不可用、0 成功切片，都必须显式报错。

### 1.3 非目标

- 不做模型路由、负载均衡、自动降级；
- 不做在线模型热切换；
- 不改会话里「用户显式选模型」的优先级；
- 不优化抽取重试策略（沿用现状）。

## 2. 决策汇总

| # | 主题 | 决策 |
|---|---|---|
| D1 | 内网接入形态 | 统一 OpenAI 兼容网关（一个 `baseURL + key`，模型名走网关） |
| D2 | 后台任务模型 | 独立 `task_model` 槽位，缺省回落 `model` |
| D3 | 配置位置 | 只认配置文件（`opencode.jsonc`），改完重启生效 |
| D4 | 失败语义 | 启动自检 + 运行期显式失败 |
| D5 | 总体方案 | 统一模型槽位 + 单一解析器；删除 `OPENHIVE_CASE_EXTRACT_MODEL` |
| D6 | 严格程度 | 后台任务必须有 `task_model` 或 `model`，未配置直接拒绝作业 |
| E1 | 字段形态 | 顶层 `task_model`（snake_case，与 `default_agent` 同风格） |
| E2 | 旧 env | 硬删除读取；检测到只打 WARN，不生效 |
| E3 | 自检边界 | 只查配置完整性，错则拒绝启动；不做网络探测 |
| E4 | 无模型环境 | 跟随 PG 开关：没配 PG 不要求模型；配了 PG 必须有 |
| E5 | 前端 | 设置 → 模型页只读展示两个槽位 |
| E6 | 重试 | 沿用每片 3 次 |

## 3. 架构

### 3.1 统一解析器

新增 `packages/opencode/src/server/openhive/model-resolve.ts`。不改 `provider.ts` 的接口。

> 下面是最初的接口草图；实际签名以 `model-resolve.ts` 为准：`ID` 用 `ProviderV2.ID` /
> `ModelV2.ID` 的品牌类型（不是 `string`），错误用 `Schema.TaggedErrorClass`（这个 Effect
> 版本没有 `Data.TaggedError`），`resolveModel` 另带 `Config.Service | Provider.Service` 需求。

```ts
export type Purpose = "chat" | "task"

export interface ResolvedModel {
  readonly providerID: string
  readonly modelID: string
  readonly source: "session" | "task_model" | "model" | "fallback"
}

export class ModelUnavailable extends Data.TaggedError("ModelUnavailable")<{
  readonly purpose: Purpose
  readonly reason: "no_config" | "bad_format" | "unknown_provider" | "unknown_model"
  readonly detail: string
}> {}

export const resolveModel: (
  purpose: Purpose,
  explicit?: { providerID: string; modelID: string },
) => Effect.Effect<ResolvedModel, ModelUnavailable>
```

**解析顺序：**

| purpose | 顺序 | 都没有时 |
|---|---|---|
| `task` | `task_model` → `model` | 抛 `ModelUnavailable` |
| `chat` | 显式传入 → `defaultModel()`（现状：`model` → 最近缓存 → 第一个 provider） | 保持现状 |

**关键约束：`task` 不调用 `defaultModel()`。** 没配就是没配，不找"最近缓存"或"第一个可用 provider"。

**调用点归属：**

| 调用点 | purpose | 未配置时 |
|---|---|---|
| 案件抽取（`case-ingest-worker.ts`） | task | 作业失败，材料「有问题」 |
| 复制项目命名（`project-copy.ts:28`） | task | 回落 slug，不阻断 |
| agent 默认（`agent.ts:373`） | chat | 现状兜底 |
| ACP / CLI debug | chat | 现状兜底 |

不批量改造现有 chat 调用点；`resolveModel("chat")` 只作为新代码的统一入口。

### 3.2 配置结构与 schema 扩展

目标形态：

```jsonc
{
  "model": "gateway/chat-model",
  "task_model": "gateway/task-model",
  "provider": {
    "gateway": {
      "npm": "@ai-sdk/openai-compatible",
      "options": {
        "baseURL": "http://10.x.x.x:8000/v1",
        "apiKey": "……"
      },
      "models": {
        "chat-model": { "name": "内网对话模型" },
        "task-model": { "name": "内网抽取模型" }
      }
    }
  }
}
```

**schema 扩展（不碰上游 `packages/core`）：**

在 `packages/opencode/src/config/config.ts` 构造：

```ts
const OpenhiveInfo = Schema.extend(ConfigV1.Info, {
  task_model: Schema.optional(Schema.String),
})
```

- 把该文件里所有 `ConfigParse.schema(ConfigV1.Info, …)`（至少 `:201`、`:688`）统一换成 `OpenhiveInfo`；
- 写入路径（`update` / `updateGlobal`）使用同一 schema，避免「读得到、保存时丢掉」；
- `type Info = ConfigV1.Info & { plugin_origins?: ... }`（`:114`）增加 `task_model?: string`。

**为什么不复用 `small_model`：**

- `small_model` 用于标题生成等小任务，由 `getSmallModel()` 按 provider 选取；
- 抽取是重任务，不应被「换个便宜模型做标题」牵连；
- 两个槽位独立，运维才能单独钉住抽取模型。

### 3.3 启动自检

**落点：** `case-ingest-worker.ts` 的 `layer` 初始化内，在现有 `PG_ENV` 判断之后、起消费循环之前。

这样天然满足 E4：没配 PG → 直接 return，不检查模型；配了 PG → 必须通过模型检查。

**检查内容（只查配置，不探网）：**

1. `task_model` 或 `model` 至少有一个；
2. 格式是 `provider/model`；
3. provider 若在配置文件里声明了 `models`，模型名必须在其中；provider 来自
   `opencode auth login` / models.dev 时启动期无法离线校验（校验要 boot 实例、会往项目表写行），
   记一条 INFO「启动期无法校验，作业期再判」，由作业期的 `provider.getModel` 暴露
   `unknown_provider` / `unknown_model`。
4. 模型能解析。

**失败处置：** 抛结构化错误，Layer 构建失败 → 内核启动失败 → 顶层 `index.ts:128-136` 打印并 `exitCode = 1`。
文案必须写明缺哪个字段、哪个模型解析不出。

**成功：** 自检时解析一次并缓存 `ResolvedModel`；消费循环与作业执行复用这份缓存，不在每个作业里重读配置。
INFO 日志记录 `task_model` / `model` 的实际值与 source（不含 apiKey）。

**旧 env：** 启动时若检测到 `OPENHIVE_CASE_EXTRACT_MODEL`，打一条 WARN「已忽略，请改用 task_model」，不读取。

### 3.4 前端

落点：`packages/app/src/components/settings-models.tsx`，在模型列表上方加只读区：

```
当前生效
  聊天默认    gateway/chat-model
  后台任务    gateway/task-model      （显式配置）
  或          未设置，回落到 gateway/chat-model
```

**数据源：新增 `GET /openhive/config/models`**，只返回：

```json
{
  "chat": { "model": "gateway/chat-model", "source": "model" },
  "task": { "model": "gateway/task-model", "source": "task_model" }
}
```

**不复用 `GET /config`：**

1. 它的 success schema 是上游 `ConfigV1.Info`（`groups/config.ts:18`），没有 `task_model`；
2. 它返回整份配置，含 `provider.options.apiKey`，不应送到浏览器。

**权限：** 沿用设置页现有可见性，不新增权限模型。

**无实例上下文：** 这个口不 boot 实例，所以 `chat` 槽位只展示配置里的 `model`；
运行时若兜底到「最近模型缓存」，设置页显示「未设置」。展示不驱动运行时行为。

## 4. 数据流

```
启动
  └─ case-ingest-worker.layer
       ├─ PG 未配置 → 不起 worker，不检查模型
       └─ PG 已配置 → 自检 model/task_model
            ├─ 失败 → 内核启动失败（exitCode 1）
            └─ 成功 → 起消费循环，缓存 resolvedModel

作业执行
  └─ 建抽取器
       ├─ 用启动期缓存的 ResolvedModel（不重读配置）
       ├─ getModel → getLanguage → 调用模型
       └─ 模型不可用 → 作业「失败」+ 材料「有问题」+ reason

前端
  └─ GET /openhive/config/models → 设置页只读展示
```

## 5. 错误处理

| 情况 | 作业状态 | 材料状态 | 用户看到 |
|---|---|---|---|
| 无 `task_model` 且无 `model` | 失败 | 有问题 | 「未配置后台模型：请设置 task_model 或 model」 |
| 配置存在但解析不出 | 失败 | 有问题 | 「task_model=xxx 解析不出可用模型（provider 或模型名不存在）」 |
| 全部切片失败 | 失败 | 有问题 | 带每片失败原因 |
| 部分切片成功 | 完成 | 有问题 | 「N/M 片成功」，已抽到的照常入库 |
| 全部成功 | 完成 | 已解析 | — |

> 这是对 `case-ingest.ts` 旧注释（「同一件事说两遍」）的有意反转：作业状态是运行层聚合信号，
> 全部失败通常是模型不可达这类系统性故障，记「完成」会让队列与运维看不见它。

**0 成功切片不得记「完成」**——这是本轮要修掉的第二个根因。

**source 传播：** `parse_detail` 记录 `source`（`task_model` / `model`）；错误文案带 source；
前端设置页据此区分「显式配置」与「回落」。

## 6. 测试与验收

### 6.1 单元测试（`model-resolve.test.ts`）

| 用例 | 期望 |
|---|---|
| task：有 `task_model` | 返回它，`source = task_model` |
| task：只有 `model` | 返回它，`source = model` |

| chat：显式传入 | `source = session` |

### 6.2 作业状态测试

| 情况 | 作业 | 材料 |
|---|---|---|
| 全部切片失败 | 失败 | 有问题 |
| 部分成功 | 完成 | 有问题 + 「N/M 片成功」 |
| 全部成功 | 完成 | 已解析 |
| 无模型配置 | 失败 | 有问题，reason 含「未配置 task_model」 |

### 6.3 配置加载测试

- `opencode.jsonc` 写了 `task_model` → `config.get()` 能读到；
- `update` / 保存后 `task_model` 不丢；
- 其他未知字段仍按原行为忽略。

### 6.4 启动自检测试

- 配了 PG + 缺模型 → 启动失败；
- 没配 PG + 缺模型 → 正常启动；
- 配了 PG + 模型有效 → 正常启动。

### 6.5 前端与端点

- 设置页显示两个槽位，task 未设时显示「回落到 …」；
- `/openhive/config/models` 的响应字段白名单断言：不出现 `apiKey`、`baseURL`、`options`。

### 6.6 真栈验收（`1105反诈交流`）

## 7. 实施顺序

1. **配置层**：扩展 schema、读 `task_model`、`config.get()` 可读、写入不丢。
2. **解析器**：新增 `model-resolve.ts` + 单元测试。
3. **接入抽取**：`case-ingest-worker.ts` 改用 `resolveModel("task")`，删除 env 读取。
4. **失败可见**：作业状态与材料状态的显式落库（0 成功 / 部分成功 / 全部成功）。
5. **启动自检**：worker layer 内检查配置，失败拒绝启动。
6. **端点与前端**：`/openhive/config/models` + 设置页只读区。
7. **真栈验收**：按 §6.6 走一遍。

## 8. 不变量

1. 聊天里用户显式选的模型，优先级永远最高；
2. 后台任务永不隐式兜底到「第一个可用 provider」；
3. 错误文案永远可解释：缺哪个字段、哪个模型、source 是什么；
4. 前端拿不到 apiKey / baseURL；
5. 上游 `packages/core` 不改；改动集中在 `packages/opencode/src/config/config.ts`、
   新增的 `model-resolve.ts`、`case-ingest-worker.ts`、`case-ingest.ts` 和设置页。

## 9. 实施期约定

- 错误只需 `ModelUnavailable.reason` 枚举，不额外定义错误码；前端按 reason 映射文案。
- INFO 日志只记 `providerID/modelID` 与 source，不记 `baseURL`；provider ID 是逻辑名（如 `gateway`），不是内网地址。
- 设置页沿用现有可见性，不新增权限判断；非管理员能否看到由现有设置页权限决定。
