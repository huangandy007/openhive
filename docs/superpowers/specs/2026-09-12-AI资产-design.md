## 0. 定位与范围

「AI 资产」把三类能力统一当成「资产」，用一套元数据 / 权限 / 生命周期治理：

| 资产类型 | 本质 | 载体 |
|---|---|---|
| Skill | 方法/流程（怎么分析） | opencode 原生 skill |
| MCP | 工具/接口（能查什么） | opencode MCP + 自研 connector |
| RAG 知识库 | 资料/事实（某规定是什么） | RAGFlow |

**统一按「资产」抽象处理，只在差异处单独标注**（MCP 授权差异见 §4，生命周期差异见 §2.0）。

两个入口：
- **前端「AI 资产」工作区**（点图标栏 🧩 进入）：民警「**用**」资产。
- **治理后台「AI 资产治理」**（§4.2 八大类之一）：管理员「**管**」资产（审核/发布/上下架）。

## 1. 前端展示与管理

### 1.1 入口形态：左栏分类导航 + 中栏展示（复用三栏）

点图标栏 🧩 → 进入「AI 资产」工作区，复用三栏心智（不造独立技能市场页）：

```
左栏 = 分类导航（Skill/MCP/知识库 三 tab + 业务分类分组 + 搜索 + 空间筛选）
中栏 = 展示区（列表 / 详情 tab，承载查询/学习/收藏/评价/下指令）
右栏 = AI 会话（不变，学习时可问「这个 skill 怎么用」）
```

左栏导航结构：

```
🧩 AI 资产
├─ 🔍 搜索框（按名称/描述/标签）
├─ 筛选器：全局 / 部门 / 个人（多选，默认全部）
├─ Tab：Skill | MCP | 知识库
│    └─ 每组内按「业务分类」分组（可扩展清单）
│         └─ 资产列表项：名称 + 空间角标 + 右侧 ★（点选收藏/取消）
```

- **业务分类主分组**（情报研判/案件办理/文书写作/审讯深挖/督导考核…），民警按「我要做哪类业务」找资产；**三级空间（全局/部门/个人）降级为角标 + 筛选器**，不作主分组。
- **业务分类清单 = 可扩展字段**：上线预置一份（对应全流程环节），后续由业务管理员维护增改。

### 1.2 中栏展示（列表 + 详情 tab）

**① 列表视图**：资产卡片 = 名称 + 图标 + 一句话用途 + 业务分类 + 空间角标 + **作者** + 评分 ★ + 收藏状态。

**② 详情视图（tab 版）**：头部固定 + tab 分块。

- **头部固定**（不随 tab 切换）：名称 + 空间角标 + ★收藏 + 评分 + **作者署名** + 主按钮「▶ 让 AI 助手执行此 skill」。
- **tab 栏**：`介绍 | 注意事项 | 评价 | 版本`，默认「介绍」。
  - 介绍：是什么 / 适用场景 / 怎么用 / 示例
  - 注意事项：**显式的不确定性标注**（⚠ AI 可能在哪不准、必须人工复核什么）
  - 评价：1–5 星 + 文字 + 问题标记
  - 版本：版本号 + 变更说明

### 1.3 收藏语义（弃用「启用」，收藏 ≠ 授权）

- **收藏动作**：资产列表项 / 详情页右侧 ★，点选即收藏、再点取消。
- **收藏的作用**：只作右栏「更多 skill 抽屉」的**排序加权**——高频在前、收藏的低频排后、按当前模块筛选，**不在左栏设「我的收藏」分组**（不占导航空间）。
- **收藏 ≠ 授权**：收藏是个人偏好（加入常用清单），授权是 RBAC 读权限（能否看到/使用），彻底分离。

### 1.4 下指令给 AI（把可发现性延伸到中栏）

详情页主按钮「▶ 让 AI 助手执行此 skill」——浏览资产后认为符合当前业务，点击把一句指令填入右栏 AI 助手输入框（skill 名 + 当前上下文），可编辑后发送。与右栏指令卡「点卡片 = 填入一句话」同一机制。

### 1.5 右栏 AI 助手（指令卡机制，呼应 §8.2 / 资金分析 §6.1）

```
上下文指令（浅金底，随中栏选中动态）
常用操作（白底，当前模块高频）
聊天区
输入框 + ▸ 按钮 → 点 ▸ 从右侧滑出「更多 skill」抽屉
```

「更多 skill」抽屉收纳其余有权 skill（按 skill 分组 + 最近使用上浮 + **收藏低频排后**），不在右栏常驻占位。

> **「AI 资产」工作区的右栏不投影**：进入 AI 资产工作区时，右栏指令卡**不做投影切换**，仍停留在此前所切换的业务模块（如资金分析）；「AI 资产」本身不是业务分析模块，不产生自己的指令卡投影。

### 1.6 元数据模型（前端可见 vs 治理可见）

| 字段 | 民警可见 | 治理后台可见 |
|---|---|---|
| 名称 / 图标 / 一句话描述 / 业务分类 / 空间角标 / **作者** | ✓ | ✓ |
| 评分 / 使用次数 / 收藏状态 | ✓ | ✓ |
| 版本号 / 所属部门 / 状态 / 变更说明 | 部分（版本记录） | ✓ |
| 启用数 / 反馈明细 / 审计日志 | — | ✓ |

> 「作者」= 创建人（署名给领域专家荣誉）；「所属部门」= 组织归属，两者分离。

## 2. 生命周期流程

### 2.0 生命周期适用性（差异标注）

7 状态机（草稿→…→归档）**主要针对 Skill**；MCP / 知识库生命周期简化：

| 资产 | 生命周期 |
|---|---|
| Skill | 完整 7 状态机（内容正确性 + 可泛化性审核） |
| MCP | 简化：注册配置 → 授权 → 下发 → 可用/下线（仅技术审核，无内容审核） |
| 知识库 | 简化：上传资料 → 审核 → 建库 → 可用/下线（审资料准确性，无「可泛化性」） |

### 2.1 状态机（7 状态）

```
草稿 ──提交审核──▶ 审核中 ──业务审核通过──▶ 已发布 ──发起迭代──▶ 迭代中
  ▲                  │驳回                                      │
  └──────────────────┘                                          │新版本发布替换旧版
                                                                 ▼
                                                              已发布
                                                               │发现问题下线
                                                               ▼
                                                              已下线 ──修复重新上线──▶ 已发布
                                                               │
                                                               ▼（长期不用）
                                                              已归档（终态）
```

### 2.2 流转动作 + 触发者

| 当前状态 | 动作 | 触发者 | 目标状态 | 物理动作 |
|---|---|---|---|---|
| 草稿 | 提交审核 | 作者 | 审核中 | 复制到 `/assets/pending/` |
| 审核中 | 业务审核通过 | 业务管理员 | 已发布 | 经技术发布后复制到 `/assets/{global,dept}/skills/` |
| 审核中 | 驳回 | 业务管理员 | 草稿 | 退回草稿 |
| 已发布 | 发起迭代 | 作者 | 迭代中 | 新版本入 `pending`，旧版保留发布目录 |
| 迭代中 | 新版本发布 | 业务+系统管理员 | 已发布 | 新版本替换旧版 |
| 已发布 | 发现问题下线 | 管理员 | 已下线 | 移出发布目录 |
| 已下线 | 修复重新上线 | 作者+管理员 | 已发布 | 重新入发布目录 |
| 已下线/已发布 | 归档 | 管理员 | 已归档 | 移到 `/assets/archive/` |

### 2.3 审核两道关（审核权分离）

- **业务审核**：业务管理员审「套路对不对 + 可泛化性」。
- **技术发布**：系统管理员查「能跑 + 无安全问题」。
- 两道关分离（业务专家管内容，IT 管技术合规）。

### 2.4 迭代语义

- 「迭代中」= 已发布版本**继续可用** + 新版本草稿在途（版本号 +1）。
- 新版本走完整审核，发布后**替换**旧版，回到「已发布」。

### 2.5 物理迁移（沙箱 → pending → 发布目录）

```
作者沙箱 /workspaces/{authorId}/{project}/   ← 草稿（个人资产也留这里）
   └─提交审核（复制）→ /assets/pending/{name}/   ← 审核中（不迁移，停在 pending）
        └─发布（复制）→ /assets/{global,dept}/skills/{name}/  ← 已发布
             └─归档 → /assets/archive/{name}/
```

- 提交审核、发布两次迁移之间，审核中文件停在 `/assets/pending/`。
- **迭代的文件处理**：发起迭代 = 新版本入 `pending`（旧版保留发布目录）；新版本发布 = **先删旧 + 复制新**（或临时目录 + 原子 rename），避免「直接覆盖」残留旧版本已删文件。
- 提交审核/发布用 **MCP 工具驱动**（`submit_skill_for_review` / `publish_skill`），鉴权靠 capability。
- **个人资产升级为全局/部门资产时，不动用户沙箱的原始文件**：发布是「复制」到发布目录，用户沙箱里的原始文件保留，后续迭代仍在沙箱原文件上修改完善。

### 2.6 站内信通知（状态变化推送到人）

| 状态变化 | 推送给谁 | 内容 |
|---|---|---|
| 草稿 → 提交审核 | 业务管理员 | 「有 skill 待审核」 |
| 审核中 → 通过 | 作者 + 系统管理员 | 「已过业务审核，待技术发布」/「有待发布」 |
| 审核中 → 驳回 | 作者 | 「被驳回 + 理由」 |
| 待发布 → 已发布 | 作者 | 「已发布上线」 |
| 已发布 → 下线 | 作者 + 使用者（收藏/最近用过） | 「已下线 + 原因」 |
| 已下线 → 重新上线 | 使用者 | 「已修复重新上线」 |
| → 已归档 | 作者 | 「已归档」 |

- 归入现有「系统」类 + 「🧩 资产」标签。
- **发布不广播给全体**（避免通知轰炸，新 skill 让民警在资产工作区主动发现）。

## 3. 权限管理

### 3.1 四类权限动作

| 权限 | 含义 | 对应动作 |
|---|---|---|
| 读 | 看到、使用 | 浏览、收藏、调用 |
| 写 | 编辑内容 | 作者改草稿 / 发起迭代 |
| 审 | 审核、批准上线 | 业务审核 |
| 管 | 上下架、删除、批量授权 | 系统管理员 |

### 3.2 三级空间 × 可见范围

| 空间 | 可见范围（读） | 维护者 |
|---|---|---|
| 全局资产 | 全单位可用 | 系统 + 业务管理员 |
| 部门资产 | 本科室可见 | 部门业务管理员 |
| 个人资产 | 仅本人可见 | 作者自己 |

### 3.3 角色 × 权限矩阵

| 角色 | 读 | 写 | 审 | 管 |
|---|---|---|---|---|
| 使用者（全体民警） | ✓ | — | — | — |
| 资产作者 | ✓（自己的） | ✓（自己的） | — | — |
| 业务管理员 | ✓ | — | ✓ | — |
| 系统管理员 | ✓ | — | — | ✓ |

### 3.4 授权组（跨部门定向授权）

三级空间只能按「组织归属」授权（全局/部门/个人），表达不了「跨部门的一群人」（如电诈专案组）。补「**授权组**」：

```
资产可见范围 = 三级空间范围（全局/部门/个人） ∪ 授权组范围（指定用户组）
```

- **授权组 = RBAC 里的一种自定义 role**（`role_type='group'`），跨部门拉人进组。
- 资产授权给组 = `role_resource` 加一条（`role_id=组, resource_id=资产, perm=读`）。
- 完全复用 §14.3 的 RBAC 三张表（`role` / `user_role` / `role_resource`），不新造权限体系。
- **不冲突**：授权组是业务层资产授权，opencode 原生权限是内核操作安全，两个层面；**零新增源码改动**，通过已规划的「capability 签发 + 工具执行守卫」（§3.1 三处必改之一）生效。

### 3.5 授权 vs 收藏（彻底分离）

| 概念 | 本质 | 谁决定 | 落点 |
|---|---|---|---|
| 授权 | RBAC 读权限 | 管理员/系统 | `role_resource` + capability |
| 收藏 | 个人偏好 | 民警自己 | 影响右栏「更多 skill 抽屉」排序 |

### 3.6 三层拦截（capability 下沉执行层，AI「想调也调不了」）

**原理**：大模型只能调用「系统在请求里塞给它的 `tools` 清单」里的工具，没有「扫描全系统工具」的能力。所以「不调取」不是「劝 AI 别用」，而是「不放进视野 + 执行硬拦 + 数据兜底」三层：

| 层 | 拦截点 | 效果 |
|---|---|---|
| ① 工具清单过滤 | 组装 `tools` 前按 capability 过滤 | **看不到**（清单里没有，模型无从调用） |
| ② 工具执行鉴权 | 执行器入口再验 capability | **调不了**（幻觉/注入强行调 → AccessDenied + 审计） |
| ③ MCP 账号兜底 | 受限账号 + RLS | **拿不到**（即使执行了，数据库只吐有权数据） |

## 4. MCP 授权差异

MCP 是「连接」（靠读 `opencode.json` 的 `mcp` 段发现），授权比 skill 多两层：

| 层 | 问题 | 落点 | 与 skill 对比 |
|---|---|---|---|
| ① 授权 | 谁能用 | RBAC `role_resource`（resource_type=mcp） | 一致（授权组、三级空间都适用） |
| ② 下发 | 连到哪、怎么连 | 按用户拼进各自 `opencode.json` 的 `mcp` 段 | MCP 独有（skill 拼 `skills.paths`，机制类似） |
| ③ 身份 | 以谁的身份连 | 连接注入 `X-User-ID` + 服务端 RLS | MCP 独有、最关键（skill 无「连接身份」） |

**数据隔离四环**：授权（谁能用）→ 下发（连到哪）→ 连接带身份（以谁的身份）→ 服务端 RLS（只能拿谁的数据），环环相扣，缺一环就漏数据。

> 完整案例（张三查「资金数据查询 MCP」）见 §14.1 capability 与 §11.7，本设计已确认「下发带身份 + RLS 过滤」的链路。

## 5. Skill 制作（资产来源）

### 5.1 主路径：自然语言编写 + 测试迭代（4 步）

```
① 复盘/讨论（人主导）：作者（一人或专家组）对某工作复盘，形成「怎么做最优」的思路/共识
② 自然语言生成：把思路用大白话输送给 opencode「请帮我生成一个 skill」
③ 测试迭代：测试生成的 skill → 发现问题 → 修正 → 再测（草稿在作者沙箱正常试用，无特殊 UI）
④ 发起审核：测试成功、认为可用了 → 提交审核（进入 §2 生命周期）
```

- **入口 = 用户与 AI 助手对话**：作者在自己工作区右栏与 AI 对话「请帮我生成一个 skill」，AI 生成的 skill 产物落盘到对应的工作目录沙箱，**无需专门入口**。
- **思路来源是人**（复盘/讨论/共识），不是 AI 从行为痕迹自动归纳。
- 「生成 skill 的 skill」不写进设计（meta-skill 不明确为系统内置）。
- 测试迭代 = 草稿 skill 在作者环境正常试用，**无特殊 UI**。

### 5.2 降级的两种方式（基本不用）

- **AI 反向生成**（分析记录一键沉淀）：降级——不可靠（AI 脑补伪经验）。
- **模板配置**：降级——呆板不适用。

## 6. 与 design-v2 §11 的差异修正

| design-v2 §11 原设计 | 本设计修订 |
|---|---|
| §11.2 三级空间（全局/部门/个人） | 补「授权组」（跨部门定向授权） |
| §11.4「AI 反向生成」为第一制作方式 | 降级；主路径 = 自然语言编写 + 测试迭代 |
| §11.5「启用 = 授权 + 加入可用清单」 | 拆为「授权（RBAC）+ 收藏（个人清单）」，「启用」弃用 |
| §8.3 站内信三类（系统/AI/文件） | 系统类补「🧩 资产」标签，承载生命周期通知 |
| §11.6 物理落地 | 补迭代文件处理（先删旧+复制新）、审核中停在 pending |

## 7. 待决策点

- **批量授权**：管理员可把资产一键授权到整个部门（§11.5 已有），与「授权组」并存，保留。
- **发布通知范围**：已定「不广播」，若后续需要「部门新资产」轻量提示，再议。
- **业务分类清单**：上线预置一份（对应全流程环节），具体词条由业务管理员维护。
- **知识库建库粒度**：RAGFlow 按「案件一个库」还是「主题一个库」（法条库/办案规范库/历史案例库）？（沿用 design-v2 §18 待决策点第 9 条）
