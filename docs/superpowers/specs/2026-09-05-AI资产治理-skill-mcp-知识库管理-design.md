# AI 资产治理设计：Skill / MCP / 知识库的管理与运营

- **日期**：2026-09-05
- **状态**：待审阅
- **主题**：把 Skill / MCP / RAG 知识库统一为「AI 资产」，设计其管理机制、角色分工、制作方式与完整生命周期（上线 / 启用 / 反馈 / 说明）
- **关联**：`2026-09-05-公安全流程工作平台-中栏多形态内容区与交付层-design.md`（§5/§6）、`2026-09-05-竞品差距分析-workbuddy与千问办公-design.md`（差距 3 业务技能资产化）、`2026-08-17-多用户多租户改造-design.md`（RBAC §4）

---

## 1. 核心抽象：三类资产，一套治理

先破除「Skill / MCP / 知识库各管各」的散乱，把三者统一抽象为 **AI 资产（Asset）**，用同一套治理框架管理：

| 资产类型 | 本质 | 落地载体 |
|---|---|---|
| Skill | 方法 / 流程（怎么分析） | opencode 原生 skill |
| MCP | 工具 / 接口（能查什么、调什么） | opencode MCP + 自研 connector |
| RAG 知识库 | 资料 / 事实（某规定是什么） | RAGFlow |

**为什么必须统一**：三者在运行时是「一条链」（Skill 编排 → 调 MCP 拿数据 → 查知识库拿资料，见工作平台 spec §6），治理上就必须一套元数据、一套权限、一套生命周期，否则链条断在哪一头都查不清。

### 1.1 统一资产元数据模型

每个资产（无论 Skill/MCP/知识库条目）都带以下字段：

| 字段组 | 字段 |
|---|---|
| 基础 | 名称、ID、类型、一句话描述、图标、标签 |
| 归属 | 所有者、所属部门、可见范围（全局 / 部门 / 个人） |
| 版本 | 版本号、变更说明（git 留痕，符合「最小侵入」） |
| 状态 | 草稿 / 审核中 / 已发布 / 已下线 / 已归档 |
| 运营 | 启用数、使用次数、评分、反馈列表 |

---

## 2. 分层与权限（对接现有多租户 RBAC）

### 2.1 三级资产空间

| 层级 | 可见范围 | 维护者 |
|---|---|---|
| **全局资产** | 全单位可用 | 系统管理员 + 业务管理员 |
| **部门资产** | 本科室可见可用 | 部门业务管理员 |
| **个人资产** | 仅本人可见 | 民警自己（私藏草稿） |

### 2.2 权限（复用 RBAC `role_resource`）

每个资产有四类权限动作，与现有多租户 RBAC 的角色资源表对齐：

- **读**：看到、使用该资产
- **写**：编辑内容（作者）
- **审**：审核内容、批准上线（业务管理员）
- **管**：上下架、删除、批量授权（系统管理员）

> 不新造权限体系，直接挂到已有的 `role / role_resource` 上，资产即一种资源类型。

## 3. 角色与分工：谁来管理、谁制作

| 角色 | 谁担任 | 职责 |
|---|---|---|
| **系统管理员** | 科信 / IT | 平台运维、账号、全局资产上下架、用量/审计 |
| **业务管理员** | 法制 / 业务骨干 / 老民警专家 | **审核 skill 内容质量与业务正确性**、审知识库内容、批准上线 |
| **资产作者** | 业务骨干 + AI 辅助 | 制作 skill、维护知识库、响应反馈迭代 |
| **使用者** | 全体民警 | 启用 / 使用 skill、评分、反馈 |

**关键原则**：skill 是「业务经验的封装」，**审核权必须在业务专家手里，不能只走 IT**。IT 管技术合规（能跑、不出错），业务专家管内容正确（套路对不对、结论可不可信）——两者分离，缺一不可。

---

## 4. Skill 制作：低门槛 + 业务专家主导 + AI 反向生成

这是整套体系的命门——**老民警不会编程，所以制作门槛必须低**。设计三种递进的制作方式：

### 4.1 三种制作方式

| 方式 | 做法 | 适合谁 | 门槛 |
|---|---|---|---|
| **① AI 反向生成（最省事）** | 民警做完一次完整分析后，把「分析记录」（工作平台 spec §5）一键「沉淀为 skill」——AI 从「这次怎么分析的」自动生成 skill 草稿 | 所有民警 | 零 |
| **② 自然语言编写** | 民警用大白话描述「我遇到这类案件是怎么分析的」，AI 转成结构化 skill（步骤 + 工具调用 + 触发条件） | 业务骨干 | 低 |
| **③ 模板配置** | 提供 skill 模板，业务专家填关键字段（适用场景 / 输入 / 步骤 / 输出） | 进阶作者 | 中 |

### 4.2 制作来源分工

- **主力**：业务骨干 / 老民警（有经验、懂套路）——他们是内容的源头。
- **加速器**：AI 从「分析记录」反向生成，把个人经验自动沉淀成 skill 草稿。
- **兜底**：科信 / IT 处理技术型 skill（格式处理、数据清洗等），不管业务套路。

> **核心闭环**：`分析记录（定稿）→ 一键沉淀为 skill → 发布 → 供他人复用`。这是「个人提效」迈向「组织增智」的关键动作——老民警的一次分析，变成全单位可复用的技能。

## 5. Skill 生命周期：上线 → 启用 → 反馈 → 说明

### 5.1 状态机

```
草稿 → 提交审核 → 审核中 → 已发布（上线） → 迭代中 → 已下线 → 已归档
                 ↑ 驳回（退回草稿）          ↑ 修改后重新提交
```

### 5.2 上线流程

1. **提交**：作者把草稿提交审核。
2. **业务审核**：业务管理员审核业务正确性 + 合规性（套路对不对、结论是否可能误导）。
3. **技术发布**：系统管理员做技术检查（能正常跑、无安全问题）后发布上线。
4. **上架**：进入「资产中心 / 技能市场」，全单位（或授权范围）可见。

### 5.3 启用 / 安装

- **展示形态**：一个「资产中心」（对标千问的「技能与专家套件市场」、WorkBuddy 的技能分发）。
- **启用方式**：民警浏览资产中心 → 点「启用」→ 资产加入自己的可用列表。
- **批量授权**：管理员可把某个资产一键启用到整个部门（如「话单关系分析」全员启用）。
- **启用的本质**：不是复制代码，而是「**授权 + 加入我的可用清单**」。资产是共享的，启用 = 授权可见可用（复用多租户 RBAC，而非拷贝）。

### 5.4 反馈

- **使用后反馈**：评分（1–5 星）+ 文字反馈 + 问题标记（不准 / 过时 / 报错）。
- **回流**：反馈汇总给作者 + 业务管理员，驱动迭代。
- **运营数据**：使用次数、成功率、评分进入资产运营数据，决定「哪些 skill 值得留、哪些该下线」。

### 5.5 说明（介绍页）

每个资产有一个「介绍页」，用**业务语言**写（不是技术文档，民警要看得懂）：

| 板块 | 内容 |
|---|---|
| 是什么 | 一句话定位 + 解决什么问题 |
| 适用场景 | 什么案件 / 什么环节能用 |
| 怎么用 | 操作步骤、输入什么、产出什么 |
| 示例 | 一个完整的使用案例（含输入输出样例） |
| 注意事项 | AI 可能不准的地方、需人工复核的点、局限 |
| 版本记录 | 版本号、更新说明、更新人 |

## 6. 对标竞品与差异化

| 维度 | WorkBuddy | 千问办公 | openhive 建议 |
|---|---|---|---|
| 技能制作 | 专业配置 | 预制市场 | **业务专家 + AI 反向生成（分析记录→skill）** |
| 分发 | 企业内分发 | 技能市场 | 三级资产空间 + 部门批量启用 |
| 审核 | 企业治理 | 平台审核 | **业务管理员审内容、IT 审技术，分离** |
| 特色 | 数字员工 | 专家套件 | **公安业务经验资产化（护城河，竞品无）** |

## 7. 待决策点

1. **资产中心形态**：是独立的「技能市场」页面，还是嵌入左栏资源面板（opencode 现有资源面板形态）？倾向后者（复用现有面板，最小侵入）。
2. **审核流程的强制程度**：个人私藏 skill 是否也需要审核？建议：个人使用不审核、进入部门/全局共享才审核。
3. **知识库的管理粒度**：RAGFlow 知识库是「按案件一个库」还是「按主题一个库」（法条库 / 办案规范库 / 历史案例库）？影响检索质量与权限切分。
4. **反馈的闭环深度**：反馈只是给作者看，还是要引入「迭代评审」（业务管理员定期复盘低分 skill）？
5. **首批要资产化的业务 skill**：与工作平台 spec §12 待决策点 7 联动——首批「公安研判技能包」具体含哪几个。
