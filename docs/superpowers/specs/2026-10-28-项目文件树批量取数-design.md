# 项目文件树批量取数 · 设计

- **日期**：2026-10-28
- **状态**：待评审
- **关联**：`2026-09-11-项目管理-design.md`（左栏文件 tab）；本次是**取数方式**的替换，不改任何界面形态
- **前置**：同日的 `fix(app): 文件树逐目录并发取数`（3f816fa693）——那条把串行改并发，是**止血**；本文是**根治**

## 0. 一句话

把「前端一个目录问一次、问一百次」改成「服务端在一次请求里走完整棵树、一次交回」，并且交回来的清单与现在**逐字、逐序相同**。

## 1. 为什么（全部实测，真栈 020602 / 项目 1219278f）

| 组合 | 中位耗时 | 差值含义 |
|---|---|---|
| 无身份请求 | **0ms** | 框架本身零成本 |
| 有身份 · 无项目头 | **25ms** | 身份层固定成本 |
| 有身份 · 有效项目头 | **50ms** | ＋归档状态查远端 PG 25ms |
| 有身份 · 不存在的项目 | 26ms | 查不到项目行就提前返回 |

- 文件树清单 264 条，**约 100 趟请求**：串行 4865ms，并发 8 之后 796ms（今日已落）。
- 结论：**每个请求 50ms 固定底座 × 请求次数**。真正的目录读取（`fs.list`）不到 1ms，其余全耗在两次远端往返上。
- 并发已经到顶了：浏览器同源连接上限是 6，再把并发调高只会让它自己排队。

⇒ 唯一还能数量级下降的维度是**请求次数**。

## 2. 端点契约

```
GET /openhive/project/tree
头：x-openhive-project: <projectId>      ← 与 /file 同一条契约，中间件已把目录锚好
```

响应 `200`：

```json
{
  "paths": ["001测试\\", "superpowers\\.agents\\plugins\\marketplace.json", "opencode.json"],
  "truncated": false
}
```

| 字段 | 含义 |
|---|---|
| `paths` | 与今天前端 `walk` 产出的清单**逐字、逐序相同**（见 §3） |
| `truncated` | 是否因为上限截断 |

> **没有 `total` 字段**（2026-10-28 实现前修正）：截断后会停止遍历，那时给出的「总数」只能是
> 「已收集的条数」＝ `paths.length`，等于把同一个数报两遍；要报**项目真实总数**就得扫完整个项目，
> 那样上限省下的成本又还回去了。宁可不给这个数，也不给一个含义含混的数。

**为什么不复用 `/file`**：那是上游端点，改它等于给自己埋冲突点（本项目第一号约束）。新端点是 fork 自有文件。

**为什么用头而不是查询参数**：`projectLocationLayer` 已经按头把请求目录锚到 `{沙箱根}/{userId}/{projectId}`，服务端拿到的 `InstanceState.context.directory` 就是项目目录，客户端再传一次目录只会多一条会漂的输入。

## 3. 顺序规则（本设计的核心约束）

今天前端 `walk` 的产出口径是：**文件就地收下，目录钻进去、回来再按原位置补，空目录补自己**。新端点必须**一字不差**地复刻，否则树会当场乱序——文件跑到别的目录底下、空目录挤到最前面。

具体四条：

1. 每一层按 `FileSystem.list` 的返回顺序处理（目录在前，同类型按名字排）。
2. 文件 ⇒ 直接进清单。
3. 目录 ⇒ 递归；递归回来后，若**这一支下面一个文件都没有**，把这一支的路径补进清单（空目录因此出场）。
4. 跳过：`ignored` 为真的项；**整条路径第一段**是 `.git` 或 `.opencode` 的项（不分大小写；只看第一段——`资料\.git\` 是项目内容，照常）。

> 第 4 条今天住在**前端**（`openhive-files.ts` 的 `isHiddenRoot`），因为前端走 `/file`、只能自己过滤。新端点由服务端遍历 ⇒ **判据搬到服务端**，随前端 `walk` 一起删（见 §5）。只留一份，不做「两边都挡」的纵深——`#002-06` 的取向是同一判断只写一处；两处漂了的表现是「看得见却动不了」或「动得了却看不见」。
> ⚠️ 服务端这一份要与 `file.ts` 的 `inGit` **逐字同形**（那是拦改动的那一侧，本端点是拦显示的这一侧；两处边界不同形就会出现「树里看不见、直接构造请求却动得了」）。
> ⚠️ `.opencode` 在服务端**没有任何守卫**（`file.ts` 只拦 `.git`）。本端点是它今天唯一的过滤点，别把这条写成「防住了」——它只是不画、不遍历。

## 4. 上限与截断

- 上限 **50000** 条路径。达到上限即停止遍历。
- 达到上限时 `truncated: true`，`paths` 交出已收集的部分（不额外报「总共有多少」——理由见 §2 那条注）。
- **前端必须把这件事说出来**：文件树顶部显示一条「文件太多，只列了前 5 万个」；不得静默截断。
  - 理由与既有纪律一致：**半个清单冒充完整清单是谎**（`openhive-files.ts` 文件头，`project-files.ts` 的三态裁定）。
  - 这是本项目第一次**允许**交出不完整的清单，所以它必须自带一句话说明；没有那句话的实现一律视为错误。

**为什么不做流式**（用户 2026-10-28 裁定）：流式的复杂度主要在中途失败怎么办、边收边建树的一致性、以及怎么测；而 50000 条路径约 4MB、gzip 后约 1MB，一次返回在本项目的规模下完全够用。真撞上更大的项目，先看清是什么项目再谈。

## 5. 前端改动

`packages/app/src/project/openhive-files.ts`：

- `listProjectFiles` 改为调 `GET /openhive/project/tree`，带 `x-openhive-project` 头。
- **删掉** `walk`、今日刚加的并发闸门、以及 `isHiddenRoot`（它随 `walk` 一起失去调用者）——留着就是两份实现（`#002-06`：同一个判断两处各写一份，改一处漏一处不报错也不变红）。隐藏根判据此后只在服务端有一份（§3）。
- 返回值类型**不变**（`readonly string[] | undefined`），所以 UI 调用方零改动。
- 新增一个可选出口承载 `truncated`：**不改现有签名**，另加 `listProjectTree` 返回 `{ paths, truncated } | undefined`，由 `listProjectFiles` 包一层。这样既有调用方（`project-data.ts:242`）一行不用动，需要提示的界面走新函数。

`packages/app/src/workspace/workspace-entry.tsx`：取数改调 `listProjectTree`，把 `truncated` 传进文件树。

`packages/app/src/components/file-tree*.tsx`：新增一条截断提示（一行小字，不做弹窗）。

**取不到时**（新端点 404 / 5xx / 体不成形）⇒ 与今天一样交 `undefined`，界面显示「取不到，点击重试」。不降级回老的逐目录方式——**前后端同仓同发布**，留一条降级路径只会让「哪条在跑」变得说不清；真要回滚，回滚整个提交。

## 6. 测试策略

| 层 | 用例 |
|---|---|
| 服务端（新建 `project-tree.test.ts`） | **把今天 `openhive-files.test.ts` 的 20 多条顺序用例逐条迁移过来**：文件就地/目录后序/空目录补自己/只有空子目录/全空目录/`ignored` 跳过/`.git` 与 `.opencode` 隐藏（含「只看第一段」的对照组）/大小写/`.gitx` 不误伤 |
| 服务端 | 截断：造 50001 条 ⇒ `truncated: true`、`paths.length === 50000` |
| 服务端 | 读目录失败 ⇒ 500（不交半棵树）；`/file` 端点行为一个字不变 |
| 前端 | 解析：正常数组、`truncated` 传参、体不成形/非 200 ⇒ `undefined` |
| 前端 | `listProjectFiles` 的签名与返回值语义不变（既有调用方零改动） |
| 真栈验收 | 大项目（测试1027）上，**新旧两版清单逐字对比相同**；请求数从约 100 降到 1；端到端时间记录 |

**验收判据（必须先跑出来再提交）**：同一项目、同一时刻，新端点产出的 `paths` 与今日并发版 `listProjectFiles` 的返回值 `JSON.stringify` **完全相等**。

## 7. 风险

| 风险 | 处置 |
|---|---|
| 顺序漂移（最危险，树会画错） | §6 的逐字对比判据；顺序用例全部迁移到服务端 |
| 删掉前端 `walk` 后发现还有调用者 | 动手前 `grep` 全部调用点（今天只有 `project-data.ts:242` 与 `workspace-entry.tsx:615/909`） |
| 新端点忘了 `.git`/`.opencode`，把 `.opencode` 的 node_modules 全下发给前端 | 服务端过滤 + 迁移过来的隐藏根用例守着 |
| 大项目响应体过大 | 50000 上限 + `truncated` 提示 |
| 服务端单次遍历太慢（极端目录数） | 记录耗时；超过 3 秒再谈流式，不提前做 |

## 8. 不做的事

- 不做流式返回（用户裁定，见 §4）。
- 不改 `/file` 端点（上游）。
- 不动能力面板 `217ms` 与身份层 `25ms` 那两条——它们是独立的两笔账，本文只管文件树。
- 不做前端缓存/预取（那个是「切回已看过项目」的体验优化，与本设计正交）。
- 不做按目录懒加载（那会把请求数又拉回去）。

## 9. 预期收益（按 §1 实测推算）

| | 今天（并发 8） | 本设计 |
|---|---|---|
| 请求次数 | ≈100 | **1** |
| 文件树取数耗时 | 796ms | **≈100–300ms**（50ms 底座 ＋ 服务端本地遍历） |
| 对远端 PG 的压力 | 100 次归档查询 | 1 次 |

> 数字是推算，不是实测；落地后按 §6 的真栈验收补实测值。
