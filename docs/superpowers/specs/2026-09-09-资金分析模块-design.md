# 资金分析模块设计

- **日期**：2026-09-09
- **状态**：待审阅
- **主题**：将既有资金分析模块（传统重型工具）重构为 openhive 的「AI 优先」资金分析工作区
- **关联**：`2026-09-06-openhive-design-v2.md`（总体设计，本设计是其「情报研判 → 资金分析」环节的落地）

---

## 0. 一句话结论

资金分析从「几十个手工按钮的传统工具」重构为 **openhive 项目内的一个三栏分析工作区**：左栏资金项目树（数据轴），中栏多形态视图（明细/聚合统计/关注清单/桑基/图谱/分析记录/文件），右栏 AI 驱动清洗、分析、关联、生成产物。**数据与工作空间彻底解耦，产物落到当前工作的 openhive 项目。**

> **设计定位（薄界面 + 厚 skill）**：界面只做「操作 + 浏览 + 确定性查询展示」；分析能力由 **skill（AI 资产）** 扩展，汇集领域专家经验。**确定性查询/统计走 MCP（平台基础设施），需要专家经验的研判分析走 skill**——确定性的事不滥用 AI，AI 只用在「离不开专家经验」的地方。呼应 openhive 三层架构：opencode（harness/界面）→ skill（方法/能力）→ 产物。

|---|---|

## 3. 整体架构与数据流

### 3.1 三栏界面

```
┌─────────┬──────────────────────────────┬─────────────────┐
│ 左栏     │          中栏                 │    右栏          │
│ 资金项目 │  多形态视图（按数据类型切换）：│   AI 分析助手    │
│ 树       │   · 明细视图                 │                 │
│ ├资金A   │   · 桑基图                    │  清洗/分析/关联/  │
│ │ ├0205  │   · 图谱视图                 │  生成产物         │
│ │ └0206  │   · 分析记录视图             │                 │
│ ├资金B   │   · 文件视图                 │                 │
│ └...     │                              │                 │
└─────────┴──────────────────────────────┴─────────────────┘
```

> 图中栏视图为示意，完整清单见 §5（明细 / 聚合统计 / 关注清单 / 桑基 / 图谱 / 分析记录 / 文件，共 7 个）。

**左栏交互（资金项目，四 tab）**：

左栏顶部「最近 / 全部 / 已归档 / 当前」四个 tab：

| tab | 内容 | 过滤 |
|---|---|---|
| 最近 | 我最近打开过的项目，最近 10 个，按 `last_accessed_at` 降序，每项显示项目名 + 角色标签（owner/member）+ 最后访问时间 | 有权 + 活跃 |
| 全部 | 我参与的活跃项目**列表**（平铺，每项目一行），顶部搜索框（按项目名过滤）+「＋新建项目」按钮 | 有权 + 活跃 |
| 已归档 | 我拥有的已归档项目，每项显示项目名 + 归档时间 +「恢复」按钮，点恢复 = `archived` 改回 0 | 有权 + 已归档（owner） |
| 当前 | **当前选中项目的内部树（项目名 → 节点 → 账户）**；未选中时空白，空态引导「尚未选择项目，去『最近』或『全部』选一个」 | —（已选中即有权） |

**交互规则**：
- **点项目 = 选中 + 自动切「当前」**：在「最近 / 全部 / 已归档」点某个项目，自动切到「当前」tab 展示其内部树。
- **默认进入**：已有当前项目时停在「当前」tab，否则停在「最近」tab。
- **建项目入口**：「全部」tab 顶部「＋ 新建资金项目」按钮；列表为空时显示空态引导。

**权限过滤是铁律**：项目列表（最近/全部/已归档）显示的项目，都必须是「当前用户在 `fund_project_member` 有 `status=0` 有效记录」的项目（数据轴权限）——被撤销（`status=1`）或从未被邀请的项目，任何列表都不出现。「已归档」tab 仅 owner 可见（归档后 member 失权），管理员在治理后台兜底看全部归档项目。

**位置指示（用户始终知道「我在哪」）**：顶栏显示「openhive 项目 · session」；左栏选中态高亮当前节点/账户；中栏顶部面包屑显示「资金项目 / 节点路径 / 当前账户」完整路径。

### 3.2 两条独立的轴（关键架构原则）

```
【数据轴】资金项目 → 节点 → 账户 + 交易明细
   存储：业务数据 PG + RLS，按「资金项目 ↔ 用户」授权

【工作空间轴】openhive 项目 → 产物（报告/图谱/分析记录/文件）
   存储：沙箱目录 + git，产物落这里

桥梁 = 「我此刻在哪个 openhive 项目工作」的运行时上下文
   （产物落地时记 project_id，不反过来把数据绑定到空间，不建关联表）
```

### 3.3 数据流（读 MCP / 写 API）

```
【写入】上传文件 → 进沙箱 → AI 对话清洗 → 中栏展示清洗对比
        → 人点「确认入库」→ 前端直调后端 API → 提交导入任务到 RabbitMQ 队列
        → worker 消费 → 批量 COPY 写 PG → 完成通知回推前端

【读取】AI 说「查 0206 近3月进账」→ 调「资金数据查询 MCP」
        → MCP 带 X-User-ID → 后端 RLS 过滤 → 返回该用户有权看的数据
```

## 4. 数据模型

### 4.1 存储分工

| 数据线 | 存哪 | 说明 |
|---|---|---|
| 资金数据（账户 + 流水） | 业务数据 PG | 分区 + RLS + 批量导入 |
| 涉案关系/资金链路（图） | 业务数据 PG（entity/relation 表） | 只存提取后的关系，递归 CTE 查询 |
| 账户→人 身份映射 | 业务数据 PG（graph_entity/account_identity 表） | 关系表 + 外键，一跳 join |
| 分析记录 + 产物文件 | 沙箱（openhive 项目目录）+ git | Markdown + frontmatter |

### 4.2 资金数据表（业务 PG）

```sql
fund_project (        -- 资金项目（数据轴一级组织单元）
  id         BIGSERIAL PRIMARY KEY,
  name       TEXT NOT NULL,
  archived   INTEGER DEFAULT 0,       -- 归档标记（0活跃/1归档）
  last_accessed_at TIMESTAMP          -- 最后访问时间（归档触发依据）
)

fund_project_member ( -- 数据权限（独立于 openhive 项目权限，微信群模型）
  fund_project_id BIGINT REFERENCES fund_project(id),
  user_id         TEXT,               -- 复用 auth.user.id
  role            TEXT,               -- owner / member
  inviter         TEXT,               -- 介绍人（谁拉进来的；owner 默认=自己）
  invite_time     TIMESTAMP,          -- 介绍时间（owner 默认=建项目时间）
  status          INTEGER DEFAULT 0,  -- 0=有效，1=已撤销
  UNIQUE(fund_project_id, user_id)
)

fund_node (          -- 节点（多级自关联，≤10 级）
  id              BIGSERIAL PRIMARY KEY,
  fund_project_id BIGINT NOT NULL REFERENCES fund_project(id),
  name            TEXT NOT NULL,
  parent_id       BIGINT REFERENCES fund_node(id),
  sort_order      INTEGER,           -- 同级节点排序（大间隔序号）
)

fund_account (       -- 账户（开户信息）
  id             BIGSERIAL PRIMARY KEY,
  fund_node_id   BIGINT NOT NULL REFERENCES fund_node(id),
  account_no     TEXT,               -- 账户编号
  account_number TEXT,               -- 账户号码
  account_type   TEXT,               -- 账户种类
  sort_order     INTEGER,            -- 同节点下账户排序（大间隔序号）
  holder_name    TEXT,               -- 开户人员
  id_card        TEXT,               -- 身份证号（明文，研判对象）
  reg_phone      TEXT,               -- 注册手机
  wechat_id      TEXT,               -- 微信号
  wechat_account TEXT,               -- 微信账号
  login_phone    TEXT,               -- 登录手机
  status         TEXT,               -- 账户状态
  track_status   TEXT,               -- 关注/调取状态（空=未关注；待调取/已调取待导入/已导入）
  earliest_date  DATE,               -- 交易最早日期
  earliest_time  TIME                -- 交易最早时间
)

fund_transaction (   -- 交易明细（大表，按月分区）
  id                BIGSERIAL PRIMARY KEY,
  account_id        BIGINT NOT NULL REFERENCES fund_account(id),
  trade_time        TIMESTAMP,
  amount            NUMERIC(18,2),
  counterparty_acct TEXT,            -- 对方账户
  debit_credit      CHAR(1),          -- 借贷标志（D进账/C出账）
  balance           NUMERIC(18,2),
  summary           TEXT,
  trade_channel     TEXT
  -- 注意：对方户名不存这里，通过 join 映射表得到（见 4.3）
) PARTITION BY RANGE (trade_time);
```

### 4.2.1 资金项目权限（微信群模型）

谁建项目谁是 **owner**（群主），建项目时同步写一条 `inviter=自己, invite_time=建项目时间, status=0`。权限规则：

| 规则 | 内容 |
|---|---|
| 拉人 | owner 和 member 都能邀请他人，被邀者 role=member，记 inviter=邀请人 |
| 撤销 | 只有 owner 能撤销某人（status=1）；owner 永远 status=0 |
| 级联撤销 | 不做（B 被撤不影响 B 拉进来的 C） |
| 重新邀请 | 可，status 改回 0，并更新 inviter（记录最后拉他的人） |
| 群主转让 | 不做（owner 固定） |
| 退群 | member 可自己删自己；owner 不能退群 |

**这是数据轴的自主拉人授权，不需要管理员逐条配**（管理员只在兜底时介入）。

**权限管理入口**：在资金项目内就地操作，类比微信群的「群成员管理」——入口是「当前」tab 树顶部的项目名（根节点）右键 →「成员管理」面板，owner/member 在这里拉人、撤销、退群；**不通过治理后台逐条配**。治理后台只保留兜底场景（如 owner 调离时的归档/权限回收）。

### 4.2.2 资金项目归档（按项目，冷热分离）

- **触发**：`last_accessed_at` 超 1 年未访问 → 进入待归档列表，owner 或管理员确认；owner 也可**主动归档**（不达 1 年）。
- **动作**：`archived=1` + 从活跃列表移到「已归档」tab + **数据保留不删**（流水表按月分区仍留 PG）。
- **权限**：归档后 member 失权、owner 保留查看+恢复权。
- **恢复**：`archived` 改回 0，member 按 status=0 记录恢复。
- **兜底**：owner 调离（僵尸账户）时，管理员兜底归档。
- **粒度**：按项目，不做节点级。

### 4.2.3 资金项目树 + 拖拽

**树模型**：邻接表（`parent_id` 自关联，≤10 级）。节点量小（几十~几百），递归 CTE 查询足够，不需要路径枚举/闭包表。

**节点与账户允许混合**：一个节点下既能挂账户（`fund_account.fund_node_id`）又能建子节点（`fund_node.parent_id`），两条独立引用天然支持。

**拖拽规则**：

| 规则 | 内容 |
|---|---|
| 节点拖拽 | 改 `parent_id` + `sort_order` |
| 账户拖拽 | 改 `fund_node_id` + `sort_order` |
| 跨项目拖拽 | **不允许**（`fund_project_id` 不可改） |
| 排序 | 节点与账户**分开排序**（各自 sort_order） |
| 环检测 | 拖节点 X 到父节点 P 下，须查 P 是否为 X 的子孙（从 P 沿 parent_id 向上查祖先，遇 X 即拒） |

**sort_order 用大间隔序号**（1000/2000/3000…），插入取中间值（如 1500），避免每次拖拽重排整层；间隔耗尽才重排。

**右键操作**：节点/叶子支持右键「加载明细 / 新增子节点 / 新增账户 / 重命名 / 删除」。

| 操作 | 权限 |
|---|---|
| 加载明细 | owner + member（读数据，RLS 过滤） |
| 新增子节点 / 新增账户 | owner + member |
| 重命名 | owner + member |
| 删除 | **仅 owner** |

**删除保护**：禁止删除非空节点（须先清空其子节点/账户）、禁止删除有交易流水的账户（须先清空流水）。资金流水是涉案数据，级联删除是数据灾难，用「禁止删非空」兜底。

### 4.2.4 关注清单（框定账户 + 调取状态流转）

「框定重要账户」不只是看看，而是**管理调取进度、防止账户多了搞不清哪些调了哪些没调**。落地为**关注清单**（中栏独立视图，见 §5）：民警把重要账户「加入关注」，跟踪其调证进度。

**加入关注的入口（A 为主 + B/C 为辅）**：
- **主入口**：聚合统计视图——每行（对方账户）加「关注」勾选框，民警浏览统计、结合案情框定时就地勾选。
- **辅入口**：明细视图「对方账户」列右键 →「加入关注」；「当前」tab 树账户右键 →「加入关注」。

**状态机**（`fund_account.track_status`，空 = 未关注）：

| 状态 | 含义 | 流转触发 | 自动/人工 |
|---|---|---|---|
| 待调取 | 已框定，需调取流水 + 开户信息 | 民警「加入关注」 | 人工（研判决定） |
| 已调取待导入 | 数据已到手，未入库 | 民警「标记已调取」 | 人工（线下调证系统看不到） |
| 已导入 | 数据已入库，可分析 | 「确认入库」成功 | 系统自动 |

**实现要点**：
- **「已导入」自动标记**：RabbitMQ worker 批量 COPY 写 PG 成功后，在「完成通知回推前端」的同时，根据入库数据涉及的账户，把它们的 `track_status` 从「已调取待导入」自动更新为「已导入」（入库数据自带账户标识，映射已知）。
- **「标记已调取」人工按钮**：关注清单里每个「待调取」账户有「标记已调取」按钮（或右键），民警线下调完证回来点一下。
- **可选增强**：上传数据文件时，若系统能从文件识别对应账户，可自动把这些账户从「待调取」推进到「已调取待导入」（上传 = 数据到手）；但「识别文件属于哪些账户」有难度（一个文件可能含多个账户），主路径仍是人工标记。

**原则**：能可靠感知的自动（已导入）、感知不到的人工（待调取、已调取），保证状态永远可信。

### 4.3 账号→人 身份映射（关系表，不用图）

```sql
-- person = 全局六要素实体库 entity 中 six_type='人' 的实体 + person 扩展表（§4.4/§12.1）
-- 「人」的关键标签（name/tags）在 entity，专属字段（身份证/职业/前科/家庭/手机）在 person

account_identity (    -- 对方账户（六要素「网」虚拟身份）→ 人 的映射
  id                BIGSERIAL PRIMARY KEY,
  counterparty_acct TEXT UNIQUE,   -- 对方账户（= fund_transaction.counterparty_acct，银行卡号/支付宝/财付通号）
  person_id         BIGINT REFERENCES entity(id)  -- 持有人（指向全局实体库中 six_type='人' 的实体）
)
```

**明细回显链路**：`fund_transaction.counterparty_acct（对方账户）→ join account_identity.counterparty_acct → join entity（six_type='人'）→ 回显姓名/关键标签`；完整属性（身份证/职业/前科）再 join `person`。原始流水表只存账户号码，不存人名。

**「人」的信息分层（研判视角，非档案视角）**：民警对「人」最需要的是**标签**（前科/职业特征/涉案标记），不是完整档案，所以分三层展示：

| 层 | 内容 | 展示位置 |
|---|---|---|
| 关键标签（常驻） | 姓名 · 职业 · 前科标记 · 涉案标记 · 自定义标签 | 明细「对方账户」后、图谱节点上 |
| 身份档案（弹窗） | 身份证、家庭成员、持有手机、住址等完整字段 | 点人名/标签呼出「人员详情」弹窗 |
| 关联关系（弹窗/图谱） | 关联账号、涉案关系、关联案件 | 弹窗内 + 图谱钻取 |

**标签与溯源**：标签存 `entity.tags`（数组），每个标签带 `source`（AI 提取 / 民警标注 / 业务系统同步）；前科拆两半——`person.criminal_record` 摘要（常驻「前科·诈骗」）+ 完整前科记录（弹窗看判决时间/案由）。

> **澄清（开户名 vs 持有人）**：`fund_account.holder_name` 是开户时登记的姓名（原始数据自带，可能是经办人/名义人）；`account_identity.person_id` 是研判查明的**实际持有人**。两者可能不同（开户名 ≠ 实际持有人），回显时优先展示研判查明的 `person`，`holder_name` 作为原始字段保留对照。

**身份映射的入口（就地标记；实体库 AI 自动维护，无人工入口）**：

**就地「标记持有人」**（不跳转，守护心流）：
- 触发：明细表「对方账户」列右键 →「标记持有人」；或右栏 AI 说「把 138XXXX 标记为张三」——面板 + AI 对话两条路径，写同一张 `account_identity`。
- 交互：轻量面板（姓名 + 选填 身份证/职业/备注），非全屏跳转。
- 提交三步：① 先查重（身份证号强唯一，到全局 `person` 库查同名/同证，命中复用、未命中新建）；② 建/复用 `account_identity`；③ 顺带记一条「判定理由」到分析记录（§4.5 语义分离）。
- **标记 = 人判断，不是 AI 判断**：谁是持有人是民警的专业判断，走「人确认闸门」（B 类），AI 只辅助查重/补全。

**实体库无人工入口（AI 自动维护）**：`person` 是全局共享实体（话单/资金/轨迹共用），但**不向普通用户开放人工建档入口**——实体数据由「持有人研判」等 AI 闭环在工作过程中自动存入、自动查重。**合并去重**由管理员在治理后台兜底（AI 自动查重为主，人工合并是纠错例外），普通用户不直接操作实体库。

### 4.3.1 持有人研判流水线（AI 编排 + 两闸门确认）

日常工作闭环：浏览明细 → 聚合框定 → 调取开户信息 → 识别生活线索 → 查业务系统 → 判定持有人 → 建档关联 → 全局复用。其中「识别线索 → 查证 → 判定 → 建档」封装为右栏一次触发的「持有人研判」，AI 编排整条链，人在两个闸门拍板：

**闸门 1 —— 线索确认**：AI 扫明细备注，自动提取生活线索（车辆加油 / 高速缴费 / 手机充值 / 商户名），列出「待查证线索清单」。民警勾选要查的、划掉误识别的（提取交给 AI，判断留给人）。

**闸门 2 —— 持有人判定（多候选 + 置信度）**：AI 调「业务系统查询 MCP」查证（车辆→车主、手机→实名、缴费→账户、户籍→身份），汇总「开户人 vs 生活线索指向人」比对，给出**多候选 + 置信度 + 各自依据**（如 张三 87%｜张三丰 12%），民警选一个确认。

**建档弹窗（AI 预填，人确认）**：确认后 AI 预填弹窗字段——姓名 / 身份证 / 职业来自业务系统查证结果，判定理由由 AI 自动生成（引用的线索 + 查证结果 + 开户人比对）。民警核对 / 修正 → 确认 → 写 `person` + `account_identity` + 判定理由进分析记录。

### 4.4 涉案关系图（业务 PG，只存提取后）

```sql
entity (              -- 全局六要素实体库主表（§12.1）
  id        BIGSERIAL PRIMARY KEY,
  six_type  TEXT,                  -- 人/事/地/物/组织/网
  name      TEXT,
  tags      TEXT[],                -- 研判标签（前科/涉案标记/自定义），每个带 source 溯源
  ...
)

person (              -- 「人」的扩展属性（six_type='人' 实体的专属字段）
  entity_id       BIGINT UNIQUE REFERENCES entity(id),
  id_card         TEXT,            -- 身份证
  occupation      TEXT,            -- 职业
  criminal_record TEXT,            -- 前科摘要（常驻「前科·诈骗」）
  family          TEXT,            -- 家庭成员
  phone           TEXT,            -- 持有手机
  ...
)

relation (            -- 实体间关系 / 资金链路（多跳）
  id          BIGSERIAL PRIMARY KEY,
  from_entity BIGINT REFERENCES entity(id),
  to_entity   BIGINT REFERENCES entity(id),
  rel_type    TEXT,                -- 资金往来/同户/关联…
  source      TEXT                 -- 人工标注 or AI 抽取
)
```

### 4.5 数据/语义分离原则

| 类型 | 落点 |
|---|---|
| 交易事实（金额/借贷/对方账号…） | `fund_transaction`（干净，只存事实，不做频繁 UPDATE） |
| 身份映射（账户→人） | `account_identity` + `entity`/`person`（关系表，全局复用） |
| 涉案关系/资金链路 | `relation`（图，提取后） |
| 分析判断（这笔可疑、张三这次是共犯…） | 分析记录（沙箱 Markdown，随案情变） |

**原则**：原始流水表保持干净，语义与判断分离——身份映射、涉案关系、分析判断都不往流水表堆字段。

## 6. 按钮降级映射（AI 优先重构的核心）

| 类 | 处理方式 | 按钮 |
|---|---|---|
| A. 交给 AI 对话 | 右栏说一句，AI 执行 | 数据清洗/批量清洗、一键分析、资金流数据分析、金额统计、关联关系（初步）、节假日 |
| B. 人确认闸门 | 简化确认 + AI 留痕 | 入库确认、专家关联/角色标注（确认）、发起银行提供（AI 生成调证请求 + 提交留痕） |
| C. 前端视图操作 | 保留为轻控件 | 显示异常、刷新、选定/取消、列显示隐藏、进账/出账底色、搜索 |
| D. 剔除 | 本次不做 | 报送/推送数据到观点分析 |

**「资金分析 skill」是方法封装**：右栏 AI 助手的核心是一个「资金分析 skill」，它编排「调『资金数据查询 MCP』查数据 → LLM 分析/生成 → 写产物到 openhive 项目 + git 留痕」。关联分析、资金链、生成研判报告等都是 skill 内部的能力，不是独立功能模块。

**右栏「资金分析 skill」能力清单**：

```
清洗    「这批数据有重复、格式乱，帮我清洗」
持有人研判「识别生活线索→查业务系统→判定持有人→建档关联」
关联    「找出和张三有资金往来的账户」
资金链  「追一下这笔钱从哪来、到哪去（几跳）」
统计    「汇总各关联方的进出账金额」
标注    「把这些账户标为涉案，理由记进分析记录」
出产物  「生成资金流向图」「生成研判报告」「记一条分析思路」
```

**「发起银行提供」**（需留痕）：右栏让 AI 生成调证请求（理由、账户、时间段），提交时留痕（谁、何时、向哪家银行、要什么数据），轻量工作流。

### 6.1 AI 能力的可发现性（解决「民警不知道问什么」）

AI 优先不意味着消灭按钮——按钮的「可发现性」和「可学性」有价值。按钮降级为**右栏顶部的「指令卡」**，点卡片 = 自动把对应一句话填入输入框发给 AI，而非彻底消失。

**指令卡分两组**：

| 组 | 内容来源 | 形态 |
|---|---|---|
| **上下文指令**（随中栏状态动态） | 选中几个账户 → 「关联分析/资金链追踪/标为涉案/汇总进出账」；上传文件 → 「清洗入库/预览数据」 | 浅金底卡片，随选中实时变化 |
| **常用操作**（固定） | 清洗数据 / 一键分析 / 生成资金流向图 / 生成研判报告 | 白底卡片 |

**三层引导（新手到熟练的渐进）**：

1. **上下文指令 + 常用操作**：点卡片 = 填入一句话，AI 执行并**展示过程**。民警点按钮看到「原来这样问就能让 AI 做这个」，是被动学习。
2. **AI 主动给下一步**：AI 每次执行完，末尾主动给出「可继续」的提示词（如「追一下张三的资金链」「把张三标为涉案」），引导民警顺着往下。
3. **自由输入**：熟练后民警直接打字，AI 理解意图。

**关键原则**：
- 指令卡文字 = 原按钮的「业务语言」重新组织（「资金流数据分析」「专家关联」「金额统计」本就是民警听得懂的业务词），执行方式从「点一下出结果」改为「点一下 → AI 做并展示过程」。
- 输入框占位文字明确提示「说说你想做什么，或点上面的卡片…」，降低空白焦虑。
- 引导逐步收拢：新手阶段指令卡全展开；用久后常用项收成「最近/常用」，引导转向自由输入。
- 此设计呼应竞品分析中「千问办公的推荐提示词」与「Cloudflare 的前置化解焦虑」——AI 产品不能给用户空白画布，要给「可点的话题」。

### 6.2 数据清洗（分层落地 + 能力边界）

**落地形态（三层，非纯 LLM skill）**：清洗 = 资金分析 skill 的「清洗」子能力，编排「后端规则引擎（确定性）+ LLM（语义）」，产物是「清洗对比 + 问题清单」，人点「确认入库」才落 PG。

> **「清洗对比」和「问题清单」指什么**：「清洗对比」= 明细级「清洗前 vs 清洗后」逐行/逐字段对照（能看到 AI 改了每行的什么，如 `¥12,480,600` → `12480600.00`、列头「对方帐号」→「对方账户」）；「问题清单」= AI 标记出、需人拍板的具体问题行（疑似重复对/余额勾稽不符/字段缺失/金额异常），可点击定位到明细行。两者并排展示。

| 层 | 干什么 | 形态 |
|---|---|---|
| skill（编排层） | 理解意图（洗哪批/什么要求）→ 调后端引擎 → 展示清洗对比 → 收集人确认 | skill 子能力 |
| 后端清洗引擎（执行层） | 列头映射规则、编码/分隔符/金额/日期转换、完全重复去重、借贷/通道枚举标准化 | 写侧后端服务 |
| LLM（语义层） | 列头语义识别、生活线索提取、异常判断建议 | LLM 调用 |

**五类清洗工作**：

1. **格式与字段对齐**：列头语义映射（「对方帐号」→ `counterparty_acct`）、编码/分隔符统一、金额格式（千分位/`¥`/`元`）、日期格式（`2026/3/4`、`20260304`、Excel 序列号）、多 sheet/多文件合并、跳表头空行。
2. **去重**：完全重复行 AI 自动去；疑似业务重复（同账户+时间+金额）只标记、人判断（可能是真实两笔）。
3. **数据校验与异常**：必填缺失、类型错误（金额出现文字）、余额勾稽（上笔余额 ± 本笔金额 = 本笔余额）、账号/手机/身份证格式、金额精度（元/分/万元）——AI 标记，人决定。
4. **字段标准化**：借贷方向统一 D/C、交易通道枚举、账户脱敏格式规整、时间戳统一。
5. **语义提取（AI 独有）**：从摘要识别生活线索（加油/高速/充值/商户），打标签，供「持有人研判」闸门 1 用。

**能力边界（核心红线：涉案数据只「转换+标记」，不「删除+语义判断」）**：

| 类别 | 具体 | 谁做 |
|---|---|---|
| 确定性清洗 | 列头映射、格式统一、完全去重、类型转换、枚举标准化 | ✅ AI 自动 |
| 有歧义 | 疑似业务重复、余额勾稽不符、字段缺失、金额异常 | ⚠️ AI 标记 + 人确认 |
| 高风险 | 删除数据行、判断「是否涉案」 | ❌ 只人做 |

## 7. 技术选型（实现时验证）

| 能力 | 方案 |
|---|---|
| 资金数据查询（读） | 自研「资金数据查询 MCP」，带 X-User-ID + RLS |
| 资金数据入库（写） | 后端 API + RabbitMQ 异步队列（worker 消费 → 批量 COPY 写 PG → 完成通知）+ 分区表 |
| 数据清洗 | 写侧「清洗引擎」（确定性规则）+ LLM 语义（列头识别/线索提取），skill 编排，只转换+标记不删数据 |
| 图谱渲染 | AntV G6（前端） |
| 图存储 | PG 两张普通表 + 递归 CTE（不上图数据库） |
| 桑基图/统计图 | ECharts |
| 业务系统查询（车辆/手机/缴费/户籍） | 自研「业务系统查询 MCP」（read-MCP），带 X-User-ID + capability 鉴权，AI 实时查 |
| 聚合统计（对方账户 GROUP BY） | 默认实时 GROUP BY（MCP 跑聚合 SQL，分区 + 索引够快），不做入库预聚合物化表 |

**聚合统计的升级信号**（现在不触发）：实测「对方账户聚合」单次查询 > 1~2 秒、或该统计被高频反复查询时，再上 PG 物化视图（`MATERIALIZED VIEW` + `REFRESH CONCURRENTLY`）。**不做「入库时预聚合物化表」**：物化表是快照，增量入库后必须同步刷新，否则与明细表不一致（研判大忌）；固定维度也覆盖不了临时统计口径（时间切片/借贷方向/本方账户筛选）；且不要手写「入库 upsert 全量聚合表」（并发/幂等/不一致风险最高）。

**图数据库的升级信号**（现在不触发）：需对全量 200 万条/日流水做实时图算法时，再上 Apache AGE 或独立图库。

1. **「发起银行提供」的审批粒度**：是「提交即留痕」还是要「上级审批」？当前按「AI 生成 + 提交留痕」设计，未引入审批流。
