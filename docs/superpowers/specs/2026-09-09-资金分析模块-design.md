# 资金分析模块设计

- **日期**：2026-09-09
- **状态**：待审阅
- **主题**：将既有资金分析模块（传统重型工具）重构为 openhive 的「AI 优先」资金分析工作区
- **关联**：`2026-09-06-openhive-design-v2.md`（总体设计，本设计是其「情报研判 → 资金分析」环节的落地）

---

## 0. 一句话结论

资金分析从「几十个手工按钮的传统工具」重构为 **openhive 项目内的一个三栏分析工作区**：左栏资金项目树（数据轴），中栏多形态视图（明细/桑基/图谱/分析记录/文件），右栏 AI 驱动清洗、分析、关联、生成产物。**数据与工作空间彻底解耦，产物落到当前工作的 openhive 项目。**

---

## 1. 核心决策（已与用户确认）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 交互范式 | **AI 优先重构**：几十个按钮 → 右栏 AI 驱动，中栏只留查看 + 少数人确认 |
| 2 | 数据来源 | **手动上传文件**（无旧系统流转、无外部调证） |
| 3 | 标注落点 | **图谱 + 分析记录都要**（实体/关系入图，人判断理由进分析记录） |
| 4 | 流向图形态 | **两层**：中栏可交互桑基图 + 导出图片进报告 |
| 5 | 模块定位 | 图标栏进入资金分析三栏界面 |
| 6 | 项目概念 | **三层项目解耦**：openhive 项目（工作空间）≠ 资金/话单项目（数据组织），不建关联表 |
| 7 | 产物归属 | 落到「当前工作的 openhive 项目」 |
| 8 | 数据接入 | 上传控件 + AI 清洗 + 确认入库 |
| 9 | 读写分工 | 读走 MCP（供 AI 查），写走 API（供人确认入库） |
| 10 | 图谱粒度 | 只存「提取出的涉案关系」，正常交易留在流水表不入图 |
| 11 | 节点层级 | `fund_node` 多级自关联，实际不超过 10 级 |
| 12 | 账号→人 | **关系表 + 外键**（person/account 表），不用图 |

## 2. 规模修正（相对总体设计）

总体设计 §2 写「100+ 用户」。实际规模为：

| 项 | 实际值 |
|---|---|
| 用户数 | **1600 人** |
| 资金流水入库 | **高峰每日 200 万条**（约 7.3 亿条/年） |

**连带要求**：
- 原始流水表必须**按月分区 + 批量 COPY 导入**（不可逐条 insert）。
- 用户规模从「100+」修正为「1600」，总体设计 §2 的「用户规模」条需同步更新。
- 图谱只存「提取后的涉案关系」（决策 10），故规模小，不上图数据库。

## 3. 整体架构与数据流

### 3.1 三栏界面

```
┌─────────┬──────────────────────────────┬─────────────────┐
│ 左栏     │          中栏                 │    右栏          │
│ 资金项目 │  多形态视图（按数据类型切换）：│   AI 分析助手    │
│ 树       │   · 明细视图                 │                 │
│ ├资金A   │   · 桑基图                    │  清洗/分析/关联/  │
│ │ ├0205  │   · 图谱视图                 │  生成产物         │
│ │ └0206  │   · 分析记录视图             │                 │
│ ├资金B   │   · 文件视图                 │                 │
│ └...     │                              │                 │
└─────────┴──────────────────────────────┴─────────────────┘
```

### 3.2 两条独立的轴（关键架构原则）

```
【数据轴】资金项目 → 节点 → 账户 + 交易明细
   存储：业务数据 PG + RLS，按「资金项目 ↔ 用户」授权

【工作空间轴】openhive 项目 → 产物（报告/图谱/分析记录/文件）
   存储：沙箱目录 + git，产物落这里

桥梁 = 「我此刻在哪个 openhive 项目工作」的运行时上下文
   （产物落地时记 project_id，不反过来把数据绑定到空间，不建关联表）
```

### 3.3 数据流（读 MCP / 写 API）

```
【写入】上传文件 → 进沙箱 → AI 对话清洗 → 中栏展示清洗对比
        → 人点「确认入库」→ 前端直调后端 API → 批量 COPY 写 PG

【读取】AI 说「查 0206 近3月进账」→ 调「资金数据查询 MCP」
        → MCP 带 X-User-ID → 后端 RLS 过滤 → 返回该用户有权看的数据
```

## 4. 数据模型

### 4.1 存储分工

| 数据线 | 存哪 | 说明 |
|---|---|---|
| 资金数据（账户 + 流水） | 业务数据 PG | 分区 + RLS + 批量导入 |
| 涉案关系/资金链路（图） | 业务数据 PG（graph 表） | 只存提取后的关系，递归 CTE 查询 |
| 账号→人 身份映射 | 业务数据 PG（person/account 表） | 关系表 + 外键，一跳 join |
| 分析记录 + 产物文件 | 沙箱（openhive 项目目录）+ git | Markdown + frontmatter |

### 4.2 资金数据表（业务 PG）

```sql
fund_project (        -- 资金项目（数据轴一级组织单元）
  id         BIGSERIAL PRIMARY KEY,
  name       TEXT NOT NULL
)

fund_project_member ( -- 数据权限（独立于 openhive 项目权限）
  fund_project_id BIGINT REFERENCES fund_project(id),
  user_id         TEXT,               -- 复用 auth.user.id
  role            TEXT,               -- owner / member
  UNIQUE(fund_project_id, user_id)
)

fund_node (          -- 节点（多级自关联，≤10 级）
  id              BIGSERIAL PRIMARY KEY,
  fund_project_id BIGINT NOT NULL REFERENCES fund_project(id),
  name            TEXT NOT NULL,
  parent_id       BIGINT REFERENCES fund_node(id)
)

fund_account (       -- 账户（开户信息）
  id             BIGSERIAL PRIMARY KEY,
  fund_node_id   BIGINT NOT NULL REFERENCES fund_node(id),
  account_no     TEXT,               -- 账户编号
  account_number TEXT,               -- 账户号码
  account_type   TEXT,               -- 账户种类
  holder_name    TEXT,               -- 开户人员
  id_card        TEXT,               -- 身份证号（明文，研判对象）
  reg_phone      TEXT,               -- 注册手机
  wechat_id      TEXT,               -- 微信号
  wechat_account TEXT,               -- 微信账号
  login_phone    TEXT,               -- 登录手机
  status         TEXT,               -- 账户状态
  earliest_date  DATE,               -- 交易最早日期
  earliest_time  TIME                -- 交易最早时间
)

fund_transaction (   -- 交易明细（大表，按月分区）
  id                BIGSERIAL PRIMARY KEY,
  account_id        BIGINT NOT NULL REFERENCES fund_account(id),
  trade_time        TIMESTAMP,
  amount            NUMERIC(18,2),
  counterparty_acct TEXT,            -- 对方账户
  debit_credit      CHAR(1),          -- 借贷标志（D进账/C出账）
  balance           NUMERIC(18,2),
  summary           TEXT,
  trade_channel     TEXT
  -- 注意：对方户名不存这里，通过 join 映射表得到（见 4.3）
) PARTITION BY RANGE (trade_time);
```

### 4.3 账号→人 身份映射（关系表，不用图）

```sql
person (              -- 人（六要素「人」）
  id         BIGSERIAL PRIMARY KEY,
  name       TEXT NOT NULL,
  occupation TEXT,                 -- 职业（「干什么的」）
  id_card    TEXT,
  ...
)

account_identity (    -- 账号（六要素「网」虚拟身份）→ 人的映射
  id         BIGSERIAL PRIMARY KEY,
  account_no TEXT UNIQUE,          -- 对方账号（虚拟身份）
  person_id  BIGINT REFERENCES person(id)  -- 持有人（外键，一跳 join）
)
```

**明细回显链路**：`fund_transaction.对方账号 → join account_identity → join person → 回显姓名/职业`。原始流水表只存账号，不存人名。

> **澄清（开户名 vs 持有人）**：`fund_account.holder_name` 是开户时登记的姓名（原始数据自带，可能是经办人/名义人）；`account_identity.person_id` 是研判查明的**实际持有人**。两者可能不同（开户名 ≠ 实际持有人），回显时优先展示研判查明的 `person`，`holder_name` 作为原始字段保留对照。

### 4.4 涉案关系图（业务 PG，只存提取后）

```sql
graph_entity (        -- 六要素实体（§12.1）
  id        BIGSERIAL PRIMARY KEY,
  six_type  TEXT,                  -- 人/事/地/物/组织/网
  name      TEXT,
  ...
)

graph_relation (      -- 涉案关系 / 资金链路（多跳）
  id          BIGSERIAL PRIMARY KEY,
  from_entity BIGINT, to_entity BIGINT,
  rel_type    TEXT,                -- 资金往来/同户/关联…
  source      TEXT                 -- 人工标注 or AI 抽取
)
```

### 4.5 数据/语义分离原则

| 类型 | 落点 |
|---|---|
| 交易事实（金额/借贷/对方账号…） | `fund_transaction`（干净，只存事实，不做频繁 UPDATE） |
| 身份映射（账号→人） | `account_identity` + `person`（关系表，全局复用） |
| 涉案关系/资金链路 | `graph_relation`（图，提取后） |
| 分析判断（这笔可疑、张三这次是共犯…） | 分析记录（沙箱 Markdown，随案情变） |

**原则**：原始流水表保持干净，语义与判断分离——身份映射、涉案关系、分析判断都不往流水表堆字段。

## 5. 中栏多形态视图

复用 design-v2 §9.1「内容视图注册表」，按数据类型切换：

| 视图 | 渲染 | 数据来源 |
|---|---|---|
| 明细视图 | 账户统计汇总 + 交易明细（join 持有人） | PG 流水表 + account_identity/person |
| 桑基图 | 资金流向（可交互钻取） | 提取后的资金链路（图） |
| 图谱视图 | 涉案关系网络（拖拽/缩放/钻取） | graph_entity/relation |
| 分析记录视图 | 分析思路/结论（可编辑） | 沙箱 Markdown |
| 文件视图 | 当前 openhive 项目的其他产物文件（研判结论、用户记录、报告、导出的图） | 沙箱项目目录 + git |

- 进账/出账的底色（蓝/白）由 `debit_credit` 列渲染，不存字段。
- 桑基图两层：中栏可交互钻取 + 一键导出图片进报告。

## 6. 按钮降级映射（AI 优先重构的核心）

| 类 | 处理方式 | 按钮 |
|---|---|---|
| A. 交给 AI 对话 | 右栏说一句，AI 执行 | 数据清洗/批量清洗、一键分析、资金流数据分析、金额统计、关联关系（初步）、节假日 |
| B. 人确认闸门 | 简化确认 + AI 留痕 | 入库确认、专家关联/角色标注（确认）、发起银行提供（AI 生成调证请求 + 提交留痕） |
| C. 前端视图操作 | 保留为轻控件 | 显示异常、刷新、选定/取消、列显示隐藏、进账/出账底色、搜索 |
| D. 剔除 | 本次不做 | 报送/推送数据到观点分析 |

**右栏「资金分析 skill」能力清单**：

```
清洗    「这批数据有重复、格式乱，帮我清洗」
身份映射「把 138XXXX 账号标记为张三」
关联    「找出和张三有资金往来的账户」
资金链  「追一下这笔钱从哪来、到哪去（几跳）」
统计    「汇总各关联方的进出账金额」
标注    「把这些账户标为涉案，理由记进分析记录」
出产物  「生成资金流向图」「生成研判报告」「记一条分析思路」
```

**「发起银行提供」**（需留痕）：右栏让 AI 生成调证请求（理由、账户、时间段），提交时留痕（谁、何时、向哪家银行、要什么数据），轻量工作流。

### 6.1 AI 能力的可发现性（解决「民警不知道问什么」）

AI 优先不意味着消灭按钮——按钮的「可发现性」和「可学性」有价值。按钮降级为**右栏顶部的「指令卡」**，点卡片 = 自动把对应一句话填入输入框发给 AI，而非彻底消失。

**指令卡分两组**：

| 组 | 内容来源 | 形态 |
|---|---|---|
| **上下文指令**（随中栏状态动态） | 选中几个账户 → 「关联分析/资金链追踪/标为涉案/汇总进出账」；上传文件 → 「清洗入库/预览数据」 | 浅金底卡片，随选中实时变化 |
| **常用操作**（固定） | 清洗数据 / 一键分析 / 生成资金流向图 / 生成研判报告 | 白底卡片 |

**三层引导（新手到熟练的渐进）**：

1. **上下文指令 + 常用操作**：点卡片 = 填入一句话，AI 执行并**展示过程**。民警点按钮看到「原来这样问就能让 AI 做这个」，是被动学习。
2. **AI 主动给下一步**：AI 每次执行完，末尾主动给出「可继续」的提示词（如「追一下张三的资金链」「把张三标为涉案」），引导民警顺着往下。
3. **自由输入**：熟练后民警直接打字，AI 理解意图。

**关键原则**：
- 指令卡文字 = 原按钮的「业务语言」重新组织（「资金流数据分析」「专家关联」「金额统计」本就是民警听得懂的业务词），执行方式从「点一下出结果」改为「点一下 → AI 做并展示过程」。
- 输入框占位文字明确提示「说说你想做什么，或点上面的卡片…」，降低空白焦虑。
- 引导逐步收拢：新手阶段指令卡全展开；用久后常用项收成「最近/常用」，引导转向自由输入。
- 此设计呼应竞品分析中「千问办公的推荐提示词」与「Cloudflare 的前置化解焦虑」——AI 产品不能给用户空白画布，要给「可点的话题」。

## 7. 技术选型（实现时验证）

| 能力 | 方案 |
|---|---|
| 资金数据查询（读） | 自研「资金数据查询 MCP」，带 X-User-ID + RLS |
| 资金数据入库（写） | 后端 API + 批量 COPY + 分区表 |
| 图谱渲染 | AntV G6（前端） |
| 图存储 | PG 两张普通表 + 递归 CTE（不上图数据库） |
| 桑基图/统计图 | ECharts |

**图数据库的升级信号**（现在不触发）：需对全量 200 万条/日流水做实时图算法时，再上 Apache AGE 或独立图库。

## 8. 待决策点

1. **「发起银行提供」的审批粒度**：是「提交即留痕」还是要「上级审批」？当前按「AI 生成 + 提交留痕」设计，未引入审批流。
2. **批量导入的吞吐目标**：200 万条/日的批量 COPY，单机 PG 需压测确认；是否需异步队列（导入任务排队，完成通知）。
3. **资金项目权限管理入口**：`fund_project_member` 的授权（谁给谁开资金项目权限）在哪个界面配？建议复用治理后台，但需确认。
4. **清洗的 AI 能力边界**：AI 清洗能处理哪些（去重/格式/字段对齐），哪些必须人看——需首批清洗规则清单。
