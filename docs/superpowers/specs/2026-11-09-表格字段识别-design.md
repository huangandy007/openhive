# 表格字段识别与明细补全 · 设计（2026-11-09）

> 上游讨论记录见 `03-实体显示与治理.md` §4、§4.1、§9.1-7、§9.1-9，以及 2026-11-09 的本轮讨论。
> 本文是**设计**，不是实施计划。状态：范围与各节决策已由用户逐节确认（见 §2）。

## 1. 背景与实测证据

### 1.1 问题

`1105反诈交流`（项目 id `ab050e6c-dfdc-4659-b9e2-09a3d75b1390`）35 份资金 xls、**177,713 行**明细已入库，但：

| 指标 | 实测 |
|---|---|
| `case_fact_row` 行数 | 177,713（不是没解析，是解析了） |
| `started_at` 非空率 | 100% |
| `amount` / `balance` 非空率 | 100% |
| `counterparty` / `caller` / `callee` 非空率 | **0%** |
| `aggregate_money` 余额走势 / 明细匹配 | 空（按对手方匹配，对手方全空） |
| 明细行 citation | 0（设计裁定：表格明细不写 citation，id = `材料#sheet#行号`） |

真实银行表头样本：`交易对方名称`、`交易对方账卡号`、`查询账号`。

### 1.2 根因（三条，逐条有代码落点）

**R1：把「表头文本」当成字段身份。**

`detectMapping`（`case-mapping.ts:201`）的词典层规则是：精确相等优先，否则「表头以词典词**结尾**且全表唯一」。
`交易对方名称` 不以 `交易对方` 结尾（后面还有 `名称`），`交易对方账卡号` 不以 `对方账号` / `对方卡号` 结尾，
`查询账号` 不在任何词表里 ⇒ 三列全部落到 `unknownColumns` → extras。**补词表只是延长这个前提的寿命，解决不了表头换名。**

**R2：每个字段只取一列，且 `counterparty` 混装了两种概念。**

词典把 `对方账号` 和 `对方户名` 都指向 `counterparty`，而 `detectMapping` 的循环**每个字段最多命中一列**
（`case-mapping.ts:212-231`）。一张表同时有对手账号列和对手户名列时，只有一列进标准列，另一列进 extras——
**即使表头全部命中，信息也丢一半**。同时没有「本方账号」，也没有「收付方向」。

**R3：extras 的键是原表头文本**（`case-rows.ts:11-16`）。`收货地址` 与 `收件地址` 是两个键，换一家数据源就查不到。
这与 R1 同构，只是发生在 extras 里。

### 1.3 其他数据类型的现状（同一前提，同一病）

| 类型 | 现状 | 结论 |
|---|---|---|
| 资金 | `amount`/`balance` 通，对手方/本方全丢 | 本设计首批验收 |
| 话单 | 词典覆盖 `主叫/被叫/通话时长/通话时间`，能落标准列；但每字段只取一列，两个时间列（呼起/呼止）都以「时间」结尾 ⇒ 候选不唯一 ⇒ `started_at` 为空；表头变体同样 miss | 同批接入 |
| 订餐/物流 | `FACT_FIELDS` 无地址/商户/收寄人/电话 ⇒ 全进 extras；两列时间同样不认；`kind` = 其他（枚举里也没有订餐/物流） | 本期只保证字段可查 |
| 文本笔录 | 走 LLM 抽取，不受影响 | 不动 |

`case_material.kind` 由 `classifyMaterialType`（`case-mapping.ts:297-302`）事后按列判定，只有 `话单/资金/其他` 三档；
一个材料一个 kind，工作簿里多张表时**最后一张赢**（`case-ingest.ts:368`）。

### 1.4 目标

1. 识别引擎与数据类型解耦：**字段目录驱动**，资金/话单/订餐共用一套召回、校验、兜底；
2. 表头换名不再靠补词典：多路召回＋人工确认沉淀为全局别名库；
3. 资金明细补齐「对手方账号 / 对手方户名 / 本方账号 / 收付方向」；
4. 认不出的列仍然可查（extras 键规范化），且不静默错（单位闸、形状校验、待确认）。

### 1.5 与上游规格的关系（避免读者被判为自相矛盾）

- `03-实体显示与治理.md` §4.1 说「表格通路缺的是聚合与提升，不是抽取」——这句在**真实资金表上被证伪**：
  对手方识别率 0%，没有可聚合的字段。本设计取代该判断。
- `03` §8 的「不新增数据表」是对**显示治理那一期**的验收约束。本设计新增 `case_field_alias` 与
  `case_field_alias_version` 两张**不含案件事实数据**的元数据表（只有表头文本与版本号），属于新 feature，
  不受该条约束——在此显式说明，不让它变成下一轮评审的歧义。

## 3. 字段目录与识别流程

### 3.1 字段目录（Field Registry）

`DICTIONARY` 从「字段 → 同义词」升级为「字段 → 定义」，同义词只是其中一项：

```ts
interface 字段定义 {
  名: string                     // 标准名，落列名或 extras 键
  落点: "列" | "extras"
  种类: "账号" | "户名" | "号码" | "金额" | "余额" | "时间" | "时长" | "地点" | "商户" | "方向" | "文本"
  归一化: (原值: string) => string   // 去空格、去 +86、账号去横线；**只作用于值，不进指纹、不作别名键**
  形状?: RegExp                  // 证据层：整列命中率 ≥ 0.9
  同义词: string[]                // 即现有词典，降为其中一层
}
```

**资金字段**（`落点: 列`）：

| 字段 | 同义词（新增/保留） | 形状证据 |
|---|---|---|
| `counterparty`（对手账号） | 对方账号、对方账户、对方卡号、交易对方账卡号、对手账号、对方卡账号 | 账号/卡号形状或高填充率 |
| `counterpartyName`（对手户名，列 `counterparty_name`） | 交易对方名称、对方名称、对方户名、对手户名、收方名称、付方名称 | 中文姓名 / 组织名，非纯数字 |
| `ownerAccount`（本方账号，列 `owner_account`） | 查询账号、本方账号、本方账户、账号、卡号、客户账号 | 账号/卡号形状或高填充率（**不是**姓名形状） |
| `amount` | 交易金额、金额、发生额、交易额、收入金额、支出金额 | 两位小数 |
| `balance` | 余额、账户余额、交易后余额、当前余额 | 两位小数 |
| `direction` | 借贷标志、收付标志、资金方向、交易方向 | 收/付/进/出/借/贷 |
| `startedAt` | 交易时间、发生时间、时间… | 时间形状 |

**话单字段**：`caller`、`callee`、`startedAt`、`durationSec`（复用现有），新增同义词如 `主叫用户号码`、`对方手机号`、`通话开始时间`；
`对方号码` 归 `callee`，不得与 `caller` 争抢（争抢时走 D2 的触发条件）。

**「交易对方」的归属变更**：旧词典把它归 `counterparty`，与「户名 / 名称」语义冲突。本设计移到 `counterpartyName`；
若该列实际是账号形状，形状校验会把它退回待确认，人工确认时可改判为 `counterparty`。

**订餐/物流字段**（`落点: extras`）：`address`、`merchant`、`contactPhone`、`personName`、`deliveredAt`。
`startedAt` 只承载「发生时间」（下单时间）；送达时间进 `deliveredAt`，两者都命中时按别名库/词典优先级取一列，其余留 extras。

**跨类型共用**：`ownerName`（本方户名）走 extras 的 `ownerName`，不进标准列。

**命名约定**：字段名一律 **camelCase**（与现有 `startedAt` / `durationSec` 一致），DB 列名 snake_case，由落库层映射。

**归一化只作用于「写进标准列的值」**：账号去空格/横线、号码去 `+86`；若归一化结果与原文不同，原文仍进 extras
（A16「原始值从不改写」仍成立）。别名键与格式指纹都**不做**这一步（`#011-01`）。

### 3.2 识别流程（类型无关）

```
表类型推断（按列形状投票）
      ↓
① 别名库（原始表头精确命中，仍过单位闸）
      ↓
② 词典（精确 → 后缀唯一）
      ↓
③ 形状特征（时间、金额、账号、手机号）
      ↓
④ 触发式模型兜底（一次材料 ≤ 1 次调用）
      ↓
证据校验（单位闸 + 形状命中率 + 候选唯一性）
      ↓
待确认清单 → 人工确认 → 写入别名库
```

**表类型推断**：按列形状投票（11 位手机号占比、16–19 位账号占比、两位小数占比、时间形状占比），
输出 `资金 / 话单 / 其他（含订餐物流）`，只用于挑选「候选字段集」，**不写库、不改变 `kind` 的判定顺序**
（`classifyMaterialType` 仍按 `话单 → 资金 → 其他`，避免行为漂移）。

**召回顺序的两轮制（关键）**：先对**所有字段**做精确匹配，落定后再做后缀匹配。
否则「对方账号」会被排在前面、带通用词「账号」的 `ownerAccount` 用后缀抢走，
真正该认领它的 `counterparty` 反而拿不到。后缀轮同样要求候选唯一。
通用词（`账号`、`卡号`、`时间`、`金额`）只能在后缀轮里用，且不得抢已被精确命中的列。

**修饰语优先于通用词**（两轮制解决不了「后缀抢后缀」）：

- 表头含 `对方 / 对手 / 交易对方 / 收方 / 付方` ⇒ 只允许归对手方字段：以 `账号 / 卡号` 结尾归 `counterparty`，
  以 `名称 / 户名` 结尾归 `counterpartyName`；`账号`、`卡号` 这类通用词**不得**把它抢给 `ownerAccount`。
- 表头含 `本方 / 查询 / 客户 / 本人` ⇒ 只允许归 `ownerAccount`。
- 不含上述修饰语时，通用词才是 `ownerAccount` 的候选，且仍要求唯一。

**别名也要服从字段集**：别名命中后，若目标字段不在本表推断出的候选字段集里，视为冲突（见 §4.2-5）。

**证据校验的三条硬规则**：

1. 单位闸（`case-mapping.ts:129`）永远按**原始表头**跑，别名与模型都不能绕过；
2. 形状证据不达标的认领一律进待确认，不静默接受；
3. 同一字段有多个候选列时，按形状命中率取最高；前两名差距 < 5% ⇒ 不猜，进待确认。

### 3.3 触发式模型调用（D2）

满足任一条件才调用，一条材料最多一次（把所有 sheet 的表头 + 前 20 行样例一起送）：

- 关键字段缺失：资金缺 `counterparty` 或 `amount`；话单缺 `callee` 或 `startedAt`；
- 多字段争抢同一列（如两列都能当 `counterparty`）；
- 规则认领的列过不了形状校验；
- **有形状证据但未认领**的列占比 > 30%（`备注`、`摘要`、`网点` 这类纯文本列不计，否则每份银行流水都会触发）。

**模型输出是「列 → 字段名」的声明，字段名必须在枚举内**（`generateObject` schema 用字段目录生成），
认不出的列返回 `unknown`，**不得编造字段名**。模型结果同样要过 §3.2 的证据校验；与别名库冲突时别名库优先（D3）。

## 4. 全局别名库（D6/D7）

### 4.1 表形状

```sql
CREATE TABLE auth.case_field_alias (
  header       text        NOT NULL,   -- 原始表头，仅 trim + 空白折叠
  field        text        NOT NULL,   -- 字段目录里的名；可以是列字段，也可以是 extras 字段
  material_id  text        NOT NULL,   -- 哪份材料触发确认
  project_id   text        NOT NULL,   -- 只作追溯，不做隔离
  confirmed_by text        NOT NULL,
  confirmed_at timestamptz NOT NULL,
  hit_count    integer     NOT NULL DEFAULT 0,  -- 每解析一份材料中用到一次 +1（不按行）
  revoked_at   timestamptz,
  PRIMARY KEY (header),
  CONSTRAINT case_field_alias_header_len CHECK (char_length(header) BETWEEN 1 AND 200)
);

-- 缓存失效的运行时版本号。别名一变就 +1；源码里的 `识别版本` 只在改识别算法时 +1。
CREATE TABLE auth.case_field_alias_version (
  id      smallint PRIMARY KEY DEFAULT 1 CHECK (id = 1),
  version bigint   NOT NULL DEFAULT 0
);
INSERT INTO auth.case_field_alias_version (id, version) VALUES (1, 0);
```

`source` 列本期**不加**：D6 规定唯一写入口是人工确认，加一个只会取一个值的枚举是投机设计。

### 4.2 五条安全边界

1. **键必须是原始表头，不许归一化后入键**（`#011-01`）——`金额` 与 `金额（万元）` 归一化后同键，
   别名一旦命中就等于绕过单位闸。别名只回答「这串字符是哪个字段」。
2. **别名只提高召回，不提供证据**：命中后仍过单位闸与形状校验，不达标进待确认。
3. **优先级：别名 > 词典 > 形状 > 模型**；别名不得把一列两位小数说成手机号（证据层仍拦）。
4. **别名一变，缓存必须失效**：`识别版本`（`case-mapping.ts:282`）是**源码常量**，运行时改不了，
   不能用它做别名失效。改用 DB 计数器 `case_field_alias_version.version`：每次确认/撤销 +1，
   与别名写入**同一事务**。指纹改为 `sha256([识别版本, alias_version, 原始表头, 每列形状])`
   （`formatFingerprint` 增加一个参数，调用点 `case-ingest.ts:350` 与测试同步）。
   别名一变指纹全变 ⇒ 旧缓存不可达、重新识别一次；重识别是确定性的，不花钱（除非命中 §3.3 触发条件）。
   源码 `识别版本` 仍按既有注释只在改词典/单位闸/特征层规则时 +1。
   **一个解析任务开始读一次 `alias_version`，随任务传下**——不要每张 sheet 各读一次，否则同一材料
   内可能出现两张表用不同版本、缓存与 `parse_detail` 对不上。
5. **别名只对「当前推断字段集」生效**：同一表头在不同类型表里可能含义不同（如「号码」）。
   命中后若目标字段不在本表推断出的候选集里，**不生效、进待确认**，并记录冲突原因。

### 4.3 并发与撤销

- 同一表头重复确认 ⇒ 主键冲突，提示「已存在，请先撤销」；
- **表头在同一张表里重名时不写别名**（键区分不出是哪一列）：该列走待确认，按位置处理（`第N列`）；
- 撤销 = `revoked_at` 置位 + `alias_version` +1（与撤销**同一事务**），不物理删除（留审计）；
- 每次确认/撤销记 `confirmed_by`、`project_id`、`material_id`，并在材料详情展示「已复用 N 次」；
- `hit_count` 在解析命中别名时于同一解析事务 +1（**一份材料一次**，不按列/行——否则数字失去意义）；
- `field` 由**服务端**按字段目录校验，不信任前端传值；`header` 长度 1–200（建表 CHECK 兜底，端点先回 400）。

### 4.4 写权限

材料所在项目的**属主（`role = 'owner'`）**才能确认/撤销别名；普通成员只能看到待确认项。
理由：库是全局的，写错的代价跨案件；权限沿用现成的项目成员模型（`project_member.role` 只有
`owner` / `member` 两档，**没有「管理员」这一档**），不新建权限体系。判据复用 `project-actor.ts` 的 `成员角色()`。

## 5. 待确认与人机闭环（D5）

### 5.1 载体

不新增 `parse_status` 值（该枚举由迁移 0031 冻结）。在 `case_material.parse_detail` 里加 `mapping` 段，
**按工作表名分组**（一份材料可以有多张表，平铺会互相覆盖）：

```json
{
  "mapping": {
    "模型": { "调用": 1, "失败": "ECONNREFUSED" },
    "工作表": {
      "Sheet1": {
        "来源": { "3": "别名库", "7": "词典", "12": "模型" },
        "待确认": [{ "列号": 9, "表头": "摘要", "建议字段": null, "原因": "多列争抢" }],
        "未知列": 3,
        "方法": "别名"
      }
    }
  }
}
```

- `模型` 放顶层：一次材料只调一次模型，不能记到某一张表头上；
- 来源与待确认按**列号（0 起，与 `mapping` 的键一致）**，不按表头——表头重名/为空时不歧义；
- `applyParseAction` 的 `detail` 是**整份替换**（`case-store.ts:287-294`），写 mapping 时要把整份 detail 一起给；
  成功路径没有 `reason/slices`，只写 `mapping`；
- **每次解析都写**（含缓存命中），否则角标会随缓存命中消失（见 §6.4）；
- 迁移 0031 对 `parse_detail` 的 COMMENT 写的是「有问题原因明细」，本条是**扩展**不是改语义，注释已冻结、不动。

### 5.2 流程

1. 解析完成时，若 `待确认` 非空，材料卡片显示角标「N 列待确认」（不改变 `parse_status`，材料仍是「已解析」）；
2. 点开可看到每列的原表头、样例值、建议字段与来源；
3. 属主选定字段 ⇒ 写别名库 + `alias_version` +1（同事务）⇒ 提示「重新解析该材料」；
4. 模型不可达 ⇒ `模型.失败` 记错误名（沿用「原因只取错误名」的约定），照常入库，待确认照列。

## 6. 数据模型变更

### 6.1 `0035_case_fact_columns.sql`

```sql
ALTER TABLE auth.case_fact_row
  ADD COLUMN counterparty_name text,
  ADD COLUMN owner_account     text,
  ADD COLUMN direction         text;

ALTER TABLE auth.case_fact_row
  ADD CONSTRAINT case_fact_row_direction CHECK (direction IS NULL OR direction IN ('收', '付'));
```

只改父表：PG 的 `ADD COLUMN` 自动下发到 16 个已有分区，不写 16 条分区语句。
配 `0035_case_fact_columns.down.sql`。`counterparty` 的语义收窄写进 `COMMENT`。

### 6.2 `0036_case_field_alias.sql`

一个迁移里三件事（都属「别名库」这一件事，拆开反而要求两次部署）：

1. 别名表与版本表（§4.1）；
2. 给 `case_table_format` 加 `result jsonb`（缓存命中也要能恢复来源/待确认，见 §6.4）；
3. drop 后重建 `case_table_format_method` 的 CHECK，加入 `别名`（见 §6.4）。

另配 down 文件：恢复三值 CHECK、删列、删两张新表。

### 6.3 写入契约

`FactRowInput`（`case-store.ts:305`）加三个可选字段；`insertFactRows` 的列清单与绑定参数同步——
**18 列 × 500 行 = 9000 个绑定参数**（现有注释写的是 15 列 × 500 = 7500，要一起改，仍远低于 65535 上限）。
`toFactRows`（`case-rows.ts:121`）负责填值：

**字段类型必须拆开**：`FactField` 只含**标准列**字段；新增 `识别字段 = FactField | ExtrasField`。
`mapping` 的值是 `识别字段`，`toFactRows` 按字段目录的 `落点` 决定写法：列字段写标准列，extras 字段写
`extras[字段名]`。`case-rows.ts` 现有的 `是事实字段()` / `选中列()` / `单元格()` 都只认 `FACT_FIELDS`，
必须改成按字段目录判断；否则 extras 字段会被当成「未知列」，键又退回原表头，整条设计白做。

- `direction`：显式列 → 按下表归一化；无显式列 → `amount` 为负记 `付`；都没有 → null，原文本进 extras。
  `case-rows.ts` 的 `解析失败()` 要加 `direction`（归一化为 null 即视为失败），否则认不出的原值会被当成
  「已用标准列」而不进 extras，原文就再也看不到了。
  **正数且无标志不推**（银行流水正数可能全是收入，也可能全是支出）：

  | 原值 | 归一化 |
  |---|---|
  | 收、进、入、贷、转入、收入 | `收` |
  | 付、出、借、转出、支出 | `付` |
  | 其他 / 空 | null（进待确认） |

- `counterparty`：有账号列时只写账号；只有户名列时 **`counterparty` 与 `counterpartyName` 都写该值**
  （前者兜住 `aggregate_money` 的按名匹配，后者是规范来源），不是二选一；
- extras 键：`落点: extras` 的字段用 camelCase 字段名（如 `ownerName`、`address`）；未认出的列仍用原表头 / `第N列`。

### 6.4 识别结果与缓存

`MappingResult` 增加 `待确认 / 来源 / 方法`。**缓存必须连同它们一起存**：
`读格式`（`case-ingest.ts:705`）现在只返回 `columns`，同格式的第二份材料命中缓存后，
既拿不到来源、也拿不到待确认 ⇒ 角标消失、部分映射被静默复用（`#011-01` 的同一类失效）。
0036 给 `case_table_format` 加 `result jsonb` 存 `{来源, 待确认, 方法}`；缓存命中时
`跑表格` 用 `result` 写 `parse_detail.mapping`，与现场识别走同一条出口。

`mapping` 的值类型从 `FactField` 放宽为 `识别字段`（§6.3）；`读格式` / `写格式` 的签名同步。
`method` 现有 CHECK 只允许 `词典 / 特征 / 模型`（`0032_case_table_format.sql:28`），
0036 里 **drop 后重建**为 `词典 / 特征 / 别名 / 模型`（0032 已冻结，不原地改；down 文件恢复三值）。
`method` 的取值语义：**模型参与过就记「模型」**（最不可复现），否则用到别名记「别名」，再否则沿用现有两层——
不让「别名 + 模型」这种组合被记成一个看起来更可信的值。

原表头已整份存于 `case_table_format.header`，且 `case_material.fingerprint` 指向它，
因此 extras 用字段名作键**不丢失**「原件上写的是什么」。

## 7. 模型复用（D12，硬约束）

- 模型解析仍走 `解析启动模型(config, env)`（`case-ingest-worker.ts` 启动时解析一次，来源进审计）；
- 调用仍走 `建抽取器` 同一个 seam：`instances.provide({ directory }, Effect.gen(getModel + getLanguage))` → `建调用模型(语言)`；
  表格路径新增一个同形状的 `建表头识别器`，**不复制** provider 解析、不新建客户端、不新增重试；
- 调用封装复用 `generateObject` + schema + `AbortSignal.timeout` + 详细失败（`case-extract-ai.ts`）；
- 审计字段沿用 `model / modelSource / promptVersion`，模型调用次数与失败原因进 `parse_detail.mapping.模型`；
- 模型输入只有表头 + 前 20 行样例，**不把整表送进模型**（`#011-03` 的面积教训）；
- **默认送原始样例**（2026-11-09 拍板，覆盖先前「默认脱敏」的提案）：模型输入为表头 + 前 20 行原文。
  样例因此含姓名、账号、金额，**前提是所用模型为内网 / 自部署**；识别审计必须记录 `modelSource` 与模型端点标识，
  以便事后追溯「哪些材料的原文送给了哪个模型」。这是一条有合规成本的决策，不是默认安全的。
- **可选脱敏开关**：部署配置 `表头识别.脱敏 = true` 时，账号保留前 4 后 4、姓名保留姓、金额只给位数与量级，
  另附列形状摘要（字符类 / 长度 / 命中率）；默认关闭（即送原文）。脱敏会削弱「账号 vs 号码」「姓名 vs 地址」的区分，
  开启时验收须把「因脱敏而认不出」与「模型不可达」分开统计。

## 9. 测试策略

遵循仓库铁律：每条改动先写会红的用例（TDD）→ 改到绿 → 变异验证（拆掉修复必须红，红法按 `#003-03` 三类记）→ 受影响 package 的 typecheck + 测试 + oxlint（在仓库根，`#004-10`）→ grep 同类落点。

必须覆盖的用例（至少）：

1. `交易对方名称` / `交易对方账卡号` / `查询账号` 三列表头，在**无别名**时分别进待确认，**有了别名**后落
   `counterpartyName` / `counterparty` / `ownerAccount`（列 `counterparty_name` / `counterparty` / `owner_account`）；
2. 同一表同时有对手账号列与对手户名列 ⇒ 两列都落库（回归 R2），不是只取一列；
2b. 「对方账号」必须由 `counterparty` 认领，**不能被 `owner_account` 的后缀「账号」抢走**（两轮制）；
3. 别名命中「金额（万元）」时单位闸仍拦下（回归 `#011-01`），进待确认；
4. 别名命中一列日期但目标字段是 `counterparty` ⇒ 形状校验拦下，进待确认；
5. 别名写入后 `alias_version` 递增，指纹变化、同表不再命中旧缓存；撤销后同样失效；
5b. 别名写入与 `alias_version` 递增在同一事务：故意让递增失败，别名行不得留下；
6. 模型不可达 ⇒ 解析仍完成、材料标待确认、`parse_detail.mapping.模型.失败` 有错误名；
7. 模型返回非法字段名 ⇒ 丢弃，不影响已通过证据校验的规则结果；
8. `direction` 三路取法（显式列 / 金额为负 / 无）；借贷标志的方向词各落 `收` 或 `付`，认不出的进待确认；
8b. 同一材料里表头重名 ⇒ 不写别名，走位置键；
9. extras 键用字段名：`收货地址` 与 `收件地址` 在两份材料里落同一个 `address` 键；
10. 话单两个时间列不唯一 ⇒ 待确认，而不是静默 `started_at` 为空；
11. 重放不变量：行数与 `amount` 总和不变；
12. **缓存命中不丢待确认**：同一指纹的第三份材料命中 `case_table_format` 时，`parse_detail.mapping.待确认` 仍在；
13. 同一表头在不同字段集下：别名目标字段不在候选集 ⇒ 不生效、进待确认（§4.2-5）；
14. `aggregate_money` 回归：只有户名列、没有账号列时，按户名实体查余额走势仍非空；
    有 `owner_account` 时，按本方账号查得到该账户的流水；
15. 多 sheet 材料：两张表的待确认分别落在各自的 sheet 键下，互不覆盖；
16. 模型入参快照：**默认送原文**（断言样例含完整账号，防有人误把脱敏改成默认）；
    开关 `表头识别.脱敏 = true` 时断言没有完整账号/姓名（按 `case-extract-ai` 的入参快照断言）；
16b. `dryRun` 下三处写路径全不落库（`case_fact_row` / `case_table_format` / `case_material.parse_detail`），
    且返回结构与真实解析一致；
17. 别名确认端点：非 owner 403、非法 `field` 400、header 超长 400。

## 10. 验收标准

### 10.1 资金（首批）

- 真实 1105 项目 35 份资金 xls 全部通过重放；
- `counterparty` 非空率 ≥ 95%，`owner_account` 非空率 ≥ 95%（**行级**：非空行 ÷ 35 份材料的总行数）；
- `direction` 有值率**据实报告**（无标志无符号的行记未知，不凑数）；
- 未知列占比 < 20%（**列级**：`unknown_columns` 之和 ÷ 各 sheet 表头列数之和；与 §3.3 的 30% 触发阈值不是同一个口径——
  触发是「花钱的线」，验收是「质量的线」，中间 10% 不承诺）；
- 单位回归 0 例；
- `aggregate_money`：按账户实体规范值查 1105 的余额走势**非空**，且按本方账号能命中该账户的明细；
- 模型调用可审计：单材料 ≤ 1 次，`parse_detail.mapping.模型` 有调用次数与失败原因。

### 10.2 话单（同批）

- 别名库覆盖真实话单的常见表头变体；
- 话单 **聚合视图不在本期**（03 §4 的 Top 10–20 属下一期），本期只承诺明细字段正确；
- 真实话单样本是否存在于 1105 项目尚未核实（见 §11）。

### 10.3 订餐/物流

- 只承诺：地址、商户、联系电话、下单时间**可查**——「可查」的定义是**行详情里能看到规范键与值**；
  **不提供**按地址/商户聚合的 HTTP 或 MCP 工具，也不承诺 SQL 可索引；
- 轨迹点视图不做（03 §9.1-7 未决）。

| 缺口 | 说明 |
