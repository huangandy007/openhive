# 案件数据预处理与字段契约 · 工作指引

> **状态**：工作指引草案（2026-11-11），用于指导预处理 skill 的编写；不是实现计划。
> **上游**：`2026-11-09-事实卡片抽象/01-事实卡片与数据翻译-设计.md`（表结构与翻译层）、`过程文档/03-微信流水预处理-字段口径与转换规则.md`（唯一有实测样本的一类）、`过程文档/05-实体属性标记与入库规范.md`、`过程文档/06-备注字段与交易语义-存储与关联.md`。
> **范围**：一份原始材料进来，预处理 skill 应该怎么读、怎么判、产出哪些列；这些列又如何落到 `case_fact_row` / `case_event` / `case_event_participant` / `case_relation` / `case_entity_alias` / `case_entity.attrs` / `case_citation`。
> **标记约定**：
> - ✅ **已实测**：有真实样本、跑过、有守恒数字（目前只有微信流水）；
> - ⚠️ **草案**：结构可复用，但没有真实样本验证，阈值与列名待样本校准；
> - ❌ **本轮不做**：明确不在预处理范围。
> **明文原则（硬约束）**：账号、证件号、手机号、姓名、金额全程明文。预处理**不做掩码、不做脱敏**；源文件自带 `*` 或位数不足是**数据缺陷**，不是本系统的脱敏，按 §5.5 处理。

## 0. 一页结论

1. **预处理只做四件事**：准入判定、相对角色翻译、格式固定（列名/列序/取值口径）、可追溯补全。**不做实体消解、不做跨文件归并、不做事件合并**。
2. **每份材料只产出两份东西**：`标准副本`（原始列 + 标准列 + 判定依据列 + 行号）和 `转换说明`（指纹、闸门结果、列映射、对账、告警）。原件永久不动。
3. **标准副本的四组列是固定结构**：原始列一字不改；标准列是结论、可重算；判定依据列说明「为什么这么判」；行号是回原文的唯一锚点。
4. **两道闸 fail-closed**：表头闸（必需列齐全）+ 值验证闸（方向、金额、时间、绑定关系等逐项过阈值）。任一不过整份拒收，只出拒收报告，不产出标准明细。
5. **所有类型共用一套落库槽位**（01 §3.5）：明细行、事件卡片、参与者、关系、别名、属性、出处。预处理不直接写库，只把「一行」摆成翻译层能直接消费的形状。
6. **金额永远正数，方向单独一列**；`借`=付、`贷`=收；禁止用负数金额表达方向，否则合计会把收支相抵。
7. **标准列里不留 `-`**；空就是空。源文件的 `-` 只留在原始列，否则下游会把 `-` 当卡号建实体。
8. **属性列必须命名成 `属性:<归属>:<键>`**，归属只允许 `对方` / `本方`；裸的 `对方银行卡号` 会被内核合成候选认成账号，既挂不上属性又制造错误实体。
9. **实体属性只写「原文里读到的事实」**：每个值带 `出处`（材料#工作表#行号），同键不同值并存、不覆盖，空值和占位符不写。
10. **当前只有微信流水可以照着写**；银行、支付宝、话单、住宿、出行、订餐都需要先拿真实样本校准，不能把本文的草案列名当成已验证契约。

## 1. 预处理与内核的边界

### 1.1 谁做什么

| | 预处理（skill） | 内核（opencode） |
|---|---|---|
| **做** | 准入判定、相对角色翻译、格式固定（列名/列序/取值口径）、可追溯补全 | 识别、明细落库、出处绑定、翻译成卡片与实体、查询 |
| **不做** | 实体 id、实体消解、关系抽取、事件合并、跨文件归并、用途判断 | 不重做逐行角色判断；不「猜着转」 |
| **产物** | 标准副本 + 转换说明（原件指纹、逐项闸结果、未转换行） | `case_fact_row` / `case_event` / `case_entity` / 等 |
| **拒绝** | 任一闸不过 ⇒ 整份拒收，只出拒收报告 | 收到拒收结论 ⇒ 不入库（执行方式待定，01 §13 Q12） |

**为什么角色翻译必须在预处理**：识别层只有「列」没有「行」，而「对方账号」这个答案不在任何一列里，在「借贷标志 × 两列账号」的比较结果里。预处理把逐行推理做完，翻译层只认标准列名、只做实体归并。

### 1.1.1 为什么「用途判断」不在预处理

**判据一句话：预处理只做「格式对齐」——凡是必须「看内容才能下结论」的，全交给入库翻译层。** 解码是「还原」，所以归预处理；「扫到中国石化判成加油」是「解释」，所以不归。

预处理**必做三件为判定铺路的事**（机械、确定性）：

1. **备注原文逐字保留**——不截断、不归一化、不合并换行；它是判定层唯一的输入。
2. **保住 `##` 分段与 `键：值` 结构**——不要在清洗阶段把它拍平成一句话。
3. **`UTF8#…` 解码**——base64 → 中文商户名，纯还原；解码失败保留编码原文并进告警，不伪造商户名。

预处理**一律不做**：贴标签、猜用途、填 `purpose`；按语义筛行、丢「看不懂」的行、去重。

**为什么不能顺手在这里判**：① 标准副本是落盘产物，判完就固化，词表一升级就得重跑几万行文件；② skill 可被用户随时改，判定口径不能放在会被随手改的地方；③ 判定的产出是 `case_event.purpose` + `purpose_basis`（带版本、可审计、人工可改），skill 没有库访问，也不该有（`06` §6.1、§6.7）。

### 1.2 产物形态

```
<原文件名>-标准副本.xlsx
  ├ sheet「标准明细」：原始列 + 标准列 + 判定依据列 + 行号
  └ sheet「转换说明」：源文件 SHA-256/字节数、表头行号、数据行数、
      两道闸逐项结果、绑定关系与列映射、判定规则分布、
      对账（行数/金额/分类条数/户名覆盖/名册条目）、告警清单
<原文件名>-拒收报告.xlsx
  └ 只说明「哪条闸不过、实测多少、缺哪列」，不产出标准明细
```

- 源文件指纹进转换说明；同一文件重复转换应得到同一结果（幂等）。
- `规则版本` 必须写进转换说明，并在规则变化时 +1。接入内核缓存后，不升版本会让旧缓存绕过新规则（`#011-01`）。
- 多工作表：默认只处理第一张有数据的表；其余表**至少告警**，不静默丢弃（03 §12-2）。

### 1.3 什么时候允许「补」

只允许**跨行一致性补全**，并且必须可追溯：

- 同一账号在本文件里另一行读到户名 ⇒ 可补，写 `依据:户名依据` 指出取自哪一行；
- 同一账号在本文件里从未出现名字 ⇒ 不补，留空；
- 不跨文件补齐（跨文件账号名册属实体层，不是预处理职责）；
- 不猜、不做拼音/同音字/编辑距离/模糊匹配（01 §3.8.3）。

**补全的出处要指向「读到名字的那一行」，不是「被补的那一行」。** 否则复核时按出处翻回去，看到的是一行本来就没有名字的记录，证据链断掉。

## 2. 标准副本的四组列

### 2.1 结构

| 组 | 内容 | 规则 |
|---|---|---|
| 原始列 | 源文件全部列，一个字不改 | 证据；丢了就没了 |
| 标准列 | 预处理算出来的结论 | 可重算；列名与取值按本文契约 |
| 判定依据列 | `依据:规则`、`依据:户名依据`、`依据:来源列`、`依据:告警` 等 | 让审查看得出「读到」与「推得」 |
| 行号 | 该数据行在原 sheet 的物理行号（1-based，表头也算行） | 与 `case_citation.locator.row` 同口径，回原文的唯一锚点 |

### 2.2 命名硬规则

1. **优先用内核字段词表里已有的名字**：`对方账号`、`本方账号`、`交易金额`/`金额`、`发生时间`、`借贷标志`、`主叫号码`、`被叫号码`、`通话时长` 等。词表命不中的标准列，会掉进 `extras`，翻译层要显式按列名读——这是允许的，但必须写进契约。`备注` 不在词表是**有意为之**：原文照旧进 `extras`（键=备注），语义由翻译层落成卡片（`06` §3、§5）。
2. **属性列**：`属性:<归属>:<键>`，归属只允许 `对方` / `本方`。入库端用 `^属性:(对方|本方):(.+)$` 识别，不参与四层字段召回、不进待确认弹窗；原文仍留在 `extras`。
3. **判定依据列**：统一加 `依据:` 前缀（如 `依据:判定规则`），避免与字段同义词撞名。该前缀目前内核未特殊处理，靠「名字不在词表」落进 extras；**像 `对方支付帐号` 这种会与 `对方账号` 争抢合成候选的审计列，必须降为 `依据:` 列**；`对方账号类型` 仍是翻译必需列，靠「标准列优先」定序压住合成候选。
4. **`-` 不进标准列**：源文件的 `-` 只保留在原始列；标准列统一清成空。
5. **金额正数**：`金额(元)` 永远 ≥ 0；方向只由 `收付方向` 表达。源文件用负数表示支出的，预处理取绝对值并把方向判出来。
6. **时间**：标准列 `发生时间` 统一为 `YYYY-MM-DD HH:MM:SS`（UTC+8）；原始时间字符串留在原始列。建议同时产出 `时间精度`（到日/到分/到秒）与 `时间类型`（发生/记录/入库），便于内核直接落 `precision` / `time_type`。
7. **不写实体 id**：预处理只写账号/号码/名称原文，实体 id 由内核归并时生成。

### 2.3 标准列的最小集合（所有类型通用）

| 列 | 必填 | 说明 |
|---|---|---|
| `行号` | ✅ | 原表物理行号 |
| `发生时间` | 视类型 | 规范时间；点事件给一个，区间事件给开始 |
| `结束时间` | 区间事件 | 规范时间；点事件留空，不编造 |
| `发生时间原文` | ✅ | 原文照抄，永不改写 |
| `时间精度` | 建议 | 到日/到分/到秒 |
| `时间类型` | 建议 | 发生/记录/入库 |
| `金额(元)` | 视类型 | 正数 |
| `备注` | 可选 | 原文照抄，不截断、不归一化 |
| `收付方向` | 视类型 | 收/付；不要写借/贷 |
| 判定依据列 | ✅ | 至少 `依据:判定规则` 与 `依据:告警` |
| 类型专属列 | 见 §4 | 账号、号码、地点、班次等 |

## 3. 从标准列到内核字段

> 预处理**不直接写表**。下表说明翻译层会把这些标准列放到哪里，写 skill 时按这个目标产列。

### 3.1 明细层 `case_fact_row`

| 标准列 | 落点 | 备注 |
|---|---|---|
| `行号` | `case_citation.locator.row` | sheet 名同时进 locator |
| `发生时间` | `started_at` | Unix 秒；由内核换算 |
| `发生时间原文` | `started_raw` | 原文照抄 |
| `时间精度` | `precision` | 到日/到分/到秒 |
| `时间类型` | `time_type` | 发生/记录/入库 |
| `金额(元)` | `amount` | 正数；numeric(18,2) |
| `余额(元)` | `balance` | 正数 |
| `备注` | `extras`（键=`备注`） | **不建列**（06 §5，2026-11-12 修正）；原文照抄，只作翻译层输入与人工回显 |
| `本方账号` | `owner_account` | `0035_case_fact_columns.sql:9` 新增列 |
| `对方账号` | `counterparty` | 账号/商户号/虚拟身份标识，按 `对方实体类型` 区分 |
| `对方户名` | `counterparty_name` | `0035_case_fact_columns.sql:8` 新增列 |
| `收付方向` | `direction` | 收/付；词表暂未收 `收付方向`，见 §6 |
| `主叫号码` | `caller` | 话单 |
| `被叫号码` | `callee` | 话单 |
| `通话时长(秒)` | `duration_sec` | 话单 |
| 其他标准列 | `extras` | 键沿用该标准列的中文名，原值不改；若已命中词表 extras 字段（如 `address`/`merchant`），用词表键名 |

#### 3.1.1 明细层的真实能力边界（2026-11-11 按迁移核对）

**`case_fact_row` 的类型化列只覆盖资金和话单**，其余类型没有专属列：

| 类型 | 有类型化列吗 | 现在能落到哪 | 能不能成卡/能查 |
|---|---|---|---|
| 资金 | ✅ `amount/balance/direction/counterparty/owner_account/counterparty_name` | 明细列；备注与用途留 `extras` | 明细可查；卡片/关系未接 |
| 话单 | ✅ `caller/callee/started_at/duration_sec` | 明细列；通话类型/地点/费用进 extras | 明细可查；卡片未接 |
| 住宿 | ❌ | 全部进 `extras`（房号、宾馆、入住/退房时间） | 不能 |
| 火车 / 飞机 | ❌ | 全部进 `extras`（班次、出发/到达、座位号） | 不能 |
| 订餐 / 扫码 | 部分 ✅（`amount/started_at/counterparty`） | 商户、订单号、地址进 extras | 不能 |

> **别把「能存明细」当成「能成卡、能查」**：01 的「所有类型共用明细 + 卡片 + 参与者」是目标态；当前迁移只落了明细，`case_event` 还没有 `occurred_end/amount/attrs`，参与者表、表数据→事件卡的翻译路径都还没落地。住宿/出行/订餐今天进来，只能停在 extras。

### 3.2 卡片层 `case_event`

| 九格 | 来自标准列 | 说明 |
|---|---|---|
| 干什么 | 由材料类型/模板决定（不是逐行标准列） | 资金交易/通话/住宿/乘车/乘机/消费/支付；事件类型词表待定（01 Q17） |
| 何时 | `发生时间` + `时间精度` + `时间类型` | 区间事件再加 `结束时间` → `occurred_end` |
| 谁（主体） | 主体标识列（本方账号/主叫号码/入住人证件号/乘客证件号/下单人） | 参与者 `ordinal=0` |
| 和谁 | 对方标识列（对方账号/被叫号码/同住人/商户） | `ordinal=1..n` |
| 何地 | 地点列（宾馆/出发地/到达地/商户地址） | 参与者 `role='地点'`，地点是实体，不是列 |
| 多少钱 | `金额(元)` | `case_event.amount`，正数 |
| 其他 | `房号`/`座位号`/`车次`/`订单号` 等 | 只放**不参与过滤**的进 `attrs`；会出现在「帮我找出…」里的必须成为实体或独立列 |
| 出处 | `行号` + sheet | `case_citation(fact_type='event')` |
| 可信度 | 预处理不改 | 默认 `自动抽取` |

### 3.3 参与者、关系、别名、属性

| 产出 | 来自 | 规则 |
|---|---|---|
| `case_event_participant` | 主体/对方/地点/同住人/班次等 | 每行有 `role`、`mention_text`（原文写法）、`ordinal`；`ordinal=0` 固定为主体 |
| `case_relation` | 由卡片汇总 | 只允许 7 类：通话/转账/实名登记/实际使用/同案/持有/同行；**哪些卡片能建边必须由规则显式声明**，不声明就不建 |
| `case_entity_alias` | 户名/姓名/证件号/手机号/账号/车牌/地址/名称 | `kind` 按类型；`value` 归一化、`raw_value` 原文；户名挂账户，不是人 |
| `case_entity.attrs` | `属性:<归属>:<键>` | 见 §5；值带出处 |
| `case_citation` | 行号 + sheet + 材料 id | 行级 `fact_id = <material>#<sheet>#<row_no>`；表名可能含 `#`，不要反解析 |

### 3.4 关系边：哪些建、哪些不建

| 数据 | 建边 | 不建边 |
|---|---|---|
| 转账（账户↔账户） | `账户 --转账--> 账户` | — |
| 提现/充值（对方账号=本方账号） | 不建自环；只记卡片 + 银行卡属性 | ❌ 不建 `转账` 自边 |
| 消费（账户→商户） | **默认不建**；模板显式声明「付款账户↔商户」时才建，且只建到组织/地点 | 不建「账户↔账户」；不默认把商户汇入资金流 |
| 话单 | `号码 --通话--> 号码` | — |
| 住宿 | 不建「人—宾馆」假边；人—同住人可建 `同行`（需显式声明） | ❌ 不建「人—宾馆」 |
| 火车/飞机 | 人—同行人 `同行`（需声明）；班次作为参与者角色 | ❌ 不建「人—班次」边（班次是物品实体，走参与者） |
| 订餐 | **默认不建**；模板显式声明「付款账户→商户」时才建 | 不建「人—商户」 |

> 这条表是 01 §4.0.4「关系必须由模板/规则显式声明」的落地：不声明就不建，避免「张三—同行—XX宾馆」这种假关系自己长出来。

## 4. 分类型处理指引

### 4.1 微信支付账户流水 ✅（唯一有实测样本）

**输入必需列**：`查询账号`、`付款方支付帐号`、`收款方支付帐号`、`借贷标志`、`交易金额`、`交易余额`、`交易时间`。缺一列拒收。

**处理动作**（详见 03）：

1. **本方/对方是相对角色**：`借` ⇒ 本方=付款方、对方=收款方；`贷` ⇒ 反之。按列名硬取会错掉接近一半的行。
2. **每侧是「支付账号 + 名下卡 + 开户行」一组**：不能跨方拼列，不能拿卡号当支付账号的备胎。
3. **对方账号只取支付帐号**：银行卡不是账号；提现/充值时对方账号 = 本方账号。
4. **「收款方的商户名称」是收款方账户的开户人姓名**，不是消费场景商户名；归属跟着收款方走。
5. **户名可跨行补全**：按账号名册补，写 `依据:户名依据`；补全出处指向读到名字的那一行。
6. **消费商户号三形态都认**：直连、间连（账号取单号、户名取机构、强制企业并告警）、只有商户名。

**标准列（v2 建议，顺序即契约）**：

`行号`、`本方账号`、`本方户名`、`本方主体类型`、`收付方向`、`对方账号`、`对方账号类型`、`对方户名`、`对方主体类型`、`对方实体类型`、`金额(元)`、`余额(元)`、`发生时间`、`发生时间原文`、`时间精度`、`备注`、`属性:本方:银行卡号`、`属性:本方:开户行`、`属性:对方:银行卡号`、`属性:对方:开户行`、`依据:判定规则`、`依据:对方来源列`、`依据:对方支付帐号`、`依据:户名依据`、`依据:告警`

> 与 03 §9 的 v1 相比：把 `本方银行卡号/本方开户行/对方银行卡号/对方开户行` 四列改成 `属性:` 列（否则会被合成候选误认成账号）；新增 `对方实体类型`、`余额(元)`、`发生时间原文`、`时间精度`、`备注`；`判定规则/对方来源列/对方支付帐号/户名依据/告警` 加 `依据:` 前缀（`对方支付帐号` 从标准列降为依据列，仍保留原始取值）。**这属于契约 v2，skill 版本必须 +1。**

**`对方账号类型` → `对方实体类型` 映射**：

| 对方账号类型 | 对方实体类型 | 说明 |
|---|---|---|
| 支付账号 | 账户 | 微信/支付宝账号 |
| 直连商户号 / 间连商户号 | 组织 | 商户号不是银行账户 |
| 商户名 | 地点 / 组织 | 按 01 §3.5 判据：能指认物理场所（XX餐厅/XX超市）→ 地点；公司/机构/品牌 → 组织 |
| 空 | 无 | 无对手行 |

**逐行落库**：

- 卡片：`type=资金交易`；`occurred_at=发生时间`；`amount=金额`；`summary` 一期不加；**余额留在明细行 `balance`，不进卡片**。
- 参与者：本方账户 `ordinal=0`，角色按方向取 `付款方/收款方`；对方账户（或商户）`ordinal=1`，角色相反。
- 关系：转账 → `账户 --转账--> 账户`；消费 → **默认不建边**，模板显式声明才建「付款账户↔商户」；提现/充值 → 不建边。
- 别名：本方户名、对方户名 → `kind='户名'`（挂账户）。
- 属性：四列 `属性:*` → 对应账户实体的 `attrs`。
- 备注：原文进 `extras`（键=`备注`），**不建 `remark` 列**（06 §5）。预处理只做三件：原文逐字保留、保住 `##` 结构、`UTF8#` 解码；**不判用途、不贴标签**（§1.1.1、`06` §6.7）。用途/商户由二期在**内核翻译层**入库时判定（`06` §6.1）。
- 无对手行：仍可产卡片，只写本方参与者；不建边；`依据:判定规则=无对手`。
- 畸形账号（含 `*` 或位数不足）：**不建账户实体**，只留 `mention_text`；不写属性；告警。

**闸门**（03 §8.2）：

| 检查项 | 阈值 |
|---|---|
| 查询账号非空 | 100% |
| 借贷标志合法（借/贷） | 100% |
| 金额可解析 | 100% |
| 时间可解析且是合法时刻 | 99% |
| 方向与本方一致 | 98% |
| 银行卡号与开户行成对 | 100%（反向「有行无卡」逐行告警，不拒收） |
| 收款方开户人可分类（个人/企业） | 100% |

**守恒对账**：行数、借/贷金额合计、五类对手条数、户名覆盖数、名册条目数。实测基线：699 行、借 30,412.92、贷 18,143.92。

**坑**：时区按 `+08:00`；标准列不留 `-`；`对方来源列` 必写；一个账号一个开户人是前提，出现一名多号要告警而不是取第一行。

### 4.2 支付宝流水 ⚠️（无样本，列名待校准）

**输入必需列（常见形态）**：`支付宝交易号`、`交易创建时间`、`付款时间`、`交易金额`、`收/支`、`交易对方`、`对方账号`、`商品名称`、`交易状态`、`备注`。退款/关闭单独有状态列。

**处理动作**：

1. **方向**：`收入`→收，`支出`→付，`不计收支`单列，不并入收/付。
2. **时间**：`付款时间`作为发生时间；`交易创建时间`进 extras；精度到秒。
3. **金额**：实付金额为准；订单金额、退款金额分别进 extras，不相互抵减。
4. **对方**：`对方账号`可能是邮箱/手机号/淘宝账号，**不能一律当银行账户**；按形状与 `交易对方` 判断实体类型（账户/虚拟身份/号码/组织/地点）。
5. **商户**：`商品名称`不等于商户名；商户名优先取 `交易对方`/`商家名称`，取不到就留空，不硬编。
6. **交易号去重**：同一交易号跨行重复只保留一条；退款行与原交易行分开，不合并。
7. **内部流转**：余额宝/花呗/提现到卡等，对方可能是本人；按「对方账号=本方账号」判自流转，不建自环边。

**标准列**：与微信同一套，另加 `交易号`、`交易状态`、`商品名称`、`订单金额(元)`、`退款金额(元)`；后四者按 extras 落库。

**闸门（草案）**：交易号非空 100%、金额可解析 100%、方向合法 100%、时间可解析 99%、状态可识别 100%。**阈值需用真实样本校准后再定。**

**坑**：导出文件编码/表头多行；`收/支` 有「不计收支」第三种值；退款可能以负数出现；对方账号形状多样。

### 4.3 银行流水 ⚠️（无样本，列名待校准）

**输入必需列**：`交易日期/交易时间`、`交易金额`、`借贷标志`（或 `收付标志`）、`余额`、`对方账号`、`对方户名`、`本方账号`、`本方户名`、`摘要/用途`、`流水号`。开户行可能在本方列或表头。

**处理动作**：

1. **方向**：有借贷标志就用标志；只有带符号金额时，按符号判方向并取绝对值，同时告警「方向由符号推断」。
2. **余额连续性**：按时间排序后核 `上一条余额 ± 本笔金额 = 本条余额`。一期作为**告警**，不作为拒收闸（很多银行导出缺余额或跨行合并）。
3. **对方账号**：可能是卡号/账号，可能带银行名、空格、横线；归一化去空格横线，**不补位、不截取**。
4. **对手户名**：原文照抄；不要把「XX银行XX支行」当户名。
5. **摘要/用途**：原文进 `备注` 列（落库时进 `extras`）；不要把摘要里的「转账/消费」当交易类型列。
6. **内部转账**：本方与对方账号相同 → 自流转，不建自环边。
7. **冲正/退款/手续费**：单独标记（`依据:业务类型`），不与原交易合并；手续费行可能无对方。

**标准列**：与微信同一套；另加 `流水号`、`依据:业务类型`；本方开户行用 `属性:本方:开户行` 表达。

**闸门（草案）**：金额可解析 100%、时间可解析 99%、借贷标志合法 100%、本方账号非空 100%、流水号唯一（同文件内）100%。

**坑**：不同银行列序/表头差异大，优先走「数据源档案」而不是写死；金额千分位；日期格式多样；对方账号为空的行（利息、手续费）不能当「无对手」拒收；跨行清算行不是真实对手。

### 4.4 话单 ⚠️（无真实样本，01 已登记缺口）

**输入必需列**：`主叫号码`、`被叫号码`、`通话开始时间`、`通话时长`、`通话类型`。可选：`通话地点/基站`、`费用`、`对方归属地`。

**处理动作**：

1. **角色固定**：主叫=caller，被叫=callee，不做相对角色判断。
2. **时长**：`HH:MM:SS`、`MM:SS`、纯秒数都要转成秒；短信/上网记录没有时长，留空。
3. **时间**：统一 UTC+8；精度到秒。
4. **通话类型**：语音/短信/上网等进 extras；不要把短信行套上通话时长。
5. **地点**：有基站/通话地点时，作为参与者的 `role='地点'`；**01 P3 参与者表落地前，地点只进 extras 并在缺口里说明**，不要生成假的地点实体。
6. **去重**：同一通话在双方导出里各出现一次时，**不自动合并**（同 01 D2 的跨源重复口径），出候选。

**标准列**：`行号`、`主叫号码`、`被叫号码`、`发生时间`（通话开始）、`发生时间原文`、`时间精度`、`通话时长(秒)`、`通话类型`、`通话地点`、`费用(元)`、`备注`、`依据:规则`、`依据:告警`。`通话开始时间` 原文留在原始列。

**落库**：`caller/callee/started_at/duration_sec`；事件 `type=通话`；参与者角色 `主叫/被叫`；关系 `号码 --通话--> 号码`（`times`、`first_at/last_at` 汇总）。

**闸门（草案）**：主叫/被叫非空 100%、时间可解析 99%、语音行时长可解析 100%、号码形状合法率 95%。

**坑**：`+86`、分机、短号、国际号码；隐私号/虚拟号（实体 `号码`，subtype 虚拟号，不与人焊接）；同一号码多运营商；归属地不是身份；基站位置不精确，不能当住址。

### 4.5 住宿登记 ⚠️（无样本；需要多行合成规则）

**输入必需列**：`姓名`、`证件号`、`入住时间`、`退房时间`、`宾馆名称`；可选 `房号`、`同住人`、`宾馆地址`、`金额`。

**处理动作**：

1. **一次住宿 = 一张卡**：入住行 + 退房行 + 同住人行要合成一张；**模板表达不了多行合成，必须走代码规则**（01 §4.7.7）。
2. **区间事件**：`occurred_at=发生时间（入住）`，`occurred_end=结束时间（退房）`；缺退房时间 ⇒ 开区间，`case_event.attrs.时间形态=开区间`，**不编造结束时间**。
3. **主体**：有证件号 → 人实体（强标识）；只有姓名 → 只留 `mention_text`，不做姓名模糊匹配。
4. **同住人**：每个同住人一条参与者（`role='同住人'`）；同住关系可建 `同行` 边，但必须显式声明。
5. **宾馆**：能指认物理场所 → `地点`；连锁品牌/公司 → `组织`；地址层级全存（省→市→县→街道→社区→街路巷→建筑物→单元房屋）。
6. **房号**：进 `attrs`（不参与过滤）；若以后出现「按房号找」再升级为独立列。

**标准列**：`行号`、`入住人姓名`、`入住人证件号`、`同住人姓名`、`同住人证件号`、`宾馆名称`、`宾馆地址`、`房号`、`发生时间`（入住）、`结束时间`（退房）、`发生时间原文`、`时间精度`、`金额(元)`、`备注`、`依据:规则`、`依据:告警`。`入住时间`/`退房时间` 原文留在原始列。

**落库**：事件 `type=住宿`；`occurred_at=发生时间`、`occurred_end=结束时间`；参与者 人 `ordinal=0`（入住人）、同住人、地点（宾馆）；`case_event.attrs={房号}`；别名 `kind='证件号'`/`'姓名'`；地址写 `case_entity_alias kind='地址'`（八级全存）。

**闸门（草案）**：入住≤退房、入住人可识别（证件号或姓名至少一）、宾馆名称非空、时间可解析 99%。

**坑**：入住/退房跨天；换房产生多行；同住人多个；未成年人；宾馆名称写法不一（全称/简称/后缀）；地址只存到街道会丢层级；`(个人)` 之类占位不是姓名。

### 4.6 火车 / 飞机 ⚠️（无样本；需要多行合成规则）

**输入必需列**：`乘客姓名`、`证件号`、`车次/航班号`、`出发站/机场`、`到达站/机场`、`出发时间`、`到达时间`；可选 `座位号`、`票号/订单号`、`同行人`、`金额`。

**处理动作**：

1. **区间事件**：`occurred_at=发生时间（出发）`，`occurred_end=结束时间（到达）`；跨日要保留日期，不能只取时刻。
2. **班次是实体**：`车次/航班号` 建成 `物品` 实体（canonical=`G1234`），参与者 `role='班次'`；不要塞进 `attrs`，否则「同一班次还有谁」查不了（01 §3.5 缝 3）。
3. **出发地/到达地是两个地点**：参与者两行，`role='出发地'` / `'到达地'`。
4. **同行人**：同一订单/票号的多名乘客可合成一张事件，每人一条参与者；也可建 `同行` 边，但必须显式声明。
5. **座位号/票号**：进 `case_event.attrs`；票号用于去重，不进卡片摘要。
6. **退票/改签**：单独标记，不与原行程合并。

**标准列**：`行号`、`乘客姓名`、`乘客证件号`、`同行人`、`班次`、`出发地`、`到达地`、`发生时间`（出发）、`结束时间`（到达）、`发生时间原文`、`时间精度`、`座位号`、`票号`、`金额(元)`、`备注`、`依据:规则`、`依据:告警`。`出发时间`/`到达时间` 原文留在原始列。

**落库**：事件 `type=乘车/乘机`；`occurred_at=发生时间`、`occurred_end=结束时间`；参与者 人 `ordinal=0`、同行人、出发地、到达地、班次；`case_event.attrs={座位号,票号}`；关系 `同行`（显式声明才建）。

**闸门（草案）**：出发≤到达、班次格式合法、出发地≠到达地、乘客可识别、时间可解析 99%。

**坑**：车次跨日；机场/车站全称/简称/三字码；同一班次不同日期不是同一事件；国际航班时区；改签后原票作废但记录仍在。

### 4.7 订餐 / 扫码 / 消费 ⚠️（无样本）

**输入必需列**：`下单人姓名/号码`、`商户名称`、`金额`、`下单时间`（或支付时间）；可选 `商户地址`、`订单号`、`联系电话`、`商品名称`。

**处理动作**：

1. **事件类型**：`消费`（订餐/购物）或 `支付`（扫码）；不要把所有行都叫「转账」。
2. **主体**：下单人姓名/号码 → 人/号码；有支付账号时，付款账户也是主体（可两者都写，角色区分）。
3. **商户**：有物理场所 → `地点`；公司/品牌 → `组织`；`商户名称` 是平台店铺名时，不能直接当公司名，能取到营业执照名再升级。
4. **地址**：配送地址 ≠ 消费地点，必须分开：`商户地址` 进地点角色，`收货地址` 进 extras，不混用。
5. **金额**：实付金额为准；订单金额、优惠金额进 extras，不相互抵减。
6. **订单号**：去重键；同一订单多行（多个商品）合成一张卡，走代码规则。

**标准列**：`行号`、`下单人姓名`、`下单人号码`、`商户名称`、`商户类型`、`商户地址`、`订单号`、`金额(元)`（实付）、`发生时间`（下单或支付）、`发生时间原文`、`时间精度`、`对方账号`、`备注`、`依据:规则`、`依据:告警`；`订单金额(元)`、`退款金额(元)`、`商品` 进 extras，不相互抵减。

**落库**：事件 `type=消费/支付`；`occurred_at=发生时间`、`amount=金额`；参与者 人/号码 `ordinal=0`、商户（地点/组织）、地址（地点）；`case_event.attrs={订单号,商品}`；关系**默认不建**，模板显式声明「付款账户→商户」时才建（有支付账号时）。

**闸门（草案）**：金额可解析 100%、时间可解析 99%、商户或地址至少一、订单号唯一（同文件内）95%。

**坑**：退款/取消；平台补贴导致实付≠订单；商户名是店铺名不是公司；外卖地址不是消费地点；扫码支付的对方可能是个人账户。

### 4.8 笔录 / 询问 / 讯问等文本 ⚠️（不走表格副本）

文本材料不走「标准副本」流水线，走现有 `跑文本` 抽取。预处理（如果有）只做分块/清洗，不做实体合并。要形成的字段：

| 产出 | 字段 | 要求 |
|---|---|---|
| 实体 | 类型 / 规范值 / 别名 / 细类 | 人、号码、账户、虚拟身份、车辆、物品、地点、组织 |
| 别名 | `kind` / `value` / `raw_value` / 出处 | 姓名、证件号、手机号、账号；原文写法必须保留 |
| 关系 | 类型 / 两端 / 认定依据 | 类型只能用 7 类：通话/转账/实名登记/实际使用/同案/持有/同行；认定依据写 `basis` 原文或计算来源，缺依据不入库 |
| 事件 | 类型 / 时间 / 参与者 / 摘要 / 出处 | `occurred_raw` 原文保留；精度按原文判 |
| 出处 | `locator` 按材料类型给可回原文的位置（PDF 页码/段落、文本起止偏移等） | 与 01 的 `locator` 口径一致，能回到原文位置 |

**硬要求**：原文不改写、不脱敏；模型输出必须带 `mention_text`；同名不合并；置信度低进待确认；人工确认后才转正。

- 图片 / 视频 / 物证照：只登记材料，不做 OCR / 识别；
- docx / pdf / pptx：只做文本抽取，不做表格结构化；
- 产物（本平台生成的文件）：不解析、不推进解析状态（0031 的硬边界）；
- 跨文件实体归并、跨文件账号名册、事件合并：属内核实体层，不是预处理。

## 5. 实体属性专项（`case_entity.attrs`）

### 5.1 存哪、什么形状

**不建表、不加列**，用现成的 `case_entity.attrs jsonb`（`0031_case_fact_layer.sql:76`）。形状固定：

```json
{
  "开户行":   [{ "值": "招商银行", "出处": "mat_x#Sheet1#12" }],
  "银行卡号": [{ "值": "6214830012341234", "出处": "mat_x#Sheet1#12" }],
  "证件号":   [{ "值": "330501199001011234", "出处": "mat_x#Sheet1#12" }]
}
```

规则：

1. 每个键的值是**数组**；元素固定 `值` + `出处`；
2. `出处` = `<material_id>#<工作表名>#<行号>`，与 `case_citation` 行级 id 同形；
3. 同键同值只留一条，出处取**首次读到该值**的行；
4. 同键不同值**并存**，一条不删；
5. 值明文原文，不掩码、不格式化；
6. `subtype` 是系统保留键（现有写入点只写细类），**skill 不得产出 `属性:*:subtype`**。

### 5.2 命名与词表

```
属性:<归属>:<键>
```

- **归属只有两个值**：`对方`、`本方`，决定挂到对手实体（`counterparty`）还是本方实体（`ownerAccount`）。**当前规范只覆盖资金流水这类有「对手/本方」两端的行**；话单、住宿、出行没有 `counterparty/ownerAccount` 语义，**先不要自造第三种归属**，等规范扩展。
- **键必须来自受控词表**，skill 负责把同义词归一成词表叶子词；入库端不做同义词匹配。
- 词表放独立小文件（建议 `case-attribute-registry.ts`），**不混进 `case-field-registry.ts`**，否则属性列会参与字段识别与表类型投票。

### 5.3 建议词表（分批，先小后大）

**v1 必做（05 已定）**：

| 键 | 挂哪 | 说明 | 示例 |
|---|---|---|---|
| `开户行` | 账户 | 银行卡的开户银行 | 招商银行 |
| `银行卡号` | 账户 | 该实体名下的卡号 | 6214… |
| `证件号` | 账户 | 户主/登记证件号 | 3305… |

**v1.1 建议扩展（需拍板后进词表）**：

| 实体类型 | 建议键 | 说明 |
|---|---|---|
| 账户 | `账户性质` | 个人/企业（来自 `主体类型`） |
| 账户 | `账户类型` | 借记卡/信用卡/对公账户（有来源才写） |
| 账户 | `开户日期` | 原文有才写 |
| 账户 | `登记证件号` | 户主证件号；与 `证件号` 二选一，避免语义混 |
| 人 | `证件类型` | 身份证/护照/… |
| 人 | `性别` / `出生日期` | 有来源才写，不从身份证号反推 |
| 人 | `户籍地` / `现住址` | 地址按八级存 |
| 号码 | `运营商` / `归属地` | 只写来源给的，不按号段猜 |
| 号码 | `号码类型` | 手机/固话/虚拟号/短号 |
| 车辆 | `车牌号` / `车辆类型` / `品牌型号` / `车架号` | 车牌号也是强标识，注意与人/账户区分 |
| 地点 | `地址层级` | 省/市/县/区/乡镇街道/社区/街路巷/建筑物/单元房屋（八级全存） |
| 地点 | `场所类型` | 宾馆/餐厅/超市/加油站… |
| 组织 | `统一社会信用代码` / `注册地址` / `联系电话` | 有来源才写 |
| 物品 | `品牌` / `型号` / `序列号` | 班次是实体，不是物品属性 |
| 虚拟身份 | `平台` / `账号` / `昵称` / `绑定手机号` | 平台名要受控（微信/支付宝/QQ…） |

> 扩展词表是**建议**，不是既成事实。词表一旦定下，skill 产出的键必须全部在内；出现词表外的键，**不要写库**，进告警与 `extras`。

### 5.4 归属怎么判

- 资金行：`属性:对方:开户行` 挂到对手账户；`属性:本方:开户行` 挂到本方账户。
- 话单行：**v1 不写属性**。`归属地`/`运营商` 若将来要挂到号码实体，需先扩展归属定义（主叫/被叫），不能直接套 `对方/本方`。
- 一行同时有对方卡号和开户行：两者**共享同一个出处**，读侧按出处配对。
- 提现/充值：对方账号 = 本方账号，卡号/开户行仍写 `属性:对方:*`？**不**——此时对方就是本方，统一写 `属性:本方:*`，避免同一张卡挂到两个实体。预处理阶段按「对方账号是否等于本方账号」归一归属。

### 5.5 什么能写、什么不能写

**能写**：

- 原文里直接读到的开户行、卡号、证件号、运营商、车型等；
- 同一次观察里成对出现的卡号 + 开户行（共享出处）。

> 别名（姓名/证件号/手机号/账号/车牌/地址）走 `case_entity_alias`，**不写进 attrs**；两者不是同一个槽。

**不能写**：

| 别写 | 去哪 |
|---|---|
| 备注、用途、商户、交易类型 | 备注原文在 `case_fact_row.extras`；用途/商户/交易类型属事件层；都不是实体属性 |
| 户名（账户登记在谁名下） | `case_entity_alias kind='户名'`；不是人实体、不是 attrs |
| 由身份证号反推的性别/生日 | 除非来源明确给出，否则不写 |
| 由号段猜的归属地/运营商 | 不写；只写来源给的 |
| 推断的「这个人有几个账户」「主要活动地」 | 不写；这是查询/分析结论，不是属性 |
| 来源自带掩码或位数不足的账号 | **不写**；只留 `mention_text` + 告警（01 §4.0.5 坑 1） |
| `-`、`无`、`未知`、`(个人)` 这类占位 | 不写；空值不写 |
| 聚合值（合计、笔数、首末时间） | 不写；关系表或查询算 |
| 实体 id、内部编码 | 不写；由内核生成 |

### 5.6 冲突、去重与配对

1. **同键不同值并存**：甲材料说招商银行、乙材料说建设银行 ⇒ 两条都在，谁也别覆盖谁。读侧回答「有两份材料分别给出…」。
2. **同键同值去重**：只留一条，保留首次出处；不要每行都追加一条把库撑大。
3. **卡号与开户行配对**：同一次观察写入的两者共享出处；如果一份材料只有卡号、另一份只有开户行，**不要用「最新一条」硬配**，让读侧按出处展示。
4. **合并语义必须是「读 → 追加 → 写」**：现有 `attrs || excluded.attrs` 是键级覆盖，会静默丢证据，实现时必须改（`case-fact-store.ts:73`）。
5. **属性没有独立信任态**：现在不标「已确认/已排除」；需要逐条处置时再评估独立表，不要提前建。

### 5.7 校验与验收

- [ ] 属性列不出现在「待确认」弹窗与「未认出」清单；
- [ ] `query_entities` 返回的 `attrs` 含 `开户行`、`银行卡号`，且带 `出处`；
- [ ] 「这个账户的开户行是什么」能答出值，并能按出处回查原行；
- [ ] 两份材料对同一账户给出不同开户行时，两条都在；
- [ ] 同一值在多行重复出现时只留一条；
- [ ] 原始列原文仍完整存在于 `extras`；
- [ ] 掩码/畸形账号没有进 `attrs`、没有建实体；
- [ ] `subtype` 没有被 skill 当成属性写。

## 7. 闸门、守恒与变异验证

### 7.1 两道闸

**表头闸**：必需列齐全。表头行不要求在第一行，在前 10 行里找命中必需列最多的一行；缺列时报「缺少必需列：X」，不要误报「找不到表头」。

**值验证闸**：逐项检查，任一不过整份拒收。通用检查项：

| 检查 | 含义 | 阈值（按类型定） |
|---|---|---|
| 主体标识非空 | 本方账号/主叫/入住人/乘客 | 100% |
| 方向合法 | 收/付、借/贷 | 100% |
| 金额可解析 | 去千分位、货币符号后可转 numeric | 100% |
| 时间可解析 | 合法时刻 | 99% |
| 绑定关系 | 卡号与开户行成对、方向与本方一致 | 98–100% |
| 关键分类可判 | 个人/企业、实体类型 | 100% |

**闸门必须被证明会拦**：用变异样本验证——改必需列名、把方向改成第三值、破坏卡行成对、把金额改成文本；每次都应拒收、退出码非 0、只出拒收报告、不产标准明细。

### 7.2 守恒对账

每份材料至少核：

- 行数守恒（原始有效行 = 标准明细行 + 跳过行，跳过原因可解释）；
- 金额守恒（借/收合计、贷/付合计与原始列一致）；
- 分类条数守恒（转账/提现/消费/充值/无对手等条数与规则分布一致）；
- 户名覆盖（能补全的补全，补不了的逐条解释）；
- 绑定守恒（有卡必有行、有行无卡逐行告警）；
- 标准列无 `-`、无掩码账号被当实体。

### 7.3 金标准集

每类数据至少一份「原件 + 期望标准副本」，作为 skill 的回归基线；规则改动必须跑金标准集，不能只看「这次跑通了」。金标准集的期望副本要包含：标准列、判定依据列、告警、拒收/通过结论。

**一份住宿登记进来，标准列至少要有**：

`行号`、`入住人姓名`、`入住人证件号`、`同住人姓名`、`同住人证件号`、`宾馆名称`、`宾馆地址`、`房号`、`发生时间`、`结束时间`、`时间精度`、`金额(元)`、`备注`、`依据:规则`、`依据:告警`

**实体属性只记三件事**：值是什么、挂给谁、哪一行读到的。其余（用途、商户、备注、推断）都不进 `attrs`。
