### ⚠️ 第一优先：网关本身（其余项的前置）

- [ ] **T014 实现网关（Auth 服务的 HTTP 面）**：登录 HTTP 端点 + JWT 验签 + httpOnly Cookie 下发 +
  注入 `X-User-ID` + 错误呈现。[无依赖，但**是 T015/T016 的前置**]
  [出参：浏览器带 Cookie 访问 → 网关验签 → 注入头 → opencode 认身份]
  - 形态待定：`002-auth-account/plan.md` R3 倾向「网关模块内嵌」，未定案。
  - ✅ **已裁定（2026-09-29，002 收尾）：走「认链路不可达」，spec `FR-002` 的措辞已同步改掉**
    原「由网关**验签**注入」。依据：`X-User-ID` 是**明文头、不是凭证**
    （`packages/opencode/src/server/user-identity.ts` 顶部有言），且 002 交的中间件
    （`middleware/user-identity.ts`）**只查头是否存在、既不剥离也不校验**——
    所以「不可伪造」**只能**由链路保证。本 task 据此多出两项硬要求：
    ① **网关注入前必须剥离客户端传入的 `X-User-ID`**（是覆盖，不是拼接）——
      否则够得着网关的用户可以自填身份；② **内核端口只对网关可达**（回环绑定 / 网络策略），
      并写进部署文档。**可选加固**（网关注入时加签名字头 / 两段间 mTLS）**不在 003 范围**。
    > 为什么不做验签：它要两段共享密钥的分发与轮转，而本阶段两段同机、端口对用户不可达——
    > 收益抵不上密钥管理成本。将来若内核端口的暴露面变大，再回来加。
    > ⚠️ 别再把它读成「已经有人验签了」：当前**没有任何验签**，安全全押在链路可达性上。
  - ⚠️ 002 的车牌门**默认关**（`OPENHIVE_REQUIRE_USER_ID` 未设即直通）。网关上线时置 `1` 打开。
  - 🔑 **`AUTH_JWT_SECRET` 必须 ≥ 32 字符**（002 评审 I7 加的地板，依据 RFC 7518 §3.2）。
    002 只交了**检查**（`packages/auth/src/token.ts` 的 `jwtSecret`，短了就抛 `WeakJwtSecretError`），
    而**全仓库没有任何生产代码调用它**——执行点就在这里。网关要做两件事：
    ① 在**启动路径**上调一次（`jwtSecret(process.env)`）并留着结果，让弱密钥当场起不来、
    而不是等到签发时才 500；② 把「≥32 字符」写进部署文档 / `.env.example`，
    别让运维靠报错反推。
    > 这条与上面 I2 脱敏是同一种移交：**003 只承诺「别绕过它」是不够的，得知道它存在**。

- [ ] **T019 引导首个管理员**（002 评审 I1）[无依赖]
