# 资产内容编辑与悬停文案 — 设计

> 状态：待评审
> 日期：2026-10-31
> 涉及：`packages/asset-service`、`packages/opencode/src/server/openhive`、`packages/app/src/ai-assets`、`packages/app/src/project`、`packages/auth/src/migrations`

## 1. 问题

三件事，同一个根：**资产的可读文案没有写入路径，悬停还读错了地方。**

1. **悬停显示英文**。左栏项目管理 → 技能 Tab，鼠标移到技能卡片上弹出的说明，取自 SKILL.md 的 frontmatter `description`。多数技能的 SKILL.md 是英文写的，用英文原文弹出，同事读不懂。
2. **介绍改不了**。详情页「介绍」读 `auth.asset.description`，这列只在建草稿那一次写入（`service.ts:218`），之后全仓没有任何 UPDATE。
3. **注意事项没有字段**。「注意事项」Tab 里那条黄框是产品级硬性提示（FR-003），下面那句「该资产尚未填写专属注意事项」是写死的空态——**没有地方可填**，因为它根本没有对应的列。

## 2. 本次范围

**做：**

- 新增两个字段：功能描述（`summary`）、注意事项（`precautions`）
- 三个字段（介绍 / 功能描述 / 注意事项）的内容编辑入口
- 悬停文案改为读「功能描述」

**不做（明确排除，避免误解为遗漏）：**

- **版本历史**。见 §3 裁定 5——它的写入点（`start_iteration`）在产品里不存在，现在建表就是建一张永远不长行的表。版本 Tab 维持只读现状。
- 技能名称、标签、分类、图标的编辑。不在本次范围。
- 富文本 / Markdown 渲染。三个字段都是纯文本，按纯文本显示。

## 3. 决策记录

| # | 决策 | 理由 |
|---|---|---|
| 1 | 新增独立「功能描述」字段，与「介绍」并存 | 介绍写长（功能 + 怎么用 + 涉及哪些文件），功能描述写一句话专供悬停 |
| 2 | 迁移时把现有 `description` 整段复制到 `summary` | 现网 9 条资产的介绍本来就是一句话中文（26–60 字）。回填后上线当天悬停即为中文，不必人工补录 9 条 |
| 3 | 编辑权限按已有 `write` 权限判 | 复用 `effectivePermissions()`（`authorization.ts:283`），不新增权限概念。**今天 `write` 只来自作者身份**——生产代码里没有任何授予 `write` 的路径（`grantAssetToGroup` 唯一的生产调用写死 `perm: "read"`，`authorization.ts:229`） |
| 4 | 每个 Tab 内各自一个「编辑」按钮 | 一次只提交一个字段，失败不影响其他栏；不需要草稿态与整体校验 |
| 5 | 版本历史单独立项，本轮不动 | `start_iteration` 是唯一 +1 的动作，产品里**没有入口**，只有测试在调。现网 9 条资产 `version` 全是 1。建表只会得到一行「v1 初始导入」，版本号也永不变化 |

## 4. 数据模型

### 4.1 迁移 `0026_asset_content_fields.sql`

```sql
ALTER TABLE auth.asset ADD COLUMN summary text NOT NULL DEFAULT '';
--> statement-breakpoint
ALTER TABLE auth.asset ADD COLUMN precautions text NOT NULL DEFAULT '';
--> statement-breakpoint
-- 回填：现有「介绍」整段复制到「功能描述」（裁定 2）
UPDATE auth.asset SET summary = description WHERE summary = '';
```

`.down.sql` 对称删除两列。

用 `NOT NULL DEFAULT ''` 而不是可空：空串与「没填」在这三个字段上语义相同，多一种 null 态会让前端多一个分支，没有收益。

### 4.2 类型与写入

- `metadata.ts` 的 `AssetMetadata` 加 `summary: string`、`precautions: string`
- `asset.ts` 的 `COLUMNS`、`toMetadata()`、`insertAsset()` 同步
- `service.ts` 的 `CreateDraftAssetInput` **不加**这两个字段：建草稿时不传，走默认空串。之后由编辑入口填。

### 4.3 长度上限

| 字段 | 上限 | 依据 |
|---|---|---|
| 介绍 `description` | 2000 字 | 长文：功能 + 用法 + 文件 |
| 功能描述 `summary` | 200 字 | 悬停浮层 260px 宽，超过就读不完 |
| 注意事项 `precautions` | 1000 字 | 多条注意事项 |

超限返回 400，消息里带上限值。校验放在 `asset-service`（与 `validateAssetMetadata` 同一层），路由只负责把错误翻译成 400。

## 5. 后端接口

`PATCH /openhive/assets/:id`，加在 `packages/opencode/src/server/openhive/assets.ts`（与现有 `GET /openhive/assets` 同文件）。

请求体（部分更新，带哪个改哪个）：

```json
{ "description": "...", "summary": "...", "precautions": "..." }
```

| 步骤 | 实现 |
|---|---|
| 身份 | 复用 `favorites.ts` 的 cookie 取用户 |
| 找资产 | `assetById()`，没有 → 404 |
| 判权限 | `effectivePermissions(viewer, asset, grants).has("write")`，没有 → **403** |
| 授权先于校验 | 与 `governance-assets.ts:367` 同一纪律（`#004-09`）：**有资产但无权 → 403 先于长度校验的 400**。不让人靠「400 还是 403」的差别判断自己的请求内容是否合法。（资产不存在一律 404，与 `favorites.ts:140` 同一口径——不存在是存在性问题，不是权限问题。） |
| 校验 | 长度上限、非字符串类型 |
| 写入 | 新函数 `updateAssetContent(db, id, patch)`：只写这三个内容列 + `updated_at = now`，**不碰 `status` / `version`** |
| 回包 | 写入后读回完整 `AssetMetadata`（与收藏接口同取向：回**读回来的真状态**，不回「我送了什么」） |

`updateAssetContent` 放在 `asset.ts`，与 `updateAssetLifecycle` 并列。两者互不覆盖：前者只写内容列，后者只写生命周期列——这一点在 `asset.ts:424` 的注释里已经声明过，本次是把它兑现。

### 5.1 「有没有写权限」怎么告知前端

`GET /openhive/assets` 的响应加一个平行数组 `writableIds: string[]`——**本页里我可写的资产 id**。

与 `favoritedIds` 完全同构（`assets.ts` 文件头 §「带『我收藏了哪些』」已论证过这个形状）：不往 `AssetMetadata` 上加 per-user 字段，因为那份类型与治理后台共用，加了会让另一个出口回假值。

计算方式和 `favoritedIds` 一样：在本页资产上逐个判一遍，授权行用 `grantsFor()` **一次取全**再内存匹配。相比现状会增加 1 条 SQL（`grantsFor`），但**不是按资产逐条查**——页大小与查询数无关。

## 6. 悬停文案取值规则

`映射内核清单()`（`project-assets.ts:296`）现在只查「assetId → 标题」一个 map。扩成两个：

```
assetId → 资产名（现有）
assetId → 功能描述 summary（新增）
```

回包里的 `内核技能.description` 按以下顺序取值：

1. 库里这条资产的 `summary` 非空 → 用它
2. 否则 → 内核给的 SKILL.md `description`（现状）
3. 两者都没有 → 前端不弹浮层（`capability-panel.tsx:127` 已有此行为，不改）

**项目自带的技能（库里没有这条记录）永远走第 2 档**，仍是 SKILL.md 原文。这是数据边界不是缺陷：没有资产记录就没有功能描述可读。

`capability-source.ts:89` 与 `capability-panel.tsx:239/253` 都不改——它们只是搬运，取值在服务端完成。

## 7. 前端

### 7.1 详情页三个 Tab 加编辑

`asset-detail.tsx`：介绍 / 注意事项 / 功能描述 三个面板各加一个「编辑」按钮。

- 按钮**只在 `writableIds` 含本资产时才渲染**。没接线就不渲染，是这个文件已有的纪律（`asset-detail.tsx:34`）。
- 点击后该面板切成 textarea + 「保存」「取消」。
- 保存成功：用接口回来的 `AssetMetadata` 就地更新，退出编辑态。
- 保存失败：红字就地显示错误，**textarea 内容保留**，不清空不退出——用户敲的字不能因为一次网络失败消失。
- 取消：丢弃编辑内容，回到只读态。

「注意事项」Tab 保持不变的是：产品级黄框（FR-003 硬性要求）**始终显示**，资产专属注意事项显示在它下面；为空时才显示「该资产尚未填写专属注意事项」。

### 7.2 版本 Tab

**不动。** 保持只读，那句「暂无变更说明」原样保留——等版本历史立项时再一起处理。

## 9. 残留与风险

1. **回填后「介绍」与「功能描述」内容完全相同**（现网 9 条）。要等作者各自把介绍写长、功能描述改短，两者才会分开。这是裁定 2 的直接代价，不是 bug。
2. **项目自带的技能悬停仍是 SKILL.md 原文**（可能英文）。没有资产记录就没有可编辑的功能描述。
3. **`write` 权限今天等价于「仅作者本人」**。设计上支持授权 write 给别人，但生产代码没有任何授予入口。将来要开放协作编辑，需要先补授予入口——这件事不在本次范围。
4. **版本 Tab 维持只读且内容几乎恒为 v1**。见裁定 5，等版本历史立项。
5. **本次不动上游文件**。新路由、新函数都落在 fork 自有的 `server/openhive/` 与 `asset-service/` 内，符合「最小化与官方合并冲突」的第一号约束。
