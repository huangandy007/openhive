## 0. 一句话结论

明细表（`auth.case_fact_row`）**冻结，不再按数据类型加列**；新增一层**统一的「事实卡片」（事件）**，卡片引用实体、保留原文提及、带出处，作为跨类型分析（时空碰撞、串并、轨迹）的唯一基座。

## 1. 问题从哪来（实测证据）

### 1.1 库里看到的现象

对项目 `ab050e6c-dfdc-4659-b9e2-09a3d75b1390`（2026-11-09 只读查询）：

- 材料共 38 份：**35 份资金 + 3 份其他，零份话单**
- 20 份银行流水：行数、`amount`、`balance`、`started_at` 有值，但 `counterparty / counterparty_name / owner_account / direction` **全部为 NULL**
- 原文堆在 `extras`，键是原表头：`"查询账号": "6217995510035536514"`、`"交易对方账卡号": "1448061302"`、`"交易对方名称": "腾讯微保"`、`"借贷标志": "借"`
- 这些银行材料的 `parse_detail` 是 **NULL** —— 当前代码入库必写 `parse_detail.mapping`，故只可能来自旧版本内核

### 1.2 当前代码跑真文件的结果

用临时探针（`.superpowers/probe-all-bank.ts`，只读、离线、不走缓存、不调模型）逐份跑源文件：

| 数据 | 份数 | 认出的列 |
|---|---|---|
| 银行流水 | 20 | 7/7：`查询账号→ownerAccount`、`交易对方名称→counterpartyName`、`交易对方账卡号→counterparty`、交易金额、交易余额、`借贷标志→direction`、交易时间 |
| 财付通 | 15 | 6/6：`查询账号→ownerAccount`、交易金额、交易余额、交易时间、`借贷标志→direction`、`收款方的商户名称→counterpartyName` |

**结论：识别逻辑当前是对的，库里的 NULL 是旧内核留下的存量数据。**（真栈内核不热重载，改完源码不重启仍在跑旧版。）

### 1.3 订餐数据的实测（推翻了此前的口头结论）

用一份典型订餐表头 `订单号/下单时间/订单金额/收货人/联系电话/收货地址/商家名称/送达时间` 调 `候选字段集`：

```
候选字段 = startedAt, amount, balance, counterparty, counterpartyName,
           ownerAccount, direction, ownerName
```

- 该表被 `交易词` 正则（含「金额」）判成 **资金**；
- 订餐相关的五个字段 `address / merchant / contactPhone / personName / deliveredAt` **一个都不在候选集**；
- 因此这五列**当前认不出来**，只能以原表头进 `extras`（原文不丢，但没有规范键，跨材料统计做不了）。

## 2. 数据类型「列不完」→ 排除两条路

用户给出的事实：未来还有**住宿、火车、飞机、扫码**等轨迹类数据，且**根本列不完**。

因此排除：

- ❌ 每来一类数据就加一批列（表宽由业务类型数量决定）
- ❌ 一个类型建一张明细表（DDL 会追着业务跑）

## 3. 讨论中形成的核心判断

### 3.1 明细与分析的分离

| 层 | 职责 | 是否随类型增长 |
|---|---|---|
| 明细（`case_fact_row`） | 原文照抄，能回溯到「文件·表·行」 | **不增长**，新类型全进 `extras` |
| 卡片（事件） | 统一格式回答「谁/何时/何地/干什么/和谁/多少」 | 格式固定 |
| 实体（档案） | 认人：账号/号码/证号 → 同一个实体 ID | 类型有限 |

### 3.2 「固有字段」的正确含义

不是把业务字段固化，而是固化**警察永远会问的几个问题**：

```
谁？  什么时候？  在哪儿？  干了什么？  和谁？  多少钱？
```

来源无穷，问题有限。

### 3.3 原文与出处是两件事

- **每个值留原文**（不是把整份文件丢附件）：归一化改写过的值，原文必须还在
- **每条结论带出处**，精确到 `material_id + sheet + row_no`：法官要能一秒翻回那一格

### 3.4 卡片第二格存什么

```
实体ID  +  角色（入住人/付款方/主叫…）  +  该论元的原文提及（那一格的文字）
```

不是只存 ID，也不是只存文字：
- 只存文字 → 跨文件串不起来（现状困境）
- 只存 ID → 翻不回原文，不能当证据

### 3.5 已有「实体」开发不是白做

实库/代码盘点：

| 已有 | 状态 |
|---|---|
| `case_entity`（人/号码/账户/虚拟身份/车辆/物品/地点/组织，别名、信任态） | 正是「谁」这一轴 |
| `case_relation`（通话/转账/实名登记/实际使用/同案/持有/同行） | 正是「和谁」这一轴 |
| `case_event`（时间、参与者、摘要、信任态） | 「何时/干了什么」的雏形 |
| 实体清单、关系图（1～2 跳、≤50 节点）、实体档案页、告警、产物引用 | 读取端资产，数据补齐即活 |
| 合并实体、改信任态 | 已有 |

**真正的断点**：实体/关系/事件**只有一条写入路径** —— 文字材料的 AI 抽取（`packages/opencode/src/server/openhive/case-ingest.ts:627` `跑文本`）。表格明细只写 `case_fact_row`，一条实体/关系/事件都不写。

### 3.6 已知的四处不足（有据可查）

| 位置 | 问题 | 后果 |
|---|---|---|
| `packages/auth/src/migrations/0031_case_fact_layer.sql:116` | `case_relation.type` CHECK 写死 7 种 | 住宿/乘车/扫码要加类型就得改迁移 |
| `0031:154-172` | `case_event` 缺地点、金额、属性 | 住宿「住哪儿」、资金「多少钱」没处放 |
| 出处 | **表在、写入者缺**：`auth.case_citation` 已通用，`fact_type` 已含 `event`/`row`，但 `'row'` 至今**没有任何生产写入者**（`case-mcp-tools.ts:440` 自述） | 表格明细与事件都翻不回原文 |
| `participants text[]` | 参与者不区分角色，且存的是**规范值**不是实体 id | 分不清谁是嫌疑人、谁是被转账方；合并实体后引用会断 |

### 3.7 参与者的两处缺陷（2026-11-09 静态核实：读代码 + grep，未跑真栈）

| 位置 | 事实 | 后果 |
|---|---|---|
| `case-extract.ts:532` | 写进 `participants` 的是 `canonicalValue`（规范值） | 与 `case-entity-list.ts:105` 按 `canonical_value` 匹配一致，这一处自洽 |
| `case-propagation.ts:48` | 用 `entityId` 去匹配 `participants` 的元素 | 两处口径不同；除非规范值恰等于实体 id，否则匹配不到 ⇒ **实体被修正/排除后，「事件依据已变更」实际不生效**（`标依赖已变更` 的 events 计数恒为 0） |
| `case-merge.ts` | 全文不含 `case_event` / `participants`，合并只改关系两端 | 合并后，以被并入者规范值为参与者的事件**从主体时间线消失** |

三条指向同一个根因：**`participants` 用字符串存参与者——不是实体 id、没有角色、还要求每个读者自己对「存什么」的理解一致**。这正是新表 `case_event_participant` 要解决的问题。

## 4. 文献核对结果

### 4.1 这套东西正式的名字：事件中心知识图谱（EKG）

Guan et al., *What is Event Knowledge Graph: A Survey*（TKDE 2022）：

> EKG 有两类节点（事件、实体）和三类有向边（事件-事件、事件-实体、实体-实体）。事件-实体边的含义是**论元角色**。Rospocher et al. 2016 用 Action / participant / time / location 建模，对应（what, who, when, where）。
> 实体中心的 KG 是 EKG 的特例。

→ 卡片与实体**不是二选一**，是同一张图里的两类节点。

### 4.2 文献证实我们做对的

- 卡片 = 事件实例（节点），不是属性容器
- 论元必须引用实体，同时保留提及原文（mention-level provenance）
- 出处必须可回溯（W3C PROV：`wasDerivedFrom` / `wasGeneratedBy`）
- 时间分「发生/记录/入库」= 双时间（valid time / transaction time），`case_fact_row.time_type` 已踩对
- 认人要有优先级 + 时间约束：时间感知实体消解（Christen & Gayler, PAKDD 2013；TKDE 2018 隐式时间 ER；2025 年「disagreement decay」）

### 4.3 文献指出我们漏掉的

| 缺口 | 说明 | 后果 |
|---|---|---|
| **事件共指（Event Coreference）** | 同一次住宿在多份材料里出现，是同一事件不是两个 | 重复计数、图谱重复节点 |
| **论元补全（Argument Completion）** | 抽取常缺论元；补出来的必须与原文抽出的区分 | 分不清「原文没写」与「系统推断」 |
| **事件-事件关系** | 时序/因果/条件/主题（我们只做了事件-实体边） | 「案发前打了电话」只能临时排序 |

### 4.4 必须纠正的说法

- **出处不能由模型给**。*The Provenance Gap*（2026）的实证：前沿 LLM 生成的引用零可验证，连 LLM 当裁判都会把编造的引用判为有效。→ 出处必须由代码在抽取时按明细行主键绑定，模型碰不到。
- **可信度粒度不够**。业内做法是给每条知识打 `EXTRACTED / INFERRED / GENERATED`，并支持双时间窗、取代关系（SUPERSEDES）、以及明确输出「不确定」。
- **实体别名不能只是字符串集合**。属性会随时间演化（换号、改姓），别名要带**有效期**，否则同一个号码的不同机主会被合并成一个人。

### 4.5 与实战工具对照

- Palantir Gotham：对象图，人/组织/地点/设备/**事件**/文档都是节点，边是类型化关系，保留来源文档。
- 国内：专利 CN110688495B 提出「实体-关系-事件」模型；2023 年《Establishment Method of Knowledge Graphs for Public Security Cases》用「人、物、事、时间、位置」五要素。
- 警告：事件中心模型的通病是**事件节点增长极快、遍历变慢** → 不能把所有明细都变事件，要有门槛。

## 5. 校准后的卡片（三层）

```
第一层：事件本体
  干什么(what) │ 谁+角色(who) │ 何时-区间(when) │ 何地-实体(where)
  │ 涉及谁+角色 │ 金额/数量 │ 类型专属属性

第二层：事件之间的关系
  时序（先/后/同时） │ 因果 │ 同一事件（共指）

第三层：溯源与信任（独立层）
  来源：明细行（文件·表·行）+ 原文片段
  方式：原文抽取 / 推断 / 模型生成
  时间：有效时间窗 + 记录时间（双时间）
  更正：取代关系（SUPERSEDES，不覆盖）
  信任：自动抽取 / 已确认 / 已修正 / 存疑 / 已排除，允许「不确定」
```

## 6. 待定问题（下一轮必须定的）

1. **地点精确到什么级别算「同一个地方」** —— 宾馆名 / 地址 / 行政区？直接决定「案发地周边住过」能不能查出来。
2. **事件粒度** —— 一条明细 = 一张卡片？住宿的「入住」与「退房」是一张卡片的时间两端，还是两张？
3. **事件共指判据** —— 同源重复 与 跨源同一事件，判定标准不同，要分别定。
4. **事件间关系做到哪一步** —— 建议先只做「时序」，因果不做（靠模型猜，最容易错且无法验证）。
5. **认人的优先级与冲突处理** —— 身份证 > 手机号 > 账号 > 姓名；无证号时怎么算、同号换机主怎么拆。
