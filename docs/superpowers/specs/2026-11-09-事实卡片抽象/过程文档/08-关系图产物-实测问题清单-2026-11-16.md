## P0-1 手动加节点被「同名复用」吞掉（最严重）

### 现象

双击空白加节点，画布上出现几个圆；关掉标签页重开，多出来的全没了。

### 复现与实测

真栈 `:3010`，文件 `111.hgraph`：

- 连续双击空白 3 次。请求里是 3 条 `加节点`，名称全是「新节点」、类型「未分类」，id 是 `临时n1/2/3`。
- 服务端 200 应答：

```json
{"映射":{"临时n1":"n4","临时n2":"n4","临时n3":"n4"},"复用":["新节点"],"新增":{"节点":0}}
```

- 客户端顶部「节点 7」，DOM 里 `data-node-id` 是 `[n1,n2,n3,n4,n4,n4,n4]`，**盘上只有 4 个**。
- 换个名字再验一次：把 n4 改名为「唯一测试节点」，再双击 2 次 → `映射 {"临时n7":"n5","临时n8":"n5"}`、`新增 1`；UI 7 / 盘 5；关标签页重开 → **节点 5**。
- 连带效应：拖其中一个「副本」发出 `移动` 里 id `n4` 出现 4 次（`更新:4`），四个圆一起塌到一个坐标；自动布局发 7 个目标（`更新:7`）。

### 根因（三处，缺一不可）

1. **服务端前提安错了**：`packages/opencode/src/server/openhive/hgraph-edit.ts:409`。R7 同名的判据是「没给显式 id（`/^[net]\d+$/`）且名称+类型相同 ⇒ 复用」。手动加节点的临时 id 是 `临时n1`（中文前缀，不匹配该正则），于是**手动加节点和 AI 加节点走了同一条分支**。而设计 §6.4 说得明确：「**AI 加节点时**，若图上已有同名同类型…复用它」。这不是行为取舍，是判据安错了前提。
2. **客户端不查映射撞车**：`packages/app/src/center/case-views/hgraph/editor.tsx:281-289` 的 `换id` 只做 id 替换，不检查多个临时 id 映射到同一正式 id，于是本地文档真的长出 4 个 id 相同的节点。
3. **默认名保证撞名**：`editor.tsx:1574-1597` 加节点默认名恒为「新节点」、类型恒「未分类」，保证从第二个起必然撞名。`history.ts:18` 的注释甚至已经写明这个坑（合并撤销要「先删保留者，否则 R7 会把副本并过去」），说明团队知道它有牙，只是手动加节点这条路漏了。

### 同类落点（grep 过，`#002-06`）

复制/粘贴走的是 `graphops.ts:57` 的 `复制计划`，命名是「原名+副本」、临时 id 同样不匹配显式形状 ⇒ **同一个节点粘贴两次，第二份会被并进第一份**（代码路径已定位，未实测）。Alt+拖同理。合并撤销已用「先删保留者」规避。

### 修法

- **服务端**：给 `应用操作` / `应用并写回` 加一个显式入参（如 `同名复用?: boolean`，缺省 false），`case-hgraph-tools.ts:348` 的 `graph_add` 传 true，HTTP `/ops` 不传。判据只此一处（`#002-06`）。现有用例 `case-hgraph-edit.test.ts:214`（④b「带临时 id 的复用也要进映射」）要跟着改成显式走 AI 路径，并新增一条「手动路径同批两个同名节点 ⇒ 新增 2、两个不同 id」的红用例。
- **客户端兜底**：`换id` 后按 id 去重；若发现映射值撞车（`new Set(映射值).size < 键数`），不静默合并，直接弹「图和你本地不一致，请重新载入」。
- **默认名**：改成「新节点 N」或带序号，别让「同名」变成常态。结果里的 `复用` 数组目前 UI 完全没展示，至少给一行提示「复用了已有节点 X」，AI 路径需要这句话（§6.4 原文也要求）。

## P0-2 超时丢了应答 ⇒ 重试带旧版本 ⇒ 假「别人改过」

### 现象

网慢/内核忙时提示「没存上」，点「重试」却被告知「这份图在你打开之后被改过」——其实改它的就是用户自己上一次超时的写。

### 实测

Playwright 拦截 `/openhive/hgraph/ops`：`route.fetch()` 先让服务端落盘，再延迟 12.5s 回包，超过客户端 10s 上限。

- 服务端已写成功：`版本 cb3491b7bc56029516fb17084f7c3b43`、`更新于 2026-11-16T20:20:39+08:00`、n2 坐标已变。
- 客户端：状态栏「没存上」+「重试」，版本仍停在 `ec709c66…`。
- 点「重试」→ 请求带 `版本:"ec709c66…"` → 服务端 **409**：

```json
{"error":"这份图在你打开之后被改过。为避免覆盖别人的改动，请重新载入","code":"VERSION_CONFLICT","最新版本":"cb3491b7bc56029516fb17084f7c3b43"}
```

界面显示「这份图在你打开之后被改过 / 重新载入 / 保留我的改动」。会话早些时候那个「版本对不上」的 409 就是这个机制，不需要有第二个人在场。

### 根因

设计 §6.2 与 `hgraph-ops.ts:503` 的注释都写明了正解——「同幂等键重复调用返回上次结果、不重复写入（重试安全）」，且幂等判定**排在 CAS 之前**，正是为「重试带旧版本」准备的。

但客户端 `editor.tsx:864-870` 的 `写` 调用只传 `批次`（`批-${++序号}`，每次发送重新生成），**从不传 `幂等键`**；`hgraph-api.ts:159` 留了参数位、服务端 `幂等索引` 也在等它，就是没人填。AI 工具路径反而填了（`case-hgraph-tools.ts:348`）。

### 修法

- **主修**：客户端为每一次发送生成稳定的幂等键（如 `web:${图路径}:${序号}`），失败重试时**仅当重试载荷与上次失败载荷逐字相同**（同版本、同操作）才复用同一个键；载荷变了就换新键（否则服务端重放旧结果，新改动被静默丢弃）。服务端已有 10 分钟窗口，够用。
- **兜底（不改语义）**：收到 `timeout` 或 409 时先 `读` 一次，若盘上内容与「已存文档+本批」一致，说明自己的写其实成功了，直接采纳版本静默收口，不弹「别人改过」。

## P0-3 幻影重复态永不自愈（P0-1 的放大器）

`editor.tsx:1077`：`轮询` 在 `新版本 === 版本()` 时直接 return。

P0-1 产生的重复节点是**一次 200 成功应答**带来的，版本已经同步推进，所以每 10 秒轮询都判定「无变化」，重复态会一直留到用户手动关标签页。

P0-1 修好后源头没了，但建议 `发送` 成功分支加一道断言：`换id` 后 id 不唯一 ⇒ 立即请求重载。这样任何映射撞车都不会变成看不见的本地脏数据。

### ① 滚轮缩放：本机正常，但「小数 deltaY」被当成双指平移

**实测数值**（默认视口 `translate(0 0) scale(1)`，光标在画布空白处）：

| 输入 | 结果 |
|---|---|
| `wheel(0, -120)` | `scale(1)` → `scale(1.15)`，放大 ✅ |
| `wheel(0, +120)` | `scale(1.15)` → `scale(1)`，缩小 ✅ |
| `wheel(+120, 0)` | 缩放不变，`translate(-120 0)`，横向平移（设计如此） |
| 光标压在节点上 `wheel(0, -120)` | `scale(1.749)` → `scale(2.011)`，同样放大 ✅ |
| **合成** `deltaY: 3.75`（小数） | `scale` 不变，只平移 3.75px ❌ |

**根因**：`canvas.tsx:83` 的 `是双指平移` 用「小数 deltaY」当触控板判据：

```ts
return 事件.ctrlKey !== true && (事件.deltaX !== 0 || 事件.deltaY % 1 !== 0)
```

Windows 精密触控板、开了「平滑滚动」的鼠标、倾斜滚轮都会送出**小数 deltaY 或非零 deltaX**，于是每一次纵向滚动都被判成「双指平移」——只挪画布、不缩放。用户看到的就是「滚轮缩不动」。若你的输入设备是以上几类，这条就能完整解释；若是普通整数档滚轮仍不缩放，需要你补充浏览器/设备信息才能继续定位（本机 Chromium + 整数档滚轮是正常的）。

**修法（建议）**：不要用 delta 小数位猜设备（不可靠）。改判据为「横向占优才算平移」：

```ts
// 只有 |deltaX| > |deltaY|（横滑 / 倾斜滚轮）才平移；纵向一律缩放。
return 事件.ctrlKey !== true && Math.abs(事件.deltaX) > Math.abs(事件.deltaY)
```

代价是触控板「纵向双指」不再是平移（会变成缩放）。设计 §5.15 的平移还有「空格 + 拖」「中键拖」两条，仍可用；若要保留纵向双指平移，加一个「滚轮行为：缩放 / 平移」设置，默认缩放。红用例：`deltaY: 3.75` 必须改变 `scale`；`deltaX: 120, deltaY: 0` 必须只平移。

### ② 连线拖拽：落点判定只认圆心 15px，标签不算，失败零反馈

**实测**（连线模式，金色已点亮）：

红用例：拖到目标节点**标签**上松手必须建边（或至少出浮层）；落到真空白松手必须不建边且有提示。

### ② 「没有手型，左键拖不能平移画布」——能力在，可发现性与光标反馈不在

实测（真栈读 computed style 与 viewport `transform`）：

- 容器 `cursor: auto`；全画布**没有** `grab/grabbing` 任何一处；节点是 `cursor-pointer`，边是 `auto`。
- 空白左键拖 = **框选**（`transform` 不变，出现选框）——设计 §5.15 的本意，不是缺陷。
- 空格+左键拖 ⇒ `transform` 变；中键拖 ⇒ 变。用户自己也复现了「按住空格键点击拖拽可以移动画布」。
- 双指平移未验（无触控板，见缺口表）。

所以缺陷不是「不能平移」，而是**没有一个看得见的平移入口**：按住空格时游标不变、零提示。会按空格的能平移，不会的以为画布是死的——对不懂快捷键的民警，「发现不了」就等于「没有」。

修法（代价从小到大，建议 1 + 3 一起做）：

1. 空格按下/抬起切容器 `cursor: grab`，拖动中 `grabbing`。状态变量 `空格` 已存在（`canvas.tsx:349`），只差一个 class 绑定。
2. 空白悬停保持 `default`——别用 `grab`，否则和「左键拖是框选」自相矛盾。
3. 工具栏现有「指针 / 连线」两按钮扩成「指针 / 手 / 连线」，选「手」时左键拖即平移、cursor `grab`。这是不用记快捷键的唯一可发现入口，顺带补上 §5.1 的工具栏分组。
4. 可选：画布角落一行细提示「空格 + 拖动可平移」。

### ③ 用户新发现：普通滚轮不缩放，Ctrl+滚轮才缩放

这与第二轮 ① 是同一根因的两面。判据在 `canvas.tsx:83`：

```ts
const 是双指平移 = (事件: WheelEvent) =>
  事件.ctrlKey !== true && (事件.deltaX !== 0 || 事件.deltaY % 1 !== 0)
```

- **Ctrl+滚轮** ⇒ 第一项为 false ⇒ 走缩放。这就是用户看到的「按住 Ctrl 滚能放大缩小」。
- **普通滚轮** ⇒ 只有 `deltaY % 1 !== 0` 才被判成双指平移。用户的鼠标/驱动给出**小数 `deltaY`**（如 `3.75`）时，普通滚轮被当成「触控板双指平移」拿去平移几像素，于是表现成「滚轮没反应」。
- 我用 `page.mouse.wheel({ deltaY: 100 })` 合成的是整数事件 → 走缩放（1 → 1.15），所以在我这边「看起来正常」。**这是典型的设备相关假绿**：同一份代码，两种鼠标两个结论。

待补的最后一步实测：已在该页面装了滚轮探针（捕获 `deltaX / deltaY / deltaMode / ctrlKey`，见 `window.__wheelLog`），用户在此页普通滚一轮即可读出本机真实值。若确认存在小数/小增量 `deltaY`，判据必须改。

修法方向（不要再靠 `% 1`）：

- 普通滚轮一律缩放；`ctrlKey === true`（触控板捏合也带这个）同样缩放；
- 平移只认可解释的组合：`deltaX` 占优、或 `deltaMode === 0` 且 `|deltaY| < 阈值` 且事件来自触控板（无法可靠区分时，**宁可缩放**，因为缩放是滚轮的普遍预期）；
- 结论写回设计 §5.15，别只留在代码注释里。

#### V13 图例位置：钉死在画布坐标 (12,48)，不能挪，压住的节点点不到

**用户报告**：「图例放的位置不科学，一是不能移动，二是遮挡了显示的区域。」——三条都实测复现。

**① 它不在画布角上，而在画面左上方压着图。**

- 实测（浅色，1920×863，画布容器 1185×590）：图例屏幕框 `(629,268) 174×94`，距画布左缘 **273px**、上缘 41px，落在画面左中部、图的正上方。
- 根因不是「像素没调好」，是**两套坐标系**：`legend.tsx:41` 写死 `<g transform="translate(12 48)">`，锚的是 **viewBox 用户坐标**；而 `canvas.tsx:1086-1087` 的 svg 是 `viewBox="0 0 760 680"` + `preserveAspectRatio="xMidYMid meet"`。容器 1185×590 时缩放 **0.867**、实际绘制带 659×590 居中、**左右各留 263px 空带** ⇒ 用户坐标 `(12,48)` 被推到屏幕 `(629,268)`；图例也随缩放从设计值 196×108 缩成 174×94。
- 换句话说：图例锚的是「画布坐标系左上角」，不是「用户看得见的左上角」。**窗口越宽、画布越扁，它离左缘越远、越深地压在图上**；窄窗口反而更靠近角（这一档没实测，见缺口）。
- 12 这个横向偏移本来是为避开左上角，但真正的偏移来自 letterbox：`translate` 只贡献约 10px，剩下 263px 全是 viewBox 居中留的。

**② 不能移动（实测）。**

- 从图例中部按住左键拖 120×60px：图例 `(629,268)` 一分不动，画布 `transform` 也不变——**图例不动、画布也不动，拖拽等于没发生**。
- 可交互的只有两处：展开态「收起」24×14、收起态「图例」牌 52×22；**没有拖动句柄**。
- **也没有位置持久化字段**：`file.ts:164` 的设置形状里没有图例位置；收起只是本地 UI 态（`legend.tsx:12-16`），不写文件、不进撤销栈。折叠后那块 52×22 的小牌仍钉在同一个位置，**折叠解决不了「位置」问题**。

**③ 遮挡不只是视觉，被盖住的节点点不到（实测）。**

- 空格+拖把节点 n2 / n3 平移到图例下方，`elementFromPoint` 在 n2 中心 `(662,349)`、n3 中心 `(790,341)` 都返回 `hgraph-legend` / `hgraph-legend-item`；点 n2 中心前后选中集都是空——**被图例盖住的节点无法选中**，必须先平移把内容挪出来才能编辑。
- 原因：图例在 `canvas.tsx:72` 的 `内嵌界面` 名单里（本意是防止拖图例变成平移画布、双击图例加节点），指针事件被它整块吞掉。
- 图例框是**不透明**填充（`--v2-background-bg-layer-01`，浅色 `#FAFAFA`），压在图上就是一块实心白卡。证据截图 `legend-overlap.png`（本次新增，与本文件同目录）：「新节点02」的标签被压掉半截，第三个节点的圆被切掉半边，还压住了一个文字块。

**④ 与设计的关系：设计只给了折叠，没给挪位。**

- `08-关系图产物-设计.md:398`（§5.6）原文：「图例常驻（可折叠）……**小画布上图例挡内容，折叠成一个小图标**」——设计**预见了遮挡**，但只给了折叠一条路，没有挪位。
- 实现连「小画布自动折叠」都没做：`legend.tsx` 里没有任何画布尺寸判断，永远展开 108 高。

**修法（三选一，需先裁定形态，按 CLAUDE.md 不先斩后奏）：**

| 方案 | 做法 | 代价 |
|---|---|---|
| A 可拖 + 记住位置 | 图例加拖动句柄，位置存 `localStorage`（按文件 id）或写进 `设置.图例位置` | 改动小；仍占画面，用户得自己摆 |
| B 移出画布（推荐） | 编辑态图例放到画布外的编辑器 chrome（工具栏右端或画布下沿窄条），画布内只留「图例」小胶囊；导出仍走 T015 隐藏只读渲染（那条路径图例本就在 svg 内，§8 要求导出含图例） | 要改设计口径（编辑态图例不再画在 svg 里），HTML/SVG 两套渲染 |
| C 兜底自动折叠 | 不论 A/B，补「画布宽或高低于阈值 ⇒ 自动收起成 52×22 胶囊」 | 只缓解，不解决位置 |

完成判据（无论选哪个）：红用例钉住「图例不与任何节点/边重叠时仍可点中节点」与「图例位置在刷新后保持（若选 A）」；并补一条「小画布自动收起」的用例。

#### V14「指针 / 连线 / 加文字」不是工具栏的一行，是浮在画布上「独占一条」

**用户报告**：「指针、连线、加文字三个按钮独占一行不科学，占用了画布的显示区域。」——实测属实，而且比「占地方」严重：**瞄着节点点下去，改的是模式或凭空加内容**。

**② 点它会误触发动作（实测，两条）。**

**③ 与设计不符。**

- §5.1（`设计.md:328-332`）：工具栏**全图标、分四组**，第一组「选择｜画」里就是**指针、连线、加节点、文字**；§5.2 也写「工具栏两个模式：指针 / 连线」。

**④ 画布面积账（实测）。**

**② 外环填 12：数字存进去了、环不画、也没有任何提示（用户报告 + 代码根因；真栈当前卡在「正在加载文件…」，本轮未能在界面上复跑，见文末取证备注）。**

  3. 该节点没有连线 ⇒ 自动档 0 ⇒ `canvas.tsx` 的 `<Show when={环档(点) >= 1}>` 不渲染环。

## 第五轮：功能范围补记（2026-11-16）

### E1 图里只有实体节点，没有事件节点

**用户报告**：「只有实体节点，没有事件节点。」

**核实（代码）**：

- `.hgraph` 的 `节点` 只有 `名称 / 类型 / 细类 / 来源 / 可信度 / 属性 / 出处 / 时间{首,末} / 坐标 / 外环 / 样式`（`file.ts:53-74`），**没有事件对象需要的字段**（时点、事件类型、参与人）。
- `类型` 是自由文本，没有把「事件」列为可选项；`来源` 只有实体与手写两条路。
- 「从库加入」走的是实体选择器（`entity-picker.tsx`），**库里的事件没有进图的通道**。

**设计口径**：08 设计里「事件」只出现一次——第 129 行「查询已经有了（实体、关系、**事件**、明细行）」，说的是取数能力，**不是节点模型**；节点形状、类型色、图例、检查器各节都没有事件。所以这不是实现漏做，是**设计未覆盖**。

**要做的话，先得定这四件事**：

1. 事件节点画成什么（实体是圆，事件通常用菱形/方片，避免与实体混淆）；
2. 类型色与首字（现在圆内是类型首字）；

### U3 删除按钮与 Delete 键：功能同源，差的是「按得动的时候」

**用户报告**：「删除按钮是不是可以和键盘的 delete 键就有同等功效，要沿用用户的习惯。」

**核实（代码）——三个入口已经是同一个动作**：
- 工具栏「删除」`toolbar.tsx:82-92` → `动作表.删除所选()`；
- 检查器批量态「删除」`inspector.tsx:499-508` → 同一个；
- Delete 键 `canvas.tsx:895-901` → 同一个（`选中` 为空时直接 return，不发动作）；
- `删除所选` 是全模块唯一的「选中 id → 类别」翻译点（`editor.tsx:1602-1615`，节点 / 边 / 文字三类都认）；
- 有用例钉「工具栏按钮与画布 Delete 打到同一个动作条目、各 1 个批次」「检查器输入框里按 Delete 不删节点」（`editor.test.tsx:1349`、`:1387`）。

**所以差的不是功能，是可达性**：
- 按键处理器只挂在**画布容器**的 `keydown` 上（`canvas.tsx:852`；容器 `tabindex="0"` 见 `:1021`），焦点只靠点画布才给（`:567` `容器?.focus()`）；
- **实测**：点「筛选」按钮后 `document.activeElement` 从 `div[hgraph-canvas]` 变成 `button[hgraph-filter-toggle]`，`canvas.contains(activeElement) === false` ⇒ 那次 Delete 事件根本不到处理器，**静默无效**；同一个选中状态下点工具栏「删除」照删。
- 设计 §11 落点清单第 12 行（`08-关系图产物-设计.md:838`）要求「快捷键挂在 `hgraph/` 的画布容器上，**不注册全局热键**」——所以修法不能改 `window` 级。

**已裁定（用户 2026-11-16）**：Delete 的监听上移到**编辑器根容器**（`editor.tsx:1685-1696` 的 `hgraph-editor` 根 `div`；仍在 `hgraph/` 内，不是全局热键），输入框 / 可编辑区照旧不删（`canvas.tsx:855-862` 那条守卫要原样搬过去，M1 实测过）。

**修法要点（防双触发）**：画布在根容器内部，事件会冒泡——要么**根容器独家接管** Delete / F2 / 撤销重做（画布那段删掉），要么画布保留并在根容器里判断 `事件.target` 是否已在画布内。不许两处都调动作表（同一次按键删两遍 = 两次写盘、两个撤销步）。选哪个由实现时按「最小改动 + 单一出处（`#002-06`）」定。

**完成判据**：点工具栏任意按钮 → 点画布选中节点 → 按 Delete 能删（且只删一次：写盘批次 = 1）；焦点在检查器输入框里按 Delete 只删文字（`editor.test.tsx:1387` 继续绿）；演示态按 Delete 仍静默（`present.test.tsx:940` 继续绿）。
