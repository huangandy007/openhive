# 备注字段 · 存储与关联（交易语义）

> **状态**：一期定稿，待实现（2026-11-11）
> **日期**：2026-11-11
> **定位**：回答「备注这一列怎么存、存哪张表、以后怎么查」。备注描述的是**一笔交易干了什么**，不是账户或人的属性——所以它与 `05-实体属性标记与入库规范.md` 是两条线：那边管账户的属性（开户行、银行卡号），这边管交易的语义（用途、商户、摘要）。

> **过程**：本文按讨论顺序组织，含两次理解修正——先把重点放在「交易类型」，后改为「用途类别 ＋ 商户」；先以为卡片层要同步加列，后确认现在不需要。

## 0. 一页结论

1. **备注是交易语义，不是实体属性**——不进 `case_entity.attrs`（与 05 分界）。
2. **一期最小可用**：`case_fact_row` 加 `remark` 列；识别层认它；识别版本加一；新增一个 `query_rows` 工具。四件事缺一，备注都等于「存着但问不到」。
3. **卡片层现在不加**：表格来源目前根本不建卡片，给卡片加摘要列无处可放。等翻译层做起来，卡片自然带一句摘要，从备注取即可。
4. **商户名、用途分类是二期**。用途类别（手机充值 / 车辆加油 / 车辆过路费 / 停车 / 餐饮 / 购物……）才是实际工作最关心的，但它是**推断值**，必须带判断依据、可人工修正，不能每次让 AI 现猜。
5. **原文永不改写**：备注原文照抄进 `remark`，不截断、不掩码、不归一化（A16；明文原则，2026-11-10 拍板）。
6. **检索是扫描，但够用**：`%关键词%` 走不了普通索引，靠「项目分区 ＋ 时间/账户先收窄」压小范围；结构化列（用途、商户）建索引后，日常查询不扫文字。

## 1. 问题是什么

用户的实际提问是：**「AI 交互时，问不到这笔交易到底是干什么的。」**

备注里写着交易用途、商户、渠道，但这些信息现在既没有被识别，也没有被任何 AI 工具暴露：

- 备注被明确判成「无信息列」（`case-field-registry.ts:375-378`，正则 `备注|摘要|网点|说明|用途|序号`），识别层永远不看它；
- 值照旧进 `case_fact_row.extras["备注"]`（`case-rows.ts:175-189`），原文没丢；
- 但 AI 手里只有查实体、关系、事件、单行的工具，没有「按关键词翻流水」的口子。

结论：**数据是全的，语义是锁着的。**

## 3. 定性：备注属于哪一层

| 层 | 备注的角色 | 落点 |
|---|---|---|
| 明细（一行流水） | 原文证据 | `case_fact_row.remark` |
| 卡片（一笔交易） | 摘要、类型、用途、商户 | `case_event`（二期，翻译层） |
| 实体（账户/人/商户） | 不挂备注 | `case_entity` 不写 |

**为什么不能进实体属性**：备注描述「这笔钱为什么动」，不描述「这个账户/人是谁」。混进 `case_entity.attrs` 会把两层语义搅在一起——以后查「这个人的账户属性」会混入交易说明，查「这笔交易干了什么」又要跨表拼。

---

## 4. 优先级修正（重要）

最初的设计重点放在「交易类型（转账/消费/提现）」上。**2026-11-11 用户指出：实际工作最关心的不是这个，而是「手机充值、车辆加油、车辆过路费、消费的商户名称」。**

因此：

- **交易类型是粗筛，不是结论。** 它能回答「这是不是消费」，回答不了「消费在什么事上」；
- **用途类别 ＋ 商户名才是结论**，也是「帮我找出」类提问的主语；
- 但两者性质不同：商户名是原文里有的，用途类别是判出来的。存储与可信度要求不同（见 §6）。

## 5. 一期：备注可存、可查（最小可用）

### 5.1 数据层：加列

`case_fact_row` 增加：

```sql
remark text   -- 备注原文：照抄、不截断、不掩码、不归一化
```

不动 `extras`：原文仍按原表头留底（A16）。识别成功后，该列不再重复进 `extras`。

### 5.2 识别层：三处一起改

只加列不认列，列永远是空的。三处必须同改（`#002-06`：按同一前提判定的落点要一起找）：

| 落点 | 改什么 | 位置 |
|---|---|---|
| 字段目录 | 新增 `remark`，同义词收窄为 `备注/摘要/用途/附言/交易备注/转账备注` | `case-field-registry.ts` 字段定义区 |
| 候选字段集 | 资金、话单两组都加入 `remark`，否则不参与认领 | `case-field-registry.ts` `候选字段集`（资金 / 话单两个 Set） |
| 无信息列 | 把 `备注`、`摘要`、`用途` 从正则里摘掉；`网点/说明/序号` 保留 | `case-field-registry.ts:375-378` |

### 5.3 识别版本加一

格式指纹包含 `识别版本`（`case-mapping.ts:409-418`，当前 `"7"`）。改认列规则必须把它加一，否则旧格式缓存命中时继续套用没有 `remark` 的旧映射，老文件重解析仍认不出备注（`#011-01`）。

### 5.4 给 AI 一个翻明细的工具（新增 `query_rows`）

没有这个工具，`remark` 只是躺在库里。建议签名：

```
query_rows({
  关键词?,      // remark / merchant 模糊匹配
  起?, 止?,     // 交易时间窗
  账户?,        // 本方或对方账号
  方向?,        // 收 / 付
  金额最小?, 金额最大?,
  限制?
})
```

返回：`material_id`、`sheet`、`row_no`、`started_at`、`amount`、`counterparty`、`remark`、出处 id（`材料#工作表#行号`）。默认按时间倒序，截断时按 `截断缺口` 口径明说。

### 5.5 一期全落点清单

| # | 落点 | 性质 |
|---|---|---|
| 1 | 迁移加 `case_fact_row.remark` | 加 |
| 2 | 字段目录加 `remark` | 加 |
| 3 | 候选字段集（资金、话单）加 `remark` | 加 |
| 4 | `是无信息列` 摘掉 备注/摘要/用途 | 改 |
| 5 | 识别版本 `"7"` → `"8"` | 改 |
| 6 | `FactRowInput` 类型、写入语句、回读 select 补 `remark` | 加 |
| 7 | `get_citation` 行分支返回 `remark`（顺带补 `counterparty_name`/`owner_account`/`direction`，见 05 讨论） | 加 |
| 8 | 新增 `query_rows` 工具 | 加 |
| 9 | 测试：原表「备注」列 → `remark`；无信息列不再吞它；缓存旧版本失效 | 新增 |

全部是机械改动，无一处需要新架构。

## 6. 二期：用途与商户（判断性工作）

### 6.1 商户名

- 来源优先取备注 `子商户名称` 段，其次才是 `收款方的商户名称` 列；
- 预处理时解码 `UTF8#…`；遇到「间连交易…请联系收单机构查询」这类占位话术，不当作商户名；
- 落点：明细行 `merchant`（现有 extras 字段 `merchant` 可直接用），卡片层作为「跟谁交易」。

### 6.2 用途类别

- **受控词表**：手机充值、车辆加油、车辆过路费、停车、餐饮、购物、医疗、娱乐、其他/未分类；
- **判断依据必须留**：命中哪个词 / 哪条规则（例如「中国移动」→ 手机充值），随值一起存；
- **判不出就标「未分类」**，不硬猜；
- **人工可改**，改完保留原判断与修改痕迹（属性/事件信任态机制可复用）；
- **词表由内核统一维护**，不随每个 skill 各写一套：加油、ETC、中国移动这些词跨数据源通用；各家备注的写法才归 skill。

### 6.3 卡片层（等翻译层）

`case_event` 上承载：

- `summary`：一句人看的摘要（来自备注主体）；
- 用途类别：必须在卡片上可查（「找出所有车辆加油的消费」是典型提问，按设计 §3.5 判据不能只进 `attrs`）；
- 商户：作为参与者/交易对方；若需要按商户聚合，则升级为 `组织` 实体。

### 6.4 与 05 的边界

- 05 管「账户的属性」（开户行、银行卡号）——属于实体，写 `case_entity.attrs`；
- 本文管「交易的语义」（备注、用途、商户）——属于明细与卡片，不写实体属性。

## 7. 检索性能：是扫描，但够用

1. **本质**：`remark ilike '%关键词%'` 是全文扫描，普通 B-tree 索引用不上。
2. **先收范围**：`case_fact_row` 按 `project_id` 哈希分 16 片，查询必带项目号 → 只扫一片；再叠加时间窗、账户、方向、金额，候选行通常只剩几千行。
3. **数据量级**：一个案子几万到几十万行、每行备注几十字，扫描在毫秒到百毫秒级，交互可接受。
4. **要加速时的三档**：
   - `pg_trgm` GIN 索引：能加速 `%关键词%`，但按三字一组建索引，两个字的词（「加油」「话费」）效果打折；
   - **优先把常用维度变成结构化列**（用途、商户）并建普通索引——「加油的消费」查列不扫文字；自由词搜索才回退到备注；
   - 千万级、要求秒级全文检索时才考虑外部检索引擎，当前规模不必。
5. **结论**：一期先扫 ＋ 收窄范围，用真实数据量测；日常分析走结构化列。

## 8. 后期怎么关联到

```
case_fact_row（一行：remark / 金额 / 时间 / 对手）
   │ 翻译层（二期）
   ▼
case_event（一张卡：summary / 用途 / 商户 / amount）
   │ 参与者
   ▼
case_entity（账户 / 人 / 商户）
   ▲
   └── case_citation 指回 材料#工作表#行号
```

对应提问：

1. **按备注找交易**：「备注里带‘红包’的流水」→ `query_rows`（一期）；
2. **按交易看语义**：「这笔钱干什么用了」→ 卡片 `summary`/用途（二期）；一期可先看 `remark`；
3. **按用途/商户统计**：「手机充值几笔、多少钱」「在哪些加油站消费」→ 结构化列/商户实体（二期）。

## 9. 一期验收判据

1. 原表「备注」列的值进入 `case_fact_row.remark`，内容与原文逐字一致；
2. 该列不再出现在「未认出/待确认」清单，也不被「无信息列」吞掉；
3. 改动前的旧格式缓存不再命中（识别版本已加一），重解析后备注可识别；
4. `query_rows` 能按关键词、时间窗、账户查到行，并返回 `材料#工作表#行号`；
5. `get_citation` 能按该行 id 取回 `remark`；
6. 空备注行不报错，存 `null`，原文为空即空。

## 附：讨论过程（一步一步）

1. **发现**：AI 问不到备注语义。
2. **核查**：备注被「无信息列」排除识别；值在 `extras`；AI 无行级查询工具。
3. **初版建议**：拆 `##` 段，交易类型、商户进卡片摘要。
4. **用户修正一**：交易类型和商户名不是实际工作最关心的；最关心的是**用途**（手机充值、车辆加油、车辆过路费）和**消费的商户名称**。
5. **实测验证**：消费 146 行；真商户名在 `子商户名称`；「收款方的商户名称」多为占位话术；用途关键词可命中但有误判（「充值」≠「手机充值」）。
6. **用户担心复杂度**：拆分是否麻烦。结论：拆是小事，分类是长期活；一期做机械的，二期做判断的。
7. **用户问检索**：本质是文字扫描。结论：靠分区与范围收窄，日常走结构化列，不必上搜索引擎。
8. **用户收敛范围**：是否只加 `remark` 列即可、卡片暂不需要。**确认**：卡片现在不需要；但「一列」之外还有识别三处、识别版本加一、查询工具三件，缺一则问不到。
