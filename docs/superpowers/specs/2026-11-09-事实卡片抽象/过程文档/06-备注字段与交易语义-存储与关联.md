## 0. 一页结论（2026-11-12 修正版）

1. **备注是交易语义，不是实体属性**——不进 `case_entity.attrs`（与 05 分界）。
2. **`case_fact_row` 不加 `remark` 列**。备注作为未识别列照旧进 `extras`（键 = 原表头；预处理标准副本固定列名后为「备注」），原文一个字都不丢。
3. **翻译层是唯一消费者**：入库时用途规则读 `extras` 里的备注原文，产出结构化结果——这是备注从「文字」变成「可查语义」的唯一路径。
4. **结构化落点（二期）**：`case_event.purpose`（用途，独立列、可索引）+ 参与者角色（商户是谁）+ `purpose_basis`（规则 / 命中词 / 版本）+ 行级 citation；人工可改，改完留痕。
5. **原文永不改写**：不截断、不掩码、不归一化（明文原则，2026-11-10 拍板）。
6. **AI 不扫备注原文**：按用途查走 `case_event.purpose` 索引、按商户查走参与者表索引；备注原文只用于回显与人工复核。`query_rows` 只按时间 / 账户 / 方向 / 金额翻明细，**不提供备注关键词参数**。

**为什么加列是错的**：① 值本来就在 `extras`，加列只是搬一遍；② 制造「AI 可查原文」的假路径——`ilike` 扫描既慢又不可审计；③ 与「翻译在入库、查询读结论」相反；④ 给「最小化与官方合并冲突」凭空加列、迁移与字段目录改动。

## 1. 问题是什么

用户的实际提问是：**「AI 交互时，问不到这笔交易到底是干什么的。」**

备注里写着交易用途、商户、渠道，但这些信息现在既没有被识别，也没有被任何一层读成语义：

- 备注被明确判成「无信息列」（`case-field-registry.ts:375-378`，正则 `备注|摘要|网点|说明|用途|序号`），识别层永远不看它——**这是有意为之**（备注不该占用标准列）；
- 值照旧进 `case_fact_row.extras["备注"]`（`case-rows.ts:175-189`），原文没丢；
- 但**翻译层还没有**（表格来源目前根本不建卡片），所以没有任何东西把 `extras` 里的备注读成用途/商户；AI 手里也就只有查实体、关系、事件、单行的工具。

结论：**数据是全的，语义是锁着的；锁不在存储层，在翻译层。**

## 3. 定性：备注属于哪一层（修正后）

| 层 | 备注的角色 | 落点 |
|---|---|---|
| 明细（一行流水） | 原文证据（照抄，不解释） | `case_fact_row.extras["备注"]`（**不建列**） |
| 翻译层（入库时） | 读原文 → 判用途/商户 | 无独立存储；产出下面卡片层的值 |
| 卡片（一笔交易） | 用途、商户、摘要的**结构化结论** | `case_event.purpose` + 参与者角色 + `purpose_basis`（二期） |
| 实体（账户/人/商户） | 不挂备注 | `case_entity` 不写 |

**为什么不能进实体属性**：备注描述「这笔钱为什么动」，不描述「这个账户/人是谁」。混进 `case_entity.attrs` 会把两层语义搅在一起——以后查「这个人的账户属性」会混入交易说明，查「这笔交易干了什么」又要跨表拼。

## 4. 优先级修正（2026-11-11，仍然有效）

最初的设计重点放在「交易类型（转账/消费/提现）」上。**2026-11-11 用户指出：实际工作最关心的不是这个，而是「手机充值、车辆加油、车辆过路费、消费的商户名称」。**

因此：

- **交易类型是粗筛，不是结论。** 它能回答「这是不是消费」，回答不了「消费在什么事上」；
- **用途类别 ＋ 商户名才是结论**，也是「帮我找出」类提问的主语；
- 但两者性质不同：商户名是原文里有的（可抽取），用途类别是判出来的（推断值）。可信度要求不同（见 §6）。

## 5. 一期：不建列（2026-11-12 修正）

### 5.1 裁定

`case_fact_row` **不加 `remark` 列**。备注原文留在 `extras`，理由见 §0 末段。

### 5.2 一期「不做」清单（逐条对照旧方案）

| 旧方案 | 现在 |
|---|---|
| 新迁移加 `case_fact_row.remark text` | **不做**——原文已在 `extras` |
| 字段目录加 `remark`、候选字段集加 `remark` | **不做**——备注不是标准列，也不该参与认领 |
| `是无信息列` 摘掉 `备注/摘要/用途` | **不做**——那会把备注变成待确认噪声，且与「不建列」矛盾 |
| 识别版本 `"7"` → `"8"` | **不做**——识别规则没变，缓存指纹不该动（`#011-01` 教训的适用前提是「规则变了」） |
| `case-store.ts` 写入/回读补 `remark` | **不做**——`extras` 照旧写入，回读整份返回 |
| `get_citation` 行分支返回 `remark` 字段 | **不做单列**——`get_citation(row)` 整份返回 `extras`，备注原文自然在里面 |
| `query_rows` 支持备注关键词 | **不做**——只按时间 / 账户 / 方向 / 金额翻明细（下节契约） |

**一期只剩一件机械改动**：确认 `extras` 里的「备注」在行级出处回读时能原样返回（若 `get_citation(row)` 现在只回部分字段，补成整份 `extras`）。

### 5.3 给 AI 一个翻明细的工具（`query_rows`，不含备注关键词）

```
query_rows({
  材料?,        // material_id
  账户?,        // 本方或对方账号
  方向?,        // 收 / 付
  金额起?, 金额止?,
  时间起?, 时间止?,
  游标?, 限制?
})
```

返回：`material_id`、`sheet`、`row_no`、`started_at`、`amount`、`direction`、`counterparty`、`counterparty_name`、`owner_account`、`extras`（含备注原文，回显用）、行级出处（`材料#工作表#行号`）。默认按时间倒序，截断时按 `截断缺口` 口径明说（契约见 `09` §4.4）。

**它回答什么**：「把这几天这个账户的流水翻给我看」「5000 元以上那几笔的原文是什么」。

**它不回答什么**：「哪些是加油」「在哪家店消费」——那是用途/商户，走二期的结构化字段（§6、§7）。

## 6. 二期：用途与商户（判断性工作）

### 6.0 三个问题的一页答案（2026-11-12）

> **口径归属**：本节规则已并入 `01` §3.11 作为正文（2026-11-12）；**规范性以 `01` §3.11 为准**，本文保留实测证据、优先级推导与回归基线数值。

| 问题 | 答案 | 详见 |
|---|---|---|
| 分类在哪做 | **入库期的翻译层，逐行一次，写库定死**。不在预处理、不在 skill、不在查询、不在 AI | §6.1 |
| 要不要用 AI | **批量打标不用，且明确禁止**。AI 只做单笔解释与开发期提议新规则 | §6.6 |
| 以后加大类/小类怎么办 | **词表是数据不是代码**：类别存字符串（非 PG enum）、词表版本化；一级近乎冻结、二级生长；内核词表 + 源规则包 + 案件级增量 | §6.4 |
| 放 skill 里做会不会更好 | **一半**：skill 只提供「解析写法 + 源特有词 + 标准输出结构」；词表语义、优先级骨架、落库字段归内核 | §6.7 |

一句话总纲：**准确性不来自「更聪明的判定器」，来自分清哪部分是取出来的、哪部分是判出来的，并且判出来的那部分必须带依据、可重跑、可证伪。**

### 6.1 判定在哪做：唯一落点与存储（2026-11-12）

```
case-ingest.ts
  读表 → 识别材料 → toFactRows（明细行，备注进 extras）
                              ↓
                         ★ 判定段 ★
                   逐行读 extras["备注"] → 判 purpose / purpose_basis
                              ↓
                 写 case_event.purpose + purpose_basis
```

- **时机**：入库那一刻，一次性全量跑完。不是查询时算，不是用户提问时算。
- **位置**：`packages/opencode/src/server/openhive/` 下的独立模块（建议 `case-purpose.ts`），由 `case-ingest.ts` 在明细行可用、卡片写入之前调用。**不能放 skill**——skill 无库访问、可被随手改、不参与版本审计。
- **前置依赖：`case_event` 必须先建起来。** 按 §1 现状，**表格来源目前根本不建卡片**（`case_event` 只由 AI 抽取那条路写），所以「判定代码」与「可写的地方」是同一个缺口；P4 的起点是先让表格来源产出卡片，再谈用途。
- **存储**：`case_event.purpose`（独立列、普通索引）+ `purpose_basis`（命中词 / 规则 / 词表版本）+ 行级 citation。按 01 §3.5 判据，用途是查询主维度，**不能只进 `attrs`**。
- **人工可改**：改完保留原判断与修改痕迹（复用属性/事件信任态机制）。
- **原文一字不改**：判定只读 `extras`，从不回写备注。

**为什么这个位置不可替代**：预处理产出的标准副本是落盘产物，判完就固化，词表一升级就得重跑几万行文件；查询时判则每问一次算一次，既慢又不可复现。只有「入库判一次 → 结论存库 → 之后只查结论」这一条路同时满足可审计与可重算。

### 6.2 三级判据：分清「取出来的」与「判出来的」

| 层 | 做什么 | 确定性 | 落点 |
|---|---|---|---|
| ① 字段事实 | 读源文件自己声明的列：`交易类型` 5 值、收/支 | 100%（按源） | `direction`；作为判定依据，**不写进 `purpose`** |
| ② 结构抽取 | 从 `##` 分段里**取**值：`子商户名称`、`UTF8#` 解码、收款方列、号码、车牌 | 高（可核对原文） | 参与者（商户角色）、`attrs`、对象 |
| ③ 语义判定 | **判**用途 / 小类 | 推断值，必须带依据 | `case_event.purpose` + `purpose_basis` |

三条纪律：

1. **`交易类型` 是粗筛，不是结论**（§4）：它回答「是不是消费」，不回答「消费在什么事上」。所以它进方向与依据，不进 `purpose`。
2. **推断层必须带依据**：`purpose_basis` 记「命中哪个词 / 哪条规则 / 词表版本」，依据可回放，结论才可审计；人工能据此推翻（01 §3.10：推断值不能当原文）。
3. **fail-closed**：判不出落「未识别转账 / 消费其他」，不硬猜（与 `#011-02` 单位闸同一条纪律：宁可交人工，不可静默错）。

### 6.3 有序优先级表（first-match wins）

实测三份真文件后最值钱的结论：**错误很少出在「认不出」，多数出在「认出了多个、顺序排错」**。所以规则必须是一张**有序表**，不是无序遍历的词表。一条规则 = 前置条件 + 匹配词 + 输出类 + 优先级；先命中先返回。

骨架（从高到低）：

```
退款 > 红包 > 手续费 > 信用卡还款 > 零钱通(备注主体只有它) > 提现至本人卡
> 账户充值 > 停车 > 车辆过路费 > 车辆加油 > 手机充值 > 生活缴费 > 保险
> 医疗 > 餐饮 > 交通出行 > 住宿 > 娱乐订阅 > 美容休闲 > 教育政务 > 购物
> 扫码(渠道标记) > 转账 > 兜底(未识别转账 / 消费其他)
```

四组由实测逼出来的修正（不改就是成片错标）：

| 现象 | 错法 | 修正 |
|---|---|---|
| 信用卡还款行的 `交易类型` 是「提现/转账至银行卡」，备注写「信用卡还款」 | 判成提现至本人卡 | **信用卡还款排在提现之前** |
| `中石化易捷便利店消费` | 判成车辆加油 | 加油规则**排除「便利店/超市」**（判购物） |
| `ETCP-临时停车缴费` 与 `高速通行费` 互吞 | 停车 / 过路互相错判 | 停车只认「停车/停车场/P云/ETCP」，过路只认「通行费/ETC/高速」 |
| `微信转账;零钱通…` 与单独主体的 `零钱通支付` | 全部判成零钱通划转 | **仅当备注主体只有零钱通**才是划转；作为后缀时按前面的类，只记 `渠道=零钱通` |

**「扫码付款」不是标签，是渠道**：真数据里扫码对象既有商店也有个人（收款户名常是店主本人），所以一级仍判消费或转账，另记 `渠道=扫码`。

### 6.4 受控词表：两级 + 加类准入 + 扩展机制

> **口径归属**：规则字段、三层归属、扩充六步、回归量化门、防乱纪律的**规范正文在 `01` §3.11.4**（2026-11-12 补入）；本节留计算与操作的细则、一个完整例子和反例。

**两级**：

- **一级（资金性质，12 个，近乎冻结）**：消费 / 转账 / 红包 / 提现至本人卡 / 转至他人银行卡 / 信用卡还款 / 零钱通划转 / 账户充值 / 退款 / 手续费 / 未识别转账 / 未分类
- **二级（只给「消费」生长，15 个）**：购物 / 餐饮 / 医疗 / 保险 / 生活缴费 / 手机充值 / 车辆加油 / 停车 / 车辆过路费 / 交通出行 / 住宿 / 娱乐订阅 / 美容休闲 / 教育政务 / 其他
- **两条正交信息不占标签位**：`渠道`（扫码 / 微信转账 / 零钱通 / 银行卡 / Apple 账单）；`对象`（商户 / 手机号 / 车牌 / 场所 / 银行卡尾号）

**加小类的准入判据**（不是想到就加）：有稳定查询需求 + 有可判定的词 + 真数据里有量（≈ ≥50 笔或 ≥1%）。达不到就进「其他」。实测标尺：保险 688、生活缴费 1,017、零钱通划转 1,634 够格；教育政务 27 笔先留观察位。

**扩展机制**：

| 方向 | 机制 |
|---|---|
| 新数据源（银行 / 支付宝 / 话单） | **规则包**：内核词表与优先级骨架共享，各源只加解析器 + 源特有词 + 字段映射。新源不碰内核、不碰迁移 |
| 新大类 / 小类 | 类别存**字符串**、词表版本化；一级冻结、二级生长；报表按一级出、明细看二级，加小类不动历史口径 |
| 个案差异（本案关心赌资、那案关心货款） | 留**案件级词表增量**：内核词表 + 案件补充词，不污染全局。可后置，接口先留 |

**一次扩充的完整走法**（规范见 `01` §3.11.4.3，这里给可照抄的例子）：

> 场景：二级「其他」里聚类出 `云视听极光 198`、`奇异果TV 42`、`腾讯视频 37`，合计 277 笔。

| 步 | 具体动作 | 本例取值 |
|---|---|---|
| 1 发现 | 按二级＝`其他` 拉备注聚类表 | 三个商户，277 笔 |
| 2 定归属 | 三者都是视频会员 | 归已有二级 `娱乐订阅`，**不加新类** |
| 3 定优先级 | 插在「车辆类」之后、「购物」之前 | 取两邻规则的中点（如 40），不盲添到末尾 |
| 4 写规则 | `字段=备注#子商户名称`，`排除=[退款]` | JSON 见 `01` §3.11.4.1 |
| 5 回归 | 期望：`娱乐订阅 +277`、`其他 −277`、**其余 13 个二级与 12 个一级一律不变** | 不符就停，先查误伤 |
| 6 升版本 | 词表 `v1.2 → v1.3` | 新旧 `purpose_basis.词表` 可区分 |
| 7 抽样 | 从新增的 277 条里抽 30 条看原文 | 全部是会员订阅才合入 |

**反例：不加 `排除` 会怎样**。把 `中石化` 直接放进「车辆加油」的 `任一`，会把 `中石化易捷便利店` 的商超消费一起算成加油（§6.3 修正行已记录这个坑）。教训不是"再加个判断"，而是**有误伤风险的词必须把排除词一起写上**；同时说明回归要看**每个类**的计数，而不只看目标类——目标类涨了、别的类也涨了，就是误伤。

**这类改动不需要动代码**：加规则是改规则表 + 升词表版本；只有新增**一级类**或新增**判定手段**（如第一次用金额符号）才需要动引擎。这条界线决定了「扩充」日常由实施/办案人员做、只有引擎改动才要内核维护者。

### 6.6 AI 的位置：解释单笔、发现新规则，不批量打标

**结论：入库时的批量分类不用 LLM，一次都不该用。** 四条理由：

| 理由 | 具体 |
|---|---|
| 成本 / 延迟 | 一个案子几万到几十万行，每次全量过模型压垮流程 |
| 不稳定 | 同输入两次结论不同 ⇒ 破坏「同一案件同一结论」，报表对不上账 |
| 不可审计 | 没法指着一行问「你凭什么判餐饮」；规则能指到「命中『美团』+ 词表 v3」 |
| 规则更准 | 备注是高度结构化的 `键：值`，规则在真数据上已吃到 99.6%（未分类 0.36%） |

AI 有两个**正当**位置，都不在批量路径上：

1. **开发期：规则冷启动助手（离线、人在环）**。把「未识别」的备注聚簇，让 AI 提议「这批 `某某代扣` 像保险还是生活缴费」，人确认后**落成规则**。AI 产出规则，不产出标签。
2. **运行期：单笔兜底解释（按需）**。用户指着某一行问「这笔是干什么的」，AI 读原文给建议，但必须标清「AI 推断，非规则结论」，且**不写回 `purpose`**（要留就单独存 `purpose_suggested`）。绝不预跑全表。

**明确的反例**：不要把分类塞进右栏 AI 的提示词里「每次现算」——最贵、最不可复现、最不可审计。

### 6.7 边界：预处理 / skill / 内核 / 翻译层

| 归 skill（跟数据格式走、会频繁变） | 归内核（跨源稳定、是查询口径） |
|---|---|
| 怎么切 `##`、`UTF8#` 解码、间连占位识别 | **受控词表本身**（类的名字与语义） |
| 该源字段映射、典型写法、源特有词 | **优先级骨架**（正确性的来源，必须唯一） |
| 产出 `{purpose, purpose_basis, 置信度}` 标准结构 | **落库字段**（`purpose` / `purpose_basis` 是 DB 契约） |

三条理由：

1. **词表放 skill 会让两张表对不上账**：两个 skill 对「餐饮」定义稍有不同，报表就永远对不平。类别语义必须单点定义。
2. **skill 可被用户改**（项目级/用户级 skill 都能加词），若直接写库，改错一个词就污染数据。所以要设闸门：**skill 只产出「建议 + 依据」，翻译层校验类名是否在枚举内**，不在就落「未分类」并记缺口——`#004-09`：门放在副作用之前。
3. **格式变了只改 skill**，不碰内核、不碰迁移、不碰官方合并面（本项目第一号约束）。

**预处理（skill 的产物生成阶段）明确不做判定**，但必须做三件为判定铺路的事：

| 必须做（机械、确定性） | 一律不做（要判断） |
|---|---|
| 备注原文**逐字保留**，不截断、不归一化、不合并换行 | 贴标签、猜用途、填 `purpose` |
| 保住 `##` 分段与 `键：值` 结构 | 判断「这算购物还是餐饮」 |
| `UTF8#…` **解码**（base64 → 中文商户名，纯还原） | 按语义筛行、丢「看不懂」的行、去重 |

划界判据一句话：**预处理只做「格式对齐」——凡是必须「看内容才能下结论」的，全交给入库翻译层。** 所以解码归预处理（还原，不是解释），「扫到中国石化判成加油」不归（解释）。

### 6.8 商户名与对象抽取

- 来源优先取备注 `子商户名称` 段，其次才是 `收款方的商户名称` 列；
- `UTF8#…` **在预处理阶段解码**；遇到「间连交易…请联系收单机构查询」这类占位话术，不当作商户名；
- **落点**：卡片的参与者（`case_event_participant`，角色 = `商户` / `收款方`），并挂到 `组织` 或 `地点` 实体；若暂时无参与者表，先写 `case_event.participants`（兼容列），但角色缺失要在缺口里明说。
- **对象抽取**（与用途并列的第二类结论，属三级判据的②层）：手机号、车牌、场所、银行卡尾号。实测去重数：号码 12 / 250 / 883，车牌 1 / 2 / 4，子商户 74 / 536 / 575——这正是「缴费号码、加油/停车车辆、常去店面」三类提问的数据基础。

### 6.9 卡片摘要

`case_event.summary` 可从备注主体取一句（二期与翻译层一起落）。它不是查询维度，只是给人看的一行字。

### 6.10 与 05 的边界

- 05 管「账户的属性」（开户行、银行卡号）——属于实体，写 `case_entity.attrs`；
- 本文管「交易的语义」（用途、商户、摘要）——属于卡片层，不写实体属性，也不在明细层建列。

## 7. 检索：查结论，不扫原文

1. **按用途**：「找出所有车辆加油的消费」→ `case_event.purpose = '车辆加油'`，普通 B-tree 索引，走 `query_events`。
2. **按商户**：「在哪些加油站消费」→ 参与者表按 `entity_id` + 角色 `商户` 查，再回卡片。
3. **按原文回显**：只有「这一笔的原文是什么」时才读 `case_fact_row.extras`，按 `material_id + locator{sheet,row}` 点查，不扫描。
4. **不做 `remark ilike '%词%'` 关键词查询**：两个字的词（「加油」「话费」）`pg_trgm` 也打折，扫描结果不可审计；同样的提问应由用途/商户字段回答。
5. **数据量级**：一个案子几万到几十万行，点查与索引查询都是毫秒级；不需要外部检索引擎。

## 8. 后期怎么关联到

```
case_fact_row（一行：extras[备注] / 金额 / 时间 / 对手）
   │ 翻译层（二期）：读 extras 里的备注原文，判用途/商户
   ▼
case_event（一张卡：purpose / summary / amount）
   │ 参与者（商户角色）/ 关系
   ▼
case_entity（账户 / 人 / 商户）
   ▲
   └── case_citation 指回 材料#工作表#行号
```

对应提问：

1. **按交易看原文**：「这一笔的原文和备注」→ `query_rows` 或 `get_citation(row)`（一期，回显）；
2. **按用途找交易**：「哪些是手机充值、加油」→ `case_event.purpose`（二期）；
3. **按商户统计**：「在哪些店消费、一共多少钱」→ 参与者表 + `case_relation`（二期）。

## 9. 验收判据（修正后）

**一期（不建列）**

1. 原表「备注」列的值逐字留在 `case_fact_row.extras`，与原文一致（含换行、`##` 分段）；
2. 没有新增迁移、字段目录与识别规则零改动，识别版本仍为 `"7"`；
3. `get_citation(row)` 能整份返回该行 `extras`，备注原文可取回；
4. `query_rows` 能按时间 / 账户 / 方向 / 金额查到行并回 `材料#工作表#行号`；**不提供备注关键词参数**；
5. 空备注行不报错，`extras` 里该键为空或缺席，原文为空即空。

**二期（用途/商户）**

6. 用途规则能对 §2.5 的样本给出与人工判断一致的分类，误判（如「剑来…充值服务」）落在「未分类」或带依据的正确类；
7. 每个 `purpose` 值都有 `purpose_basis` 与行级 citation；人工修改后可回溯原判断；
8. 「按用途查」「按商户查」走索引，不出现 `extras` 文本扫描；
9. **分类结果与 §6.5 首版基线一致**（一级 12 类合计 = 31,719，二级 15 类合计 = 消费 7,767）；改词表后能全量重算，且新旧 `purpose_basis` 的版本可区分；
10. **批量路径零模型调用**（可按模型调用计数/审计日志核验）；只有单笔解释路径允许调模型，且结果不写回 `purpose`；
11. **预处理产物里没有用途/分类列**（预处理不判用途，§6.7）；`grep` 标准副本列名即可核验；
12. **判定代码在内核模块、由 `case-ingest` 调用**，不在 skill 内；skill 只产出规则包与解析结果。
13. **扩充走六步且过回归门**（§6.4、`01` §3.11.4）：每条规则有 `id`／显式 `优先级`／有风险时的 `排除`；回归 diff 里目标类上升数 = 新命中数、其他类零变化；词表版本递增；新增命中抽样准确率 ≥ 90%。
