# 微信账户流水 · 字段口径与转换规则（沉淀）

> **状态**：口径沉淀 · 已并入设计文档（`01` §2.4、§4.0.6，2026-11-11）；§9 补了与实体属性规范的对接说明
> **日期**：2026-11-10
> **定位**：这是「数据翻译」的**输入端口径**，不是新的架构决策。上游是 `01-事实卡片与数据翻译-设计.md` 里「明细 → 卡片」的翻译层；本文只回答一件事——**一份微信账户流水进来，哪些列是相对的、哪些字段是绑定的、哪些值可以推出来、哪些推不出来。**
> **证据**：全部数字来自真文件 `tmp/file_example/085e9858e5a007713ee37155d@wx.tenpay.com.xls`（28 列 × 699 行）的实跑；脚本与产物在 `tmp/skill-微信账户流水预处理/`。这是一份**演示级原型**，尚未进仓库、尚未接入平台的 skill 资产流水线。
> **过程**：本文按**四轮修订**组织。每一轮都记「原来的理解 → 指出问题 → 改成什么 → 实测变化」，因为**被推翻的理解本身是资产**——它标注了同类数据最容易看错的地方。

---

## 0. 一页结论

1. **本方/对方是相对角色，不是列。** 借贷标志决定谁是本校：`借` ⇒ 付款方是本校，`贷` ⇒ 收款方是本校。按列名取「对方」会错掉接近一半的行。
2. **每一侧是「主体 + 它名下的卡 + 开户行」绑成一组。** 支付帐号是主体，银行卡号是它名下的卡，开户行是那张卡的开户行。不能跨方拼列，也不能拿卡号当「支付帐号缺失时的备胎」。
3. **「对方账号」只取支付帐号。** 微信交易一律是支付账号对支付账号；银行卡不是账号。提现/充值时对方账号就等于本方账号，真正移动的那张卡记在卡号/开户行两列。
4. **「收款方的商户名称」是收款方账户的开户人姓名**，不是消费场景的商户名。它跟着收款方走：贷方行落进本方户名，借方行落进对方户名。末尾括号标注主体类型——含「个人」是个人，其余按企业。
5. **户名可以补全。** 同一账号在本文件里只要有一行读到名字，其他行就能按账号名册补。补进来的值单独记在「户名依据」列，与原文读到的值分得开——审查看的是证据强度。
6. **两道闸，任一不过整份拒收。** 表头闸（必需列齐全）+ 值验证闸（七项逐项通过率）。不做「猜着转」。
7. **原始列是证据，标准列是结论。** 原始 28 列一个字不改地保留，后面追加 20 个标准列。原始列丢了就没了，标准列坏了可以重算。
8. **时区按 `+08:00` 解析。** 微信导出的时间戳不带时区标记，按 UTC 会整体错 8 小时。

## 1. 为什么要单独沉淀这一层

事实卡片的翻译层要求「一条源记录 = 一张卡片」，卡片要填「本方/对方/方向/金额/时间」。这些字段在源文件里**不是现成的**：

- 源文件只有「付款方支付帐号」「收款方支付帐号」，没有「本方」「对方」；
- 源文件没有「对方账号」这一列，得从两列里按方向挑一列；
- 源文件的「收款方的商户名称」看着像商户名，实际是开户人姓名，且只描述收款方一侧；
- 提现/充值的「对方」是本人的银行卡，不是外部主体。

也就是说，**翻译层拿到的第一手数据本身就带着四个坑**。这四个坑在四轮沟通里逐个被指出来，下面按顺序记。

## 3. 第一轮：本方/对方是**相对角色**

**原来的理解**：`收款方支付帐号` 是对方，`付款方支付帐号` 是本方。

**问题**：这只在「钱出去」时成立。贷方行里钱是进来的，收款方就是本校。

**改成**：

```
本方方 = 借 ? 付款方 : 收款方
对方方 = 借 ? 收款方 : 付款方
```

并把它做成一道**值验证闸**（方向与本方一致，阈值 98%）：`借` 行里付款方支付帐号必须等于查询账号，`贷` 行里收款方支付帐号必须等于查询账号。这条闸验的不是数据脏，而是**这份数据真的符合本 skill 的假设**——表头长得像、方向规律对不上，说明是另一种取数口径，宁可拒收。

**实测**：699/699 通过。按列名硬取对方的旧逻辑，会错掉其中 336 行（贷方行）。

---

## 4. 第二轮：三列是**一组绑定**

**原来的理解**：对手标识「哪列有值取哪列」，银行卡号是支付帐号缺失时的替补。

**指出问题**：

> 付款方支付帐号、付款方银行卡所属行、付款方银行卡号 这三个字段是绑定在一起的，付款方支付帐号是唯一的，他需要绑定付款方银行卡号……收款方同理。

**改成**：按「方」解析，不按「列」解析。

```
付款方 = { 支付帐号, 银行卡号, 开户行 }
收款方 = { 支付帐号, 银行卡号, 开户行 }
对方方 = 借贷 === "借" ? 收款方 : 付款方
```

后果有两处：

1. **提现/充值**：对方方的支付帐号等于本校，说明是同一主体，钱在本人的支付帐号与本人卡之间移动。判据是「对方方有卡」，但**对方账号仍写支付帐号**（见第六节）。
2. **双标识转账**：对方既有支付帐号又绑着卡（本样本 29 行）。旧逻辑只取支付帐号，把这 29 行的卡号和开户行丢了。

另加一道「卡行成对」闸（有卡必有行，阈值 100%）：577/577 通过。反向的「有行无卡」本样本有 2 行（行 3、行 77），不拒收，逐行告警。

---

## 5. 第三轮：「收款方的商户名称」= 开户人姓名

**原来的理解**：这是消费行才有的商户名。

**指出问题**：

> 收款方的商户名称，他代表的是收款方账户的开户人姓名，括号中有（个人）字样标识的开户人是个人，否则就是企业名称。

**改成**：它是**收款方这一组的第四个字段**，不是某一类交易专属。归属跟着收款方走：

- 贷方行：收款方 = 本校 ⇒ 落进 `本方户名`
- 借方行：收款方 = 对方 ⇒ 落进 `对方户名`

括号解析锚定在**末尾**，名字剥掉标注，类型单独成列：含「个人」⇒ 个人，其余（企业/商户…）⇒ 企业。`(个人)` 这种只有标注没有名字的占位，名字空、类型保留。

**实测**：个人 553 / 企业 146；按侧拆开是本方（贷方）336 行全为个人 —— 这本身就是强证据：账户主是同一个人，不论金额与方向。

**为什么要纠**：把它当「消费行的商户名」，336 行贷方行的户名就无处安放，整体错位。

---

## 6. 第四轮：对方账号只取支付帐号；户名可补全

这一轮同时收到两条意见。

### 6.1 「对方账号」只能取支付帐号

**原来的做法**：提现/充值那 275 行，把银行卡号写进了 `对方账号`。

**指出问题**：

> 对方账号只能是付款方支付帐号、收款方支付帐号，因为微信交易只能是微信支付账号对微信支付账号。

**改成**：`对方账号` 只从支付帐号两列取；支付帐号为空时才退回商户号（消费），再退回只有商户名。银行卡号与开户行各归各列，一列不丢。

**实测变化**：`对方账号类型` 里「银行卡」这个取值归零，分布变成 支付账号 549 / 直连商户号 78 / 间连商户号 65 / 商户名 3 / 空 4；提现 268 + 充值 7 行的对方账号全部等于本方账号。

**口径要记住的一点**：判「是不是提现」看卡，写「对方账号」写支付帐号——**判据与取值是两件事，不能混**。

### 6.2 户名可以补全

**原来的做法**：本行没有户名就留空——借方行的 `本方户名`、贷方行的 `对方户名` 全空。

**指出问题**：

> 本方户名有的是空值，这个你完全可以补全，对方户名也可以根据已知的信息进行补全。

**改成**：先把全表的「账号 → 开户人」和「商户号 → 名称」汇成名册（前提：一个支付帐号只对应一个开户人，本样本 48 个账号无一冲突），再逐行补：

| 缺什么 | 怎么补 | 依据 |
|---|---|---|
| `本方户名` | 按**查询账号**查账号名册 | 同一账号在别的行当过收款方 |
| `对方户名`（对方账号 = 本方账号） | 直接沿用本方户名 | 同一账号，户名必然相同，不算推断 |
| `对方户名`（其他） | 按对方账号查账号名册，再查商户名册 | 该账号/商户号在别的行出现过名字 |

补进来的值写进新增的 `户名依据` 列（`本方户名取自行2（同账号）`），**留空 = 全部来自本行原文**。这条列是必须的：户名一旦补进来，「每一行都能回到原文」就不再天然成立，得让审查看得出哪些是读到的、哪些是推的。

**实测**：本方户名 699/699；对方户名 687/699；415 行用到补全。差的 12 行逐条能解释（见第 10 节）。

**一个实证样例**：行 6 的对方账号 `085e9858e0a36c9f21e8228cf@…` 在全表从未以收款方出现，但行 118 里它是收款方、户名「李长山」——说明这是李长山本人的另一个微信账号。补全不是猜，是**跨行一致性**。

## 7. 判定规则与实测分布

```
1. 对方方.支付帐号 非空 且 ≠ 本方方.支付帐号        ⇒ 转账
2. 否则 对方方.银行卡号 非空
     ⇒ 借 = 提现（零钱→本人卡）；贷 = 充值（本人卡→零钱）
     对方账号 = 对方方的支付帐号（此时 = 本方账号）
3. 否则 借 且 商户号可解析                          ⇒ 消费
4. 否则 借 且 收款方开户人姓名可读（非 `(个人)` 占位）⇒ 消费（只有户名，没有账号）
5. 都不满足                                          ⇒ 无对手
```

| 规则 | 条数 |
|---|---|
| 转账 | 274（其中 29 行是双标识） |
| 提现 | 268 |
| 消费 | 146（直连 78 / 间连 65 / 只有商户名 3） |
| 充值 | 7 |
| 无对手 | 4 |
| 畸形账号（已告警，不拒收） | 6 |

**消费的商户号三种形态都必须认**：直连（纯数字）、间连（一整句「间连交易……【机构】通过单号查询」，账号取单号、户名取机构名、强制企业并告警「真实商户需向该机构查询」）、只有商户名没有商户号。只认直连，146 行消费会全部变成「无对手」。

**无对手必须可解释**：本样本 4 行，两侧账号都是 `-`、商户名是 `(个人)` 占位。这是「有对手但没有任何标识」，不是判定漏了列。

## 8. 闸门

### 8.1 表头闸

必需列：`查询账号`、`付款方支付帐号`、`收款方支付帐号`、`借贷标志`、`交易金额`、`交易余额`、`交易时间`。缺一列拒收。

表头行不要求在第 1 行：在前 10 行里找命中必需列最多的那一行（至少命中 3 个）。找法改成「命中最多」而不是「必须同时含某两列」，是为了让**报错说实话**——原来的写法缺列时会误报「找不到表头行」，现在报「缺少必需列：查询账号」。

### 8.2 值验证闸（七项，任一不过整份拒收）

| 检查项 | 阈值 |
|---|---|
| 查询账号非空 | 100% |
| 借贷标志合法（借/贷） | 100% |
| 金额可解析 | 100% |
| 时间可解析（`yyyyMMddHHmmss` 且是合法时刻） | 99% |
| 方向与本方一致 | 98% |
| 银行卡号与开户行成对 | 100% |
| 收款方开户人可分类（个人/企业） | 100% |

**闸门要被证明会拦**。用两份变异样本验证（脚本 `验证/造变异样本.py`）：变异 A 把「查询账号」改名 → 表头闸拒收、退出码 2；变异 B 把前 80 行借贷标志改成「未知」→ 借贷合法率 88.56%、值验证闸拒收、退出码 2。两次都**不产出标准明细**，只产出拒收报告。

## 9. 产出契约

一个 xlsx，两个 sheet。`标准明细` = 原始 28 列 + 20 个标准列（共 48 列）。

标准列（顺序即契约）：

`行号`、`本方账号`、`本方户名`、`本方主体类型`、`本方银行卡号`、`本方开户行`、`收付方向`、`对方账号`、`对方账号类型`、`对方户名`、`对方主体类型`、`对方支付帐号`、`对方银行卡号`、`对方开户行`、`对方来源列`、`判定规则`、`金额(元)`、`发生时间`、`户名依据`、`告警`

两条写进契约的细节：

- **标准列里不留 `-`**。源文件用 `-` 表示「无」，标准列是结论，统一清成空；原始列保留 `-` 原文。否则下游会把 `-` 当成银行卡号建实体。
- **`对方来源列` 必须写**：`对方账号` 到底取自哪一列，是我方模型最容易出错的地方，逐行标出来才可核。

> **与实体属性规范的对接（2026-11-11 补，见 `05` 与 `01` §2.4 / §13 Q9）**：
> - 卡号/开户行四个标准列应产出为 `属性:本方:银行卡号`、`属性:本方:开户行`、`属性:对方:银行卡号`、`属性:对方:开户行`，而不是裸列名。裸的 `对方银行卡号` / `本方银行卡号` 会被内核的合成候选认成 `counterparty` / `ownerAccount`（`case-mapping.ts:139-166`），既挂不上属性，又会制造错误实体。
> - `收付方向` 目前不在字段目录的 `direction` 同义词内（`case-field-registry.ts:141-146`）。二选一：给词表补 `收付方向`，或让翻译层显式读原始 `借贷标志`；否则该列会落进 `extras`、卡片方向缺失。
> - `对方支付帐号` 也会被合成候选认成 `counterparty`，与 `对方账号` 构成重复候选——按「标准列优先」定序。

`转换说明` sheet 记：源文件 SHA256/字节数、表头行号、数据行数、两道闸逐项结果、绑定关系与列映射、判定规则、对账（五类条数、借/贷金额、户名覆盖、名册条目数）、告警清单。

## 10. 补全的边界（推不出来的就是推不出来）

- **12 行没有对方户名**，逐条解释：4 行是 `无对手`（两侧都没账号，无可补）；8 行是贷方转账，付款方账号在全表里从未以收款方身份出现——其中 6 个还是 `(1522782591)`、`（）(1714876288)` 这种形状异常的值（已同时进告警）。
- **补全只依赖本文件**。跨文件的账号名册是后续能力（接实体层），不是这个 skill 的职责。
- **一个账号一个开户人是前提**。真出现一名多号，现在的实现取「第一行」，不报冲突——这是已知缺口，接实体层时要改成冲突检测。
- **借方行的本方户名**现在靠贷方行反推；整份文件若没有任何贷方行，本方户名就补不出来。这类文件应告警而不是硬编。
- **间连交易的真实商户查不到**：商户号只是收单机构侧的订单号。要追真实商户，得拿这个单号去问机构。

## 11. 与平台流程的接口（待接）

openhive 已有 skill 资产的审核/发布流水线：七态状态机（`draft` / `in_review` / `pending_tech` / `published` / `iterating` / `offline` / `archived`）+ 三道关 + `auto-delivery`（只认 `type='skill'` 且 `status='published'`）。预处理 skill 应当挂在这条流水线上。

两条必须记住的边界：

1. **流水线审的是 skill 本身，不是每一份文件的转换结果。** 所以两道闸不能省——它们保护的是「某份具体文件适不适合这个 skill」，这件事审核时不可能逐份预判。
2. **`gates` 字段目前全仓无人消费。** 闸门的结论现在只写在产物里和调用者的退出码里；要让平台真正拦住坏数据，得让入库链路读这个结论（拒收 → 不落库 + 报「材料格式不支持」），否则「拒收」只是一个文件，没人执行。
