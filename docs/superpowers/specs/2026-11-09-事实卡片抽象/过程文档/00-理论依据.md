## 1. 问题陈述：为什么这件事需要理论

### 1.1 事实

案件数据来源无界：资金流水、话单、住宿、火车、飞机、扫码、订餐、快递……每一类的字段都不一样，且**还会继续增加**。

此前做法是"每来一类数据，给明细表加一批列"。实测结果是：

- 表宽由**业务类型数量**决定，永远追不上；
- 跨类型分析（时空碰撞、串并、轨迹）无法进行——因为每类数据的列不同，无法用一条查询覆盖。

### 1.2 关键观察

民警的问题看着很多，剥掉业务外壳后是有限的几个：

```
谁？   什么时候？   在哪儿？   干了什么？   和谁？   多少钱？
（who / when / where / what / with whom / how much）
```

**来源无穷，问题有限。** 因此正确的抽象对象不是"业务字段"，而是**这几个问题本身**。

### 1.3 由此得到的核心命题

> 把每条源记录翻译成一个**统一格式的事件实例**（事实卡片），事件通过**实体**回答"谁/在哪"，通过**出处**回答"凭什么信"。
>
> 明细层（原文照抄）与分析层（统一卡片）分离；明细层永不随业务类型加列。

这个命题不是我们发明的。它在文献里有名字、有定义、有已知缺陷——见第 2 章。

## 2. 核心理论：事件中心知识图谱（EKG）

### 2.1 定义

事件中心知识图谱（Event-centric Knowledge Graph, EKG）的两类节点与三类边 [T-01]：

| 构成 | 内容 |
|---|---|
| 节点 A | **事件**（event）——发生过的一件事 |
| 节点 B | **实体**（entity）——人、号码、账户、车辆、地点、组织…… |
| 边 ① | 事件 — 事件（时序、因果、共指） |
| 边 ② | 事件 — 实体（**论元角色**：谁参与了这件事、扮演什么） |
| 边 ③ | 实体 — 实体（关系：亲属、通话、转账……） |

**关键结论**：实体中心的图谱是 EKG 的**特例**。所以"做卡片"与"做实体"不是两条路线之争，而是同一张图里的两类节点。

### 2.2 论元模型

Rospocher 等人的事件建模用四要素：**Action / participant / time / location** [T-02]，与 1.2 的（what / who / when / where）一一对应。

- 事件本身承载 what；
- 论元把事件接到实体上，并**说明角色**（入住人 / 付款方 / 主叫 / 收款方）；
- 时间与地点是论元，也是**可查询的维度**——地点必须是实体引用，否则无法跨文件归一。

### 2.3 已知代价（必须在设计时承认）

事件中心模型的通病是**事件节点增长极快、图遍历变慢** [T-01 及相关工程实践]。国内同类专利也把"人、物、事、时间、位置"五要素作为案件知识图谱骨架 [T-30]。

**因此**：不是所有明细行都无条件变成事件。要有**门槛**（是否有可识别的主体、时间、类型），以及分页/上限等读取端约束。

### 2.4 ✅ 采纳规则

| 编号 | 规则 |
|---|---|
| R2-1 | 事件与实体是**两类节点**，不是"事件=实体的属性" |
| R2-2 | 事件到场地的连接**必须带角色**，不能只存一组参与者 |
| R2-3 | 地点必须是实体引用（`entity_id`），不能只存地址字符串 |
| R2-4 | 事件生成设门槛；读取端设上限（沿用现有图谱 1–2 跳、≤50 节点的做法） |

## 3. 溯源理论：出处是独立的一层

### 3.1 国际标准

W3C PROV 把"来源"建成独立的三元结构 [T-03]：

| 概念 | 含义 | 在我们的系统里 |
|---|---|---|
| Entity | 被产生的东西 | 一条事实（实体/关系/事件/明细行） |
| Activity | 产生它的过程 | 一次解析/抽取 |
| Agent | 谁/什么做的 | 机器或民警 |

核心关系：`wasDerivedFrom`（从哪来）、`wasGeneratedBy`（由哪次过程产生）、`wasAttributedTo`（归谁）。

**要点**：出处不是事实的一个字段，而是**事实与来源之间的一条独立记录**——因为同一条事实可以来自多个来源。

### 3.2 出处不能由模型给

*The Provenance Gap* 一类研究给出实证：前沿大模型生成的引用**可验证率极低**，连"用另一个大模型当裁判"都会把编造的引用判为有效 [T-04]。

**结论**：出处必须由**代码**在抽取时按源记录的主键绑定，模型碰不到、也改不了。

现有实现已经踩对：`auth.case_citation` 以 `(fact_type, fact_id, material_id, locator)` 记录，`locator` 由代码写入而非模型输出。

### 3.3 知识来源要分级

业内做法是给每条知识标注来源方式，常见三档：

| 标记 | 含义 | 何时用 |
|---|---|---|
| EXTRACTED | 原文里直接有 | 表格某格、笔录原句 |
| INFERRED | 由已有信息推出 | 由"入住 3 天"推出退房日 |
| GENERATED | 模型生成 | 摘要、归类 |

**必守的一条**：这三档必须能区分，否则"原文没写"和"系统猜的"混在一起，证据链就断了（论元补全的经典问题）。

### 3.4 更正用取代，不用覆盖

事实会被修正。正确做法是**保留旧值 + 记录取代关系（SUPERSEDES）**，而不是原地覆盖：

- 旧值仍在，能回答"当时为什么这么判"；
- 新值生效，能回答"现在是什么"；
- 两者之间的变更历史可查。

现有 `auth.case_fact_change` 就是这一层（`before` 完整快照、`after` 新值、操作人、原因），且只增不改。

### 3.5 允许"不确定"

系统必须能明确输出「不确定」，而不是被迫二选一。对应到现有设计是 `trust_state` 的 `存疑`，以及"证据不足就不合并、只给候选"。

### 3.6 ✅ 采纳规则

| 编号 | 规则 |
|---|---|
| R3-1 | 出处写在独立的引用记录里，一条事实可有多条出处 |
| R3-2 | 出处由代码按源记录主键写入，**模型不得参与** |
| R3-3 | 每条事实标记来源方式（原文/推断/生成） |
| R3-4 | 更正不覆盖，走留痕 + 取代 |
| R3-5 | 证据不足时输出「存疑」，不得默认判真 |

## 4. 事件的身份与粒度

### 4.1 事件不是"一个点"

Vossen & Cybulska 把事件建成五槽模板：**动作 / 时间 / 地点 / 人参与者 / 非人参与者**，并明确指出：**事件粒度是可调参数** [T-05]。

- 收得太紧 ⇒ 每个提及都是独立事件（同一件事被拆成很多条）；
- 放得太松 ⇒ 过度合并（不同的事被吞成一条）。

因此"一条记录算几个事件"不是哲学问题，而是**必须先定的工程参数**。

### 4.2 共指判据

两个事件提及指同一件事，判据是**在同一时间、同一地点、有相同参与者的情况下，描述同一个动作** [T-05]。

跨文档共指公认比文档内更难：文档内可以靠上下文与相邻句，跨文档没有文本桥接 [T-07][T-08]。

### 4.3 事件身份是三档，不是二值

Hovy 等人提出：**完全同一 / 部分同一 / 不同**（quasi-identity）[T-06]。

意义：不要强迫系统回答"是/不是"。**"部分同一"是常态**，它对应我们的"待确认"。

### 4.4 ✅ 采纳规则

**粒度规则（R4-1）：卡片粒度 = 源记录的原子性，不跨行合并。**

| 来源形态 | 卡片数 | 时间 |
|---|---|---|
| 一行含入住时间 + 退房时间 | 1 张 | 区间 `[入住, 退房)` |
| 退房时间缺失 | 1 张 | 开区间，标"进行中/未知" |
| 来源把入住、退房各发一行 | 2 张 | 各为点事件，再用"同一次住宿"连接 |
| 换房、续住各一行 | 每行 1 张 | 同上 |

依据：国内旅馆业数据交换标准 GA 233.1-1999 中，**入住时间、入住天数、续住时间、退房时间本就是同一条旅客记录的不同字段** [T-22]——来源数据自己是"一次住宿 = 一条记录"。

**为什么禁止跨行合并**（R4-2）：合并属于共指层，造卡片属于生成层。两层混在一起，出错时无法区分"抽错"还是"合错"。

**共指判定（R4-3）：三层**

| 层 | 判据 | 处理 |
|---|---|---|
| L1 | 同一源记录（material + sheet + row_no 相同） | 视为同一事件 |
| L2 | 类型同 + 时间同 + 地点实体同 + 主体集合同 + 金额/数量同 | 自动合并，保留全部出处 |
| L3 | 类型同、时间重叠或邻近、地点同、主体至少一个重合，其余有差异 | **不自动合并**，进待确认 |

**同源 / 跨源分开（R4-4）**：同源重复允许 L2；**跨源一律 L3**。依据 4.2 的难度差异，以及代价不对称——**错误合并会污染轨迹且不可见，重复只是多一条且可见**。

**合并必须留依据（R4-5）**：记哪几个字段相同、来源是哪几条、谁确认的，且可拆回。

## 5. 时间

### 5.1 点事件与区间事件

时间数据库的标准区分：**点事件**（发生在一个时刻）与**区间事件**（持续一段）[T-14]。

经典例子：点模型无法区分「一次 4 天住宿」与「两次连续 2 天住宿」，除非另加属性；区间模型天然区分。

因此：话单（点 + 时长）、转账（点）、住宿（区间）、乘车（区间或点+时长），**卡片的时间字段必须支持区间**，不能强行压成点。

### 5.2 双时间

时间事实有两个独立维度（bitemporal）[T-13]：

| 维度 | 回答 | 我们的字段 |
|---|---|---|
| 有效时间（valid time） | 事情**什么时候发生** | `occurred_at` |
| 记录时间（transaction time） | 这条记录**什么时候被写下/入库** | `created_at` / 入库时间 |

现有 `time_type` 的 `发生 / 记录 / 入库` 三值踩对了这一点，必须保留。

### 5.3 精度

时间可能只到日、到分、到秒。**精度是信息的一部分**，不能用一个默认值补全。

- 现有 `precision`（`到日 / 到分 / 到秒`）必须随值一起保留；
- 精度不足时，比较必须按区间处理（"到日"意味着当天任意时刻），不能当具体时刻；
- 缺失就是缺失，标"未知"，**不推测**。

### 5.4 关系集合

Allen 区间代数定义 14 种关系 [T-09]，TimeML 沿用同一体系 [T-10]。

我们**只取四种**：`先`、`后`、`同时/重叠`、`同一事件`。理由：这四种能覆盖"案发前打过电话""案发后乘车离开"这类问题，且每一种都能由时间戳**确定性地**算出来，不需要模型判断。

### 5.5 时序是计算，不是抽取

从**文本**抽取时序关系的可靠度很低：

- 实体对上的标注者一致性约 77% [T-12]；
- 时序关系标注的 Cohen's κ 约 0.59（中等一致）[T-12]；
- 国际评测 TempEval-3 的最好成绩 F1 约 0.53–0.57 [T-11]；
- 用精确 Allen 模式，仍会产生 7–9% 的不一致图 [T-12]。

但我们有个结构性优势：**我们的时间大多来自结构化时间戳**（入住时间、通话开始时间、转账时间）。比较两个时间戳是算术，不是判断。

**结论**：结构化时间走计算；文本时间缺失或模糊时，标"未知"，不抽取、不推测。

### 5.6 ✅ 采纳规则

| 编号 | 规则 |
|---|---|
| R5-1 | 事件时间支持区间（`occurred_at` + `occurred_end`），不得压成单点 |
| R5-2 | 保留 `occurred_raw`（原文）与 `precision`（精度），规范值只用于比较 |
| R5-3 | 区分发生时间与记录/入库时间（`time_type`） |
| R5-4 | 事件间只算四种关系：先 / 后 / 同时重叠 / 同一事件 |
| R5-5 | 时间缺失即标未知；不做模型抽取、不做默认补全 |

## 6. 实体与识人

### 6.1 实体消解的基本流程

标准流程 [T-15]：

```
阻塞（blocking，先按可靠键分桶）
  → 候选对（同一桶内两两比）
  → 判定（规则 / 概率模型）
  → 聚类（判为同一人的连成一组）
  → 人工审核（高代价错误必须由人兜底）
```

**阻塞是关键**：不阻塞就是全表两两比较，数据量一大直接爆炸。可靠键（身份证、手机号）天然是阻塞键。

### 6.2 标识符强度不是等价的

| 标识符 | 唯一性 | 会变吗 | 强度 |
|---|---|---|---|
| 身份证号 | 全国唯一、终身 | 不会 | **最强** |
| 手机号 | 同一时刻唯一 | **会换主人** | 中 |
| 银行账号 | 同一时刻唯一 | 会销户重开 | 中 |
| 姓名 | 大量重名 | 会改 | **最弱** |

依据：实体消解中"强标识符优先、弱标识符只作辅助"是基本纪律；把弱标识符当主键会导致大规模错误合并。

### 6.3 时间感知消解：别名必须带有效期

属性会随时间演化（换号、改户名）。因此别名不能只是字符串集合，必须带**有效期区间**：

- Christen & Gayler 的自适应时间感知实体消解 [T-16]；
- 带隐藏时间信息的规则型消解 [T-17]；
- 2025 年的"不一致衰减"（disagreement decay）：时间越远的冲突证据权重越低 [T-18]。

**直接后果**：`case_entity.aliases text[]` 这种纯字符串结构**不足以支撑正确消解**。

### 6.4 二次放号

手机号注销后会被重新投放（"二次放号"），原机主的绑定可能被新机主接管，已有刑事判例 [T-28]。

工业界的处理办法是计算 **LPRD（Last Possible Reassignment Date，最后可能的重新分配日期）**，用时间阈值判断"这个号在当前时点还是不是同一个人" [T-27]。

**规则推论**：同一个号码的两段使用期**时间不重叠**时，**不得合并**为同一人。

### 6.5 ✅ 采纳规则

| 编号 | 规则 |
|---|---|
| R6-1 | 合并优先级：身份证号 > 手机号 > 银行账号 > 姓名 |
| R6-2 | 每个标识符带有效期区间；**区间不重叠的同号不得合并** |
| R6-3 | 有证号且相同 ⇒ 自动合并 |
| R6-4 | 无证号、同手机号且区间重叠 ⇒ 自动合并，标注依据 |
| R6-5 | 仅姓名相同 ⇒ **不得合并**，只能作显示/候选 |
| R6-6 | 多项相容但无强标识 ⇒ 候选，交人工认定 |
| R6-7 | 每次合并写依据 + 留痕，且可拆回 |

## 7. 地点

### 7.1 地点是实体，不是字符串

地点出现在多种形态里：标准地址、宾馆名、商户名、车站名、基站小区。它们必须归到**同一个地点实体**上，否则跨文件的"同一个地方"永远对不上。

地名消歧研究表明：**地址层级**是消歧最有效的特征 [T-26]；把地址、地名、地点描述建成图（层级 + 别名 + 邻近）优于字符串匹配。

### 7.2 国内标准地址体系

"一标三实"标准地址的层级是 [T-19][T-20][T-21]：

```
省 → 市 → 县 → 乡镇(街道) → 社区 → 街路巷(小区) → 建筑物 → 单元房屋
```

配套标准：`GA/T 1219-2015`（地址/房屋基础信息数据项）、`GA/T 2000.32-2014`（地址元素分类与代码）、`GB/T 2260`（行政区划代码）。

### 7.3 为什么不做半径

犯罪地理学的**可变面元问题（MAUP）**：同一批点数据，换一种聚合单元，相关性结论可能反转 [T-23]。因此"多远算同一个地方"**没有唯一正确值**，任何半径都是业务选择。

参考量级（仅作参考，不是规范）：

| 来源 | 数值 |
|---|---|
| 国内时空碰撞专利实施例 [T-25] | 案发点 100 m 碰撞、10 km 活动范围、案发前 3 天 / 后 1 天 |
| 住宅盗窃近重复研究 [T-24] | 缓冲 250 m、上限 600 m |
| 住宅盗窃特征聚类尺度 [T-24] | 约 2.2 km |

既然没有唯一值，且本轮业务不需要范围查询，**不做半径**就是最稳的选择：不引入一个日后无法解释的口径。

### 7.4 ✅ 采纳规则

| 编号 | 规则 |
|---|---|
| R7-1 | 地点一律建为地点实体（`case_entity.type = 地点`） |
| R7-2 | 实体上存三样：标准地址（按一标三实拆级）、原始地址文本、别名 |
| R7-3 | 地点粒度定到**场所/建筑物**；房间号是事件属性，不参与地点判定 |
| R7-4 | 判定同一地点：已解析层级**全部一致**；缺级不参与比较但必须标出 |
| R7-5 | 只有名称时按名称归一（去后缀、统一全半角/括号/空格）后比 |
| R7-6 | 判不了（同名不同址、名址不可比）⇒ **不合并**，标待确认 |
| R7-7 | 不引入坐标、不做距离与半径计算 |

> **备注**：层级存全后，「同社区 / 同街道」这类**包含关系**筛选不需要坐标也不需要半径，随时可加。它与"算周边"是两件事。

## 8. 被否决的方案及理由

否决理由同样有约束力——它们说明"为什么不能走回头路"。

| # | 否决方案 | 否决理由 | 依据 |
|---|---|---|---|
| 8.1 | 每类数据加一组列 / 建一张明细表 | 表宽由业务类型数量决定，永远追不上；跨类型查询无法写 | §1.1 实测 |
| 8.2 | 入库时定死"多远算同一个地方" | 没有唯一正确值（MAUP）；且本轮不需要范围查询 | [T-23] §7.3 |
| 8.3 | 跨源疑似同一件事自动合并 | 文献表明跨文档共指最难；错误合并污染轨迹且不可见 | [T-07][T-08] §4.4 |
| 8.4 | 仅凭姓名合并实体 | 重名极普遍；一旦错并，两个人的轨迹混成一个 | §6.2 |
| 8.5 | 自动做因果推断 | LLM 因果分类接近随机且严重过度自信（多项 2025 评测）；把非因果序列判成因果 | [T-29] §5.5 |
| 8.6 | 让模型给出处 | 生成的引用可验证率极低，LLM 裁判也查不出 | [T-04] §3.2 |
| 8.7 | 事件属性全塞 JSONB | 地点要参与实体链接、时间要排序、金额要统计；塞进去后变成全表扫 + 代码内判，约束也写不了 | §2.2 §7.1 |
| 8.8 | 新建"卡片表"取代 `case_event` | 现有 9 个代码文件在读 `case_event`；另起一套 → 两套事件模型、读取端分叉 | 代码核实，见 `讨论记录.md` §3.6 |

### 8.5 的补充说明

我们**不是**否定因果关系的重要性，而是否定**自动推断**它：

- 系统只呈现时间顺序（"案发前 3 小时有通话"）；
- 因果结论由民警下，系统保留人工填写"依据"的位置；
- 依据：模型在因果分类任务上接近随机，且置信度严重校准失当。

## 12. 这套理论不能保证什么

写清楚边界，避免把"有理论基础"误当成"结果一定对"：

1. **不保证抽取正确。** 理论解决的是"怎么表示"，不是"从原文抽得准不准"。抽取准确率要靠评测集单独度量。
2. **不保证跨源共指能自动完成。** 文献本身承认这是最难的场景；我们的选择是交给人。
3. **不保证实体一定认得对。** 没有强标识符的人只能停在候选——这是设计选择，不是缺陷。
4. **不保证事件图不膨胀。** EKG 的已知代价；只能靠门槛与读取端上限控制。
5. **不保证因果。** 我们明确不做自动因果推断，理由见 §8.5。
