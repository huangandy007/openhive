# 实体属性 · 标记与入库规范

> **状态**：规范定稿，待实现（2026-11-11）
> **日期**：2026-11-11
> **定位**：回答一件事——**实体的业务属性（开户行、银行卡号、证件号……）由谁标、怎么标、存哪里、怎么合并、怎么读**。上游是 `01-事实卡片与数据翻译-设计.md` 的实体层与 §2.3 出处铁律；输入端口径见 `03-微信流水预处理-字段口径与转换规则.md` §0 第 2 条（「主体 + 它名下的卡 + 开户行」绑成一组）。
> **结论先行**：**用现成的 `case_entity.attrs`（jsonb），不建实体属性表。** skill 负责把属性列标出来，入库端负责写进去。
> **过程**：本文按讨论顺序组织。**被推翻的方案也记下来**——它标出了同类需求最容易过度设计的地方。

---

## 0. 一页结论

1. **存储不动**：`case_entity.attrs` 已经是 `jsonb NOT NULL DEFAULT '{}'`（`packages/auth/src/migrations/0031_case_fact_layer.sql:70-80`），读侧 `query_entities` 已原样返回给 AI（`case-mcp-tools.ts:169-184`）。**不加表、不加列、不加迁移。**
2. **标记语法**：skill 用 `属性:<归属>:<键>` 作为列名，如 `属性:对方:开户行`。入库端一条正则识别，不参与四层字段召回。
3. **归属**只有两个值：`对方`、`本方`，决定属性挂到哪个实体上。
4. **值明文原文**，不做掩码、不做脱敏（2026-11-10 拍板）。
5. **出处内嵌在值里**：每个属性值携带「材料#工作表#行号」，满足 §2.3「要么指到文件·表·行，要么标推断」。
6. **合并是追加去重，不是覆盖**。现有 `attrs || excluded.attrs` 的键级覆盖必须先改掉，否则会静默丢证据。
7. **读侧零改动**：AI 已经能读到 `attrs`；按属性值反查（「哪些账户开户行是招商银行」）将来加一个 GIN 索引即可，仍不建表。
8. **前置缺口**：表格链路目前**不建实体**（`跑表格` 只写 `case_fact_row`）。标得再清楚，也要先有「明细 → 对手实体」这一步，属性才有挂载点。

---

## 1. 问题是什么

用户的实际提问是：**「AI 交互时，问实体对应的银行卡、开户行，问不到。」**

拆开看，这不是一个「存储缺失」问题，而是三处断裂：

- 值**在行上有**：`对方银行卡号`、`对方开户行` 不在字段目录里，认不出，逐行落进 `case_fact_row.extras`，键是原表头（`case-rows.ts:175-189`）；
- 实体**上有位置没内容**：`case_entity.attrs` 存在，但全仓唯一写入点只写了细类（`case-ingest.ts:722`，`attrs: { subtype: 细类 }`）；
- 中间**没有搬运步骤**：从「明细行」到「实体属性」没有任何代码，表格来源甚至连实体都不建（见 §8）。

一句话：**数据是全的，语义挂不上去。**

## 3. 方案取舍

### 3.1 曾提议：独立表 `case_entity_attribute`

动机是三条未来需求：逐属性出处、属性级信任态与人工处置、按属性值精确反查并建索引。

**否决理由（2026-11-11，用户指出）**：当前需求只有「问得到」；jsonb 已经能内嵌出处、能用数组表达多值、能加 GIN 索引做反查；为尚未出现的需求提前建表，是与 `case_entity.attrs` 做重复的事，违反「简单优先」。

**三条顾虑与 jsonb 的对应解法：**

| 顾虑 | jsonb 解法 |
|---|---|
| 说不出处 | 值里内嵌 `出处: "材料#工作表#行号"` |
| 冲突被悄悄覆盖 | 每个键存数组，不同值并存；合并规则显式定为「追加去重」 |
| 不能按属性反查 | 需要时对 `attrs` 建 GIN 索引，`@>` 查询即可 |

**将来什么情况下值得回头建表**：属性需要逐条人工确认/排除、需要审计每一次修改、或属性值规模大到 jsonb 更新成本不可接受。**这三种情况现在都没出现。**

### 3.2 采纳：`case_entity.attrs`

不新增表，不新增列。本规范只定义**怎么标、怎么写、怎么合并**。

### 3.3 为什么不能直接把值裸塞进去

两个坑，必须用规范挡住：

- **键漂移**：`开户行` / `开户银行` / `银行名称` 是同一个意思。若拿原表头当键，库里会长出三个键，AI 以后要猜。
- **静默覆盖**：`attrs || excluded.attrs` 会把「乙材料说招商银行」直接盖掉「甲材料说建设银行」，且谁也不知道发生过。

所以键必须来自**受控词表**，合并必须**追加**。

## 4. 列名规范

### 4.1 语法

```
属性:<归属>:<键>
```

- **归属**：`对方` | `本方`。决定写到哪个实体的 `attrs` 上。
  - `对方` → 本行的对手账户实体（`counterparty` 对应实体）；
  - `本方` → 本行的本方账户实体（`ownerAccount` 对应实体）。
- **键**：受控词表中的叶子词，大小写、别名一律由 skill 归一，**入库端不做同义词匹配**。
- **值**：明文原文，允许整列为空；空值不写属性。

### 4.2 首批词表

| 键 | 说明 | 示例值 |
|---|---|---|
| `开户行` | 银行卡的开户银行 | `招商银行` |
| `银行卡号` | 该实体名下的银行卡号 | `6214…` |
| `证件号` | 证件号码（身份证等） | `3305…` |

词表放在独立的小文件（建议 `case-attribute-registry.ts`），**不放进 `case-field-registry.ts`**：标准字段参与候选字段集与表类型投票，属性混进去会污染识别。

### 4.3 识别规则

入库端用一条正则判：

```
^属性:(对方|本方):(.+)$
```

命中即：
1. 该列**不参与**四层字段召回；
2. **不进**「未认出」清单，**不进**待确认弹窗；
3. 原文照旧留在 `extras`（键为原表头），原文不失（A16「原始值从不改写」）。

### 4.4 为什么用分隔符，而不是直接写「对方开户行」

因为入库端要能**不看键表**就判出「这是属性列，不要拿去做字段识别」。`属性:(对方|本方):` 这一段是唯一确定依据；写「对方开户行」还得先查词表才知道它是不是属性，且与「对方户名」这种标准字段难以区分。

### 4.5 位置

**与数据列同表、同行**，不单独开 sheet。

原因：`readSheets` 会把每个 sheet 都当数据表解析（`maxSheets: 8`），多开一张 `_属性` sheet 就多一份误判与被截断的风险。

### 4.6 skill 侧的职责边界

skill **只需**：认出哪些列是属性、把列名写成上述规范、把值保持明文原文。

skill **不需要也不应该**：决定实体 id、做账号归一之外的实体合并、判断属性属于哪个人。实体身份规则留在内核一处，否则不同 skill 各算一套，同一个账户会变成两行。

## 5. attrs 形状与合并规则

### 5.1 形状

```json
{
  "开户行":   [{ "值": "招商银行", "出处": "mat_xxx#Sheet1#12" }],
  "银行卡号": [{ "值": "62148300xxxx1234", "出处": "mat_xxx#Sheet1#12" }],
  "证件号":   [{ "值": "330501199001011234", "出处": "mat_xxx#Sheet1#12" }]
}
```

规则：

1. 每个键的值是**数组**，元素固定两个字段：`值`、`出处`；
2. `出处` 格式为 `<material_id>#<工作表名>#<行号>`，与 `case_citation` 的行级 id 同形；
3. 同键同值**只保留一条**，出处取该值首次出现的那一行；
4. 同键不同值**并存**，一条都不删；
5. 不改写值本身：明文原文，不做掩码、不做格式化。

### 5.2 合并规则

写入前先读出现有 `attrs`，按键合并：

- 现有键没有该值 → 追加；
- 已有同值 → 跳过（保留原出处）；
- 同一行同时产出的多个属性 → 各自独立写入。

**必须替换掉现有实现**：`case-fact-store.ts:73` 的 `attrs = auth.case_entity.attrs || excluded.attrs` 是**键级覆盖**，直接用会静默丢证据。改为显式的「读 → 合并 → 写」，或在 SQL 里用 jsonb 数组拼接表达式。

### 5.3 卡号与开户行是配对的

`03-微信流水预处理-字段口径与转换规则.md` §0 第 2 条已确认：**支付帐号是主体，银行卡号是它名下的卡，开户行是那张卡的开户行**。

本规范**不引入复合键**，配对关系用**同一条出处**表达：同一次观察里写入的 `银行卡号` 与 `开户行` 共享同一个 `出处`，读侧按出处即可配对。

已知边界（记入 §9）：若某卡号先以单独一列出现、之后才出现带开户行的行，去重后可能留下没有配对信息的代表出处。当前数据（微信流水）里两列同行出现，暂不处理；真实数据出现该形态时再定规则。

## 7. 读侧与问答

**读侧不改。** `query_entities` 已返回 `attrs`（`case-mcp-tools.ts:169-184`），AI 可直接回答：

- 「这个对方账户的开户行是什么？」→ 取该实体 `attrs.开户行`；
- 「这个账户有哪几张卡？」→ 取 `attrs.银行卡号` 数组；
- 「这个结论哪来的？」→ 取对应元素的 `出处`，回 `case_fact_row` 核原文。

**反查（将来）**：「哪些账户的开户行是招商银行」需要 `attrs` 上的 GIN 索引，`attrs @> '{"开户行":[{"值":"招商银行"}]}'` 即可。现在不做，等真实查询出现。

---

## 8. 前置缺口：表格链路不建实体

这是当前最重要的一条，单独列。

- `跑表格`（`case-ingest.ts:398`）只写 `case_fact_row`，不建实体、不建关系；
- 全仓唯一 `upsertEntity` 调用在**文本抽取分支**（`case-ingest.ts:716`）。

因此：**对表格来源的数据，库里的对手账户实体本来就不存在。** 属性规范解决「标明白」，但要让 AI 真问得到，必须先补「明细 → 对手实体」这一步（属于 `01` 设计里的翻译层）。

**建议顺序：**

1. 补「表格 → 对手实体/本方实体」最小步骤；
2. 按本规范识别属性列并写入 `attrs`；
3. 改 skill 输出 `属性:<归属>:<键>` 列；
4. 真栈验收（问银行卡、问开户行、两来源冲突）。

## 9. 未决事项

1. **银行卡号要不要实体化。** 当前作为属性。若出现「按卡号反查是谁的账户」，它应升级为 `账户` 实体（subtype=银行卡）；关系类型里暂无「绑定」，届时需一并定。
2. **属性级信任态。** 现在属性没有「已确认 / 已排除」；需要人工逐条处置时，再评估是否升级为独立表。
3. **反查索引。** 需要时给 `attrs` 加 GIN，不建表。
4. **户名归属。** `对方户名` 是账户属性还是人？按 `01` §3.8，户名不是人；除非有实名登记关系。当前仍按账户侧处理。
5. **事件属性是否同规。** `case_event.attrs`（`01` §3.5）将来可复用同一套「键 + 值 + 出处」形状，但事件没有「对方/本方」归属，需另定标记方式。
6. **词表版本。** skill 产出的键必须在内核词表内；skill 版本与词表版本如何校验，落在转换说明里，尚未定。

## 10. 验收判据

实现完成后逐条验：

1. 属性列不出现于「待确认」弹窗与「未认出」清单；
2. `query_entities` 返回的 `attrs` 里有 `开户行`、`银行卡号`，且带 `出处`；
3. 「这个账户的开户行是什么」能答出值，并能按出处回查原行；
4. 两份材料对同一账户给出不同开户行时，**两条都在**，不互相覆盖；
5. 同一值在多行重复出现时，只留一条，库不膨胀；
6. 原始列原文仍完整存在于 `extras`。
