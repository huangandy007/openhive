## 一、议题与背景

### （一）问题的发现

对本项目真文件（微信账户流水，28 列 × 699 行）按现有主链逐站实跑，第二站「列识别」暴露问题：

1. **28 列仅认出 6 列**：查询账号、交易金额、交易余额、交易时间、借贷标志、收款方的商户名称。另有 2 列记「待确认」，18 列进入 `extras`。
2. **`case_fact_row.counterparty`（对方账号）整列为空。** 699 行入库、跳过 0 行，但系统给不出对手方。
3. 原文未丢失——未认出的列按原表头堆在 `extras` 里。**数据是全的，语义是缺的。**

### （二）病因

现有字段目录假设「一列 = 一个固定语义」，据此把列贴到字段上。但本批数据里 `付款方支付帐号` 这一列的意思**逐行变化**：

- 借方行：该列即本方，`收款方支付帐号` 为对方；
- 贷方行：该列即对方，`收款方支付帐号` 为本方。

即同一列在不同行扮演不同角色。**「对方账号」这个答案不在任何一列里，而在两列的比较结果里。** 识别层只有列、没有行，因此无论怎么选列都选不出它。

会议确认：这不是「字段表少了几列」的问题，是**识别层与翻译层的职责错位**——识别层被迫替翻译层做逐行判断。

### （三）原方案的局限

此前讨论的解决方向是增强识别能力（扩充词典、特征规则、模型兜底）。会议认为该方向仍有必要，但**单独使用不能解决本问题**：模型与词典能提高「列认对」的比例，却无法把逐行变化的相对角色翻成绝对角色，也无法在上千行量级上给出可复核的依据。

### （四）本次议定方向

改由**预处理层**在入库之前完成翻译：以 skill 把原始文件转换成标准格式副本，副本落在指定文件夹；人看过副本后，右键该文件夹执行解析入库，系统逐个文件入队解析。

会议一致认为该方向可行，并明确其价值在于**把「解释」与「落库」拆开**：副本可看、可改、可重做，转错不产生垃圾数据；入库退化为纯机械动作；一种数据格式对应一个 skill，新数据源是「增加一个适配器」，不改内核——与「薄界面 + 厚 skill」的架构一致。

## 二、议定事项

### （一）总体流程

```
原件（项目材料目录）
   │  ① 预处理：skill 读原件，校验后写副本
   ▼
副本目录（标准格式 xlsx + 转换说明）
   │  ② 人工复核：打开副本看结论与依据
   ▼
右键副本文件夹 →「解析该文件夹下的文件」
   │  ③ 逐个文件建材料、入队
   ▼
case_ingest_job → case_table_format → case_fact_row
   │  ④ 解析入库（此时不再判断语义，只做搬运）
   ▼
事实卡片 / 实体 / 关系
```

**议定：**

1. 预处理**不改动原件**，只产出副本；原件永久保留在项目材料目录。
2. 副本存储在**另行指定的文件夹**，与原件物理分开，便于人工复核与批量入库。
3. 入库环节沿用现有机制，**不新增解析逻辑**。

### （二）预处理层的职责边界

预处理层只做三件事：

1. **准入判定**：判断这份文件是否属于本 skill 能处理的数据格式；
2. **角色翻译**：把相对角色（付款方/收款方）翻成本方/对方/方向；
3. **格式固定**：输出列名、列序、取值口径统一的副本。

**不做**：实体消解、关系抽取、事件合并、跨文件归并。这些属翻译层之后，预处理不能越位。

### （三）准入：两道闸，任一不过整份拒收

仅凭表头匹配不足。实测表明，表头完全匹配的文件，其值行为也可能与本 skill 的假设相反（如另一家银行的导出以「借」记银行视角的流出，方向正好相反）。故设两道闸：

| 闸 | 验什么 | 不过怎么办 |
|---|---|---|
| 表头闸 | 必需列是否齐全 | 拒收，说明缺哪一列 |
| 值验证闸 | 值的行为是否符合假设（方向一致性、金额/时间可解析、字段绑定完整性、主体可分类等） | 拒收，说明哪一项低于阈值、实测多少 |

**议定：**

1. 拒收时**不得产出标准格式文件**，只产出拒收报告；文件名须能区分（`-拒收报告.xlsx`），避免下游误当可用副本。
2. 拒收理由必须**可操作**——说清与本 skill 的哪一条前提对不上，不得只写「该文件不能使用本 skill」。原实现中「缺列」误报为「找不到表头行」的做法已纠正。
3. 阈值不放宽换取通过率。值验证不过说明取数口径不同，应由人判断该找哪个 skill，不由脚本猜。

### （四）副本的列结构：四组并存

会议否决「副本只留本方/对方两列」的做法。理由：只留结论，判断过程即消失；一旦判反，副本看起来一样整齐。

副本须同时装下四组：

| 组 | 内容 | 作用 |
|---|---|---|
| 一、源列原样 | 原件全部列，一字不改、一列不删、位置不动 | 证据 |
| 二、系统判定 | 本方账号、对方账号、方向、账号类型、判定规则 | 结论 |
| 三、判定依据 | 对方账号取自哪一列、户名是原文读到的还是推来的、逐行告警 | 可核对 |
| 四、溯源 | 原件行号 | 可回查 |

原则：**原始列是证据，标准列是结论。** 标准列坏了可以重算，原始列丢了就永远没了。

### （五）转换说明随副本同行

每份副本必须配一份转换说明，随副本一起存放，内容至少包括：

1. 使用的 skill 名称与版本；
2. 表头匹配结果、未认出的列；
3. 值验证逐项通过率与阈值；
4. 未成功转换的行数与原因；
5. 原件指纹（SHA-256）与字节数。

**议定：** 原件指纹必须有，用于校验副本与原件是否对应；原件被替换或更正后，副本不得继续被当作现行副本入库。副本自身若被人工修改，亦须能够识别（待定，见第四节）。

### （六）批量入库：右键文件夹

**议定：** 支持对文件夹整体执行「解析该文件夹下的文件」，系统逐个文件建材料、逐个入队，由既有作业队列按序处理。

落点说明（均沿用现有机制，不新建）：

1. **幂等**：材料表以 `(project_id, 指纹)` 唯一，同一文件重复拖入不产生第二条材料；
2. **入队**：人工触发的作业以过去时刻入队，从而置顶于队列；
3. **重解析**：已有材料可右键「重新解析」，显式要求重跑；**上传本身只落盘、不入队**，不因重拖而重跑（2026-11-12 定，见 `07` §4）；
4. **状态**：材料状态沿用 未入队 → 排队中 → 解析中 → 已解析 / 有问题，人工跳过为终态。

### （七）skill 的治理：走既有七态流水线

会议确认，预处理 skill **不需要另建机制**，直接作为资产走现有流水线：

- 状态：`draft` → `in_review` → `pending_tech` → `published`，另有 `iterating` / `offline` / `archived`；驳回为 `in_review → draft` 的一次转移；
- 角色：作者（`author`）→ 业务审核（`business_reviewer`）→ 技术发布（`system_admin`）；
- 送达：`auto-delivery` 只认 `type='skill'` 且 `status='published'`；
- 落地：发布目录即副本来源目录；版本、迭代说明、下线原因、可见范围（全局/部门/指定人员/个人）均为现成字段。

**议定：** 「一种数据格式一个 skill」，新格式即新资产，各走一遍审核发布，不改代码。

### （八）审核覆盖范围的界定（重要）

会议明确一条边界，防止误以为「审核通过 = 转换结果正确」：

> **流水线审核的是 skill 本身，不是「这份文件用这个 skill 转出来对不对」。**

核心理由：现有审核是**流程性**的——它记录「谁在何时放行」，不检查 skill 内容，更不检查 skill 面对某一份具体文件会产出什么。经代码核对，生命周期中声明过关要求的字段全仓无人消费，运行时真正拦人的是「当前状态」与「操作角色」。

**由此议定：**

1. 两道技术闸**不可省略**，且必须留在 skill 内、由每次运行执行；
2. 发布前的样本验证由作者负责；
3. skill 包内应附**金标准样本**（原件 + 期望副本），技术发布时由审核人对照一眼。此机制目前不存在，列为待建事项（第三节）。

### （九）全员发布的污染风险

skill 一经发布即对可见范围内全员生效。若转换规则有错，则所有人生成的副本同期出错，且错误形态一致、不易被发现。

**议定：** 金标准样本 + 版本号 + 下线能力三者配套使用；发现规则错误时先下线，再迭代发布，不靠口头通知。

## 三、风险与防控

| 序 | 风险 | 防控措施 | 状态 |
|---|---|---|---|
| 1 | 副本与原件脱节：原件后来被替换或更正，副本不会随之变化 | 以原件指纹校验；不一致即提示重做 | 议定 |
| 2 | 两个 skill 都能处理同一份文件 | 设优先级，或由人工选择 | 待定 |
| 3 | 格式微调即整份拒收：同一家渠道新增一列，表头即不完全一致 | 做「接近匹配 + 列出差异」，由人确认后放行 | 待定（与「不猜着转」原则存在张力，需明确确认动作与责任归属） |
| 4 | 副本被人工修改：人可能在 Excel 里改动单元格 | 须能识别「该副本已非系统产物」 | 待定（需定：改了还能不能入库、如何标记） |
| 5 | skill 规则错误波及全员 | 金标准样本、版本、下线 | 议定（机制待建） |

## 四、未决事项

1. **新格式由谁写、怎么加。** 现有路径是开发编写并走流水线；备选是现场用自然语言描述「哪列是付款方、哪列是收款方」临时生成转换配置。前者稳、后者快，尚未取舍。
2. **拒收结论如何真正拦住入库。** 目前拒收只是「不产出副本」，缺少副本的文件自然不入库；但若人工把原件直接放到解析入口，现有链路仍会解析。需要入库链路读取准入结论——否则「拒收」只是文件，不是门。
3. **副本目录规范。** 命名规则、按项目隔离、副本与原件是否同项目，均未定。
4. **人工修改过的副本。** 能否入库、如何标记、由谁批准，未定。
5. **同一账户的副本跨文件归并。** 户名补全目前只在本文件内生效；跨文件名册属实体层职责，需另行对接。

---

## 五、结论

1. 同意「预处理后再入库」方案，作为数据文件入库链路的正式组成。
2. 预处理层以 skill 承载，一种数据格式一个 skill，走既有七态审核发布流水线。
3. 副本必须同时装下「原文、判定依据、结论」三样，并配转换说明与原件指纹。
4. 准入以两道闸（表头、值验证）执行，任一不过整份拒收，拒收理由须可操作。
5. 批量入库沿用「右键文件夹解析」与现有作业队列，不新增解析逻辑。
6. 业务审核与技术发布不替代技术闸；发布前须附金标准样本（机制待建）。
