# 数据流全景

> 本文回答一个问题：**这套系统里的数据，从哪来、经过哪些站、到哪去。**
>
> 内容按流程组织，不重复字段定义与规则细节——那些在 `01-事实卡片与数据翻译-设计.md`（下称「设计文档」）里。每节末尾标注设计文档的对应位置，便于对照。
>
> 定位：这是**读图用的索引件**，不是规范。当两者冲突时，以设计文档为准。

---

## 摘要

整个系统只有**三条往里写的流、两条往外读的流**，外加一条横切的「重来」流：

- **写**：入库主链 / 学习回流链 / 修正与重建链
- **读**：AI 取数链 / 页面取数链（同一根管子，两个出口）
- **重来**：规则或模板版本变化后，按新版本重放

跨这几条流还挂着**四本账**：入库作业、异常告警、AI 候选、出处。

判据只有一条（设计文档 §0.0）：

> **一切数据的最终消费者是 AI；界面只负责让数据变正确、让人能复核 AI。**

所以下面每条流，都要问同一句话：**这条流断了，AI 会不会答错、而且错得像个正确答案。**

---

## 一、入库主链：一份材料进来，走过六个驿站

（设计文档 §2.2、§4.0、§7.9）

```
① 上传        → case_material 一行 + case_ingest_job 一条
② 识别        → 列映射（列下标 → 字段名），四层召回
③ 明细落库    → case_fact_row，一行一条，原文照抄
④ 出处绑定    → case_citation(fact_type='row' / 'event')
⑤ 翻译成卡片  → case_event + event_participant + relation + entity_alias
⑥ 收尾        → job 状态、material.parse_status
```

### 1.1 数据在这条链上变形了两次

**第一次变形，在 ②③ 之间：「看到一个格子」→「知道这个格子叫什么」。**

这一步只改标签、不改值——`5000.00` 还是 `5000.00`，只是多了个名字叫「交易金额」。所以它**错了不会马上暴露**，会一路错到底。现有的四层召回、单位闸、面积闸都是在出口兜这一层（`#011-02`、`#011-03`）。

**第二次变形，在 ③⑤ 之间：「一行」→「一张卡片」。**

这是新增的一层，也是整套设计的心脏（设计文档 §4.0）。它做四件事：

1. **定行**——哪些行算数（排除表头重复行、合计行、空行；跳过行数必须上报）；
2. **抽槽**——每格填到九格的哪一格（槽位来自 `case_card_template`，映射是数据，不是代码）；
3. **归并实体**——同一个账号认成同一个账户（内存 Map，一份材料只查库几百次）；
4. **落库**——卡片、参与者、关系、别名、出处一起写，一个材料一个事务、500 行一批。

两次变形之间的差别很重要：第一次错了是**标签错**，改个映射就能修；第二次错了是**事实错**，已经在库里长成了一张卡片，只能重放。

### 1.2 这条链现在跑到哪

| 步骤 | 状态 | 说明 |
|---|---|---|
| ① 上传 | ✅ 已有 | |
| ② 识别 | ✅ 已有 | 四层召回 L0–L3 |
| ③ 明细落库 | ✅ 已有 | 原始行全文入 `case_fact_row`，未知列进 `extras` |
| ④ 出处绑定 | ⚠️ 表在人在，写入无人 | `case_citation` 早已支持 `fact_type='row'/'event'`，但至今没有一段代码往里写 |
| ⑤ 翻译成卡片 | ❌ 一行代码都没有 | |
| ⑥ 收尾 | ✅ 已有 | |

**结论：入库链走到「照抄」就断了。** 库里现在是「一堆原文行 + 一堆空壳卡片」，AI 问「谁给谁转了多少钱」时，实际仍然只能看见列名。后面两条读的流管子修得再完整，流的也是空水。

## 二、学习回流链：人对过一次，下次就自动

（设计文档 §6.3、§6.4、§6.5）

它不是独立的一条链，是插在主链 ② 上的一个回环：

```
人点「确认这一列是交易金额」
  → 同一事务写记忆（别名 / 数据源档案 / 模板转正）
  → 记忆版本 +1（让旧格式缓存与旧翻译结果全部不可达）
  → 下次同一份表头进来，② 直接命中，不再问人
  → hit_count +1（判断这条记忆值不值得留）
```

模板转正走同一条闭环，只是把「写别名」换成「写 `verified_at`」。

### 2.1 难点不在「写进去」，在「写进去的东西不能污染旧数据」

每一条记忆写入都必须伴随**版本号 +1**，让格式指纹对不上——否则会出现「表头一模一样、但单位声明变了」时缓存照旧命中、单位闸根本不跑的静默错（`#011-01`）。

还有一条容易被当成可选项、实际是必需的支流：**撤销**。别名置 `revoked_at`、版本再 +1，让撤销后的旧缓存同样不可达。**没有撤销入口的学习，是把一次误判固化成了默认值。**

### 2.2 防「越学越错」的四道闸

1. 写别名前过单位闸；
2. 别名键用**原始表头**，不做归一化（归一化会丢语义）；
3. 冲突**不覆盖**，必须人确认（后到覆盖会让结果随到达顺序漂）；
4. 一切可撤销，且撤销后旧缓存不可达。

## 三、修正与重建链：改一处，下游全刷

（设计文档 §3.7、§4.0.4、§6.4）

人改一张卡片，或者规则/模板版本变了之后，数据要往回退再重走：

```
人改卡片 / 规则版本变了 / 模板版本变了
  → case_fact_change 记一笔（谁改的、为什么改、改成什么）
  → 该材料按新版本重放翻译
  → 卡片 id = hash(材料, 表, 行号, 规则版本, 模板版本)   ← 版本一换，id 就换
  → 旧卡片作废，新卡片写入
  → 关系不能增量累加，必须「先删、再按卡片 group by 重算」
```

**一条硬约定：卡片是唯一事实，关系只是汇总。**

- 关系任何时候都能从卡片重算出来；
- 反过来不成立——从关系回不到卡片。

所以凡是想「直接改关系表」的改动都是错的；凡是想「关系增量累加」的优化，在重解析场景下都会算重。

## 四、AI 取数链：数据往库外走的主路

（设计文档 §9、§7.3、§7.4）

```
AI 说「查一下这两个人有没有资金往来」
  → 选工具（7 个：search_materials / query_entities / query_relations
             / query_events / aggregate_money / find_crossings / get_citation）
  → case-mcp-tools.ts 统一入口（不另写 SQL）
  → 走 case-fact-read.ts / case-entity-list.ts / case-graph.ts
  → 返回 { 数据, 口径, 缺口, 截断缺口, 限制说明 }
  → 同时往 stderr 留一行痕迹
```

这条流已经有的几个特征，**不是设想、是代码里跑着的**：

- 每次返回都带**「这次是怎么查的」**（口径）和**「漏了什么」**（缺口、截断缺口）；
- 默认 50 条、上限 200 条，超限必须报出「请求多少、实际给多少」；
- 错误原文只写 stderr，不进给模型的上下文。

为什么非要带这些：**AI 不会像人那样追问「你是不是只查了五十条」。** 不把不确定性随数据一起交出去，模型就会把半截结果当全量讲（设计文档 §0.0 推论①）。

**这条流现在最大的洞：返回的每一条都点不回原文**——因为主链第 ④ 步没人写。

## 五、页面取数链：和上一条是同一根管子

（设计文档 §9）

设计上，页面 API 与 AI 工具**共用同一批取数函数**，页面不另写 SQL。

理由不是「省代码」，是：两边一旦各写一遍，「AI 说 A、页面显示 B」就只是时间问题，而这种不一致**没有任何人能发现**——因为没有人同时看两边。

所以这条不是「另一条流」，是同一条流的第二个出口。对外表现上还有两条：

- 页面把 `口径` / `缺口` 原样展示，AI 原样引用，**同一句「不确定」**；
- AI 的回答若涉及具体事实，必须能给出 `material_id + sheet + row_no`；给不出就不下结论。

## 六、跨流的四本账

不属于任何一条主线，但每次流动都会碰到。

| 账本 | 记什么 | 谁写 | 断了的后果 |
|---|---|---|---|
| `case_ingest_job` | 这次入库跑到哪一步、错在哪 | 主链本身 | 卡住时不知道该重试还是该改数据 |
| `case_alert` | 解析异常（跳过行过多、单位可疑） | 主链本身 | 静默丢数据 |
| `case_ai_proposal` | 跨源重复候选、待人工裁定的推断 | 翻译层 + 查询层 | 同一笔交易被统计两次 |
| `case_citation` | 这句话从哪来 | **写下数据的那一步顺手写** | **见下** |

最后一条是这套设计里唯一「不能事后补」的：

> **出处必须在生成数据的同时绑定。事后再回溯，就一定有漏的、有猜的。**

而且它必须由程序写，**AI 碰不到、也不许它自己说**——因为模型编造引用时，连另一个模型去核对都查不出来（设计文档 §7 相关论证）。

## 七、一张总图

```
         ┌────────────── 学习回流 ──────────────┐
         │  人确认 → 写记忆 → 版本+1 → 下次命中  │
         ↓                                      │
  上传 → 识别 → 明细落库 → 出处绑定 → 翻译成卡片 → 收尾
  ①      ②      ③          ④          ⑤         ⑥
         │                                          │
         └──────────── 修正与重建 ◄─────────────────┘
              改卡片/升版本 → 重放 → 关系重算

                    case_event / participant
                    case_entity / alias
                    case_relation
                           │
                           ↓
                 ┌──── 唯一取数层 ────┐
                 ↓                    ↓
             AI（7 工具）          页面 API
                 ↓                    ↓
          答案 + 口径 + 缺口      展示 + 复核入口
                 └──── 同一句「不确定」────┘
```

## 八、按「断了会怎样」排序的薄弱点

不是按工作量，是按**断了以后 AI 会错得多隐蔽**排：

1. **翻译层不存在**——库里没有可查的卡片，所有查询都退化成「看列名猜」。这是唯一一件「不做就全盘落空」的事。
2. **出处无人写**——AI 的每句结论都点不回原件。人说错会被人怀疑，AI 说错不会，所以这是人唯一能核对它的手段。
3. **零结果不分类**——「真的没有」和「还没解析」长得一样，用户会一律读成前者。**错得像个正确答案**，这是系统里最危险的一种错。
4. **关系可能算重**——重解析材料时若增量累加，统计翻倍且看不出来。
5. **同一个人被认成两个**——后面每一句汇总都错，而且错得很顺。
6. **「像是」与「确实是」不区分**——`户名叫张三的账户` 被讲成 `这就是张三`。

前三条也正是 `大白话版.md` 第十一节里「只做三件」的那三件：**有没有东西可查、查到的能不能被证实、错了会不会装成对的。**
