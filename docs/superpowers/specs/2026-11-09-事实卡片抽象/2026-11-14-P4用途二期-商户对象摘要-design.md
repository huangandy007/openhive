## 0. 一页结论

在翻译层新增一个**纯函数抽取模块**（`case-remark-facts.ts`），从备注里取三类②层事实：

| 事实 | 落点 | 本轮口径（用户裁定） |
|---|---|---|
| 商户（`##子商户名称`） | 参与者 `role=商户` + 实体 `type=组织` | **新增**，不动现有收款方参与者 |
| 车牌 | 参与者 `role=车辆` + 实体 `type=车辆` | **参与者 + 实体**，不是只写 attrs |
| 手机号 | 参与者 `role=号码` + 实体 `type=号码` | 同上 |
| 摘要 | `case_event.summary` | 备注主体清洗 + **回退链**（商户 → 收款方名 → 用途） |

准入门：商户只对 `一级=消费` 抽，并剔渠道/占位值。用途判定、关系重建、卡片九格、资金流视图**全部不动**。

## 1. 背景与范围

`01` §3.11 的用途判定（P4-A）已验收：31,719 行真数据逐类判定，词表 v1.4，A21 人工复核 33/34。但「这条流水在**哪**花的、**什么车、什么号**」还没有数据基础——备注里的 `子商户名称`、车牌、手机号从未被抽取；`case_event.summary` 列在、写入器却硬编码 `null`（`case-translate-store.ts` 事件映射）。

本设计只做这一刀，不含：

- 学习层（数据源档案 `case_source_profile`、卡片模板编辑器）；
- AI 接卡片层（AI 抽取路径不判用途、不抽备注事实，保持现状）；
- 前端/卡片九格展示商户与对象（只保证数据在，展示另立）；
- `query_events` 增按商户/车牌/号查询的参数（实体清单与参与者已可查，专用查询口另立）；
- 预处理阶段解码（P0 未开工；内核兜底解码，见 §7）；
- 用途词表改动（本刀不动 `case-purpose-rules.ts`）。

## 2. 实测证据（2026-11-14，三份真文件 31,719 行）

用生产链路（`readSheets` → `detectMapping` → `toFactRows` → `判定用途`）实测：

| 观测 | 数 |
|---|---|
| 消费行 | 7,630 |
| 其中现有收款方有名称（来自 `收款方的商户名称` 列，带 `(商户)`/`(个人)` 后缀） | 7,622 |
| 其中收款方为空/`-` | 8 |
| 备注含 `子商户名称`（全用途） | 6,467 行 / 去重 1,080 个 |
| 备注含 `子商户名称`（消费内） | 6,230 行 |
| 备注商户与收款方名（去后缀）**同名** | 581 |
| 备注商户与收款方名（去后缀）**不同** | 5,649 |
| `UTF8#` 编码商户名 | 32 行（全部可解码） |
| 渠道/占位值 | 生活缴费 1,005；手机充值 143；手机充值-中国移动 48；信用卡还款 67；零钱通 167（提现）；零钱通 1（划转）；微信转账到QQ 2 |
| 车牌 | 137 行 / 6 个（消费/停车 125、消费/其他 12；加油 0） |
| 手机号 | 540 行 / 543 次 / 82 个（转账 344 次、手机充值 173 次、其余 26） |
| 备注主体 ≤10 字 | 20,193 行（多为「微信转账;微信转账」「网银联单号类型：网联」） |
| 备注主体空/占位（`-` / `#|#`） | 294 行 |
| 备注主体 >80 字 | 87 行 |

两条关键结论支撑设计：

1. **备注商户 ≠ 收款方**（5,649/6,230 不同）：列上是收单/结算主体（武汉三喜通物流有限公司），备注才是门店（武汉宇通天运）。二者都要留，不能互相覆盖。
2. **子商户值混着渠道词**：`生活缴费`/`手机充值`/`信用卡还款`/`零钱通` 不是商户，是用途/渠道本身；不做闸会把渠道当组织建实体。

## 3. 口径与规则

### 3.1 商户

| 项 | 规则 |
|---|---|
| 用途闸 | 仅 `一级 = 消费` 的行抽取 |
| 来源 | 备注 `##子商户名称：` 段（首个出现）→ `UTF8#` 解码 → 去首尾空白 |
| **不用**列的偏差 | `06` §6.8 写「其次取 `收款方的商户名称` 列」。实测该列已作为现有 `收款方` 参与者入账（7,622 行），再建一个同值的 `商户` 参与者是同一事实两写（`#002-06`）。故本轮**只用备注段**；列值继续由收款方承担。此偏差在 §6 登记 |
| 值闸 | 空、`-`、`#|#` → 不建；等于 `生活缴费` / `信用卡还款` / `零钱通` / `微信转账到QQ`，或以 `手机充值` 开头 → 不建 |
| 解码失败 | 不伪造：不建商户；量化脚本单列「解码失败」计数（真数据现为 0） |
| 去重 | 一卡一个商户（取首次出现） |
| 实体 | `type=组织`，规范值 = 解码后的商户名（原样，不剥后缀、不改写）。实测无地址形态值，故不取 `地点`（`06` §10 #7 的裁定，见 §6） |

### 3.2 车辆 / 号码

机械抽取（②层），不设用途闸。

| 项 | 规则 |
|---|---|
| 车牌 | `/(?:^|[^A-Za-z0-9])([京津沪渝冀豫云辽黑湘皖鲁新苏浙赣鄂桂甘晋蒙陕吉闽贵粤青藏川宁琼][A-Z][A-Z0-9]{4,5}[A-Z0-9挂学警港澳]?)(?![A-Za-z0-9])/g`；前后不得紧邻字母数字；大写归一；一卡多车去重后各一条 |
| 手机号 | `/(?:^|\D)(1[3-9]\d{9})(?!\d)/g`；前后不得紧邻数字；去重 |
| 落点 | 参与者 `role=车辆` / `role=号码`，实体 `type=车辆` / `type=号码`，规范值 = 归一后的值 |
| 顺序 | 商户 → 车辆 → 号码；同类型内按首次出现 |

### 3.3 摘要（所有资金卡都写）

```
备注 → 去 `备注：` 前缀 → 取首个 ## 前的主体
     → 空白折叠（\s+ → 单空格）
     → 按 [;；] 拆段、相同段去重保序（「微信转账;微信转账」→「微信转账」）
     → 无信息判定 → 命中则走回退链
```

无信息判定（任一成立即回退）：

- 空、`-`、`#|#`；
- 折叠后只剩渠道/类型词：`微信转账`、`微信红包`、`微信转账;微信红包`（折叠后逐词判）；
- 首段是元数据键：以 `网银联单号类型`、`相关方`、`title`、`receiver`、`子商户名称` 开头。

回退链：`子商户名称`（解码后且过 §3.1 值闸）→ 收款方名（`counterpartyName ?? counterparty`，去 `(商户)`/`(个人)` 后缀）→ `用途.二级 ?? 用途.一级`。

最终按 **Unicode 码点**截断 60 字（`Array.from`，避免截断代理对），被截断时补 `…`。

## 4. 数据流与模块划分

```
case-ingest
  └─ toFactRows（备注进 extras）                    ← 不改
       └─ 翻译资金（case-translate.ts，纯函数）
            ├─ 判定用途（case-purpose.ts）           ← 不改
            ├─ 抽取备注事实（case-remark-facts.ts）  ← 新增
            └─ 卡片草稿：participants 追加、摘要字段
                 └─ 写入翻译结果（case-translate-store.ts）
                      ├─ 实体：账户 / 组织 / 车辆 / 号码
                      ├─ 参与者：ordinal 0、1 不变；追加 2、3…
                      └─ case_event.summary（现在是硬编码 null）
```

### 4.1 新模块 `packages/opencode/src/server/openhive/case-remark-facts.ts`

纯函数、不碰库、不读时钟、不调模型（与 `case-translate.ts` 同一条纪律）：

```ts
export interface 备注事实 {
  商户: string | null
  车辆: string[]
  号码: string[]
  摘要: string | null
}

export interface 抽取备注事实输入 {
  备注: string | null
  /** 用途判定结果（用途闸看一级，摘要回退末级用二级 ?? 一级）。 */
  用途: { 一级: string; 二级: string | null }
  对手名: string | null
}

export function 抽取备注事实(input: 抽取备注事实输入): 备注事实
```

内部只导出这一个函数与两张词表常量（`商户值闸词们`、`摘要元数据键们`），供测试与量化脚本引用。

### 4.2 翻译层改动（`case-translate.ts`）

- 类型：

```ts
export type 实体类型 = "账户" | "组织" | "车辆" | "号码"

export interface 卡片参与者 {
  规范值: string
  角色: "付款方" | "收款方" | "商户" | "车辆" | "号码"
  提及: string
  ordinal: number                       // 0/1 固定为付款方/收款方，追加从 2 起
  实体: boolean
  实体类型: 实体类型
}
```

`卡片草稿.participants` 由二元组放宽为 `[卡片参与者, 卡片参与者, ...卡片参与者[]]`（前两位语义不变），新增 `摘要: string | null`。

- 流程：判定用途后调用 `抽取备注事实({备注: 备注文本(row), 用途, 对手名: row.counterpartyName ?? row.counterparty})`，按 §3.2 顺序追加参与者，`摘要` 进卡片草稿。
- `实体键(类型, 规范值)` 与 `账户键(规范值) = 实体键("账户", 规范值)` 一并落在这里（`#002-06` 单一出处）。

### 4.3 写入层改动（`case-translate-store.ts`）

- 实体缓存键 `账户键(v)` → `实体键(p.实体类型, p.规范值)`；`upsertEntity` 的 `type` 与 `事实id(projectId, p.实体类型, 规范值)` 同步（账户 id 不变，新类型新 id）。
- `事件们` 的 `summary: null` → `summary: 卡.摘要`。
- 关系重建保持解构前两位（`[主体, 对手]`）并加注释说明「前两位永远是付款方/收款方」（`case-entity-attrs.ts:130` 的 `participants[0]/[1]` 同理）。
- 受保护卡（人工结论）整卡跳过逻辑不变——新参与者随卡一起保护。

## 6. 与上游文档的偏差 / 裁定（登记）

1. **`06` §6.8「来源其次取 `收款方的商户名称` 列」**：本轮不从列抽商户，理由见 §3.1（列已入账为收款方，重复无信息）。方向是「商户=门店、收款方=结算对手」，与 06 的分工一致，只是不做重复落点。
2. **`06` §10 #7「商户实体类型 组织 vs 地点」**：按真实数据裁为 **组织**——1,080 个去重值里全是商号/公司/平台名，无地址形态；本刀又不含场所抽取，故不留 `地点` 分支。
3. **`06` §10 #3「`UTF8#` 解码在预处理」**：预处理（P0）未开工，内核翻译层兜底解码（32 行实测全部成功）；P0 开工后两处解码同语义，届时以预处理为准，内核代码保留无害（`#002-06`：同一前提单一出处——届时需复核是否删内核兜底，登记为后续待办）。

## 7. 错误处理与边界

| 场景 | 处理 |
|---|---|
| 备注缺失 / 空 | 不建商户与对象；摘要走回退链（收款方名 → 用途） |
| `UTF8#` 解码失败 | 不建商户，计数；不伪造、不把 base64 当商户名 |
| 商户值命中值闸 | 不建商户；摘要回退链同样跳过该值 |
| 同一卡多个车牌/号码 | 去重后各一条，ordinal 依次递增 |
| 人工结论卡 | 写入层整卡跳过（含新参与者），保持人工值 |
| 重放（同一材料再入库） | 先清机器事实再写：参与者按 ordinal 重建、实体按 `(type, canonical)` upsert ⇒ 幂等；`#013-04` 的父子行保护照旧 |
| 实体同名跨类型（某商户名同时也是账户规范值） | `case_entity` 唯一键是 `(project_id, type, canonical_value)` ⇒ 两条实体并存，符合预期 |
| 掩码商户/号码 | 车牌/手机号正则天然不命中掩码；商户名照原文落库（不脱敏，按项目约定明文） |
