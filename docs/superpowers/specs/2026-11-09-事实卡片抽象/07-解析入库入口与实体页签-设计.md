> **日期**：2026-11-11（定稿）／2026-11-12（实现前修订）
> **定位**：回答两件事——**两项功能下架**（左栏「实体」页签、文件上传后自动解析入库），以及**解析入库的入口收敛到右键**、补齐多选批量。上游衔接 `01-事实卡片与数据翻译-设计.md` §5.1（用户只做四件事）、`过程文档/04-预处理后再入库-专题会议纪要.md`（六）（批量入库：右键文件夹）、`过程文档/02-数据流全景.md` 一（入库主链 ①）。

## 0. 一页结论

1. **实体页签下架，实体详情页保留**。左栏 `会话 / 文件 / 实体 / 能力` → `会话 / 文件 / 能力`；`entity-profile.tsx`、`case://` 伪路径、`entity-api.ts` 全部不动。
2. **本轮不给详情页补入口**。表格链路今天不建实体（全仓唯一 `upsertEntity` 在文本分支），从材料点进去对流水类材料只能是空的——那种入口比没有更像坏了。
3. **上传只落盘**。删掉 `handleUpload` 里「写盘后同请求入队」那一段，上传不再产生材料行与作业；文件在树上就是「未入队」，悬停文案已经写好了下一步。
4. **上传完成弹窗加一行提示**，指向右键「解析入库」。不加就等于让刚传完的文件看着像丢了。
5. **右键「解析入库」支持多选**，且选中集里的文件夹按既有「目录下待入队」展开——一个文件与一个文件夹可以一起选。
6. **只有「解析入库」支持多选**；其余四项（重新解析 / 取消解析 / 跳过解析 / 查看解析结果）在多选时置灰并说明原因。
7. **批量失败不再中断**：逐个发、失败继续、收尾一起报（成功数 + 失败数 + 前几条原因）。
8. **服务端不加批量接口**，理由沿用仓库里的既定裁定：批量接口迟早会被写成「按状态全集扫」，把用户跳过的文件翻回来。

## 1. 问题是什么

两条下架理由都由用户给出，原文要点：

- **实体 Tab**：「第一性功能实际意义不大，不能给用户带来实际收益。」
- **文件导入自动解析入库**：「与数据先要进行预处理后再入库相冲突。」

第一条在代码里有硬证据支撑：这个面板的数据源对流水类是空的（见 §2.4）。

第二条是一条**流程约束**：原件进来只是留档，进库的应当是预处理产出的**标准格式副本**。上传即解析等于绕过了预处理这一站，于是「先预处理、再入库」就只剩一句口号。

用户的入口主张也一并明确：解析入库仍在**鼠标右键的解析功能及其二级功能**里；为多文件场景补两件事——**对文件夹下所有文件发送解析**、**多选文件后发送解析入库**。

## 5. 决定三：解析入口收敛到右键

### 5.1 右键对象怎么算

沿用下载那一套判据，**同一个函数**，不另写一份（`file-tree.tsx:723-733` 的 `判下载目标`）：

- 右键那一行**在选中集里**且选中集 > 1 ⇒ 作用于整个选中集（`selection`）；
- 否则只看这一行：文件就是它自己（`file`），文件夹就是它下面的候选（`folder`）。

判据是「右键行在不在选中集里」，不是「选中集大小」——选中两项后右键第三行，用户要的是第三行（`file-tree.tsx:720-721` 的注释）。

**实现要求**：把 `判下载目标` **改名**为 `判菜单目标`（或等价的中性名），下载那两处调用（`:744`、`:1452`）与解析共用这一个。不要为解析抄一份三元判断——那就是第二份「同一个前提」（`#002-06`），下次改选区规则必漏一处。

### 5.2 候选口径（新纯函数 `选中集待入队`，写在 `case-materials-view.ts`）

对选中集里每一项分别求候选：

- **文件**：未入队 / 有问题 / 没有材料行 ⇒ 算；已解析、已跳过、排队中、解析中、产物、不可解析扩展名 ⇒ 不算；
- **文件夹**：直接复用 `目录下待入队`（`case-materials-view.ts:162-190`）；
- 去重后合计 N（选中了文件夹 A 又选中了 A 里的文件 B 时，B 只算一次——复用 `目录下待入队` 里的 `见过` 集合）。

**判据只写一份（2026-11-12 定，`#002-06`）**：文件级规则今天已经在 `目录下待入队` 的函数体里了。**不要**在新函数里抄一遍状态清单——把那段循环体抽成 `文件待入队(path, row, extensions)`，`目录下待入队`（对目录下每个文件）与新的 `选中集待入队`（对选中集里的单个文件）都调它。抽完 `目录下待入队` 的既有用例必须原样全绿。

⚠️ **与 `入队不可用原因`（`case-materials-view.ts:215`）在「已跳过」上故意不一致**，实现时不许「合并成一个就好」：单项右键时「已跳过」是**放行**的（那是人明确要恢复这一份），批量时是**排除**的（批量动作不该把跳过的东西翻回来）。这条差异在 `:145-157` 的注释里已写，抽函数时把它搬到 `文件待入队` 头上。

**已跳过一律排除**，包括用户亲手 Ctrl 选中的那一份。但**不能让排除静默发生**：选中项里只要有被排除的，确认框补一句「另有 M 个选中项不在本次范围（已解析 / 已跳过 / 正在解析）」——这里的单位是**选中项**（一份文件、或一个展开后 0 候选的文件夹各算一项），不是文件数。

### 5.3 只有「解析入库」支持多选

| 子项 | 多选时 | 原因文案 |
|---|---|---|
| 解析入库 | **作用于整个选中集** | — |
| 重新解析 | 置灰 | 「多选时只能用「解析入库」」 |
| 取消解析 | 置灰 | 同上 |
| 跳过解析 | 置灰 | 同上 |
| 查看解析结果 | 置灰 | 同上 |

理由：重新解析是「重跑这一份」的语义，批量重跑的风险与交代成本都远高于批量入队；取消与查看没有批量意义。不置灰的话会出现「解析入库作用于 100 份、重新解析只作用于右键的那 1 份」——同一菜单两种作用范围，比没有更糟。

**多选时「解析入库」亮不亮，不能再按右键那一行判（2026-11-12 定）**：现在五项都吃同一份 `菜单依据()`（由 `菜单对象()` 单独推出，`file-tree.tsx:1239-1285`）。多选场景下若右键的恰是**已解析**那一行，而选中集里还有未入队文件，`入队不可用原因` 会看到「已解析」把整项灰掉，整批做不了。判据改为：

- 多选（`是选中集(path)` 为真）⇒ 「解析入库」亮起当且仅当 `选中集待入队` **非空**；`rowsLoaded` 未就绪时仍走原有「还在读 / 读取失败」两句话，不猜；
- 单选 ⇒ 维持现有行为（文件夹一律放行到确认框、文件按 `入队不可用原因`）；
- 其余四项在多选时一律置灰并给统一原因，与作用范围无关。

**子菜单触发项右侧的状态文字**：多选时显示「已选 **K** 项」，**K 是选中集的大小**，不是候选数（候选要展开文件夹才知道，那是确认框的事）；`file-tree.tsx:1224-1233` 的 `状态文案` 增一支，单选时维持现有行为。**K 与确认框里的 N 是两个数**，见 §5.4。

### 5.4 确认框与 0 候选

- 标题：「解析选中的 **N** 个文件」，**N 是展开后的候选数**（不是选中集大小 K，也不是文件夹个数）；正文在有条目被排除时追加 §5.2 的那句（用「M 个选中项」）；
- **N = 0 时仍然弹窗**，确认键置灰、正文说清为什么（与文件夹的分支同款，`file-tree.tsx:646-657`）；直接 `return` 会让用户以为右键菜单坏了；
- 单个文件夹的文案与行为不变：「将解析这个文件夹下的 N 个文件」。

### 5.5 批量执行与失败交代

- 逐个 `状态.parse(path, "入队")`，**失败不中断**（今天的文件夹批量是 `break`，`file-tree.tsx:663-676`——这一处行为**确实变了**）；收集失败项（路径 + 原因）；
- 收尾按服务端真实状态重拉一次（`状态.reload()`），弹窗关闭；
- 成功：`已加入解析队列（S 个文件）`，**S 是实际成功份数**，不是候选数 N（沿用文件夹批量的文案）；N = 0 时压根走不到这里；
- 有失败：再报一条 `F 个文件没能入队`，列出前 3 条「文件 → 原因」，并说明「重来一次只补没成功的，不会重复」。入队幂等，重试是安全的；**S + F = N**（`F` 是失败的**文件**数，与 §5.2 的 `M`（被排除的**选中项**数）不是一个数，别复用同一个字母）；
- 文件夹批量与多选批量**共用同一个执行函数**，只是候选来源不同（`目录下待入队` vs 选中集展开）。今天的失败分支会弹「文件夹解析中断」（`file-tree.tsx:668-672`），改造后这句**不再存在**。

**这条改动必须有用例钉住**：现有文件夹批量用例（`file-tree.test.tsx:3253`）只走全成功路径，**没有任何一条注入失败**——把 `break` 改成「继续」时现有测试红绿不变，等于没守。用例写法：用测试里的假材料状态（`假.记.解析` 那套）让**中间那一份** `parse` 回 error，断言「后面几份仍然被发出去」＋「收尾一条失败 toast 且列出原因」。

### 5.6 为什么服务端仍然不加批量接口

沿用 `file-tree.tsx:628-640` 的既定理由：批量接口迟早会被写成「按状态全集扫」，把「已跳过」翻回来；而按文件分开的成败，只有在前端这一层才说得清。批量**只活在前端**。

### 5.7 已知行为：批内执行顺序是倒序

人工「入队」是置顶的，置顶算法是「排到本项目最老那条排队作业前 1 秒」（`case-ingest.ts:143-146`）。一批 N 份逐个发，后发的更早，于是**批内执行顺序为倒序**。

功能上无害（整批仍排在别的作业之前），且改它要动置顶算法——一个高频、且与上游同步相关的位置。**本次不改，只记录**：用户若盯着列表看，会看到文件不按点击顺序完成。
