# 解析入库入口与实体页签 · 设计

> **状态**：设计定稿，待实现（2026-11-11）
> **日期**：2026-11-11
> **定位**：回答两件事——**两项功能下架**（左栏「实体」页签、文件上传后自动解析入库），以及**解析入库的入口收敛到右键**、补齐多选批量。上游衔接 `01-事实卡片与数据翻译-设计.md` §5.1（用户只做四件事）、`04-预处理后再入库-专题会议纪要.md`（六）（批量入库：右键文件夹）、`02-数据流全景.md` 一（入库主链 ①）。
> **结论先行**：**下架的是「给人浏览的实体清单」与「上传顺手解析」，不是「AI 查实体」的能力；入队这件事全系统只留一个入口——右键「解析入库」，它同时支持文件夹、多选、以及两者混选。** 服务端仍然不提供批量接口。
> **证据**：本文所有 `file:line` 均为 2026-11-11 在 `multi-tenant` 分支上实读所得。

## 0. 一页结论

1. **实体页签下架，实体详情页保留**。左栏 `会话 / 文件 / 实体 / 能力` → `会话 / 文件 / 能力`；`entity-profile.tsx`、`case://` 伪路径、`entity-api.ts` 全部不动。
2. **本轮不给详情页补入口**。表格链路今天不建实体（全仓唯一 `upsertEntity` 在文本分支），从材料点进去对流水类材料只能是空的——那种入口比没有更像坏了。
3. **上传只落盘**。删掉 `handleUpload` 里「写盘后同请求入队」那一段，上传不再产生材料行与作业；文件在树上就是「未入队」，悬停文案已经写好了下一步。
4. **上传完成弹窗加一行提示**，指向右键「解析入库」。不加就等于让刚传完的文件看着像丢了。
5. **右键「解析入库」支持多选**，且选中集里的文件夹按既有「目录下待入队」展开——一个文件与一个文件夹可以一起选。
6. **只有「解析入库」支持多选**；其余四项（重新解析 / 取消解析 / 跳过解析 / 查看解析结果）在多选时置灰并说明原因。
7. **批量失败不再中断**：逐个发、失败继续、收尾一起报（成功数 + 失败数 + 前几条原因）。
8. **服务端不加批量接口**，理由沿用仓库里的既定裁定：批量接口迟早会被写成「按状态全集扫」，把用户跳过的文件翻回来。

## 1. 问题是什么

两条下架理由都由用户给出，原文要点：

- **实体 Tab**：「第一性功能实际意义不大，不能给用户带来实际收益。」
- **文件导入自动解析入库**：「与数据先要进行预处理后再入库相冲突。」

第一条在代码里有硬证据支撑：这个面板的数据源对流水类是空的（见 §2.4）。

第二条是一条**流程约束**：原件进来只是留档，进库的应当是预处理产出的**标准格式副本**。上传即解析等于绕过了预处理这一站，于是「先预处理、再入库」就只剩一句口号。

用户的入口主张也一并明确：解析入库仍在**鼠标右键的解析功能及其二级功能**里；为多文件场景补两件事——**对文件夹下所有文件发送解析**、**多选文件后发送解析入库**。

### 3.2 保留什么，为什么

- **`entity-profile.tsx`（1101 行）与它的三个子视图**：这是「查某个人时能看到他的全部事实」的能力，与「浏览一份 80% 是噪声的清单」不是同一件事；

- **AI 侧 `query_entities` 等工具**：它们与前端零耦合（`case-mcp-tools.ts:153`），下架界面不等于下架能力。

### 3.3 为什么本轮不补入口

任何「从材料点进去」的入口，对流水类材料点开都是空的（§2.4）；「从对话点开」要先给聊天渲染加 `case://` 链接能力，工作量最大、收益同样为零。**入口应当由「事实卡片」这一层来给**——等翻译层把流水建出实体之后，卡片上的对手账户才是那个自然的落点。现在硬加一个入口，只是把「空的」提前暴露给用户。

### 3.4 验收判据

1. 左栏只剩三个页签，键盘 ← → 在 `会话 → 文件 → 能力 → 会话` 上环绕；
2. 全仓 `grep EntityPanel` 无结果（测试、stories 一并清理）；
3. `case://<项目>/entity/<id>` 的解析与渲染用例仍然通过（详情页没被碰坏）；
4. `entity-api` 的四个下游（`case-detail-api` / `case-alerts-api` / `case-artifact-save` / `case-alert-entry`）测试通过。

2. **盘上文件不变**：上传仍按「目标位置同名即拒绝」判重（`file.ts:836,841`），与内容无关；内容去重仍由 `(project_id, fingerprint)` 唯一索引在**解析时**完成（`case-store.ts:81-96`）。
3. **同名同内容的两份文件，谁先被解析谁占材料行**：后解析的那份命中冲突，会把老行的 `path/file_name` 改写成新路径（`case-store.ts:89`）。这是既有实现，不是本次引入；批量解析会让它更容易被撞到，写入 §9 备查。

### 4.3 提示放哪、说什么

放在**上传完成**的那张弹窗里（done 态），不加 toast——上传本来就用弹窗收尾（`file-transfer-dialog.tsx:37-40`），再弹一条 toast 是同一件事的第二个说法。

### 4.4 为什么不在上传弹窗里问「要不要现在解析」

那等于在右键之外再养一个入队入口，且与「先预处理、再入库」直接冲突：原件刚上传就被问要不要入库，用户多半会点「要」。入口只有一个，才不会出现两套状态文案。

## 5. 决定三：解析入口收敛到右键

### 5.1 右键对象怎么算

沿用下载那一套判据，不另写一份（`file-tree.tsx:723-732`）：

- 右键那一行**在选中集里**且选中集 > 1 ⇒ 作用于整个选中集；
- 否则只看这一行：文件就是它自己，文件夹就是它下面的候选。

判据是「右键行在不在选中集里」，不是「选中集大小」——选中两项后右键第三行，用户要的是第三行（`file-tree.tsx:720-721` 的注释）。

### 5.2 候选口径（新纯函数 `选中集待入队`，写在 `case-materials-view.ts`）

对选中集里每一项分别求候选：

- **文件**：未入队 / 有问题 / 没有材料行 ⇒ 算；已解析、已跳过、排队中、解析中、产物、不可解析扩展名 ⇒ 不算；
- **文件夹**：直接复用 `目录下待入队`（`case-materials-view.ts:162-185`）；
- 去重后合计 N。

**已跳过一律排除**，包括用户亲手 Ctrl 选中的那一份。理由与文件夹批量同一条（仓库既定裁定，`:153-157`）：跳过是人的意志，批量动作不该把它翻回来；要恢复就单点那一份。但**不能让排除静默发生**：选中项里只要有被排除的，确认框补一句「另有 M 个不在本次范围（已解析 / 已跳过 / 正在解析）」。

### 5.3 只有「解析入库」支持多选

| 子项 | 多选时 | 原因文案 |
|---|---|---|
| 解析入库 | **作用于整个选中集** | — |
| 重新解析 | 置灰 | 「多选时只能用「解析入库」」 |
| 取消解析 | 置灰 | 同上 |
| 跳过解析 | 置灰 | 同上 |
| 查看解析结果 | 置灰 | 同上 |

理由：重新解析是「重跑这一份」的语义，批量重跑的风险与交代成本都远高于批量入队；取消与查看没有批量意义。不置灰的话会出现「解析入库作用于 100 份、重新解析只作用于右键的那 1 份」——同一菜单两种作用范围，比没有更糟。

**子菜单触发项右侧的状态文字**：多选时显示「已选 N 项」，**N 是选中集的大小**，不是候选数（候选要展开文件夹才知道，那是确认框的事）；`file-tree.tsx:1224-1233` 的 `状态文案` 增一支，单选时维持现有行为。

### 5.4 确认框与 0 候选

- 标题：「解析选中的 N 个文件」；正文在有条目被排除时追加 §5.2 的那句；
- **N = 0 时仍然弹窗**，确认键置灰、正文说清为什么（与文件夹的分支同款，`file-tree.tsx:646-657`）；直接 `return` 会让用户以为右键菜单坏了；
- 单个文件夹的文案与行为不变：「将解析这个文件夹下的 N 个文件」。

### 5.5 批量执行与失败交代

- 逐个 `状态.parse(path, "入队")`，**失败不中断**；收集失败项（路径 + 原因）；
- 收尾按服务端真实状态重拉一次（`状态.reload()`），弹窗关闭；
- 成功：`已加入解析队列（S 个文件）`，**S 是实际成功份数**，不是候选数 N（沿用文件夹批量的文案）；N = 0 时压根走不到这里；
- 有失败：再报一条 `M 个文件没能入队`，列出前 3 条「文件 → 原因」，并说明「重来一次只补没成功的，不会重复」。入队幂等，重试是安全的；S + M = N。
- 文件夹批量与多选批量**共用同一个执行函数**，只是候选来源不同（`目录下待入队` vs 选中集展开）。

### 5.6 为什么服务端仍然不加批量接口

沿用 `file-tree.tsx:628-640` 的既定理由：批量接口迟早会被写成「按状态全集扫」，把「已跳过」翻回来；而按文件分开的成败，只有在前端这一层才说得清。批量**只活在前端**。

### 5.7 已知行为：批内执行顺序是倒序

人工「入队」是置顶的，置顶算法是「排到本项目最老那条排队作业前 1 秒」（`case-ingest.ts:143-146`）。一批 N 份逐个发，后发的更早，于是**批内执行顺序为倒序**。

功能上无害（整批仍排在别的作业之前），且改它要动置顶算法——一个高频、且与上游同步相关的位置。**本次不改，只记录**：用户若盯着列表看，会看到文件不按点击顺序完成。
