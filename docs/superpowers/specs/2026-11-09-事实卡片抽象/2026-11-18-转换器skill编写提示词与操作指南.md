# 转换器 skill 编写：提示词、原理与操作指南

> **状态**：可执行草案（2026-11-18）。契约部分对齐 `2026-11-18-数据格式自适应与自动入库-需求.md` §6；代码口径对齐 `packages/opencode/src/server/openhive/` 现有实现。
> **用途**：给人看「为什么要这么写」，给 AI 看「照着写什么」。§2 是可直接复制的提示词，配合 `superpowers:writing-skills` 使用。
> **样本与原型**：`tmp/skill-微信账户流水预处理/`（演示级，未入仓库）；字段口径见 `过程文档/03-微信流水预处理-字段口径与转换规则.md`；属性语法见 `过程文档/05-实体属性标记与入库规范.md`。

---

## 0. 怎么用这份文档

1. 新建一个 skill 时，把 **§2 的提示词整块**复制进会话（连同 `superpowers:writing-skills` 一起调用）。
2. 替换提示词里的 `{格式名}`、`{样本路径}`、`{技能目录}` 三个占位符。
3. 先让 AI 交「格式档案」和「基线错法」，**不要让它直接写完整实现**——这两个产物决定识别卡和 SKILL.md 该防什么。
4. 按 §5 的步骤验收：golden 测试 → 变异测试 → 拒收样本 → 5,000 行性能 → 发布启用 → 真栈拖入。

**不要**把转换器写进 `packages/opencode/src/`。它是技能资产，四件套放技能目录，由资产流水线发布（FR-04）。

---

## 1. 三个物件，各自负责一件事

| 物件 | 给谁看 | 回答什么问题 | 失败会怎样 |
|---|---|---|---|
| `adapter.json`（识别卡） | 内核 | 「这份文件该不该用它」 | 认不出 / 认错格式 |
| `convert.*`（转换器） | 内核子进程 | 「源文件 → 事实行 JSON」 | 入库错数据，且没有红字 |
| `SKILL.md` | 人、模型 | 「它的边界、坑、证据在哪」 | 后续维护者按错误理解改规则 |

三者是**同一份规则的三个投影**，不是三份可以各自演化的文档：

- 表头闸、阈值只写在 `adapter.json` 一处，`convert` 读它，内核探测也读它（`#002-06`：同一前提不许两处各写）；
- `SKILL.md` 解释「为什么」，不重复贴一遍字段表；
- 版本号只在 `adapter.json` 里是权威值，`report` 从它复制。

## 2. 提示词（复制这一块）

````markdown
你是 openhive 的「数据格式适配器工程师」。任务：为「{格式名}」编写一个可被内核自动识别、自动执行的转换器 skill。

样本：{样本路径}
技能目录：{技能目录}

先按 superpowers:writing-skills 的流程做（基线 → 写 SKILL → 压测），但本任务不是纯文档：你要交付**可运行的确定性代码**和**可复现的测试**。文档写得好但转换器跑不对，等于没交付。

────────────────────────────────
一、先读这些（按顺序，别跳）
────────────────────────────────
1. docs/superpowers/specs/2026-11-09-事实卡片抽象/2026-11-18-数据格式自适应与自动入库-需求.md
   —— §6.1 识别卡、§6.2 转换器输出、§6.3 属性列、§6.4 状态与原因码、FR-02~FR-06。
2. 同目录 01-事实卡片与数据翻译-设计.md 的 §2.4、§4.0（本方/对方、绑定关系、四层识别）。
3. 同目录 过程文档/05-实体属性标记与入库规范.md（属性列语法、键词表、合并语义）。
4. packages/opencode/src/server/openhive/case-store.ts 里的 `FactRowInput`（事实行唯一结构）。
5. packages/opencode/src/server/openhive/case-translate.ts 的 `翻译资金`（下游到底读哪些字段、哪些行会被跳过）。
6. packages/opencode/src/server/openhive/case-attribute-registry.ts（属性列正则与键词表）。
7. packages/opencode/src/server/openhive/case-time.ts（时间口径：Unix 秒、Asia/Shanghai）。
8. 原型参考：tmp/skill-微信账户流水预处理/（它产 xlsx 副本，是旧形态；字段判断仍然有效，输出形态按本提示词改成 JSON）。

注意：转换器**不 import 内核代码**。它是独立子进程，技能目录被单独发布，解析器要自带。内核与转换器各有一份时间/金额/币种解析逻辑，这是进程隔离的必然重复——用同一组测试向量钉住，别让两边漂。

────────────────────────────────
二、产物：四件套，缺一不算交付
────────────────────────────────
{技能目录}/
  SKILL.md           # 何时用、字段绑定、两道闸、已知限制；description 只写触发条件
  adapter.json       # 识别卡，给内核看
  convert.ts         # 确定性转换实现
  test/
    fixtures/        # 真实样本（脱敏）+ 变异样本
    expected/        # expected.factRows.json / expected.report.json
    convert.test.ts  # golden + 计数守恒 + 变异 + 拒收

────────────────────────────────
三、铁律（违反任何一条 = 交付无效）
────────────────────────────────
1. 转换器是纯函数：不连数据库、不读数据库凭据、不调模型、不发网络请求、不读技能目录以外的文件。
2. 不修改源文件。原始值被归一化改写过时，把原文留在 `ownerAccountRaw` / `counterpartyRaw` / `startedRaw`。
3. fail-closed：表头闸或值闸任一不过 ⇒ 整份拒收，只写 `report.json`，**不产出任何事实行**。不许「能转多少转多少」。
4. 金额一律正数、字符串、两位小数；方向只用 `收` / `付`。不许用正负号暗示方向。
5. `rowNo` 是源文件的 **Excel 行号**（含表头行偏移，不是数组下标）。它是出处的最后一段，错了就回不到原文。
6. 属性列只写进 `extras`，键必须是半角冒号：`属性:对方:开户行` / `属性:本方:银行卡号`。空值不写。归属写错不会报错，只会把属性挂到错误实体上。
7. 户名不是属性：本方户名 → `extras.ownerName`；对方户名 → `counterpartyName`。
8. 时间输出 **Unix 秒（UTC epoch）**，按 Asia/Shanghai 解释。认不出就跳过该行并记原因，不许用当前时间、不许猜。
9. 输出只有两个 JSON 文件；stdout/stderr 不得混入 JSON；按退出码区分结果（见五）。
10. 同样输入必须产出逐字节相同的输出：顺序稳定、无时间戳、无随机数、无 `Date.now()`。
11. 阈值和必需列只写在 `adapter.json`；`convert.ts` 读它，不许在代码里写第二份数字。
12. 不新增状态、不写库、不写 `case_material`。内核负责入库。

────────────────────────────────
四、第一步：把样本读透（先不写代码）
────────────────────────────────
交一份「格式档案」，必须是实测数字，不许写「大概」：
- 工作簿有几个 sheet、表头在第几行、原始列数、数据行数；
- 每列的样例值、空值率、是否可能是标准字段；
- 每一侧（本方/对方）由哪些列绑定成一组：主体账号、名下卡号、开户行、户名；
- 哪些值是相对的（随借贷方向变化）、哪些是绝对的；
- 空行、合计/小计行、特殊业务（提现、充值、退款、冲正、内部划转）各多少行；
- 三条基线：总行数、金额合计、收/付计数（后面每个测试都拿它们对账）；
- 已知不可判定的值：列出来，进 `warnings`，不许猜。

然后做 writing-skills 的 RED：让一个不知情的子代理只拿样本和一句「把这些流水转成标准格式」，记录它**错在哪**（按列名硬取对方、把商户名当商户、时间按 UTC 等）。SKILL.md 必须针对这些真实错法写，不许凭空列注意事项。

────────────────────────────────
五、第二步：写识别卡 adapter.json
────────────────────────────────
结构见需求 §6.1。逐字段要求：
- `id`：kebab-case，永久稳定，不复用。建议与技能目录名一致。
- `name`：给人看的中文名。
- `version`：semver。**转换规则或阈值一变就升版本**，并重跑 test。
- `kind`：`"converter"`。
- `materialType`：`"资金"` / `"话单"` / `"其他"`。
- `match.requiredHeaders`：只放「缺了就无法转换」的列。可选列放 `optionalHeaders`。多放一列，就多一类本该能转的文件被拒。
- `match.priority`：100 起。同一格式族细分时高者优先；打平不猜（内核返回 null）。
- `admission.checks` / `thresholds`：必须可执行、可复现，且与 `report.gates` 的项名一一对应。分母为 0 的检查项按通过算（样本里没有这种情况）。
- `rowRules`：给人读的规则摘要，内核不执行它。
- `entry`：`command` / `input` / `output`。当前约定：
  - 内核以 `cwd = 技能目录` 启动：`bun run convert.ts --input <源文件绝对路径> --out <输出目录绝对路径>`
  - 转换器读 `--input`，写 `<out>/factRows.json` 与 `<out>/report.json`。
  - `input` 目前是提示值；实际可能是 `.xls` / `.xlsx` / `.csv`，转换器三种都要吃。
  - 这条 CLI 约定与 N3（`case-converter-runner.ts`）同步定稿；实现前先确认执行器没改参数名。
- `output.rows` / `output.report`：固定文件名。
- 可选扩展 `enrich`：见第七节。它尚未写进需求 §6.1，**用到时先拍板再写**。

退出码约定（写进 SKILL.md，执行器按它映射原因码）：
- `0`：转换完成（可以有 `skippedRows`，但整份被接受）；
- `3`：闸门拒收（写 `report.json`，不写 `factRows.json`）；
- `1`：转换器异常（读文件失败、未捕获异常）。
内核映射：`3` + 表头缺列 ⇒ `未识别:缺必需列:<列名>`；`3` + 值闸 ⇒ `未识别:值闸不过:<检查项>`；`1` ⇒ `失败:转换器异常`。

────────────────────────────────
六、第三步：写转换器 convert.ts
────────────────────────────────
输出分两个文件，不要合并成一个。`factRows.json` 只有事实行：

```json
{
  "rows": [
    {
      "sheet": "Sheet1",
      "rowNo": 2,
      "startedAt": 1730000000,
      "startedRaw": "20241127113320",
      "precision": "到秒",
      "timeType": "发生",
      "amount": "1234.56",
      "balance": "5678.90",
      "direction": "收",
      "ownerAccount": "085e9858...",
      "ownerAccountRaw": "085e9858...",
      "counterparty": "6217...",
      "counterpartyRaw": "6217...",
      "counterpartyName": "张三",
      "currency": "CNY",
      "extras": {
        "ownerName": "李四",
        "备注": "转账",
        "交易类型": "转账",
        "属性:对方:开户行": "招商银行",
        "属性:对方:银行卡号": "6214..."
      }
    }
  ]
}
```

`report.json` 只有报告：

```json
{
  "adapterId": "wechat-wallet-statement",
  "adapterVersion": "1.0.0",
  "sourceSha256": "...",
  "headerGate": { "通过": true, "缺列": [] },
  "gates": [
    { "项": "方向与本方一致", "分母": 699, "命中": 699, "阈值": 0.98, "实际率": 1.0, "通过": true }
  ],
  "counts": { "总行": 699, "产出": 699, "跳过": 0 },
  "warnings": [{ "rowNo": 3, "code": "有行无卡", "detail": "..." }],
  "skippedRows": [{ "rowNo": 5, "reason": "合计行" }]
}
```

文件名以 `adapter.json` 的 `output.rows` / `output.report` 为准，默认就是 `factRows.json` / `report.json`。

字段口径（以 `FactRowInput` 为准）：
- `sheet` / `rowNo`：必填。多 sheet 时每行都要带自己的 sheet 名。
- `startedAt`：必填，Unix 秒。用 `Date.UTC(...) / 1000 - 8 * 3600`，**禁止** `new Date("2026-01-02 03:04:05")`（按进程时区漂）。
- `precision`：`到日` / `到分` / `到秒`；缺省按 `到日`。
- `amount`：必填，正数字符串，无千分位。原值是负数就取绝对值，方向由方向列决定。
- `direction`：必填，`收` / `付`。方向列缺失时才允许「负数 ⇒ 付」；正数不猜。
- `ownerAccount` / `counterparty`：必填，非空；空则该行跳过（原因码复用 `缺本方账号` / `缺对方账号`）。
- `currency`：缺列或空 ⇒ `CNY`；`人民币` / `RMB` / `元` ⇒ `CNY`；其余转大写原样保留（认不出的币种宁可算非人民币，也不静默当人民币）。
- `counterpartyName`：对方户名。`extras.ownerName`：本方户名（下游会变成实体别名）。
- `extras.备注` / `extras.交易类型`：下游用途判定会读，有就保留。
- `extras` 里只有 `ownerName` / `备注` / `交易类型` / `属性:*` 会被下游读取，其余键当前不入库。关键信息不要只放在别的 extras 键里。
- **不要输出** `projectId` / `materialId` / 数据库 id：由内核注入。

跳过行：转换器自己判定并写入 `skippedRows`（空行、合计行、方向不明、金额无法解析、时间无法解析、缺本方账号、缺对方账号）。原因用语尽量复用下游 `翻译资金` 的词表，便于两边计数对账。不要既产出又被下游跳过——同一行只在一处判。

实现要求：
- 表头行在前 10 行内找「命中必需列最多」的一行；并列取最早。把 `headerRow` 记进 report。
- 不要用 `sheet_to_json({ blankrows: false })`：它会吞掉空行、让 `rowNo` 偏移。用 `ws["!ref"]` 的起始行 + 数组下标算 Excel 行号。
- 账号列按文本读。若单元格是数值且超过 15 位，Excel 已经丢精度，**无法恢复**：整份拒收或逐行告警，不许补零、不许转科学计数法。
- 每一侧按「方」解析，不按「列」解析：先定本方方/对方方，再从那一组里取账号、卡号、开户行、户名。
- 名册类补全（同账号在其他行出现过的户名/开户行）先建一次 Map，再单遍回填。不许每行回头扫全表（O(n²)）。
- 属性列的值来自本行该侧的绑定列；本行没有就留空，不产观察。
- 排序稳定：按 `sheet`、`rowNo` 升序输出。

────────────────────────────────
七、第四步：数据库匹配与「新数据列」
────────────────────────────────
转换器**永远不查库**。需要库里数据补全时，只有两条合法路径：

A. 行内已有 → 直接写属性列。例：源文件有「对方银行卡所属行」⇒ `属性:对方:开户行`。

B. 行内只有键、值在库里 → 输出键，并在 `adapter.json` 声明富化需求，由内核富化层批量查、回填、带依据与置信度。建议的扩展结构（**尚未写进 §6.1，先用先拍板**）：
{
  "enrich": [
    {
      "kind": "案件库",
      "from": "counterparty",
      "to": "属性:对方:开户行",
      "policy": "fill-empty"
    },
    {
      "kind": "参考库",
      "ref": "bank-card-bin@2026-11",
      "from": "counterparty",
      "to": "属性:对方:开户行",
      "policy": "fill-empty"
    }
  ]
}

约束：
- 先 distinct 键，再批量查；不许逐行查（远端 PG 单次往返 22ms，5,000 行就是 110 秒——`#013-09`）。
- 查不到：参考类留空 + `warnings`；身份类进「待确认」，不猜。
- 每个补全值必须能追溯「值 + 依据 + 置信度 + 版本」；追溯由内核做，转换器不许伪造依据。
- 富化结果不进 `adapter.json`、不落缓存文件；重跑必须重新取。
- 富化的落点只有三类：属性列、户名别名、已声明的标准字段。**不许动态新增标准字段**——标准字段是闭集（`case-field-registry.ts`），下游翻译层只认那些。库里查到「客户姓名」时走别名，不要自造 `客户姓名` 标准列。
- `policy` 首批只建议 `fill-empty`（本行空才补）。`override` 会覆盖源文件证据，必须单独裁定并留痕。
- N4（富化层）未实现前，转换器只能产键 + 声明；不许在转换器里用 `pg` / `Bun.sql` 绕开凭据边界。

────────────────────────────────
八、第五步：实体属性字段怎么建（让 AI 查得到）
────────────────────────────────
转换器写的是**列名**；内核解析后把归属剥掉，把值挂到对应实体上。最终 `case_entity.attrs` 的形状是：
{ "开户行": [{ "值": "招商银行", "出处": "<material_id>#Sheet1#2" }] }
AI 通过 `query_entities` 读到的就是这份 `attrs`。

**先过一个前提闸：属性只在「这一侧的账号能建实体」时才入库。** 内核 `翻译资金` 调 `是账户形状`（归一化后 `^\d{6,32}$`，`case-field-registry.ts`）判本方可建/对方可建；不满足时（微信 `...@wx.tenpay.com`、支付宝邮箱、掩码账号），这一侧的属性和户名别名都会被丢弃，只剩 `mention_text`。所以写属性列前先确认：规范账号是数字账号吗？不是的话，先按 §7 的待定项裁定「用哪一列当规范账号」，不要写了属性却以为它会入库。

因此：
- 归属决定挂哪个实体。`属性:对方:开户行` 挂对方账户，`属性:本方:开户行` 挂本方账户。写反了不会报错，只会答错。
- 键决定「是什么属性」。首批词表：`开户行`、`银行卡号`、`证件号`；词表外照收，但必须在 SKILL.md 登记并保持稳定。
- 同一实体同一键的多个值会并存（按值去重、保留首次出处），不要为了「只留一个」而丢证据。
- 不要把标准字段再做成属性：账号、户名、金额、时间、方向已经有标准列。
- 不要把户名做成属性：户名走 `case_entity_alias`（`extras.ownerName` / `counterpartyName`），它参与实体归并。
- 一行一侧出现多张卡/多个开户行时，不要拼成一个字符串。要么用稳定后缀键（`银行卡号2`，并在 SKILL.md 声明），要么只保留主卡并逐行告警——先定规则，再写代码。

────────────────────────────────
九、第六步：测试（RED → GREEN → 变异）
────────────────────────────────
1. golden：真实脱敏样本 → `expected.factRows.json` / `expected.report.json`，深度相等。
   - 先断言 `rows.length > 0`、行数守恒、金额合计、收/付计数，再做深度相等。防「空跑绿」（`#013-03`）。
2. 拒收：改坏一列必需列 → 退出码 3、有 report、**没有 factRows.json**。
````

## 3. 原理解析：为什么规则长这样

### 3.1 转换器为什么插在「读表之后、识别之前」

现有入库顺序是：读表 → 查数据源档案/格式缓存 → 四层识别 → 模型兜底（`case-ingest.ts` 的 `跑表格`）。B 类格式的问题不是「列名认不出」，而是**同一列的含义随行变化**——微信流水的「付款方/收款方」谁算本方，取决于这一行的借贷标志。档案只能做「列 → 字段」的静态映射，做不了逐行角色翻译。

所以 M2 的顺序是：读表 → **先问适配器注册表** → 命中就执行转换器、直接读 JSON 事实行，跳过四层识别；未命中才走原路径。转换器失败落「有问题」，不回退模型——因为「模型猜出来的半份数据」比「明确失败」更难发现、更难审计。

### 3.2 为什么必须是确定性代码，不是模型

一笔资金的「本方/对方」写反，不会报错：它会安静地建成两个实体、安静地算错资金流向，最后以「分析结论」的形式出现。模型每次跑可能不一样，无法用 golden 测试钉住，也无法向办案人解释「为什么这行是对方」。确定性代码的代价是写一次规则，收益是同一份文件永远得到同一份结果、每一条都能回到 `材料#表#行`。

### 3.3 为什么要有识别卡，而不是让内核读 SKILL.md

内核要在**只读表头的一秒内**决定「用不用它」。SKILL.md 是给人读的长文，模型可以读，内核不能稳定解析。`adapter.json` 是机器契约：必需列、可选列、优先级、两道闸的阈值、入口命令。它同时是发布时的校验对象（M10：坏包不许发布/启用）。

### 3.4 为什么两段式闸门

- **表头闸**便宜：只读表头，不碰数据行，用来在 1 秒内给「已识别/未识别」。
- **值验证闸**贵：要读样本行甚至全量，用来回答「表头像 ≠ 这份数据真的符合假设」。

两段分开的好处是：上传后立刻有反馈，全量转换在后台跑；而且「表头对、方向规律不对」会被值闸挡住——那通常说明是另一种取数口径，不是脏数据。任一不过整份拒收，因为半份数据进了库，后面所有统计都带一个说不清的缺口。

### 3.5 为什么属性列要带 `属性:<归属>:<键>` 前缀

内核的合成候选会把「对手修饰 + 账号词尾」认成 `counterparty`、把「本方修饰 + 账号词尾」认成 `ownerAccount`。裸的「对方银行卡号」不会被当成属性，而会被当成**对方账号**，进而造出一个错误实体——没有红字，只有答错（`01` §13 Q9 / M8）。前缀是让这两类列在语法层就分开：`属性:` 开头的一律不参与表类型投票与字段召回。

归属写进列名而不是值，是因为归属是**结构**：它决定这条观察挂到本方实体还是对方实体。写进值里就得再解析一次，而且没法在 SQL/jsonb 层直接按归属取。

### 3.6 为什么户名走别名、不走属性

户名参与**实体归并**：同一个账户在不同材料里叫「张三」「张三（个人）」「张*三」，要靠 `case_entity_alias` 把它们连到同一个实体。属性只是实体的描述（开户行、卡号、证件号），不参与归并。把户名塞进属性，AI 能读到名字，但「按户名搜实体」会搜不到。

### 3.7 为什么富化在内核、不在转换器

转换器跑在子进程里，**不注入数据库凭据**。这是权限边界，不是性能优化。富化需要：批量查、缓存、版本、置信度、失败降级、审计。这些都依赖内核的连接池与项目身份，放在转换器里等于把凭据发给每个技能包。所以转换器只产「键」，内核负责「查 + 回填 + 留痕」。

### 3.8 为什么金额取正、方向单列

`sum(amount)` 如果收支相抵，看起来像「这个账户没交易」。金额永远存正数，方向只用 `收/付` 表达，统计时按方向分组。也不要从负号反推方向——那会和方向列冲突，同一事实两个来源（`#002-06`）。

### 3.9 为什么 `rowNo` 必须是 Excel 行号

出处是 `material_id#sheet#rowNo`。用户拿着结论回原文核对时，打开 Excel 看到的行号必须能对上。用数组下标（从 0 开始、空行被吞）会整体偏移，出处就废了。

### 3.10 为什么阈值只能有一个出处

内核探测读 `adapter.json` 的阈值，转换器全量跑也校验同一批指标。如果代码里再写一份数字，改了一处、忘了另一处，就会出现「探测通过、转换拒收」或反过来——两边都觉得自己对。所以 `convert.ts` 启动时读同目录的 `adapter.json`，阈值、必需列都从那里取。

## 4. 注意事项（按踩坑后果排序）

### 4.1 角色与字段

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 按列名硬取「对方」 | 贷方行（钱进来）本方/对方整体互换，接近一半行错 | 先按方向定「本方方/对方方」，再从那一侧取字段 |
| 把银行卡号当账号的备胎 | 对方账号变成卡号，实体建错 | 支付账号是主体，卡号是它名下的卡，各进各的列/属性 |
| 提现/充值当成外部交易 | 对手账号写成本人卡号，凭空多一个对手 | 对方账号仍写支付账号（可能等于本方）；移动的卡进 `属性:对方:银行卡号/开户行` |
| 把「收款方的商户名称」当消费商户 | 336 行收入行的户名整体错位 | 它是**收款方账户的开户人姓名**，跟着收款方走；含「个人」是个人，其余按企业 |
| 借贷方向直接套「借=付」 | 不同银行/不同导出口径可能相反 | 用「方向与本方一致」值闸验证：借方付款方必须等于查询账号，贷方收款方必须等于查询账号 |
| 户名塞进属性 | 按户名搜不到实体 | 本方户名 → `extras.ownerName`；对方户名 → `counterpartyName` |
| 账号带横线/全角/`+86` 直接入库 | 同一账户被建成两个实体 | 标准列写归一化值，原文写 `*Raw`；归一化规则与内核 `case-field-registry` 保持一致 |

### 4.2 数据形状

- **空行会吞行号**：`sheet_to_json({ blankrows: false })` 让数组下标和 Excel 行号错位。用 `!ref` 起始行 + 保留空行。
- **表头不一定在第 1 行**：在前 10 行里找命中必需列最多的一行；并列取最早，并把 `headerRow` 写进报告。
- **合并单元格**：只有左上角有值；表头合并要向右/向下填充，否则必需列被判缺失。填充规则写进 SKILL.md。
- **长账号精度**：Excel 数值单元格超过 15 位已经丢精度。检测到就拒收/告警，不许补零。账号列优先按文本读。
- **日期单元格**：可能是序列号、可能是文本、可能是格式化后的 `1/2/26`。解析用原始值/ISO，`startedRaw` 保留用户看到的原文。
- **多 sheet**：默认只处理通过表头闸的那一个；多个都过就取第一个并告警，不许静默合并。
- **CSV 编码**：中文银行导出常见 GBK。读不出来就报「读文件失败」，不要用替换字符硬转（会把户名变成乱码，且无法发现）。
- **全角/千分位/括号负数**：金额先剥千分位、全角转半角；`(1,234.56)` 这种会计负数要识别，认不出就跳过并告警。

### 4.3 契约

- 属性列只认**半角冒号**。全角 `属性：对方：开户行` 不会被识别，会静默变成普通列——写测试钉住。
- `rowNo` 从 1 开始，表头行也占号；第 1 行数据通常是 2。
- `amount` 是字符串，不是 number：`numeric(18,2)` 的整数位可到 16 位，超过 JS 安全整数范围。
- `direction` 只允许 `收`/`付`；`收入`/`支出`/`借`/`贷` 必须先映射。
- `extras` 里除 `ownerName`/`备注`/`交易类型`/`属性:*` 外，当前不会被下游读取；别把关键事实只放在那里。
- 拒收时不要写 `factRows.json`。写了空数组也不行——「有文件」会被下游当成可用产物。

### 4.4 性能

- 单遍扫描，所有名册/映射先建好（账号→户名、账号→开户行、借贷映射）。别在行循环里回头扫全表。
- 不要逐行做字符串拼接大对象、不要逐行 `JSON.stringify`。最后一次性写文件。
- 转换器不查库；如果未来允许，也必须 distinct + 批量（`#013-09`：逐行语句 = O(N×RTT)，远端 22ms/次）。
- 5,000 行是当前验收规模；10 万行时先量内存和 GC，再谈流式。

### 4.5 安全与治理

- 不读 `process.env` 里的数据库配置；不 `fetch`；不 `import` 技能目录外的文件。
- 日志不要打印整行原文（含户名、账号、证件号）。要定位就打印 `rowNo` + 错误类型。
- 转换器不自己启用、不自己发布；启用是项目属主的动作，发布走资产流水线。
- 版本升了必须重跑 test；`report.adapterVersion` 从 `adapter.json` 复制，不许手写。
- 不要把「可信技能自动启用」当成默认行为；它是项目级开关，默认关闭。

### 4.6 测试

- golden 只断言 `toEqual` 容易「空跑绿」：先断言行数、金额合计、收/付计数，再深度比较。
- 变异要拆**语义**，不是改格式：拆掉方向切换、改属性归属、把时区改成 UTC。格式类变异（多一个空格）证明不了规则对不对。
- 拒收测试要断言「没有 factRows 文件」，不能只断言退出码。
- 内核与转换器各有一份解析器，用同一组向量钉住；发现两边不一致，先查谁的口径是权威（`case-time.ts` / `case-rows.ts`），不要各改一半。

```ts
import * as XLSX from "xlsx"
import { createHash } from "node:crypto"
import { mkdirSync, readFileSync, writeFileSync } from "node:fs"
import { join } from "node:path"

const 卡 = JSON.parse(readFileSync(join(import.meta.dir, "adapter.json"), "utf8"))
const 参数 = process.argv.slice(2)
const 取值 = (名: string) => {
  const i = 参数.indexOf(名)
  return i >= 0 ? 参数[i + 1] : undefined
}
const 输入 = 取值("--input")
const 输出目录 = 取值("--out")
if (输入 === undefined || 输出目录 === undefined) {
  console.error("用法: bun run convert.ts --input <file> --out <dir>")
  process.exit(1)
}

const 源字节 = readFileSync(输入)
const 源sha = createHash("sha256").update(源字节).digest("hex")
const 工作簿 = XLSX.read(源字节, { type: "buffer", cellDates: false, cellText: true })

// 1) 找 sheet 与表头行
const 必需列: string[] = 卡.match.requiredHeaders
let 选中: { 名: string; 行集: unknown[][]; 起始行: number } | undefined
for (const 名 of 工作簿.SheetNames) {
  const 表 = 工作簿.Sheets[名]!
  const 行集 = XLSX.utils.sheet_to_json<unknown[]>(表, { header: 1, raw: false, defval: "", blankrows: true })
  const 起始行 = XLSX.utils.decode_range(表["!ref"] ?? "A1").s.r
  let 最佳 = -1
  for (let i = 0; i < Math.min(10, 行集.length); i++) {
    const 命中 = 必需列.filter((列) => 行集[i]!.includes(列)).length
    if (命中 > 最佳) 最佳 = 命中
  }
  if (最佳 === 必需列.length) {
    选中 = { 名, 行集, 起始行 }
    break
  }
}

// 2) 表头闸
if (选中 === undefined) {
  const 报告 = { adapterId: 卡.id, adapterVersion: 卡.version, sourceSha256: 源sha,
    headerGate: { 通过: false, 缺列: 必需列 }, gates: [], warnings: [], skippedRows: [] }
  mkdirSync(输出目录, { recursive: true })
  writeFileSync(join(输出目录, "report.json"), JSON.stringify(报告, null, 2))
  process.exit(3)
}

// 3) 定位表头、建列索引
const { 名: sheet名, 行集, 起始行 } = 选中
const 表头下标 = 行集.findIndex((行) => 必需列.every((列) => 行.includes(列)))
const 表头 = 行集[表头下标]!.map((v) => String(v).trim())
const 列 = (名: string) => 表头.indexOf(名)
const 单元格 = (行: unknown[], 名: string) => {
  const i = 列(名)
  return i < 0 ? "" : String(行[i] ?? "").trim()
}

// 4) 逐行转换：先按「方」绑定，再取字段
const rows: Record<string, unknown>[] = []
const skippedRows: { rowNo: number; reason: string }[] = []
for (let i = 表头下标 + 1; i < 行集.length; i++) {
  const 行 = 行集[i]!
  const rowNo = 起始行 + i + 1 // Excel 行号从 1 开始
  if (行.every((v) => String(v ?? "").trim() === "")) {
    skippedRows.push({ rowNo, reason: "空行" })
    continue
  }
  const 借贷 = 单元格(行, "借贷标志")
  if (借贷 !== "借" && 借贷 !== "贷") {
    skippedRows.push({ rowNo, reason: "方向不明" })
    continue
  }
  const 查询账号 = 归一化账号(单元格(行, "查询账号"))
  const 本方方 = 借贷 === "借"
    ? { 账号: 单元格(行, "付款方支付帐号"), 卡: 单元格(行, "付款方银行卡号"), 行: 单元格(行, "付款方银行卡所属行"), 户名: "" }
    : { 账号: 单元格(行, "收款方支付帐号"), 卡: 单元格(行, "收款方银行卡号"), 行: 单元格(行, "收款方银行卡所属行"), 户名: 剥主体类型(单元格(行, "收款方的商户名称")) }
  const 对方方 = 借贷 === "借"
    ? { 账号: 单元格(行, "收款方支付帐号"), 卡: 单元格(行, "收款方银行卡号"), 行: 单元格(行, "收款方银行卡所属行"), 户名: 剥主体类型(单元格(行, "收款方的商户名称")) }
    : { 账号: 单元格(行, "付款方支付帐号"), 卡: 单元格(行, "付款方银行卡号"), 行: 单元格(行, "付款方银行卡所属行"), 户名: "" }

  const 时间 = 解析时间(单元格(行, "交易时间"))
  const 金额 = 解析金额(单元格(行, "交易金额"))
  if (时间 === undefined) { skippedRows.push({ rowNo, reason: "时间无法解析" }); continue }
  if (金额 === undefined) { skippedRows.push({ rowNo, reason: "金额无法解析" }); continue }
  if (查询账号 === "" || 本方方.账号 === "") { skippedRows.push({ rowNo, reason: "缺本方账号" }); continue }
  if (对方方.账号 === "") { skippedRows.push({ rowNo, reason: "缺对方账号" }); continue }

  const extras: Record<string, string> = {}
  if (本方方.户名 !== "") extras["ownerName"] = 本方方.户名
  const 备注 = 单元格(行, "备注")
  const 交易类型 = 单元格(行, "交易类型")
  if (备注 !== "") extras["备注"] = 备注
  if (交易类型 !== "") extras["交易类型"] = 交易类型
  const 属性 = (归属: "本方" | "对方", 键: string, 值: string) => {
    if (值 !== "") extras[`属性:${归属}:${键}`] = 值
  }
  属性("本方", "银行卡号", 本方方.卡)
  属性("本方", "开户行", 本方方.行)
  属性("对方", "银行卡号", 对方方.卡)
  属性("对方", "开户行", 对方方.行)

  rows.push({
    sheet: sheet名,
    rowNo,
    startedAt: 时间.秒,
    startedRaw: 单元格(行, "交易时间"),
    precision: 时间.精度,
    timeType: "发生",
    amount: 金额,
    balance: 解析金额(单元格(行, "交易余额")) ?? undefined,
    direction: 借贷 === "借" ? "付" : "收",
    ownerAccount: 查询账号,
    ownerAccountRaw: 单元格(行, "查询账号") || undefined,
    counterparty: 归一化账号(对方方.账号),
    counterpartyRaw: 对方方.账号 || undefined,
    counterpartyName: 对方方.户名 || undefined,
    currency: 解析币种(单元格(行, "币种")),
    extras
  })
}

// 5) 值闸 + 报告 + 写文件（略：按 adapter.json 的 thresholds 逐项算分母/命中）
```

要点：

- 时间 `解析时间` 返回 `{ 秒, 精度 }`，秒按 Asia/Shanghai 算（`Date.UTC(...) / 1000 - 8*3600`）。
- `归一化账号` 只做全角转半角、去空白/横线；原文另存。
- 属性写入统一走 `属性()`，空值自动不写——不要散落 `if`。
- 代码里没有阈值数字；全部来自 `卡.admission.thresholds`。

## 7. 与需求文档的衔接：还没拍板的事

写转换器前，下面几条要么已经定了，要么必须先问：

1. **`enrich` 是否进 §6.1**：本文给的是建议结构；需求文档目前只有 §6.5 的查询契约，没有适配器声明。没有声明，内核富化层不知道「用哪个键补哪个属性」。
2. **`entry` 的 CLI 参数**：本文约定 `--input/--out`；N3 实现时若改成环境变量或位置参数，四件套必须同步。
3. **拒收退出码**：本文用 `3`；执行器要按这个映射原因码，不能只看 stderr 文本。
4. **一行多卡/多开户行**：用后缀键还是只留主卡 + 告警，需按业务裁定；两种都会影响 AI 查询口径。
5. **`precision` / `timeType` 是否要求转换器填**：不填时内核按 `到日` / 默认类型处理；对资金流水建议填，避免「知道到秒却按到日算」。
6. **多 sheet 文件**：只处理一个 sheet 还是逐 sheet 产出，需与材料模型对齐。
7. **版本语义**：规则不变、只改文案要不要升版本？建议只升 `version` 当转换结果可能变化时；纯文档改动不动版本。
8. **需求 §6.2 的图示与 §6.1 不一致**：§6.1 声明 `output.rows` / `output.report` 是两个文件，§6.2 的示例却把 `rows` 与 `report` 画在同一个对象里。本文按 §6.1 的两文件实现（`factRows.json` 只有 `rows`，`report.json` 只有报告），建议回写 §6.2 的示例。
9. **非数字账号怎么建实体（微信/支付宝）**：`翻译资金` 用 `是账户形状`（`^\d{6,32}$`）判本方可建/对方可建。微信支付账号、支付宝邮箱、带掩码的账号都不满足 ⇒ 只留提及，属性与户名别名全部丢弃。三个候选方向，必须选一个：① 转换器把银行卡号当规范账号（有卡时）；② 按 `materialType` 放宽 `是账户形状`，允许字母/`@`；③ 接受提及-only，属性走别的挂载点（设计变更）。选 ① 会改变「支付账号是主体」的口径；选 ② 会扩大实体合并面（需防重号）；选 ③ 要先有新的挂载模型。**这条不裁定，微信格式的属性列写了也不会入库。**

这些没定之前，转换器可以先按本文实现，但要在交付说明里标「依赖待定项 X」。

## 8. 附：字段与词表速查

### 8.1 标准字段（写进 `rows[]` 顶层）

| 字段 | 类型 | 资金必填 | 说明 |
|---|---|---|---|
| `sheet` | string | 是 | 工作表名 |
| `rowNo` | number | 是 | Excel 行号，从 1 开始 |
| `startedAt` | number | 是 | Unix 秒，Asia/Shanghai |
| `startedRaw` | string | 否 | 时间原文 |
| `precision` | `到日`/`到分`/`到秒` | 否 | 缺省 `到日` |
| `timeType` | `发生`/`记录`/`入库` | 否 | 建议 `发生` |
| `amount` | string | 是 | 正数、两位小数 |
| `balance` | string | 否 | 两位小数 |
| `direction` | `收`/`付` | 是 | 只这两个值 |
| `ownerAccount` | string | 是 | 本方账号（归一化后） |
| `ownerAccountRaw` | string | 否 | 本方账号原文 |
| `counterparty` | string | 是 | 对方账号（归一化后） |
| `counterpartyRaw` | string | 否 | 对方账号原文 |
| `counterpartyName` | string | 否 | 对方户名 |
| `currency` | string | 否 | 缺省 `CNY`；认不出保留大写原值 |
| `caller` / `callee` | string | 话单 | 主叫 / 被叫 |
| `durationSec` | number | 话单 | 通话时长（秒） |
| `extras` | object | 否 | 见 8.2 |

**禁止输出**：`projectId`、`materialId`、数据库主键、`case_material` 状态字段。

### 8.2 `extras` 里下游会读的键

| 键 | 用途 |
|---|---|
| `ownerName` | 本方户名 → `case_entity_alias kind='户名'` |
| `备注` | 用途判定输入 |
| `交易类型` | 用途判定输入 |
| `属性:<对方\|本方>:<键>` | 实体属性观察，挂到对应侧实体 |

其余键当前不被下游读取，不要放关键事实。

### 8.3 属性键

首批：`开户行`、`银行卡号`、`证件号`。词表外照收，但必须在 SKILL.md 登记并保持稳定。

### 8.4 跳过原因（与下游 `翻译资金` 对齐）

`空行`、`合计行`、`小计行`、`方向不明`、`金额无法解析`、`必填槽为空`、`时间区间倒置`、`时间无法解析`、`缺本方账号`、`缺对方账号`。

转换器自己判过的行，不要再让下游判一次；计数要对得上。

### 8.5 原因码（内核写，转换器只触发）

```
未识别:无匹配适配器
未识别:缺必需列:<列名>
未识别:值闸不过:<检查项>
失败:读文件
失败:转换器异常
失败:入库异常
```
