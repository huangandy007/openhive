## 1. 问题与证据

### 1.1 合并断链

`case-merge.ts` 的合并只做三件事：并别名（`:200-207`）、改关系端点（`:182-193`）、删被并入行（`:209`）。**它不碰**：

- `auth.case_event_participant.entity_id` → 被并入行一删，参与者指向不存在的实体，事件从幸存者的时间线里消失；
- `auth.case_entity_alias.entity_id` → 户名别名悬空，`户名对齐` 的 `join ae` 落空，阻断 1 的修复随之失效。

设计 `01` §12.2 的「合并断链」风险仍在。

### 1.2 传播是一条死路

`case-propagation.ts:48`：

```sql
and exists (select 1 from unnest(participants) as 参与者 where 参与者 = ${entityId})
```

`participants text[]` 存的是**规范值**（`01` §3.3），`entityId` 是实体 id。两边永远不相等 ⇒ 「改实体 → 事件标依据已变更」实际返回 **0 条**。这不是漏，是 id-vs-value（`#006-11` 同型）。

### 1.3 阻断 1：账户归属不认户名对齐

`aggregate_money(B)` 入账 2 笔 / 25000，漏了「A→李四 10000」：李四经未撤销户名对齐到账户 B，但 `aggregate_money` 的账户过滤只认关系端点 id（`case-mcp-tools.ts:1555-1575`）。同一份数据，A 的出口 3 笔 / 35000 与 B 的入口对不上。

### 1.4 两个探索原语缺失

`case-mcp-server.ts` 注册了 9 个工具（`search_materials` / `query_entities` / `query_relations` / `query_events` / `aggregate_money` / `find_crossings` / `get_citation` / `query_rows` / `query_timeline`），**没有** `explore_entity` 与 `money_flow`（`09` §4.1 / §4.2）。

### 1.5 两处读端口径不齐

- `query_timeline` 的参与者摘要不剔除「已排除」实体值，`query_events` 有；
- `裁决` 对 entity 类事实不触发资金重算，relation / event 类会（第一期阻断 2 的修复只覆盖后两者）。本期**不补**——实测该重算无可观测行为（`重建关系` 只读事件与人工关系，entity 裁决不改这两类输入），见 §7.2 的裁定。

## 3. 共享读基

两个前提各收成**唯一出处**（`#002-06`），所有读者接上去，不许各自再抄一份条件。

### 3.1 基 1：事件参与者条件（升级）

现有函数 `case-mcp-tools.ts` 的 `事件参与者条件(ctx, 实体)` 升级为三路并集：

```
p.entity_id ∈ (实体.id, 对齐代表(实体))          -- 参与者表：本人 或 正向对齐
OR p.entity_id ∈ 对齐到账户(实体)                 -- 参与者表：对齐到本账户的人/组织（仅账户）
OR participants text[] ∈ (规范值 ∪ 别名集)         -- 旧数据 / AI 抽取路径回退
```

- **正向对齐**（已有）：按人查时，表格事件的参与者是账户，用 `对齐代表` 换成账户 id。
- **反向对齐**（新增）：按账户查时，笔录事件的参与者是人（李四），必须把「唯一户名对齐到本账户的人/组织」也算进来。判定与 `户名对齐` 对称且同样 fail-closed：别名值只对应唯一账户时才成立。
- **text[] 回退**：`participants` 存规范值；用 `case_entity.canonical_value` 与 `case_entity.aliases` 一起匹配。合并只把旧值并进别名、不改 text[]，这一路让合并前写入的事件仍然命中。
- **同名歧义（缺口 #11，fail-closed）**：`participants` 只存值不存类型，唯一索引是 `(project_id, type, canonical_value)` ⇒ 同一规范值可以同时对应人、组织。该值在项目内对应 **≥2 个未排除实体**时不按值归属（不猜）；参与者表支路按 `entity_id` 判，不受影响。被挡掉的条数由 `实体档案` 写进 `缺口`（`参与人同名未归属 N 条…`），`explore_entity` 原样透传。
- 参与者表 `entity_id` 可为空（对不上档案）——这类行走 text[] 回退。

**反向对齐集**（新增导出函数 `对齐到账户(projectId, 账户id)`）：返回「唯一户名对齐到该账户」的人/组织 id 集，供基 1 与基 2 共用（`#002-06`）。判定：

```sql
select pe.id
  from auth.case_entity pe
 where pe.project_id = ?
   and pe.type in ('人', '组织')
   -- 该人的规范值恰好只对应一个账户（fail-closed 的一半）
   and (select count(distinct a.entity_id) from 户名来源(?) and a.value = pe.canonical_value) = 1
   -- 且这个账户就是本账户（另一半）
   and exists (select 1 from auth.case_entity_alias a
                join auth.case_entity ae on ae.project_id = a.project_id and ae.id = a.entity_id
               where a.project_id = ? and a.entity_id = ? and a.kind = '户名' and a.revoked_at is null)
   and exists (select 1 from auth.case_entity_alias a
               where a.project_id = ? and a.entity_id = ? and a.kind = '户名'
                 and a.revoked_at is null and a.value = pe.canonical_value)
```

实现时按 `户名来源` 的调用约定拼（它已以 `where` 结尾），并只用一次子查询、由两个读者共享。

**消费方**：`query_events` / `query_timeline` / `find_crossings`（已调用，自动继承）、`case-propagation.标依赖已变更`（改为同一子查询）、基 2（同一集合）。

### 3.2 基 2：账户归属条件（新增）

关系归属某账户的判据，**不逐行投影**，用集合成员判定：

```
归属(端点) = 端点 ∈ (账户.ids ∪ 对齐到账户(账户))
关系归属该账户 ⇔ 归属(from_id) XOR 归属(to_id)      -- 恰好一端落在集合里
```

因此：

- 关系 `A → 李四`（人，唯一对齐到账户 B）在账户 B 的视角下归属 B；方向按**落在集合里的一端**判（from 侧在集合 ⇒ 出，否则入）；对手方是**另一端**（A），不需要改写端点。
- **两端都落在集合里 ⇒ 账户内部关系，不归属**（如 `李四 → B`，两端都归属 B）。它会在账户视角下变成自环，既不产生对手方也不产生方向；不画、不计数，写进缺口。这正是「恰好一端」而非 `OR` 的原因。
- 候选 0 个或 ≥2 个一律不归属（fail-closed），候选数进缺口。
- 对「人 / 组织」自身查关系时不套用（集合只由账户 id 构建，人的档案保持原口径）。

**消费方**：

| 读口 | 怎么用 |
|---|---|
| `aggregate_money` | 账户过滤、方向改用本条件；对手方分组与金额口径不变 |
| `实体档案`（`case-entity-list.实体档案`） | 中心是账户时，`关系触达` / `关系可见` / `涉及` 三处谓词改用本条件；`关系总数` / `对方数` 随之对齐 |
| `关系图`（`case-graph.关系图`） | 中心是账户时，端点落在集合里的边纳入图；边的另一端仍是对方实体，不新增节点；缺口交代「N 条关系经户名对齐归属本账户」 |

**语义**：这不是「同一个人」的合并，只是读端把「户名唯一对应的账户」当作该笔资金的归属方；实体本身仍是两行，列表与关系事实不隐藏。

### 3.3 fail-closed 与缺口

- 别名对应多个账户 ⇒ 不对齐、不归属；该条关系的候选数进 `缺口`（`aggregate_money` 已有同型处理，实体档案/关系图沿用）。
- 不静默：任何「没算进来」的数量必须在 `缺口` 里有一句可读的话。

## 4. 合并与传播

### 4.1 合并新增两步

顺序固定：**先改指向，再删被并入行**；两步都在既有事务内。

1. `update auth.case_event_participant set entity_id = 幸存者.id where project_id = ? and entity_id = 被并入.id`
2. `update auth.case_entity_alias set entity_id = 幸存者.id where project_id = ? and entity_id = 被并入.id`

`participants text[]` **不改**：旧规范值成为幸存者的别名，由基 1 的 text[] 回退命中。

### 4.2 留痕与拆分

**改指即留痕（缺口 #6）**：合并留痕 `before` 的四份快照（`关系们` / `参与者们` / `别名们` / `引用们`）全部取改指语句的 `UPDATE … RETURNING` 结果，**不取改指前的读**。改指前的读填不满「读 ↔ 改」之间落进来的行：远端 PG 16.3 探针（锁住一条关系行、把合并钉在「关系改指」）实测修前留痕 `参与者们 [E1]` 而实际 `[E1,E2]`、`别名们 [A1]`/`[A1,A2]`、`引用们 [X1]`/`[X1,X2]`，拆分 `未恢复=[]` 却恢复不回去。

- 关系：两次改指的 `RETURNING` 合并成实改集；旧端点从「这条 update 没动的那一侧」回读（正向只改 `from` ⇒ 返回的 `to` 是原值；反向反之）；`M→M` 两边都命中，由正向记（正向执行后 `from_id` 已是主体，反向回读会记错）。
- 自环清单由同一份实改集按**改指后的端点**算，再逐条标 `已排除`。
- 残余窗口的兜底是**条件删除**：删被并入行前检查四类行都不再指向它（同一条 `DELETE … RETURNING`，同一份快照）；仍有行指向 ⇒ 抛 `合并冲突 concurrent_write`，整次合并回滚。关系改指语句取快照早于等行锁，窗口内新插的关系它一条都看不到、也不改指——只有回滚能避免「被并入行删掉后关系悬空」。
- **残余（`#002-02` 登记）**：条件删除到事务提交之间仍有毫秒级窗口；彻底闭合需要所有写关系/参与者/别名/引用的入口共取咨询锁（翻译、重算、人工多条写路径），超出本期。

拆分时按留痕把四处指向恢复。**被人动过的不覆盖**：行已不存在、或 `entity_id` 已不是幸存者（被后续合并/重放改过），进现有的 `未恢复` 清单，不静默。

**代价**：一宗合并可能涉及上千参与者行，留痕体积变大。接受——拆分必须原样恢复，这是 `01` §9.3 的承诺。

### 4.3 传播改写

`标依赖已变更(projectId, entityId)`：

- 关系依赖不变（`from_id / to_id = entityId`）；
- 事件依赖改走基 1（参与者表 + text[] 回退），不再拿 id 比规范值；
- 返回的 `{ relations, events }` 计数与只打时间戳的语义不变。

### 4.4 语义收益

「人」被改动时，标的是「参与这个人的账户事件」（经正向对齐）与「这个人作为参与者的笔录事件」（参与者表/文本值），不再是 0 条。这正是 `01` §9.4 想要的依赖传播。

## 6. `money_flow`（工具层）

契约以 `09` §4.2 为准。

| 项 | 内容 |
|---|---|
| 入参 | `账户`（必填）、`起?`、`止?`、`方向?`（收 / 付 / 全部）、`对手?` |
| 数据 | 笔数；收入合计 / 支出合计（分列，不相抵）；首末；对手排行前 20（笔数、金额、首末）；单笔最大前 10（含出处代表）；集中度（前 3 对手占比）；`外币行数` |
| 空原因 | `确实没有交易` / `实体没有关联账户` / `账户未在材料中出现` / `项目内资金材料未翻译` / `外币行全部未计入` |
| 下一步 | `explore_entity`（对手）/ `query_rows`（大额明细）/ `query_timeline`（同期事件） |
| 依赖 | 没翻译时必须返回 `项目内资金材料未翻译`，不许返回 0 笔 |

实现方式：

- 汇总、对手方、外币行数、空原因四拆、时间窗校验、`解析账户` **全部复用 `aggregate_money`**（`case-mcp-tools.ts:1537`），不另写 SQL；基 2 的归属修复自动生效；
- 外层补三项：
  1. `首末`：关系窗内 `min(first_at)` / `max(last_at)`；
  2. `集中度`：前 3 对手金额 ÷ 本方向合计，分方向各算；
  3. `单笔最大前 10`：取 `case_event` 的资金交易事件（CNY、未排除、经基 1 涉及该账户），带出处代表。
- `方向` / `对手` 为过滤参数：`对手` 先 `解析实体`，再按代表过滤。
- **口径声明**：「单笔最大」取事件而非明细行——要「单笔 + 出处」，事件天然两者都有；代价是「只有笔录人工关系、没有对应流水事件」的笔不进这个榜。该缺口写进 `缺口`，不静默。
- 查询次数：同 `explore_entity`，实测钉住。

## 7. 零碎口径

1. **参与者摘要共享函数**：`query_events` 与 `query_timeline` 的「参与者摘要」收成同一函数，已排除实体值一律剔除。`#002-06`：两处各写一遍迟早漂。
2. **entity 类裁决触发重算 —— 本期不落地（2026-11-13 实现前裁定）**：`重建关系` 的输入只有「未被排除的人工转账关系」与「未被排除的资金交易事件」；entity 的确认 / 排除 / 修正 / 撤销都不改这两类输入（`case-trust.ts` 的 entity 白名单只有 `canonicalValue` / `entityType`；改名后旧值进别名，由基 1 的 text[] 回退命中）。因此重算**没有任何可观测行为**，写不出会红的用例；按「找不到根因/红不了就不动代码」暂不做，等「实体排除 / 改类型影响事件聚合」出现消费者时再补。缺口登记在 `STATUS.md`。
3. **A6 疑似换主（2026-11-13 落地）**：判定挂在身份标注的同一出口（`case-identity.ts`），
   不新增档。`读身份标注` 的实名登记查询多取 `first_at` / `last_at`；同一实体上有两个不同的人
   的未排除 `实名登记` 边，两人时间窗（同一人多条边先取并集）互不重叠、间隔 > 90 天常量
   （`五个待定问题的调研结论.md:194`）⇒ 说明追加「疑似换主：甲 起~止 → 乙 起~止，相隔 N 天，
   不能认定当前归属」，`身份标注.提示` 带短句、`身份后缀` 把它带进摘要。任一方缺时间窗、
   重叠或相接、间隔 ≤ 90 天 ⇒ 不提示（fail-closed）。号码与账户同构覆盖；不自动合并本来就
   成立（`合并实体` 只有手动端点）。
