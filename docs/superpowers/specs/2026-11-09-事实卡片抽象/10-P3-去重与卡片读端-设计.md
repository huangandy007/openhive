## 1. 问题与证据

### 1.1 跨来源重复计数（6 条既有红）

同一笔转账被两条关系各记一次：

| 来源 | 写入点 | 粒度 |
|---|---|---|
| `source_kind='human'` | `case-ingest.ts` 笔录抽取（`:815-820`） | 每条原文一句 = 一笔 |
| `source_kind='data'` | `case-translate-store.ts` 的 `重建关系`（`321-409`） | 每对（付款方→收款方）= 一条聚合 |

`aggregate_money` 的 `count(*)` / `sum(amount)` 不分来源，实测 A 全窗：

```
出 6 笔 / 360000.00（应为 3 笔 / 180000.00）
入 3 笔 / 56000.00（应为 2 笔 / 28000.00）
```

`09` §4.3 的旧假设「关系只有笔录一条写入路径」已被 P2 的 `重建关系` 推翻。

### 1.2 端点未对齐

笔录关系写的是**人**，流水聚合写的是**账户**：

```
human:   账号A → 李四（人）     李四（人） → 账号A
data:    A → 账户B              B → A
```

所以「同一对」在两边对不上；`对手方` 也会把「李四」与「账户B」列成两个人。对齐证据是 P2 写入的 `kind='户名'` 别名（`case_entity_alias`，迁移 `0039`）。

### 1.3 表格卡片对「按实体查」隐形

`query_events` / `find_crossings` 只查 `case_event.participants text[]`（`case-mcp-tools.ts:893`、`:1557`）；表格来源的卡片参与者只在 `case_event_participant` 表里（`重建关系` 同样 join 该表，`case-translate-store.ts:370-373`）。按实体查事件查不到它们。

## 3. 语义定义

### 3.1 端点对齐（`case-party.ts`，新增）

对任意实体 id 求「同一方代表」：

1. 类型是「账户」⇒ 代表就是它自己。
2. 类型是「人」/「组织」⇒ 查 `case_entity_alias`：`kind='户名'`、`revoked_at is null`、别名所属实体未被排除、且别名值 = 该实体规范值。
   - **唯一**候选账户 ⇒ 代表 = 该账户。
   - 0 个或 ≥2 个候选 ⇒ 代表 = 它自己（**不对齐**），候选数进 `缺口`。
3. 其他类型 ⇒ 代表 = 它自己。

**显示值**：分组用代表实体；显示优先「用户名」（唯一户名的人名），无户名才显示账户规范值 —— 这样 `对手方.0.对手方 = "李四"` 的金标准不变，同时人和账户B 只出现一行。

**证据前提共享**（`#002-06`）：与 P2.5 `读身份标注` 同一条前提（未撤销户名、未排除实体），抽成共享查询，不允许两处各写。

### 3.2 「同一笔转账」的判定（仅写端使用）

匹配键 = （对齐后的 `from` 代表, 对齐后的 `to` 代表）+ 币种 `CNY` + 金额 + **UTC+8 日历日**。

- **一一匹配**：同一键下，human 关系与流水事件各自按 `(时间, id)` 排序，`row_number()` 相同者视为同一笔；只排除「前 N 个」事件（N = 该键下 human 条数）。多出的 human 不覆盖任何事件（保留）；多出的事件正常进机器聚合。
- 下列情况**不匹配**（fail-closed，宁可多算也不吞）：
  - human 关系缺 `first_at`，或事件缺 `occurred_at`；
  - human 关系 `trust_state = '已排除'`（被排除的事实不覆盖数据）。
- **已知缺口**：human 关系无币种字段（`09` §12 已登记「笔录口述的外币转账仍按人民币」）。本期把 human 一律视为 CNY 参与匹配；若笔录口述的是外币而同额同日恰有 CNY 事件，会误判为同一笔 —— 该缺口本期不修，登记在案。
- 匹配结果计数（human 未被覆盖数 / 事件未被覆盖数）进 `缺口`，不静默。

## 4. 数据变更：迁移 `0040_case_relation_times_cny.sql`

```sql
alter table auth.case_relation add column if not exists times_cny integer;
```

- 可空：human 行写 null（读侧回退到 `times`，因为笔录无币种、按 CNY 计）。
- `重建关系` 写入 `times_cny` = 该对 CNY 事件数；`times` 语义不变（全币种，Q16）。
- 老机器行不 backfill：下一次重放会整对重建（`重建关系` 是删后重聚合）；未重放的老数据读侧回退 `times`，与今日行为一致。
- 附 `down.sql`（`drop column if exists`）。按 `migrations/README.md`：不用 `CONCURRENTLY`，语句间写 `--> statement-breakpoint`。

**汇总/对手方的笔数** = `coalesce(times_cny, times, 1)`；该值为 0 的关系（纯外币）**不进汇总与对手方**，仍出现在 `query_relations`（事实列表不隐藏）并由 `缺口` 交代外币行数。

## 5. 写端：`重建关系` 的去重与保护

在 `case-translate-store.ts` 的 `重建关系` 中，每个 chunk 增加三步（前两步各一条 SQL）：

1. **取候选**：该 chunk 的 human 转账关系（`source_kind='human'`、`trust_state <> '已排除'`、`type='转账'`）与 `资金交易` 事件（CNY、带参与者的付款方/收款方）。
2. **对齐 + 一一匹配**：按 §3 计算「被覆盖事件 id 集合」。
3. **聚合排除**：聚合 SQL 加 `and e.id <> all(被覆盖事件)`；`times_cny` 用 `count(*) filter (where e.currency = 'CNY')` 写入。

**保护规则修正（重要，语义变更）**：

- 保留：机器行只删自己那条确定性 id（`事实id(projectId,"转账",from,to)`）且 `trust_state in ('自动抽取','存疑')`；已确认/已修正的机器行绝不覆盖。
- **删除**：原「该对存在任何人工结论行 ⇒ 整对不写机器行」的粗粒度保护（`case-translate-store.ts:331-341`、`:386`）。去重后 human 与机器行覆盖**互不相交**的转账，可以并存；旧规则会把「笔录没说、流水有」的转账整对静默丢掉（`#013-04` 同型：保护父行不能连孩子一起覆盖）。

## 6. 读端

### 6.1 `aggregate_money`

- `汇总.笔数`：`sum(coalesce(times_cny, times, 1))`；`汇总.合计`：`sum(amount)`（不变，只 CNY）。
- `对手方`：分组键改为**对齐后的对方代表**，显示值按 §3.1；排除 `coalesce(times_cny, times, 1) = 0` 的行。实现可以 join 别名在 SQL 里换键，也可以取回后按代表重聚合 —— **无论哪种，分组键必须是代表实体**，不能一处按规范值、一处按代表（`#002-06`）。
- `缺口` 增一条（仅当存在纯外币关系）：`N 条转账关系金额为 0.00 且笔数含外币（外币金额不进合计）`。
- `query_relations` **不改**：它按事实列事实，human 与机器行都该看得见；`缺口` 说明「同一笔转账可能有人工与流水两条，汇总已去重」。

### 6.2 参与者条件共享

新增 `事件参与者条件(实体)`（`case-mcp-tools.ts` 内或相邻模块）：

```sql
exists (select 1 from unnest(participants) as 参与者 where 参与者 = ${规范值})
or exists (select 1 from auth.case_event_participant p
            where p.project_id = ${projectId} and p.event_id = case_event.id
              and p.entity_id = ${对齐代表})
```

人/组织的对齐代表 = 唯一未撤销户名账户；0 或 ≥2 候选回落到实体自己（fail-closed）。

`query_events`、`find_crossings`、`query_timeline` 共用（`#002-06`）。已排除实体的值剔除逻辑保持原样。

### 6.3 `query_timeline`（新工具）

契约照抄 `09` §4.3：

| 项 | 内容 |
|---|---|
| 入参 | `实体?` 或 `地点?`（二选一）、`起?`、`止?`、`类型?`、`游标?`、`限制?` |
| `数据` | 事件按 `(occurred_at, id)` 升序：时间与精度、类型、参与者摘要、信任态、代表出处；`缺时间条数` |
| `空原因` | `无事件` / `对象未登记` / `时间全部缺失` / `能力未就绪`（地点分支） |
| 分页 | 游标分页（复用 `case-row-query.ts` 的签发/校验形状，不造第二套） |
| 下一步 | `get_citation`（抽验）/ `query_rows`（该事件明细） |

- 参与者摘要：批量读 `case_event_participant` + 回退 `text[]`，**与事件查询分开**（1 次批量）。
- 代表出处：`引用们`（`case-fact-read.ts:251`）批量取，**1 次**。
- **查询次数上限 5**（A8）：事件 1 + 参与者 1 + 出处 1 + 身份标注（有实体时）1 + 兜底 1。
- 注册：`case-mcp-server.ts` 的 `工具名` 与分发 + `instructions` 一句（工具卡按 `openhive-case_` 前缀兜底，无需另改）。

## 9. 风险与回滚

| 风险 | 影响 | 对策 |
|---|---|---|
| 匹配误判（同日同额多笔） | 少算 / 多算 | 一一匹配按排序配对，只排除与 human 条数相同数量的事件；未覆盖数进缺口 |
| 人名歧义（多个账户同户名） | 错误合并对手 | fail-closed：0 或多候选不对齐，候选数进缺口 |
| `重建关系` 性能 | 重放变慢 | 每个 chunk 只多 2 条查询；500 对/批不变 |
| 迁移 0040 与上游冲突 | 同步成本 | 新迁移文件、不改既有文件；`IF NOT EXISTS` |
| 老数据未重放 | `times_cny` 为空、按 `times` 回退 | 与今日行为一致；不 backfill，重放即重建 |

回滚：迁移有 `down.sql`；代码回滚到本期前提交即可恢复旧行为（旧行为本身是 6 条红单）。
