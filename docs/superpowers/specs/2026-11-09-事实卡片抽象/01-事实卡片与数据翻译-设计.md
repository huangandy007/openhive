## 0. 一页摘要

### 0.0 第 0 条判据：数据的最终消费者是 AI

> **一切数据的最终消费者是 AI；界面只负责两件事——让数据变正确，让人能复核 AI。**

这条不是偏好，是排序依据：任何取舍都用「**AI 能不能答对**」判，而不是用「页面能不能看到」判。

**三条推论**

| # | 推论 | 对设计的约束 |
|---|---|---|
| 1 | **「能取到」与「会取到」是两件事** | 数据层保证「能取到」（解析正确、落盘完整、索引对）；工具层保证「会取到」（MCP 工具的描述、参数、条数、分页、空结果语义）。只做前者，AI 照样答错 |
| 2 | **界面分三类，按「离 AI 多远」排投入** | ① **读数据的展示型**（实体清单、现有邻域图、档案页）ROI 最低，可冻结；② **改数据的操作型**（确认列、定名、修正实体、撤销）是**数据正确性的输入端**，不能砍；③ **产出型**（2026-11-11 补：关系图产物，见 `08`）——它是**给人讲述用的成品**，既不服务于「让 AI 答对」，也不服务于「把数据改对」，按产品价值单独排期，**不受本条判据约束** |
| 3 | **不需要人知道数量，但系统必须自知** | 实体数/关系数不进界面，但必须进自检：查询返回 0 条时，系统要能分清「确实没有 / 没关联账户 / 账户未出现 / 材料未翻译」四种（§3.8.5） |

**由它推出的取舍**

| | 结论 |
|---|---|
| 冻结 | **现有邻域图视图**（`graph.tsx`）、实体清单、实体档案页——只保证不崩，不再投入。⚠️ **不含** `08` 的关系图产物：那是新建的独立文件与视图，与邻域图并存（`08:55`），不属「冻结」范围 |
| 加强 | 解析正确率（认列 / 单位 / 方向 / 时间）、翻译层（明细 → 卡片）、MCP 工具的空结果语义 |
| 出处 | 不是元数据，是**让人复核 AI 的唯一手段**，因此必须由代码绑定、模型碰不到（§2.3） |

> **前提**：用户主要用自然语言提问，而不是点开档案页逐条翻。若实战中民警大量依赖浏览，这条判据要重新裁定——它约束的是投入排序，不是功能取舍的永久结论。

### 0.1 建成什么

```
原件 ──► 预处理（skill，两道闸）──► 标准副本 ──► 识别层 ──► 翻译层 ──► 卡片（事件）──► 实体 ──► 查询层 ──► 页面 / AI
                                                    │           │
                                                    └─── 学习层（别名 / 格式 / 数据源档案 / 卡片模板）───┘
```

- **预处理层**（skill，内核之外）：原件 → 标准格式副本。相对角色（付款方/收款方 → 本方/对方/方向）在这里翻成绝对角色；入库只做搬运，不再判断语义（§2.4，见 `04`）。
- **明细层**（`case_fact_row`）：原文照抄；**不按业务类型加列，也不给备注加列**。备注原文留在 `extras`（键=原表头），只作为翻译层输入与人工回显；用途/商户在用途二期（P4）落成卡片字段（§3.11）。
- **卡片层**（`case_event` + 参与者）：统一回答「谁 / 何时 / 何地 / 干了什么 / 和谁 / 多少」。
- **实体层**（`case_entity` + 别名 + 关系）：把人、号码、账户、地点串起来。
- **学习层**：确认一次，以后自动认。
- **查询层**：页面与 AI 共用同一套取数函数；**AI 是主要消费者，页面负责操作与复核**（§0.0）。

### 0.2 五条设计要求怎么落

| 你的要求 | 本文落点 |
|---|---|
| ① 每类数据一份翻译规则，**如何判定规则是对的** | §2.4（预处理层：相对角色在入库前解决，见 `03` / `04`）+ §4.0（一份材料怎么翻译）+ §4.1（映射与算法拆开）+ §4.3（**四级判据 + 静默零容忍 + 金标准集 + 上线门禁**）+ §4.5（首批规则清单） |
| ② 查询速度优化 | §7（实测基线、索引清单、查询规范、防 N+1、分桶）+ §7.9（**解析速度**与写入铁律）+ §7.10（备注/属性检索成本） |
| ③ 降低操作难度、能自动化就自动化、按钮优先 | §5（自动化阶梯 L0–L3 + 按钮化交互清单） |
| ④ 系统记住东西、越用越聪明 | §6（**四类记忆**：别名 / 格式 / 数据源档案 / 卡片模板 + 学习闭环 + 四道防错闸）+ §4.7（不用开发就能加类型） |
| ⑤ 能复用就复用 | §8（复用清单，逐项给现有文件/表） |

### 0.3 不做什么（沿用理论依据）

不做半径/周边（R7-7）、不自动跨源合并（R4-4）、不做因果推断（§1.2）、不新建卡片表（§8.4）、不让模型给出处（R3-2）。

### 0.4 两条硬约束（容易被后来的开发无意破坏）

| 约束 | 内容 | 落点 |
|---|---|---|
| **明文** | 账号/证件号/手机号/姓名/金额**全程明文**，不脱敏、不掩码、不打码 | §10.1 |
| **不逐行往返** | 一份材料一个事务，每 500 行一批；任何写入路径都不许逐行 insert | §7.9.1 |

这两条都不是"优化建议"，破坏其中任何一条，产出的东西就不可用。

## 1. 目标与非目标

### 1.1 目标（可验收）

| 编号 | 目标 | 验收方式 |
|---|---|---|
| G1 | 表格材料能产出卡片，且每张卡片能翻回「文件·表·行」 | 抽 50 张卡片，全部能定位到原文单元格 |
| G2 | 资金类数据端到端可用：上传 → 卡片 → 实体 → 页面/AI 可查 | 真实 20 份银行流水，问「某账户给谁转了多少」得到正确汇总 |
| G3 | 认过一次的格式，第二次全自动 | 同一格式再上传，零人工确认 |
| G4 | 认不出的东西**看得见**，不静默 | 未知列、待确认项、跳过行数全部上报 |
| G5 | 关键查询在百万级卡片下仍是交互速度 | §7.8 指标 |

> **G2 的边界（必须一起验收）**：银行流水只有「对方户名」没有身份证，所以 G2 的准确措辞是
> 「**户名为 X 的账户**跟谁有资金往来」。要答「X 这个人」，必须靠外部证据把账户焊到人（§3.8.2 M3）。
> 焊不上时，结果标「户名匹配，未核实身份」，**不得当成已核实的人作答**。

### 1.2 非目标

- 不做「案发周边 N 公里」（已拍板）。
- 不做跨源事件自动合并（只出候选）。
- 不做因果推理。
- 不做跨项目共享记忆（列为开放问题 Q3，本轮按项目隔离）。
- 不重写实体表、关系表、现有图谱视图（`graph.tsx`）、实体档案页。`08` 的关系图产物是**新增**的文件与视图，三类既有资产都不动。

## 2. 总体架构

### 2.1 五层职责（预处理层 + 四个内核层）

| 层 | 职责 | 现有落点 | 本轮动作 |
|---|---|---|---|
| **预处理层** | 原件 → 标准格式副本：准入两道闸、相对角色翻译、列名/列序/口径固定 | **不在内核**：skill 资产七态流水线；原型在 `tmp/skill-微信账户流水预处理/` | **新增**首个 skill（§2.4，见 `04` / `03`） |
| 识别层 | 认表头、认表类型、认单位与形状（副本的标准列也要认） | `case-recognize.ts`、`case-field-registry.ts`、`case-header-ai.ts`、`case-field-alias.ts` | **复用**，补「数据源档案」快路径；**逐列核对标准列名是否在字段词表内**（§2.4、§13 Q9） |
| 翻译层 | 把一行翻译成一张卡片（相对角色已在预处理完成，这里只做实体归并与落库） | **不存在**（文字材料走 `跑文本`） | **新增** `case-translate.ts` + 资金规则模块；其余类型走模板（§4.7） |
| 卡片/实体层 | 存事件、参与者、实体、关系 | `case_event`、`case_entity`、`case_relation` | **`case_event` 加 3 列、`case_entity.attrs` 改合并语义** + **新建 3 表**（模板表见 §3.9、数据源档案表见 §6.2）；`case_fact_row` 不加列 |
| 查询层 | 页面和 AI 的取数 | `case-fact-read.ts`、`case-entity-list.ts`、`case-mcp-tools.ts` | **复用**，补地点/时间线查询 |

### 2.2 数据流（以一份微信流水为例）

```
⓪ 预处理（本轮新增，见 `04` / `03`）
   ├ skill 读原件（项目材料目录）；原件不动、永久保留
   ├ 两道闸：表头闸（必需列齐全）+ 值验证闸（方向一致性、金额/时间可解析、卡行成对…）
   │   任一不过 ⇒ 整份拒收，只产出 `-拒收报告.xlsx`，不产出标准副本
   ├ 相对角色 → 绝对角色：借贷标志决定本方方；「支付帐号 + 名下卡 + 开户行」按方绑定
   └ 产出：标准副本（原始列原样 / 标准列 / 判定依据 / 行号 四组并存）+ 转换说明（含原件 SHA-256）

⓪′ 人工复核 → 右键副本文件夹「解析该文件夹下的文件」
   └ 逐个文件建 case_material、入队 case_ingest_job（幂等：同一指纹不产生第二条材料）

① 识别（已有）
   ├ 副本的标准列名若命中字段目录 → L0 / 词典直接认；原件列仍在，可交叉核对
   ├ 未命中 → 别名层 → 词典 → 特征 → 模型（L1/L2）
   └ 产出：列映射 + 待确认项 + 类型（资金）+ 模板建议（§4.7.4）

② 明细落库（已有）
   └ 每行 → case_fact_row（原文照抄，未知列进 extras；备注也在 extras）

③ 出处绑定（本轮新增，最重要）
   └ 每行 → case_citation(fact_type='row', fact_id='<材料>#<表>#<行>')
      ⚠️ 这张表早已支持 row，但至今无人写（`case-mcp-tools.ts:440` 自述）

④ 翻译成卡片（本轮新增）
   ├ 规则：时间/金额/对方账号/对方户名/本方账号/方向
   │        （**直接取副本的标准列，不重做逐行角色判断**）
   ├ 实体：账号 → 账户实体（一等公民）；户名 → 账户上的一条别名
   │        （`case_entity_alias kind='户名'`，**不是边、也不是人实体**）；
   │        人靠外部证据焊上来（§3.8.2 M3）
   ├ 实体属性：`属性:<归属>:<键>` 列 → 对应实体 `attrs`（§3.10，见 `05`）
   ├ 卡片：case_event + case_event_participant
   └ 每个卡片槽保留原文提及；对不上实体就留空 entity_id + 保留原文

⑤ 查询
   ├ 页面：时间线 / 资金视图 / 实体档案
   └ AI：同一套函数（query_events / query_rows / aggregate_money / find_crossings）
```

### 2.3 一条铁律

> **卡片槽里的每个值，要么能指到「文件·表·行」，要么明确标「推断」。**
> 不满足就不生成这张卡片（宁可少一张，不要一张无法自证的卡）。

**这条铁律同样约束实体属性与备注**：属性值必须在值里内嵌 `出处`（`材料#工作表#行号`），不满足就不写进 `attrs`（§3.10，`05` §5.1）；备注是原文照抄，本身即证据。用途/商户这类**推断值**属二期，届时必须随值带「判断依据」，不能当原文（`06` §6.2）。

### 2.4 预处理层与内核的边界（04 议定）

| | 预处理（skill） | 内核（opencode） |
|---|---|---|
| **做** | 准入判定、相对角色翻译、格式固定（列名/列序/取值口径） | 识别、明细落库、出处绑定、翻译成卡片与实体、查询 |
| **不做** | 实体消解、关系抽取、事件合并、跨文件归并 | 不重做逐行角色判断；不「猜着转」 |
| **产物** | 标准格式副本 + 转换说明（原件指纹、逐项闸结果、未转换行） | `case_fact_row` / `case_event` / `case_entity` / `case_citation` |
| **拒绝** | 任一闸不过 ⇒ 整份拒收，只出拒收报告 | 收到拒收结论 ⇒ 不入库（执行方式待定，§13 Q12） |

为什么把角色翻译放在预处理：识别层只有「列」没有「行」，而「对方账号」这个答案不在任何一列里，在两列的比较结果里（`04` §一(二)）。所以翻译层对副本只需「认标准列名 + 归并实体」，不再逐行推理。

**副本的列公约（沿用 `03` §9 与 `05` §4）**

1. 原始列一个字不改；标准列是结论，可以重算。
2. 标准列里不留 `-`（源文件的 `-` 只留在原始列），否则下游会把 `-` 当卡号建实体。
3. 属性列必须命名成 `属性:<归属>:<键>`——**裸的 `对方银行卡号` / `本方银行卡号` 会被现有合成候选认成 `counterparty` / `ownerAccount`**（`case-mapping.ts:139-166`），不是无害的。
4. `收付方向` 目前不在字段目录的 `direction` 同义词里（`case-field-registry.ts:141-146`）；副本若只靠这一列表达方向，会落进 extras——见 §13 Q9。`判定规则`、`户名依据`、`告警`、`对方来源列`、`主体类型` 等「判定依据」列同理，保留在 `extras`、由翻译层显式读取，不影响九格。

### 3.2 新增 `auth.case_entity_alias`（带有效期的别名）

现有 `case_entity.aliases text[]` 只有字符串，**无法表达「这个号 2019–2022 是张三」**（R6-2）。

```sql
CREATE TABLE auth.case_entity_alias (
  id          text    NOT NULL,
  project_id  text    NOT NULL,
  entity_id   text    NOT NULL,
  kind        text    NOT NULL,          -- 姓名/户名/证件号/手机号/账号/车牌/地址/名称/其他
  value       text    NOT NULL,          -- 归一化后的值（比较用）
  raw_value   text    NOT NULL,          -- 原文（显示与回溯用）
  valid_from  integer,                   -- 生效起点（Unix 秒），未知为 NULL
  valid_to    integer,                   -- 生效终点（Unix 秒），未知为 NULL
  source_kind text    NOT NULL,          -- 表格/文本/人工
  material_id text,
  citation_id text,
  created_at  integer NOT NULL,
  revoked_at  integer,
  PRIMARY KEY (project_id, id)
);
CREATE INDEX case_entity_alias_lookup ON auth.case_entity_alias (project_id, kind, value);
CREATE INDEX case_entity_alias_entity ON auth.case_entity_alias (project_id, entity_id);
```

**关键约定**

- **不建 `(kind, value)` 唯一约束**：同一个号码在不同时间属于不同人是合法状态（二次放号）。
- 合并判定时**必须比较时间区间**：区间重叠才可能同一人；不重叠不合并（R6-2）。
- 现有 `aliases text[]` 保留为「未结构化的别名」，新代码只读新表；迁移时把旧值写成 `kind='其他'`、时间未知。
- `kind='户名'` 挂在**账户实体**上，表示「这个账户登记在谁名下」。它不是人名实体、也不是关系边：人只有在被外部证据焊上后才成为独立实体（§3.8.2 M3），那时才写 `账户 --实名登记--> 人`。

### 3.3 新增 `auth.case_event_participant`（论元 + 角色）

现有 `participants text[]` 存规范值：无实体 id、无角色、合并实体后不更新（见 `过程文档/讨论记录.md` §3.7）。

```sql
CREATE TABLE auth.case_event_participant (
  id           text    NOT NULL,
  project_id   text    NOT NULL,
  event_id     text    NOT NULL,
  entity_id    text,                     -- 对不上档案时为空，但原文必须留
  role         text    NOT NULL,         -- 主体/对方/入住人/同住人/付款方/收款方/主叫/被叫/地点/出发地/到达地/车辆/物品/班次/经办人/其他
  mention_text text    NOT NULL,         -- 该槽在原文里的写法
  citation_id  text,                     -- 指向 case_citation（行级出处）
  ordinal      integer NOT NULL,
  PRIMARY KEY (project_id, id),
  UNIQUE (project_id, event_id, ordinal)
);
CREATE INDEX case_event_participant_entity ON auth.case_event_participant (project_id, entity_id);
```

**角色词表放在代码常量里，不写成数据库 CHECK。**
理由：`case_relation.type` 写成 CHECK 后，加一种业务关系就要改迁移（`0031:116` 的教训）。角色是业务属性、会增长；时间关系是稳定集合、可以用 CHECK（见 3.4）。

**角色词表同时是模板界面「角色」下拉的唯一来源**（§4.7.3）：用户只能在词表里选，不能自造角色；需要新角色时改代码常量（与实体类型同一条纪律）。

**`ordinal = 0` 固定为「主体」。** 九格里的「谁」和「和谁」在表里是同构的两行，靠这一条约定区分：
- 时间线/卡片上显示为「谁」的，取 `ordinal = 0` 那一行；
- 其余为其他参与方；
- 「某实体的全部事件」查询不过滤 ordinal，按 `entity_id` 即可。

### 3.4 新增 `auth.case_event_relation`（事件间时序）

```sql
CREATE TABLE auth.case_event_relation (
  id         text    NOT NULL,
  project_id text    NOT NULL,
  from_event text    NOT NULL,
  to_event   text    NOT NULL,
  type       text    NOT NULL,
  basis      text    NOT NULL,           -- 计算/人工
  created_at integer NOT NULL,
  PRIMARY KEY (project_id, id),
  UNIQUE (project_id, from_event, to_event, type),   -- 同一条边只存一份；重放时走 upsert
  CONSTRAINT case_event_relation_type CHECK (type IN ('先','同时','同一事件')),
  CONSTRAINT case_event_relation_basis CHECK (basis IN ('计算','人工')),
  CONSTRAINT case_event_relation_not_self CHECK (from_event <> to_event)
);
CREATE INDEX case_event_relation_to ON auth.case_event_relation (project_id, to_event);  -- 反向遍历（"先于它"）
```
> `UNIQUE (project_id, from_event, to_event, type)` 自带 `(project_id, from_event)` 前缀，正向遍历不再另建索引。
> 它只在**两端按固定序写入**的前提下才等于「一条边只存一份」：`同时` 必须 `from_event < to_event`（见上），否则 `(A,B)` 与 `(B,A)` 都能落库。约束本身不会替你排序。
> 写成约束而不是靠写入方自觉，理由同 `0033` 的 `case_fact_change_explain_deny`：别指望每个调用点都记得。

**只存三种，不存「后」**：`后` 是 `先` 的反向读；`同时` 对称，写入时按 `from_event < to_event` 的固定序存一行。**同一事实只存一份**，避免两行不一致。

### 3.5 扩展 `auth.case_event`

现有列（`0031:154-172`）：`id / project_id / type / occurred_at / occurred_raw / precision / time_type / participants / summary / trust_state / created_at`。

```sql
ALTER TABLE auth.case_event ADD COLUMN occurred_end integer;              -- 区间事件结束（住宿）
ALTER TABLE auth.case_event ADD COLUMN amount      numeric(18,2);         -- 金额（六问之一，必须有独立列）
ALTER TABLE auth.case_event ADD COLUMN attrs       jsonb NOT NULL DEFAULT '{}';  -- 类型专属属性（房号、通话时长等）
```

- `occurred_end` 为 NULL ⇒ 点事件或开区间（由 `attrs.时间形态` 区分）。
- `amount` **必须是独立列，不能塞进 `attrs`**：它是六问之一，`aggregate_money` 与「只查大额」都要按它过滤/排序，JSONB 里查既慢又没类型。
- `attrs` 只放**不参与查询过滤**的属性；凡是需要按它筛选/排序的，必须变成实体引用或独立列（R2-3、§8.7）。
- 由此推出一条二期的硬约束：**「帮我找出所有车辆加油的消费」这类按用途筛选的查询，用途类别不能只进 `attrs`**（§3.11），必须成为独立列或可索引的实体/关系值。
- **用途列不在此处加**：`purpose` + `purpose_basis` 属用途二期（P4），见 §3.11.2；本节只列一期立即加的三列。

#### 九格 ↔ 字段对照（这张表是卡片契约的准绳）

| 九格 | 存在哪 | 状态 |
|---|---|---|
| 干什么 | `case_event.type` + `summary` | 已有 |
| 何时（点到区间） | `occurred_at` / `occurred_raw` / `precision` / `time_type` / **`occurred_end`** | 后一列新增 |
| **谁**（主体） | `case_event_participant` 中 **`ordinal = 0`** 的那一行 | 新建 |
| **和谁**（其他参与方） | 同表其余行 | 新建 |
| **何地** | 同表 `role='地点'` 的行（地点是实体，**不需要单独列**） | 新建 |
| 多少钱 | **`case_event.amount`** | **新增（原缺口）** |
| 其他属性 | `case_event.attrs` | 新增 |
| 出处 | `case_citation`，`fact_type='event'` | 已有表，缺写入 |
| 可信度 | `case_event.trust_state` | 已有 |

两条容易写歪的地方：

1. **「谁 / 和谁 / 何地」在实现上是一张表的三行，不是三列。** 三者结构相同（实体 + 角色 + 原文提及），差别只在 `role`。这也是为什么不能沿用 `participants text[]`——数组装不下角色和原文。
2. **「谁」槽不限定实体类型。** 住宿可以是「张三（人，带身份证）」，资金只能是「账户 6217…（账户，人不明）」。**人缺位是合法状态**（§3.8）。卡片照样成立，只是暂时连不到人。

#### 类型 × 九格：逐类核对

> 前提：**不存在「某类型的数据表」**。所有类型共用同一套（明细 + 卡片 + 参与者），差别只在规则怎么填格。
> 所以问题是「每类数据能不能填满九格」，不是「要不要新建表」。

| 类型 | 干什么 | 何时 | 谁（主体） | 和谁 | 何地 | 多少钱 | 其他 |
|---|---|---|---|---|---|---|---|
| 资金 | 资金交易 | 点 | 账户 | 账户 | — | ✅ `amount` | 余额（`attrs`）；备注原文在 `extras`，用途二期进 `purpose`（§3.11） |
| 话单 | 通话 | 点 | 号码（主叫） | 号码（被叫） | — | — | **时长** |
| 住宿 | 住宿 | **区间** | 人（有身份证） | 人（同住） | 地点（宾馆） | ✅ | 房号 |
| 订餐 | 消费 | 点 | 姓名 / 号码 | 组织（商户） | 地点（地址） | ✅ | 订单号 |
| 火车/飞机 | 乘车/乘机 | **区间** | 人 | 同行人 | **出发地 + 到达地** | ✅ | **车次/航班号** |
| 扫码支付 | 支付 | 点 | 账户 | 账户 / 商户 | — | ✅ | — |

「出处」「可信度」对所有类型相同（`case_citation` + `case_event.trust_state`），表中省略。

**九格对类型不敏感**，这是它作为抽象的价值。但有三类字段会掉进缝里：

**缝 1：会被用来筛选的数值（时长、房号、座位号）**

`attrs` 只放「不参与过滤」的。判据一句话：

> **这个字段会不会出现在「帮我找出……」的句子里？会 → 不能只进 `attrs`。**

- `duration_sec`（通话时长）→ **话单落地时必须加独立列**，不加就查不了「通话超过 60 秒」。现在不加（YAGNI），但要记为「已知待加」，不是忘了。
- 房号、座位号 → 先放 `attrs`，等真实查询出现再加列。

**缝 2：起点和终点是两个地点**

火车/飞机是区间事件，九格只有一个「何地」。参与者表能装两行（`role='出发地'` / `role='到达地'`）——**结构上没问题**，这正是把地点做成实体引用而非列的好处。
代价：地点与时刻的绑定丢失（不知出发地对应起点、到达地对应终点）。目前靠 role 命名隐含，够用；将来若要做「按地点切片时间段」，再考虑加 `at_offset`。

**缝 3：车次/航班号是串并键，不是「其他」**

「同一车次还有谁」是**典型串并场景**。放 `attrs` 就要扫 JSONB，等于查不了。
⇒ **车次建成实体**（`type='物品'`，canonical = `G1234`），卡片里 `role='班次'`。查「同一班次的所有乘客」直接走参与者表索引。

#### 商户归「地点」还是「组织」

判据：**能指认一个物理场所的 → 地点；公司 / 机构 / 品牌 → 组织。**

| 例子 | 归哪 | 理由 |
|---|---|---|
| XX宾馆、XX餐厅、XX超市 | 地点 | 能去，能按地址/空间筛 |
| 腾讯微保、中国移动、XX物流有限公司 | 组织 | 不是一个地点；「中国移动营业厅」才是 |

**为什么较真**：type 决定合并方式——地点按一标三实 + 名称归一（§3.6），组织按名称归一。归错就永远合并不上。

#### 已知的坑：`case_entity.type` 也是 CHECK 写死的

`0031:80-82` 把实体类型写死为 8 种（人/号码/账户/虚拟身份/车辆/物品/地点/组织）。将来要加「班次」「软件/App」就得改迁移——**这与 `case_relation.type` 写死 7 种是同一个坑**。

本轮**不动**（改动面太大）：车次先用 `物品` 承载。但新增任何实体类型前，先想清楚是走迁移还是改成代码侧校验。

#### 九格管不了的部分

九格只回答「这件事是什么」，**不回答「事与事、人与人的网」**：

| 网 | 在哪 |
|---|---|
| 实体 ↔ 实体（转账/通话/实名/同行） | `case_relation` |
| 事件 ↔ 事件（先/同时/同一件） | `case_event_relation`（§3.4） |

核对「表是否符合九格」时，只看事件与参与者两张；关系表不在九格范围内。

### 3.6 地点怎么表示（沿用 D1 拍板：只判「是不是同一个地方」，不做周边）

地点就是一类实体（`case_entity.type='地点'`），不加新表。判同一性靠**两条路径 + 一个兜底**：

```
路径 A（有地址）：比一标三实层级
   省 → 市 → 县/区 → 乡镇街道 → 社区 → 街路巷 → 建筑物 → 单元房屋
   逐级比，一致到哪级就停在哪个粒度；不一致即不同

路径 B（只有名称）：比归一后的名称
   全称/简称/有限公司后缀/空格全半角/括号 → 归一 → 相等才合并
   "XX宾馆" ≡ "XX宾馆有限公司" ⇒ 同一实体（别名表 kind='名称' 存两种写法）

兜底：两条都判不了 ⇒ 不合并，标「待确认」，进候选队列
```

**存储要求**（决定 A 路径能不能跑）：

| 存哪 | 内容 |
|---|---|
| `case_entity.canonical_value` | 显示用名称（原始写法中最完整的一个） |
| `case_entity_alias`（`kind='名称'`） | 每种名称写法一条 |
| `case_entity_alias`（`kind='地址'`） | 每种地址写法一条；层级**全存**（八级都要，不只存到街道） |

**层级必须全存**：只存到「街道」虽然够判同一性，但用户以后想按「同社区」「同街道」筛就查不出来了。全存不多花成本，省下的是将来补数据的返工。

**明确不做**：不算距离、不算半径、不按经纬度聚类（R7-7）。「案发地周边住过」这类查询，本轮的回答是「查不了」，不给出近似结果冒充准确结果。

### 3.7 卡片 ID 与重放

- 卡片 id = `hash(project_id, material_id, sheet, row_no, 规则版本, 模板版本)` 的确定性值（复用现有 `事实id` 思路）。规则或模板任一版本变化 ⇒ id 变化 ⇒ 旧卡片按下面的重放规则替换。
- 重放同一材料：**先删本材料的机器事实**（`删除本材料的事实`），保留人工确认过的（已有机制）。
- **不新增删除语义**，复用现有事务边界。

### 3.8 账户是一等公民：户名 ≠ 人怎么解

**问题**：银行流水只有「对方户名」，没有身份证号。按姓名匹配，「张三」可能对上 30 个人；不匹配，则整条链路断在「户名」这一层，AI 只能答「户名为张三的账户」，答不出「张三」。

#### 3.8.1 核心判断：锚点是账户，不是人

| | 账户 | 姓名 |
|---|---|---|
| 唯一性 | 一个账号只属于一个主体 | 全国几十万个「张三」 |
| 稳定性 | 不变（除转让，可用有效期表达） | 改名、化名、同音字 |
| 可验证 | 银行系统里是实名的 | 无任何约束 |

> **系统里「谁」的第一身份是账户；人通过 `实名登记` 这条边挂到账户上。**
> 先把账户认准，人后到；不是先找人再找账户。

这条决定了三处实现：

- 账户实体（`case_entity.type='账户'`）是**一等公民**，必须从第一份流水就建。
- 人名可以晚到。参与者表的 `entity_id` 允许为空，`mention_text` 保留原文（§3.3）。
- 查询按**账户**组织，不按姓名组织。姓名只用于「显示」和「找候选」。

#### 3.8.2 四条焊接机制（按可靠性排序，自动 → 半自动）

| 机制 | 做什么 | 自动？ | 依据 |
|---|---|---|---|
| **M1 账号相同** | 同一账号 = 同一账户实体 | ✅ 全自动 | 账号天然唯一 |
| **M2 账号 + 户名** | 在账户上记一条 `case_entity_alias(kind='户名')`（**不是边、也不是人实体**） | ✅ 全自动 | 银行导出本身如此 |
| **M3 外部证据焊接** | 从别的材料里抽 `(身份证, 账号)` 对，命中即把账户焊到人 | ⚠️ 半自动 | **这是真正解决问题的一条** |
| **M4 案件内唯一性** | 案件里只有 1 个「张三」且流水里该户名只有 1 组账号 ⇒ 出高置信候选（落 `case_ai_proposal`，人点一次采纳） | ⚠️ 要人点一次 | 唯一性推断 |

**M3 的证据从哪来**（这些材料本来就该进系统）：

- **询问/讯问笔录**：「我尾号 6514 的卡」→ `(身份证, 账号)`。复用现有 `跑文本` 抽取框架（关系类型已含 `实名登记`、实体已含账户）；**但「模型能否稳定给出这一对」尚未实测**，不稳就补针对性提示或规则校验（`#004-03`：没验证过的不写成已覆盖）。
- **银行开户资料 / 账户查询回执**：通常带证件号。
- **运营商实名登记**：手机号 ↔ 身份证。
- **案件里已录入的嫌疑人身份证**：办案人自己填的，最可靠。
- **微信 / 支付宝实名信息**。

M3 的价值在于：**它把「名字」变成「人」，靠的是证据，不是猜测。** 一旦命中，写一条 `账户 --实名登记--> 人` 关系 + 人的别名一条，以后全自动（§6）。

#### 3.8.3 明确不做：姓名模糊匹配

不做拼音、不做同音字、不做编辑距离、不做「张三」≈「张 三」。一万七千行里做模糊匹配，等于批量制造假合并，且错得无法自证。重名是常态，不是数据质量问题。

#### 3.8.4 查询侧必须诚实降级（三级）

任何涉及「人」的查询结果，必须落在三档之一，且**在输出里明写**：

| 档 | 含义 | 显示 |
|---|---|---|
| **已核实** | 有强标识链（M1+M2+M3 焊死） | 正常结果 |
| **户名匹配** | 只有 M2/M4，人未核实 | 结果 + 显著标记「户名匹配，未核实身份」 |
| **无匹配** | 对不上任何实体 | 明确说「查不到」，不给近似值冒充 |

#### 3.8.5 「0 笔」必须拆成四种可能（防静默错误）

现在 `aggregate_money` 查的是 `case_relation where type='转账'`，表格数据一条都没写，所以返回 **0 笔**——用户会读成「这两人没关系」，实际是数据没进来。**这是最危险的错误类型：错得像个正确答案。**

返回 0 笔时，必须给出以下之一，每种对应一个可点的引导动作：

| 原因 | 判定方式 | 界面给的下一步 |
|---|---|---|
| 确实没有交易 | 该实体有账户、账户在已翻译材料中出现过 | 正常空结果 |
| 实体没有关联账户 | 该实体无 `实名登记` 边 | 「关联账户」按钮 |
| 账户未在材料中出现 | 账户实体存在但无任何卡片 | 「检查是否漏传材料」 |
| 项目内资金材料未翻译 | 该项目 `case_relation` 转账为 0 条 | 「去解析」 |

### 3.9 新增 `auth.case_card_template`（卡片模板）

承载 §4.7 的「映射」，让用户在前端配置，不必每加一类数据就发版。

```sql
CREATE TABLE auth.case_card_template (
  id         text    NOT NULL,
  project_id text    NOT NULL,
  name       text    NOT NULL,           -- 用户可见名："话单（XX运营商）"
  event_type text    NOT NULL,           -- 产出的卡片 type
  slots      jsonb   NOT NULL,           -- 九格填法，见 §4.7.2
  required   text[]  NOT NULL,           -- 必须填满才产卡片的格
  version    integer NOT NULL DEFAULT 1,
  verified_at integer,                   -- NULL = 未验证，产出的卡片不进 AI 默认查询
  hit_count  integer NOT NULL DEFAULT 0,
  created_at integer NOT NULL,
  PRIMARY KEY (project_id, id)
);
CREATE INDEX case_card_template_type ON auth.case_card_template (project_id, event_type);
```

约定：

- **只存映射，不存算法**。单位/方向/时间/金额的解析一律走代码（§4.7.5）。
- `slots` 里的字段名必须是字段词表中的键；写入前校验，非法键拒绝保存。
- `verified_at IS NULL` 的模板产出的卡片带「未验证」标，AI 默认查询不返回（§4.7.6）。
- 模板变更时 `version + 1`，并使已缓存的翻译结果失效（与 `case_field_alias_version` 同一套做法）。

### 3.10 `case_entity.attrs`：实体属性的标记与入库（见 `05`）

**不建表、不加列。** `case_entity.attrs` 已是 `jsonb NOT NULL DEFAULT '{}'`（`0031_case_fact_layer.sql:76`），读侧 `query_entities` 已原样返回给 AI（`case-mcp-tools.ts:168-184`）；缺的是「谁标出来、怎么写、怎么合并」。

**列名规范（skill 产出）**

```
属性:<归属>:<键>        例：属性:对方:开户行
```

- 归属只有 `对方` / `本方`，决定属性挂到对手实体还是本方实体；
- 键来自受控词表（首批 `开户行` / `银行卡号` / `证件号`），入库端不做同义词匹配；词表放独立小文件，**不混进 `case-field-registry.ts`**；
- 入库端一条正则 `^属性:(对方|本方):(.+)$` 判出属性列：**不参与四层字段召回、不进「未认出」清单与待确认弹窗**；原文仍留在 `extras`。

**为什么必须带前缀**：`case-mapping.ts:139-166` 的合成候选会把「对手修饰 + 账号词尾」认成 `counterparty`、把「本方修饰 + 账号词尾」认成 `ownerAccount`。裸的 `对方银行卡号` / `本方银行卡号` 会被当成账户标识——不仅挂不上属性，还会制造错误实体。

**attrs 形状与合并**

```json
{ "开户行": [{ "值": "招商银行", "出处": "mat_x#Sheet1#12" }] }
```

- 每个键一数组，元素固定 `值` + `出处`（与 `case_citation` 行级 id 同形）；
- 同键同值去重（保留首次出处），同键不同值**并存**；
- 合并必须「读 → 追加 → 写」，**替换掉** `case-fact-store.ts:73` 的 `attrs || excluded.attrs`——键级覆盖会静默丢证据；
- 先有「明细 → 对手/本方实体」这一步，属性才有挂载点；表格链路目前不建实体（`case-ingest.ts:398`），这是 §4.0.6 的前置缺口；
- 卡号与开户行是配对的：同一次观察写入的两者共享同一个 `出处`，读侧按出处配对（`05` §5.3）。

### 3.11 备注：不建列，原文留 `extras`，语义在入库时判定（2026-11-12 修正）

**裁定：`case_fact_row` 不加 `remark` 列。**

#### 3.11.1 原文怎么存

- **原文保底**：备注作为未识别列照旧进 `case_fact_row.extras`（键 = 原表头；预处理标准副本固定列名后为「备注」）。不截断、不掩码、不归一化（明文，§10.1）。
- **预处理只做三件机械事**：原文逐字保留；保住 `##` 分段与 `键：值` 结构；`UTF8#…` 解码（base64 → 中文商户名，失败保留编码原文并告警）。**不判用途、不贴标签**——判据是「预处理只做格式对齐，凡需看内容下结论的都交给入库翻译层」。
- **为什么加列是错的**：① 值本来就在 `extras`，加列只是搬一遍；② 制造「AI 可查原文」的假路径——`ilike` 扫描既慢又不可审计；③ 与「翻译在入库、查询读结论」相反；④ 给「最小化与官方合并冲突」凭空加列、迁移与字段目录改动。

#### 3.11.2 语义在哪判（唯一落点）

```
case-ingest.ts
  读表 → 识别材料 → toFactRows（明细行，备注进 extras）
                              ↓
                         ★ 判定段 ★
                   逐行读 extras["备注"] → 判 purpose / purpose_basis
                              ↓
                 写 case_event.purpose + purpose_basis
```

- **时机**：入库那一刻，一次性全量跑完；不是查询时算，不是用户提问时算。
- **位置**：`server/openhive` 下独立模块（建议 `case-purpose.ts`），由 `case-ingest.ts` 在明细行可用、卡片写入之前调用。**不放 skill**：skill 无库访问、可被随手改、不参与版本审计。
- **前置依赖**：`case_event` 先建起来。表格来源目前不建卡片（只有 AI 抽取那条路写 `case_event`），这是 §4.0.6 的前置缺口，也是 P4 的起点。
- **存储（用途二期，P4）**：`case_event.purpose`（独立列，可索引）+ `purpose_basis`（规则 / 命中词 / 词表版本）+ 参与者角色 + 行级 citation。用途不能只进 `attrs`（§3.5）。
- **人工可改**：改完保留原判断与痕迹（复用属性/事件信任态机制）。

#### 3.11.3 三级判据与优先级

| 层 | 做什么 | 确定性 | 落点 |
|---|---|---|---|
| ① 字段事实 | 读源文件自己声明的列：`交易类型` 5 值、收/支 | 100%（按源） | `direction`；作判定依据，**不进 `purpose`** |
| ② 结构抽取 | 从 `##` 分段**取**值：`子商户名称`、解码后的商户名、号码、车牌 | 高（可核原文） | 参与者、`attrs`、对象 |
| ③ 语义判定 | **判**用途 / 小类 | 推断值，必须带依据 | `purpose` + `purpose_basis` |

纪律：`交易类型` 是粗筛不是结论；推断层必须带依据；判不出落「未识别转账 / 消费其他」，**不硬猜**（与 §4.4 单位闸同一条 fail-closed）。

规则是**有序表**（first-match wins），不是无序遍历词表——实测中错误多数出在「命中多个、顺序排错」：

```
退款 > 红包 > 手续费 > 信用卡还款 > 零钱通(备注主体只有它) > 提现至本人卡
> 账户充值 > 停车 > 车辆过路费 > 车辆加油 > 手机充值 > 生活缴费 > 保险
> 医疗 > 餐饮 > 交通出行 > 住宿 > 娱乐订阅 > 美容休闲 > 教育政务 > 购物
> 扫码(渠道标记) > 转账 > 兜底(未识别转账 / 消费其他)
```

四组必须遵守的判定（实测逼出来的）：

| 现象 | 错法 | 修正 |
|---|---|---|
| 信用卡还款行 `交易类型` 是提现/转账至银行卡 | 判提现 | 信用卡还款排在提现之前 |
| `中石化易捷便利店消费` | 判加油 | 加油排除「便利店 / 超市」 |
| `ETCP-临时停车缴费` 与 `高速通行费` | 互吞 | 停车只认「停车/停车场/P云/ETCP」，过路只认「通行费/ETC/高速」 |
| `微信转账;零钱通…` | 判零钱通划转 | 仅当备注主体只有零钱通才是划转；作后缀只记渠道 |

「扫码付款」是**渠道**不是标签：扫码对象既有商店也有个人（收款户名常是店主本人），一级仍判消费或转账，另记 `渠道=扫码`。

#### 3.11.4 词表、规则与扩充机制

**两级词表**

- **一级（资金性质，12 个，近乎冻结）**：消费 / 转账 / 红包 / 提现至本人卡 / 转至他人银行卡 / 信用卡还款 / 零钱通划转 / 账户充值 / 退款 / 手续费 / 未识别转账 / 未分类
- **二级（只给「消费」生长，15 个）**：购物 / 餐饮 / 医疗 / 保险 / 生活缴费 / 手机充值 / 车辆加油 / 停车 / 车辆过路费 / 交通出行 / 住宿 / 娱乐订阅 / 美容休闲 / 教育政务 / 其他
- **正交信息不占标签位**：`渠道`（扫码 / 微信转账 / 零钱通 / 银行卡 / Apple 账单）、`对象`（商户 / 手机号 / 车牌 / 场所 / 银行卡尾号）。
- **加小类准入**：有稳定查询需求 + 有可判定的词 + 真数据里有量（≈ ≥50 笔或 ≥1%）；达不到进「其他」。类别存**字符串**（不用 PG enum）、词表版本化；一级冻结、二级生长，报表按一级出、明细看二级。

**核心主张：规则是数据，判定引擎才是代码。** 扩充规则 = 改一份规则表 + 升词表版本，**不动判定代码**。这不是洁癖：词条会长到几百条、数据源会从一个变成三个，硬编码进 `if/else` 之后既改不动也验不了。

##### 3.11.4.1 一条规则的字段

每条规则一行，字段固定：

| 字段 | 含义 | 硬约束 |
|---|---|---|
| `id` | 规则标识，形如 `娱乐订阅.视频会员` | 全表唯一，**永不复用** |
| `优先级` | 整数，**小者先判** | 显式数字，取 10 的整数倍留插入空位；**不靠文件内顺序** |
| `适用源` | 微信 / 支付宝 / 银行 / 通用 | 不匹配直接跳过 |
| `前置` | 字段级条件（交易类型、收/付方向、金额符号） | 只取「①层字段事实」，不猜 |
| `字段` | 命中位置：`备注原文` 或预处理产出的结构化段（如 `备注#子商户名称`） | 不可得的字段不得作为条件 |
| `任一` | 命中词 / 短语列表 | 单字与通用字禁入（3.11.4.5） |
| `排除` | 命中后仍可否决的词 | 有误伤风险的词**必填** |
| `输出` | 具体类名（二级叶子，或直接是一级类） | **必须在词表枚举内**，否则落「未分类」并记缺口（`#004-09`：门在副作用之前） |
| `说明` | 这条规则讲什么 | 原样写入 `purpose_basis.规则` |

```json
{
  "词表版本": "v1.3",
  "规则": [
    {
      "id": "娱乐订阅.视频会员",
      "优先级": 40,
      "适用源": ["微信", "通用"],
      "前置": { "交易类型": ["支付账户消费", "商户消费"] },
      "字段": "备注#子商户名称",
      "任一": ["云视听极光", "腾讯视频", "奇异果TV"],
      "排除": ["退款"],
      "输出": "娱乐订阅",
      "说明": "视频会员订阅"
    }
  ]
}
```

`优先级` 为什么写数字而不靠文件顺序：两个人各加一条规则、合并后顺序一变，判定结果就静默改变了；数字让「插在哪两条之间」成为可评审的显式决定。

##### 3.11.4.2 三层归属：谁能加什么

| 层 | 落点 | 谁能改 | 生效范围 |
|---|---|---|---|
| 全局词表 + 优先级骨架 | 内核内置规则文件（随版本发布） | 内核维护者 | 全部项目 |
| 源规则包 | 每源一份（微信 / 支付宝 / 银行…） | 实施编写 + 内核审核 | 该源全部项目 |
| **案件级增量** | `project_id` 隔离的独立存储（形态 P4 定，见 `06` §10） | 办案民警 / 实施 | 仅本项目 |

- 案件级增量只提高**规则**命中优先级，**不豁免回归与复核**——不做绕过校验的后门。
- 类别语义、优先级骨架、落库字段归**内核**；解析写法与源特有词归 **skill**；skill 只产出「建议 + 依据」，翻译层校验类名在枚举内才写库。
- skill **不存**判定规则，预处理**不判**用途（3.11.2、预处理指引 §1.1.1）。

##### 3.11.4.3 扩充流程：六步，每次照走

| 步 | 做什么 | 产出 |
|---|---|---|
| 1 发现 | 从 `purpose='未识别转账'`、二级 `其他`、人工标错里捞候选 | 候选备注清单 |
| 2 聚类 | 按备注**去重分组看频次**，不逐行看 | 「某商户 × 笔数」表 |
| 3 写规则 | 定输出类、命中词、**优先级插在哪两条之间**、排除词 | 一条规则 |
| 4 回归 | 三份真文件 + 金标准集跑一遍，diff 各类计数 | 差异表 |
| 5 升版本 | 词表版本 +1；受影响行可重算 | `purpose_basis.词表` 写新版本 |
| 6 抽样复核 | 从新增命中里抽 30 条人工核 | 准确率记录 |

##### 3.11.4.4 回归的量化门

改一条规则后，只允许出现这几种变化：

| 判定 | 要求 |
|---|---|
| ✅ 目标类上升 | 上升数 = 新命中数 |
| ✅ 未识别 / 其他下降 | 与上升数对称 |
| ❌ **其他类任何变化** | 都是误伤信号，查清才能合入 |
| ❌ 一级 12 类合计 ≠ 行数 | 直接拒收 |

新增命中的抽样准确率 ≥ 90% 才合入；金标准标注集上须 100%（基线见 `06` §6.5）。

##### 3.11.4.5 防「越加越乱」四条纪律

1. **一个词只属一类**——跨类靠优先级 + `排除` 解决，不靠词表顺序。
2. **新词必须比旧词更具体**——`易捷便利店` 不能归「加油」（它是商超），见 3.11.3 修正行。
3. **单字 / 通用字禁入**——`充`、`卡`、`店` 不许当命中词；`充值` ≠ `手机充值`（`06` §2.5 实测踩过）。
4. **改词表先 grep 全部消费方**（`#002-06`）：报表、导出模板、AI 提示词里硬编码的类名清单必须同步，否则一处改、三处对不上。

##### 3.11.4.6 新规则从哪来

离线发现、人工确认、再落成规则；**批量路径全程零模型调用**（3.11.5）：

```
未识别 / 其他 的备注 → 去重聚类（频次表）
        ↓
AI 离线提议「候选类 + 命中词 + 排除词」（只出建议，不写库）
        ↓
人工确认（抽样看原文）
        ↓
写成一条规则 → 走 3.11.4.3 的 4–6 步
```

AI 是**提词员**不是判定者：它的产出必须过人的确认与回归门，才进词表。

#### 3.11.5 版本、回归与 AI 边界

- **幂等可重算**：判定是纯函数（一行 + 词表版本）；改词表能全量重跑，新旧 `purpose_basis` 可对比。
- **版本入库**：`purpose_basis` 带词表/规则版本；不升版本会出现无法解释的统计漂移（`#011-01`）。
- **回归基线**：三份真实微信流水（699 / 16,992 / 14,028 行，合计 31,719）为首版基线，一级 12 类合计必须等于行数。完整基线、推导与准入标尺见 `06` §6.5。
- **AI 不批量打标**：成本、不稳定性、不可审计、规则更准四条理由；AI 只做单笔解释（标「AI 推断」，不写回 `purpose`）与开发期提议新规则（离线、人确认后落成规则）。

#### 3.11.6 查询与验收

- **检索**：按用途走 `case_event.purpose` 索引；按商户走参与者表索引；备注原文只用于回显与人工复核，**不做关键词检索**。
- **`query_rows` 不提供备注关键词参数**（契约见 `09` §4.4）。
- **验收**：见 §11 A20（分类与基线一致、依据可回溯、批量路径零模型调用、预处理产物无用途列）。

## 4. 翻译规则（每类数据一份）

### 4.0 翻译流水线：一份材料怎么变成卡片、实体、关系

整个系统的核心就是一个函数：

```
翻译(一份材料) → { 卡片[], 实体[], 关系[] }
```

其余设计（索引、界面、学习、性能）都是它的外围。

#### 4.0.1 六段

| 段 | 做什么 | 现状 |
|---|---|---|
| ⓪ 预处理（表格来源） | 原件 → 标准副本：准入、相对角色、口径（§2.4） | ❌ 新增（skill，见 `04`） |
| ① 认表 | 表头 → 列映射 | ✅ 已有（四层识别） |
| ② 定行 | 哪些行产卡片 | ❌ 新增（规则定义） |
| ③ 抽槽 | 每行按模板取六个问题槽 + 其他属性 | ❌ 新增（翻译层；槽位来自 §4.7 模板） |
| ④ 归并实体 | 值 → `entity_id` | ❌ 新增（"解析实体"的实质） |
| ⑤ 落库 | 卡片/参与者/关系/出处 | ⚠️ 散在现有函数里，需串起来 |

```ts
翻译一份材料(材料):
  # ① 认表（已有）
  mapping = 识别(表头, 样本)                # {列下标 → 字段}
  # ② 定行（新）
  行们 = [行 for 行 in 表 if 有效行(行, mapping)]
  # ③抽槽 + ④归并（新，一份材料一次扫描）
  实体缓存 = Map()                          # "账户|6222…" → entityId
  for 行 in 行们:
      甲 = 取或建(实体缓存, "账户", 归一(行.ownerAccount))
      乙 = 取或建(实体缓存, "账户", 归一(行.counterparty))
      方向 = 映射方向(行.direction)          # 借→付，贷→收
      卡片.push({
        id: hash(材料, 表, 行号, 规则版本, 模板版本),  # 确定性，重传不重复
        type: "资金交易",
        occurred_at: 解析时间(行.startedAt),
        amount: 解析金额(行.amount),          # 失败 ⇒ 整行跳过并计数
        participants: [
          {entity: 甲, role: 方向=="付" ? "付款方" : "收款方", mention: 原文, ordinal: 0},
          {entity: 乙, role: 方向=="付" ? "收款方" : "付款方", mention: 原文, ordinal: 1},
        ],
        attrs: { 余额 },                      # 卡片属性；备注原文留 extras，用途二期进 purpose
        citation: "<材料>#<表>#<行号>",
      })
  # ⑤ 落库（一个材料一个事务，500 行一批）
  批量写 case_event + case_event_participant
  批量 upsert case_relation（times/amount/first_at/last_at 增量）
  批量写 case_citation(fact_type='event')
  写 case_entity_alias(kind='户名')：账户 → 户名提及
  写 case_entity.attrs：属性:<归属>:<键> 列 → 对应实体（§3.10）
```

#### 4.0.2 一行 → 卡片 + 参与者 + 关系 + 别名（真实列名）

输入一行（列名 | 值）：

| 交易时间 | 交易金额 | 交易余额 | 借贷标志 | 交易对方账卡号 | 交易对方名称 | 查询账号 | 查询户名 |
|---|---|---|---|---|---|---|---|
| 2024-11-09 09:15:03 | 5000.00 | 12,300.00 | 借 | 6222021234567890123 | 李四 | 6217001234567896514 | 张三 |

> 示例用完整账号（§10.1 明文原则）。**源文件自带掩码的号码不能这样处理**——见 §4.0.5 坑 1。

| 产出 | 内容 |
|---|---|
| `case_event` | `type=资金交易`、`occurred_at`、`precision=到秒`、`amount=5000.00`（**永远正数**，本列见 §3.5 新增）、`attrs={余额}`（`purpose` 二期填；一期留空） |
| `case_event_participant` ×2 | 账户 `6217001234567896514` `ordinal=0`、`付款方`（**查询账号＝本方＝主体**）；账户 `6222021234567890123` `ordinal=1`、`收款方`；各自带 `mention_text`（该格的原文） |
| `case_relation` | 账户 `6217001234567896514` --转账--> 账户 `6222021234567890123`，`times+1`、`amount+5000`、`first_at/last_at` |
| `case_entity_alias` | 账户 `6217001234567896514` `kind='户名'` = 张三（来自「查询户名」列）；账户 `6222021234567890123` `kind='户名'` = 李四（来自「交易对方名称」列） |
| `case_fact_row` | 备注原文留在 `extras`（键=原表头），**不建 `remark` 列**（§3.11） |
| `case_entity.attrs` | 该行若带 `属性:对方:开户行` / `属性:对方:银行卡号`，写入对手账户实体，值带出处（§3.10） |

> `kind='户名'` **不是** `'姓名'`：它挂在**账户**上，是一条「这个账户登记在谁名下」的记录，不是一条人名记录。
> 人只有在被外部证据焊上后（§3.8.2 M3）才成为独立实体，并写 `账户 --实名登记--> 人`。

#### 4.0.3 实体不是"抽"出来的，是"归并"出来的

**a) 归一化——只做不丢语义的**

| 类型 | 做 | **绝不做** |
|---|---|---|
| 账号 | 去横线、去空格、全角转半角 | 不模糊、不补位、不截取 |
| 手机号 | 去 `+86`、去空格 | 不判归属地 |
| 户名/名称 | 去首尾空格、全角括号转半角 | 除「有限公司」这类后缀外不改写 |
| 姓名 | 只 trim | **不做拼音、同音字、编辑距离** |

**b) 阻塞键——决定"跟谁比"**

| 类型 | 阻塞键 | 命中后 |
|---|---|---|
| 账户 | 完整账号（归一后） | 直接复用，无需判断 |
| 人 | 身份证号 | 直接复用 |
| 号码 | 手机号 | 直接复用 |
| 组织 / 地点 | 归一后名称 | 复用，但标「名称匹配」 |

**c) 内存 Map——性能与正确性都要**

一份 5,000 行的流水，若逐行查库：上万次 `select`，且同账号可能被并发建出多条。用 Map 后每份材料只查库几百次。**这是硬要求，不是优化。**

#### 4.0.4 卡片是事实，关系是汇总

`case_relation` 现有列正好够用（`0031:105-109`）：`times`（笔数）、`amount`（合计）、`first_at/last_at`（首末）、`source_kind='data'`（数据直记，不需人工依据）。

约定：

- **卡片是唯一事实**，关系是对卡片的聚合；
- 关系必须**可从卡片重建**（按两端实体 `group by` 一次重算），重解析材料时先重建再写，避免算重；
- **哪些卡片能生成实体-实体边，必须由模板/规则显式声明**。例：资金 = 付款方↔收款方，话单 = 主叫↔被叫；住宿三方参与（人 + 同住人 + 宾馆）不声明就不建边——否则「张三—同行—XX宾馆」这种假关系会自己长出来；
- 界面显示汇总读关系表（快），下钻明细读卡片（准）。

#### 4.0.5 五个必须处理的现实坑

| # | 坑 | 规则 |
|---|---|---|
| 1 | **源文件自带掩码**（`6222****1234`） | 含 `*` 或位数不足 ⇒ **不建账户实体**，只留 `mention_text`。否则不同人的同尾号会被合成一个账户，时间线上长出根本不存在的资金链。<br>⚠️ 这不是本系统脱敏（本系统**全程明文**，§10.1），而是源文件导出时就是这样——数据本身不全，不能当强标识 |
| 2 | **方向与符号** | `借`=支出（甲方付款），`贷`=收入。**金额永远存正数**，方向只用角色表达。绝不用负数金额——合计会把收支相抵，看起来像没交易 |
| 3 | **备注 / 摘要 / 用途认不出** | 字段目录（`case-field-registry.ts:65-154`）共 **16 个字段**（10 个落标准列 + 6 个落 extras），**没有「备注/摘要/交易类型/用途」**；`是无信息列`（`case-field-registry.ts:375-378`）还把「备注/摘要/用途」判成无信息列（`#002-06`：两处共用同一份判据）。⇒ 备注原文停在 `extras`（不丢），但**没有任何一层把它读成语义**，AI 问不到「这笔钱干什么用」。<br>注：字段目录不认「备注」是**有意为之**（§3.11），不是这一坑的根因；真正的缺口在翻译层没把用途/商户结构化。<br>**用途二期修法（§3.11）**：用途规则在入库时读 `extras` 里的备注原文，产出 `case_event.purpose`（独立列，可索引）+ 参与者角色 + `purpose_basis`（依据）+ 行级 citation；人工可改。**不加 `remark` 列、不升识别版本、不提供备注关键词查询**（`#011-01` 的教训是「让旧缓存失效」，这里连缓存指纹都不动）。<br>事件类型仍统一成 `资金交易`；用途/商户结构化与「只查转账」是二期 |
| 4 | **跨源重复** | 同一笔交易同时出现在双方导出的流水里 ⇒ **不自动合并**（D2），出候选；判据：同金额 + 同一天 + 对手账号互为对方。候选落 `case_ai_proposal`（用 `kind` 区分，`payload` 存两张卡片 id），**不新建表** |
| 5 | **一个 sheet 多个表** | 有效行判定须排除表头重复行、合计/小计行、空行；跳过行数必须上报（§4.6） |

#### 4.0.6 落地当前缺口

| 缺 | 影响 | 量级 |
|---|---|---|
| 行级/事件级出处写入 | 卡片翻不回原文 | 小（表已就绪） |
| 参与者表 | 角色缺失、合并后断链 | 中（建表 + 改读写） |
| 实体别名表（带类型与有效期） | 户名/账号挂不到账户上 | 中（建表） |
| `query_rows`（**不含**备注关键词） | 明细只能靠人工翻表 | 小 |
| 实体属性写入（`属性:` 列 → `attrs`） | 银行卡/开户行问不到；合并会覆盖 | 中（`05`） |
| **表格 → 实体** | 属性无处可挂、对手账户不存在 | 中（翻译层第一步，`05` §8） |
| 用途/商户结构化（`case_event.purpose` + 参与者角色） | 备注只能人工看；「找加油消费」问不到 | 中（用途二期，P4；§3.11） |
| **翻译层本身** | 一切的核心 | 大 |

### 4.1 一条规则的接口：七个字段，两样东西

```ts
interface 翻译规则 {
  id: string                      // "资金/v1"
  模板: string                    // 指向 case_card_template 的一行（代码规则用内置模板行）
  适用: (表头: string[], 样本: string[][]) => 匹配度   // 复用现有候选字段集
  列: Record<槽, string[]>        // 槽 → 可接受的标准字段（来自字段目录；实际填法来自模板）
  值: {
    时间: { 格式: 时间格式[], 时区: "UTC+8" }
    金额: { 单位映射: Record<string, 倍数>, 默认单位: "元" }
    方向: Record<string, "收" | "付">
    币种: Record<string, string>
  }
  实体: { 槽映射: Record<string, "人"|"账户"|"地点"|"组织">, 去重键: string[] }
  门槛: { 必需槽: string[], 有效行: (行) => boolean }
}
```

**规则不是一坨，拆开看只有两样东西：**

| | 是什么 | 放哪 | 谁能改 |
|---|---|---|---|
| **映射** —— 哪个字段填九格的哪一格 | **数据**（一张表而已） | `case_card_template` | ✅ **用户在前端配**（§4.7） |
| **算法** —— 单位换算 / 方向判定 / 时间解析 / 金额形状 | **逻辑** | 代码 | ❌ 只有开发，且必须有金标准集守着 |

把映射当逻辑锁进代码是设计错误：它让「加一类数据」等于「发一次版」。而算法恰恰相反——**它一旦可配，就是批量静默错误的入口**（`#011-02`）。

**代码规则不是「另一种东西」**：`资金/v1` 同样有一行模板（内置模板，迁移里随规则写入，`verified_at` 已填），只是额外挂了算法。所以「映射进模板表、算法进代码」对两类规则都成立，区别只在**这行模板能不能由用户改**（内置 vs 用户自建）。

### 4.2 执行顺序（复用现有识别顺序）

```
① 数据源档案命中（新增快路径，见 §6.2）
② 格式指纹命中 case_table_format（已有）
③ 别名层（已有）
④ 词典精确 / 词典后缀 / 形状（已有）
⑤ 模型兜底（已有，仅认不出的列）
⑥ 仍认不出 → 进「未知列」，原文进 extras，界面标出来
```

### 4.3 规则怎么判定「对」——本节是核心

**「对」必须分四级判，缺一级就会自欺。**

#### 4.3.1 四级判据

| 级别 | 判什么 | 判据 | 门槛 |
|---|---|---|---|
| **C1 列级** | 每个表头被判成什么 | 与人工标注的金标准逐列比对 | 准确率 ≥ 98%，**误认 0** |
| **C2 值级** | 该类型用到的金额/时间/方向/币种解析出的值（不涉及的项不判） | 与原文语义逐值比对 | **100%**（错一个，整张卡片作废） |
| **C3 行级** | 一行能否生成完整卡片 | 该类型模板里标记为「必需格」的槽全部有值 | 完整率 ≥ 95% |
| **C4 案件级** | 汇总结果 | 笔数、合计、对手方数与人工核算一致 | **完全一致** |

**C1 的「误认 0」是硬红线**：认成错的字段并落地，比认不出更危险。认不出会进待确认、看得见；认错了会静默产生错卡片。

#### 4.3.2 四类错误，容忍度不同

| 错误 | 定义 | 例子 | 容忍 |
|---|---|---|---|
| **漏认** | 该认的没认出来 | 「交易金额（元）」没认成金额 | 有上限，且必须可见（进未知列/待确认） |
| **误认** | 认成错误字段 | 「手续费」被认成「交易金额」 | **0** |
| **错值** | 列对了，值解析错 | 「万元」没换算、借贷方向反了、12 小时制当 24 小时 | **0** |
| **静默** | 错了但既不报错也不进待确认 | 单位冲突被吞掉 | **0** |

> 依据：`#011-02`（单位闸黑名单必漏 ⇒ 默认单位一律 fail-closed）、`#011-03`（面积闸按扫描成本）、`#011-01`（归一化丢语义会让校验被缓存绕过）。

#### 4.3.3 金标准集（golden set）

每类数据建一个**小而硬**的集合：

| 要求 | 规格 |
|---|---|
| 份数 | 3–5 份真实文件，覆盖**不同来源系统**（不同银行/不同运营商） |
| 覆盖 | 表头变体、单位变体（元/万元/分）、借代方向变体、时间格式变体、空值、合计行 |
| 标注内容 | ① 每列语义（含「无信息」）② 20 行的人工卡片 ③ 该文件的汇总答案 |
| 谁标 | 业务方标注 + 开发复核；两人不一致处仲裁并记录 |
| 存放 | `packages/opencode/test/fixtures/translate/<类型>/`，含 `expected.json` |

**金标准本身也要能自证**：每份文件标注「这份为什么算金标准」（来源、覆盖了哪个变体）。

#### 4.3.4 上线门禁

```
新增/修改规则
  → 跑金标准集
  → C1 ≥ 98% 且误认 0
  → C2 = 100%
  → C3 ≥ 95%
  → C4 完全一致
  → 才允许启用（规则版本 +1）
任一不达标 ⇒ 规则不启用，本次改动作废
```

**每次改规则必须重跑同一套金标准集**（回归），不允许「改完只测新文件」。

#### 4.3.5 上线后的运行期验证

- 每类数据每月抽 N 份新文件（N ≥ 3）做人工复核；
- 复核结果回写金标准集（新增变体）；
- 发现误认/静默 ⇒ **回滚规则版本**，旧版本可继续用。

### 4.4 三类高危解析的强制规则

| 项 | 规则 | 依据 |
|---|---|---|
| **单位** | 无默认单位的字段一律 fail-closed：全括号对 + 裸后缀逐 token 判；认不出 ⇒ 整列未知 + 待确认，**不按默认值硬算** | `#011-02` |
| **方向** | 借贷标志必须映射成「收/付」；映射表之外的取值 ⇒ 该行不出卡片，计「跳过行」并上报 | 资金方向反了等于金额符号反了 |
| **时间** | 保留原文 + 精度；时区统一 UTC+8；12 小时制必须带 AM/PM 才解析，否则降级「到日」并把实际精度写进 `precision`（`case_event` 的 CHECK 只认 到日/到分/到秒） | 时间错 = 卡片全错，且从界面上看不出来 |

### 4.5 首批规则清单

| 规则 | 形态 | 状态 | 说明 |
|---|---|---|---|
| `微信账户流水` skill（预处理） | **代码（skill）** | **本轮先做** | 两道闸 + 标准副本，见 `03` / `04`；副本产出后再进 `资金/v1` |
| `资金/v1` | **代码规则** | **本轮必做** | 需要借贷方向映射与单位换算（算法），有 35 份真实文件可建金标准集 |
| 话单 | **模板** | 等真实数据 | 槽位纯映射（主叫/被叫/时间/时长），用户配即可，**不写代码** |
| 订餐 | **模板** | 等真实数据 | 同上（地址/商家/收货人/金额） |
| 住宿 | **代码规则** | 等真实数据 | 入住行 + 退房行合成区间卡片，模板表达不了（§4.7.7） |
| `通用/v1` | 代码规则（兜底） | 可先做 | 认不出类型时：只有时间+主体的行才出卡片，其余留在明细 |

**没有真实数据就不写规则**，避免写出「看起来对、没验证过」的东西（`#004-03`）。
模板化之后这条更好守：等真实数据到了，**用户当场配模板**，不需要开发预先猜。

### 4.6 无效行与跳过行

规则必须定义「哪些行不产卡片」，并**计数上报**：

- 表头重复行、合计行、小计行、空行；
- 关键槽缺失且无法解析的行；
- 单位/方向无法判定的行。

界面上显示「本文件 5,000 行，生成卡片 4,982 张，跳过 18 行（原因：合计行 12、方向不明 6）」。**跳过的必须能点开看是哪几行。**

### 4.7 卡片模板：把「映射」交给用户

#### 4.7.1 要解决的问题

按 §4.1 的旧做法，每加一类数据就要开发写一份规则。资金做完了，话单再写一遍，住宿再写一遍——用户说得对：**这条路会一直慢**。

#### 4.7.2 关键洞察：映射就是「九格的填法」

一类数据的全部特殊之处，无非是「哪个字段填哪一格」。而这本质上是一张表，不是一段程序。

`case_card_template` 的一行：

```json
{
  "name": "话单",
  "event_type": "通话",
  "slots": {
    "谁":     { "字段": "caller",      "角色": "主叫", "实体类型": "号码" },
    "和谁":  [{ "字段": "callee",      "角色": "被叫", "实体类型": "号码" }],
    "何时":   { "字段": "startedAt" },
    "何时止": null,
    "何地":   null,
    "多少钱": null,
    "其他":   { "时长": "durationSec" }
  },
  "required": ["谁", "何时"]
}
```

模板只管**「值从哪一列来」的格**：`谁 / 和谁 / 何时 / 何时止 / 何地 / 多少钱 / 其他`。
「干什么」由 `event_type` 列给，「出处」「可信度」由代码写（§2.3 铁律），**这三样不可配**。

话单、订餐、火车、扫码——**全是同一张模板的不同填法，不需要写新代码**。

#### 4.7.3 前端怎么配（全是下拉和勾选）

```
┌─ 新建卡片模板 ───────────────────────────┐
│  类型名称  [ 通话        ]                │
│                                           │
│  谁（主体）  [ 主叫号码 ▾ ] 角色[ 主叫 ▾ ] │
│  和谁        [ 被叫号码 ▾ ] 角色[ 被叫 ▾ ] │
│  何时        [ 通话时间 ▾ ]                │
│  何时止      [   无     ▾ ]                │
│  何地        [   无     ▾ ]                │
│  多少钱      [   无     ▾ ]                │
│  其他        [ 时长 ▾ ]  [ + 添加 ]        │
│                                           │
│  必须填满才产卡片：                        │
│  ☑ 谁   ☑ 何时   ☐ 和谁                   │
│                                           │
│  [ 预览前 20 行翻译结果 ]                  │
└───────────────────────────────────────────┘
```

下拉选项**只来自三份代码词表**：字段词表（`case-field-registry.ts` 的 16 个字段：10 个落标准列 + 6 个落 extras）、角色词表（§3.3）、实体类型词表（§3.5 那 8 种）。用户不可能填出词表以外的东西——这是「不打字」和「不出错」同时成立的原因。

**属性列不在下拉里**：`属性:<归属>:<键>` 是实体属性（§3.10），不是九格槽，也不是字段词表的一员——它不进模板、不进候选字段集，由入库端单独识别。

#### 4.7.4 系统先猜，用户只点确认

字段识别完成后，按字段组合给模板建议：

| 识别出的字段组合 | 建议模板 | 置信 |
|---|---|---|
| `caller + callee + startedAt + durationSec` | 通话 | 高，直接套用 |
| `counterparty + amount + direction + startedAt` | 资金 | 高（已有规则） |
| `address + merchant + amount + startedAt` | 订餐 | 中，请用户确认 |
| `personName + address + startedAt + amount` | 住宿 | 中，且可能需区间合并 |

猜得出直接套，猜不出才让用户点。**多数情况用户只需点一次「对」。**

#### 4.7.5 永远不许配的四类

| 不许配 | 为什么 |
|---|---|
| 单位换算（元/万元/分） | 配错 = 静默 10000 倍错（`#011-02`） |
| 借贷方向映射 | 配反 = 收支相反 |
| 时间格式解析 | 配错 = 时间全错 |
| 金额形状校验 | 配松 = 把余额当金额 |

用户在模板里**只能选「哪列是什么」**，不能选「怎么算」。这两件事必须分开，否则模板会把 §4.3 的判据全部架空。

#### 4.7.6 两个防错设计

1. **保存前必须预览**：先跑前 20 行，让用户看到翻译出来的卡片长什么样，不对就改。
2. **新模板标「未验证」**：第一份文件产出的卡片打此标；用户确认过一次后转正。未验证模板产出的卡片**不进 AI 的默认查询范围**。

#### 4.7.7 模板表达不了什么

| 表达不了 | 例子 | 怎么办 |
|---|---|---|
| 多行合成一张卡 | 住宿的入住行 + 退房行 | 仍需代码规则 |
| 行间计算 | 冲正抵消、余额校验 | 仍需代码规则 |
| 跨行去重 | 同一笔出现在双方流水里 | 共指问题，不是模板的事 |

最终形态：

```
模板（覆盖 80% 的普通类型）   ← 用户在前端配，零开发
代码规则（覆盖需要计算的特殊类型） ← 开发写，映射也用模板行（内置）
模板优先，规则兜底
```

注意这里的「模板」指**用户可改的模板**；代码规则的内置模板行不能被用户改（§4.1）。

#### 4.7.8 成本对比

| | 旧设计 | 模板化后 |
|---|---|---|
| 加「话单」 | 开发排期：写规则、写测试、发版 | **用户 3 分钟配一个模板** |
| 加「火车」 | 同上 | 用户配（出发地/到达地两个角色） |
| 加「住宿」 | 同上 | 仍需开发（区间合并） |

## 5. 自动化与操作简化

### 5.1 用户只做四件事

1. **把文件放进项目材料目录**（原件永远不动）；
2. **让 skill 做预处理，看一眼副本**（结论 + 依据 + 转换说明；不通过则看拒收报告）；
3. **右键副本文件夹入库**（系统逐个文件建材料、入队）；
4. **看结果，点「对」或「不对」**；只在系统拿不准时点按钮选一个答案（不打字）。

### 5.2 自动化阶梯

| 级别 | 触发条件 | 用户动作 |
|---|---|---|
| **L0 全自动** | 数据源档案命中，或格式指纹命中 | **零动作** |
| **L1 自动** | 识别层认出全部关键列，无待确认 | 零动作（只提示「已自动完成」） |
| **L2 半自动** | 有 1–3 个待确认项 | 点按钮选（每个候选一个按钮） |
| **L3 建档** | 全新数据来源 | 一次确认列映射 + 模板 → 系统记为数据源档案 → 以后 L0 |

**目标**：同一来源的文件，第二次起 ≥ 90% 走 L0。

### 5.3 按钮化交互清单

| 场景 | 界面 | 禁止 |
|---|---|---|
| 待确认列 | 每个候选字段一个按钮 + 「保持未知」；「全部按建议」一键 | 要求输入字段名 |
| 单位冲突 | 「元 / 万元 / 分」三选一 + 原文提示 | 默认替用户选 |
| 借方/贷方 | 「收 / 付」二选一，显示样例行 | 让用户查代码 |
| 实体候选（同一人） | 「是同一个人 / 不是 / 不确定」三按钮 | 要求写理由（理由可选） |
| 卡片对不对 | 「✓ 正确 / ✗ 有错」两按钮；✗ 后出现原因三选一（识别错/抽取错/材料本身有问题） | 要求打长文本 |
| 时间缺失 | 「原文没有 / 看不清 / 只知日期」三按钮 | 让用户补时间 |
| 预处理拒收 | 显示哪条闸不过、实测多少；「换一个 skill / 查看原件」 | 只写「格式不支持」 |
| 解析失败 | 「重试」一个按钮；已确认内容不得被冲掉 | 让用户重传文件 |

**文字输入只保留一个例外**：选择「排除/修正」时写一句理由（现有库约束 `case_fact_change_explain_deny` 要求）。理由给**原因选项 + 可选补充**，仍是按钮优先。

### 5.4 默认值与批量

- 有明确建议时，**默认选中建议**，用户只需确认（不是让用户从头选）。
- 待确认项 ≥ 5 条时提供「全部按建议处理」，并在执行前显示将写入什么。
- 所有确认动作支持**撤销**（别名已有 `revoked_at`，界面目前缺入口——本轮补）。

### 5.5 失败与重试

- 解析失败落「有问题」+ 原因，用户点「重试」即可（已有 `applyParseAction`）。
- **重试不得丢失人工结论**：沿用现有「删除本材料的事实只删自动抽取/存疑」的机制。
- 后台作业可离开页面（已有 `case_ingest_job`），进度可见。

### 5.6 什么时候**不**给用户出选择题

界面上不提供「注定失败」的按钮（现有 `material-facts.tsx` 已踩过这个坑：六类待确认原因里只有两类能靠写别名解决）。新增按钮前必须确认：**这个动作真的能成功吗？**

## 6. 学习与记忆

### 6.1 已有的两类记忆（复用）

| 记忆 | 表 | 现状 |
|---|---|---|
| 表头别名 | `case_field_alias` + `_version` | 已有：确认→写库→版本+1→旧缓存不可达 |
| 表格格式 | `case_table_format` | 已有：指纹命中直接套 mapping，`hit_count` 计数 |

### 6.2 新增两类记忆：数据源档案 与 卡片模板

**问题**：格式指纹是「这一份表头 + 数据特征」，同一家银行**不同月份列顺序变了**就不命中。

**方案**：`auth.case_source_profile`（按项目隔离）

```sql
CREATE TABLE auth.case_source_profile (
  id            text NOT NULL,
  project_id    text NOT NULL,
  name          text NOT NULL,        -- "XX银行导出"（用户可改）
  fingerprint   text NOT NULL,        -- 样例指纹
  header_set    jsonb NOT NULL,       -- 表头集合（顺序无关）
  type          text NOT NULL,        -- 资金/话单/住宿...
  rule_version  text NOT NULL,
  hints         jsonb NOT NULL,       -- {单位, 时间格式, 方向约定, 文件名模式}
  hit_count     integer NOT NULL DEFAULT 0,
  created_at    integer NOT NULL,
  PRIMARY KEY (project_id, id)
);
```

**与格式缓存的区别**

| | 格式缓存 | 数据源档案 |
|---|---|---|
| 粒度 | 一份确切格式 | 一类来源 |
| 条件 | 指纹完全一致 | 表头集合重合度 ≥ 阈值 |
| 作用 | 直接套映射 | 套映射 + 单位/时间/方向约定 |

档案的 `type` 与模板的 `event_type` 同值对应：档案命中 ⇒ 一次把「哪列是哪字段」（档案）+「字段怎么变卡片」（模板）+ 单位/时间/方向约定（`hints`）全定下来。

#### 卡片模板（第四类记忆）

**它记的是「这类数据怎么翻译」，而不是「这个文件有哪几列」。**

| | 别名库 | 格式缓存 | 数据源档案 | **卡片模板** |
|---|---|---|---|---|
| 记什么 | 一个表头 → 一个字段 | 一份文件 → 列映射 | 一类来源 → 约定 | **一类数据 → 九格填法** |
| 解决 | 「金额（元）」认不出 | 同格式不重复识别 | 同来源列顺序变了 | **新类型不用开发** |
| 表 | `case_field_alias` | `case_table_format` | `case_source_profile` | `case_card_template` |

四层叠起来就是一次完整的自动处理：

```
档案命中 → 知道单位和约定
  ↓
格式命中 → 知道哪列是哪字段
  ↓
别名兜底 → 知道没见过的表头是什么
  ↓
模板命中 → 知道这些字段怎么变成卡片
```

前三次是「认表」，第四次是「翻译」。**四层全命中 = 用户零操作。**

模板的「变聪明」体现在 `hit_count`：命中越多越可信；一旦用户改动模板，`version+1`，旧翻译结果失效重算。

### 6.3 学习闭环

```
用户点确认
  → 同一事务写记忆（别名 / 数据源档案；模板转正时写 verified_at）
  → 版本 +1（使旧格式缓存与旧翻译结果不可达）
  → 下次识别优先命中
  → hit_count +1
```

模板转正（§4.7.6）也走这条闭环：只是把「写别名」换成「写 `verified_at`」，版本与命中计数的道理完全相同。

### 6.4 冲突与失效

| 情况 | 处理 |
|---|---|
| 同一表头已有别名，又要改成别的字段 | **不静默覆盖**，提示「以前定为 X，改成 Y？」（吸取 `#010-05`：后到覆盖会让结果漂） |
| 规则版本变化 | 使格式缓存与卡片重建，`case_table_format` 增加 `rule_version` 失效判断 |
| 模板改动 | `version+1`；卡片 id 含模板版本（§3.7），用该模板产出的卡片按重放规则重建 |
| 撤销确认 | 别名置 `revoked_at`，版本 +1；界面必须有撤销入口（现有缺口） |

### 6.5 防「越学越错」的四道闸

1. **写别名前过单位闸**（已有，`case-field-alias.ts:64`）；
2. **别名键用原始表头，不归一化**（`#011-01`）；
3. **冲突不覆盖，必须人确认**；
4. **一切可撤销，且撤销后旧缓存不可达**。

### 6.6 预处理 skill 的版本与下线（同一套防错）

预处理规则一旦错，**全员同期错**（`04` §二(九)）。所以它走资产七态流水线，并必须配三样：金标准样本（原件 + 期望副本）、版本号、下线能力。发现错误先下线，再迭代发布——不靠口头通知。

同时记住 04 的边界：**流水线审的是 skill 本身，不是「这份文件转得对不对」**（`04` §二(八)）。所以两道技术闸必须留在 skill 内、每次运行都执行；发布前的样本验证由作者负责（金标准样本机制待建）。

## 7. 查询性能

### 7.1 实测基线（2026-11-09，远端 PG，含网络往返）

| 查询 | 耗时 | 执行方式 |
|---|---|---|
| 明细按时间取 100 行 | 138 ms | **Parallel Seq Scan**（17.7 万行） |
| 明细按项目计数 | 84 ms | 全表扫 |
| 实体别名搜索（旧的 `aliases` 数组） | 0.2 ms | 表仅 190 行 |

库存规模：44 份材料 / 177,713 行明细 / 277 MB；190 实体 / 69 事件。

### 7.2 索引清单

| 表 | 索引 | 状态 |
|---|---|---|
| `case_fact_row` | `(project_id, started_at)` | **新增**（现在全表扫） |
| `case_event` | `(project_id, occurred_at)` | 已有 |
| `case_event_participant` | `(project_id, entity_id)` | 新增（`(project_id, event_id)` 由 `UNIQUE (project_id, event_id, ordinal)` 的前缀覆盖，不重复建） |
| `case_entity_alias` | `(project_id, kind, value)`、`(project_id, entity_id)` | 新增 |
| `case_event_relation` | `UNIQUE (project_id, from_event, to_event, type)`（正向）、`(project_id, to_event)`（反向） | 新增 |
| `case_citation` | `(project_id, fact_type, fact_id)` | 已有 |

**别名表反而比现在快**：现在搜别名是 `unnest(aliases)` 扫数组，实体到十万级会变慢；新表是 B 树等值查。

### 7.3 查询规范（硬约束）

所有读取函数必须同时满足：

1. **带 `project_id`**（且为索引首列）；
2. **带时间窗 / 实体 / 材料之一**，禁止无界全表扫；
3. **带 `limit`**（默认 50，上限 200，超限截断并回写「缺口」）；
4. **返回 `口径` 与 `缺口`**（已有约定，继续执行）；
5. **空结果必须分类**：0 条时区分「确实没有 / 身份没对上 / 数据没入库」，不得把后者当空集返回（§3.8.5）。

### 7.4 防 N+1（最容易犯的坑）

- 事件列表接口**一次返回**参与者摘要与出处摘要，不允许前端逐卡取数；
- 50 张卡片 = 3 次查询（事件、参与者批量、出处批量），不是 150 次；
- 验收：用真实数据量测一次列表渲染的查询次数，写进测试。

### 7.5 分页

- 时间线用**游标** `(occurred_at, id)`，不用 `offset`（深翻页 offset 会越来越慢）；
- 每页固定 50，前端预取下一页。

### 7.6 计算侧性能（比查询更容易出事）

| 计算 | 风险 | 方案 |
|---|---|---|
| 事件共指（同源 / 跨源，§4.0.5 坑 4） | 17 万卡片两两比 = 310 亿次 | **先分桶**：事件类型 + 时间桶（如 ±1 天）+ 地点实体 + 主体集合；桶内比较 |
| 实体消解 | 全表两两比 | **阻塞键**：证件号 / 手机号 / 账号；无强标识不进自动比较 |
| 翻译入库 | 逐行写库慢 | 批量插入（每 500 行一批），同一材料一个事务 |

### 7.7 分区与增长阈值

- `case_event` / `case_event_participant` **本轮不分区**；
- 触发条件：单表 > 500 万行或单项目 > 200 万行 ⇒ 按 `project_id` 哈希分区（照 `case_fact_row` 的做法）。**这两个阈值是估算，需一次 500 万行压测校准。**
- 哈希分区只带来**查询裁剪**：同一项目的数据散在 16 个分区里，**不能按项目单独 `DROP`/归档**，清理只能走 `DELETE`。这是已知局限，别指望分区解决「删掉一个案子」。
- 超过千万级且分析查询拖慢交互 ⇒ 才考虑分析副本（不换主库）。

### 7.8 验收指标

| 场景 | 数据量 | 目标（p95） |
|---|---|---|
| 时间线首屏（50 张卡片） | 100 万卡片 | ≤ 300 ms（含网络） |
| 实体档案首屏 | 同上 | ≤ 300 ms |
| 资金汇总 | 单账户 1 万笔 | ≤ 500 ms |
| 明细按时间取 100 行 | 100 万行 | ≤ 50 ms（库内） |

### 7.9 解析（入库）性能

#### 7.9.1 铁律：任何写入路径都不许逐行往返

远端 PG 一次往返 **80–140 ms**（实测）。逐行 insert 时，这个延迟会乘以行数——再快的逻辑也救不回来。

> **一份材料 = 一个事务；每 500 行一批。**
> 违反这条，解析时间从「3 分钟」变成「25 小时」。

#### 7.9.2 这笔账

改造后每行约写 5 行（卡片 + 2 参与者 + 出处 + 关系增量），17.7 万行 ≈ 90 万行写入。但真正决定耗时的是**往返次数**：

| 写法 | 往返次数 | 90 万行耗时（估算） |
|---|---|---|
| 逐行 insert + 逐行提交 | 90 万 | ≈ 25 小时（不可用） |
| 逐行 insert，单事务 | 90 万 | ≈ 25 小时（事务不省往返） |
| **批量 500 行 + 单事务** | **1,800** | **≈ 3 分钟** |
| 批量 + `COPY` | 180 | ≈ 30 秒 |

同一份工作、同样写入量，**写法差 1000 倍**。

#### 7.9.3 三处真风险

| 风险 | 表现 | 对策 |
|---|---|---|
| **实体归并逐行查库** | 5,000 行流水 → 1 万次 `select` → 17 分钟 | 内存 Map，一份材料内去重，查库降到几百次（§4.0.3c） |
| **索引拖慢插入** | 每个索引让插入慢 5–15% | 见 7.9.5，先建一个，其余按实测加 |
| **模型识别** | 秒级，但每张表**一次**，不是每行 | 指纹/别名命中即不调；只有首次见的新格式才慢 |

#### 7.9.4 三层提速，各管一段

| 层 | 手段 | 状态 |
|---|---|---|
| 识别层 | 格式指纹 + 别名库命中 ⇒ 不调模型 | ✅ 已有 |
| 翻译层 | 规则是确定性代码，比模型快几个数量级；**可按材料并行** | 新增 |
| 写入层 | 批量 + 单事务 + 后台作业 | 要守 |

`case_ingest_job` 已提供后台作业与进度，**复用，不另做一套**。

#### 7.9.5 索引的写入代价

§7.2 列的 6 个索引不会一次性建。顺序：

1. `case_fact_row (project_id, started_at)` —— **先建**，它是当前最慢查询（§7.1：明细按时间取 100 行 138 ms，Parallel Seq Scan）的直接解药；
2. 随 P2/P3 建表时一并建各自的外键索引（新建表时索引成本最低）；
3. 其余等**实测出慢点**再加，不凭想象建。

#### 7.9.6 落地第一步：先测基线（这三个数现在没有）

| 要测的 | 怎么测 | 为什么必须先测 |
|---|---|---|
| 一份 5,000 行流水当前解析耗时 | 真栈跑一次，记时间 | 没有基线，「变快/变慢」无从判断 |
| 17.7 万行全量重解析耗时 | 同上 | 决定改规则后能否全量重跑 |
| 批量 vs 逐行的真实差值 | 同一份 5,000 行两种写法各跑一次 | 验证 7.9.2 的估算是否成立 |

> 本文 7.9.2 的数字是**按往返 100 ms 推算的估算，不是实测**。落地前必须补测。

#### 7.9.7 验收目标

| 场景 | 目标 | 用户感受 |
|---|---|---|
| 单份 5,000 行流水 | ≤ 30 秒 | 点一下，片刻后可看 |
| 单份 50,000 行流水 | ≤ 5 分钟 | 后台跑，可离开 |
| 全量重解析 17.7 万行 | ≤ 15 分钟 | 改完规则能重跑 |
| **上传响应** | **立即返回** | 立刻看到「已收到，解析中」+ 进度 |

最后一行是体验底线：**用户永远不该盯着转圈**。进度、可离开、可重试，都是已有能力（`case_ingest_job`）。

### 7.10 备注原文与实体属性的检索

| 查询 | 走什么 | 成本 |
|---|---|---|
| 备注原文（只回显，不供 AI 查） | `case_fact_row.extras`；按 `material_id + locator{sheet,row}` 取单行 | 点查，不扫描；**不做关键词检索**（§3.11） |

## 9. 页面与 AI 的一致性

> 本节是 §0.0 的落地：AI 是主要消费者，页面必须与它同一口径、同一出处、同一句「不确定」。

1. **唯一取数层**：页面 API 与 AI 工具共用同一批取数函数（`case-fact-read.ts` / `case-entity-list.ts` / `case-graph.ts`），AI 侧入口是 `case-mcp-tools.ts`；两侧都不另写 SQL。
2. **口径回传**：每次查询返回 `口径`（用了什么过滤）与 `缺口`（截断、未覆盖），页面原样展示，AI 原样引用。
3. **答案必须带出处**：AI 的最终回答若涉及具体事实，必须能给出 `material_id + sheet + row_no`；给不出就不下结论。
4. **不确定要说出来**：候选实体、疑似重复、时间缺失，必须在回答里显式标注。
5. **查询侧怎么落地**：工具契约、统一返回信封（摘要 / 数据 / 口径 / 缺口 / 空原因 / 出处 / 下一步）、追查纪律与预算，见 `09-AI探索与MCP工具-设计.md`。本节只定「必须一致」，`09` 定「怎么做到」。

## 10. 权限与安全

- 沿用现状：每条 SQL 带 `project_id`，入口校验成员（`校验成员`），工具不接受模型传项目名。
- 本轮**不引入 RLS**：RLS 涉及连接池与请求上下文，与现有 `Effect` 上下文有冲突风险（`#010-07`）；卡片结构稳定后单独立项。
- 卡片与明细同属业务数据：**不进每用户 SQLite**。

### 10.1 明文原则（2026-11-10 拍板，硬约束）

> **账号、身份证号、手机号、姓名、金额，全程明文。不脱敏、不掩码、不打码，任何环节都一样。**

覆盖范围：

| 环节 | 要求 |
|---|---|
| 入库 | 原样存，不做任何截断/替换 |
| 存储 | `case_fact_row` / `case_entity` / 卡片，全部明文 |
| 展示 | 页面、导出、打印，全部显示完整值 |
| 日志 | 不承载业务值；错误信息与崩溃上报过滤完整账号（见下方代价） |
| 送模型 | 不脱敏（前提：模型内网/自部署） |
| 检索/聚合 | 按完整值比对 |

实体属性（开户行、银行卡号、证件号）与备注原文同属业务值，按同一原则处理：明文入库、不掩码（`05` §0-4、`06` §0-5）。

**现状核实**（2026-11-10 grep 全仓）：存储与展示本来就是明文，前端 `packages/app/src/center` 无任何掩码逻辑（测试文件里出现的 `6222****0001` 是夹具样例字符串，不是打码代码——`grep 掩码\|脱敏` 只命中这些测试）。全仓**唯一**的脱敏点是一处：

| 位置 | 作用 | 现状 |
|---|---|---|
| `case-header-ai.ts:88-106` + 配置 `case_table_mask_samples` | 送**表头模型**的样例做掩码 | **默认关闭**（`case-ingest-worker.ts:87`，仅当配置为 `true` 才开） |

按本原则，这个开关**不再开启**。它的去留（删除代码还是留着但保证永不开启）列入实现计划处理——本轮只定原则，不改代码。

#### 两类「掩码」必须分清

| | 谁做的 | 怎么办 |
|---|---|---|
| **本系统脱敏** | 我们主动打码 | ❌ **一律不做**（本原则） |
| **源文件自带掩码** | 银行/运营商导出时就是这样（`6222****1234`） | ✅ **原样保存**，但**不当强标识**——见 §4.0.5 坑 1 |

第二类不是我们的策略，是数据本身不全。系统绝不"补全"它，也绝不因为源文件打了码就在库里再打一层。

#### 明文的代价（必须配的补偿控制）

明文意味着一旦泄漏就是完整泄漏。要真做明文，下列控制**不能省**：

| 控制点 | 要求 |
|---|---|
| 访问 | 成员校验在入口一次（已有）+ 每条 SQL 带 `project_id`（已有） |
| 审计 | 谁查了哪个案子、查了什么，要有记录（本轮建议补，见 §13 Q8） |
| 日志 | 错误信息/SQL 日志不得回显完整账号；崩溃上报要过滤 |
| 模型 | 只允许内网/自部署模型；走公网 API 等于把明文送出去 |
| 备份 | 备份文件按同等级数据管理 |
| 导出 | 导出即出域，需单独授权。本轮不提供**数据**导出；唯一例外是 `08` 的关系图产物导出 PNG（图上含明文姓名、账号、金额），实现时必须同时给出「谁导出、导出到哪」的授权与留痕口径，不能默认放开（见 §14 Q23） |

**一条明确的红线**：若将来接入任何公网大模型 API，明文进模型 = 数据外泄，届时必须先解决这条，**不能偷偷把开关改回脱敏了事**（那是静默策略变更）。

## 11. 端到端验收标准

| 编号 | 场景 | 通过条件 |
|---|---|---|
| A1 | 上传一份从未见过的银行流水 | 自动识别出时间/金额/对方/方向；无静默错误；待确认项 ≤ 2 |
| A2 | 同一格式再上传 | **零人工确认**（L0） |
| A3 | 打开任意一张卡片 | 能一键跳到原文单元格；原文与卡片值一致 |
| A4 | 问「某账户给谁转了多少」 | 笔数/合计/对手方数与人工核算**完全一致**，每条可查出处 |
| A5 | 合并两个实体 | 事件、关系、别名、引用全部跟着走；可拆回 |
| A6 | 同一手机号不同时段 | 系统提示「疑似换主」，不自动合并 |
| A7 | 重传同一材料 | 卡片重建，人工确认过的结论仍在 |
| A8 | 50 张卡片列表 | 查询次数为常数（≤ 5），不是 N+1 |
| A9 | 识别失败 | 显示原因 + 一键重试；不丢已确认内容 |
| A10 | AI 回答 | 每个事实性结论都带出处；无出处时明确说"查不到" |
| A11 | 只有户名没有身份证 | 答「户名为 X 的账户」，并标「未核实身份」；不冒充「X 本人」 |
| A12 | 问一个账户，但资金材料未翻译 | 返回「材料未解析」+ 去解析入口，**不返回「0 笔」** |
| A13 | 上传一份 5,000 行流水 | **立即返回**「解析中」，可离开页面；≤ 30 秒完成并产出卡片 |
| A14 | 用户在前端新建一个「通话」模板 | 下拉只能选字段/角色/实体类型词表内的值；保存前能预览前 20 行翻译结果；未验证模板产出的卡片不出现在 AI 默认查询，用户确认一次后转正 |
| A15 | 备注原文不丢（2026-11-12 修正） | 原表「备注」值逐字留在 `case_fact_row.extras`（键=原表头），不进待确认、不被丢弃；**不加 `remark` 列、不改识别版本**；`get_citation(row)` 能整份返回含备注的 `extras`；「按用途/商户查」归二期（`case_event.purpose` + 参与者角色） |
| A16 | 实体属性可答（`05`） | 属性列不进待确认；`query_entities.attrs` 有 `开户行`/`银行卡号` 且带出处；两份材料给出不同开户行时**两条都在** |
| A17 | 预处理两道闸（`03` / `04`） | 副本同时装下「原始列/标准列/判定依据/行号」+ 转换说明 + 原件 SHA-256；变异样本被拒收且**不产出标准副本** |
| A18 | 批量入库 | 右键副本文件夹 ⇒ 逐个建材料、入队；同一指纹重复拖入不产生第二条材料 |
| A19 | 相对角色 | 贷方行的本方/对方与「查询账号」一致（按列名硬取会错掉 336/699 行，`03` §3） |
| A20 | 用途分类可审计（2026-11-12 加入，`06` §9） | 一级 12 类合计 = 明细行数（首版基线 31,719），消费二级合计 = 消费数；每条 `purpose` 带 `purpose_basis`（命中词 / 规则 / 词表版本）与行级出处；改词表可全量重算且新旧版本可区分；批量路径零模型调用；预处理产物里没有用途列 |
