# 项目技能提交审核 · 设计

> 状态：待评审（2026-11-01）
> 关联：009-ai-assets（资产治理 / 生命周期）、2026-11-01-skill版本迭代
> 本文只解决一件事：**作者在项目里做出来的 skill，怎么在界面上交出去审核。**

## 1. 要解决的问题

### 1.1 现象

作者做完一个 skill，界面上没有任何入口能把它提交审核，也不知道该说什么。目前唯一走得通的路径是：自己记得资产编号，在右栏对 AI 说一句「把资产 xxx 提交审核」，由模型调 MCP 工具 `submit_skill_for_review`。

### 1.2 根因（三条，都有落点）

| # | 根因 | 证据 |
|---|---|---|
| R1 | 提交动作只有 MCP 一个入口，界面没有 HTTP 通路 | `packages/opencode/src/server/openhive/assets.ts:142-147` 只有列表 / 内容 / 迭代三组路由 |
| R2 | 作者的两条来路做出来的东西**还不是资产**，连提交资格都没有 | `create_skill_draft` 是唯一入库口（`governance.ts:472-483`），界面无入口 |
| R3 | 即使已经是草稿，界面也看不见它：资产列表只放行 `published` + `iterating` | `assets.ts:211` |

### 1.3 一个必须先修的前提

「这是不是库里的资产」今天**判错了**：

- 服务端注释明确写着「前端**不得**用 `assetId !== undefined` 判是不是库里的，只能比 `enabled`」，而 `assetName` 才是「库里确有这份资产」的标记（`project-assets.ts:121-123`）。
- 但 `assetName` 的查表只对 `state.enabled` 构建（`project-assets.ts:458-465`），**草稿没有启用行**（建草稿只建链接，`service.ts:253`）。
- 前端分拣用的是 `enabled.has(assetId)`（`capability-source.ts:63-74`）⇒ 草稿会落进「本项目自带」。

结论：**不先修 R4，后面所有标签都是错的。**

| # | 根因 | 证据 |
|---|---|---|
| R4 | 来源判定缺少正确信号（库里有没有这个 id），前端只能拿 enabled 猜 | 同上 |

## 2. 目标与非目标

**目标**

1. 项目「能力」面板里，每条 skill 都能看出**来源**和**阶段**，并给出**唯一的下一步动作**。
2. 未入库的 skill 能在界面上完成「入库 → 提交审核」，不需要用户知道资产编号或目录。
3. 提交后作者能看到进度，被驳回能看到原因。

**非目标（本次不做）**

- 不做审核台改造（治理台已有待审队列，`asset-governance.tsx:147`）。
- 不做跨项目链接（同一草稿链进第二个项目）。
- 不做批量提交、不做多选。
- 不做资产中心「我的创作」视图（本期只做能力面板；资产中心后续接入同一份判定）。

## 3. 关键决策

| # | 决策 | 结论 | 为什么 |
|---|---|---|---|
| D1 | 提交审核从哪儿取内容 | **`/draft/<assetId>`**（用户拍板） | 只需 assetId；与项目无关；库里不存用户路径（避开 `#010-04`） |
| D2 | 「未入库」是否一键入库＋提交 | **一键**（用户拍板） | 用户只需要理解一个按钮；缺的信息表单一次补完 |
| D3 | 发布成功后草稿副本与项目链接 | **删副本 + 链接改指发布目录**（用户拍板） | 保证「项目里用的 = 线上那份」，消灭静默的旧版本 |
| D4 | 来源 / 阶段的判定 | **服务端按 assetId 查库，回 `assetStatus` / `assetOwnerId`** | 判定只留一处（`#002-06`）；不再让前端用 enabled 猜 |
| D5 | 驳回理由怎么显示 | **读 `auth.asset_notification` 最近一条 `reject_business`**，不加列 | 通知表已有 `asset_id` / `action` / `body`（`notify.ts:225-228`），无需迁移 |
| D6 | 被同名技能覆盖的条目 | **不给提交按钮**，先提示改名或移走 | 交上去的可能不是 AI 正在用的那份 |
| D7 | 重复提交 | 状态机天然拒绝；错误文案「已经提交过了」，按钮请求中禁用 | 幂等由状态机兜底，界面只负责别让它难堪 |
| D8 | 审核中作者继续改草稿 | **允许**，但界面标明「送审版已锁定，改动不影响本次审核」 | 提交是复制到 `pending/`；不说明就会变成「我明明改了」的投诉 |
| D9 | 可见范围 | 表单**必选**；选「部门」时用**账号档案里的部门**（只读展示，不让填） | 默认 `personal` 会导致「发布了但同事搜不到」（`governance.ts:459-461`）。部门不可编辑：允许自选等于给「以别的部门名义发布」开口子（2026-11-01 实现期裁定） |
| D10 | MCP 的 `submit_skill_for_review` | **同步改为从 `/draft/<id>` 复制**，`sourceDirectory` 入参下线 | 两条提交路不得有两个取内容的来源（`#002-06`） |

## 4. 设计

### 4.1 身份与阶段：一条技能只有一种身份

服务端在 `映射内核清单()` 里按 assetId 批量查 `auth.asset`，为每条技能补两个字段：

```ts
export interface 内核技能 {
  readonly name: string
  readonly description?: string
  readonly location: string
  readonly assetId?: string
  readonly assetName?: string
  /** 库里查得到才有。查不到 = 未入库（本项目自带）。 */
  readonly assetStatus?: AssetStatus
  /** 见到库里的行才有；用于「我的」判定。 */
  readonly assetOwnerId?: string
}
```

前端分拣规则（唯一一处）：

```
有 assetStatus           → 库内条目，阶段 = assetStatus
没有 assetStatus         → 本项目自带，阶段 = 未入库
assetStatus === "draft"  → 可提交（作者本人）
其余阶段                 → 只显示进度，不给提交按钮
```

> 查表**一次批量**（`where id in (...)`），不逐条查；查不到就是查不到，不回落到 enabled 推断。

### 4.2 界面：能力面板的每一行

| 阶段 | 角标 | 右侧 | 悬停说明 |
|---|---|---|---|
| 未入库 | `未入库`（错误色） | 按钮「提交审核」 | 「先登记名称和分类，再送给业务审核」 |
| 草稿 | `草稿`（警示色） | 按钮「提交审核」 | 「送给业务审核，通过后由管理员发布」 |
| 草稿（被驳回过） | `草稿` + 一行驳回理由 | 按钮「提交审核」 | 理由来自最近一条驳回通知 |
| 审核中 | `审核中`（强调色） | 文案「等业务审核」 | 「送审版已锁定，改动不影响本次审核」 |
| 待技术发布 | `待技术发布` | 文案「等管理员发布」 | 同上 |
| 已发布 | `已发布`（成功色） | 按钮「发起新版本」 | 已有能力，复用 |
| 迭代中 | `迭代中` | 按钮「提交这一版」 | 已有能力，复用 |
| 已下线 / 已归档 | 同状态名 | 不给提交 | 本期不做 |

约束：

- 每条技能**最多一个按钮**；没有下一步时按钮位留空，不放假按钮。
- 按钮的 `disabled` 由请求中状态驱动，防连点。
- 面板宽度有限：按钮文字在窄宽度下缩成图标 + `aria-label`（沿用面板现有的无障碍写法）。

### 4.3 未入库的提交：表单 + 两段串行

点「未入库」的提交审核 → 弹出小表单：

| 字段 | 来源 | 必填 |
|---|---|---|
| 名称 | SKILL.md frontmatter（服务端已能读，`skillNameOf`） | 是（可改） |
| 功能描述 | SKILL.md `description`；没有则**用户填** | **是**（2026-11-01 实现期裁定：`auth.asset` 有 `CHECK (btrim(description) <> '')`，空描述不迁移就存不进去，故必填） |
| 分类 | 管理员维护的闭集（`category-store.ts`） | **是** |
| 谁能用 | global / department / targeted / personal | **是** |
| 部门 | **账号档案里的部门，只读展示**（2026-11-01 实现期裁定：端点不读可编辑的部门，部门取自 `auth.user.dept`；让用户自选等于给「以别的部门名义发布」开口子） | 不适用 |

确认后前端**串行调两个接口**：

1. `POST /openhive/assets/draft` → 入库，返回 `assetId`
2. `POST /openhive/assets/:id/submit` → 提交审核

**不做「原子」端点**：入库成功、提交失败是可能且可恢复的中间态。界面停在「草稿」并提示「已入库，提交失败，请再点一次提交审核」——比一个假装原子的接口诚实，也更好重试。

### 4.4 接口契约

```
POST /openhive/assets/draft
body: { projectId, skillPath, name, description, category, visibility, department? }
       // description 必填（非空）：见 §4.3 注。skillPath 必须是带 SKILL.md 的目录，否则 400。
  skillPath = 内核报告的 location 的父目录（项目内相对路径）
200: { assetId, name, status: "draft", visibility }
400: 分类不存在 / 路径不合法 / 目标项目不属于你
403: 越出沙箱边界
```

**不做同名去重**：库里允许两个同名资产（内核按名字去重，面板已有「被同名覆盖」的诊断）。重复入库只可能来自连点，由按钮请求中禁用兜住。

```
POST /openhive/assets/:id/submit
body: 无
200: { assetId, status: "in_review" }
400: 状态不允许（已提交过 / 不是草稿）
403: 不是作者
```

**授权**：两个端点都先 `authorizeTransition(viewer, asset, grants, action)`，与迭代三端点同形（`assets.ts:397`）。**不新写任何权限判断**（`#005-24`）。

**边界（最关键的一段）**：`skillPath` 必须走与 MCP 完全相同的两层校验——

1. 调用目录（`projectId` 推出的项目目录）必须落在 `<沙箱根>/<userId>/` 内；
2. `skillPath` 解析后必须仍在调用目录内，且**经 realpath 后**仍成立（`#009-03`：只比字面路径会被链接绕过）。

任一层不过 ⇒ 403，一个文件都不复制（`#004-09`）。**实现时直接复用 `governance.ts` 的 `sandboxDirectoryOf()` / `resolveSourceDirectory()`，不另写一份。**

### 4.5 提交的存储动作

`submit_review` 的 `storage` 从 `sourceDirectory` 改为 **`draftDirectory(root, assetId)`**：

```
<assetsRoot>/draft/<assetId>  ── copy ──▶  <assetsRoot>/pending/<assetId>
```

- 前端 / 模型都不再提供目录；
- 项目删了也能提交（草稿副本不依赖项目）；
- 作者原目录的后续改动不进入审核——这一点由 4.2 的「送审版已锁定」文案承担。

MCP 侧同步：`submit_skill_for_review` 删掉 `sourceDirectory` 入参，工具描述与返回的 `next` 文案一并改（`governance.ts:93-104`、`:491`）。

### 4.6 发布成功后收拾草稿

`publish_tech` / `publish_iteration` 成功后：

1. 删除 `<assetsRoot>/draft/<assetId>`（若存在）；
2. 把项目里的链接改指发布目录：**在发布流程里显式调用 `linkSkill(项目目录, assetId, 发布目录)`**，不依赖送达对账。
   理由：`reconcileSkillLinks` 的 `linkSkill` 遇到目标不同确实会重建（`project-skill-link.ts:200-207`），但它只处理 `desired` 里的资产；「没启用也没自动送达」的资产根本不在 `desired` 里，等对账永远等不到。

> 现状风险（已核实代码路径）：`reconcileSkillLinks` 对「目标在 `draft/` 下的链接」明确不动（`project-skill-link.ts:187-195`）；发布又只搬 `pending/`（`service.ts:810-824`）。若该资产既未手动启用、也未被自动送达，项目里的那份会长期停在提交前。本设计把这条一并关掉。

### 4.7 驳回理由

不新增列。作者侧查询：

```sql
select body from auth.asset_notification
where asset_id = $1 and recipient_id = $2 and action = 'reject_business'
order by created_at desc limit 1
```

通知正文已含理由（`notify.ts:162`）。**已知残差**：通知没有重试、可能缺行；缺行时界面显示「尚未提交过」，不编理由。

### 4.8 错误与并发

| 情况 | 表现 |
|---|---|
| 连点两次提交 | 第二次 400，文案「已经提交过了」 |
| 两个标签页同时提交 | 先到者生效；后到者 400「状态已变化，请刷新后再试」。（2026-11-01 实现期裁定：不复用「已经提交过了」——并发那一刻可能是别人动的它，说「已提交过」是第二种假话） |
| 入库时分类已停用 | 400「这个分类已停用，请重新选择」 |
| 入库后提交失败 | 停在草稿 + 「已入库，提交失败，请再点一次」 |
| 内核没读到清单 | 整块保持「暂时读不到」+ 重试，**不**把每条画成未入库（`#002-02`） |

## 6. 测试与验收

**必须写的红用例（先红后绿）**

1. 服务端：内核清单里，库里的草稿带 `assetStatus: "draft"`；手写的 skill 不带（不带 = 未入库）。
2. 服务端：提交 `submit_review` 从 `/draft/<id>` 复制；`pending/` 内容与草稿一致，与作者原目录的后续改动无关。
3. 服务端：`POST /:id/submit` 非作者 403、已提交 400、成功 200 且状态 `in_review`。
4. 服务端：`POST /draft` 的 `skillPath` 带 `../..` ⇒ 403，且 `<assetsRoot>` 下不新增任何目录。
5. 服务端：发布后草稿副本被删、项目链接指向发布目录。
6. 前端：未入库行显示「未入库 + 提交审核」；确认表单后串行两请求；提交失败停在草稿并给出可重试文案。
7. 前端：审核中行没有按钮、有「送审版已锁定」说明。
8. 前端：被同名覆盖的条目没有提交按钮。

**变异验证**：至少对 1、2、4、5 各拆一次修复，确认对应用例转红（`#003-03`）。

**门禁**：`packages/opencode`、`packages/asset-service`、`packages/app` 各自的 typecheck + 测试 + oxlint，在仓库根跑。

**真栈验收**（作者本人操作）

- 上传一个 skill 文件夹 → 能力面板显示「未入库」→ 点提交、选分类与可见范围 → 出现在治理台「待业务审核」。
- 管理员驳回 → 作者在面板看到理由 → 再提交 → 通过 → 发布 → 项目里的链接指向线上那份。

## 7. 风险与未决

| 风险 | 说明 | 处理 |
|---|---|---|
| 内核重扫时机 | 从外部拷入的 skill 目录，内核是否立刻可见，取决于重扫触发 | 实测确认；若不可见，面板需要「刷新能力」入口（不在本期） |
| 通知缺行 | 通知失败不重试，驳回理由可能读不到 | 显示「尚未提交过」，不编造 |
| 上传路径 | 外部上传到项目目录的具体位置（`.opencode/skill/` 还是别处）会决定 `skillPath` | 实现前实测一次 |
| MCP 契约变更 | `submit_skill_for_review` 少一个参数，模型侧提示词需要同步 | 工具描述里写明新口径 |

## 8. 术语

- **未入库**：内核看得见、`auth.asset` 里没有这行。这不是资产，没有 assetId。
- **草稿**：已入库、状态 `draft`。可提交。
- **送审版**：提交那一刻复制进 `pending/` 的快照，审核审的是它。
