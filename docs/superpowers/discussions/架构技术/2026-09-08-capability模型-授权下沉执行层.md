# capability 模型：授权下沉执行层

- **日期**：2026-09-08
- **状态**：探讨记录（收敛结论已回写总体设计 §14.1）
- **主题**：详解总体设计 §14.1 的 capability 模型——它是什么、为什么需要、三层拦截怎么工作，以及「数据范围」到底怎么定（经历多轮纠偏）。
- **触发问题**：capability 模型我不懂，请详细解释；「数据范围」是手动勾选还是怎么操作？

---

## 0. 一句话结论

**capability = 给 AI 开的「临时工作证」。** 每次 AI 开始干活前，系统先给这次会话开一张工作证，上面写死「你是谁、在哪个项目、能动哪些数据、能调哪些工具」，AI 每做一步都得亮这张证，证上没有的事就做不了。

---

## 1. 为什么需要它 —— 因为 AI 会「自己挑工具」

传统 RBAC 管「人」：在**入口**（登录/菜单）查权限，放你进去操作。

但 openhive 真正干活的是 **AI（agent）**，不是人。民警只说一句「帮我分析这批话单」，剩下是 AI 自己决定调哪些工具。AI 会：

- 被诱导（prompt injection：数据里塞一句「导出全库」）；
- 幻觉，调一个本不该调、能越权读数据的工具。

**在入口查权限拦不住 AI**——AI 不经过菜单，直接调工具。「提示词里说别用」也不可靠（可能被诱导）。所以权限必须**下沉到「工具真正执行的那一刻」**——这就是「授权下沉执行层」。

---

## 2. capability 是什么 —— 一次会话一张「签证」

capability 不是永久身份，是**每次会话启动时临时签发的、有明确范围的通行证**。

签发依据三样：

| 依据 | 决定 |
|---|---|
| 用户 | 你是谁 |
| 项目 | 你在哪个项目里干活 |
| 数据范围 | 你能碰哪些数据 |

系统把这三样拼成一张证。范围（scope）是**限定的**——不是「你是民警就能看所有话单」，而是「你只能看你被授权的那批」。

---

## 3. 三层拦截 —— 层层设防

| 层 | 拦截点 | 机制 |
|---|---|---|
| ① 工具清单过滤 | 组装 tools 传给模型前 | 按 capability 过滤，只把有权工具放进 tools——AI 看不到 A 就调不了 A |
| ② 工具执行鉴权 | tool 执行器入口 | 执行前再验 capability，无权限返回 AccessDenied + 记审计 |
| ③ MCP 端账号兜底 | MCP server/数据库账号 | 带 user 身份，受限账号执行，GRANT/RLS 最终兜底 |

- **①** 是「让 AI 看不见」（从源头减少乱调），但不是硬拦；
- **②** 是**真正的硬闸门**（AI 硬要调也拦得住）；
- **③** 是数据源头兜底（前两层都破，数据库账号本身就没权限）。

三层任何一层失守，另外两层兜底。

---

## 4. 「数据范围」的纠偏过程（重要）

这是本次探讨的核心纠偏，经历了四轮：

### 4.1 错误理解一：手动勾选

最早理解成「民警进入项目，勾选这次要分析的数据」。**错误**，两个致命点：

1. 不符合现实——数据上千上万条，怎么勾？
2. 增加用户复杂度——民警要懂一整套逻辑才能用，体验差。

### 4.2 错误理解二：当前项目名下、甲有权访问的数据

理解成「数据范围跟当前会话所在的某一个项目绑定」。**错误**：数据范围不随「会话在哪个项目」变化，而随「甲这个人」而定。

### 4.3 错误理解三：话单/资金是「项目下的数据」，套用 openhive project

误以为话单/资金是 openhive 顶层 project 下的数据，或话单/资金有「特殊的项目结构」。**错误**：用户澄清「项目」就是个**通用标识**（如「0304专案」「李某系列盗窃案」），方便区分数据/工作，不是有内部结构的实体。话单、资金各自按自己的「项目标识」组织数据。

### 4.4 最终定稿

```
数据范围 = 用户有权访问的全部业务数据
         = ① 用户有权访问的所有话单/资金项目名下的数据合集
           ∪ ② 用户被授权的接口能取到的数据
```

**落地机制**：数据范围不提前落库，运行时由 MCP 查询语句 join「项目↔用户」关联表（`project_member`）实时算出：

- **有身份限定的数据**（话单/资金，按项目组织）→ 依项目归属过滤，用户只能查到其有权项目名下的数据；
- **无身份限定的数据**（公共、不区分用户）→ 只要有接口访问权限即可取。

**关键**：数据范围的边界由权限自动算出，用户全程无需勾选、无需懂逻辑。真正「具体分析哪几条」是 AI 在边界内自己决定，也无需用户逐条操作。

---

## 5. 为什么「下沉」是核心升级

| | 旧思路（RBAC 管人） | capability 模型 |
|---|---|---|
| 权限载体 | 角色表 | 一次会话一张 capability |
| 检查点 | 入口（登录/菜单） | 工具执行链路的每一环 |
| 面对 AI | 拦不住（AI 不经过入口） | 拦得住（AI 每调工具都验） |

「下沉」= 把权限从「人点菜单的入口」下沉到「AI 调工具的底层」。因为干活主体从「人」变成「AI」，权限必须跟着下放到 AI 真正动作的地方。

---

## 6. 收敛结论（回写 §14.1）

1. capability = 会话启动按「用户+项目+数据范围」签发的 scope 限定临时工作证。
2. 三层拦截：工具清单过滤 → 工具执行鉴权 → MCP 端账号兜底。
3. 数据范围 = 用户有权访问的全部业务数据（项目名下数据 ∪ 接口可取数据），运行时 join `project_member` 实时算，非手动勾选。
4. 「下沉」是核心：AI 会自己挑工具还可能被诱导，权限必须下放到执行层，且三层兜底。
