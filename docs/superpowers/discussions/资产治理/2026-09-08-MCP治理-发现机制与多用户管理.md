# MCP 治理：原生发现机制与多用户管理

- **日期**：2026-09-08
- **状态**：探讨记录（收敛结论已回写总体设计 §11.7）
- **主题**：继 skill 治理之后，厘清 MCP 的原生发现机制（源码结论），并推敲「如何对不同用户管理 MCP」的三层问题，以及会话启动成本与缓存选型。
- **触发问题**：opencode 原生 MCP 发现机制是怎样的？不同用户如何管理 MCP？是否每次登录都要校验授权（会不会慢）？要不要上 Redis？

---

## 0. MCP 与 skill 的本质差异

| 维度 | skill | MCP |
|---|---|---|
| 本质 | 文件（文件夹 + `SKILL.md`） | 连接（一段连接配置） |
| 发现方式 | 扫描目录里的文件夹 | 读 `opencode.json` 的 `mcp` 列表 |
| 能力清单 | `SKILL.md` 写死的 description | 连接后 `listTools` 动态拉取 |
| 全局/局部 | 目录位置决定 | 无目录概念，只有「配置在哪个用户的 opencode.json」 |
| 治理核心 | 「放哪个目录」 | 「谁能用 / 连到哪 / 以谁的身份连」 |

**一句话**：skill 是文件，靠放对目录被发现；MCP 是连接，靠写对 `opencode.json` 里的 `mcp` 配置被发现。

## 1. opencode 原生 MCP 发现机制（源码结论）

### 1.1 配置来源：`opencode.json` 的 `mcp` 字段

MCP 定义写在配置文件里（`packages/core/src/v1/config/config.ts:113`）：

```jsonc
{
  "mcp": {
    "话单查询": { "type": "local", "command": ["npx", "mcp-server-huadang"], "environment": {} },
    "资金分析": { "type": "remote", "url": "http://.../mcp", "headers": {} }
  }
}
```

### 1.2 两种连接类型（`mcp.ts` schema）

| 类型 | 连接方式 | 字段 |
|---|---|---|
| `local`（本地进程） | `StdioClientTransport` 起子进程，stdin/stdout 通信 | `command`、`cwd`、`environment` |
| `remote`（远程服务） | `StreamableHTTPClientTransport` 或 `SSEClientTransport` 连 URL | `url`、`headers`、`oauth` |

### 1.3 发现流程（`mcp/index.ts` 的 `create`）

```
读 opencode.json 的 mcp 配置（Record<名称, 配置>）
  → 遍历每个 MCP：
      enabled === false？→ 跳过
      type === "remote"？→ connectRemote（连 URL，OAuth 可选）
      type === "local"？→ connectLocal（起子进程）
      → 连接成功 → client.listTools() 拉工具清单（McpCatalog.defs）
      → 每个工具转成 opencode 可调用的 Tool（convertTool）
  → 连接失败 → 记 warning「server unavailable」，不阻断
```

**关键**：配置里只写「怎么连」，工具清单是运行时 `listTools` 拿到的——MCP 的能力是动态问服务器要的，不是配置写死的。

## 2. MCP 多用户管理的三层

MCP 治理核心不是「放哪」，而是三个问题：

| 层 | 问题 | 落点 |
|---|---|---|
| ① 授权 | 谁能用这个 MCP | RBAC `role_resource`（resource_type=`mcp`） |
| ② 下发 | 这个 MCP 连到哪、怎么连 | 每个用户 opencode.json 的 `mcp` 段 |
| ③ 身份 | 以什么身份去连（数据隔离） | headers/environment 注入用户 ID + RLS/GRANT |

### 2.1 层①：授权（与 skill 同一套）

```
role_resource: role_id, resource_type="mcp", resource_id, perm
perm ∈ {读, 写, 审, 管}   （§11.2）
```
「授权」= 给某角色挂「读 话单MCP」这条记录。

### 2.2 层②：下发（按用户拼 opencode.json）

管理员在治理后台配 MCP，用户看不到「怎么连」细节，只看到「我能用哪些 MCP」。三级空间：

| 空间 | 落法 |
|---|---|
| 全局 MCP | 连接配置写进所有用户 opencode.json |
| 部门 MCP | 只写进该部门用户 opencode.json |
| 个人 MCP | 只写进本人 opencode.json |

与 skill 的 `skills.paths` 是同一套「按用户下发 config」机制，只是字段不同。

### 2.3 层③：身份（MCP 独有、最关键）

MCP 真连数据库/服务取数据，必须连接时带上用户身份，否则数据越权。注入方式：

| MCP 类型 | 身份注入 | 字段 |
|---|---|---|
| `remote` | HTTP 请求带 `X-User-ID` | `mcp.headers` |
| `local` | 进程 `environment` 注入 `USER_ID` | `mcp.environment` |

服务端拿到身份后做 RLS 过滤——**这正是 §14.1 capability 第三层「MCP 端账号兜底」的落点**。

数据隔离链路四环相扣：授权（谁能用）→ 下发（连到哪）→ 连接带身份（以谁的身份）→ 服务端 RLS 过滤（只能拿谁的数据）。

## 3. 会话启动成本分层（回应「登录会不会慢」）

### 3.1 登录 ≠ 会话启动

| 动作 | 成本 |
|---|---|
| 登录（Auth 发 cookie） | 极轻，毫秒级 |
| 会话启动（读 config、连 MCP、listTools、加载 skill、签发 capability） | 重，秒级 |

### 3.2 各步骤成本

| 步骤 | 耗时 | 是否瓶颈 |
|---|---|---|
| 查角色 → 算授权 | 毫秒级 | ❌ |
| 下发 config（拼 mcp 段） | 毫秒级 | ❌ |
| **连接远程 MCP + listTools** | **秒级** | ✅ 这才是 |

**结论**：权限校验（轻）每次会话都要做 + 缓存；MCP 连接（重）用复用 + 懒连接。别因担心延迟砍掉权限校验——那砍错地方了。

## 4. 缓存选型：要不要 Redis

**结论：不需要。** 以 openhive 规模（100+ 用户、并发活跃 20~30%）用「进程内 TTL Map」够。

| 判断维度 | 现状 |
|---|---|
| 缓存内容 | 角色→MCP/skill 授权映射（几条到几十条） |
| 访问频率 | 每次会话启动一次，低频 |
| 数据量 | 一个 Map 装得下 |
| 一致性 | 权限变更几分钟内生效，可短 TTL |

**上 Redis 的信号**（现在都不满足）：用户上千并发数百、需跨实例共享缓存、缓存内容大或查询慢、需分布式锁/限流/排行榜。

核心判断标准一条：**要不要「跨进程/跨机器共享缓存」。** 现在不需要。

真正的坑不是「没用 Redis」，而是「把 Redis 写死进调用方，以后换不掉」。

## 5. 预留 vs 预实现（回应「为什么不现在就按上千设计」）

| | 含义 | 现在成本 | 现在该做吗 |
|---|---|---|---|
| 预留 | 抽象成接口，留扩展点 | 几乎零 | ✅ 该做 |
| 预实现 | 真的搭重型组件（Redis/分库/微服务） | 高（现在就要运维） | ❌ 规模没到是负担 |

**正确姿势 = 接口先行**：

```ts
interface AuthCache { get/set/invalidate }
class InMemoryAuthCache implements AuthCache { /* TTL Map */ }  // 现在
class RedisAuthCache implements AuthCache { /* Redis */ }        // 以后换实现，调用方零改动
```

「为后期埋坑」的正解是「现在就埋接口」，不是「现在就上 Redis」。

**为什么不能现在按上千设计**：换 PG 违背「最小侵入、持续 merge upstream」约束（动 `sql.ts` 冲突爆炸）；多实例现在用不上反而增复杂度。规模是「一次性买断成本」，现在付收益等规模到才兑现——亏本。接口是「现在付极小成本、以后收益巨大」的期权。

真正要「现在埋」的是架构级扩展点（§6.1 水平扩展后手、§12 数据接入留接口），Redis 是实现细节，抽象掉即可。

## 6. 收敛结论（回写 §11.7）

1. MCP 是「连接」不是「文件」，从 opencode.json 的 `mcp` 段读取，连接后 `listTools` 动态拉工具。
2. MCP 多用户管理三层：授权（RBAC）→ 下发（按用户拼 config）→ 身份（headers/environment 带用户 ID + RLS 过滤）。
3. 数据隔离四环：授权 → 下发 → 连接带身份 → 服务端 RLS；身份层是 MCP 独有、接 capability 第三层。
4. 会话启动成本：权限校验毫秒级不是瓶颈，MCP 连接秒级才是；轻逻辑缓存，重连接复用+懒连接。
5. 缓存：进程内 TTL Map，不上 Redis；上 Redis 的信号是「跨进程共享缓存」。
6. 预留 vs 预实现：接口先行（`AuthCache` 接口 + 进程内实现），规模到了换实现不改调用。
