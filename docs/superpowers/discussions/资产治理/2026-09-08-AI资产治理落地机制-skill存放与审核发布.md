# AI 资产治理落地机制：skill 的存放、审核、发布

- **日期**：2026-09-08
- **状态**：探讨记录（收敛结论已回写总体设计 §11.6）
- **主题**：总体设计 §11 写了「审核/发布/上下架」这套治理动作，但没讲清它们和 opencode 原生「skill = 文件夹 + 放位置」这套物理机制怎么对应。本文逐轮澄清这个断层，收敛出可落地的映射。
- **触发问题**：skill 生成后存放在哪？提交审核提交到哪？审核是什么形式？发布到底指什么（opencode 里用 skill 要「安装到项目」，有全局/局部）？

---

## 0. 问题根源

文档 §11 的「提交审核 → 审核 → 发布」是**业务语言**，opencode 原生的「skill = 含 `SKILL.md` 的文件夹，放到能被扫描的目录即生效」是**物理机制**。两者之间缺一个翻译层：治理动作到底对应什么物理操作？

**核心结论**：治理动作 = 对 skill 文件夹做「复制/移动 + 权限控制 + 元数据状态机」。skill 文件始终是一个含 `SKILL.md` 的文件夹，躺在文件系统某处；「草稿/待审/已发布/下线」是元数据，和文件物理位置解耦但同步。

---

## 1. opencode 原生的 skill 发现机制（源码结论）

opencode 发现 skill 有 **5 个渠道**（`packages/opencode/src/skill/index.ts` 的 `discoverSkills`），按扫描顺序：

| # | 渠道 | 扫描模式 | 可见范围 |
|---|---|---|---|
| 1 | `~/.claude/skills/`、`~/.agents/skills/` | `skills/**/SKILL.md` | 全机（全局） |
| 2 | 项目链上的 `.claude/`、`.agents/` | 同上 | 该项目 |
| 3 | opencode 配置目录（`config.directories()`） | `{skill,skills}/**/SKILL.md` | 全局/项目 |
| 4 | `cfg.skills.paths` 显式指定 | `**/SKILL.md` | 按配置 |
| 5 | `cfg.skills.urls`（远程拉取到 cache） | `**/SKILL.md` | 按配置 |

其中渠道 3 的「配置目录」由 `config/paths.ts` 的 `directories()` 固定返回四个：`Global.Path.config` + 项目目录链上的 `.opencode/` + 家目录链上的 `.opencode/` + `OPENCODE_CONFIG_DIR`。

### 1.1 `Global.Path.config` 是什么

`packages/core/src/global.ts` 定义，值 = `path.join(xdgConfig, "opencode")`：

| 平台 | 最终值 |
|---|---|
| Linux | `~/.config/opencode` |
| macOS | `~/Library/Preferences/opencode` |
| Windows | `%APPDATA%\opencode` |

**关键细节**：对外暴露的 `config`（`Interface.config`）是 `Flag.OPENCODE_CONFIG_DIR ?? Path.config`，即**优先取环境变量 `OPENCODE_CONFIG_DIR`**，没设才退回 XDG 路径。而 `OPENCODE_CONFIG_DIR` 本身是个**纯环境变量**（`flag.ts:63` 直接读 `process.env["OPENCODE_CONFIG_DIR"]`），没有配置文件、没有前端界面。

### 1.2 为什么全局 skill 不用 `OPENCODE_CONFIG_DIR`

`OPENCODE_CONFIG_DIR` 不只是 skill 目录，还是 opencode **整个 `opencode.json` 的读取位置**（`config.ts:264/432`）。把它指到 `/assets/global`，等于让 opencode 去 `/assets/global/opencode.json` 读全部配置，副作用太大。

**结论：全局/部门统一走 `skills.paths`**——它语义纯净，只影响 skill 目录，不影响 config 文件位置。

## 2. 治理动作 ↔ 物理操作（翻译表）

| 治理动作（§11） | opencode 物理操作 |
|---|---|
| 提交审核 | 把 skill 文件夹从作者沙箱**复制到资产中心待审区** `/assets/pending/{name}/`，元数据登记「待审核」 |
| 审核 | 业务专家在治理后台打开待审区 skill，看内容、试跑、评可泛化性，点通过/驳回 |
| 发布 | 通过后复制到发布目录 `/assets/{global,dept}/{...}/skills/{name}/`，并让目标用户 `skills.paths` 挂上该目录 |
| 授权/启用 | 用 opencode 已有的 `Permission.evaluate("skill", name, ...)` 控制「扫到了但没授权」也用不了 |
| 下线 | 把文件夹移出发布目录（或从 paths 摘除），扫不到即失效 |

---

## 3. 发现渠道 ↔ openhive 资产层级

opencode 原生只有「机器级全局 + 项目局部」，没有「部门」这一层。openhive 要三级，映射：

| 资产层级 | 物理位置 | opencode 怎么扫到 | 要不要配 paths |
|---|---|---|---|
| 全局 | `/assets/global/skills/{name}/` | 所有用户 `skills.paths` 含该目录 | 要（统一写） |
| 部门 | `/assets/dept/{deptId}/skills/{name}/` | 该部门用户 `skills.paths` 含该目录 | 要（按部门写） |
| 个人 | 用户沙箱项目 `.opencode/skill/` | opencode 原生项目目录扫描 | 不必 |

**`skills.paths` 的真正角色**：它是唯一能「给不同用户指向不同 skill 目录」的配置项。全局和个人可以靠原生目录约定省掉，唯独「部门」这一层 opencode 没有，必须靠 paths 补齐。

## 4. 角色分工（建目录的不是 opencode）

| 角色 | 是谁 | 干什么 |
|---|---|---|
| opencode 内核 | 官方、不动 | 只**被动扫描** `skills.paths`/配置目录，加载 `SKILL.md`。不建目录、不复制、不懂「待审/发布」 |
| openhive 资产服务 | 自研 | 执行「上传→待审→发布→下线」全动作：建 `/assets` 下目录、复制文件、维护元数据状态机 |

目录用 `mkdir -p`（递归 + 已存在跳过）语义，幂等。

**关键联动**：资产服务把文件放进 `/assets/global/skills/`，opencode 不会自动知道，必须通过 `skills.paths` 让 opencode 扫得到——「文件放哪」和「opencode 扫哪」要显式对上。

---

## 5. 前端配置 ↔ 路径约定

**结论：前端只配「范围」，系统算「路径」。**

- 前端（治理后台「发布」动作）唯一要配的是：发布范围 = `全局` / `部门（选具体部门）`。
- 路径 = 资产根（默认 `/assets`）+ 约定子目录 + 业务对象（`deptId`、`name`）自动拼出。
- **不暴露路径给界面**：路径是技术细节，暴露易配错，且和权限耦合后难排查。

唯一可能需要路径配置的场景是换存储位置，放**部署层**（运维改环境变量/服务配置），不是前端。

## 6. 内网 docker 部署的挂载

`/assets` 是「共享资产层」，独立于用户隔离沙箱 `/workspaces`，单独挂一个**共享卷**，两个容器挂同一卷但权限分开：

| 挂载 | 内容 | 访问者 | 权限 |
|---|---|---|---|
| `/assets` | skill/MCP/知识库资产 | 资产服务 rw + opencode ro | 共享卷 |
| `/workspaces` | 每用户沙箱目录 | opencode rw | 持久卷 |
| `/data` | 每用户 SQLite | opencode rw | 持久卷 |
| config | `opencode.json`（含 `skills.paths`） | opencode r | ConfigMap/下发 |

`/assets` 必须资产服务和 opencode **挂同一个底层卷**，否则资产服务写进去的 skill，opencode 永远扫不到。

## 7. 「提交审核」靠什么驱动（skill 还是工具）

opencode 天生只会「改文件」，不知道「提交审核」是什么。要让它能做，必须给它**工具**（或带脚本的 skill），把业务动作翻译成可执行操作。

**结论：用 MCP 工具，不用 skill。** 区分：

| 机制 | 适合 | 例子 |
|---|---|---|
| skill | 教模型怎么分析/怎么做业务（生成内容） | 研判套路、话单分析 |
| MCP 工具 | 确定性副作用动作（调 API、复制文件、改状态） | 提交审核、发布、上下架 |

自研一个「资产治理 MCP server」，暴露 `submit_skill_for_review(skill_name)`、`list_my_skills()`、`publish_skill(name, scope)` 等工具。民警说「把 XXX skill 提交审核」→ 模型看到工具 description → 调工具 → 工具代码（不是模型猜）执行：定位沙箱 skill 源目录 → 复制到 `/assets/pending/` → 调资产服务 API 登记元数据 → 返回结果。

**为什么对**：① 动作确定性（不靠模型猜，否则复制错地方、漏登记）；② 鉴权靠 capability（§14.1，工具执行器入口只认 capability，民警只签发「提交」，管理员才签发「发布」）；③ skill/工具分工清晰——「生成 skill 的 skill」产出文件夹，「资产治理 MCP 工具」负责提交/发布。

---

## 8. 收敛结论（回写 §11.6）

1. skill 文件 = 含 `SKILL.md` 的文件夹，始终躺在文件系统某处；治理状态是元数据，与物理位置解耦同步。
2. 物理存放：`/assets/{pending,global,dept/{deptId},archive}/…`，资产服务负责建目录/复制，opencode 只扫描。
3. 发现渠道：全局/部门走 `skills.paths`（下发 config 时按用户部门自动拼），个人走项目 `.opencode/skill/`。
4. 治理动作翻译：提交审核=复制到 pending；发布=复制到 global/dept 目录 + paths 挂载；下线=移出目录；授权=Permission.evaluate。
5. 前端只配「范围」，路径系统约定；换存储位置走部署层。
6. docker：`/assets` 共享卷，资产服务 rw + opencode ro。
7. 提交/发布驱动用「资产治理 MCP 工具」，鉴权靠 capability。
