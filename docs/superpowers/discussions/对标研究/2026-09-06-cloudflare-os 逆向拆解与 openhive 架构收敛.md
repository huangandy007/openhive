# cloudflare-os 逆向拆解与 openhive 架构收敛

- **日期**：2026-09-06
- **状态**：待审阅
- **主题**：逆向拆解 cloudflare-os（一个「以成品交付为中心」的 AI 工作平台），提炼可复用规律，收敛出 openhive 的「三层架构」心智模型
- **关联文档**：`2026-08-17-openhive-design-v1.md`、`2026-08-30-前端落地策略-opencode换皮-design.md`、`2026-09-05-AI资产治理-skill-mcp-知识库管理-design.md`、`2026-09-05-公安全流程工作平台-中栏多形态内容区与交付层-design.md`、`2026-09-05-竞品差距分析-workbuddy与千问办公-design.md`

---

## 1. 结论摘要

本文回答一个核心问题：**cloudflare-os 这个优秀范例，对 openhive 到底有什么用？**

结论三点，层层收敛：

1. **cloudflare-os 最值钱的地方不是它的技术**（底层全在 Cloudflare 上，内网用不上），而是它用三个设计决策，独立印证了 openhive 竞品分析里那几个「该做但还没做」的判断是对的。
2. **它对 openhive 最大的价值**：证明了 openhive 写在纸上、但 opencode 完全没有、所以最没底的那条核心链路——「业务技能包 → 结构化结论 → 交付层」——是可行的，且给出了具体形状。
3. **最终收敛出的心智模型**：openhive 分三层——**opencode（能力内核，不动）→ skill（方法，长在 opencode 之上）→ 有形产物（成品，落回案件）**。openhive 的价值不在 opencode 内核里，而在「内核之上 + 内核边界」。

---

## 2. cloudflare-os 拆解

### 2.1 一句话：它解决了什么问题

**把「和 AI 对话」从『聊天』升级为『在隔离沙箱里生成并运行一个只属于你的私有 Web 应用』——Agent 的产物是一个可复用、可分享、被沙箱隔离的「成品」，而不是一段文字。**

### 2.2 它为什么有效（三个互相咬合的设计决策）

| 决策 | 内容 |
|---|---|
| A | Agent 的产物是**一等公民的成品**（gadget），不是消息流 |
| B | 用「**模板(Blueprint)/实例(Gadget) 分离**」同时买到复用与隔离 |
| C | 用「**能力授权(Gatekeeper)**」而不是「角色权限表」管 Agent 对外部服务的访问 |

OS 隐喻贯穿全系统（kernel / shell / drivers / processes / executables），且代码结构 1:1 对应隐喻——这不是修辞，是「命名即架构」。

### 2.3 它的完成标准

- **单元层**：一次 agent 交互的「done」= 产出**一个能在沙箱里跑起来、被持久化、可再次打开**的 gadget——而不是「AI 回了一段话」。
- **系统层**：从「一句话」到「可运行成品」，用户**全程零人工工程介入**。

---

## 3. 对 openhive 最有用的价值

**cloudflare-os 用「模板/实例分离 + 产物即成品」这两个绑死在一起的结构，把 openhive 写在纸上、但 opencode 完全没有、所以最没底的那条链路——「业务技能包 → 结构化结论 → 交付层」——变成了一个已经跑通的参照物。**

它压在 openhive 三个最没底的 P0 上：

| 困境 | cloudflare-os 如何解 |
|---|---|
| ① 范式纠偏（民警不写代码，却拿着 opencode 换皮） | 证明「AI 工作平台的价值载体可以是成品，不是代码编辑器」 |
| ② 交付层（opencode 无「成品」概念，只能凭空设计） | 把「模板 + 结构化填充」生成链路跑通，模板/实例分离正是「技能包/案件」的结构 |
| ③ 护城河（担心「分析记录→skill→复用」是伪需求） | Blueprint（可分享模板）证明「一次好的产出→可复用模板」能形成飞轮 |

## 4. openhive 三层架构心智模型（核心收敛）

这是本文最重要的结论。openhive 分三层：

```
opencode = harness（能力内核，让大模型能持续正确干活）   → 不动
skill    = 方法（教 AI 怎么做事，含"先厘清再分析"）       → 全部长在 opencode 之上
产物     = 成品（五类：文档/表格/演示/图/分析记录）        → 落回案件、可重新打开、留痕
```

### 4.1 第一层：opencode（能力内核）—— 不变

opencode 的本质是**「让大模型持续正确工作的一套 harness 工程」**——agent 循环、上下文管理、工具调度、会话状态、模型调用。这是最难、最不可见、最不该重造的部分。openhive 的复用价值和「持续 merge upstream」都押在它身上。

**但「内核不变」≠「opencode 零改动」。** 边界横切三处必改（多租户 spec 已定）：

| 必改点 | 位置 | 为什么 |
|---|---|---|
| ① 用户中间件 | 请求入口 | X-User-ID → 锚定沙箱 + 路由每用户 db |
| ② Database 按用户路由 | database.ts | 全局单例 → Map<userId, 连接>（唯一深改 core） |
| ③ 工具执行守卫 | 工具 dispatch 入口 | capability / RBAC 下沉执行层 |

### 4.2 第二层：skill（方法）—— 长在 opencode 之上

skill = 「教 AI 怎么做事」。业务技能包、研判记录、类案对照全部落地为 opencode 原生 skill，靠 skill 的 `description` 自主触发。

**触发方式（勿滑向硬钩子）**：软触发为主（description + prompt 约定「该调时调」）+ 关键节点显式提醒（点「生成图谱」「结束会话」时主动触发），不追求硬事件钩子。

**skill 的制作主体（命门）**：内容源头 = 业务骨干 / 老民警；加速器 = AI 反向生成（分析记录→skill）；兜底 = IT（技术型 skill + 技术合规）；审核权 = 业务专家（审内容正确性），与 IT 审技术分离。

### 4.3 第三层：有形产物（成品）—— 五类，落回案件

opencode 的产物天生是「改文件」，openhive 要的是「交付物」。这不是「改 opencode」能解决的，只能在 opencode 之上补。

**五类产物（别漏第五类）**：

| 类别 | 形态 | 说明 |
|---|---|---|
| 交付物 | 文档 docx | 研判报告、公文、方案、文书 |
| 交付物 | 表格 xlsx | 统计报表 |
| 交付物 | 演示 pptx | 方案汇报 |
| 交付物 | 图（图谱/图表） | 关系图谱、资金流向图、时序图 |
| **过程资产** | **分析记录** | 分析思路 + 分析结论（一等公民，护城河落点） |

**完成判据**：一次 AI 研判交互的「完成」= 一个交付物已落回案件空间、可重新打开、git 留痕；否则就是「本轮未交付」。

## 5. 必须钉死的几个点（防滑回 / 纠正记录）

> 本节是前面对话中对「我的理解」做过的**纠正记录**——凡纠正过的地方最易随时间遗忘，故单独钉死在此。每行左边是易滑回的说法，右边是纠正后的正确说法。

| # | 易滑回的说法 | 纠正后的正确说法 |
|---|---|---|
| 1 | opencode 完全不动 | 内核不动，边界三处必改（中间件 / db 路由 / 执行守卫） |
| 2 | skill 自动触发 | 软触发 + 关键节点显式提醒，不做硬钩子 |
| 3 | 四类产物 | 五类产物，含「分析记录」（过程资产，护城河） |
| 4 | 用户「下载安装」skills | 「启用 = 授权 + 加入可用清单」，不是复制代码 |
| 5 | IT 封装 skills | 业务专家是内容源头，AI 反向生成加速，IT 只兜底技术 |
| 6 | 先厘清需求再调 skill | 需求厘清主要长在 skill 内部（skill 第一步即厘清输入/目标） |
| 7 | 交付层靠「改 opencode」加出来 | 「成品」概念 opencode 天生没有、改不出来；只能在 opencode 之上用 skill 补（是「缺」不是「变」） |
| 8 | 全流程 8 个环节一次铺满 | 全流程梳理眼界要对，但落地分期——先研判，再横向复制邻近环节 |
| 9 | 审核走 IT 一道关 | 审核权在业务专家（审「套路对不对、结论可不可信」），IT 只审技术合规，两者分离 |

关于第 6 点补充：用户需求表达不清是真实问题（尤其非技术用户）。但「厘清需求」不是 skill 之外独立的前置环节，而是**内嵌进每个业务 skill 的开头步骤**；「不断沉淀厘清需求」和已有的「分析记录」能力是同一条链——模糊需求最终固化为结构化分析结论，那才是「需求被厘清」的落点。

## 6. 可复用规律（5 条）

1. **产物即完成**：每个 AI 交互的终点是「一个能重新打开、落库留痕的成品」，不是「对话回合结束」。
2. **模板 / 实例分离**：共享的「怎么做」（模板/技能包/交付模板）与私有的「我这一份」（实例/案件/具体产物）必须是系统级的两类实体。
3. **私有默认，分享显式**：多用户 AI 的安全姿态是「出生即隔离」，共享是显式、有边界的动作。
4. **Agent 是被授权主体，授权下沉执行层**：每次会话签发 scope 限定的 capability，工具执行器只认 capability，不认角色表、也不靠提示词。
5. **注册式扩展替代改造式扩展**：加模块/视图/资产/数据源 = 注册一条，框架零改动；一条统一抽象让注册制跑得起来。

## 7. 可执行操作清单

- [ ] 1. 立「产物即完成」为第一验收标准：把生成链路终点「生成→预览→存回案件」提升为所有 AI 交互的统一完成判定；本轮不产成品则明示「本轮无交付物」。
- [ ] 2. 在代码里把「模板/实例」落成两个明确类型：业务技能包、交付层模板、报告模板归「模板类」；案件、具体产物、分析记录归「实例类」。禁止混用一个实体。
- [ ] 3. 把 §12.1「运行时三层拦截」升级为 capability 模型：会话启动时按「用户 + 案件 + 勾选数据范围」签发 scope 限定的 capability，执行器入口只认 capability。
- [ ] 4. 统一扩展点为「注册表」：中栏视图、工作区、AI 资产（Skill/MCP/知识库）全部「注册=新增，框架零改动」。
- [ ] 5. 模型配置抽象成 provider 列表 + openai-compatible 兜底：多单位路由统一走一个 openai-compatible 网关入口，新增单位 = 网关加一条路由 + 配额。
- [ ] 6. 用一个最小 demo 跑通「agent 出成品」闭环：让 AI 从勾选话单数据生成一份 docx 研判报告并落回案件、可重新打开、git 留痕。这条通了 P0 交付层才成立。
- [ ] 7. 边界自查：面向民警的界面/介绍页只出现「案件/研判/报告」业务语言；OS 隐喻、capability 等词只出现在内部架构文档。

## 8. 边界（不可迁移 / 救不了你的部分）

1. **Cloudflare 技术栈**：Workers / Durable Objects / Dynamic Workers / Facets 全部不可用（内网私有化）。能迁移的是「serverless + 每用户状态隔离 + 沙箱执行」的概念，不是技术。
2. **「成品闭环廉价到默认发生」的工程**：cloudflare-os 靠 serverless 把「部署=运行时」吞掉；openhive 要自建 docx 生成、图谱渲染、对象存储落库，这块它帮不上。
3. **公安业务知识的内容**：Blueprint 证明的是「模板复用能形成飞轮」这个机制，不是「话单关系分析怎么做」这个内容。护城河的内容只能靠老民警输入。
4. **面向业务人员的界面**：OS 隐喻和 builder 心智是给开发者的，界面必须用业务语言重新设计。
