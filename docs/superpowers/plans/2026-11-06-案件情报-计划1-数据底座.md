# 案件知识与情报体系 · 计划 1：数据底座 实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把设计稿里的事实层落成 PostgreSQL 真表，并给出 `parse_status` 状态机与可测试的 DAO —— 后续 6 份计划（导入通路、左栏、harness、纠错、MCP、视图）全部踩在这层上。

**Architecture:** 9 张表进现有 `auth` schema（前缀 `case_`），走现有迁移运行器（`packages/auth/src/migrate.ts`）；`case_fact_row` 用 `HASH (project_id)` 16 分区，避免每建一个项目就要跑一次 DDL。状态机写成纯函数（不碰库）；DAO 只认 `{ execute(sql) }` 这一最小形状，于是生产 `bun-sql` 与 PGlite 用同一份实现。

**Tech Stack:** PostgreSQL / Drizzle ORM 1.0.0-rc.2 / Bun 1.4.2 / PGlite（经 `@opencode-ai/auth/test-support`）/ `@opencode-ai/auth` 迁移运行器。

**Spec:** `docs/superpowers/specs/2026-11-05-案件知识与情报体系/design.md`（§4.2 事实层、§5.2 处理状态、§9.1 可信状态）

## Global Constraints

- **项目隔离走应用层，不引入 RLS**（用户 2026-11-06 裁定）。所有 DAO 函数**必须**把 `project_id` 放进 `WHERE`；**`project_id` 必须出现在每张新表的主键里**（不要求代理 id —— `case_fact_row` 刻意用自然键 `(project_id, material_id, sheet, row_no)`）—— 不给「只按 id 查」的入口。
- **仓库里现有迁移一条 RLS 都没有**（`grep -rni "row level security\|create policy" packages/auth/src/migrations/` 输出为空）。本计划不打破这个现状。
- 迁移文件：`packages/auth/src/migrations/NNNN_name.sql` ＋ 同名 `.down.sql`；编号 **0031**；语句分隔符 **`--> statement-breakpoint`**（单独成行、前后空行）。
- **整轮迁移跑在一个事务里** ⇒ 不许出现 `CREATE INDEX CONCURRENTLY`（会报 `25001` 并让整轮失败，见 `migrations/README.md` 第 1 条）。
- 表一律建在 schema `auth` 下，**前缀 `case_`**（与 `auth.asset_*` / `auth.project_*` 同风格）。
- 时间列一律 `integer` **Unix 秒**（与 `packages/auth/src/time.ts` 的 `nowSeconds()` 同口径，别用 `timestamptz`）。
- 金额列 `numeric(18,2)` —— **JS 侧读出来是 string**，断言必须拿 string 比。
- **测试只许在受影响 package 内跑**：`cd packages/opencode && bun test test/server/<file>`。根目录 `bun test` 被 scripts 强制 `exit 1`。
- **`packages/opencode` 没有 `@electric-sql/pglite` 依赖。** 本包侧起 PG 夹具**只有一条路**：`startProductionDb()`（`@opencode-ai/auth/test-support`，真 PGlite socket ＋ 真 `connect()`），配 `await migrate(pg.db)`。测试里**不许** `import { PGlite } from "@electric-sql/pglite"`。
- 设计稿里的逻辑表名 → 物理表名：`material`→`auth.case_material`、`entity`→`auth.case_entity`、`relation`→`auth.case_relation`、`event`→`auth.case_event`、`citation`→`auth.case_citation`、`fact_row`→`auth.case_fact_row`、`ingest_job`→`auth.case_ingest_job`、`alert`→`auth.case_alert`、`ai_proposal`→`auth.case_ai_proposal`。

/** 夹具一定在（`beforeAll` 之后）。 */
function db() {
  if (!pg) throw new Error("真库没起来")
  return pg.db
}

/**
 * 跑一条**预期会被拒**的语句，用布尔说结果。
 *
 * 不写 `expect(...).rejects.toThrow()`：drizzle 的 `execute()` 是**懒 thenable**，不 await 不真执行
 * （`packages/auth/src/migrate.test.ts` 顶上那条注释就是这么来的）。先 await 再判，
 * 驱动是懒是急都不影响结论。
 */
async function 被拒(query: PromiseLike<unknown>): Promise<boolean> {
  try {
    await query
    return false
  } catch {
    return true
  }
}

```ts
/**
 * 材料的处理状态机（设计 §5.2 / §8.1）。
 *
 * 纯函数、不碰库：状态规则是**产品规则**，不该被埋在 SQL 里。DAO 只负责
 * 「读当前状态 → 问这里 → 带并发条件写回」。
 *
 * ## 为什么「取消」有两个落点
 *
 * - 排队中取消 ⇒ 回「未入队」：一片都没跑，等于没发生。
 * - 解析中取消 ⇒ 落「有问题」：**已提交的切片要保留**（设计 §8.1）。当成没跑过的话，
 *   下次重解析会在已有事实之上再叠一遍，用户看到的是「取消过的东西又冒出来了」。
 */
export const PARSE_STATUSES = ["未入队", "排队中", "解析中", "已解析", "有问题", "已跳过"] as const
export type ParseStatus = (typeof PARSE_STATUSES)[number]

export const PARSE_ACTIONS = ["入队", "开始", "完成", "出问题", "取消", "跳过", "重新解析"] as const
export type ParseAction = (typeof PARSE_ACTIONS)[number]

const TRANSITIONS: Record<ParseStatus, Partial<Record<ParseAction, ParseStatus>>> = {
  未入队: { 入队: "排队中", 跳过: "已跳过" },
  排队中: { 开始: "解析中", 取消: "未入队" },
  解析中: { 完成: "已解析", 出问题: "有问题", 取消: "有问题" },
  已解析: { 重新解析: "排队中" },
  有问题: { 重新解析: "排队中", 跳过: "已跳过" },
  已跳过: { 入队: "排队中" },
}

/** 这一步合不合法。不合法返回 `undefined` —— 调用点自己决定是抛错还是忽略。 */
export function nextStatus(from: ParseStatus, action: ParseAction): ParseStatus | undefined {
  return TRANSITIONS[from]?.[action]
}

/** 是否占着队列：这两种状态下的文件，「解析入库」不该亮（设计 §8.1）。 */
export function isRunning(status: ParseStatus): boolean {
  return status === "排队中" || status === "解析中"
}
```

 *
 * ## 为什么只吃 `{ execute(sql) }`
 *
 * 生产是 `bun-sql` 的 `connect()`，测试是 PGlite 撑起来的同一个驱动 —— 但**不该让 DAO

export interface Queryable {
  execute(query: SQL): PromiseLike<unknown>

export interface MaterialRow {
  id: string
  projectId: string
  fileName: string
  kind: string
  fingerprint: string
  path: string
  parseStatus: ParseStatus
  parseDetail: unknown
  queuedBy: string | null
  clockOffsetSec: number

/**
 * 建档。**幂等键是 (project_id, fingerprint)**，冲突时返回**已存在那行的 id**
 * （不是传进来的 id）—— 后续明细行 / 引用都拿这个 id，重拖同一个文件才不会分裂成两份。
 */
export async function createMaterial(db: Queryable, input: CreateMaterialInput): Promise<string> {
  const rows = rowsOf(
    await db.execute(sql`
      insert into auth.case_material (id, project_id, file_name, kind, fingerprint, path, created_at)
      values (${input.id}, ${input.projectId}, ${input.fileName}, ${input.kind},
              ${input.fingerprint}, ${input.path}, ${nowSeconds()})
      on conflict (project_id, fingerprint)
        do update set file_name = excluded.file_name, path = excluded.path
      returning id
    `),
  )
  const id = rows[0]?.id
  if (typeof id !== "string") throw new Error(`建材料没有拿到 id：${JSON.stringify(rows[0])}`)
  return id
}

export async function getMaterial(
  db: Queryable,
  projectId: string,
  materialId: string,
): Promise<MaterialRow | undefined> {
  const rows = rowsOf(
    await db.execute(sql`
      select id, project_id, file_name, kind, fingerprint, path, parse_status,
             parse_detail, queued_by, clock_offset_sec
      from auth.case_material
      where project_id = ${projectId} and id = ${materialId}
    `),
  )
  const row = rows[0]
  if (!row) return undefined
  return {
    id: String(row.id),
    projectId: String(row.project_id),
    fileName: String(row.file_name),
    kind: String(row.kind),
    fingerprint: String(row.fingerprint),
    path: String(row.path),
    parseStatus: String(row.parse_status) as ParseStatus,
    parseDetail: row.parse_detail,
    queuedBy: row.queued_by == null ? null : String(row.queued_by),
    clockOffsetSec: Number(row.clock_offset_sec),
  }
}

export interface ApplyParseActionInput {
  projectId: string
  materialId: string
  action: ParseAction
  /** 人工触发时的操作人（设计 §8.1「记谁让它入队的」）。 */
  by?: string
  /** 「有问题」的原因明细，原样落 `parse_detail`。 */
  detail?: unknown
}

/**
 * 推进状态。
 *
 * 两条保护都写在这**一条 UPDATE** 里（不许拆成两条语句：状态改了、明细没落，
 * 就成了一条说不出原因的黄三角）：
 *
 * 1. **乐观并发**：带 `parse_status = 当前值`。两个作业同时推进时后到的更新 0 行 ⇒ 抛错，
 *    而不是把对方的结论盖掉。READ COMMITTED 下 PG 会在等锁后重判 WHERE（`migrations/README.md`）。
 * 2. **明细只在给了的时候才覆盖**：`detail` 不传就保留原值，不会被顺手清空。
 */
export async function applyParseAction(
  db: Queryable,
  input: ApplyParseActionInput,
): Promise<ParseStatus> {
  const current = await getMaterial(db, input.projectId, input.materialId)
  if (!current) throw new Error(`material not found: ${input.projectId}/${input.materialId}`)

  const next = nextStatus(current.parseStatus, input.action)
  if (!next) throw new Error(`illegal transition: ${current.parseStatus} --${input.action}--> ?`)

  const 入队 = input.action === "入队"
  const 有明细 = input.detail !== undefined
  const 明细 = 有明细 ? JSON.stringify(input.detail) : null

  const rows = rowsOf(
    await db.execute(sql`
      update auth.case_material
         set parse_status = ${next},
             queued_by    = case when ${入队} then ${input.by ?? null} else queued_by end,
             parse_detail = case when ${有明细} then ${明细}::jsonb else parse_detail end
       where project_id = ${input.projectId}
         and id = ${input.materialId}
         and parse_status = ${current.parseStatus}
      returning id
    `),
  )
  if (rows.length === 0) throw new Error("状态已被别的作业改掉（并发保护）")
  return next
}

export interface FactRowInput {
  projectId: string
  materialId: string
  sheet: string
  rowNo: number
  caller?: string | null
  callee?: string | null
  startedAt?: number | null
  durationSec?: number | null
  /** numeric 列：JS 侧一律用 string 传，别用 number（`#002-01`：随驱动而变的形状）。 */
  amount?: string | null
  balance?: string | null
  counterparty?: string | null
  extras?: Record<string, unknown>
}

/**
 * 批量写明细行。**一条一条发、不用多值 INSERT**：本计划只保证正确的幂等与隔离，
 * 批量化（`COPY` / 多值 VALUES）留给计划 2 的量级任务（设计 §6.5）。
 *
 * 幂等键就是主键 `(project_id, material_id, sheet, row_no)`：重复导入同一个文件时
 * `on conflict do nothing` 把老行吃掉，返回的写入数因此会少。返回值是「**实际新写入**」的条数，
 * 不是入参长度 —— 调用点据此判断「这次有没有新东西」。
 */
export async function insertFactRows(db: Queryable, rows: FactRowInput[]): Promise<number> {
  let written = 0
  for (const row of rows) {
    const result = rowsOf(
      await db.execute(sql`
        insert into auth.case_fact_row
          (project_id, material_id, sheet, row_no, caller, callee, started_at,
           duration_sec, amount, balance, counterparty, extras)
        values (${row.projectId}, ${row.materialId}, ${row.sheet}, ${row.rowNo},
                ${row.caller ?? null}, ${row.callee ?? null}, ${row.startedAt ?? null},
                ${row.durationSec ?? null}, ${row.amount ?? null}, ${row.balance ?? null},
                ${row.counterparty ?? null}, ${JSON.stringify(row.extras ?? {})}::jsonb)
        on conflict (project_id, material_id, sheet, row_no) do nothing
        returning row_no
      `),
    )
    written += result.length
  }
  return written
}

export async function countFactRows(db: Queryable, projectId: string): Promise<number> {
  const rows = rowsOf(
    await db.execute(sql`
      select count(*)::int as n from auth.case_fact_row where project_id = ${projectId}
    `),
  )
  return Number(rows[0]?.n ?? 0)
}
