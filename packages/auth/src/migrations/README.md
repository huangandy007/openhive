# 迁移文件的写法约束

**写新迁移之前先读这页。** 运行器是 `../migrate.ts`，它的设计约束有几条**落在文件这一侧**——
写错了不会在评审里被发现，只会在**跑到一半时**炸，所以写在这里。

> 本文件**不是迁移**：`upFiles()` 只认 `*.sql`（且排除 `*.down.sql`），`.md` 会被直接跳过。
> 放在这个目录里，是因为**下一个写迁移的人会打开这个目录**——写在 `tasks.md` 或
> `state.md` 里等于没写（那些文件在 feature 收尾后就冻结了）。

## 1. `CREATE INDEX CONCURRENTLY` **不能写**（2026-10-02 审查 R-15 登记）

`migrate()` 把**整轮迁移包在一个事务里**（T021，治的是 002 评审 I4「改了库、没记账」）。
代价是一条硬约束：

- `CREATE INDEX CONCURRENTLY` / `DROP INDEX CONCURRENTLY` **不允许在事务块里执行**，
  硬写会报 **`25001`**（`CREATE INDEX CONCURRENTLY cannot run inside a transaction block`），
  而且**整轮迁移一起失败**——不是只坏那一个文件。
- 这条约束**此前没有任何一处写过**（取数，**输出应为空**：`grep -rn "CONCURRENTLY" packages/auth/src/migrations/*.sql packages/auth/src/migrate.ts`
  ——⚠️ 别搜整个 `packages/auth/src`，**本页自己就会命中**）。所以它在 2026-10-02 的代码审查里
  被记为缺口 **R-15**，落点就是这一页。

**那大表要建索引怎么办**：`CONCURRENTLY` 的意义是「建索引时不长时间锁表」。真到需要它的规模时，
它**不属于迁移**——按部署侧的一次手工 / 一次性脚本处理（在事务外单独跑），
并在部署记录里留下痕迹。**不要**为了它去改 `migrate()` 的事务语义：那会退回
「中途失败留下改了库、没记账」，那正是这类结构要挡的东西。

## 2. 语句分隔符是 `--> statement-breakpoint`

运行器按这个分隔符切分、**逐条**执行（多语句一次性下发在各驱动上不可移植）。
分隔符**必须单独成行**，前后留空行。

## 3. 整轮一个事务 ⇒ 自幂等**不再是运行器的依赖**（但也不是放开写非幂等）

第二代运行器中途失败是**整轮回滚**，所以重试是在干净状态上重跑。
⚠️ 已知还留着半边的正是 `rollback()`：它仍是「先跑 down、后删记账」，
中途失败同样会留下「改了库、没记账」（见 003 `state.md` 缺口表）。

## 4. 并发正确性依赖服务端的默认隔离级别 = `READ COMMITTED`

`migrate()` 的推理（advisory 锁 + 整轮一个事务 ⇒ 等锁的 runner 拿到锁后读到**新账**）
建立在 `READ COMMITTED` 上——每条语句取新快照，而「读账」排在等锁之后。
**代码不设置它、也不校验它**，只是把「PG 默认是 READ COMMITTED」当作前提写在 `migrate()` 的注释里。

⇒ 部署侧必须显式保证（`deploy-todo.md` **D-12**，来源 = 2026-10-02 审查 A3 · **R-16**）。
若服务端默认被改成 `REPEATABLE READ` / `SERIALIZABLE`，行为**不再是同一条推理**，
最坏是可串行化失败导致迁移整轮重跑。

## 5. 别改 `migrate.ts` 里的 `MIGRATION_LOCK_KEY`

它专属于本用途（advisory 锁的命名空间是**整个数据库**）。改了之后，
**旧版 runner 与新版 runner 会各自持一把不同的锁**，互斥就没了——
而且这种失败是静默的：两边都「成功」，只是不再互斥。
